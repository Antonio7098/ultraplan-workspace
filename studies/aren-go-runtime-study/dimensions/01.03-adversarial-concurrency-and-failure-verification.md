# 01.03 Adversarial Concurrency and Failure Verification

Roadmap priority 3. Verification is a Phase 1 acceptance concern and remains a gate for every later slice.

## Purpose

Find repeatable Go techniques for proving invariants under races, panics, partial writes, restarts, resource exhaustion, and scheduling variation instead of relying on happy-path unit tests.

## Steps

- Inventory race-detector, stress, fuzz, fault-injection, leak, metamorphic, and crash-recovery suites.
- Map each test technique to the invariant it is intended to falsify.
- Inspect test seams for clocks, transports, storage, schedulers, process runners, and randomness.
- Check whether failures are deterministic enough to reproduce and diagnose.
- Identify expensive suites that are separated from fast presubmit tests and how they are gated.

- Which concurrency failures would ordinary coverage miss?
- Can the suite force cancellation at every lifecycle boundary?
- How does it prove absence of duplicate terminal events, leaks, and partial commits?
- Which techniques are proportionate for Aren Phase 1 rather than infrastructure-scale theatre?
