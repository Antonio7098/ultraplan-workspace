# 01.13 Daemon, Local API, and Multi-Client Lifetime

Roadmap priority 13. Covers Phases 14 and 15 only when work must outlive clients or share durable inventory and resource control.

## Purpose

Compare long-lived Go server ownership, loopback or socket APIs, explicit workspace context, client detach and reconnect, graceful shutdown, versioning, and thin multi-language client contracts.

## Steps

- Identify the process that owns accepted work and what happens when the submitting client exits.
- Trace local transport setup, caller authentication, protocol versioning, request identity, and workspace scoping.
- Inspect attach, detach, stream reconnect, status recovery, and cancellation from a second client.
- Follow startup, signal handling, graceful drain, forced shutdown, restart, and upgrade paths.
- Separate stable wire contracts from server-internal Go types and implementation details.

## Questions

- Does client exit affect the accepted run?
- Can another client find and observe the same run without sharing process memory?
- How are local callers authenticated and workspaces identified?
- What is the smallest stable contract a non-Go client must implement?
