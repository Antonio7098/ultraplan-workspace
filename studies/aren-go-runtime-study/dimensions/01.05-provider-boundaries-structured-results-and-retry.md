# 01.05 Provider Boundaries, Structured Results, and Retry

Roadmap priority 5. Covers Aren Phases 3 through 6 without allowing provider SDK details to leak into the lifecycle core.

## Purpose

Compare provider-neutral Go boundaries for live model requests, stream normalization, usage accounting, structured-output enforcement, validation, retry classification, backoff, and bounded repair.

## Steps

- Trace one request through provider selection, request translation, transport, stream decoding, validation, and final result.
- Identify the neutral event and error vocabulary and every provider-specific escape hatch.
- Inspect structured-output requests, schema conversion, parse and validation failures, and repair prompts.
- Distinguish transport retry, provider retry, validation repair, and user cancellation.
- Check deadlines, rate limits, retry budgets, jitter, usage data, and partial-output handling.

## Questions

- Is the provider interface shaped by Aren semantics or by one vendor SDK?
- Can a successful HTTP status still produce a typed execution failure?
- Which failures are safe to retry, and who owns the attempt budget?
- Are token usage and partial output preserved when a stream fails late?
