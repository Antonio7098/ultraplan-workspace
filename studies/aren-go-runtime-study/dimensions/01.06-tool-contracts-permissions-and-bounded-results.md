# 01.06 Tool Contracts, Permissions, and Bounded Results

Roadmap priority 6. Covers Phase 7 representation and the Phase 8 rule that permission must be decided before a governed effect starts.

## Purpose

Study Go tool registries and invocation paths that validate model-selected calls, decide permission before effects, preserve typed failures, and bound or externalise large results without corrupting the conversation.

## Steps

- Trace tool discovery, schema exposure, call parsing, argument validation, selection, permission, execution, and result assembly.
- Check duplicate names, unknown tools, schema mismatch, malformed model output, and provider-specific call identifiers.
- Identify the exact point at which policy is decided relative to side effects.
- Inspect result size limits, truncation markers, artifact references, secret redaction, and binary content.
- Examine MCP or plugin lifecycle without assuming that protocol support proves safe execution.

- Aren Phases 7-8: ../../../../Aren/docs/phased-roadmap.md

- Tool interfaces, registries, JSON schema conversion, permission hooks, and result types.
- Tests proving denied calls have no side effect and oversized output remains explicit.

## Questions

- Can malformed or ambiguous arguments reach a tool implementation?
- Is permission checked before process start, network access, or filesystem mutation?
- How are large results represented without silently discarding evidence?
- Does the abstraction preserve tool-specific semantics or flatten them into strings?
