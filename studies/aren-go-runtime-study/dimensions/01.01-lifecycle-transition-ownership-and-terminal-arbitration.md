# 01.01 Lifecycle Transition Ownership and Terminal Arbitration

Roadmap priority 1. Supports Aren Phase 1 before any provider, tool, persistence, or daemon design is allowed to broaden the core.

## Purpose

Determine how elite Go code gives one component authority to commit lifecycle state, timing, event, and outcome coherently, while keeping work errors, runtime failures, panics, and cancellation races distinct.

## Steps

- Trace the complete path from run creation through running and terminal publication.
- Identify the single owner or gate for terminal transitions and every competing terminal producer.
- Check whether state, outcome, timing, and terminal notification become visible as one coherent commit.
- Inspect how panics and ordinary returned errors cross goroutine or task boundaries.
- Record abstractions that are smaller than Aren's contract as well as abstractions that would over-generalise it.

## Questions

- Can two goroutines publish conflicting terminal outcomes, and what prevents it?
- Is a cancellation request represented separately from confirmed termination?
- Can observers see a terminal state before its outcome or terminal event is available?
- Which parts can Aren adopt without importing a framework-sized lifecycle model?
