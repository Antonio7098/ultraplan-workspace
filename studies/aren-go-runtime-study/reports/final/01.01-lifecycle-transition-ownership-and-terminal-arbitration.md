## Executive Summary

Three Go systems at three different scales answer the same question — who is allowed to commit a terminal transition, and how do state, outcome, timing, and notification become visible as one coherent fact? — with three different mechanisms, yet converge on the same core discipline.

conc, a scoped-concurrency library, eliminates lifecycle states entirely: ownership is structural, and the owner's `Wait()` call is the single commit point where all outcomes publish together (`sources/conc/waitgroup.go:38-43`). crush, an interactive coding agent, keeps state implicit in concurrent maps but funnels every terminal publication through one emit path guarded by layered exactly-once dedup (`internal/agent/agent.go:539-548`, `internal/agent/run_marker.go:31-52`). Temporal's SDK builds the only explicit state machine of the three, with enumerated command states that panic on illegal transitions, one completion slot, and one arbitration function that emits at most one close command (`internal/internal_command_state_machine.go:183-196`, `internal/internal_task_handlers.go:1884-1958`).

Despite these differences, all three sources independently arrive at four convergent properties: (1) terminal publication passes through exactly one choke point; (2) cancellation request and confirmed termination are distinct representations; (3) panics are normalized into their own channel or typed error at goroutine boundaries — crush being the instructive exception, where panics escape `sessionAgent.Run` un-recovered; and (4) outcome recording is ordered before cascading notification so observers never see an effect ahead of its cause.

For Aren Phase 1, the transferable core is small: a funnel (one completion slot + one arbitration function, ~100 lines in temporal), a first-write-wins guard on the slot, separate cancel-request/confirmed-termination representations including cancel-in-flight states, panic normalization at every goroutine boundary, and the ordering rule "record causal outcome before triggering cancellation." What must NOT be imported is the framework bulk each source grew around its mechanism: temporal's replay machinery (~1700 lines of state machine plus event-ID arithmetic), crush's queue-fold topology shaped around its CLI client, conc's six-type pool taxonomy.

One caveat applies to every comparison here: all three source analyses report that the cited Aren requirement documents were inaccessible from the study sandbox, so alignment claims rest on the dimension text alone, not the PRD.

## Core Thesis

**Terminal coherence is not achieved by a lock; it is achieved by a funnel plus a decision about when publication happens.** Every source that answers the dimension's questions well converges on the same shape regardless of whether it has a state machine: many producers may *determine* a terminal outcome, but exactly one narrow component *commits* it, the commit carries state/outcome/notification together (or explicitly defers them together), and competing outcomes are resolved by a deterministic rule rather than a race.

The three sources then diverge on exactly one axis that Aren must choose deliberately: **where the commit point sits relative to observation.**

- conc commits at a synchronous barrier (`Wait()`), buying perfect coherence at the cost of zero intra-run visibility (`sources/conc/waitgroup.go:36-43`; collectors have no public accessors mid-run, enforced by a `TryLock` panic in `collect`, `sources/conc/pool/result_pool.go:122-126`).
- Temporal defers publication to a batch boundary: everything leaves in one RPC, so external observers see state and outcome atomically in history, while local memory can briefly say "completed" before confirmation lands (`internal/internal_task_handlers.go:1427-1472`, caveat at 1232-1234).
- crush publishes immediately but engineers ordering around it: flush-before-publish plus an event embedding the final text as a reconciliation backstop for out-of-order subscribers (`internal/agent/agent.go:735-781`).

Aren's contract — state, outcome, timing, and notification committed coherently by one owner — sits closest to what all three demonstrate, and none of them requires importing more than a few hundred lines to obtain.

## Approach Models

**conc — "commit-at-Wait" scoped ownership.** There is no running/failed/canceled enum anywhere. A run exists only between the first `Go()` and the return of `Wait()`. The owner primitive pairs a `sync.WaitGroup` with a panic catcher (`sources/conc/waitgroup.go:22-34`); `Wait()` is simultaneously the timing barrier, the outcome reader, and the notification dispatcher. Coherence is bought with total loss of intra-run visibility — partial errors and results accumulate in private collectors with no public accessors during flight (`sources/conc/pool/error_pool.go:21-22`), and premature collection is converted into a programming-error crash via a defensive `TryLock` assertion (`sources/conc/pool/result_pool.go:124-126`). This model fits when callers are synchronous and nobody else is watching.

**crush — implicit state with a guard chain.** "Running" is presence in an `activeRequests` map; "dispatched-but-not-active" is a counter; "pending cancel" is a monotonic-sequence high-water mark (`internal/agent/agent.go:185,192-197,198-206`). Nothing is persisted; durable history lives only in message `FinishReason`s. Terminal publication funnels through `publishRunComplete`, reached from four producers each prevented from double-firing by different local guards: a recursion flag, a coalescing closure, and an atomic context marker (`internal/agent/agent.go:539-548`, `1282-1325`; `internal/agent/coordinator.go:281-336`; `internal/backend/agent.go:109-121`). This model fits a long-lived interactive process where restart semantics are deferred and users prefer queueing over rejection.

**temporal-sdk-go — enumerated machine behind a funnel.** Two layers: a per-operation command state machine with 12 states where illegal transitions panic immediately (TMPRL1100, `internal/internal_command_state_machine.go:183-196,500-507`), and a workflow-level completion slot written only by the root coroutine's dispatcher, which is the sole caller of `Complete` (`internal/internal_workflow.go:555-557,692-734`). Publication is further deferred: commands, protocol messages, and the close command travel in one `RespondWorkflowTaskCompletedRequest`, so history becomes visible atomically (`internal/internal_task_handlers.go:1427-1472`). Local termination is a *proposal*; recorded history events are treated as no-ops on replay, making the server's record authoritative (`internal/internal_event_handlers.go:1322-1327`). This model fits when durability, recovery, and multi-process authority matter.

These are responses to product shape, not quality tiers: a stdlib-only library cannot justify persistence machinery; a CLI-backed interactive app cannot afford task-boundary latency; a durable orchestration engine cannot survive memory-only state.

## Pattern Catalog

### P1. The Funnel: one completion slot, one arbitration function

- **Problem:** multiple producers (normal completion, panic, cancellation, policy overrides) could each try to declare the terminal outcome.
- **Demonstrated by:** temporal-sdk-go most explicitly — five `Complete` producers write through one handler into one `(result, err)` pair, and a single function inspects that one `err` in fixed priority order (canceled > continue-as-new > failed > completed) to append at most one close command (`internal/internal_workflow.go:692-734`; `internal/internal_event_handlers.go:150`; `internal/internal_task_handlers.go:1884-1958`). conc shows the minimal version: `Wait()` as the only publication point (`sources/conc/waitgroup.go:38-43`). crush shows the degraded version: one emit path but four upstream producers held apart by cooperating guards rather than a shared slot.
- **Why it works:** conflicting outcomes cannot coexist because there is nowhere to put two of them. Arbitration becomes a total order over one value instead of a concurrency problem.
- **Copy when:** you have more than one way a run can end (which Aren does: success, work error, runtime failure, panic, cancellation).
- **Overkill/risky when:** a scope genuinely has exactly one possible producer — then the funnel is ceremony. Note even temporal needed only ~100 lines for the core funnel.
- **Evidence:** the test environment vs production divergence on repeated `Complete` calls (`internal/internal_workflow_testsuite.go:1143-1147` vs `internal/internal_task_handlers.go:653-657`) shows what happens when the slot itself isn't first-write-wins-guarded: writers are ordered today, but nothing enforces it.

### P2. First-write-wins latches for irreconcilable outcomes

- **Problem:** two racing producers of a singular terminal fact (the panic that killed the scope; the terminal event already published).
- **Demonstrated by:** conc's panic catcher uses `atomic.CompareAndSwap(nil, &rp)` — strictly first-recovered wins, verified under a 100-goroutine race (`sources/conc/panics/panics.go:26-31`; `sources/conc/panics/panics_test.go:126-145`). crush gates its dispatcher fallback dedup with an atomic bool marker carried in context (`internal/agent/run_marker.go:31-52`). temporal's `futureImpl.Set` panics on second set and its callback wrappers carry a `handled` flag that panics on second delivery (`internal/internal_workflow.go:423-434`; `internal/internal_event_handlers.go:287-343`).
- **Why it works:** a CAS latch converts "who wins?" from a locking question into a deterministic rule with a silent, cheap loser path.
- **Copy when:** any terminal fact must fire exactly once. This is nearly free (~15 LOC) and belongs in Aren's commit path from day one.
- **Watch out:** first-wins discards information. conc silently drops secondary panics including stacks (`sources/conc/panics/panics.go:29`); temporal's priority order makes lower-priority outcomes vanish. If diagnostics matter, retain losers in a log while keeping the latch authoritative.

### P3. Separate representations for cancel-requested vs terminated

- **Problem:** a cancellation signal is not a termination; conflating them lets observers act before work actually stops.
- **Demonstrated by all three, differently:**
  - conc: request = derived context canceled (`sources/conc/pool/context_pool.go:45`); confirmation = worker exit observed by the WaitGroup barrier (`sources/conc/pool/pool.go:81`). But conc has no internal representation of the request — it is fully outsourced to stdlib `context`.
  - crush: three representations — the context cancel func invocation (entry deliberately kept in `activeRequests` until the goroutine finishes, `internal/agent/agent.go:1966-1973`), a pending-cancel sequence high-water mark for accepted-not-yet-active runs (`1988-2003`), and confirmed termination when `Run` returns and persists `FinishReasonCanceled` (`501-528,1159-1160`).
  - temporal: `CANCEL_REQUESTED` fires only a context cancel; the close command requires user code to actually return `CanceledError` (`internal/internal_event_handlers.go:1688-1694`; `internal/internal_task_handlers.go:1890-1896`); dedicated machine states distinguish cancel-sent from completed-after-cancel-sent (`internal/internal_command_state_machine.go:190-195`).
- **Why it works:** each representation answers a different question ("did someone ask?", "was anyone in flight?", "did it stop?") without any one of them lying about the others.
- **Copy when:** always, if runs can be canceled. The cancel-in-flight states specifically eliminate a whole class of completion-during-cancellation races at low cost (temporal's `Test_ActivityStateMachine_CompletedAfterCancel` pins this, `internal/internal_command_state_machine_test.go:219-253`).

### P4. Sequence high-water marks for cancel-vs-dispatch races

- **Problem:** a cancel arriving while a run is accepted but not yet active — should it poison later, unrelated accepts?
- **Demonstrated by:** crush only. A monotonic accept sequence plus a max-raised per-session cancel mark covers exactly the handles accepted before the cancel and none after (`internal/agent/agent.go:217-222,1988-2003`); tests prove earlier siblings cancel-on-entry while later prompts run normally (`internal/agent/dispatch_cancel_test.go:361-447`).
- **Why it works:** the high-water mark makes coverage a pure comparison of ordinals, immune to scheduling.
- **Copy when:** run acceptance and cancellation can interleave through different entry points — likely true for Aren once any external cancellation API exists.
- **History matters:** this design exists because an earlier counted-pending-cancel scheme let later accepts consume earlier cancellations — a real bug class the reviewer caught (`internal/agent/dispatch_cancel_test.go:361-370`).

### P5. Panic normalization at goroutine boundaries

- **Problem:** a panic crossing a task boundary destroys ownership of failure semantics unless captured.
- **Demonstrated by:** conc recovers into a `Recovered` value carrying caller frames + stack, rethrowing at the `Wait` boundary or bridging to error via `AsError()` (`sources/conc/panics/panics.go:52-102`). temporal recovers at five sites, normalizing coroutine panics, deadlock detection, and illegal transitions into one typed `workflowPanicError` channel, then re-specializing by type at publication — and forbids blocking inside deferred functions during unwinding (`internal/internal_workflow.go:1234-1245,1057-1087`; `internal/internal_task_handlers.go:1305-1349`).
- **Anti-demonstrated by crush:** `sessionAgent.Run` installs no recover; repo-wide search found recovery only at HTTP middleware, MCP init, shell execution, and the TUI pump — a stream-callback panic propagates through `Run` and kills the process (`internal/server/recover.go:18`; absence documented against `internal/app/app.go:707`). Work errors, runtime failures, and panics are therefore *not* uniformly distinct there.
- **Copy when:** every goroutine/task boundary needs either recover→typed-error conversion or an explicit "panic = fatal" declaration. Crush proves the accidental mix is the worst outcome.

### P6. Outcome-before-notification ordering

- **Problem:** cascading effects (cancel-on-error, terminal events, flushes) can race ahead of the cause they derive from.
- **Demonstrated by:** conc writes the causal error into the collector *before* `cancel()` fires, with an in-place comment flagging the deliberate layering break ("leaky abstraction warning", `sources/conc/pool/context_pool.go:40-47`). crush publishes RunComplete only after `FlushAll` drains debounced writes, embedding final MessageID+Text as a backstop for out-of-order subscribers (`internal/agent/agent.go:735-781`). temporal gets the guarantee structurally: everything travels in one RPC (`internal/internal_task_handlers.go:1427-1472`).
- **Why it works:** observers can never see a consequence before its cause, which is precisely the coherence property Aren requires.
- **Copy when:** any transition triggers secondary notifications. Make the ordering rule a hard invariant in the transition code, and annotate it the way conc does.

### P7. Fail-fast illegal transitions

- **Problem:** silent corruption of lifecycle state is worse than a crash.
- **Demonstrated by:** temporal panics on any impossible transition (TMPRL1100, `internal/internal_command_state_machine.go:500-507`), recovered at the event boundary into a failed task rather than a dead process (`internal/internal_event_handlers.go:1302-1309`). conc's `TryLock` collection guard converts a would-be data race into an immediate programming-error panic (`sources/conc/pool/result_pool.go:122-126`).
- **Why it works:** bugs surface at the transition site with a stack, not three layers downstream as inexplicable state.
- **Cost:** benign edge cases need dedicated handling to avoid false alarms — temporal needed late-cancel states and cancel-of-resolved-command removal hacks (`internal/internal_command_state_machine.go:1093-1097`: "This really should not exist").

### P8. Detached bounded contexts for terminal writes

- **Problem:** shutdown can strand the very writes that record termination.
- **Demonstrated by:** crush persists cancelled turns, flushes, and dropped-prompt terminals using `context.WithoutCancel` + short timeouts so shutdown cannot drop them (`internal/agent/agent.go:509,754,1097,446`), with shutdown ordered agents-first → flush → DB close (`internal/app/app.go:743-761`).
- **Copy when:** terminal records must survive process exit. Pair with a bound (5s in crush) so a stuck store cannot hang shutdown.

## Key Differences

**Where the commit point sits.** This is the deepest divergence. conc commits at a synchronous caller-side barrier — coherent but invisible until done (`sources/conc/waitgroup.go:36-43`). temporal commits at a network boundary into durable history — coherent for external observers, slightly early for in-process ones (`isWorkflowCompleted` flips before the RPC lands, contained by stopping the event loop, `internal/internal_task_handlers.go:1232-1234`). crush commits immediately at the emit path but repairs ordering downstream with flush-before-publish and embedded-text reconciliation (`internal/agent/agent.go:735-781`). Same goal — no observer sees terminal state before its outcome — reached from opposite directions: withhold-until-complete versus publish-and-backstop.

**How state is represented.** No enum (conc: existence is ownership), memory maps (crush: `activeRequests` presence *is* busy, `internal/agent/agent.go:2048-2051`), or enumerated machine persisted as history (temporal). The driver is durability need: conc scopes die with the call stack; crush accepts losing in-flight runs on restart (recovering lazily at next prompt, `internal/agent/agent.go:1655-1687`); temporal's entire product is surviving restarts via replay.

**How arbitration is enforced.** By type structure (conc: the collector types make conflicts unrepresentable), by convention plus tests (crush: guards spread across three packages; the analysis notes honestly that a new producer bypassing `publishRunComplete` would silently break the invariant), or by a state machine that panics on violation (temporal). Only temporal's enforcement is structural at the transition level itself.

**Panic philosophy.** Rethrow at the owner (conc), normalize-to-typed-error (temporal), undeclared-and-escaping (crush). The first two are designs; the third is an accident the analysis flagged as the source's biggest gap for this dimension.

**Cancellation modeling depth.** conc delegates wholly to `context` and cannot answer "was this termination requested?" internally; crush adds two internal representations (map entry retention, sequence mark) around the context signal; temporal adds machine states distinguishing sent from accepted from survived-by-completion. Depth tracks how much cancellation ambiguity the product must resolve.

## Tradeoffs

**Coherence vs observability.** conc's commit-at-Wait makes publication atomic but offers no progress reporting, no timeouts, no watchdog — one hung task hangs the scope forever (`sources/conc/pool/pool.go:150-162`). Alternative seen: crush's split delivery semantics — lossy non-blocking for streaming deltas, bounded-blocking (50 ms/subscriber) for terminal events (`internal/pubsub/broker.go:159-236`) — buys live visibility while keeping terminals prioritized, at the cost of intermediate state having no delivery guarantee.

**Convention vs enforcement.** crush's guard chain keeps interfaces unchanged (dedup state rides in context values, `internal/agent/runid.go:14-22`) and required zero signature changes across packages — but the exactly-once property lives in review discipline and tests, not types. Alternative seen: temporal's machine makes violations panic, surfacing nondeterminism immediately, at the price of dedicated states and cleanup hacks for benign edge cases (`internal/internal_command_state_machine.go:1093-1097`).

**Determinism vs information loss.** First-wins arbitration (conc panics, temporal close-command priority) gives a deterministic winner but silently drops losers — conc loses secondary panic stacks outright (`sources/conc/panics/panics.go:29`); temporal's fixed priority means a cancel arriving after a failure was recorded simply loses (`internal/internal_task_handlers.go:1884-1958`). Alternative seen: conc's append-only error log keeps everything when outcomes are reconcilable — the split between latch-for-irreconcilable and log-for-reconcilable is itself a design lesson (`sources/conc/pool/error_pool.go:94-100`).

**Simplicity vs modeling power.** conc stays tiny by outsourcing cancellation semantics to stdlib `context`; the bill arrives as inability to distinguish requested-vs-observed termination at the library level (callers infer from returned error values, per `sources/conc/pool/context_pool_test.go:95-105`). Alternative seen: temporal's cancel-in-flight states resolve that ambiguity precisely, costing ~10 extra states and their transitions.

**Precision vs size.** Temporal scored highest (9/10) precisely because its guarantees are structural — and paid with ~1700 lines of state machine, a cooperative coroutine runtime, sticky-cache locks, and replay matching. Its own analysis concludes the transferable part is the discipline, not the volume: skip replay determinism checking and most of the bulk disappears (`internal/internal_task_handlers.go:1278-1295` is the machinery Aren doesn't need).

**Immediate publication vs batch atomicity.** Publishing at the moment of determination (crush) minimizes latency but forces every consumer to handle reordering and drops. Buffering to a boundary (temporal) gets atomicity free but holds outcomes hostage to the next task — mitigated by heartbeat/force-complete paths (`internal/internal_task_handlers.go:962-1051`).

## Decision Guide

Choose the commit-point model by answering one question: **who observes the run, and when?**

- **Only the spawning caller observes, synchronously** → conc's model. Owner + catcher pairing, `Wait()` as the sole gate, CAS panic latch. Total adoption cost: ~30 LOC per piece (`sources/conc/waitgroup.go:22-43`).
- **External observers subscribe to events during a long-lived process** → crush's model: single emit path, delivery-semantics split, flush-before-publish, embedded reconciliation payload. Adopt its sequence high-water mark if cancellation can race dispatch (`internal/agent/agent.go:1988-2003`), and its detached-bounded-context pattern if terminal writes must survive shutdown.
- **Runs must survive restarts or multiple processes need authority** → temporal's model, reduced: keep the funnel (one slot, one arbitration function), the enumerated states with fail-fast illegal transitions, and the proposal/confirmation asymmetry; discard replay matching, event-ID prediction, version markers, and the coroutine runtime unless determinism-checking becomes a requirement.

For Aren Phase 1 specifically, the roadmap constraint (lifecycle before providers/tools/persistence broadening) aligns with what every source's future-work section recommends: build the funnel first. Composition rule of thumb: take conc's primitives (latch, Recovered payload, teardown discipline), crush's cancellation representations (high-water mark, entry-retention-until-exit), and temporal's enforcement posture (first-write-wins slot guard, illegal-transition panic, typed-error normalization) — each is smaller than Aren's contract, and none drags its host framework along.

Two decisions the sources cannot make for Aren: whether transition timestamps are required (none of the three captures timing metadata at transitions in-process; conc records none whatsoever) and whether Aren wants replay-as-source-of-truth (this single requirement justifies roughly half of temporal's bulk, per its own analysis).

## Practical Tips

1. **Make the commit gate a constructor, not a convention.** Crush's own retrospective recommends turning `publishRunComplete` into "the only constructor of terminal transitions (e.g., a `Terminal` value type that must be minted once)," removing reliance on flags like `skipRunComplete` and hook stripping (evidence: the flag mechanics at `internal/agent/agent.go:1282-1286`). If Aren's terminal type can only be minted through one function, the guard chain problem disappears.
2. **Guard the completion slot with first-write-wins from day one.** Temporal left a production/test divergence here (test env ignores repeats; production overwrites, `internal/internal_workflow_testsuite.go:1143-1147` vs `internal/internal_task_handlers.go:653-657`); its analysis recommends closing exactly this gap rather than relying on writer ordering.
3. **Adopt the ordering rule as an invariant, with a comment.** "Record causal outcome before triggering cascading cancellation" — conc annotates its layering break in place (`sources/conc/pool/context_pool.go:40-44`); copy both the rule and the annotation habit.
4. **Add `handled` flags to every result callback immediately.** Temporal's wrappers panic on second delivery, catching producer bugs loudly and early (`internal/internal_event_handlers.go:287-343`). Cost: one bool per callback site.
5. **Lift the accept-counter + sequence high-water mark verbatim** for cancel-vs-dispatch races, and port crush's property tests with it — including the gated-machinery integration test that parks a coordinator so a cancel deterministically lands in the accepted-not-active window (`internal/backend/accepted_run_integration_test.go:27-63`).
6. **Normalize panics at boundaries into one typed error carrying a stack**, and forbid blocking operations during unwinding (temporal detects `runtime.gopanic` on the stack during yield and re-panics, `internal/internal_workflow.go:1057-1087`, pinned by `test/integration_test.go:9713-9767`).
7. **Write terminal publications with detached, bounded contexts** so shutdown cannot strand them (crush: `context.WithoutCancel` + 5s timeout, `internal/agent/agent.go:509`).
8. **Test against observable events, not internals.** Crush asserts exactly-one terminal event by reading the published broker channel and failing on a second event (`internal/agent/run_complete_test.go:228-245`); its probe-model race test converts a locking bug into a numeric assertion (max concurrent streams == 1, `internal/agent/dispatch_race_test.go:19-67`). Both styles test the contract callers depend on.
9. **Keep reconcilable outcomes in a log, irreconcilable ones behind a latch.** Errors accumulate append-only; the singular panic/event goes through CAS (`sources/conc/pool/error_pool.go:94-100` vs `sources/conc/panics/panics.go:29`). Decide per channel, don't unify.
10. **If Aren ever needs incremental ordered progress events,** conc's single sequencer-goroutine stream (`sources/conc/stream/stream.go:121-138`) is the smallest known-good analog — but note its panicking-task placeholder substitution alters the observed callback sequence (`sources/conc/stream/stream.go:78`); anything richer (subscribers, replay) exceeds all three sources and needs fresh design.

## Anti-Patterns / Caution Signs

- **Guard chains instead of choke points.** When exactly-once correctness spans multiple packages connected by hooks, flags, and context markers, any new producer that bypasses the emit path silently breaks the invariant — crush's stated residual risk (`internal/agent/agent.go:539-548` relies on cooperation from four upstream sites). Caution sign: adding a terminal producer requires knowing about unwritten conventions.
- **Secondary paths below the primary arbitration bar.** Crush's `Summarize` checks busy and registers active requests without holding `dispatchMu` and contains a dead cancel-key lookup (`sessionID+"-summarize"` can never match, `internal/agent/agent.go:1976` vs `1355`). Caution sign: side-entry points into the run system that skipped the main path's serialization review.
- **Undeclared panic contracts.** Five unrelated recover sites scattered by subsystem, none wrapping the core run loop (crush, repo-wide `recover()` search) — panics escape through the exact boundary this dimension asks to control. Caution sign: grepping for `recover()` returns results everywhere except the component that owns lifecycle.
- **Test doubles that disagree with production semantics.** Temporal's test env makes repeat `Complete` a no-op while production overwrites (`internal/internal_workflow_testsuite.go:1143-1147`). Caution sign: a safety property that holds in tests because the fake enforces it, not because the real thing does.
- **Racy tests patched with sleeps.** Conc's own suite admits intrinsic raciness in first-error ordering and papers over it with sleeps plus candid comments (`sources/conc/pool/result_error_pool_test.go:66-90`). Acceptable as documentation of scheduler-dependence; dangerous when mistaken for coverage. Caution sign: `time.Sleep` guarding an ordering assertion.
- **Reusable scopes muddying terminality.** Conc pools reset accumulators and `initOnce` after `Wait` for reuse, and sticky accumulators caused a real bug (issue #128, `sources/conc/pool/error_pool_test.go:121-134`). Caution sign: a "completed" object that can run again, complicating any audit log of transitions. Terminality for identity, not for liveness, is a choice to make consciously.
- **Blocking inside deferred functions during panic unwinding.** It freezes the panic and lets post-panic code emit spurious commands — temporal had to add detection (`internal/internal_workflow.go:1077-1083`). Caution sign: defers that do I/O on the panic path without a guard.
- **Hand-maintained mark hygiene.** Crush clears cancel marks at three places maintained manually (`internal/agent/agent.go:330-334,1265-1279,403-424`); tests cover staleness, but the invariant lives in discipline. Caution sign: an invalidation rule with N call sites and no owner object.
- **Best-effort quiescence waits.** Polling sleeps (200ms increments up to 5s) presented as shutdown barriers (`internal/agent/agent.go:2026-2034`) — fine for UX, wrong as a correctness mechanism. Caution sign: "wait for exit" implemented as a sleep loop feeding a non-barrier step.

## Notable Absences

Evidence the sources do *not* provide, relevant to Aren Phase 1 scoping:

- **No transition timestamps anywhere.** Conc records no timing metadata at all (only perf notes in doc comments, `sources/conc/pool/pool.go:27-29`); crush's states are ephemeral maps with no timestamps; temporal's timing lives server-side in history, outside the SDK's in-process commit. If Aren requires captured transition timestamps, no studied source offers a template — it must be designed fresh.
- **No persisted queryable run/status row in two of three sources.** Crush has no status field on sessions (checked via `internal/session/session.go:50-63`) and no status-like enums beyond message `FinishReason` constants; its analysis explicitly states crush offers no template for durable run rows. Temporal's authoritative record is server-owned history, not an SDK-level construct.
- **No subscriber/replay-grade event publication below framework scale.** Conc's `Stream` is the ceiling for small ordered publication; anything with subscriptions, replay, or delivery guarantees exceeds all three sources.

## Open Questions

1. **Does Aren's PRD impose transition-timing requirements?** None of the three sources captures in-process transition timestamps; this must be decided from the unread requirement docs, not inferred from the study (flagged independently by all three analyses).
2. **Does Aren want replay-as-source-of-truth?** Per temporal's analysis, this single requirement justifies roughly half its code volume (command/event matching, event-ID prediction, version markers). Deciding "no" early removes the largest temptation to import framework bulk.
3. **How many terminal producers will Aren have?** Crush's single atomic-bool marker suffices only for exactly two publishers (`internal/agent/run_marker.go:31-52`); more producers need the generalized ledger — a `Terminal` minting constructor per its recommendation, or temporal-style slot-plus-arbiter.
4. **What is Aren's declared panic contract?** Recover→typed-error conversion (conc, temporal) or explicit fatal declaration; crush's accidental mix is the documented anti-model. Unresolved: whether Aren's task bodies may invoke user/plugin code whose panics should be contained rather than fatal.
5. **Can Aren's cancellation request be observed internally?** Conc cannot answer "was this termination requested?" within its own types; Aren Phase 1 wants cancellation-request represented alongside confirmed-termination — the open sub-question is whether crush's three-representation scheme (signal, pending mark, confirmed outcome) or temporal's state-machine variant better fits Aren's scale.
6. **Ordering argument completeness (from temporal's gaps):** production writer ordering that determines the winning outcome under simultaneous event-panic and policy-override lives mostly in code comments, not tests — no studied source demonstrates a formally tested total-order proof for multi-producer terminal resolution; Aren should pin its chosen arbitration order with an explicit test.
