## Executive Summary

This dimension asks whether a Go program can start, observe, cancel, and reap a subprocess *tree* reliably, and what happens to descriptors, output, and privileges when it tries. The two sources answer from opposite ends of the systems spectrum.

docker-agent is a userspace `os/exec` supervisor for short-lived shell tools. Its two primary runners (`pkg/tools/builtin/shell/shell.go:32`, `pkg/tools/builtin/backgroundjobs/backgroundjobs.go:54`) implement competent cross-platform tree-kill — `Setpgid:true` + `kill(-pid,SIGTERM)` on Unix (`pkg/tools/builtin/shell/cmd_unix.go:14-25`), `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` on Windows (`pkg/tools/builtin/shell/cmd_windows.go:20-73`) — plus `WaitDelay` to survive the classic backgrounded-grandchild pipe deadlock (`pkg/tools/builtin/shell/shell.go:173-198`). Four other exec sites (`script_shell`, hooks, MCP stdio, environment provider) bypass all of this, shell output is unbounded, and even the hardened paths leak `setsid`-detached descendants and race Windows job assignment. The outer Docker sandbox (`pkg/sandbox/sandbox.go:28`) is an agent-level wrapper, not a per-tool containment boundary.

runc is a privileged Linux container runtime whose subprocess supervision is kernel-enforced. Process creation is `exec.Command("/proc/self/exe","init")` with wired `Stdin/Stdout/Stderr/Dir/Env/ExtraFiles` (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:575-647`), but containment does not rely on Go: PID-namespace init-kill (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:445-448`), `cgroup.kill` with a `Freeze → GetAllPids → Kill → Thaw` fallback (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:682-720`), `CLONE_INTO_CGROUP` via `prepareCgroupFD` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:371-457`), and aggressive `CloseExecFrom` / `UnsafeCloseFrom` hygiene. It demonstrates production-grade descendant termination and descriptor closure, yet offers no generic `context.Context` cancellation, no output bounding, and no Windows equivalent — it is Linux-only by design (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils_unix.go:1`).

Convergent lesson: no source claims parent cancellation guarantees descendant death; every reliable path needs an explicit tree-kill domain (process group, job object, PID namespace, or cgroup) plus an escalation ladder and a pipe-drain strategy. Divergent lesson: docker-agent trades completeness for portability and speed, runc trades portability for kernel atomicity. For Aren Phases 8 and 17, the transferable core is the former; the latter is a reference for what "guaranteed" actually costs.

## Core Thesis

**Tree containment is not a kill signal; it is a kill domain plus a drain discipline, and the two must be designed together.**

Both sources independently prove that `cmd.Process.Kill()` or `context.WithCancel` alone cannot answer "does cancelling the parent guarantee descendants stop?" — docker-agent's Unix group kill misses `setsid` children (`pkg/tools/builtin/shell/shell_test.go:362-397`) and Windows job assignment races grandchildren (`pkg/tools/builtin/shell/cmd_windows.go:20-73`); runc's single-init kill fails for shared-PID containers without cgroup delegation (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:828-835`). A reliable supervisor must first place every descendant into a kernel-visible equivalence class that can be killed atomically — pgid, job object, PID namespace, or cgroup — and only then decide which signal to send. Without the domain, escalation is irrelevant.

The second half of the thesis is that **the pipe is the supervisor's other containment boundary.** Go's `exec.Cmd` with OS pipes blocks `Wait()` until every fd-inheriting descendant closes its copy (`pkg/tools/builtin/shell/shell.go:173-186`). docker-agent fixes this with `WaitDelay` (500ms shell, 1s background, 10s eval) at the cost of truncated grandchild output and SIGPIPE; runc fixes its control plane with dedicated sync sockets (`SOCK_SEQPACKET`) and a log-forwarding goroutine (`studies/aren-go-runtime-study/sources/runc/libcontainer/logs/logs.go:17-52`) but leaves container stdio unbounded to the caller. The takeaway for Aren is that output bounding and pipe-drain timeout are not optimizations — they are liveness prerequisites. Any design that inherits pipes without a `WaitDelay` or equivalent is one `sleep 30 &` away from hanging until timeout.

The sources diverge where product constraints force them: docker-agent needs sub-second tool latency on macOS/Windows/Linux without privileges, so it accepts best-effort SIGTERM-only group kill, unbounded shell buffers, and inconsistent hardening across six exec sites. runc needs leak-proof cleanup for containers that may fork-bomb, so it accepts Linux-only syscalls, three-stage C bootstraps (`studies/aren-go-runtime-study/sources/runc/libcontainer/nsenter/nsexec.c:640-1232`), and cgroup delegation requirements. Neither is "more correct" — they optimize for different points on the portability × guarantee spectrum. Aren should adopt docker-agent's shape and steal runc's hardening where the cost is low (early cgroup join, `Pdeathsig`, `CloseExecFrom`, freeze-before-enumerate), without importing its privilege or OS scope.

## Approach Models

**docker-agent — "portable userspace tree-kill."** The supervisor lives entirely in Go's `os/exec` layer. On Unix it sets `SysProcAttr{Setpgid:true}` at fork so the shell and its children share a pgid, then `syscall.Kill(-pid, SIGTERM)` addresses the group; on Windows it creates a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` after `Start` and closes the handle to trigger kernel kill; on js/wasm it is an explicit no-op (`pkg/tools/builtin/shell/cmd_js.go:15-24`). Timeout/cancellation is manual: `exec.Command` (not `CommandContext`) + `context.WithTimeout` + goroutine `Start`→`Wait`, with a 3s (shell) / 2s (reap) SIGTERM grace then `SIGKILL` of the direct pid (`pkg/tools/builtin/shell/shell.go:221-233`). Pipe liveness is handled by `WaitDelay`. The model fits when callers are unprivileged, cross-platform, and latency-sensitive, and when best-effort containment is acceptable with documented non-guarantees (`docs/guides/headless/index.md:87`).

**runc — "kernel-enforced container domain."** The supervisor delegates containment to the kernel. Private PID namespace makes `kill(init, SIGKILL)` atomically kill the namespace (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:445-448`); shared-PID containers fall back to `signalAllProcesses` which prefers the race-free `cgroup.kill` file then `Freeze(Frozen) → GetAllPids → Kill → Thaw` (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:682-720`). `prepareCgroupFD` / `SysProcAttr.UseCgroupFD` places the child via `clone3(CLONE_INTO_CGROUP)` before it can fork (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:371-457`). Descriptors are scrubbed with `CloseExecFrom(3)` and `UnsafeCloseFrom` before `Exec`; sync uses three dedicated pipes/sockets instead of stdio. The model fits when the caller is privileged, Linux-only, and must guarantee cleanup even under adversarial forking.

These are responses to operational constraints, not quality tiers. docker-agent cannot require cgroups or namespaces for a `cat` tool; runc cannot afford a missed pgid member for a container that `setsid` + double-forks.

## Pattern Catalog

### P1. Process-group / job-object scoped kill (userspace tree-kill)

- **Problem:** `Kill(pid)` reaches only the direct child; grandchildren survive.
- **Demonstrated by:** docker-agent. Unix `Setpgid:true` + `Kill(-pgid,SIGTERM)` (`pkg/tools/builtin/shell/cmd_unix.go:14-25`); Windows `CreateJobObject` + `AssignProcessToJobObject` + handle-close kill (`pkg/tools/builtin/shell/cmd_windows.go:20-73`). Platform split via `cmd_unix.go` / `cmd_windows.go` / `cmd_js.go` triplets.
- **Why it works:** pgid and job object are kernel-visible equivalence classes set at or near fork; a single negative-pid or job-close addresses the whole class without enumerating pids.
- **Copy when:** you need cross-platform `os/exec` tree-kill without privileges. This is the correct baseline for Aren's `shell` tool.
- **Overkill/risky when:** you already have a PID namespace or cgroup — then the group is redundant; also insufficient for `setsid`-detached or pre-existing-job children.
- **Evidence:** `pkg/tools/builtin/shell/shell.go:188-233`, `pkg/tools/builtin/backgroundjobs/backgroundjobs.go:235-272`; limitation documented by `TestShellTool_DetachedBackgroundedChildDoesNotBlockReturn` (`pkg/tools/builtin/shell/shell_test.go:362-397`).

### P2. PID-namespace as kill domain (kernel tree-kill)

- **Problem:** userspace enumeration races new forks.
- **Demonstrated by:** runc. Private PID namespace makes init the namespace's `kill -9 1` equivalent — kernel guarantees all members die (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:445-448`), implemented as single `initProcess.signal(SIGKILL)` with freezer thaw (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:472-489`); shared-PID path branches to `signalAllProcesses`.
- **Why it works:** the kernel, not userspace, owns the membership; no PID race possible.
- **Copy when:** you control namespace creation and can be PID 1 or create a new PID ns — essentially only for container/sandbox runtimes.
- **Overkill/risky when:** general shell tools; requires `unshare(CLONE_NEWPID)` + `C` bootstrap (`studies/aren-go-runtime-study/sources/runc/libcontainer/nsenter/nsexec.c:640-1232`) and `CAP_SYS_ADMIN`.
- **Evidence:** `studies/aren-go-runtime-study/sources/runc/libcontainer/integration/exec_test.go:1371-1427` (`TestHostPidnsInitKill` / `TestSharedPidnsInitKill`).

### P3. `cgroup.kill` with freeze-enumerate-kill fallback

- **Problem:** PID-namespace unavailable (shared/host PID) — how to kill atomically?
- **Demonstrated by:** runc `signalAllProcesses` (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:682-720`): try `cgroups.WriteFile(p,"cgroup.kill","1")` (atomic, race-free on cgroup v2), fallback on `ENOENT` to `Freeze(Frozen) → GetAllPids → unix.Kill → Freeze(Thawed)`. `destroy` (`studies/aren-go-runtime-study/sources/runc/libcontainer/state_linux.go:39-67`) reuses the same path for shared-PID cleanup.
- **Why it works:** `cgroup.kill` is kernel-atomic; freezing prevents fork-between-enumerate-and-kill when it is unavailable, at the cost of briefly freezing victims.
- **Copy when:** Linux cgroup v2 is delegated (systemd `Delegate=yes` or `CLONE_INTO_CGROUP`); runc's warning `"impossible to properly kill all container's processes"` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:828-835`) is the cue to avoid this path without delegation.
- **Evidence:** fallback latency vs correctness tradeoff; only freezes for `SIGKILL` paths (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:481-486`).

### P4. `CLONE_INTO_CGROUP` early join (race elimination)

- **Problem:** `Start` then `AddPid` window lets a fast grandchild escape the cgroup.
- **Demonstrated by:** runc `prepareCgroupFD` + `SysProcAttr.UseCgroupFD/CgroupFD` → `clone3` places child directly in target cgroup before first userspace instruction (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:371-457`), with fallback `startWithCgroupFD` without cgroupfd if `clone3` fails.
- **Why it works:** atomic placement eliminates the classic "fork before AddPid" race that plagues job-object and post-start cgroup approaches.
- **Copy when:** kernel ≥5.7 + cgroup v2; runc's silent retry without cgroupfd makes the optimization safe to attempt. For docker-agent's Windows path this is the analog of moving `AssignProcessToJobObject` before the child's first fork — not possible post-`Start`, which is precisely why that path races.
- **Evidence:** docker-agent's Windows race comment vs runc's eliminated race.

### P5. `WaitDelay` / sync-socket pipe-drain discipline

- **Problem:** `Wait()` blocks until every fd-inheriting descendant closes the pipe; `sleep 30 &` hangs the tool until timeout.
- **Demonstrated by:** docker-agent `cmd.WaitDelay = 500ms` (shell), `1s` (background), `10s` (eval) force-closes pipes and returns `exec.ErrWaitDelay` (`pkg/tools/builtin/shell/shell.go:173-198`, `pkg/tools/builtin/backgroundjobs/backgroundjobs.go:41-52`); runc avoids the class entirely for control planes via `SOCK_SEQPACKET` sync sockets + `ForwardLogs` goroutine (`studies/aren-go-runtime-study/sources/runc/libcontainer/logs/logs.go:17-52`, `studies/aren-go-runtime-study/sources/runc/libcontainer/sync_unix.go:18-85`), and `Poll` + `pidfd_open` for exec fifo (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:271-327`).
- **Why it works:** the supervisor stops waiting for descendant pipe closure; liveness is bounded.
- **Copy when:** any `os/exec` with `StdoutPipe`/`StderrPipe` or `bytes.Buffer` that a child could inherit; set `Cancel` + `WaitDelay` (Go 1.20+) uniformly.
- **Tradeoff:** truncates still-running grandchild output and SIGPIPE-kills its next write — documented at `pkg/tools/builtin/backgroundjobs/backgroundjobs.go:41-50`; per-call knob missing in docker-agent.
- **Evidence:** regression tests `TestShellTool_BackgroundedChildDoesNotBlockReturn` (`pkg/tools/builtin/shell/shell_test.go:334-397`) and background-jobs equivalent (`pkg/tools/builtin/backgroundjobs/backgroundjobs_test.go:427-471`).

### P6. Bounded output (`limitedWriter` / scanner limits)

- **Problem:** unbounded `bytes.Buffer` grows to O(output) and OOMs the parent.
- **Demonstrated by:** docker-agent `limitedWriter` caps background jobs at `maxBackgroundJobOutputBytes=10MB` while reporting `len(p)` to the child to avoid blocking (`pkg/tools/builtin/backgroundjobs/backgroundjobs.go:39,99-118`), with `[Output truncated]` notice on render; the synchronous `shell` tool counter-demonstrates the failure — `commandOutput.buf bytes.Buffer` unbounded (`pkg/tools/builtin/shell/shell.go:62-91`). runc counter-demonstrates at larger scale: hook `bytes.Buffer` unbounded (`studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:600-607`) and container stdio caller-managed with no limit; eval scanner capped 1M→10M (`pkg/evaluation/eval.go:500`).
- **Why it works:** returning `len(p)` while dropping excess keeps the child unblocked while bounding parent memory.
- **Copy when:** any long-lived or attacker-influenced command (`cat huge.bin`, `yes | head`). Bound the shell path too (e.g., 2–5 MB or temp-file spill).
- **Evidence:** docker-agent 10 MB background bound vs unbounded shell/script_shell/hooks; runc hook OOM vector.

### P7. SIGTERM → timed-wait → SIGKILL escalation ladder

- **Problem:** graceful shutdown handlers need SIGTERM, but ignorer processes must not stall forever.
- **Demonstrated by:** docker-agent `kill(pg)` on `timeoutCtx.Done()` then 3s grace then `cmd.Process.Kill()` (`pkg/tools/builtin/shell/shell.go:221-233`) and `reapSpawnedChild` 2s variant (`pkg/tools/builtin/shell/shell.go:244-261`); runc mirrors for `SIGKILL` via thaw after freeze (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:481-489`).
- **Why it works:** bounded grace separates polite termination from forced reaping.
- **Copy when:** always wrap group/job kill with a timed escalation; docker-agent's gap is that escalation kills only the direct pid on Unix, not the group again — re-send `Kill(-pgid)` on escalation to close the SIGTERM-ignorer leak.
- **Evidence:** runc only freezes/thaws for `SIGKILL`; docker-agent's `StopBackgroundJob` never re-kills the group (`pkg/tools/builtin/backgroundjobs/backgroundjobs.go:425-440`).

### P8. Setup-failure reaping (cancellation during startup)

- **Problem:** `Start` succeeds but `createProcessGroup`/`AssignProcessToJobObject`/cgroup setup fails — child is already running and must not leak.
- **Demonstrated by:** docker-agent `createProcessGroup` error → `reapSpawnedChild(cmd, pg)` (SIGTERM → 2s → SIGKILL + `Wait`) (`pkg/tools/builtin/shell/shell.go:207-213`); runc `initProcess.start`/`setnsProcess.start` defers on `retErr != nil` → `ignoreTerminateErrors(p.terminate())` + `manager.Destroy()` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:464-480,789-821`). Both Swallow termination errors to surface the original setup cause.
- **Copy when:** any multi-step start with fallible wiring after `fork`/`Start`.
- **Evidence:** docker-agent and runc share the same `terminate`+`Wait` shape; runc adds OOM annotation before and after.

### P9. Aggressive descriptor closure (`CloseExecFrom` / `UnsafeCloseFrom`)

- **Problem:** leaked fds keep pipes alive, bypass seccomp, or leak host handles into containers (CVE-2024-21626).
- **Demonstrated by:** runc parent `CloseExecFrom(3)` before `runc init` (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:402`), child `finalizeNamespace` `CloseExecFrom(PassedFilesCount+3)` (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:304`), and `UnsafeCloseFrom` skipping runtime poll fds before `linux.Exec` (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils_unix.go:101-128`) with `close_range(CLOSE_RANGE_CLOEXEC)` fast path. docker-agent has no equivalent beyond pipe wiring; its `checkWorkDir` preflight is the closest hygiene (`pkg/tools/builtin/shell/shell.go:316-342`).
- **Copy when:** any supervisor that spawns before exec; use `close_range` when available, `Readdirnames` loop fallback otherwise (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils_unix.go:21-35`).
- **Evidence:** `TestFdLeaks` (`studies/aren-go-runtime-study/sources/runc/libcontainer/integration/exec_test.go:1693-1780`) catches regressions.

### P10. Structured exit taxonomy (status vs signal vs timeout vs setup vs cleanup)

- **Problem:** callers need to distinguish "command failed" from "timed out" from "failed to start."
- **Demonstrated by:** docker-agent `formatCommandOutput` checks `timeoutCtx.Err()` → `ctx.Err()` ? "cancelled" : "timed out" else `cmdErr` → "Error executing..." (`pkg/tools/builtin/shell/shell.go:344-360`); `monitorJob` handles `exec.ErrWaitDelay` as success if `ExitCode==0` else `*exec.ExitError` → `statusFailed` (`pkg/tools/builtin/backgroundjobs/backgroundjobs.go:286-326`); hooks return structured `ExitCode` vs `-1` (`pkg/hooks/handler.go:248-257`). runc `utils.ExitStatus` maps `128+signal` if signaled (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils.go:18-23`), hook `Command.Run` selects on `timerCh` → `Kill()` with `"hook ran past ..."` message (`studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:620-633`), and setup failures annotate `"possibly OOM-killed"` via `OOMKillCount` delta (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:791-809`).
- **Why it works:** typed/branched classification prevents conflating cancellation with failure.
- **Copy when:** always; surface exit code structurally, not embedded in an error string (docker-agent's shell embeds via `err.Error()` only).
- **Gap:** neither source fully separates cleanup failure from run failure; runc logs freeze/thaw warnings but returns only `GetAllPids` errors (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:699-717`).

## Key Differences

**Containment primitive.** docker-agent uses a userspace-chosen class (pgid / job object) set around `exec`; runc uses kernel-enforced classes (PID namespace / cgroup) with `clone3` placement. The former is portable and unprivileged; the latter is atomic and leak-proof. The Windows job-object race (`Start` → `AssignProcessToJobObject` window) and the Unix `setsid` escape are direct consequences of the userspace choice; `CLONE_INTO_CGROUP` is the kernel answer to the same race.

**OS coverage.** docker-agent ships `cmd_unix.go` / `cmd_windows.go` / `cmd_js.go` triplets — best-effort everywhere, strong nowhere. runc is explicitly Linux-only (`//go:build !windows`, `studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:1`, vendor-only Windows code). For Aren's `shell` tool the docker-agent model is the only viable one; for an optional privileged sandbox the runc model is the strong counterpart.

**Pipe discipline.** docker-agent's primary defense is `WaitDelay` with time-bounded truncation; runc's primary defense for control planes is avoiding stdio pipes altogether (dedicated `SOCK_SEQPACKET` sync + log forwarding goroutine) and `pidfd+Poll` for fifos. Both leave the *payload* stdio unbounded — docker-agent's sync shell and runc's container stdio/hook buffers are the shared gap.

**Output bounding.** docker-agent bounds background jobs (10 MB `limitedWriter`) but not the synchronous shell, script_shell, hooks, or MCP stdio; runc bounds neither hook output nor container stdio (scanner 10 MB only for eval). The inconsistency is product-shaped: long-lived servers (background jobs) visibly needed a bound, short commands did not — until an attacker influences `cmd`.

**Timeout/cancellation API.** docker-agent has first-class `RunShellArgs.Timeout` (default 30s) with manual `context.WithTimeout` + `select` on `timeoutCtx.Done()` vs `done<-Wait()` (`pkg/tools/builtin/shell/shell.go:136-238`); background jobs distinguish `statusStopped` via `CompareAndSwap` (`pkg/tools/builtin/backgroundjobs/backgroundjobs.go:425-440`). runc has no `context.Context` on `Container.Start/Run/exec` — only hook `time.NewTimer` (`studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:595-633`) and mount-remap `context.WithTimeout(1*time.Minute)` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:682-775`).

**Descriptor hygiene.** runc is exhaustive (`CloseExecFrom`, `UnsafeCloseFrom`, `haveCloseRangeCloexec` probing, `TestFdLeaks`); docker-agent has no fd CLOEXEC pass beyond pipe wiring and relies on `bytes.Buffer` writers.

**Reaping.** Both reap eagerly: docker-agent `reapSpawnedChild` + `WaitDelay` handling of `exec.ErrWaitDelay`; runc `execSetns` decodes JSON pid then `os.FindProcess(pidFirst).Wait()` to reap stage1 zombie (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:595-629`), `signals.go:reap()` loop `Wait4(-1,WNOHANG)` (`studies/aren-go-runtime-study/sources/runc/signals.go:52-127`), and `ignoreTerminateErrors` filtering (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:1206-1228`).

**Privilege/namespacing.** docker-agent has no dropping — only `sudoAskpass` token (`pkg/tools/builtin/shell/askpass.go:58-63`) and full `os.Environ()` inheritance. runc drops via `NoNewPrivileges` → `prctl(PR_SET_NO_NEW_PRIVS)` (`studies/aren-go-runtime-study/sources/runc/libcontainer/standard_init_linux.go:153-206`), `setupUser` `Setgroups/Setgid/Setuid` (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:467-512`), capabilities, seccomp via `pidfd_getfd` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:1106-1117`), and `verifyCwd()` breakout detection (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:271-368`).

## Tradeoffs

**Portable group-kill vs kernel-atomic kill.** Benefit of pgid/job: works without privilege on all major OSes, sub-millisecond setup. Cost: incomplete domain (detached children, nested jobs) and post-Start race. Best-fit: interactive tooling like Aren's local `shell`. Failure mode: `setsid` leak; mitigated by documenting non-guarantee and using `WaitDelay` to at least unblock. Alternative: PID namespace + cgroup — atomic but Linux-only and privileged.

**`WaitDelay` responsiveness vs completeness.** Benefit: 500ms–1s bounds `Wait()` regardless of descendant pipe holds (docker-agent fix for `docker run &` hang). Cost: truncates grandchild output, SIGPIPE-kills its next write. Best-fit: always set a `WaitDelay`; tune per call (short for interactive shell, long for log capture like eval's 10s). Failure mode: still-running grandchild loses trailing output — acceptable for liveness; unacceptable for audit — then avoid pipe inheritance via file redirection.

**`cgroup.kill` atomicity vs freeze latency.** Benefit: race-free, no enumeration. Cost: requires cgroup v2 + delegation. Best-fit: privileged sandbox with `CLONE_INTO_CGROUP`. Failure mode: rootless without delegation silently degrades to single-init kill (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:349-353` warns but proceeds). Alternative: freeze-enumerate-kill — reliable but adds freeze latency even for SIGTERM handlers.

**Early join (`CLONE_INTO_CGROUP`) vs post-Start `AddPid`.** Benefit: eliminates escape window. Cost: `clone3` + cgroupfd plumbing, kernel-dependent fallback. Best-fit: always attempt when cgroup is the domain; fallback is free.

**Bounded output vs unbounded fidelity.** Benefit: prevents OOM from attacker-influenced or verbose commands. Cost: truncated output must be surfaced to the LLM/caller without breaking parsing. Best-fit: bound every `bytes.Buffer` path; `limitedWriter` that returns `len(p)` is the right adapter because it never blocks the child.

**Full-env inheritance vs hermetic filtering.** docker-agent `append(os.Environ(), ...)` keeps tools functional (PATH/HOME) but leaks secrets; runc's `prepareEnv` dedups + NUL-validates + HOME injection and `Config`+`Process` merge with per-process overrides. Best-fit for Aren: allow-list + last-wins dedup (docker-agent's `toolsetEnv` shape, runc's `prepareEnv` hygiene).

**SIGTERM-first vs SIGKILL-first.** docker-agent SIGTERM-first respects cleanup handlers but lets ignorer survive until escalation (and only the direct pid is SIGKILLed on escalation). runc SIGKILL for init-kill is immediate and kernel-enforced. Best-fit: SIGTERM-first for shell tools (user may trap), but re-kill the *group* on escalation, not just the leader.

## Decision Guide

**Choose the supervisor shape by privilege and OS need:**

- **Unprivileged, cross-platform shell tools (Aren Phase 8 default)** → docker-agent model. `exec.Command` + `SysProcAttr{Setpgid:true}` on Unix, Job Objects on Windows, `cmd.Cancel = func() error { return syscall.Kill(-pid,SIGTERM) }` + `WaitDelay` so `context.WithTimeout` triggers group kill automatically (Go 1.20+), `limitedWriter` on every buffer. Accept and document the `setsid` / nested-job non-guarantee.

- **Privileged, Linux-only sandbox (Aren Phase 17 optional hardening)** → runc model. Wrap execution in a PID namespace or at minimum a delegated cgroup v2 scope, use `CLONE_INTO_CGROUP` + `cgroup.kill` / freeze fallback, `CloseExecFrom`, `Pdeathsig`, and `verifyCwd`. Do not attempt to retrofit this onto every `shell` call — gate behind `--sandbox` or a `systemd-run --scope` wrapper.

- **Intermediate (Linux, unprivileged, no namespace)** → hybrid. Use pgid like docker-agent plus, when available, a per-invocation cgroup scope via `systemd-run --scope` or lightweight `cgroup` wrapper to get `cgroup.kill` without full container bootstrap.

**Decision rules carried from the sources:**

- If any descendant may background itself (`&`, `docker run &`, `setsid`) → you must set `WaitDelay` or avoid pipe inheritance (redirect to file). No `WaitDelay` is a bug (`pkg/tools/builtin/shell/script_shell.go:240-293` and `pkg/hooks/handler.go:224-259` are the negative examples).
- If output size is not statically known → bound it. 10 MB background bound in docker-agent is the existence proof; extend to shell with a temp-file spill or ring buffer.
- If `AssignProcessToJobObject` or `AddPid` happens after `Start` → assume a race; prefer early-join or document the window.
- If `RootlessCgroups` without delegation → treat descendant kill as best-effort and surface the warning; do not claim containment.

## Practical Tips

1. **Unify supervision into one helper.** docker-agent's biggest gap is inconsistency: 2 of 6 exec sites hardened, 4 not. Extract `pkg/subprocess` used by `shell`, `background_jobs`, `script_shell`, `hooks`, `MCP stdio`, and `environment` so `SysProcAttr`/`WaitDelay`/`limitedWriter` cannot be forgotten (`pkg/tools/builtin/shell/shell.go:188-233` vs `pkg/tools/builtin/shell/script_shell.go:240-293`).

2. **Adopt `Cancel` + `WaitDelay` uniformly (Go 1.20+).** Set `cmd.Cancel = func() error { return syscall.Kill(-cmd.Process.Pid, syscall.SIGTERM) }` (Unix) and `cmd.WaitDelay = 500ms–1s` on every `exec.Cmd`. This collapses docker-agent's manual `select` on `timeoutCtx.Done()` into stdlib cancellation and aligns with eval's `Cancel: SIGINT` pattern (`pkg/evaluation/eval.go:471-502`). Without this, `CommandContext` kills only the direct child.

3. **Bound every buffer.** Replace `commandOutput.bytes.Buffer` unbounded (`pkg/tools/builtin/shell/shell.go:62-91`) with `limitedWriter` (10 MB or 2–5 MB) or a temp-file spool. Always return `len(p)` while dropping excess so the child never blocks on a full buffer. Add `[Output truncated at N MB]` like `pkg/tools/builtin/backgroundjobs/backgroundjobs.go:377-382`.

4. **Re-kill the group on escalation.** On the 2–3s escalation path, send `Kill(-pgid, SIGKILL)` before `Kill(pid)` — docker-agent currently SIGKILLs only the direct pid (`pkg/tools/builtin/shell/shell.go:229`), so a SIGTERM-ignoring pgid member survives.

5. **Set `Pdeathsig` when you can.** `SysProcAttr.Pdeathsig = SIGTERM` (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:648-654`) makes orphaned children die if the agent crashes. Skip only when parent is PID 1 without NEWPID (the documented exception). This is ~1 line and closes the agent-crash leak that pgid alone cannot.

6. **Scrub fds with `CloseExecFrom`.** Probe `close_range(CLOSE_RANGE_CLOEXEC)` then fallback to fd-directory walk (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils_unix.go:21-35,74-128`), skipping runtime poll fds. Add a `TestFdLeaks`-style regression (`studies/aren-go-runtime-study/sources/runc/libcontainer/integration/exec_test.go:1693-1780`) that compares `fdList` before/after `runContainer`.

7. **Handle `exec.ErrWaitDelay` explicitly.** Treat `Wait()` returning `ErrWaitDelay` as success if `ProcessState.ExitCode()==0` (`pkg/tools/builtin/backgroundjobs/backgroundjobs.go:291-301`); otherwise map to `statusFailed`. For runc's control planes, log `FatalLevel` from `ForwardLogs` separately (`studies/aren-go-runtime-study/sources/runc/libcontainer/logs/logs.go:31-49`).

8. **Reap on setup failure.** Any error after `Start` must `SIGTERM → 2s → SIGKILL → Wait` via a shared `reapSpawnedChild` before returning, swallowing termination errors to surface the original cause (`pkg/tools/builtin/shell/shell.go:207-213`; `studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:464-480`).

9. **Validate `cwd` and `env` before fork.** Preflight `checkWorkDir` (`pkg/tools/builtin/shell/shell.go:316-342`) + `verifyCwd` after `Chdir` (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:271-368`); dedup env reverse-iteration with NUL rejection (`studies/aren-go-runtime-study/sources/runc/libcontainer/env.go:24-97`). Note the TOCTOU caveat and ensure `cmd.Dir=cwd` is explicit (`pkg/tools/builtin/shell/shell.go:195`).

10. **Document non-guarantees per platform.** Copy hook docs (`docs/guides/headless/index.md:87`) and runc's rootless warning (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:832-835`) into `shell` and `background_jobs` `Instructions()`: Unix pgid limits, Windows assignment race + nested-job failure, js/wasm no-op, absence of cgroup/namespace for local tools.

11. **Pin pipe-hang and descendant-kill with tests.** Port `TestShellTool_BackgroundedChildDoesNotBlockReturn` timing test and `TestReapSpawnedChild` (`pkg/tools/builtin/shell/shell_test.go:334-451`) plus runc's `TestHostPidnsInitKill`/`TestSharedPidnsInitKill` with `sleep 1h` + `Signal(SIGKILL)` → `Wait` both (`studies/aren-go-runtime-study/sources/runc/libcontainer/integration/exec_test.go:1371-1427`). Assert cgroup pids are 0 after kill when delegation is available.

## Anti-Patterns / Caution Signs

- **Unsupervised exec sites alongside supervised ones.** `script_shell` (`pkg/tools/builtin/shell/script_shell.go:240-293`) and `hooks` (`pkg/hooks/handler.go:224-259`) using bare `CommandContext` + `Run()` with no `SysProcAttr`/`WaitDelay` while `shell` is hardened — any new tool that copies the simpler template silently regresses. Caution sign: `grep` for `exec.Command` finds sites without `platformSpecificSysProcAttr`.
- **Unbounded `bytes.Buffer` on attacker-influenced output.** `commandOutput` (`pkg/tools/builtin/shell/shell.go:62-91`) and runc hook `bytes.Buffer` (`studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:600`) — one `cat`, `yes`, or verbose hook OOMs the parent. Caution sign: `bytes.Buffer` as `Stdout` without a `limitedWriter` or file spool.
- **Post-Start group/job assignment without race acknowledgement.** Windows `AssignProcessToJobObject` after `Start` (`pkg/tools/builtin/shell/cmd_windows.go:20-73`) with no comment about the escape window; similarly post-Start `AddPid` without `CLONE_INTO_CGROUP` attempt. Caution sign: `Start` and `Assign`/`AddPid` separated by arbitrary code.
- **SIGTERM-ignorer survival via single-pid escalation.** `kill(-pgid,SIGTERM)` then `Kill(pid,SIGKILL)` (`pkg/tools/builtin/shell/shell.go:221-233`) — group members ignoring SIGTERM survive because escalation is not re-directed at the group. Caution sign: escalation path that does not re-address the kill domain.
- **Missing `WaitDelay` on piped commands.** Any `StdoutPipe`/`StderrPipe` or `bytes.Buffer` wiring without `WaitDelay` inherits the `&`-grandchild hang. Caution sign: `exec.Cmd` literal without `WaitDelay` field.
- **Full `os.Environ()` inheritance without filtering.** `toolsetEnv` `append(os.Environ(), ...)` (`pkg/tools/builtin/shell/shell.go:277-287`) leaks secrets; `script_shell` at least rejects undeclared keys like `LD_PRELOAD` (`pkg/tools/builtin/shell/script_shell.go:271-273`) but the main shell does not. Caution sign: `os.Environ()` passed through without allow-list.
- **Silent non-guarantee.** No doc that `setsid`/daemonized children escape pgid, that Windows nested jobs fail, or that js/wasm has no containment (`pkg/tools/builtin/shell/cmd_js.go:15-24` is the only explicit no-op). Caution sign: `Instructions()` with no containment caveat.
- **Inconsistent `Cmd` reuse.** runc's `cloneCmd` before retry without cgroupfd (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:445-456`) exists because `exec.Cmd` cannot be reused after `Start` — reusing the same `Cmd` is a latent `ErrWait already called` bug (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:1206-1228`).
- **Freeze without thaw, or freeze for non-SIGKILL.** runc correctly freezes only for `SIGKILL` paths (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:688-699`); freezing for `SIGTERM` would stall graceful handlers. Caution sign: unconditional `Freeze` on every `Signal`.
- **Lint without coverage.** `ConstructorCommandExec` forbids `exec` in constructors (`lint/constructor_command_exec.go:10-54`) but no lint enforces `WaitDelay`/`SysProcAttr` on every exec site — the exact gap docker-agent fell into.

## Notable Absences

- **No per-tool cgroup/namespace/resource bounding in docker-agent.** No `RLIMIT_NOFILE`/`RLIMIT_AS`, `Setrlimit`, CPU/memory limits, or `unshare` per shell invocation; outer Docker sandbox is the only isolation and it does not bound individual `exec` calls. runc provides the counter-model but requires privilege.
- **No generic `context.Context` cancellation in runc.** Only hook mounts have timeouts; `Container.Start/Run/exec` cannot be cancelled via context (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:204-231` negative evidence). The termination pattern is `defer` + `terminate()` on startup error, not context propagation.
- **No output bounding for container stdio in either source.** docker-agent bounds only background jobs; runc bounds nothing for container processes. Both leave memory exhaustion to the caller.
- **No cross-platform descendant-inspection tests.** docker-agent has timing regression tests but no `ps`/`/proc`/job-enumeration asserting no surviving descendant; runc has `TestFdLeaks` and PID-namespace kill tests but no hung-pipe/orphan test under cgroup delegation matrix. No test exercises the `setsid` escape or Windows assignment race under controlled conditions.
- **No `Pdeathsig` in docker-agent.** Unix children are not configured to die if the agent crashes; runc sets it (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:648-654`) and documents the PID1 exception.
- **No Windows containment in runc.** `grep` for job objects yields only vendor (`studies/aren-go-runtime-study/sources/runc/vendor/golang.org/x/sys/windows/*.go` negative evidence).
- **No idempotency guard for concurrent `Signal`/`Destroy`.** runc's `Container.signal` holds `m` (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:438-442`) but `destroy` (`studies/aren-go-runtime-study/sources/runc/libcontainer/state_linux.go:39`) does not; concurrent kill/destroy behavior is unspecified.
- **No fd CLOEXEC hardening in docker-agent** beyond pipes; runc's `CloseExecFrom` / `UnsafeCloseFrom` / `close_range` probing has no analog.

## Per-Source Notes

Brief anchors; the synthesis above carries the comparative weight.

- **docker-agent (5/10):** Unprivileged Go `os/exec` supervisor for `shell` and `background_jobs`. Correct pgid/job-object scoping, `WaitDelay` pipe fix, and SIGTERM→SIGKILL ladder for its two main runners, but inconsistent across six exec sites, unbounded synchronous output, and best-effort termination with documented races. Best-in-study source for portable patterns Aren can lift directly; weakest on uniform hardening and resource bounding.

- **runc (6/10):** Privileged Linux OCI runtime. Kernel-strong containment via PID namespace + cgroup.kill/freeze with `CLONE_INTO_CGROUP` early join, exhaustive fd closure, and typed exit/OOM taxonomy. Linux-only, no generic context cancellation or output bounding, hook buffers unbounded. Best-in-study source for what "guaranteed" tree-kill actually requires and what it costs; not a drop-in model for Aren's local tools without privilege.

## Open Questions

1. **Is `script_shell`'s lack of supervision intentional?** No comment or test addresses whether `pkg/tools/builtin/shell/script_shell.go:240-293` bypassing `SysProcAttr`/`WaitDelay`/bounding is a trusted-admin assumption or an oversight. If Aren introduces script-admin execution, this must be decided explicitly.

2. **What truncation UX does Aren want for bounded output?** 10 MB `limitedWriter` with `[Output truncated]` works for background jobs; synchronous shell needs a policy (prefix+truncation notice vs temp-file spill vs ring buffer) that preserves LLM-parsable structure.

3. **Should escalation re-kill the group?** docker-agent's current SIGKILL targets only the leader; re-sending `Kill(-pgid,SIGKILL)` closes the SIGTERM-ignorer leak at the cost of a slightly harsher second signal. runc's cgroup path avoids the question entirely — which semantic does Aren promise?

4. **Does Aren need `Pdeathsig` and `CloseExecFrom` by default?** Both are low-cost (one `SysProcAttr` field, one pre-Start syscall) and close the agent-crash orphan and fd-leak vectors. Is the Linux-only nature acceptable for a cross-platform tool?

5. **What is the containment claim for `--sandbox` vs local tools?** `pkg/sandbox/sandbox.go:28-170` wraps the agent in Docker, but `shell`/`background_jobs` still run as host processes unless the whole agent is containerized. Should Phase 17 execution types optionally route through the sandbox per-call to get real cgroup/namespace isolation?

6. **Can `Container.Start/Run` gain `context.Context` in runc's model, and should Aren's sandbox?** Hook timeout (`studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:620-633`) shows the pattern; generalizing it would let Aren cancel startup with `signalAllProcesses` and a startup timeout for `parseSync`/`ForwardLogs` (currently unbounded, `studies/aren-go-runtime-study/sources/runc/libcontainer/sync.go:189-203`).

7. **How is the Windows assignment race tested?** Neither source has a test that asserts grandchildren spawned between `Start` and `AssignProcessToJobObject` are killed. If Aren must guarantee Windows tree-kill, does it need a pre-start job assignment (e.g., `CREATE_SUSPENDED` + assign + resume) or a different primitive?
