## Executive Summary

Two sources, two deliberately different scopes, and one lesson: Aren's executor boundary should stay narrow, type-specific, and local-first until a measured requirement proves otherwise.

- **Nomad** is a worker manager. It solves distributed-readiness problems with a narrow `DriverPlugin` gRPC contract, server-authoritative allocation state, `AllocModifyIndex` as a monotonic fencing analogue, node-level heartbeats, and graceful client disconnect handling — all without per-task leases or remote driver RPC. Rating: **9/10**.
- **runc** is a kernel-mediated container runtime. It solves nothing at the application layer because the kernel *is* the worker. Identity is `(PID, start_time)`, acknowledgement is a SOCK_SEQPACKET sync handshake, and the only "remote" capability is CRIU's TCP page-server for checkpoint streaming. Rating: **4/10** on the distributed rubric, by design.

Convergence: both treat the executor boundary as deliberately thin (11/12 method interface), keep type-specific concerns behind an opaque or capability-flagged seam, and use atomic-on-disk state (`state.json`, `LocalState` in BoltDB) as the durability anchor. Divergence: where Nomad implements at-least-once + idempotent acceptance via batched `Node.UpdateAlloc` and `AllocModifyIndex`, runc collapses "submitted" and "accepted" to a single in-process handshake. Nomad proves you can do thousands of allocs per node without remote executor RPC; runc proves you can be fully local and still have a rigorous executor contract.

Aren should copy the narrow-interfaces-plus-capability-flags pattern from Nomad, the kernel-tuple identity and explicit state-machine-per-state from runc, and the persistent-handle recovery from both. Arenis explicitly warned against adopting leases, fencing tokens, artifact-transfer services, or remote driver RPC until a single-node bottleneck is measured.

## Core Thesis

**A narrow, capability-declared executor interface — type-specific where semantics demand it, persistent-handle-based where recovery matters, and server-authoritative where state diverges — scales further than any premature remote layer.** Nomad demonstrates the production-scale proof (thousands of allocations per node, multiple isolated runtimes, crash recovery); runc demonstrates the deliberate non-distributed floor (kernel-mediated identity, atomic state, sync-socket handshake). Aren should adopt the narrow-contract-and-capability pattern, defer leases and fencing tokens until a measured stale-completion race appears, and keep executors in-process or local subprocess rather than introducing a remote RPC surface that complicates isolation without demonstrated gain.

## Approach Models

### Nomad: Capability-Adapter with Server Authority

Nomad partitions the problem along three axes:

1. **Scheduler / client split.** The server (Raft FSM + scheduler) is sole authority for allocation placement; the client owns local lifecycle through `allocRunner` → `taskRunner` → `DriverPlugin` (`client/allocrunner/alloc_runner.go:373-416`, `client/allocrunner/taskrunner/task_runner.go:570-798`).
2. **Two-tier isolation: Driver → Executor.** The `DriverPlugin` interface (`plugins/drivers/driver.go:50-68`) handles runtime-specific actions (docker, qemu, java, exec, raw_exec); the lower `Executor` interface (`drivers/shared/executor/executor.go:60-97`) handles OS process isolation (cgroups, namespaces, chroot) for the `exec` family via `UniversalExecutor`. Docker bypasses the Executor layer entirely, talking directly to the Docker daemon.
3. **Capability-driven extension.** Every driver declares `Capabilities{SendSignals, Exec, FSIsolation, NetIsolationModes, MustInitiateNetwork, MountConfigs}` (`plugins/drivers/driver.go:166-196`); the scheduler filters feasibility before dispatch rather than encoding type-specific knowledge.

This produces type-specific success/cancellation/output semantics (docker image pull vs. raw process vs. qemu VM), a uniform supervisor loop (prestart hooks → driver start → poststart hooks → wait → restart), and a single point of duplication (`AllocModifyIndex`) that handles both retry and stale completion.

### runc: Kernel-Mediated Local Executor

runc answers the dimension by structural refusal: the kernel is the worker.

- **Executor seam.** `Container` struct (`sources/runc/libcontainer/container_linux.go:33-46`) binds a single host root and a state dir to a single init process; the inner `parentProcess` interface (`sources/runc/libcontainer/process_linux.go:38-57`) abstracts four flavors (`initProcess`, `setnsProcess`, `restoredProcess`, `nonChildProcess`).
- **Identity.** `(PID, start_time)` captured from `/proc/PID/stat` at `procReady` time (`sources/runc/libcontainer/process_linux.go:1010`, `sources/runc/libcontainer/container_linux.go:948-951`). Reattach reads `state.json` and refuses to act if the tuple does not match — kernel-mediated fencing without application tokens.
- **Acknowledge.** SOCK_SEQPACKET `syncSocket` carries typed sync messages (`procReady`, `procRun`, `procHooks`, `procMountPlease`, `procSeccomp`) (`sources/runc/libcontainer/sync.go:41-203`); the parent sends `procRun` only after `procReady`, the init `execve`s only after `procRun`. No retry, no timeout on the sync socket itself.
- **State machine.** Explicit struct-per-state (`stoppedState`, `runningState`, `createdState`, `pausedState`, `restoredState`, `loadedState`) enforces legal transitions (`sources/runc/libcontainer/state_linux.go:84-245`).

The result is a runtime that has leases, heartbeats, fencing, and duplicate-dispatch protection — except they are all kernel primitives (`/proc` stat, cgroup freezer, clone flags), not application protocols.

## Pattern Catalog

### 1. Narrow interface with capability flags (Nomad)

- **Problem:** A single executor type cannot encode docker image pull semantics, raw process isolation, qemu VM lifecycle, and java JVM tuning without becoming a union type with dozens of optional methods.
- **Demonstrated by:** Nomad — `DriverPlugin` is 11–12 methods, every other concern is a `Capabilities` bit or opaque `TaskConfig.rawDriverConfig` (`plugins/drivers/driver.go:50-68`, `plugins/drivers/driver.go:166-196`).
- **Why it works:** Forces scheduler/client to treat drivers uniformly while preserving room for type-specific features. New drivers add capabilities without changing the interface.
- **When to copy:** Whenever Aren has more than one executor flavor with divergent runtime semantics.
- **When overkill:** When there is only one executor type and no concrete need for the second. A narrow interface without multiple implementations is just premature abstraction.
- **Evidence:** `plugins/drivers/driver.go:50-68`, `plugins/drivers/driver.go:166-196`, `drivers/docker/driver.go`, `drivers/exec/driver.go`, `drivers/qemu/driver.go`.

### 2. Persistent handle + `RecoverTask` (Nomad)

- **Problem:** Agent crash mid-task must not duplicate work or lose state.
- **Demonstrated by:** Nomad — `StartTask` returns `TaskHandle{Version, Config, State, DriverState}` (`plugins/drivers/task_handle.go:13-22`), persisted to BoltDB `LocalState` (`client/allocrunner/taskrunner/state/state.go:14-28`); on restart, `RecoverTask(handle)` reattaches without replaying (`plugins/drivers/client.go:157-162`).
- **Why it works:** The handle is opaque and driver-defined, so the supervisor never inspects driver internals. Recovery is part of the contract, not a special case.
- **When to copy:** Whenever the executor outlives a single supervising process invocation.
- **When risky:** If `RecoverTask` semantics are not contract-tested. Nomad's gap: no integration test kills the plugin mid-task and asserts `WaitTask` recovery without duplicate `TaskStarted`.
- **Evidence:** `plugins/drivers/task_handle.go:13-22`, `client/allocrunner/taskrunner/task_runner.go:1244-1325`, `plugins/drivers/client.go:157-162`.

### 3. Atomic state persistence with identity tuple (runc)

- **Problem:** Crash before or after a meaningful boundary must leave either zero state or fully consistent state — never partial.
- **Demonstrated by:** runc — `state.json` is written via `CreateTemp` + `Rename` only after `procReady` (`sources/runc/libcontainer/container_linux.go:882-906`), and carries `(InitProcessPid, InitProcessStartTime)` as the durable identity receipt (`sources/runc/libcontainer/container_linux.go:871-906`).
- **Why it works:** Atomic rename eliminates torn writes; the start-time tuple eliminates PID-reuse spoofing on reattach.
- **When to copy:** Always, at any boundary that must survive crash. The rename pattern is two lines; the start-time discipline is harder but cheap.
- **When overkill:** For ephemeral state that is recomputable from upstream sources.
- **Evidence:** `sources/runc/libcontainer/container_linux.go:871-906`, `sources/runc/libcontainer/factory_linux.go:124-148`.

### 4. Server-authoritative state, client-monotonic reporting (Nomad)

- **Problem:** Multiple writers (clients) and one reader (server/operator) must converge without leases.
- **Demonstrated by:** Nomad — `AllocModifyIndex` is the fencing analogue: client discards stale server updates if `oldUpdate.AllocModifyIndex > update.AllocModifyIndex` (`client/allocrunner/alloc_runner.go:1038-1042`); server's Raft FSM decides final allocation state; client-reported `TaskStates/ClientStatus` are validated, not authoritative (`client/client.go:2376-2383`).
- **Why it works:** Convergence through monotonic IDs is cheaper than leases and works across partitions without explicit fencing tokens.
- **When to copy:** Whenever there is a natural authority (server, scheduler, leader) and a set of reporters.
- **When risky:** If there is no obvious authority, or if reporters must act without consulting it.
- **Evidence:** `client/client.go:2608-2614`, `client/allocrunner/alloc_runner.go:1036-1047`, `client/util.go:44-46`, `client/client.go:2376-2383`.

### 5. Hook-based lifecycle composition (Nomad)

- **Problem:** Setup steps (artifacts, vault, identity, network, cgroup assignment) vary across drivers but follow a common shape — run before the driver, after the driver, etc.
- **Demonstrated by:** Nomad — `prestart` → `runDriver` → `poststart` → `wait` → `exited` → `stop` (`client/allocrunner/taskrunner/task_runner.go:640-682`); each hook is an `interfaces.TaskPrestartHook` with `Done` persistence (`client/allocrunner/taskrunner/state/state.go:74-99`).
- **Why it works:** Hooks are replayable after crash (Done flag persisted), composable across drivers, and don't require the driver interface to know about them.
- **When to copy:** Whenever executor setup has multiple orthogonal concerns (auth, artifact fetch, resource assignment, network setup) that should not all be driver-specific.
- **When overkill:** If setup is one step and never varies.
- **Evidence:** `client/allocrunner/taskrunner/task_runner.go:570-798`, `client/allocrunner/taskrunner/state/state.go:74-99`.

### 6. Two-tier separation: driver semantics vs. OS process isolation (Nomad)

- **Problem:** OS-level isolation (cgroups, namespaces, pty, chroot) is shared across multiple executor flavors but must not be re-implemented per driver.
- **Demonstrated by:** Nomad — `Executor` interface (`drivers/shared/executor/executor.go:60-97`) is the lower boundary; `UniversalExecutor.Launch` configures cgroups, user, workdir, FIFOs, starts in process group; `Shutdown` sends signal, waits grace, kills process tree (`drivers/shared/executor/executor.go:360-440`, `:616-688`).
- **Why it works:** `exec`, `java`, `qemu` share `UniversalExecutor`; docker does not (it talks to Docker daemon directly). The boundary is real but optional.
- **When to copy:** When OS-level process control is shared but higher-level semantics diverge.
- **When overkill:** When every executor already needs custom process control.
- **Evidence:** `drivers/shared/executor/executor.go:60-97`, `:360-440`, `:616-688`.

### 7. SOCK_SEQPACKET sync handshake for parent-child acknowledgment (runc)

- **Problem:** Parent and init must coordinate multi-stage setup (namespace creation, cgroup apply, config delivery, execve) without races or message-boundary confusion.
- **Demonstrated by:** runc — two sockets: `initSock` (bootstrap config + final PID, stream) and `syncSock` (typed sync messages, SOCK_SEQPACKET) (`sources/runc/libcontainer/process_linux.go:59-116`, `sources/runc/libcontainer/sync_unix.go:18-85`).
- **Why it works:** SOCK_SEQPACKET preserves message boundaries (one sync message = one `recvmsg` call); typed messages eliminate parsing ambiguity; FDs can travel via `SCM_RIGHTS` on the same channel.
- **When to copy:** Whenever a parent process must coordinate a multi-stage child initialization that carries file descriptors.
- **When overkill:** For one-shot "fork and exec" with no shared setup.
- **Evidence:** `sources/runc/libcontainer/sync.go:41-203`, `sources/runc/init_linux.go:422-431`, `sources/runc/libcontainer/process_linux.go:512-525`.

### 8. Node-level heartbeat + `stop_after_client_disconnect` (Nomad)

- **Problem:** Partitioned workers must not publish authoritative completion, but per-task leases add write amplification.
- **Demonstrated by:** Nomad — node `HeartbeatTTL` (`client/client.go:2226`) and `heartbeatStop` watch loop (`client/heartbeatstop.go:57-70`); after disconnect timeout, local allocs are destroyed; scheduler concurrently marks them `AllocClientStatusLost` (`scheduler/util.go:777-795`).
- **Why it works:** Lost detection happens at the node granularity; allocation-level reconciliation uses `AllocModifyIndex`. Lease cost is O(allocations) avoided.
- **When to copy:** When worker count is large and liveness signal can be aggregated.
- **When risky:** During the window between heartbeat expiry and local destroy, the same job may run twice. Acceptable for idempotent batch/service work; not for exactly-once.
- **Evidence:** `client/client.go:177-179`, `:1926-2292`, `client/heartbeatstop.go:49-126`, `scheduler/util.go:777-795`.

### 9. Explicit state-machine struct per state (runc)

- **Problem:** Illegal transitions (destroy while running, exec on stopped container) must fail with typed errors, not silently corrupt state.
- **Demonstrated by:** runc — `stoppedState`, `runningState`, `createdState`, `pausedState`, `restoredState`, `loadedState` each enforce legal transitions; invalid returns `stateTransitionError` (`sources/runc/libcontainer/state_linux.go:84-245`).
- **Why it works:** Method dispatch on the state struct makes illegal calls impossible at compile time (the state struct simply does not have the method).
- **When to copy:** Whenever executor lifecycle has more than three states with non-trivial transition rules.
- **When overkill:** For simple linear lifecycles.
- **Evidence:** `sources/runc/libcontainer/state_linux.go:84-245`.

### 10. FIFO + logmon for output streaming without driver log awareness (Nomad)

- **Problem:** Drivers should not need to implement log collection; the runtime should observe output uniformly.
- **Demonstrated by:** Nomad — `TaskConfig.StdoutPath/StderrPath` are FIFOs (`plugins/drivers/driver.go:300-301`); `logmon` collects without driver involvement; drivers advertising `DisableLogCollection` opt out (`plugins/drivers/driver.go:188-189`).
- **Why it works:** Output path is a filesystem location, not a driver API. Adding log shipping later touches only `logmon`.
- **When to copy:** Whenever executor output should be observable regardless of driver implementation.
- **When overkill:** If output is fully managed by the driver (e.g., docker logs to a driver-specific sink).
- **Evidence:** `plugins/drivers/driver.go:300-301`, `plugins/drivers/driver.go:188-189`, `client/allocrunner/taskrunner/task_runner.go:1233-1236`.

## Key Differences

| Axis | Nomad | runc | Why |
|------|-------|------|-----|
| **Worker model** | Per-node client supervises many allocations; client is the worker | Per-process runc supervises one init; kernel is the worker | Nomad is a scheduler/runtime; runc is a container CLI |
| **Remote execution** | None — drivers are local `go-plugin` subprocesses | None for supervisor; CRIU page-server is the only TCP touchpoint | Both have deliberately local executors; remote readiness is future work |
| **Identity** | `AllocID → TaskName → TaskConfig.ID` (UUID) | `(PID, start_time)` from `/proc/PID/stat` | Nomad's identity spans nodes and sessions; runc's is kernel-bound |
| **Acknowledgement** | Batched `Node.UpdateAlloc` RPC + `AcknowledgeState` | SOCK_SEQPACKET `syncSocket` (typed messages) | Nomad is cross-process on a different node; runc is fork+exec on same kernel |
| **Stale-completion prevention** | `AllocModifyIndex` monotonicity + server `lost` transition | `(PID, start_time)` match on reattach | Nomad defends against partitioned clients; runc defends against PID reuse |
| **Durability anchor** | BoltDB `LocalState` + `PendingUpdates` queue | Atomic `state.json` rename | Both survive crash; granularity differs (task vs. container) |
| **Cancellation** | Signal → exponential backoff (`5s*4^i` capped at 2m) → `StopTask` | SIGTERM → `signalAllProcesses` over cgroup → SIGKILL | Nomad coordinates with driver via RPC; runc uses cgroup as authoritative ground |
| **Idempotency** | `AllocModifyIndex` dedup + no-op priority filter | None needed — one-shot CLI invocation | Nomad is at-least-once by design; runc is exactly-once by construction |
| **Setup before "accepted"** | Artifact prestart must complete before `StartTask` | Init must reach `procReady` before `procRun` sent | Both have a real "accepted" point distinct from "submitted" |
| **Artifact / mount transfer** | `artifactHook` with `go-getter` + hash dedup | `goCreateMountSources` goroutine + `procMountPlease` sync messages | Nomad fetches to `AllocDir` before start; runc passes FDs at exec time |

## Tradeoffs

### Narrow interface vs. rich semantics

- **Benefit:** Uniform supervisor loop, extensible driver set, scheduler agnostic to driver internals.
- **Cost:** Type-specific concerns live in opaque `rawDriverConfig` (msgpack, untyped) and `Capabilities` bit flags — harder to audit end-to-end resource accounting.
- **Best-fit context:** Many executor types with divergent semantics; scheduler must remain generic.
- **Failure mode:** Drivers abuse opaque config to encode data the scheduler needs; capabilities become a sprawl of flags.
- **Alternative (runc):** Thin interface, thick per-flavor body. Each executor flavor owns its own `start()`. Less reusable across types, but no opaque config.

### Server-authoritative state vs. per-task leases

- **Benefit:** No lease renewals; convergence via monotonic IDs is cheaper than distributed locks.
- **Cost:** Window between heartbeat expiry and local destroy: same job may run twice. For exactly-once tasks, this is unacceptable.
- **Best-fit context:** Idempotent batch/service work; large worker counts where lease amplification is a real cost.
- **Failure mode:** Zombie process publishes `Node.UpdateAlloc` after the server marked allocation `lost`; server must win via state transition, not fencing.
- **Alternative (runc):** Kernel-enforced identity prevents zombie actions — but only because the worker IS the kernel.

### BoltDB persistence on every state event vs. batched persistence

- **Benefit:** Crash recovery is bounded by last completed event; no replay-from-zero.
- **Cost:** fsync overhead per event; mitigation via `WithBatchMode` at alloc-runner scope (`client/allocrunner/alloc_runner.go:1206`).
- **Best-fit context:** Tasks where recovery latency dominates start cost.
- **Failure mode:** Hot-loop events (e.g., artifact prestart restart on transient error) drive up fsync pressure.
- **Alternative (runc):** Single atomic write per container lifecycle (`state.json` after `procReady`); events are in-memory until commit.

### `go-plugin` out-of-process isolation vs. in-process executors

- **Benefit:** Plugin crash does not take down client; driver restart via `joincontext` cancellation and `RecoverTask` (`plugins/drivers/client.go:30-38`, `client/allocrunner/taskrunner/task_runner.go:817-844`).
- **Cost:** gRPC serialization (msgpack/proto) and an extra hop even for `exec` tasks; `ErrPluginShutdown` recovery adds complexity.
- **Best-fit context:** Multiple driver types with different trust or stability profiles.
- **Failure mode:** Transient plugin restart can trigger `RETRY` result without idempotency key, risking duplicate work if `DestroyTask` is missed (`plugins/drivers/proto/driver.proto:176-182`).
- **Alternative (runc):** In-process init via `clone(CLONE_NEW*)`; no IPC, but no isolation between supervisor and child.

### Sync-socket handshake vs. blocking fork+exec

- **Benefit:** Multi-stage setup (cgroup apply, namespace create, config delivery, execve) is race-free; FD handoff via `SCM_RIGHTS`.
- **Cost:** More moving parts; if init dies before `procReady`, parent has no clean retry path (`sources/runc/libcontainer/process_linux.go:778-1063`).
- **Best-fit context:** Executors with non-trivial per-process initialization that cannot be done by the parent before fork.
- **Failure mode:** Sync socket fd leaked if init dies mid-handshake; `state.json` may be written but parent died before `procRun`, leaving an orphaned init.
- **Alternative (Nomad):** Blocking `StartTask` RPC; setup done in driver process, results returned synchronously.

### Kernel-mediated identity vs. application tokens

- **Benefit:** No token issuance, rotation, or revocation; identity is provable from `/proc`.
- **Cost:** Only works for executors where the worker IS the kernel process (i.e., init). A separate worker process would need a kernel-derived nonce or signed token.
- **Best-fit context:** Single-process container runtime.
- **Failure mode:** If init is reaped by someone else, `hasInit` returns false and every subsequent operation fails (`sources/runc/libcontainer/container_linux.go:946-951`); no tombstone beyond `state.json`.
- **Alternative (Nomad):** Application-issued handle (`TaskHandle`) persisted to BoltDB; identity is whatever the driver returned.

## Decision Guide

### When to copy the narrow-interface-with-capability-flags pattern

- Copy when there are ≥2 executor types with divergent runtime semantics and the supervisor must remain generic. Do not copy for a single executor type — it is premature abstraction.

### When to use server-authoritative state vs. per-task leases

- Use server-authoritative when there is a natural authority (server, scheduler, leader) and the work is idempotent. Add leases only if exactly-once is mandatory and zombie-process completion races are observable. Use kernel-mediated identity (runc) when the worker IS the kernel and cannot outlive the supervisor.

### When to persist `TaskHandle` for recovery

- Persist handles whenever the executor outlives a single supervising process invocation. Skip if each invocation is one-shot and re-creation is cheap.

### When to use atomic state.json rename

- Use atomic rename at every boundary that must survive crash: identity receipt, allocation state, executor config. Two lines of code eliminate torn writes.

### When to introduce hook-based lifecycle composition

- Introduce when setup has ≥3 orthogonal concerns (auth, artifact fetch, resource assignment, network setup) and they vary across executor types. Skip for one-step, never-varying setup.

### When to introduce the two-tier Driver → Executor separation

- Introduce when OS-level process control (cgroups, namespaces, pty, chroot) is shared across executor flavors but higher-level semantics diverge. Skip when every executor already needs custom process control.

### When to use SOCK_SEQPACKET sync handshake

- Use when parent and child must coordinate multi-stage setup that carries file descriptors. Skip for one-shot fork+exec with no shared setup.

### When to add explicit state-machine struct per state

- Add when the executor lifecycle has ≥3 states with non-trivial transition rules. Skip for linear lifecycles.

## Practical Tips

1. **Define `Capabilities` early.** Even if you ship one driver, the schema is cheap and forces you to think about which executor features are uniform and which are negotiated.
2. **Make driver config opaque (msgpack or cbor).** Do not let driver-specific fields leak into the generic allocation path. Validate via `TaskConfigSchema` (hclspec-style).
3. **Persist the handle synchronously after `StartTask`.** Don't batch — the handle is what makes recovery deterministic.
4. **Emit `TaskStarted` only after acceptance.** "Accepted" means the executor reached a point where it can durably report its own state. For init: after `procReady`. For a driver: after `StartTask` returns.
5. **Use `AllocModifyIndex` (or equivalent monotonic ID) before reaching for leases.** Most distributed-readiness problems are solved by making the authority authoritative and reporters monotonic.
6. **Adopt atomic state-file rename as a default.** Two lines that prevent an entire class of crash-corruption bugs.
7. **Capture `(PID, start_time)` if the executor forks directly.** It is the cheapest fencing you will ever get.
8. **Bind a unique state directory per executor instance.** `allocdir.NewAllocDir(root, id)` (Nomad) or per-container state dir (runc) — gives you isolation, recovery, and GC for free.
9. **Make cancellation explicit: signal → grace → force-kill with backoff.** Nomad's `5s*4^i` capped at 2m (`client/allocrunner/taskrunner/task_runner.go:1129-1153`) is a good starting point; tune per workload.
10. **Treat CRIU `--page-server` as a transport, not as a remote executor API.** It is one-way page streaming, not a control plane.
11. **Batch state updates to reduce RPC pressure, but persist handles synchronously.** The asymmetry is intentional — handle durability is a recovery invariant, state updates are eventual consistency.

## Anti-Patterns / Caution Signs

1. **Premature lease / heartbeat per task.** If you have not observed a stale-completion race, leases are write amplification for nothing. Nomad's node-level heartbeat + `stop_after_client_disconnect` handles partitioned workers without per-task state.
2. **Application-level fencing tokens before measuring the race.** Nomad succeeds without them; runc uses kernel-mediated start-time matching. Add a fencing epoch to `TaskHandle` only if a partitioned client actually publishes authoritative completion after reschedule.
3. **Remote executor RPC "for scale".** Drivers behind network RPC add serialization, partition handling, and auth for no measured gain. Nomad proves local `go-plugin` drivers scale to thousands of allocations per node.
4. **Opaque driver config without `TaskConfigSchema` validation.** Lets drivers encode data the scheduler needs in untyped msgpack — guarantees future debugging pain.
5. **BoltDB sync on every state event without batching mitigations.** Drives up fsync overhead on hot paths; if you must persist every event, batch at the alloc-runner scope (`WithBatchMode`, `client/allocrunner/alloc_runner.go:1206`).
6. **Ignoring cgroup failure as a warning.** `UniversalExecutor.Launch` warns but continues if not root (`drivers/shared/executor/executor.go:388-394`); tasks silently lose isolation. This is a security boundary; fail loudly.
7. **No duplicate-dispatch guard when `StartTask` is retryable.** Nomad's `RETRY` result without idempotency key (`plugins/drivers/proto/driver.proto:176-182`) leaks containers if `DestroyTask` is missed on retry. If your protocol supports retry, include a dedup token.
8. **Sync socket without timeout.** If init dies mid-handshake, parent can block forever. runc accepts this trade-off because the supervising process is the only reader; a remote executor must add timeouts.
9. **State struct without method-based enforcement.** If you write `state.Status() == Running` checks before every operation, use struct-per-state dispatch (runc) instead. Compile-time illegality is cheaper than runtime illegality.
10. **Treating CRIU `--page-server` as a general remote-execution primitive.** It is one-way TCP page streaming; the supervision protocol is still local.

## Notable Absences

- **Nomad:** no per-task fencing token; no per-task lease; no remote driver RPC (and `remote_tasks` reserved slot deliberately removed in `plugins/drivers/proto/driver.proto:410`); no idempotency key for `StartTask` retry; no integration test for stale worker publishing after `AllocClientStatusLost`; no test that kills the plugin mid-task and asserts `WaitTask` recovery without duplicate `TaskStarted`.
- **runc:** no application-level distributed mechanics of any kind — no leases, no heartbeats, no fencing tokens, no duplicate-dispatch protection, no lost-worker reconciliation, no remote submission API, no tests for remote/distributed executor (only `seccompagent` and `pidfd-kill` Unix-socket helpers exercise FD handoff). The only built-in "remote" capability is CRIU's `--page-server` TCP page streaming, and runc passes it through transparently.
- **Both:** neither demonstrates a typed error vocabulary for distributed failure modes (e.g., `ErrWorkerLost`, `ErrStaleCompletion`, `ErrDuplicateDispatch`). runc's `ErrExist`, `ErrInvalidID`, `ErrNotExist`, `ErrPaused`, `ErrRunning`, `ErrNotRunning`, `ErrNotPaused`, `ErrCgroupNotExist` are host-local only.

## Per-Source Notes

### Nomad — narrow capability-driven executor boundary

- **Approach:** Server (Raft FSM + scheduler) is sole authority for allocation placement. Client `allocRunner` → `taskRunner` drives type-specific drivers via `DriverPlugin` gRPC boundary. Two-tier isolation: `DriverPlugin` (runtime semantics) + `Executor` (`UniversalExecutor`, OS process isolation) used by `exec`/`java`/`qemu`, bypassed by docker.
- **Common contract:** 11-method `DriverPlugin` interface (`plugins/drivers/driver.go:50-68`) plus `Capabilities` negotiation and `Fingerprint` health streaming.
- **Type-specific extension:** opaque `TaskConfig.rawDriverConfig` (msgpack) decoded via `DecodeDriverConfig`; per-driver schemas (docker `config.go`, qemu `driver.go`, java `driver.go`); `Capabilities` flags; `FSIsolation` (none/chroot/image/unveil); lower `Executor` boundary only for `exec` family.
- **Identity:** `AllocID → TaskName → TaskConfig.ID` (short UUID). Hierarchical and durable.
- **Cancellation:** `handleKill` → `preKill` → `ShutdownDelay` → `killTask` with `5s*4^i` exponential backoff capped at 2m, 5 tries max → `StopTask(taskID, killTimeout, killSignal)`.
- **Streaming:** FIFO stdout/stderr + `logmon`; `ExecTaskStreamingRawDriver` and `ExecTaskStream` for interactive exec.
- **Artifacts:** `artifactHook` prestart with concurrent workers (3), `PreviousState` hash dedup, `go-getter` direct to `AllocDir`.
- **Acknowledge:** Two-stage — server `Plan` via Raft, client `AllocStateUpdated` batched via `Node.UpdateAlloc` RPC, `AcknowledgeState` persists on success.
- **Heartbeat:** Node-level `HeartbeatTTL` (no per-task leases); `heartbeatStop` watch loop.
- **Lost-worker reconciliation:** `stop_after_client_disconnect` timeout triggers local destroy; scheduler marks `AllocClientStatusLost` and reschedules.
- **Duplicate dispatch:** `AllocModifyIndex > existIndex` filter (`client/util.go:44-46`, `client/client.go:2608-2614`); `pendingUpdates.restore(toSync)` on RPC failure for at-least-once + idempotent.
- **Cleanup:** `AllocGarbageCollector` (disk threshold, inode threshold, max allocs); `destroyAllocRunner` → `ar.Destroy` → `killTasks` → destroy hooks → `DeleteAllocationBucket`.
- **Recovery:** `taskRunner.Restore` loads `LocalState`+`TaskState` from BoltDB, `restoreHandle` → `driver.RecoverTask(handle)` else `DestroyTask(force)`.

### runc — local-first kernel-mediated executor

- **Approach:** CLI binding a single container to a single host root; `Container` struct holds state dir, cgroup manager, init process; `parentProcess` Go interface abstracts four flavors (`initProcess`, `setnsProcess`, `restoredProcess`, `nonChildProcess`).
- **Common contract:** `parentProcess` interface (`sources/runc/libcontainer/process_linux.go:38-57`) with `pid`, `start`, `terminate`, `wait`, `startTime`, `signal`, `externalDescriptors`, `setExternalDescriptors`, `forwardChildLogs`; `Process` user struct with `Wait`, `Pid`, `Signal`, FD management.
- **Type-specific extension:** Each flavor owns its own `start()` because ack semantics genuinely differ:
  - `initProcess.start`: bootstrap dance (cgroups, CPU affinity, namespace setup, config delivery, `procReady`/`procRun` handshake) (`sources/runc/libcontainer/process_linux.go:778-1063`).
  - `setnsProcess.start`: joins existing container via `CLONE_INTO_CGROUP`, reads joined PID from `initSock` (`sources/runc/libcontainer/process_linux.go:459-629`).
  - `restoredProcess.start`: refuses (`sources/runc/libcontainer/restored_process.go:31-33`).
  - `nonChildProcess` (Load path): refuses start, terminate, wait (`sources/runc/libcontainer/restored_process.go:89-103`).
- **Identity:** `(PID, start_time)` from `/proc/PID/stat` captured at `procReady`; reattach must match the tuple.
- **Cancellation:** `Container.Signal` → init `signal`; SIGKILL on non-private-PID triggers `signalAllProcesses` over cgroup with rootless fallback to `signalInit`.
- **Streaming:** `tty` + `setupIO` (PTY vs stdio); pty master FD passed via `_LIBCONTAINER_CONSOLE` extra-fd slot.
- **Artifacts (mount transfer):** `goCreateMountSources` goroutine (CLONE_FS detach, joins container mntns, services `procMountPlease`); returns fds via `procMountFd`.
- **Artifacts (seccomp):** `procSeccomp` sync carries child FD; parent uses `pidfd_getfd` to clone into own process, then `cmsg.SendRawFd` over Unix socket.
- **Acknowledge:** SOCK_SEQPACKET `syncSocket` with typed messages (`procError`, `procReady`, `procRun`, `procHooks`, `procHooksDone`, `procMountPlease`, `procMountFd`, `procSeccomp`, `procSeccompDone`); init `execve`s only after `procRun`; no retry, no timeout on sync socket itself.
- **State machine:** Explicit struct-per-state (`stoppedState`, `runningState`, `createdState`, `pausedState`, `restoredState`, `loadedState`); illegal transitions return `stateTransitionError`.
- **Heartbeat:** None — cgroup freezer + `/proc` stat + PID start-time is the liveness ground.
- **Lost-worker reconciliation:** None — `Load` + `refreshState` assume the kernel still knows about init.
- **Duplicate dispatch:** None — CLI invocation is one-shot, kernel enforces single-PID-1-per-container via clone-flags.
- **Cleanup:** `destroy()` tears down cgroup + intelrdt + state dir, runs `Poststop` hooks; paused must Resume first; `restoredState` checks for `checkpoint` dir.
- **Recovery:** `state.json` atomic rename after `procReady`; `Load` reads state, `nonChildProcess` refuses to act if `(PID, start_time)` mismatch.

## Open Questions

1. **What is the seam where Aren should attach leases and fencing if a stale-completion race becomes observable?** Nomad's gap is per-task fencing; runc's is application-level entirely. A hybrid could promote `(PID, start_time)` into a richer executor handle with a kernel-derived nonce — but only if Aren needs workers that outlive the supervisor.
2. **Should Aren's `StartTask` retry include an idempotency key?** Nomad's `RETRY` result (`plugins/drivers/proto/driver.proto:176-182`) does not include dedup; if a driver misses `DestroyTask`, a retry creates a new container. Adding a `TaskConfig.ID`-based dedup is cheap and closes the duplicate-execution edge case.
3. **How should Aren test that a partitioned client's late `Node.UpdateAlloc` is rejected after the allocation is `lost`?** Both sources lack this test. Nomad's server `lost` transition is the safety net; a contract test would prove it.
4. **Is CRIU's `--page-server` a credible foundation for Aren's remote cold-start?** runc passes it through transparently; the supervision protocol is still local. If Aren adds remote restore, it would compose with CRIU rather than extend runc.
5. **What typed errors does a remote executor need?** runc's `ErrExist`, `ErrRunning`, `ErrNotRunning`, etc. are host-local. A remote layer needs `ErrWorkerLost`, `ErrStaleCompletion`, `ErrDuplicateDispatch` — and they must be checkable across the network boundary.
6. **At what point does Nomad's batched `Node.UpdateAlloc` + `AcknowledgeState` pattern break down under allocation churn?** Nomad mitigates with `GetUpdatePriority` dedup; a stress test would surface the threshold where RPC latency dominates allocation time.
7. **Does Aren's setup-before-accepted semantic need a richer handshake than Nomad's artifact prestart or runc's `procReady`/`procRun`?** Both sources define "accepted" as a real point distinct from "submitted", but neither generalizes — the question is whether Aren's drivers need a multi-stage handshake like runc's sync socket, or whether a single blocking RPC like Nomad's `StartTask` suffices.
