## Executive Summary

Two production Go agent runtimes answer the same Phase 9/10 question — how to keep model turns, tool calls, budgets, context compaction, and cancellation coherent without becoming a prompt framework — with opposite ownership choices. Crush delegates iteration to `charm.land/fantasy` (`internal/agent/agent.go:685`, `internal/agent/agent.go:796`) and adds only two `StopWhen` guards (context-window at `internal/agent/agent.go:1037-1062` and loop-detection at `internal/agent/loop_detection.go:19`), yielding a heuristic-bounded, summarize-only compaction model (`internal/agent/agent.go:1329`, `internal/message/message.go:174`). Docker-agent owns its loop explicitly in `pkg/runtime/loop.go:230-260` as `RunStream`→`runTurn`→`handleStream`→`Dispatcher.Process`→compaction/budget/iteration checks, layering hard iteration caps (`pkg/runtime/loop_steps.go:48-127`), a canonical-signature degenerate-loop detector (`pkg/runtime/toolexec/loop_detector.go:24-91`), cost/token/wall-clock budgets (`pkg/runtime/budget.go:338-373`), calibrated context-window compaction (`pkg/compaction/compaction.go:19-77`), and pre-send token truncation (`pkg/session/session.go:829-842`, `pkg/session/session.go:2506-2535`).

Both converge on three non-negotiable invariants: transcript `tool_use`↔`tool_result` pairing must survive compaction (crush via `preparePrompt` repair at `internal/agent/agent.go:1527-1687`, docker-agent via `sanitizeToolCalls` at `pkg/session/session.go:2434-2495` and boundary snapping at `pkg/compaction/compaction.go:279-313`); terminal evidence must outlive cancellation (both use `context.WithoutCancel` + timeout — crush at `internal/agent/agent.go:509`, docker-agent at `pkg/runtime/loop.go:758`); and bounding must be evaluated at a defined loop boundary, not inside provider callbacks. They diverge on enforcement timing and evidence retention: crush reports budgets post-hoc with no pre-flight gate (`internal/agent/agent.go:1906-1946`, `internal/agent/usage_fallback.go:18`) and discards structured tool outputs behind a single LLM summary; docker-agent enforces iteration pre-work but still records spend post-hoc, allowing a one-turn overshoot (`pkg/runtime/budget.go:385-407` vs `338-373`). Neither preserves verbatim evidence supporting a final answer — both replace pre-`SummaryMessageID`/`FirstKeptEntry` history with natural-language paraphrase — and neither provides a provenance or artifact graph beyond `ToolCallID` and per-message `Cost/Usage`.

For Aren, the transferable core is small: an explicit loop boundary that checks hard iteration, loop-detector, budget, and compaction in fixed order; read-time transcript sanitization; detached bounded contexts for terminal writes; and a one-turn-overshoot-aware budget model. What must be added fresh is evidence-preserving compaction and pre-flight cost admission — both sources prove omission is the default.

## Core Thesis

**A bounded agent loop is not a token limit; it is an ordering discipline over four gates evaluated at the same iteration boundary, plus an invariant repair that runs at every compaction seam.**

Both sources prove that no single guard bounds a model that keeps requesting tools: crush's two heuristics alone let any model producing distinct `toolName+input+output` signatures loop indefinitely (`internal/agent/loop_detection.go:11-39`, `internal/agent/agent.go:1037-1062`), and docker-agent's own analysis admits that zeroing all numeric limits leaves only signature-exact repetition as a stop (`pkg/runtime/toolexec/loop_detector.go:54-77`). The sources that bound reliably do so by layering independent ceilings (iteration cap checked first at `pkg/runtime/loop.go:498-503`, loop detector after batch at `pkg/runtime/loop.go:928-956`, budget before next turn at `pkg/runtime/budget.go:338-373`, overflow retry bounded to 1 at `pkg/runtime/loop_steps.go:179-196`) so an infinite loop must defeat them simultaneously. The second half of the thesis is where sources converge despite different mechanisms: compaction will orphan tool exchanges unless the seam is repaired as a read-time invariant, not a write-time aspiration. Crush repairs orphans in `preparePrompt` (`internal/agent/agent.go:1626-1687`) with synthetic `ToolResultOutputContentError`; docker-agent snaps kept-tails to `user`/`assistant` boundaries (`pkg/compaction/compaction.go:294-313`) and sanitizes every `GetMessages` call with `sanitizeToolCalls` (`pkg/session/session.go:2434-2495`) that the comment explicitly attributes to compaction producing Bedrock rejections. Either approach satisfies provider strictness; only a mechanism that survives compaction without persisting synthetic rows can claim coherence.

Cancellation separates the two models by architecture, not quality: crush fans one `genCtx` to both stream and tools simultaneously (`internal/agent/agent.go:643-646`, `internal/agent/agent.go:796`) so a single `ac.cancel()` reaches whichever phase is active via the fantasy bridge; docker-agent alternates phases strictly sequentially (`pkg/runtime/streaming.go:73-104` then `pkg/runtime/toolexec/dispatcher.go:254-266`), so there is never a moment where both are active to cancel jointly, but each phase is promptly cancelable in isolation. The divergence is a valid response to embedding model — delegated library versus integrated runtime — not a ranking.

The dominant failure seam is shared: budgets are accounts, not gates. Both sources compute cost after the turn (`internal/agent/agent.go:1906`, `pkg/runtime/budget.go:385-407`) and check it before the next, guaranteeing that the violating turn already spent. A design that promises "never exceed N" must price the prompt before calling the provider — neither source does.

## Approach Models

**crush — delegated iteration with heuristic guards.** The loop is `sessionAgent.Run` (`internal/agent/agent.go:566`) calling `fantasy.NewAgent(...).Stream(genCtx, ...)` (`internal/agent/agent.go:685-796`). Turn plumbing lives in callbacks: `PrepareStep` drains the queue (`internal/agent/agent.go:808`), `OnToolCall`/`OnToolResult` persist `message.Tool`/`message.Assistant` turns (`internal/message/message.go:163`, `internal/message/message.go:218`), `OnStepFinish` computes `FinishReason` and updates usage (`internal/agent/agent.go:808-1036`, `internal/agent/agent.go:1906`). Bounding is two `StopWhen` conditions evaluated *during* streaming: context-window remaining (`internal/agent/agent.go:1038-1056`, thresholds `largeContextWindowThreshold=200_000`, `largeContextWindowBuffer=20_000`, `smallContextWindowRatio=0.2` at `internal/agent/agent.go:53-60`) and repeated tool-call loop detection (`internal/agent/loop_detection.go:19`, SHA256 of `toolName+input+output`, `window=10`/`maxRepeats=5` at `internal/agent/loop_detection.go:11-14`). Compaction is a natural-language summary via `Summarize` (`internal/agent/agent.go:1329`) stored as `IsSummaryMessage=true` (`internal/message/message.go:174`) pointed to by `Session.SummaryMessageID` (`internal/session/session.go:50-63`), with `getSessionMessages` (`internal/agent/agent.go:1689-1709`) slicing history to that index and rewriting the summary role to `User`. Transcript coherence is repaired at read time in `preparePrompt` (`internal/agent/agent.go:1527`) via orphan filtering and synthetic error-injection. This model fits a TUI app minimizing code against a provider-abstracting library; it leaves hard iteration bounding to fantasy (no `WithMaxSteps` found in `internal/agent/agent.go:685`) and budgets to post-hoc reporting (`MaxOutputTokens` passthrough only at `internal/agent/agent.go:791-803`).

**docker-agent — owned sequential loop with layered gates.** The loop is `RunStream` → `runStreamLoop` → `runTurn` in `pkg/runtime/loop.go:230-260` with mutable `loopState` (`pkg/runtime/loop.go:628-653`) threading `iteration`, `loopDetector`, `overflowCompactions`, and `prevTurnMadeToolCalls`. Each turn executes a fixed ordering: `enforceMaxIterations` at the very top (`pkg/runtime/loop.go:498-503`, `pkg/runtime/loop_steps.go:48-127`) → `enforceBudget` before model call (`pkg/runtime/loop.go:507-512`, `pkg/runtime/budget.go:338-373`) → `ShouldCompact` check (`pkg/runtime/loop.go:569-572`, `pkg/compaction/compaction.go:69-77` with calibrated estimator at `pkg/compaction/compaction.go:99-172`) → `fallback.execute`/`handleStream` (`pkg/runtime/streaming.go:73-104`) → `recordBudget` immediately after stream (`pkg/runtime/loop.go:841-842`, `pkg/runtime/budget.go:385-407`) → `Dispatcher.Process` for tools (`pkg/runtime/toolexec/dispatcher.go:254-266`) → `LoopDetector.Record` (`pkg/runtime/loop.go:928-956`, `pkg/runtime/toolexec/loop_detector.go:24-91`). Compaction is a dedicated `pkg/runtime/compactor` package (`pkg/runtime/compactor/compactor.go:148-288`) that clones the compaction model, runs a throwaway sub-session, and calls `sess.ApplyCompaction` (`pkg/runtime/session_compaction.go:65-152`). Transcript assembly is a pure-function middleware chain (`pkg/session/session.go:2290-2362`, `2434-2495`, `2553-2630`) including `SplitIndexForKeep`, `trimMessages`, `sanitizeToolCalls`, `capToolResultContent`, and `truncateOldToolContent`. This model fits a long-lived, multi-model platform owning cost and context centrally via `budgetSet` (`pkg/runtime/budget.go:229-320`) and `resolveContextLimit` (`pkg/runtime/session_compaction.go:237-295`); the price is sequential throughput and heuristic evidence retention.

These are responses to embedding shape, not quality tiers: an app leaning on a vendor-abstracting framework correctly delegates iteration; a platform mediating teams, budgets, and models must own the boundary explicitly.

## Pattern Catalog

### P1. Fixed-order layered bounding at the iteration boundary

- **Problem:** A model that keeps requesting tools with varying arguments defeats any single heuristic.
- **Demonstrated by:** docker-agent explicitly — `enforceMaxIterations` (`pkg/runtime/loop.go:498-503`) → `enforceBudget` (`pkg/runtime/loop.go:507-512`) → `ShouldCompact` (`pkg/runtime/loop.go:569-572`) → stream → `recordBudget` (`pkg/runtime/loop.go:841-842`) → `LoopDetector.Record` (`pkg/runtime/loop.go:928-956`), plus `maxOverflowCompactions=1` (`pkg/runtime/runtime.go:386`, `pkg/runtime/loop_steps.go:179-196`). Crush shows the absence: only two `StopWhen` guards at `internal/agent/agent.go:1037-1062` with no hard `MaxSteps`/`MaxToolCalls`.
- **Why it works:** Each ceiling is independent; defeating one leaves three others. Iteration is checked pre-work (hard gate), detector post-batch (signal), budget pre-next-turn (quota), overflow retries bounded (recovery loop cap).
- **Copy when:** any loop where the provider controls continuation. The ordering — iteration first, budget second, compaction third, detector after tools — is itself a transferable detail.
- **Overkill/risky when:** bounded demo harnesses with known max depth; layering adds config surface and the one-turn overshoot (see P6) confuses callers expecting hard caps.
- **Evidence:** docker-agent's `enforceMaxIterations` raising cap by +10 on approval (`pkg/runtime/loop_steps.go:48-127`); crush's note that distinct signatures evade `loop_detection.go:11-39`; docker-agent stream idle timeout 5m (`pkg/runtime/streaming.go:19-39`).

### P2. Read-time transcript invariant repair (orphan filtering + synthetic results)

- **Problem:** Interruption, cancellation, and compaction seams orphan `tool_use` without `tool_result` (or vice versa), bricking strict providers (Bedrock requires paired counts).
- **Demonstrated by:** both — crush's `preparePrompt` builds `knownToolCallIDs`/`knownToolResultIDs` then drops orphaned results (`internal/agent/agent.go:1626-1653`) and injects synthetic error results (`internal/agent/agent.go:1662-1687`, `"tool call was interrupted..."`); docker-agent's `sanitizeToolCalls` synthesizes `No result provided` and drops orphaned `tool` messages lacking pending `tool_use` (`pkg/session/session.go:2434-2495`), with an explicit comment citing the compaction-boundary Bedrock case, plus `trimMessages` invariant at `pkg/session/session.go:2290-2362`.
- **Why it works:** Repair runs on every history assembly before the provider call, so persisted synthetic rows are not required and interrupted sessions remain callable.
- **Copy when:** any transcript that persists assistant and tool turns separately (SQLite, file, event log) and any flow where cancellation or compaction can split an exchange.
- **Risky when:** treated as authoritative history — synthetic errors (`internal/agent/agent.go:1676`) become model-visible and may be misinterpreted as real failures without a marker distinguishing them.
- **Evidence:** crush tests `TestPreparePrompt_OrphanedToolUse` at `internal/agent/agent_test.go:757`; docker-agent comment at `pkg/session/session.go:2429` motivating `sanitizeToolCalls`; crush error-path synthesis at `internal/agent/agent.go:1107-1149`.

### P3. Boundary-snapped keep-tail for compaction

- **Problem:** Truncating by token count mid-exchange orphans the retained tail.
- **Demonstrated by:** docker-agent most clearly — `SplitIndexForKeep` walks backward accumulating calibrated estimates and snaps to `MessageRoleUser/Assistant` boundary (`pkg/compaction/compaction.go:279-313`), never starting the kept window inside a `tool_use`↔`tool_result` exchange; `buildSessionSummaryMessages` injects summary as a synthetic `user` message `Session Summary: ...` at `pkg/session/session.go:1969-2037`. Crush achieves the same crudely via `getSessionMessages` slicing at `SummaryMessageID` (`internal/agent/agent.go:1689-1709`) but without calibrated token accounting.
- **Why it works:** The kept window is always a sequence of complete exchanges, so P2's repair has minimal work and provider validation never sees a truncated turn.
- **Copy when:** any compaction, truncation, or `NumHistoryItems` trimming that keeps a tail. This is smaller than the summarization itself yet more load-bearing for correctness.
- **Overkill when:** transcripts without tool calls — plain chat slicing suffices.
- **Evidence:** docker-agent `SplitIndexForKeep` returning `len(messages)` when everything fits (`pkg/compaction/compaction.go:279-313`); crush `msgs[0].Role=User` rewrite at `internal/agent/agent.go:1689-1709`.

### P4. Summarize-as-compaction with a summary pointer (discard-before, keep-after)

- **Problem:** Fitting unbounded history into a bounded context window without unbounded growth.
- **Demonstrated by:** both — crush `Summarize` creates `IsSummaryMessage=true` (`internal/agent/agent.go:1373`) and sets `Session.SummaryMessageID` (`internal/agent/agent.go:1455`), resetting `CompletionTokens, PromptTokens, Cost` (`internal/agent/agent.go:1456-1458`); docker-agent `doCompact` calls `compactor.RunLLM` then `sess.ApplyCompaction` with `Item{Summary, FirstKeptEntry, Cost, Model, Usage}` (`pkg/runtime/session_compaction.go:65-152`, `pkg/session/session.go:921-927`, `pkg/runtime/compactor/compactor.go:285-311`).
- **Why it works:** A single pointer replaces retain-all growth; recent turns stay verbatim within `keepTokenBudget` (`20k` default, scaled to `contextLimit/5` at `pkg/runtime/compactor/compactor.go:148-288`).
- **Copy when:** context windows are shared budgets and verbatim history would exceed them. For Aren Phases 9-10, expose the kept budget per agent — docker-agent's scaling to `contextLimit/5` directly serves small windows (8k GGUF) better than a fixed 20k.
- **Risky:** Lossy for evidence — all `ToolResult` payloads before `FirstKeptEntry`/`SummaryMessageID` are replaced by paraphrase (`pkg/session/session.go:2003-2037`, `internal/agent/agent.go:783`). Docker-agent explicitly notes this as a regression risk for evidence-dependent answers (`pkg/runtime/session_compaction.go:128-139` discussion). Crush's `DisableAutoSummarize` escape hatch (`internal/config/config.go:321`) can disable it entirely, deadlocking on overflow.
- **Evidence:** crush `shouldSummarize` trigger at `internal/agent/agent.go:1192-1207`; docker-agent `compactor.RunLLM` cloning with `WithMaxTokens(summaryTokenBudget)` at `pkg/runtime/compactor/compactor.go:148-288`.

### P5. Calibrated compaction estimator (heuristic + provider deltas, clamped)

- **Problem:** `len/4` heuristics drift from actual tokenizers, causing early or late compaction.
- **Demonstrated by:** docker-agent — `NewEstimator` calibrates `chars/3.5` against provider `prompt` deltas, clamped `0.75-2.0`, `calibrationMinTokens=512` (`pkg/compaction/compaction.go:99-172`), `DefaultThreshold=0.9` at `pkg/compaction/compaction.go:19-77`; `resolveContextLimit` prefers `provider_opts.context_size` then catalogue (`pkg/runtime/session_compaction.go:237-295`) and caps to compaction model's window. Crush contrasts: fixed `largeContextWindowThreshold=200_000`/`Buffer=20_000`/`smallContextWindowRatio=0.2` (`internal/agent/agent.go:53-60`) with no calibration.
- **Why it works:** Deltas reconcile heuristic with reality per provider; clamping and early bias (compact at 90%) trade extra summarization cost for fewer hard overflows.
- **Copy when:** serving multiple providers or local models with divergent tokenizers. Even a single provider benefits — provider Usage may be zero, triggering `fallbackStepUsage` (`internal/agent/usage_fallback.go:18`).
- **Overkill when:** one provider and generous window headroom; fixed threshold suffices.
- **Evidence:** docker-agent proactive trigger `ShouldCompact(input+output+added, contextLimit, threshold)` at `pkg/runtime/loop.go:569-572`; overflow bound `maxOverflowCompactions=1`.

### P6. Record-then-police budget separation (post-turn accounting, pre-next-turn gate)

- **Problem:** Cost/token/time must be measured before it can be policed, but the measurement only exists after the turn.
- **Demonstrated by:** both — crush `updateSessionUsage`/`updateSessionTokenCounters` after `OnStepFinish` (`internal/agent/agent.go:1906-1946`, `fallbackStepUsage` at `internal/agent/usage_fallback.go:18-176` with `approxTokenCount=(len+3)/4` at `usage_fallback.go:171`); docker-agent `recordBudget` after stream (`pkg/runtime/budget.go:385-407`, `pkg/runtime/loop.go:841-842`) and `enforceBudget` before next iteration (`pkg/runtime/budget.go:338-373`, `pkg/runtime/loop.go:507-512`).
- **Why it works:** Separation mirrors quota design — account the turn just finished, gate the turn about to start. Docking shared `budgetSet` across sub-sessions (`pkg/runtime/budget.go:229-320`) makes delegation spend against the root wallet.
- **Failure mode:** One-turn overshoot is guaranteed — a single expensive `MaxTokens` turn can double the cap before the next gate fires. Unpriced models (`nil` cost at `pkg/runtime/loop.go:1121-1130`) never trip `maxCost` (`pkg/runtime/budget.go:205-212` warns only).
- **Copy when:** pricing comes from provider usage. Pair with pre-flight estimation (summation of `EstimateMessageTokens` + `summaryTokenBudget`) if "never exceed" is required — neither source does today.
- **Evidence:** docker-agent `computeMessageCost` at `pkg/runtime/loop.go:1121-1130`; crush cost override via `openrouterCost` (`internal/agent/agent.go:1874`) and session storage (`internal/session/session.go:50-63`, `191-221`).

### P7. Pre-send tool-output truncation (middle-out and old-content)

- **Problem:** Tool results dominate prompt fitting; a single large file read can crowd out reasoning.
- **Demonstrated by:** docker-agent — `capToolResultContent` middle-out truncation per result (head + `[...truncated...]` + tail) at both `AddMessage` and `GetMessages` (`pkg/session/session.go:829-842`, `2553-2630`), and `truncateOldToolContent` replacing older results with `[content truncated]` when `MaxOldToolCallTokens>0` (`pkg/session/session.go:2506-2535`), configured via `agent.maxToolResultTokens`/`maxOldToolCallTokens` (`pkg/agent/agent.go:48-54`, `pkg/agent/opts.go:193-232`). Crush has no equivalent — tool output size is uncapped in `preparePrompt`.
- **Why it works:** Guarantees prompt fits without stopping the loop; recent results stay verbatim, older ones collapse to placeholders.
- **Copy when:** tools return file contents or logs. This is cheaper than compaction and runs per-turn.
- **Watch out:** Middle-out truncation hides stack traces in the removed middle; error diagnostics degrade at tight caps.
- **Evidence:** docker-agent `MaxToolResultTokens` read-time backstop at `pkg/session/session.go:2553-2604`; agent caps via `pkg/agent/agent.go:48-54`.

### P8. Detached bounded contexts plus active-cancel fan-out for terminal correctness

- **Problem:** Cancellation must reach the active phase immediately, yet terminal writes (cost ledger, summary, `RunComplete`) must survive the cancel.
- **Demonstrated by:** both — crush `genCtx=context.WithCancel(runCtx)` registered in `activeRequests` (`internal/agent/agent.go:643-657`) cancelled via `Cancel` calling `ac.cancel()` (`internal/agent/agent.go:1955-2009`), with `persistCanceledTurn` and `FlushAll` using `context.WithoutCancel(ctx)` + `5s` timeout (`internal/agent/agent.go:508-528`, `753-779`), `PublishMustDeliver` `50ms` per subscriber (`internal/pubsub/broker.go:165-236`) and `sessionMu` + `dispatchMu` + `acceptSeqGen`/`cancelMark` protecting cancel-on-entry (`internal/agent/agent.go:185-206`, `591-618`, `493-500`). Docker-agent `handleStream` multiplexes `Recv` with `ctx.Done()` and `idleTimer` 5m (`pkg/runtime/streaming.go:73-104`, `337-354`); batch `context.WithCancelCause(ctx)` aborts sibling tools (`pkg/runtime/toolexec/dispatcher.go:254-266`, `377-382`, `811-845`, `1111-1132`); deferred `turn_end` uses `WithoutCancel` (`pkg/runtime/loop.go:758`).
- **Why it works:** `WithCancel` fan-out gives prompt delivery to the active phase; `WithoutCancel` with bounded timeout ensures evidence is not lost when `genCtx` is canceled and DB shutdown proceeds (`internal/app/app.go:743-761` ordering, docker-agent `UpdateSessionTokens` via `persistence_observer.go:74-164`).
- **Copy when:** any persistence or `RunComplete` path runs under the same context as the model stream. Keep the bounded write at 5s (crush) — unbounded waits wedge `CancelAll` (`internal/agent/agent.go:2026-2034`).
- **Tradeoff:** `WithoutCancel` writes can outlive the session and delay global `CancelAll`'s spin loop; crush notes hung DB writes delay shutdown by the 5s timeout.
- **Evidence:** crush `CompareAndDelete` cleanup at `internal/agent/agent.go:657`; docker-agent `askUser` checking `ctx.Err()` before and while blocked on `Resume` (`pkg/runtime/toolexec/dispatcher.go:811-845`).

## Key Differences

**Who owns iteration.** Crush outsources iteration to `fantasy.Agent.Stream` and reacts via `StopWhen`; docker-agent owns iteration with an explicit `loopState` and checks. The driver is dependency shape: crush's value proposition is provider abstraction via `charm.land/fantasy` (`internal/agent/coordinator.go:1099-1162`), so adding a custom iteration layer would duplicate that abstraction; docker-agent's value is platform supervision (teams, budgets, sub-sessions) that requires central budgeting.

**What counts as "bounded."** Crush bounds context and repeated-signature loops only (`internal/agent/agent.go:1037-1062`); wall-clock, cost, token, and tool-call counts are observed, not bounded, and `MaxOutputTokens` is merely forwarded (`internal/agent/agent.go:791-803`). Docker-agent bounds five dimensions independently — iteration, consecutive-identical-calls, cost, tokens, wall-clock — plus idle and overflow retries. The extra gates cost configuration surface (`maxIterations`, `maxConsecutiveToolCalls`, `maxCost`, `maxTokens`, `maxTime`, `maxToolResultTokens`, `maxOldToolCallTokens`) but close the distinct-signature infinite-loop class that defeats crush.

**How degenerate loops are detected.** Both hash tool exchanges, but differently: crush SHA256s `toolName+input+output` and checks `>5` repeats in last `10` steps (`internal/agent/loop_detection.go:11-39`), so varying outputs evade it; docker-agent hashes canonical JSON per *batch* (`pkg/runtime/toolexec/loop_detector.go:24-91`), threshold `5` via `sess.MaxConsecutiveToolCalls` (`pkg/agent/opts.go:202-208`), but exempts polling tools (`view_background_agent`, `list_background_agents`, `view_background_job`) so background polling never masks a tight loop. The exemption is a liftable refinement regardless of hash scheme.

**How compaction budget is sized.** Crush uses window-relative thresholds (`200k`/`20k`/`20%`) with no calibration; docker-agent calibrates heuristics against provider Usage deltas and scales keep/summary budgets proportionally (`keepBudget=contextLimit/5`, `summaryBudget=contextLimit/4` implicit in `pkg/runtime/compactor/compactor.go:148-288`). Scaling is the material difference for small local models — docker-agent retains less verbatim context at 8k but still fits; crush's small-window path risks repeated `FinishReasonMaxTokens` when `DisableAutoSummarize` is set.

**Persistence contract for streaming.** Crush debounces `message.Service.Update` at `33ms` (`internal/message/message.go:19`) with `shouldFlushNow` sync for terminal tool-call changes (`internal/message/message.go:352-383`, `379-419`), balancing TUI responsiveness and durability; docker-agent persists immediately via `PersistenceObserver` on `MessageAddedEvent`/`TokenUsageEvent`/`SessionSummaryEvent` (`pkg/runtime/persistence_observer.go:74-164`) with no debounce. Either suffices; crush's `Publish`/`PublishMustDeliver` split (`internal/pubsub/broker.go:6-46` vs `165-236`, buffer `4096`, `50ms` MustDeliver) makes lossy streaming explicit while terminal events are bounded-blocking.

**Cancellation topology.** Crush's `genCtx` reaches stream and tools simultaneously through fantasy (`internal/agent/agent.go:643-646`); docker-agent's sequential phases mean stream and tools are never concurrent, so simultaneous fan-out is inapplicable — each phase is cancelable but not jointly (`pkg/runtime/streaming.go:89-104` vs `pkg/runtime/toolexec/dispatcher.go:254-266`). Both satisfy "prompt cancellation of the active phase"; only crush can claim simultaneous if the question is posed literally, but docker-agent's answer is correct for its architecture.

## Tradeoffs

**Heuristic (SHA256 signature) vs hard `MaxSteps`/`MaxToolCalls`.** Benefit of heuristic: content-aware, avoids false termination on alternating valid tools (crush test at `internal/agent/loop_detection_test.go:128`). Cost: distinct-output loops evade it indefinitely (crush unbounded-distinct-loops at `internal/agent/loop_detection.go:11-14`); docker-agent closes the gap with its hard iteration cap, and crush's own future recommendation is `maxSteps=80`/`maxToolCalls=100`. Best-fit: heuristic alone for exploratory coding agents where legitimate long tasks vary; hard cap mandatory for cost-bounded or user-facing loops. Failure mode of hard cap: legitimate multi-file refactors truncated. Alternative per source: pairing — use detector to stop tight loops early, hard cap as deterministic backstop.

**LLM summary vs deterministic truncation for compaction.** Benefit of summary: preserves intent and `TODO`s better than blind truncation (`internal/agent/agent.go:2241-2253` summary prompt). Cost: non-deterministic, extra latency/cost, may hallucinate; token estimates fall back to `approxTokenCount` when Usage is zero (`internal/agent/usage_fallback.go:171`). Docker-agent leans into summarization cost (proactive at 90%); crush incurring summary cost via `largeModel` rather than cheaper model (`internal/agent/agent.go:1335`) is a noted inefficiency. Best-fit: summary for conversational continuity; truncation (`keepTokenBudget` tail only) for evidence-preserving or offline replay loops. Alternative per source: `truncate-oldest` or `keep-tool-results` modes — both sources flag configurability as future work.

**Lossy streaming vs guaranteed terminal publication.** Benefit of lossy `Publish` with `bufferSize=4096` (`internal/pubsub/broker.go:40`): TUI stays responsive during fast token deltas. Cost: slow subscribers drop even `PublishMustDeliver` after `50ms` (`internal/pubsub/broker.go:45`), requiring `Re-fetch on next session-visible event` recovery (`internal/pubsub/broker.go:198-200`). Docker-agent side-steps the tradeoff by separating stream deltas (best-effort) from durable persistence (immediate). Best-fit: lossy for live display, synchronous for audit. Failure: dropped terminal forces consumers to tolerate unpaired `compaction:started` without `completed` (docker-agent hook veto at `pkg/runtime/session_compaction.go:71-76`).

**`WithoutCancel` terminal writes vs bounded shutdown.** Benefit: evidence not lost on cancellation/workspace shutdown (crush `internal/agent/agent.go:509`, `967-981` using parent `ctx`; docker-agent `pkg/runtime/loop.go:758`). Cost: hung DB write holds `CancelAll`'s `5s` spin (`internal/agent/agent.go:2026-2034`) or delays session close. Best-fit: always use detached context with explicit timeout (5s crush, bounded `FlushAll` at `internal/agent/agent.go:753`). Alternative: fire-and-forget terminal writes — correct for loss-tolerant observability but wrong for audit.

**Shared budget set vs per-turn ledger.** Benefit of shared `budgetSet` via `WithBudget`/`WithNamedBudgets` (`pkg/runtime/budget.go:229-320`): delegated agents spend against the root, centralizing cost control. Cost: accumulation is overwrite-style for `PromptTokens` (`internal/agent/agent.go:1939-1946` overwrites, not sums; `Cost` sums) so lifetime prompt tokens cannot be reconstructed post-summarization when counters are reset to summary-only (`internal/agent/agent.go:1456-1458`). Docker-agent's compaction resetting `InputTokens` to heuristic estimate (`pkg/session/session.go:921-927`) adds drift. Best-fit: shared wallet for platform; per-turn ledger for audit — store the latter alongside the summary.

## Decision Guide

**Choosing the loop owner.** If a provider-abstracting library already owns tool dispatch (fantasy, genai, anthropic SDK), delegate iteration as crush does and invest in `StopWhen` plus read-time repair — do not re-implement tool scheduling. If the runtime owns cost, teams, or sub-sessions, own the loop explicitly as docker-agent does via `loopState`; the budgeting and context-resolution logic cannot be retrofitted onto callbacks cleanly.

**Choosing the bounding mix.** Start with this rule: one hard gate (iteration or tool-calls), one pattern gate (degenerate-loop detector), one window gate (context/compaction), one quota gate (cost/tokens/time). Concrete values liftable as-is: `maxSteps=80` + `loopDetectionWindowSize=10`/`maxRepeats=5` (crush `internal/agent/loop_detection.go:11-14`) + threshold `0.9` (`pkg/compaction/compaction.go:19-77`) + expiry bounded by 1 overflow retry (`pkg/runtime/runtime.go:386`). Exempt polling tools from the detector (`pkg/runtime/toolexec/loop_detector.go:79-91`) in any environment with background polling.

**Choosing compensation vs truncation.** Use LLM summary when the loop's next step needs conversational continuity (coding agents). Use deterministic keep-tail + old-result truncation when the final answer must be auditable from retained tool outputs — set `keepTokenBudget = contextLimit/5` and `summaryTokenBudget = contextLimit/4` as docker-agent does, and retain pre-summary tool payloads as a compressed attachment (both sources suggest this as future `SummaryMetadata`).

**Choosing cancellation shape.** If tool execution is delegated to a framework that bridges context into tool calls (fantasy's `OnToolCall`), a single `genCtx` fan-out suffices (`internal/agent/agent.go:643-646`). If the runtime owns dispatch, sequential-phase cancellation is simpler to reason about — just ensure `handleStream` multiplexes `ctx.Done()` (`pkg/runtime/streaming.go:73-104`) and each tool checks `ctx.Err()` before and during `askUser` (`pkg/runtime/toolexec/dispatcher.go:811-845`). Do not claim simultaneous guarantee unless phases actually overlap; state the invariant ("each active phase is promptly cancelable; phases are sequential") instead.

**When to enforce budgets pre-work vs post-hoc.** If the contract is "best-effort stop after overshoot," the record-then-police split at `pkg/runtime/budget.go:385-407` vs `338-373` suffices. If the contract is "never exceed N," price the next prompt before calling the model (`EstimateMessageTokens` + `summaryTokenBudget`) and refuse the turn — neither source does this today, and the one-turn overshoot is the documented gap in both.

**When to scale windows for local models.** Expose `keepBudget`/`summaryBudget` per agent so an 8k-local model's recent evidence window does not collapse to a sentence. Docker-agent's proportional scaling proves the pattern; crush's `CW==0` bypass (`internal/agent/agent.go:1042-1044`) proves the failure mode when no `provider_opts.context_size` is provided.

## Practical Tips

- **Put all gates in one function called at one place.** Docker-agent's top-of-turn ordering (`pkg/runtime/loop.go:498-512` iteration → budget → model) is auditable by grep; crush's `StopWhen` evaluated inside `Stream` obscures ordering. Even when delegating to fantasy, keep a local `shouldStop()` that enumerates the Crush-owned checks and logs which fired.
- **Make transcript repair a read-time invariant, not a write-time hope.** Run `filterOrphanedToolResults`/`sanitizeToolCalls` + synthetic injection on every `GetMessages`/`preparePrompt` path (`internal/agent/agent.go:1527-1687`, `pkg/session/session.go:2434-2495`). Tested by `TestPreparePrompt_OrphanedToolUse` (`internal/agent/agent_test.go:757`, `824`) and `TestSanitizeToolCalls` — port those tests verbatim.
- **Snap kept tails to exchange boundaries.** Use `SplitIndexForKeep` (`pkg/compaction/compaction.go:279-313`) or slice only at `SummaryMessageID` that aligns to a `user` turn; never start the kept window mid-exchange. Docker-agent's synthetic `Session Summary:` as `user` role (`pkg/session/session.go:1969-1978`) keeps providers' cache semantics stable.
- **Adopt the Compare-and-Delete + monotonic high-water pattern for cancel races.** Store `activeCancel` in `activeRequests` with `CompareAndDelete` on cleanup (`internal/agent/agent.go:643-657`), and track accepted-but-not-active runs via `acceptSeqGen`/`cancelMark`/`canceledBySeq` (`internal/agent/agent.go:198-206`, `305-311`, `493-500`, `1955-2009`). This closes the enqueue→register window that an untimed `CancelAll` iteration (`internal/agent/agent.go:2022`) otherwise misses.
- **Use detached bounded contexts for every terminal write.** Wrap `persistCanceledTurn`, `FlushAll`, `publishRunComplete`, persistence observers in `context.WithoutCancel(parent)` + explicit `5s` timeout (`internal/agent/agent.go:509`, `1097`, `753-779`; `pkg/runtime/loop.go:758`). Pair with ordered shutdown `agents-first → flush → DB close` (`internal/app/app.go:743-761`).
- **Truncate tool outputs before compaction.** Apply `capToolResultContent` (middle-out head+`[...truncated...]`+tail) at both write and read time (`pkg/session/session.go:829-842`, `2553-2630`) and `truncateOldToolContent` (`2506-2535`) before prompt assembly. This keeps even `MaxTokens`-tight turns usable without stopping the loop.
- **Calibrate token estimates; do not trust `len/4`.** Reconcile heuristic `chars/3.5` against provider usage deltas, clamp `0.75-2.0`, gate on `512` minimum (`pkg/compaction/compaction.go:99-172`); fallback to `approxTokenCount=(len+3)/4` only when `step.Usage` is zero (`internal/agent/usage_fallback.go:171`). Reuse this estimator for both proactive compaction (`ShouldCompact` at `pkg/runtime/loop.go:569-572`) and budget projections.
- **Pin every lifecycle fix with an issue-numbered regression test.** Docker-agent's coverage (#3070/#3074 for terminal close, #4001/#4004 for adopt/reap analogues) is aspirational; crush already has cancel-on-entry tests at `internal/agent/dispatch_cancel_test.go:370-447` and media-workaround tests at `internal/agent/agent_test.go:896-1034` — extend the same style to budget overshoot and compaction orphan tests.
- **Default small-window local models to explicit `provider_opts.context_size`.** `ShouldCompact` returning `false` when `contextLimit==0` (`pkg/compaction/compaction.go:70`) silently disables compaction; `cw==0` doing the same in crush (`internal/agent/agent.go:1042-1044`) produces identical failure. Fail closed with a configured window rather than proceeding unbounded.

## Anti-Patterns / Caution Signs

- **`disableAutoSummarize` or `contextLimit==0` disabling compaction entirely.** Crush's `DisableAutoSummarize bool` (`internal/config/config.go:321`) and `if cw==0 return false` (`internal/agent/agent.go:1042`) and docker-agent's `ShouldCompact` guard (`pkg/compaction/compaction.go:70`) let context exceed provider limit; symptom is repeated `FinishReasonMaxTokens`/`FinishReasonLength` without recovery (`internal/agent/agent.go:989-990`, `pkg/runtime/streaming.go:274-302`).
- **Distinct-signature loops that evade single-signal detection.** Any detector keyed on `toolName+input+output` equality (crush `internal/agent/loop_detection.go:11-39`, docker-agent `pkg/runtime/toolexec/loop_detector.go:54-77`) is blind to a model cycling distinct arguments; caution sign is reliance on detector as sole bound — add a hard `MaxSteps`/`MaxToolCalls` even if detector threshold is generous.
- **Budget enforcement that lags accounting by one turn.** `recordBudget` after stream, `enforceBudget` before next turn (`pkg/runtime/budget.go:385-407` vs `338-373`; `internal/agent/agent.go:1906-1946` reporting only) guarantees overrun by one priced turn; symptom is single expensive turn doubling intended cap, invisible when `maxCost` is the only gate and models are unpriced (`pkg/runtime/budget.go:205-212` warns only).
- **Cost non-cumulative counters overwritten at compaction.** `updateSessionTokenCounters` overwrites `PromptTokens`/`CompletionTokens` (`internal/agent/agent.go:1939-1946`), then `Summarize` resets them to summary-only (`1456-1458`); `ApplyCompaction` similarly resets `InputTokens` to heuristic (`pkg/session/session.go:921-927`); reconstructing total prompt tokens post-compaction is impossible without a retained ledger.
- **Synthetic results without a marker.** Injecting `ToolResultOutputContentError{Error: "tool call was interrupted..."}` (`internal/agent/agent.go:1662-1687`) or `No result provided` (`pkg/session/session.go:2434-2495`) indistinguishable from provider errors lets the next model turn misinterpret synthetic failure as authoritative evidence.
- **`CompareAndDelete` cleanup bypass or `dispatchMu`-skipping side entry.** Crush's deferred `CompareAndDelete` (`internal/agent/agent.go:657`) is correct only if every registration goes through `activeRequests.Set`; its `Summarize` path (`internal/agent/agent.go:1355`, `1976`) registering `sessionID+"-summarize"` that never matches `Cancel`'s lookup is a demonstrated dead-key example. Docker-agent's fire-and-forget parallel tool batches similarly risk escaping `batchCtx` if a tool captures parent `ctx` before the batch is derived.
- **Hook double-fire risk on `hookedTool.Run`.** `hookedTool` executes `hooks.Runner` (parallel shell commands) without propagating tool timeout (`internal/agent/hooked_tool.go:54-73`); a hung hook blocks under `genCtx` but leaves subprocesses orphaned on `ac.cancel()`. Pair with per-hook `WithTimeout`.
- **Orphan sanitization that silently drops diagnostics.** `sanitizeToolCalls` dropping duplicates/orphans with no `ErrorCode`/`BudgetExceeded`-style event (`pkg/session/session.go:2434-2495`) hides compaction-boundary data loss; docker-agent's hook-veto path emitting `started` without `completed` (`pkg/runtime/session_compaction.go:71-76`) is the event-level analogue.
- **Middle-out truncation hiding the useful middle.** `capToolResultContent` (`pkg/session/session.go:2553-2630`) keeps head+tail but the removed middle often contains stack traces; pair truncation with structured error fields that survive truncation.

## Open Questions

1. **What is `charm.land/fantasy`'s default `MaxSteps` when Crush supplies none?** Both crush gaps and its `5/10` rating hinge on whether fantasy enforces a hard iteration cap absent `WithMaxSteps` — out of isolation boundary and not inspected (`internal/agent/agent.go:685`).
2. **Should Aren price prompts before calling the model to close the one-turn overshoot?** Both sources measure cost after the turn and gate the next; a "never exceed" budget needs `EstimateMessageTokens(prompt+attachments+keepTail)` weighed before `Stream`/`fallback.execute` — neither source demonstrates this, and the projection price versus provider Usage reliability (`fallbackStepUsage` at `internal/agent/usage_fallback.go:18`) is untested.
3. **Where should Aren retain verbatim evidence after compaction?** Both sources discard pre-summary tool payloads; the design choice is between compressed attachment/hash-chain alongside the summary item (docker-agent suggests this), a dedicated evidence store keyed by `SummaryMessageID` (crush's `SummaryMetadata` idea at `internal/session/session.go:58`), or extending the observation stream (dimension 01.04) with retained artifacts. The right granularity (per-turn ledger vs aggregated summary) is unresolved.
4. **Does Aren need sub-iteration cancellation fan-out or is sequential-phase cancellation sufficient?** Crush fans one `genCtx` simultaneously; docker-agent's sequential stream→tools model needs no simultaneous guarantee. If Aren's tool dispatch will overlap streaming (parallel tool calls feeding the next model turn speculatively), simultaneous fan-out becomes load-bearing; otherwise sequential is simpler and already proven.
5. **How should provenance be modeled without turning Aren into a framework?** Neither source offers a template — the minimal shape (artifact hash + `ToolCallID` edge on the assistant answer) versus a full citation ledger is a fresh design question for Phases 9/10 evidence checks.
6. **How to bound tool-output growth before it forces compaction?** Docker-agent's `maxToolResultTokens`/`maxOldToolCallTokens` (`pkg/session/session.go:829-842`, `2506-2535`) is the only demonstrated answer; whether Aren should bound per-tool size, per-turn size, or rely solely on compaction is unanswered, and large tool results not truncated (crush's gap) already risk silent context overflow.
