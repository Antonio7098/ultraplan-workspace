## Summary

Nomad separates scheduling/lifecycle ownership from concrete execution via a narrow `DriverPlugin` gRPC boundary. The server (scheduler + Raft FSM) is the sole authority for `Allocation` placement; the client `allocRunner`/`taskRunner` own local lifecycle, invoking type-specific drivers (`raw_exec`, `exec`, `docker`, `java`, `qemu`, `mock`) through a uniform plugin interface. Drivers translate the generic `TaskConfig` (with opaque msgpack driver config) into runtime-specific actions, while a lower `Executor` (`UniversalExecutor`) handles OS process isolation (cgroups, namespaces, chroot) for the `exec` family. Identity is hierarchical (`AllocID` → `TaskName` → `TaskConfig.ID` with short UUID), cancellation is signal + grace + force-kill with exponential backoff, streaming/logs via FIFO + logmon, artifacts via prestart hooks, and terminal reporting via batched `Node.UpdateAlloc` RPC. Lost-worker reconciliation relies on node `HeartbeatTTL` and `stop_after_client_disconnect` rather than per-task leases/fencing; idempotency is enforced via `AllocModifyIndex` filtering. There is no remote/distributed executor: all drivers are local `go-plugin` subprocesses, so remote readiness is deliberately absent.

## Rating

**Rating: 9/10**

Rationale: Exemplary narrow executor boundary — 7-method `DriverPlugin` plus `Capabilities` keeps common semantics (start/wait/stop/destroy/inspect/stats/events) uniform while pushing isolation, image, network, signal, exec, and mounts into declared capabilities and opaque config. Lifecycle ownership is crisp (server plans allocations, client `allocRunner` materializes them, `taskRunner` drives hooks→driver→wait→restart). Demonstrates local constraints (artifact idempotency, cgroup isolation, disconnect handling, AllocModifyIndex dedup) without premature distributed machinery (no lease/fencing/artifact-transfer service, no remote RPC). Would be 10 only with explicit stale-completion fencing token, which Nomad intentionally delegates to server authority.

## Answers to Dimension Questions

**What remains common across executor types, and what stays deliberately type-specific?**

Common: the 11-method `DriverPlugin` contract (`plugins/drivers/driver.go:50-68`) plus `Fingerprint` health streaming and `Capabilities` advertisement. Every driver implements `StartTask(*TaskConfig)→(*TaskHandle,*DriverNetwork)` and `Wait/Stop/Destroy/Inspect/TaskStats/TaskEvents`; cancellation (`StopTask` with `taskID,timeout,signal` in `plugins/drivers/proto/driver.proto:219-232`) and exit reporting (`ExitResult{ExitCode,Signal,OOMKilled}` in `plugins/drivers/driver.go:493-498`) are uniform. Type-specific details are pushed to: (1) opaque `TaskConfig.rawDriverConfig` decoded via `DecodeDriverConfig`/`EncodeDriverConfig` (`plugins/drivers/driver.go:359-382`) — docker `config.go`, qemu `driver.go`, java `driver.go` define own schemas; (2) declared `Capabilities` (`plugins/drivers/driver.go:166-196`) — only docker declares `MustInitiateNetwork` and extensive `NetIsolationModes`, only `exec`/`raw_exec` use `UniversalExecutor` with cgroup isolation (`drivers/shared/executor/executor.go:60-97`), `SignalTask`/`ExecTask` are optional via `SendSignals`/`Exec` flags; (3) `FSIsolation` (`none/chroot/image/unveil`) and `MountConfigs` vary per driver; (4) lower `Executor` boundary is only used by `exec` family, docker bypasses it and talks directly to Docker daemon (`drivers/docker/driver.go`). This keeps the scheduler/client agnostic while preserving docker image semantics vs raw process semantics.

**When is submitted work durably accepted, and how can a caller know?**

Two-stage acceptance. (1) Server-side: scheduler produces a `Plan` (`scheduler/generic_sched.go:687`, `scheduler/util.go:777`) committed via Raft `UpsertAllocs`; the allocation exists with `AllocModifyIndex` and `ClientStatus`. Caller (via API `Eval`) polls allocation status; terminal states are authoritative on the server. (2) Client-side: `watchAllocations` pulls `NodeSpecificRequest` → `NodeClientAllocsResponse` (`client/client.go:2500-2550`), filters by `AllocModifyIndex` (`client/client.go:2608-2614`, `client/util.go:44-46`), creates `allocRunner` and stores `Alloc` in BoltDB (`client/state/db_bolt.go:292` `PutAllocation`). `taskRunner.Run` persists `TaskHandle` synchronously after `StartTask` (`client/allocrunner/taskrunner/task_runner.go:995-1005`) and emits `TaskStarted` → `TaskStateUpdated` → `AllocStateUpdated` (`client/allocrunner/taskrunner/task_runner.go:1010`). The update is durably queued in `pendingUpdates` and flushed every `allocSyncIntv` via `Node.UpdateAlloc` RPC (`client/client.go:2416-2425`); on success `AcknowledgeState` persists `TaskStates/ClientStatus` (`client/allocrunner/alloc_runner.go:1556-1571`). Caller knows via `AllocStateUpdated` propagation to server and subsequent `Alloc.ClientStatus` (`pending`→`running`→`complete`/`failed`) observed through API or `AllocBroadcaster` (`client/structs/broadcaster.go:27`). Artifact prestart must complete before `StartTask` is called, so acceptance does not imply setup success — `TaskArtifactDownloadFailed` is a recoverable error that blocks start (`client/allocrunner/taskrunner/artifact_hook.go:57-64`).

**How are stale workers prevented from publishing authoritative completion?**

Nomad does not use fencing tokens; prevention is by making the server authoritative and clients monotonic reporters. (1) `AllocModifyIndex` is the fencing analogue: client discards stale server updates if `oldUpdate.AllocModifyIndex > update.AllocModifyIndex` (`client/allocrunner/alloc_runner.go:1038-1042`) and `watchAllocations` filters `!ok || modifyIndex > currentAR.Alloc().AllocModifyIndex` (`client/client.go:2610`). `client/util.go:44-46` checks `alloc.AllocModifyIndex > existIndex` before accepting. (2) Completion reporting is client-originated but server-validated: `AllocStateUpdated` sends only `TaskStates/ClientStatus/ClientDescription/DeploymentStatus/NetworkStatus` (`client/client.go:2376-2383`), server's Raft FSM decides final `Alloc` state; if a node is partitioned, `heartbeatStop.shouldStopAfter(now, timeout)` (`client/heartbeatstop.go:64-70`) destroys local `stop_after_client_disconnect` allocs, and scheduler concurrently marks that node's non-terminal allocs `StatusAllocLost` (`scheduler/util.go:789-796`) and reschedules them elsewhere — stale client's later `Node.UpdateAlloc` will be rejected or ignored because the allocation is already `lost`/GC'd. (3) For duplicate completion, `pendingUpdates.restore(toSync)` on RPC failure (`client/client.go:2432`) ensures at-least-once but idempotent via `AllocModifyIndex`; `GetUpdatePriority` (`client/allocrunner/alloc_runner.go:1578-1612`) dedupes no-op updates (`AllocUpdatePriorityNone`). The gap: there is no per-task lease epoch preventing a zombie process from writing artifacts after reassignment — cleanup relies on `DestroyTask(force)` and cgroup kill in `UniversalExecutor.Shutdown` (`drivers/shared/executor/executor.go:616-688`) plus GC `DeleteAllocationBucket` (`client/allocrunner/alloc_runner.go:1160`).

**Which distributed mechanisms should Aren explicitly avoid until a measured requirement appears?**

Nomad's local-only design argues for deferring: (1) **Global distributed leases/heartbeats per task**: Nomad uses node-level `HeartbeatTTL` (`client/client.go:2226` `resp.HeartbeatTTL`) not per-allocation leases; per-task Raft leases would add write amplification with no demonstrated need for single-node Aren. (2) **Fencing tokens / epoch counters for stale completion**: Nomad succeeds without them via server authority and `AllocModifyIndex` monotonicity; adding epochs before observing stale-worker completion races is premature. (3) **Remote artifact-transfer service / CAS**: Nomad's `artifactHook` uses direct `go-getter` downloads to `AllocDir` with hash deduplication (`client/allocrunner/taskrunner/artifact_hook.go:45-52`); a dedicated transfer service (streaming artifacts between workers) is unjustified until local disk/egress becomes bottleneck. (4) **Distributed GC / global GC service**: Nomad's `AllocGarbageCollector` is node-local, trigger-based on `DiskUsageThreshold/InodeUsageThreshold/MaxAllocs` (`client/gc.go:17-32`); a cluster-wide GC coordinator is unnecessary. (5) **Remote executor RPC / multi-region scheduler**: Drivers are `go-plugin` local subprocesses (`plugins/drivers/client.go:30-38`); exposing them over network (as Nomad deliberately removed `remote_tasks` `reserved 7` in `plugins/drivers/proto/driver.proto:410`) would regress isolation without proven multi-host workload. (6) **Complex network namespace federation**: `NetworkIsolationSpec` is deliberately local (`plugins/drivers/driver.go:219-224`); cross-node network invention belongs after real multi-tenant network constraints appear.

## Notable Patterns

- **Plugin capability negotiation vs. interface bloat:** Instead of giant union executor type, Nomad uses `Capabilities(){SendSignals,Exec,FSIsolation,NetIsolationModes,MustInitiateNetwork}` (`plugins/drivers/driver.go:166-196`) to let scheduler filter feasibility before dispatch.
- **Handle + Recover pattern:** `StartTask` returns opaque `TaskHandle` (`plugins/drivers/task_handle.go:13-22`), persisted; on restart `RecoverTask(handle)` (`plugins/drivers/client.go:157-162`) reattaches without replaying task. Failed recovery triggers `DestroyTask(force)` cleanup (`client/allocrunner/taskrunner/task_runner.go:1308-1314`).
- **Hook lifecycle composition:** `prestart` (artifacts, vault, identity, network, cgroup `assignCgroup`) → `runDriver` → `poststart` → `wait` → `exited` → `stop` hooks (`client/allocrunner/taskrunner/task_runner.go:640-682`, `client/allocrunner/alloc_runner.go:394-415`). Each hook is `interfaces.TaskPrestartHook` with `Done` persistence, enabling partial replay after crash (`client/allocrunner/taskrunner/state/state.go:74-99` `HookState`).
- **Log/stream isolation via FIFO:** `TaskConfig.StdoutPath/StderrPath` are FIFOs; `logmon` collects without driver needing log awareness, advertising `DisableLogCollection` capability (`plugins/drivers/driver.go:188-189`).
- **Exponential backoff kill with shutdown_delay:** `handleKill` respects `Task.ShutdownDelay` then `Kill()` with `5s*4^i` backoff capped at `2m` (`client/allocrunner/taskrunner/task_runner.go:1129-1153`), ensuring signals are not lost under driver transient failures.
- **Deterministic alloc-dir ownership:** `allocdir.NewAllocDir(AllocsDir, MountsDir, allocID)` (`client/allocrunner/alloc_runner.go:288-293`) gives each allocation an isolated chroot/mount tree, with `TaskDir` subdirs for mounts (`client/allocrunner/taskrunner/task_dir_hook.go:95-113`).

## Tradeoffs

- **Narrow interface vs. rich semantics:** Uniform `WaitTask/StopTask/DestroyTask` makes scheduler trivial but pushes image pulls, port maps, device mounts into `hookResources`/`DriverNetwork` side channels (`client/allocrunner/taskrunner/task_runner.go:180-184`, `plugins/drivers/driver.go:185-189`). Good for extensibility, harder to audit end-to-end resource accounting.
- **No per-task lease → simpler liveness, weaker fencing:** Using node `HeartbeatTTL` (`client/client.go:2226`) + scheduler `updateNonTerminalAllocsToLost` (`scheduler/util.go:789`) avoids lease renewals, but a partitioned client that retains a task can still publish a delayed `Node.UpdateAlloc` before GC; server must win via `lost` transition rather than fencing token.
- **BoltDB sync on every state event:** `PutTaskState`/`PutTaskRunnerLocalState` after each event (`client/allocrunner/taskrunner/task_runner.go:1395-1423`) ensures crash recovery but adds fsync overhead; Nomad mitigates via `WithBatchMode` (`client/allocrunner/alloc_runner.go:1206`) in alloc runner persistence.
- **go-plugin isolation vs. latency:** Out-of-process drivers via gRPC (`plugins/drivers/client.go:172-196`) give fault isolation (plugin crash → `ErrPluginShutdown` recovery at `client/allocrunner/taskrunner/task_runner.go:822`) but add serialization (msgpack/proto) and `joincontext` cancellation complexity; local `exec` tasks pay extra hop versus in-process Aren executor would.
- **Artifact getter concurrency:** `artifactHook` runs 3 workers (`client/allocrunner/taskrunner/artifact_hook.go:97`) with `PreviousState` dedup; fast for many artifacts, but concurrent `go-getter` downloads can contend on disk I/O without global throttling.

## Failure Modes / Edge Cases

- **Driver plugin crash during `StartTask`/`WaitTask`:** `handleTaskExitResult` detects `bstructs.ErrPluginShutdown` (`client/allocrunner/taskrunner/task_runner.go:822-843`), re-dispenses driver via `initDriver`, attempts `restoreHandle`; if that fails, allocation stays pending until `serversContactedCh` (`client/allocrunner/taskrunner/task_runner.go:1269-1280`). Unbounded retry could loop if plugin repeatedly crashes on that alloc's config.
- **Stale `AllocModifyIndex` replay:** `watchAllocations` may receive stale allocation if follower replica is behind; client detects `received stale allocation information; retrying` (`client/client.go:2584`) and retries after `allocSyncRetryIntv`. AllocRunner drains stale queued update if `oldModify > newModify` (`client/allocrunner/alloc_runner.go:1038-1042`) — but if two rapid server updates are coalesced, intermediate state is intentionally dropped.
- **Artifact failure is recoverable but blocks progress:** `doWork` wraps error as `NewRecoverableError(...,true)` (`client/allocrunner/taskrunner/artifact_hook.go:57-64`); `runDriver` will `restartTracker.SetStartError` and `goto RESTART` (`client/allocrunner/taskrunner/task_runner.go:641-644`), potentially hot-looping on 404/bad checksum.
- **Disk pressure GC race:** `AllocGarbageCollector.keepUsageBelowThreshold` (`client/gc.go:120-170`) checks `UsedPercent > DiskUsageThreshold` or `liveAllocs > MaxAllocs` before popping oldest GC alloc; if client is already at `MaxAllocs*2` it WARNs, but if disk fills during active downloads, `collect` may delete the very `AllocDir` a running task needs (guarded only by `ar.stateDB.DeleteAllocationBucket` after `ar.waitCh` at `client/allocrunner/alloc_runner.go:1144-1163`).
- **cgroup configuration failure:** `UniversalExecutor.Launch` warns but continues if not root (`drivers/shared/executor/executor.go:388-394`); if `usesCustomCgroup()` and not root it fatally errors — tasks silently lose isolation when Nomad runs as non-root, violating `Resources.LinuxResources` guarantees without explicit failure.
- **Lost-worker duplicate execution:** After `HeartbeatTTL` expiry, scheduler marks alloc `lost` and reschedules elsewhere (`scheduler/util.go:794`); original client may continue running until `heartbeatStop.stopAlloc` fires (`client/heartbeatstop.go:149-159` → `runner.Destroy`). During window, same job runs twice — acceptable for Nomad batch/service idempotency, but violates exactly-once for non-idempotent Aren tasks.
- **No idempotency key for `StartTask`:** `TaskConfig.ID` is random per invocation (`client/allocrunner/taskrunner/task_runner.go:1209` `ShortUUID`), so retrying `StartTask` after `RETRY` result (`plugins/drivers/proto/driver.proto:176-182`) creates a new handle rather than deduping; safe because prior handle is destroyed via `restoreHandle` cleanup, but leaked containers if driver ignores `DestroyTask`.

## Future Considerations

- **Do not add remote executor layer until single-node bottleneck is measured.** Nomad proves `go-plugin` local drivers + client `allocRunner` scales to thousands of allocs per node without remote calls. For Aren, keep executors in-process or local subprocess; introduce worker-pool RPC only after p95 local scheduling latency exceeds target.
- **If cross-node execution becomes needed, start with node-scoped `allocRunner` replication, not global executor mesh.** Nomad's federation is at scheduler/consensus layer, not executor; remote readiness should reuse `AllocModifyIndex` + `Node.UpdateAlloc` pattern before inventing per-task leases.
- **Defer artifact-transfer service.** Nomad's prestart `getter` with concurrent workers (`client/allocrunner/taskrunner/artifact_hook.go:97`) and `AllocDir` isolation suffices; a CAS/peer-to-peer layer is premature until artifact fetch dominates task start time.
- **If stale completion becomes observable, add lightweight epoch to `TaskHandle` rather than full lease.** Nomad's gap (no fencing token) can be filled minimally by incrementing a `handle.Version` on reschedule and rejecting `Node.UpdateAlloc` with old version, without periodic heartbeat.
- **Consider explicit `UpdateResources` enforcement.** `UniversalExecutor.UpdateResources` is a no-op (`drivers/shared/executor/executor.go:565-567`); for Aren dynamic resizing, implement cgroup update path before advertising the capability.
- **Preserve narrow driver contract in Aren:** define `Capabilities`-like struct early, keep driver config opaque (msgpack/cbor), and persist `TaskHandle`+`HookState` in local Bolt/Badger for crash recovery — these have proven value without distributed overhead.
