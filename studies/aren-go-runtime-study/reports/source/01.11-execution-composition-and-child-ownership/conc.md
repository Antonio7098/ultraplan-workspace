## Summary

`conc` implements flat structured concurrency around a single owner — `conc.WaitGroup` (`studies/aren-go-runtime-study/sources/conc/waitgroup.go:22-25`) — and a family of typed `pool` composition helpers layered on top of it. There is no hierarchical task tree or explicit parent/child identity; ownership is `owner -> goroutine` via `Go()` and barrier `Wait()`. Composition is achieved through builder-style conversion methods (`WithErrors`, `WithContext`, `WithResults`, `WithMaxGoroutines`) that preserve concrete limiter and aggregation semantics rather than erasing to an interface. Sequential, bounded-pool, collect-all, and fail-fast parallel patterns are all present but opt-in. Bounded parallelism uses a `chan struct{}` limiter (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:164`) and a `tasks chan func()` handoff with lazy worker reuse (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:38-66`, `studies/aren-go-runtime-study/sources/conc/pool/pool.go:150-162`). Result ordering is deterministic by submission index via `resultAggregator.nextIndex/save/collect` (`studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:96-103`, `studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:105-120`, `studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:123-141`). Sibling cancellation is explicit and off by default — `ContextPool.WithCancelOnError` (`studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:78-82`) and `WithFailFast` (`studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:87-92`). Parent terminality is strictly after child cleanup: `Wait()` blocks on `sync.WaitGroup` and propagates panics only after all children exit (`studies/aren-go-runtime-study/sources/conc/waitgroup.go:38-43`, `studies/aren-go-runtime-study/sources/conc/pool/pool.go:72-82`, `studies/aren-go-runtime-study/sources/conc/stream/stream.go:91-103`). Child events remain attributable without a global bus through per-task channels in `stream` and per-index slots in `resultAggregator`. Panic handling captures only the first panic via `CompareAndSwap` (`studies/aren-go-runtime-study/sources/conc/panics/panics.go:27-30`) and re-panics with stack (`studies/aren-go-runtime-study/sources/conc/panics/panics.go:36-39`, `studies/aren-go-runtime-study/sources/conc/panics/panics.go:52-60`).

## Rating

**6/10** — Strong bounded-pool, result-collection, and panic-propagation composition with explicit opt-in sibling cancellation and deterministic submission-ordered results, but flat single-level ownership only. No attributable child IDs, lifecycle events, nested parent trees, or terminal-state guard preventing post-terminal mutation beyond the `panicIfInitialized` config guard. Covers Phase 12 sequential/parallel/bounded/result-aggregation mechanics while retaining lifecycle/cancellation rules, but does not model Aren-style hierarchical parent/child identity or event ownership.

Rationale: earns points for concrete composition helpers that preserve executor semantics, explicit `WithCancelOnError`/`WithFailFast` policy, `WithMaxGoroutines` limiter with blocking `Go()`, and submission-ordered `resultAggregator`; loses points for lack of hierarchical ownership, child identity, and no enforced terminal state beyond `Wait` barrier (pools are reusable after `Wait` resets state).

## Answers to Dimension Questions

**When is a parent allowed to become terminal relative to child cleanup?**
Only after `Wait()` returns. `WaitGroup.Wait` (`studies/aren-go-runtime-study/sources/conc/waitgroup.go:38-43`) blocks on `sync.WaitGroup` then re-panics — the caller goroutine is not considered terminal (in Aren terms) until the barrier completes. `Pool.Wait` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:72-82`) closes the `tasks` channel, waits for workers via `handle.Wait()`, and defers `initOnce` reset — workers executing `worker()` drain `range p.tasks` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:159-161`) so they exit before `Wait` returns. `Stream.Wait` (`studies/aren-go-runtime-study/sources/conc/stream/stream.go:91-103`) waits for `pool.Wait()` first, then defers `close(queue)` + `callbackerHandle.Wait()` ensuring ordered callbacks complete before parent returns; the deferred close guarantees ordered callback completion even when `pool.Wait` re-panics. `ContextPool.Wait` (`studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:54-58`) defers `cancel` after `errorPool.Wait` to avoid leaking the derived context. There is no explicit “terminal” state flag; the library enforces cleanup completion by blocking. Reuse is explicitly allowed after `Wait` resets internal state (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:79`, `studies/aren-go-runtime-study/sources/conc/pool/error_pool.go:38`), which diverges from a strict Aren terminal-once model.

**Does one child failure cancel siblings, and is that policy explicit?**
Default: **no**. `Pool` and `ErrorPool` never cancel siblings; `ErrorPool.Wait` simply `errors.Join`s all errors (`studies/aren-go-runtime-study/sources/conc/pool/error_pool.go:44-46`). `ContextPool` only cancels when explicitly opted in via `WithCancelOnError` (`studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:78-82`) or `WithFailFast` (`studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:87-92`). When enabled, `ContextPool.Go` does `addErr` before `cancel` with a comment about leaky abstraction to preserve `WithFirstError` ordering (`studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:38-45`) and recovers panics to cancel before re-panic (`studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:30-35`). Tests explicitly verify the two policies: without `WithCancelOnError` the sibling completes and error lacks `context.Canceled` (`studies/aren-go-runtime-study/sources/conc/pool/context_pool_test.go:149-166`), with it the sibling observes `ctx.Done()` and `errors.Join` includes `context.Canceled` (`studies/aren-go-runtime-study/sources/conc/pool/context_pool_test.go:134-147`). `WithFirstError` vs joined error distinction is also verified (`studies/aren-go-runtime-study/sources/conc/pool/context_pool_test.go:168-190`, `studies/aren-go-runtime-study/sources/conc/pool/error_pool_test.go:70-79`). Simultaneous child failure is not atomically tested beyond `errors.Join` inclusion; ordering of concurrent error appends is racy but joined set is complete.

**Are results ordered by submission, start, or completion?**
**Submission order, deterministically.** `ResultPool.Go` reserves an index before dispatch (`studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:33-34` `nextIndex` under mutex `result_pool.go:96-103`), then `save(idx, f(), false)` writes to that slot (`studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:35-36`, `studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:105-120`). `collect` returns the pre-sized slice in index order, filtering errored indices stably via sorted `errored` (`studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:123-141`). The guarantee is documented: “order of the results is guaranteed to be the same as the order the tasks were submitted” (`studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:23-24`, same for `ResultErrorPool` `studies/aren-go-runtime-study/sources/conc/pool/result_error_pool.go:12` and `ResultContextPool`). Tests with random sleep verify order is not completion order (`studies/aren-go-runtime-study/sources/conc/pool/result_pool_test.go:66-84`, `studies/aren-go-runtime-study/sources/conc/pool/result_context_pool_test.go:198-230`). `Stream` likewise guarantees callback order equals submission order, not completion order (`studies/aren-go-runtime-study/sources/conc/stream/stream.go:22-25`, `studies/aren-go-runtime-study/sources/conc/stream/stream.go:61-64`). `iter.Map` also returns `res[i]=f(t)` with indexed assignment (`studies/aren-go-runtime-study/sources/conc/iter/map.go:28-31`).

**Can a child outlive or mutate state after its parent is terminal?**
By design **no** under correct usage, but the library does not enforce a terminal guard beyond `Wait`. `WaitGroup.Go` increments `sync.WaitGroup` before spawning (`studies/aren-go-runtime-study/sources/conc/waitgroup.go:29-33`), so any goroutine that has been submitted will delay `Wait` until `Done`. After `Wait` returns, the pool resets (`pool.go:79` `initOnce = sync.Once{}`; `error_pool.go:38` `errs=nil`; `result_pool.go:43` `agg={}`) and is reusable for a new generation of children — children of the previous epoch cannot mutate the already-collected result slice returned to the caller. However, nothing prevents a caller from submitting new children after `Wait` without re-`Wait`ing, leaking them; and `panicIfInitialized` only guards reconfiguration, not `Go` after `Wait` (which is allowed for reuse per `pool_test.go:128-146`). `Stream.callbacker` drains `queue` until `close` (`stream.go:126`), so callbacks cannot outlive the second `callbackerHandle.Wait` inside the deferred `Stream.Wait` close path (`stream.go:96-99`). Unlike Aren, there is no parent-terminal flag that rejects late `Go` calls or detects post-terminal shared-memory writes; attribution relies solely on the caller honoring the `Go`→`Wait` barrier idiom described in `README.md:56-62`.

## Architectural Decisions

* **Single-owner flat model over hierarchical tree** — All goroutines are owned by the `Pool`/`WaitGroup` that spawned them (`studies/aren-go-runtime-study/sources/conc/waitgroup.go:22-25`, `studies/aren-go-runtime-study/sources/conc/pool/pool.go:30-35`). There is no recursive parent→child→grandchild identity; nesting requires manually threading a `*WaitGroup` (`README.md:67-76`). This simplifies ownership at the cost of no cascading lifecycle.
* **Lazy worker creation with channel handoff** — `Pool.Go` tries `p.tasks <- f` non-blocking; only on `default` or limiter availability does it spawn a worker (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:42-66`). Workers loop on `range p.tasks` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:159-161`). This yields zero-cost pool creation and bounded goroutine count exactly equal to concurrent demand.
* **Derived cancellable context owned by the pool** — `Pool.WithContext` does `context.WithCancel` and stores both `ctx` and `cancel` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:140-148`). The pool becomes the cancellation owner; `ContextPool.Wait` defers `cancel` (`studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:55-57`) even on panic, tying sibling lifetime to the pool rather than the caller's context.
* **Panic as first-class failure with decorated re-panic** — `panics.Catcher` captures `runtime.Callers`+`debug.Stack` (`studies/aren-go-runtime-study/sources/conc/panics/panics.go:52-60`) and `CompareAndSwap` to keep only the first (`studies/aren-go-runtime-study/sources/conc/panics/panics.go:29`). Every `Wait` re-panics with `*Recovered` (`waitgroup.go:42`, `panics.go:36-39`), so panic handling is deterministic and not silently swallowed.
* **Index-reservation result aggregator** — `resultAggregator` pre-increments `len` under mutex to reserve a slot before the goroutine starts (`studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:96-103`), enabling lock-free ordering guarantee without channel sorting. Errored filtering via sorted `errored` slice (`studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:132-140`) keeps submission order even when some tasks fail.
* **Builder-chain type conversion to preserve semantics** — `Pool → ErrorPool → ContextPool` and `Pool → ResultPool → ResultErrorPool → ResultContextPool` via `deref`/`WithX` that copy `limiter` and error policy (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:118-133`, `studies/aren-go-runtime-study/sources/conc/pool/error_pool.go:54-62`, `studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:55-60`). This avoids erasing generic type `T` or limiter config, unlike an `Executor` interface approach.
* **Configuration immutability after first `Go`** — `panicIfInitialized` checks `tasks != nil` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:111-114`) and panics on late config, forcing pool replacement instead of mid-flight re-tuning. The check is not context-aware and does not prevent reuse after `Wait` reset.
* **Single-threaded ordered callback executor** — `Stream` splits execution into two owned groups: `pool` for concurrent tasks and `callbackerHandle` for sequential callbacks (`studies/aren-go-runtime-study/sources/conc/stream/stream.go:38-44`). Ordering is preserved via per-task `callbackCh` queued in submission order (`stream.go:66-69`) but task execution remains parallel.

## Notable Patterns

* **Scoped concurrency as documented goal** — README “Make it harder to leak goroutines” (`studies/aren-go-runtime-study/sources/conc/README.md:49-62`) codifies the `var wg conc.WaitGroup; defer wg.Wait()` pattern and `startTheThing(&wg)` propagation.
* **Generics for typed result collection** — `ResultPool[T]`, `ResultErrorPool[T]`, `ResultContextPool[T]` (`studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:25-28`, `studies/aren-go-runtime-study/sources/conc/pool/result_error_pool.go:16-20`, `studies/aren-go-runtime-study/sources/conc/pool/result_context_pool.go:14-18`) avoid `any` erasure.
* **`sync.Pool` for per-task channel recycling** — `stream` reuses `callbackCh` via `sync.Pool` (`studies/aren-go-runtime-study/sources/conc/stream/stream.go:142-154`), reducing allocation per `Go`.
* **`atomic.Int64` work-stealing iterator** — `iter.Iterator.ForEachIdx` farms indices via `idx.Add(1)-1` loop (`studies/aren-go-runtime-study/sources/conc/iter/iter.go:71-78`) over `MaxGoroutines` workers capped to `len(input)` (`studies/aren-go-runtime-study/sources/conc/iter/iter.go:66-69`).
* **Leaky-abstraction-aware error ordering** — `ContextPool.Go` adds error via `addErr` before `cancel` to avoid `WithFirstError` observing a `context.Canceled` before the real error (`studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:40-43`).
* **Pooled limiter as `type limiter chan struct{}`** — semantic alias with `release` helper that is a no-op when `nil` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:164-174`) enabling unified code path for bounded vs unbounded pools.
* **Zero-value usable types** — `WaitGroup` zero value valid (`studies/aren-go-runtime-study/sources/conc/waitgroup.go:20-21`), `Pool` lazy `initOnce` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:102-106`), `Iterator` defaults to `GOMAXPROCS` (`studies/aren-go-runtime-study/sources/conc/iter/iter.go:60-63`), `Mapper` mirrors (`studies/aren-go-runtime-study/sources/conc/iter/map.go:13`).

## Tradeoffs

* **Explicit vs implicit sibling cancellation** — Requiring `WithCancelOnError` (`studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:78-82`) makes the policy auditable and avoids surprise `context.Canceled` noise, but callers who expect fail-fast by default must remember the flag; error-pools without context have no way to cancel siblings at all.
* **First-error vs all-errors join** — Default `errors.Join` (`studies/aren-go-runtime-study/sources/conc/pool/error_pool.go:46`) preserves every child’s failure for debugging, while `WithFirstError` (`studies/aren-go-runtime-study/sources/conc/pool/error_pool.go:66-70`) is deterministic for `WithCancelOnError` where trailing errors are likely `context.Canceled` (`pool/context_pool_test.go:192-205`). The “first” error ordering depends on goroutine completion timing, acknowledged as racy in tests (`studies/aren-go-runtime-study/sources/conc/pool/context_pool_test.go:175-184` 10 ms sleep, `studies/aren-go-runtime-study/sources/conc/pool/result_error_pool_test.go:70-78`).
* **Blocking `Go` provides backpressure at cost of caller liveness** — `Pool.Go` blocks on `limiter <- struct{}` or `tasks <- f` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:54-66`) so unbounded submission cannot OOM the pool, but a saturated pool with `MaxGoroutines=1` can stall the submitter; there is no `TryGo` or `ctx`-aware non-blocking variant for plain `Pool`.
* **Reuse after `Wait` vs one-shot terminal** — Resetting `initOnce`/`errs`/`agg` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:79`, `studies/aren-go-runtime-study/sources/conc/pool/error_pool.go:38`, `studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:43`) matches `sync.WaitGroup` reusability and reduces allocation, but contradicts Aren’s parent-terminal-once semantics where a parent cannot be reactivated after children complete.
* **Panic preserves only first failure** — `Catcher.CompareAndSwap(nil, &Recovered)` (`studies/aren-go-runtime-study/sources/conc/panics/panics.go:29`) guarantees deterministic re-panic value but discards subsequent panics; `WaitAndRecover` (`studies/aren-go-runtime-study/sources/conc/waitgroup.go:47-52`) and `panics.Try` (`studies/aren-go-runtime-study/sources/conc/panics/try.go:7-11`) surface only one stack trace despite “all tasks still execute” guarantee (`studies/aren-go-runtime-study/sources/conc/stream/stream.go:30-32`, `waitgroup_test.go:100-114`).
* **Per-task channel vs global event bus** — `Stream` per-`Go` `getCh()`/`putCh()` (`studies/aren-go-runtime-study/sources/conc/stream/stream.go:66-69`, `studies/aren-go-runtime-study/sources/conc/stream/stream.go:136`) and `resultAggregator` slot isolation avoid a global event bus, keeping child attribution precise, but add per-task allocation and require the `sync.Pool` optimization.
* **Performance-oriented non-zero overhead** — Pool advertises ~1 µs start/teardown + 300 ns per task (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:26-29`) and `iter` 50 ns per element (`studies/aren-go-runtime-study/sources/conc/iter/iter.go:33-35`); this is why `Pool` is not zero-cost and unsuitable for “very short tasks” — tradeoff of structured cleanup vs raw `sync.WaitGroup` (`README.md:241-270` comparison).

## Failure Modes / Edge Cases

* **Reconfiguration after `Go` panics instead of returning error** — `WithMaxGoroutines(0)` panics (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:93-94`, `studies/aren-go-runtime-study/sources/conc/pool/pool_test.go:117-120`) and any `With*` after first `Go` panics via `panicIfInitialized` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:111-114`, `studies/aren-go-runtime-study/sources/conc/pool/error_pool.go:90-92`, `studies/aren-go-runtime-study/sources/conc/pool/context_pool.go:102-104`), which can crash the parent if mis-ordered rather than surfacing a composable error.
* **Simultaneous child failure + panic races `WithFirstError`** — Tests document a race where a second goroutine may return before the first’s error is registered, needing sleeps to make determinism likely but not guaranteed (`studies/aren-go-runtime-study/sources/conc/pool/context_pool_test.go:175-184`, `studies/aren-go-runtime-study/sources/conc/pool/result_error_pool_test.go:69-81`). `errors.Join` ordering is completion order, not submission order.
* **Goroutine leakage if `Wait` is omitted** — No finalizer or background reaper; the `README.md:56-62` `defer wg.Wait()` idiom is required. Plain `go` statement inside a `Pool` task that spawns its own goroutine is not tracked by the pool.
* **Panic during `Stream` callback starvation without empty callback** — Task panic must send `func(){}` before re-panic (`studies/aren-go-runtime-study/sources/conc/stream/stream.go:77-79`) or `callbacker`’s `<-callbackCh` would block forever; a task returning nil callback is tolerated via `if callback != nil` (`studies/aren-go-runtime-study/sources/conc/stream/stream.go:131-133`) but nil from non-panic path silently skips work.
* **Limiter release on panic depends on `defer` in `worker`** — `defer p.limiter.release()` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:153`) is the only path that frees a limiter slot after a panic; if a task bypasses `worker` (plain `WaitGroup` without limiter), a tight loop of panicking `Pool.Go` with `MaxGoroutines=2` could have stalled without this fix, tested in `studies/aren-go-runtime-study/sources/conc/pool/pool_test.go:106-115`.
* **Context cancellation requires task cooperation** — `ContextPool` cancels `ctx` but does not kill the goroutine; tasks that ignore `ctx.Done()` run to completion (`studies/aren-go-runtime-study/sources/conc/pool/context_pool_test.go:134-147`, `studies/aren-go-runtime-study/sources/conc/pool/result_context_pool_test.go:89-103`), so sibling cancellation is advisory.
* **Result filtering edge: errored value silently dropped** — `ResultErrorPool.Wait` defaults `collectErrored=false` and drops the `T` for errored tasks (`studies/aren-go-runtime-study/sources/conc/pool/result_error_pool.go:35-39`, `studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:128-141`, `studies/aren-go-runtime-study/sources/conc/pool/result_error_pool_test.go:48-54` expects `Len==0`), so callers that need partial results must remember `WithCollectErrored` (`studies/aren-go-runtime-study/sources/conc/pool/result_error_pool.go:44-49`).
* **`collect` concurrent use panic** — `resultAggregator.collect` asserts `TryLock` fails if `Wait` not yet completed (`studies/aren-go-runtime-study/sources/conc/pool/result_pool.go:124-126` “should not be called until all goroutines have exited”), but this is a developer error with a panic rather than a safe error.
* **Nested pool misuse after `Wait` reset** — Because `Pool.Wait` resets `initOnce` (`studies/aren-go-runtime-study/sources/conc/pool/pool.go:79`), a task that captures the pool and calls `Go` after `Wait` resurrects workers — post-terminal mutation is not rejected.

## Future Considerations
