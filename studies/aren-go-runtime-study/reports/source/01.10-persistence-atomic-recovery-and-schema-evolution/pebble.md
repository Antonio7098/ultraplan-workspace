## Summary

Pebble implements durable LSM persistence with a two-phase durable path: (1) WAL via `record.LogWriter` (blocked 32 KiB chunks with CRC, log-number-tagged recyclable and WAL-sync-offset chunks) and (2) MANIFEST via `record.Writer` + `atomicfs.Marker` directory-sync dance. The atomic unit is a `Batch` — a single sequence-numbered record group written to WAL then applied to memtable under `commitPipeline` ordering (`commit.go:146-215`). Ordering is WAL-append under `commitPipeline.mu` before memtable publish and `visibleSeqNum` ratchet (`commit.go:430-520`, `db.go:891-958`). Recovery is manifest-replay then WAL-replay with explicit truncated-tail and corruption-vs-EOF disambiguation (`recovery.go:29-661`, `open.go:105-395`, `record/record.go:466-586`). Schema evolution is gated by `FormatMajorVersion` monotonic ratchet with per-version migration closures and strict refuse-on-too-new/too-old (`format_major_version.go:34-580`, `open.go:139-138`). Checkpoint is a snapshot-isolated hard-link/copy with WAL filtering by `visibleSeqNum` (`checkpoint.go:134-467`). Crash guarantees are validated by deterministic `MemFS.CrashClone` sweeps and `errorfs` fault injection across WAL/manifest/checkpoint boundaries.

## Rating

**8/10**

Rationale: Atomicity is explicit and ordered (WAL before visibility, MANIFEST before pointer move, both with directory fsync). Recovery is honest about incomplete writes (EOF vs corruption via WAL-sync-offset read-ahead, per-format handling of recyclable log recirculation) and interrupted work (minUnflushedLogNum + seqnum replay into flushables). Schema evolution is versioned, forward-only, and checked at open. Deduplication from the perfect score: external-effect exactly-once is correctly *not claimed* (storage is idempotent, external side effects would duplicate), rollback is not supported (format moves only forward), and there is a new `FormatWALSyncChunks` transition window where older readers on newer WAL files get weaker corruption guarantees until ratchet completes.

## Answers to Dimension Questions

**What is the atomic unit, and does it match Aren-owned lifecycle state rather than external effects?**

The atomic unit is a single `Batch` (`sources/pebble/batch.go:192-240`). A Batch carries its `SeqNum`+`Count` header and 1..N mutations (Set/Merge/Delete/RangeDel/RangeKey). `Batch.Apply`/`commitPipeline.Commit` guarantees all-or-nothing: either the Batch's record group is durably appended to the WAL (`sources/pebble/record/log_writer.go:979-1009`) and visible via memtable publish (`sources/pebble/commit.go:476-520`), or none of it becomes visible. The companion `VersionEdit` is the second atomic unit for LSM metadata (MANIFEST record group written+synced+marker-moved atomically in `sources/pebble/version_set.go:502-575`). This matches Aren-owned lifecycle if Aren maps its transition outs to a commit barrier: state mutation plus outcome/events are batched together before any external-tool call. Pebble itself has no external side effects; `replayWAL` comment is explicit that flushing after WAL replay (`sources/pebble/recovery.go:438-449`) is what makes kernel-buffered WAL data durable. The failure window is between WAL append without sync and visibility: `commitPipeline` even documents that `visibleSeqNum` can ratchet before WAL sync, so a reader can observe committed data not yet durable (`sources/pebble/commit.go:175-180`). Callers must use `Sync=true` for durability, else they accept at-least-visible/before-durable.

For Aren, the pattern transfers: own-state (task status + outcome + events + artifacts manifest) should be a single batch/version-edit committed atomically; tool calls must *not* be inside the same atomic unit. Pebble's `Batch` refusing to mix `ingestedSSTBatch` with normal mutations (`sources/pebble/batch.go:1238-1244`) models that separation.

**After restart, how is interrupted work distinguished from failed or completed work?**

Three layers:

1. **Manifest boundary.** `recoveredVersion.minUnflushedLogNum` (from `VersionEdit.MinUnflushedLogNum`, `sources/pebble/internal/manifest/version_edit.go:151-158`) partitions WALs: `recoveredState.init` lists all `wal.Scan` results and splits into `walsReplay` (num >= minUnflushed) vs `walsObsolete` (deleted on `RemoveObsolete`, `sources/pebble/recovery.go:177-191`). Anything already flushed to SST and reflected in MANIFEST is completed work — its WAL is obsolete.

2. **Sequence-number continuity.** `recoverVersion` rehydrates `logSeqNum = max(LastSeqNum+1, SeqNumStart)` (`sources/pebble/recovery.go:372-376`) and `Open` replays WALs in order, ratcheting `logSeqNum` to `max(maxSeqNum)` after each logical WAL (`sources/pebble/open.go:392-395`) then setting `visibleSeqNum = logSeqNum` (`sources/pebble/open.go:402`). Batches with seqnums below the manifest's `LastSeqNum` are obsolete ghost writes that would have been flushed; those above it are the replay frontier.

3. **Truncated tail detection.** Inside `replayWAL` (`sources/pebble/recovery.go:524-568`), the loop distinguishes three outcomes per `rr.NextRecord()` error: `io.EOF` = clean tail → stop; `ErrUnexpectedEOF` on the *last* logical WAL with `strictWALTail=false` → truncated tail due to unclean crash → stop (treat incomplete last record as lost). On older WALs (`strictWALTail=true`) the same error is promoted to `ErrCorruption` (should have been closed cleanly, so truncation is unexpected). `ErrInvalidChunk`/`ErrZeroedChunk` forward to `record.Reader.readAheadForCorruption` (`sources/pebble/record/record.go:452-586`) which scans ahead for a future WAL-sync header whose `syncedOffset > invalidOffset`; if found, the invalid chunk is confirmed corruption, otherwise it's an ambiguous EOF preallocation artifact. `replayWAL` also handles interrupted ingest/excise batches specially by enqueuing an `ingestedFlushable` and forcing a WAL rotation (`sources/pebble/recovery.go:590-613`).

Completed work = in MANIFEST version + reflected sstables with `LastSeqNum` watermark. Interrupted work = trailing partial WAL record terminated uncleanly (truncated tail) — discarded but logged. Failed work = older WAL with corrupt chunk confirmed by read-ahead → return error and refuse to open (integrity over availability).

**Can recovery duplicate a tool or remote side effect, and is that stated honestly?**

Pebble does not have external tool calls; recovery duplicates only internal state-machine effects (KVs written to memtable/SST). Those are idempotent by sequence-number/level ordering: reapplying a Batch with the same `SeqNum`+`Count` yields the same visible state, and `BulkVersionEdit` forbids double-add (`sources/pebble/internal/manifest/version_edit.go:1137-1149`). So internal duplication is harmless.

The honesty is in what it *does* claim: it never claims exactly-once external effects. The WAL comment (`sources/pebble/recovery.go:438-449`) is explicit that unsynced WAL in kernel buffers is readable after crash but not durable, and Pebble's response is to *replay then flush* so the initial state becomes durable — a classic at-least-once state restoration. The `ApplyNoSyncWait` API (`sources/pebble/db.go:769-786`) is documented as "visible before synced" — identical to RocksDB's WAL manual flush. `LogData` kind is WAL-only and not applied to memtables (`sources/pebble/batch.go:597-608`), modeling event-only entries without state corruption.

For Aren, duplication risk would live *outside* Pebble: if Aren commits a Batch that includes "state=running→completed" and "trigger external tool", recovery of the second attempt would resend the trigger. Pebble's pattern requires the ordering: Batch for own-state+PROMISE → tool call (outside atomicity) → Batch for outcome/artifact, with tool work idempotency keyed by sequence number.

**How does a newer binary refuse, migrate, or safely open older data?**

*Refuse.* `lookupFormatMajorVersion` (`sources/pebble/format_major_version.go:428-466`) scans the `format-version` marker (`marker.format-version.<iter>.<value>`). If value parses > `internalFormatNewest` → `unknown format major version` error, closes marker and returns. If `< FormatMinSupported` (currently `FormatFlushableIngest`, `sources/pebble/format_major_version.go:287`) → `no longer supported` error. If dirname has legacy `CURRENT` file but no marker → `format major version 1 which is no longer supported` (`sources/pebble/recovery.go:261-270`). `Open` also early-returns `ErrDBNotPristine`/`ErrDBDoesNotExist` paths.

*Safely open older data.* If `lookupFormatMajorVersion` returns `FormatDefault` (empty marker), `Open` defaults `formatVersion = FormatMinSupported` (or `FormatMinForSharedObjects` if shared storage path) and sets `ErrorIfNotPristine=true` so an existing non-pristine DB cannot be silently overwritten (`sources/pebble/open.go:110-138`). `CheckCompatibility` of previous OPTIONS file rejects incompatible comparator/config mismatches (`sources/pebble/recovery.go:133-141`). `versionSet.initRecoveredDB` directly loads the replayed `Version` without assuming newer invariants (`sources/pebble/version_set.go:254-275`).

*Migrate.* `DB.RatchetFormatMajorVersion(fmv)` (`sources/pebble/format_major_version.go:515-559`) locks `DB.mu`, checks monotonic (refuse downgrade), sets `ratcheting=true`, then loops `current+1..target` invoking `formatMajorVersionMigrations[nextVers](d)`. Each migration is idempotent and responsible for calling `finalizeFormatVersUpgrade` which does `writeFormatVersionMarker` (`Marker.Move`, `sources/pebble/format_major_version.go:574-580`) + `vers.Store` + event. Some migrations block for compaction of marked tables (`compactMarkedFilesLocked`, `markFilesForCompactionLocked`). On `Open`, if `opts.FormatMajorVersion > d.FormatMajorVersion()` it ratchets automatically after the version/memtable/WAL are open (`sources/pebble/open.go:475-476`); for a fresh DB it writes the marker at `FormatMinSupported`.

There is no rollback after ratchet; the comment makes explicit that once bumped, prior binaries refuse to open (`sources/pebble/format_major_version.go:23-27`). Rollback testing is noted as TODO in the tracked transcoded issues but not implemented.

## Notable Patterns

- **Directory-locked store paths with failure injection below `vfs.FS`** — all persistence I/O flows through `vfs.FS` so production code has zero test hooks; `vfs/errorfs` and `vfs/mem_fs.go:38-160` provide deterministic error/latency/crash seams.
- **Atomic marker pattern reused for both MANIFEST and format-version pointers** — lexical `marker.<name>.<iter>.<value>` encoding with monotonic iter gives crash-safe pointer dereference; `LocateMarker` returns `Marker{dirFD, obsolete}` for deferred cleanup.
- **Two-level visibility sequence numbers (`logSeqNum` vs `visibleSeqNum`)** — assignment under `commitPipeline.mu`, publish via CAS loop on `visibleSeqNum`; iterators read at `visibleSeqNum` snapshot to hide concurrent in-flight batches without locking.
- **WAL-sync-offset as durability promise for failure disambiguation** — second 8-byte field in WAL-sync header encodes `syncedOffset` watermark; read-ahead returning `ErrInvalidChunk` only when sync promise confirms invalid chunk should have been valid.
- **Flushable batches as queue-prolog without memtable copy** — batches > `MemTableSize/2` skip memtable arena and sit in `mem.queue` as `flushableBatch` with `disable memory accounting` ref (`sources/pebble/recovery.go:622-628`), forcing same-log colocation and avoiding 2× copy on large ingest.
- **Virtual backing reference counting + zombie sets** — physical SST backing stays alive until no version references it *and* `virtualBackings.Unused()` empties; `zombieTables`/`zombieBlobs` extracted into `obsoleteTables` for async deletion via `deletepacer`.

## Tradeoffs

| Tradeoff | What is gained | What is sacrificed |
|----------|---------------|------------------|
| Commit visibility before WAL sync (default `Sync=false`) | Lower p95 write latency; concurrent batches publish without waiting for fsync | Crash can lose the last published writes despite them having been readable; durability only with `Sync=true` |
| Recyclable WAL reuse (zero WALs under `MaxNumRecyclableLogs`) | Avoids file-metadata fsync on every WAL rotation; critical for high-sync workloads | Requires log-number-tagged chunks and special InvalidChunk handling for leftover recyclable bytes; complicates reader |
| WAL-sync chunk upgrade gated on FMV | Backward compatible: old WALs readable before ratchet, new guarantee after | Transition window where WAL written without sync-offset has weaker EOF-vs-corruption signal until ratchet completes |
| MANIFEST is not checksummed per-record beyond `record` CRC and btree ordering checks | Simplicity, same record encoding for WAL and MANIFEST | Corruption in MANIFEST fails open hard (`checkConsistency` size check, `BulkVersionEdit` invariant panics); no graceful degrade to earlier MANIFEST |
| Forward-only format version | No complex downgrade migrations; safe for Cockroach arbitrarily-old raft log replay because `MinTableFormat` stays at PEBBLEv1 | Bad format ratchet cannot be reverted via binary rollback; forward fix required |
| `.CrashClone` simulates crashes at FS layer only | Deterministic, fast, covers 100s of crash points per test without spawning processes | Does not simulate kernel disk reordering beyond unsynced-bytes probabilistic drop, nor NVM partial-sector tear at 512B granularity |
| Checkpoint hard-links SSTs | Fast checkpoint even on 100 GiB LSM (no byte copy) | Remote/shared objects excluded (added to `remoteFiles`, catalog state written separately); restore on different store-backend version still needs object provider compatibility |

## Failure Modes / Edge Cases

- **Partial WAL record + clean tail.** A crash mid-block-write leaves a short block or zeroed padding. `nextChunk` returns `ErrInvalidChunk`/`ErrZeroedChunk`, `readAheadForCorruption` scans ahead; if no future WAL-sync promise exceeds `invalidOffset`, it returns `ErrUnexpectedEOF` and `replayWAL` drops the partial record (last WAL only). Older WAL with same pattern incorrectly returns corruption — caller context `strictWALTail` distinguishes.
- **Torn MANIFEST write.** `UpdateVersionLocked` panics `Logger.Fatalf` if any step after `ve.Encode` fails (flush/sync/marker Move). The two `SyncDir` calls (`createManifest` path and `Move`) close the marker-points-to-missing-manifest window, but a crash *between* first `SyncDir` and `Move` leaves both old and new MANIFEST durably present while marker still points to old — next `recoverVersion` replays old MANIFEST cleanly.
- **Obscured file-number reuse.** After crash, `maxFilenumUsed` ratcheted past all `List()` entries + WAL numbers (`sources/pebble/recovery.go:112-191`) prevents reuse collision with ingested external files. Mitigated by ingest crash test at `sources/pebble/ingest_test.go:3062-3099`.
- **Checkpoint while concurrent flush/compaction appends MANIFEST.** `checkpoint.go:193-245` holds `logLock` while sampling `manifestSize` and `current.Version`; `writeCheckpointManifest` copies only `LimitedReader(N: manifestSize)` at record granularity so post-snapshot VersionEdits don't bleed into checkpoint's MANIFEST copy even though sstables from those edits are not hard-linked.
- **WAL rotation without fsync.** `StandaloneManager.Create` syncs `walDir` before returning new writer (`sources/pebble/wal/standalone_manager.go:216-218`), but `LogWriter.Close` still needs `Sync`+EOF trailer before the predecessor WAL can be considered closed (`sources/pebble/wal/standalone_manager.go:312-320`); caller Contract in comment: previous writer must be closed before next `Create`.
- **Fsync-error handling.** `atomicfs.Marker.Move` and `versionSet.createManifest` panic on `dirFD.Sync()` failure (`sources/pebble/vfs/atomicfs/marker.go:234-238`, `sources/pebble/version_set.go:216-239`); philosophy is fsync errors are unrecoverable (PostgreSQL wiki model) so crash rather than continue with uncertain durability.
- **Zeroed chunk disambiguation failure.** The comment on `recyclableHeaderSize` vs `walSyncHeaderSize` zero-padding (`sources/pebble/record/record.go:303-351`) acknowledges two edge windows: remainder with `11 <= bytes < 19` and between `legacyHeaderSize` and `recyclableHeaderSize` use zero checks to decide; partial block with stray non-zero bytes from corruption incorrectly triggers `ErrZeroedChunk` → promoted to corruption only if read-ahead finds validating future syncOffset.
- **Memory-recycled Batch data race window.** `Batch.lifecycle` refcount avoids reusing `data` slice while `LogWriter` still holds reference under WAL failover (`sources/pebble/batch.go:240-305`); incorrect caller that mutates Batch after `ApplyNoSyncWait` before `SyncWait` could observe stale commit state.

- **Durability-window contract for Aren** should explicitly pick one of: (a) always `Sync=true` per own-state Batch (lower throughput, no window), or (b) periodic `LogData(nil,Sync)` group commit + explicit `visibleSeqNum` polling before acknowledging external work. Pebble's `Checkpoint.WithFlushedWAL` (`sources/pebble/checkpoint.go:45-49`) pattern is the model: empty sync record before snapshot.
- **Adopt WAL-sync-style durability watermark for Aren event log** if it stores events in a record-log format; the 8-byte `syncedOffset` promise is a lightweight alternative to per-record fsync for disambiguating EOF vs corruption without double write.

- **Format-version migration hardening**: any new Aren storage format change should add a forward-only `Format*` constant and an idempotent migration closure; test matrix must include `Newest - 2` backward opens and `k-th-write` crash clone across ratchet.
- **Rollback story**: Pebble intentionally rejects downgrade (`sources/pebble/format_major_version.go:533-534`). Aren should decide upfront whether it needs a forward-fix-only policy or versioned snapshots allowing restore-from-checkpoint downgrade.
- **Obsolete-file reclamation seam**: `Obsolete(minUnflushedNum, noRecycle)` + `deletepacer` pattern decouples WAL GC from LSM flush completion — reuse for Aren artifact GC (unflushed outcome watermark → safe prune of old event/artifacts).
