## Summary

`temporal-sdk-go` is a **stateless client-side SDK** — it owns no WAL, manifest, checkpoint file, or local embedded DB. All durable state is delegated to the Temporal Server. The SDK's "persistence" model is **history-replay**: every deterministic decision is turned into a `Command` batch that is atomically committed in a single `RespondWorkflowTaskCompleted` RPC; the server appends the corresponding history events durably and the SDK rebuilds in-memory workflow state by replaying that history on every workflow task (including after any crash/eviction). There is no local filesystem write ordering to audit — `grep` across the entire SDK finds zero `fsync`/`rename`-based WAL/manifest logic; the only `rename` is in `testsuite/devserver.go:236` for downloading the dev-server binary.

Because the SDK never claims exactly-once for external effects, it is honest about duplication windows: activities (and remote Nexus operations) are scheduled via commands but executed out-of-band; a successful activity whose completion overlaps a failed workflow task can be re-executed. Idempotency is pushed to user code and documented (`workflow/doc.go:77`, `temporal/doc.go:72`).

Schema/format evolution is handled not by file migrations but by **marker-based versioning** in history (`GetVersion` markers, SDK flags, binary checksum/build-id, typed search attributes) plus sticky-cache invalidation and replay-compatibility tests (`test/replaytests/`). The SDK detects incompatible history during replay and fails the workflow task with `WORKFLOW_TASK_FAILED_CAUSE_NON_DETERMINISTIC_ERROR` (default `BlockWorkflow` = stuck-until-fixed; optional `FailWorkflow`). No local-data migration code exists; a newer binary replays older histories by falling back to `DefaultVersion` and skipping unknown SDK flags only if already present in history.

For Aren Phase 11 this is the reference architecture for "server-is-the-WAL" — it avoids local durability entirely, which makes it crash-safe by construction but transfers all atomicity/durability guarantees to server configuration.

## Rating

**Rating: 8 / 10**

Rationale (rubric: storage coherence, atomic recovery, honest duplication, safe schema evolution, tested durability):

* **Storage coherence** — Excellent within SDK scope: all workflow state mutations (activities, timers, child workflows, Nexus ops, signals, search attributes, markers) are represented as `commandpb.Command`s queued in `commandsHelper.orderedCommands` and flushed together. No split-brain between state/outcome/events; they are one batch.
* **Atomic unit correctly scoped** — The unit is the whole WFT response, matching Aren-owned lifecycle state (deterministic decisions) not external side-effects. Separation is explicit and documented.
* **Recovery is honest** — After crash, sticky cache is discarded and history is replayed from server (`isFullHistory` check, `resetHistory` on cache miss). Interrupted vs completed work is distinguished by history event presence (e.g. `ActivityTaskScheduled` vs `ActivityTaskCompleted`). Duplication possibility is stated via idempotency guidance and activity retry/heartbeat contracts.
* **Schema evolution** — Robust for workflow code: `GetVersion`, `PreferredVersionProvider`, SDK flags with capability gating, binary checksum/build-id/worker deployment version. Weakness is rollout coupling: search-attribute size overflow silently skips the upsert (`changeVersionSearchAttrSizeLimit`), and rollback of a flag-enabled code change still requires keeping the old code path behind `GetVersion`.
* **Durability/crash tests** — Good replay/compat coverage but **no fault-injection between durable steps inside the SDK** (there are no local steps to fault). The SDK proves durability by proxy via server + replay tests. No WAL corruption handling is needed, but also no SDK-level WAL-corruption test exists.
* Deduction for "not a standalone durable runtime": if you copy only the SDK without a Temporal Server, there is zero persistence — not applicable to a pure in-process Aren host without that server.

## Answers to Dimension Questions

### What is the atomic unit, and does it match Aren-owned lifecycle state rather than external effects?

**Atomic unit = one workflow task’s command batch + protocol messages + SDK flags, committed together in a single `RespondWorkflowTaskCompletedRequest` (or failed as a single `RespondWorkflowTaskFailedRequest`).**

Evidence: all SDK mutations go through `workflowEnvironmentImpl` → `commandsHelper` (`scheduleActivityTask`, `startTimer`, `startChildWorkflowExecution`, `scheduleNexusOperation`, `upsertSearchAttributes`, `recordVersionMarker`, `recordSideEffectMarker`, etc.) which append to `orderedCommands` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_command_state_machine.go:152-154`, `studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_event_handlers.go:792-896`). No command is sent until WFT completion. In `internal_task_pollers.go:539-568` (`RespondTaskCompletedWithMetrics`) the whole batch (plus sticky attributes, eager reservations) is serialized, passed through the `outboundPayloadVisitor` (extstore offload) (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_pollers.go:598-632`), and sent as one gRPC call in `sendTaskCompletedRequest` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_pollers.go:698-762`). If any visitor or serialization step fails, the SDK deliberately discards the original completion and sends a single `RespondWorkflowTaskFailed` instead — preserving atomicity (no half-persisted command set). The server then durably appends the corresponding history events atomically; the SDK treats that as the commit point.

This matches Aren-owned lifecycle state (deterministic scheduling decisions) and **excludes** external effects. Activity execution happens out-of-band; `ExecuteActivity` only schedules (`ScheduleActivityTask` command) and the activity’s `Started/Completed` events arrive later (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_command_state_machine.go:1356-1377`). A WFT that schedules an activity and then crashes before responding will be retried and will re-schedule the same `ActivityID` deterministically (`getStringID(scheduleID)`), so the server de-duplicates scheduling but the activity may execute twice if the first execution already started. The SDK never implies that scheduling an activity equals having its side-effect. Docs are explicit: “Execution must be idempotent” (`studies/aren-go-runtime-study/sources/temporal-sdk-go/workflow/doc.go:77-78`) and “At-most once activity execution - Execute non-idempotent activities as part of your workflows” (`studies/aren-go-runtime-study/sources/temporal-sdk-go/temporal/doc.go:72`).

### After restart, how is interrupted work distinguished from failed or completed work?

**Purely by server-returned history, replayed through the command state machines — the SDK has no local recovery state.**

On restart (or sticky eviction) `GetOrCreateWorkflowContext` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:794-878`) checks whether the cached `workflowExecutionContextImpl` is still valid:

* Sticky hit only if `history.Events[0].EventId == previousStartedEventID+1` **and** same `wth` and not `IsDestroyed()` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:817-825`). Otherwise the context is evicted (`removeWorkflowContext` + `clearState`) (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:841-843`) and fully rebuilt via `createWorkflowContext` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:727-792`).
* If the poll returned a partial history (`!isFullHistory` = first event is not `WORKFLOW_EXECUTION_STARTED`), `resetHistory` rewinds the `HistoryIterator` and forces a full replay (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:851-856`, `studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_pollers.go:1305-1311`).

The replay engine (`workflowExecutionContextImpl.ProcessWorkflowTask`, `studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:1053-1295`) then classifies each event:

* `IsReplayEvent = eventID <= PreviousStartedEventId || isCommandEvent` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:282-284`). Replay events feed existing `commandStateMachine`s; non-replay events drive new code.
* For activities: `handleActivityTaskScheduled` → `CommandSent → Initiated`, `handleActivityTaskCompleted/Failed/TimedOut/Canceled` → `Completed` via `handleActivityTaskClosed` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_command_state_machine.go:1136-1172`). An interrupted activity appears as `Scheduled` + `CancelRequested` or with no closing event; the state machine stays in `Initiated/CanceledAfterInitiated` and the SDK will re-issue or cancel on the next WFT accordingly.
* For local activities: durability is the `MarkerRecorded` event. If the WFT that executed a local activity crashed before its markers were committed, the markers are absent on replay and the SDK re-executes the local activity (it is still in `pendingLaTasks`) (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:1147-1186`).
* Failed/completed workflows are `isWorkflowCompleted` + `err` in the context (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:646-695`); a destroyed context (`IsDestroyed()`) is rebuilt from scratch on the next task (`resetStateIfDestroyed`, `studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:887-913`).

Thus interrupted WFTs become timeouts/retries (server will reschedule a new WFT after `WorkflowTaskTimeout`), failed tasks appear as `WorkflowTaskFailed` events with a `Cause` that the SDK surfaces as `workflowPanicError`, and completed activities appear as closed command states. No heuristic time-window guessing — history is the ground truth.

### Can recovery duplicate a tool or remote side effect, and is that stated honestly?

**Yes, duplication can happen and the SDK is honest about it — exactly-once is never claimed for side-effects.**

Two concrete duplication windows:

1. **Activity/Nexus execution vs WFT commit**: The WFT schedules an activity (`ScheduleActivityTask` command) and the activity may start & complete on an activity worker, but if the workflow worker crashes before sending `RespondWorkflowTaskCompleted` (or the server times out the WFT), the server will reschedule the same WFT. On replay the SDK will deterministically re-issue the same `ActivityID`; the server de-duplicates scheduling by `ActivityID`+`ScheduledEventId`, but if the first activity already executed externally, its external effect may have happened once already. The next WFT will see either the activity’s completion event (if it arrived before the retried WFT) or re-dispatch it. The SDK’s retry policy may also retry independently of workflow replay. No SDK mechanism rolls back the external effect.

2. **Local activity collapsed WFT**: Local activities run inside the workflow worker; if their `MarkerRecorded` batch is lost due to a WFT failure (the markers were generated but never successfully `RespondWorkflowTaskCompleted`), replay will re-execute the local activity function. The SDK’s local-activity retry path (`retryLocalActivity` in `internal_task_handlers.go:1351-1379`) explicitly re-sends via `laRetryCh` or creates a backoff timer, acknowledging duplicate execution as expected.

Honesty:

* SDK docs mark workflows as requiring idempotent activities: `workflow/doc.go:77` (“Execution must be idempotent”), `temporal/doc.go:72` (“At-most once activity execution - Execute non-idempotent activities as part of your workflows. Temporal will not” [retry without idempotency key]).
* Client-side `ExecuteActivity` APIs carry `RequestEagerExecution` and server dedup is via `ActivityID`; there is no cross-run dedup promise in the SDK.
* WorkflowStreams `contrib` explicitly documents the TTL-gated exactly-once within its own durable session (`contrib/workflowstreams/doc.go:7`, `contrib/workflowstreams/client.go:26`) — showing that when exactly-once is provided, it is scoped and labeled, unlike raw activities/Nexus.

The SDK does not hide this; it models activities as `scheduledActivity{handled bool, callback, waitForCancelRequest}` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_event_handlers.go:56-66`) and exposes `RecordHeartbeat` so callers can make retries safe via `GetHeartbeatDetails`.

### How does a newer binary refuse, migrate, or safely open older data?

**No local file to refuse/migrate — compatibility is about replaying older histories with newer workflow code. The SDK uses marker-based versioning, not file-format migration.**

Mechanisms identified (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_event_handlers.go:958-1002`, `internal_flags.go`, `checksum.go`):

* **`GetVersion(changeID, min, max)`** — the primary patching primitive. On first execution (non-replay) it calls `resolvePreferredVersion` (optionally via `PreferredVersionProvider`) and records a `Version` marker (`versionMarkerName = "Version"`, `studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_command_state_machine.go:232-233`) plus an upsert of `TemporalChangeVersion` search attribute. On replay, `changeVersions[changeID]` is already populated from the marker event, so the call returns the recorded version even if code now requests a different range; out-of-range panics with `[TMPRL1100]` and becomes a `WorkflowTaskFailedCauseNonDeterministic` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_event_handlers.go:945-956`). For a changeID never seen before, replay returns `DefaultVersion` (`-1`) (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_event_handlers.go:965-966`), allowing old histories without that changeID to continue running old code.

* **`PreferredVersionProvider`** (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/worker.go:96-142`) — lets a newer binary decide per-execution (non-replay) which version to record, enabling a rolling deploy: initially return `DefaultVersion` so old workers can still replay; after full rollout return `MaxSupported`. The decision is recorded deterministically.

* **`MutableSideEffect`/`SideEffect` markers** — `MutableSideEffect` persists `mutableSideEffect[id][callCount]` and only appends a new `MutableSideEffect` marker when `!equals(new, old)` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_event_handlers.go:1155-1185`). `SideEffect` validates `sideEffectResult[sideEffectID]` presence on replay or panics (`No cached result found`, `studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_event_handlers.go:1065`). This makes non-deterministic code paths corrupt only if the marker sequence diverges.

* **SDK flags** (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_flags.go:14-58`) — numbered flags (e.g. `SDKFlagLimitChangeVersionSASize`, `SDKFlagProtocolMessageCommand`, `SDKFlagMemoUserDCEncode`). `tryUse(flag, !isReplay)` records a new flag only during non-replay when `capabilities.SdkMetadata` and `sdkFlagsAllowed[flag]` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_flags.go:116-136`); `set(flags…)` applies flags already seen in history regardless of replay. Unknown flag values (`> MaxUint32` or not in `sdkFlagsAllowed`) cause `unknownSdkFlagError` → WFT failure (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:311-317`). Rollback limits: downgrading a worker that introduced a flag still replays old-flags histories, but removing flag-gated code without keeping the `tryUse` call would break replay — the flag stays in history forever.

* **Binary checksum / Build ID / Worker Deployment Version** — `checksum.go:16-51` hashes the executable; `RespondWorkflowTaskCompleted/Failed` always stamps `BinaryChecksum` (+ legacy `WorkerVersion`/`Deployment` + `DeploymentOptions`, `studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_pollers.go:846-877`). When `capabilities.BuildIdBasedVersioning` is true the checksum is cleared and deployment version becomes authoritative. This is server-side routing, not a reopen refusal; the SDK never refuses to open older data — it always attempts replay and either succeeds or fails the WFT deterministically.

* **Compatibility tests** — `test/replaytests/` stores dozens of JSON histories (`local-activity.json`, `mutable-side-effect.json`, `cancel-timer-after-activity.json`, `continue-as-new.json`, `activity-same-time-as-cancel.json`, etc., `studies/aren-go-runtime-study/sources/temporal-sdk-go/test/replaytests/`) that are fed to `worker.WorkflowReplayer` in `test/integration_test.go:1605-1846` and in `worker/worker.go:151-240` (`WorkflowReplayer.RegisterWorkflow/ReplayWorkflowHistory`). CI also builds with `PreferredVersionProvider`/`GetVersion` mocks (`internal/internal_workflow_testsuite.go:3238-3239`).

* **Refusal mode** — there is no file-open refusal. On incompatible code the WFT fails with `Cause = NON_DETERMINISTIC_ERROR` or `UNKNOWN_SDK_FLAG` and, under the default `BlockWorkflow` policy (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/worker.go:539-544`), the workflow is **blocked** (WFT times out and retries forever until fixed), not rejected. With `FailWorkflow` (`studies/aren-go-runtime-study/sources/temporal-sdk-go/internal/internal_task_handlers.go:1332-1338`) it fails the workflow execution explicitly. No forward migration mutates old history; history is immutable.

## Tradeoffs

| Tradeoff | Pro | Con | Design hint for Aren if reused |
|----------|-----|-----|--------------------------------|
| **No local WAL → all durability from server** | Zero `fsync`/`rename`/`WAL` code to maintain; crash recovery is simply “lose sticky cache and refetch” — elegant and correct when server is durable | `temporal-sdk-go` alone cannot be embedded as an Aren host without an external durable log; latency bound to server round-trip; tests need dev-server | For offline/single-binary Aren, add a local WAL layer or switch to `temporalite`-style embedded server |
| **Whole-WFT atomicity** | Simple `matchReplayWithHistory` invariant; no inter-event torn writes | Burst of many activities can exceed gRPC limits → WFT failure; user must batch or raise limits | Consider capping eager-activity reservations (`MaxConcurrentEagerActivityExecutionSize`) or chunking commands |
| **Search-attribute size gate (>2KiB skip)** (`changeVersionSearchAttrSizeLimit = 2048`) | Prevents one `GetVersion` call from failing the workflow due to many distinct changeIDs | Search-attribute visibility becomes lossy; debugging “which version ran where” may miss entries silently | Budget changeIDs or raise limit; log skipped IDs at `Warn` (already present) |
| **Sticky cache: latency vs replay cost** (`defaultStickyCacheSize = 10000`, `StickyScheduleToStartTimeout = 5s`) | Hot workflows resume in microseconds without history fetch | Large working sets thrash LRU → repeated full replays; `StickyCacheTotalForcedEviction` is late signal | Size cache by working-set, not arbitrary; monitor forced-eviction metric |
| **Extstore offloading** | Keeps history small; enables >2MiB payloads via S3 | Adds second durability domain (object store); driver mis-configuration (`Name` mismatch) makes retrieval fail | Pin driver `Name` immutable after first store; test dual-path (inline + offloaded) |
| **SDK flags capability-gated** | Allows safe rollout of breaking worker changes | Workers on old servers without `SdkMetadata` cannot use new flags → silent fallback to old behavior | Gate deployments on server `GetSystemInfo` capability probe |

## Future Considerations

* **Embedded Aren host without Temporal Server**: the SDK’s statelessness is an asset for cloud deployment but a liability for single-binary/offline Aren. If analysis scope is narrowed to “just the SDK repo”, recommend pairing with an opt-in local WAL (e.g. SQLite + WAL, Bolt, or embedded `temporalio/temporalite`) and documenting the extra durability domain. Without that, recommending `temporal-sdk-go` as a standalone durable runtime for Aren is incorrect.
* **Versioning sprawl**: `GetVersion` markers are append-only. Long-lived workflows accumulating many `changeID`s hit the 2 KiB SA limit and bloat history. Consider deprecating old branches after proving no open workflows need them, using `PreferredVersionProvider` to gate removal, and compacting via `ContinueAsNew`.
* **Payload visitor concurrency**: `MaxConcurrentWorkflowTaskExternalStorageVisits` defaults to 3 (`internal_task_pollers.go:47`, `internal/worker.go:508`). Large-payload workflows should load-test with `payloadVisitorConcurrency` tuned — the default caps S3 throughput.
* **Eager activity throttling**: `MaxConcurrentEagerActivityExecutionSize` + `MaxEagerActivityReservationsPerWorkflowTask` bound Eager completions. For high-throughput Aren tools, eager activities reduce server hops but can starve slots — benchmark with tunable.
* **SDK flag operational runbook**: env-var `TEMPORAL_SDK_FLAG_<ID>=1|0` (`internal_flags.go:71-83`) exists but is “strongly discouraged”. For Aren production, prefer `WorkerOptions` + server capability alignment over undocumented env-var escapes.
* **Binary checksum deprecation path**: `BinaryChecksum` → `WorkerVersion` → `WorkerDeploymentVersion/DeploymentOptions`. The code still stamps all three for backward compatibility (`internal_task_pollers.go:852-868`). Future Aren SDKs should commit to deployment-based versioning and stop asserting on checksum.
