## Summary

Nomad is a workload orchestrator, not a durable workflow engine. It has no workflow/activity/history/replay abstraction comparable to Temporal/Cadence. Instead it provides three adjacent mechanisms that partially answer the dimension: (1) **deterministic FSM replication** via Raft where server-side state transitions must be pure functions of the Raft log entry (`nomad/fsm.go:250`, `contributing/architecture-state-store.md:13`); (2) **bounded retry/reschedule spaces** with distinct local `RestartPolicy` (`nomad/structs/structs.go:6537`) and global `ReschedulePolicy` (`nomad/structs/structs.go:6606`) plus server-tracked `RescheduleTracker`/`RescheduleEvent` (`nomad/structs/structs.go:10637`); (3) **narrow idempotency** limited to parameterized job dispatch via `DispatchIdempotencyToken` (`nomad/structs/structs.go:4476`, `nomad/state/state_store.go:1923`, `nomad/job_endpoint.go:2047`, `nomad/fsm.go:683`); and (4) **timer-like dispatch** limited to cron-based `PeriodicDispatch` (`nomad/periodic.go:23`) and evaluation reschedule delays. There is no checkpoint, child-workflow ownership, determinism checker, cancellation scope, versioning, or exactly-once effect contract. For Aren Phase 16 this is the correct negative example: Nomad shows what a scheduler does when it deliberately defers durable workflow machinery.

## Rating

**3/10** — Nomad offers strong lessons on deterministic FSM discipline and durably persisted scheduling state (Raft + snapshots/restore), and its retry/reschedule/idempotency primitives are production-hardened and well-tested. But as a durable workflow substrate it is intentionally absent: no replayable workflow code, no activity/timeout/continue-as-new/child-workflow model, no determinism enforcement tooling, no duplicate-delivery protection beyond dispatch, and no operator poison-pill handling. The value for Aren is as a reference for what to borrow (FSM determinism rule, tracker pattern, eval blocking) and what not to copy (trying to stretch batch/periodic jobs into general workflows).

## Answers to Dimension Questions

### Which code must remain deterministic and which code may perform external effects?

**Deterministic (must be pure of log inputs):** All `nomadFSM.Apply*` methods and `StateStore` mutators. The contract is explicit in `contributing/architecture-state-store.md:13-31`: `fsm.Apply` functions must be deterministic over their inputs for a given state; never generate timestamps or random IDs inside the store — pass them from the RPC handler. Example violation called out: `obj.CreateTime = time.Now()` inside `UpsertObject` is incorrect; correct is `UpsertObject(..., timestamp time.Time)`. The `.semgrep/fsm_time.yml:23` rule machine-checks this. Concrete call sites honor it: dispatch handler creates the child ID via `structs.DispatchedID(..., time.Now())` at `nomad/job_endpoint.go:2068` *before* Raft, and the FSM re-checks idempotency at `nomad/fsm.go:683` without generating time itself. Snapshot/restore (`nomad/fsm.go:123-148`) is also deterministic — it replays the persisted `PeriodicLaunch` table (`nomad/fsm.go:1695`) rather than recomputing.

**Effectful (may side-effect, must stay outside Raft):** Everything before `raftApply` and after `FSM.Apply` returns. Scheduler workers (`nomad/worker.go:88-125`) dequeue evals, take snapshots at `SnapshotIndex`, invoke the scheduler, then submit plans via Raft — the scheduler itself is effectively an activity executor. Client-side task restarts (`client/allocrunner/taskrunner/restarts/restarts.go:16-259`) use `rand.NewSource(time.Now().Unix())` and `time.Now()` for jitter/interval (`restarts.go:53, 194`) — correctly kept out of the FSM. Drivers, Consul/Vault, CSI plugins, template rendering, health checks, and deployment watchers all run outside the replicated log. The `PeriodicDispatch` daemon (`nomad/periodic.go:315-369`) sleeps on `time.After` and then calls `DispatchJob` (`nomad/periodic.go:52-75`) which goes through Raft — the timer wait is effectful, the commit is deterministic.

**Gap:** There is no language-level sandbox forcing workflows to stay deterministic (no static checker, no replay harness). Determinism is enforced only by code review + semgrep on the store boundary, not as a general workflow programming model.

### What can execute more than once after worker or daemon failure?

**Can re-execute (at-least-once, operator must make idempotent):**

- **Client task restarts and alloc rescheduling:** `RestartPolicy` is enforced locally on the client (`client/allocrunner/taskrunner/restarts/restarts.go:153-240`) — if the client dies mid-restart, the count/interval state is lost and the server will reschedule via `ReschedulePolicy` creating a new `Allocation` with a fresh `RescheduleEvent` (`nomad/structs/structs.go:10707`). The new alloc re-runs the task from scratch; there is zero dedup of task side-effects (file writes, network calls, payments).
- **Scheduler evaluations and plan applies:** Evaluations are dequeued from `EvalBroker` by multiple workers; `BlockedEvals` deduplicates queued evals per job (`nomad/blocked_evals.go:84-339`) but workers can race, Nack on `raftSyncLimit` timeout (`nomad/worker.go:48-50`), and be re-queued. The scheduler is not recorded step-by-step, so a worker crash after allocating resources but before `raftApply` simply re-runs the whole scheduling pass.
- **Periodic dispatch creation:** `PeriodicDispatch.run` (`nomad/periodic.go:315-334`) sleeps until `nextLaunch()` then derives a job ID as `fmt.Sprintf("%s%s%d", parent, PeriodicLaunchSuffix, time.Unix())` (`nomad/periodic.go:440-441`) and commits via `raftApply` (`nomad/periodic.go:75`). If the leader fails between computing `Next` and committing, the new leader recomputes `Next` from restored `PeriodicLaunch` state (`nomad/leader.go:841-846`). The launch is at-least-once — `ProhibitOverlap` (`nomad/periodic.go:352`) only skips if `RunningChildren` are still live, it does not deduplicate by launch timestamp beyond the ID prefix. Two leaders in split-brain cannot both commit due to Raft quorum, but after failover the same launch instant can be retried.
- **Client `AllocClientUpdate` heartbeats:** Batches of `Allocation` status updates sent from client to servers (`nomad/fsm.go:285-287` `applyAllocClientUpdate`) can be retried on RPC failure; each retry re-applies `DesiredStatus`/`ClientStatus`/`TaskStates` transitions. They are idempotent at the allocation-record level but not at the external service registration or volume claim level.

**Won't duplicate without new log entry:** Any write that made it through `raftApply` is linearizable and replicated; Raft prevents double-apply of the same log index. After redelivery, the FSM will re-apply the same bytes deterministically, but Nomad does not expose an end-to-end exactly-once promise to callers — clients that retry an HTTP request without an idempotency token will create a new eval/job.

**Idempotency coverage is narrow:** The only caller-supplied dedup key is `WriteRequest.IdempotencyToken` for `JobDispatch` (`nomad/structs/structs.go:449`). It is unusually robust — checked both before `raftApply` (`nomad/job_endpoint.go:2047`) and after replication inside the FSM (`nomad/fsm.go:683`) to close the TOCTOU race (fix documented in `.changelog/27353.txt:2`). But it is *only* for dispatched children of a parameterized job (`nomad/state/state_store.go:1924`). `JobRegister`, `JobDeregister`, `AllocUpdate`, `Deployment*` have no generic dedup token.

### How are workflow definition changes made compatible with existing histories?

Nomad has no `History`/`WorkflowDefinition`/`Version` concept. The closest analogs are **job versioning** (`JobVersionsResponse` at `nomad/structs/structs.go:1593`) and **FSM version-gated migrations**, not workflow history compatibility:

- **Job spec compatibility:** `req.Job.Canonicalize()` at `nomad/fsm.go:681` normalizes empty maps/slices to nil for `reflect.DeepEqual` and migrates old upgrade blocks — this is schema normalization, not replay compatibility. Diff handling (`nomad/structs/diff.go:292-304`) compares `RestartPolicy`/`ReschedulePolicy` changes to decide whether an eval is needed, but never replays prior allocations against a new scheduler build.
- **Raft log versioning:** `nomad/fsm.go:250-261` handles `IgnoreUnknownTypeFlag` (`nomad/structs/structs.go:153-158`) so old servers ignore new `MessageType`s after upgrade; `nomad/fsm.go:139-145` enterprise appliers are isolated behind `LogAppliers`/`SnapshotRestorers` maps (`nomad/fsm.go:123-148`). Snapshots carry `SnapshotType` tags (`nomad/fsm.go:28-87`) and old snapshot types are tolerated or migrated via `StateRestore` (`nomad/state/state_store.go:28-30`).
- **No replay or determinism checker:** There is no concept of replaying a recorded history against new code, no `getVersion`/`patch` API, no replay fixtures, and no worker deterministic-replay test harness. Changing a `PeriodicConfig` or `ReschedulePolicy` between job updates simply affects future allocs; in-flight allocations keep their embedded task group copy (`nomad/structs/alloc.go:104-9141`) and are not retroactively migrated. This is scheduler-versioning, not workflow-versioning.

For Aren, the lesson is that Nomad achieves rolling-upgrade safety by keeping the log entry the canonical serialized request (`nomad/structs/structs.go:10812-10818` msgpack with `MessageType` prefix) and making the store tolerate unknowns — it never needs to replay history through new workflow code because there is no workflow code.

### What concrete Aren use would justify adopting any of this machinery?

**Borrow now (small, targeted):**

- **Deterministic FSM rule:** Adopt the `architecture-state-store.md:13` discipline verbatim for any Aren server-side replicated state: pass `time.Now()`/`uuid.Generate()` into the mutation layer, never call them inside it. Enforce with a semgrep rule mirroring `.semgrep/fsm_time.yml`. This costs almost nothing and prevents a class of Raft divergence bugs.
- **Idempotency token for retried submissions:** The Nomad dispatch fix is a reference implementation: accept `IdempotencyToken` on write RPCs (`nomad/structs/structs.go:449`), store it on the child entity (`nomad/structs/structs.go:4476`), check prefix-scoped `CheckIdempotencyToken` both pre-Raft (`nomad/job_endpoint.go:2047`) and post-replication (`nomad/fsm.go:683`). Aren should add this to its external trigger → run creation edge (webhook, CLI, event bridge) — the cheapest guard against duplicate runs when clients retry after 5xx/network blips.
- **RescheduleTracker pattern for run retries:** The `RescheduleTracker.Events` + interval-window counting (`nomad/structs/structs.go:10637-10704`) is a durable, audit-friendly alternative to an in-memory retry counter. If Aren adds per-run retry (e.g., flaky LLM tool call), persist `[]RescheduleEvent{Time, PrevRunID, Delay}` keyed by parent run and enforce `Interval`/`Attempts`/`DelayFunction` exactly as Nomad does. Start with `constant` delay to avoid over-engineering exponential/fibonacci.

**Defer until proven painful:**

- **Full history replay / deterministic workflow runtime** — Nomad proves you can run a large orchestrator without it. For Aren, this machinery is only justified when (a) long-running LLM agent sessions must survive daemon loss mid-tool-call and resume from a checkpoint rather than re-executing billable/costly tool calls, or (b) you need causal debugging of past decisions. Until those are top-3 user requests, a simple "record events, re-run from last completed tool" journal beats a Temporal-style replay engine.
- **Cron/periodic dispatch** — `PeriodicDispatch` (`nomad/periodic.go:138-334`) is justified in Nomad because jobs are first-class cron citizens. For Aren, only adopt if you ship scheduled agents (daily brief, heartbeat). Even then, prefer a single lightweight cron trigger that enqueues a run via the idempotent submit path above, rather than Nomad's heap + watcher + `Tracked` map.
- **BlockedEvals/worker pool** — The eval broker + blocked set (`nomad/blocked_evals.go:31`, `nomad/worker.go:92-125`) exists to handle scheduling under capacity constraints at scale. Only relevant to Aren if you build your own resource-aware scheduler for constrained execution; for the MVP, a durable queue (e.g., Postgres `FOR UPDATE SKIP LOCKED`) is simpler.

## Architectural Decisions

- **Raft + FSM over workflow replay:** State is durably replicated via HashiCorp Raft (`nomad/fsm.go:250`, `nomad/leader.go:443`) with `raftApply(MessageType, entry)` (`contributing/architecture-state-store.md:75`) rather than an append-only workflow history that is replayed through user code. The store is MemDB with copy-on-write snapshots (`nomad/state/state_store.go:28`, `contributing/architecture-state-store.md:8-9`). Tradeoff: linearizable writes and leader-driven mutations are simpler to operate at 5k+ nodes, but you lose the ability to replay arbitrary user code deterministically.
- **Two-level retry (Restart vs Reschedule):** Local `RestartPolicy` on the client (`nomad/structs/structs.go:6537`, `client/allocrunner/taskrunner/restarts/restarts.go:26`) handles same-node task crashes with jittered `Delay` and interval reset; global `ReschedulePolicy` (`nomad/structs/structs.go:6606`) handles placement-level failures via server-generated replacement allocs tracked in `RescheduleTracker` (`nomad/structs/structs.go:10637`). Mirrors the Kubernetes RestartPolicy vs. Job-level reschedule distinction. Keeps tail latency low (local restart) while still escaping bad nodes.
- **Idempotency at the dispatch boundary only:** Rather than generic write dedup, dedup is scoped to `JobsByIDPrefix(parentID)` prefix scan (`nomad/state/state_store.go:1924`) keyed by `DispatchIdempotencyToken`. Checked both in the handler and inside the FSM (`nomad/fsm.go:683`) — a rare belt-and-suspenders pattern that fixed GH-27353 (`.changelog/27353.txt:2`). Keeps the common case fast (no global token index) at the cost of not generalizing.
- **Periodic as heap + Raft, not durable timer:** Cron `Next` is computed from wall-clock (`nomad/periodic.go:217-218` `job.Periodic.Next(time.Now().In(...))`) on the leader, stored only as next-heap entry (`nomad/periodic.go:469-479`) and `PeriodicLaunch` timestamp (`nomad/fsm.go:727-733`). Timers do not survive as durably scheduled work items with cancellation; a missed tick after failover is handled by recomputing `Next` on `restorePeriodicDispatcher` (`nomad/leader.go:841`). Simple, but can skip or double-launch around clock skew/leadership flaps — compare to workflow durable timers that are part of the history.
- **Eval dedup via BlockedEvals, not exactly-once dequeue:** `EvalBroker` + `BlockedEvals.duplicates` (`nomad/blocked_evals.go:84-92`) collapses duplicate blocked evals per job and coalesces unblocks via `duplicateCh`/`prune`/`Untrack`. Does not guarantee exactly-once scheduling; workers can still race to `Dequeue` (`nomad/worker.go:44` `dequeueTimeout: 500ms`) and Nack on Raft sync lag (`nomad/worker.go:48`). Optimizes for throughput and backpressure over uniqueness.

## Notable Patterns

- **Pass-the-clock determinism:** Every `Apply*` entry point decodes bytes produced by the handler and never calls `time.Now()` itself; contrast `job_endpoint.go:2068` (handler allocates `time.Now()` into `DispatchedID`) vs `fsm.go:727` (FSM persists but does not mint). Pattern enforced culturally (`architecture-state-store.md:13`) and mechanically (`.semgrep/fsm_time.yml`). Directly reusable for Aren's replicated submissions.
- **Interval-window rate limiting over sliding counts:** `RescheduleEligible` counts only events within `failTime - Interval` (`nomad/structs/structs.go:10695-10701`), not total-attempts-ever. This yields a leaky-bucket semantics familiar to SREs; `viableAttempts` (`nomad/structs/structs.go:6733-6797`) pre-validates that `Attempts` fit inside `Interval` given `Delay`/`DelayFunction`/`MaxDelay`, rejecting unsatisfiable configs at job submit — an unusually thoughtful validator.
- **Dual-guard idempotency:** Pre-Raft snapshot check (`nomad/job_endpoint.go:2047`) gives a fast-path `JobDispatchResponse.DispatchedJobID` without consuming Raft quota; FSM-level guard (`nomad/fsm.go:683`) covers the race where two leaders' requests are in-flight. Both return the *existing* child's `CreateIndex`/`ModifyIndex` rather than erroring, making retries transparent to callers.
- **Heap-driven timer dispatch:** `periodicHeap` (`nomad/periodic.go:469-608`) wraps Go's `container/heap` with an index map for `Update`/`Remove` by `NamespacedID`; `run` (`nomad/periodic.go:315-335`) multiplexes `updateCh` (spec changes) vs `launchCh` (next deadline) vs `ctx.Done()` (leadership loss). Comparable to a durable-timer wheel but without persisted timer handles.
- **SnapshotIndex as causal fence:** Workers capture `snapshotIndex` at `Dequeue` (`nomad/worker.go:121-125`) and write it into produced evals/allocs (`nomad/worker.go:930-932`); `snapshotMinIndex` (`nomad/worker.go:409`) blocks scheduling until Raft has applied through that index, preventing a scheduler from acting on stale state. A causal-consistency primitive that workflow engines typically hide inside history.

## Tradeoffs

- **No workflow code vs. no replay burden:** By avoiding a replayable workflow language, Nomad sidesteps the non-determinism pitfalls (random, wall-clock, global state) and version-compatibility problem entirely. Cost: every multi-step user workflow (e.g., canary deploy, rolling update with `MigrateStrategy` at `nomad/structs/structs.go:6811`) is hand-coded in Go and coupled to the scheduler; users cannot author, version, or test their own durable workflows.
- **Prefix-scoped idempotency vs. global dedup:** Scanning `JobsByIDPrefix(parentID)` (`nomad/state/state_store.go:1924`) is O(children) and never touches parents outside the namespace, so it stays cheap. But it stores the token on the child (`Job.DispatchIdempotencyToken`) and retains it only until GC (`nomad/core_sched.go:887-1230` periodic GC) — after GC, the same token will create a new job, violating long-horizon idempotency.
- **Jittered local restart vs. precise backoff:** `restarts.go:250-259` jitters by 25% of `Delay` using per-tracker `rand.Source` seeded at `time.Now().Unix()` (`restarts.go:53-68`). This spreads thundering herds across allocs but is non-deterministic and per-client; the server's `ReschedulePolicy` then adds exponential/fibonacci `DelayFunction` (`nomad/structs/structs.go:6603, 6716-6797`) with `MaxDelay`. Two knobs doing similar work at different layers can surprise operators (local restart hides a failure that would otherwise count as a reschedule attempt).
- **Heap timers vs. durably scheduled signals:** `PeriodicDispatch` computes `Next` on the fly (`nomad/periodic.go:343-348` `job.Periodic.Next(launchTime)`) rather than persisting a timer record per firing. This keeps snapshots small (only `PeriodicLaunch` last-time, `nomad/fsm.go:727-733`) but means `ProhibitOverlap` must re-derive liveness via `RunningChildren` scanning children/evals/allocs (`nomad/periodic.go:87-133`) on every tick — O(children * evals * allocs) at launch time.
- **Raft linearizability vs. throughput:** Every dispatch, job upsert, and eval mutation goes through Raft (`nomad/periodic.go:75` `s.raftApply`). Combined with `EvalBroker` backpressure (`nomad/eval_broker.go:19`, `nomad/worker.go:48` `raftSyncLimit: 5s`) this bounds burst throughput and ties periodic throughput to quorum latency — acceptable for infrastructure scheduling, too coarse for high-frequency workflow signals.

## Failure Modes / Edge Cases

- **Idempotency lapse after GC:** `CheckIdempotencyToken` iterates live `JobsByIDPrefix` (`nomad/state/state_store.go:1924`). Once dispatched jobs are GC'd (periodic job GC, `nomad/core_sched.go:887`), the token is forgotten and a retried dispatch creates a duplicate job. The store also prefixes by `parentID` (`nomad/job_endpoint.go:2048`) so tokens are only unique within a parent, not globally — cross-parent collisions are not detected.
- **Race between pre-Raft and FSM checks:** Without the FSM guard (`nomad/fsm.go:683`), concurrent dispatches with the same token could both pass the handler's snapshot check (`nomad/job_endpoint.go:2047`) and both write distinct children — this was GH-27353 (`.changelog/27353.txt:2`). The FSM fix closes it, but the handler path still returns the existing job's indices without a distinct "deduped" status code; callers that distinguish new vs. deduped via error handling will misclassify.
- **Periodic double-launch around failover:** If `dispatch` (`nomad/periodic.go:340-369`) updates the heap to `Next` then crashes before `DispatchJob` commits, the new leader's `restorePeriodicDispatcher` recomputes heap from current jobs/periodic launches and may launch the same logical tick again. `derivedJobID` (`nomad/periodic.go:440-441`) uses `time.Unix()` (second granularity), so two launches within the same second collide by ID and the second `raftApply` would overwrite or be rejected depending on `EnforceIndex` — behavior not documented.
- **Clock skew and interval arithmetic:** `RescheduleTracker.rescheduleInfo` uses `failTime.UTC().UnixNano() - lastAttempt` vs `interval.Nanoseconds()` (`nomad/structs/structs.go:10697`) and `NextRescheduleTime` adds `failTime.Add(nextDelay)` (`nomad/structs/alloc.go:526`). Wall-clock skew between servers that supplied `failTime` can make an allocation appear inside or outside the window inconsistently across nodes.
- **Poison work (unrecoverable errors):** `restarts.go:210-212` checks `structs.IsRecoverable(startErr)` and immediately returns `TaskNotRestarting` for unrecoverable errors, but `RescheduleEligible` (`nomad/structs/structs.go:10666`) has no poisoning concept — a job that repeatedly fails due to a bad image will consume all `Attempts` quickly and then silently stop rescheduling (transition to dead) without an operator-visible poison queue. Unblocking poison allocs would require manual `ForceReschedule` (`nomad/structs/alloc.go:1558-1562`) or job re-registration.
- **Determinism leak via healable mistake:** The `PeriodicDispatch.deriveJob` recover block (`nomad/periodic.go:414-423`) removes the periodic job from tracking on panic instead of failing loudly and preserving state — a bad `Copy()` can silently deregister a cron job, requiring operator re-registration to recover.
- **Blocking evals Nack storm:** Workers Nack if Raft hasn't caught up to `snapshotIndex` within `raftSyncLimit` (`nomad/worker.go:48`). Under follower lag or high write load, evals may Nack repeatedly, building backoff (`nomad/worker.go:29-37` `backoffBaselineFast/Slow`) and starving scheduling — `EvalReapCancelableInterval` (`nomad/config.go:271`) and `BlockedEvals` pruning exist to shed, but can mask failures.
- **DispatchedID entropy loss:** `structs.DispatchedID(parent, template, time.Now())` (`nomad/job_endpoint.go:2068`) embeds wall-clock; if two dispatches for the same parent land in the same nanosecond with the same `IdPrefixTemplate` they risk ID collision at `UpsertJobTxn` (`nomad/state/state_store.go:1920s`), surfaced as a transaction conflict rather than a clean idempotency hit.

## Future Considerations
