## Summary

runc is not a generic `os/exec` helper but an OCI container runtime whose subprocess supervision is a multi-stage fork-exec with Linux kernel containment. Creation uses `exec.Command("/proc/self/exe","init")` in `studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:575` with `cmd.Stdin/Stdout/Stderr/Dir/Env/ExtraFiles` wired from `studies/aren-go-runtime-study/sources/runc/libcontainer/process.go:26-55` and `studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:583-647`. Environment is rebuilt in `studies/aren-go-runtime-study/sources/runc/libcontainer/env.go:24` (dedup, NUL validation, HOME injection) and working directory is enforced via `unix.Chdir` with `verifyCwd()` breakout detection in `studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:271-368`. Exit classification uses `utils.ExitStatus` (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils.go:18`) mapping `127+signal` for signaled processes and `os/exec.ExitError` propagation in `studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:607` and `studies/aren-go-runtime-study/sources/runc/signals.go:106-126`.

Containment is via PID namespace (killing init SIGKILL kills all descendants per `pid_namespaces(7)`) plus cgroup tree killing. `signalAllProcesses` in `studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:682-720` prefers `cgroup.kill` (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:691`) then freeze→enumerate→`unix.Kill`→thaw. `Container.signal` (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:444-490`) branches: private PID namespace → single `initProcess.signal(SIGKILL)` with freezer thaw; shared/host PID namespace → `signalAllProcesses`. `destroy` (`studies/aren-go-runtime-study/sources/runc/libcontainer/state_linux.go:39-67`) also kills via cgroup for shared-PID containers. Joining the correct cgroup early uses `CLONE_INTO_CGROUP`/`clone3` via `prepareCgroupFD`/`startWithCgroupFD` in `studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:371-457`.

Descriptor hygiene is explicit: `CloseExecFrom(3)` before `runc init` in `studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:402`, `finalizeNamespace` closes `PassedFilesCount+3` (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:304`), and `utils.UnsafeCloseFrom` (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils_unix.go:101`) before `linux.Exec`. `processComm` pipes and `syncSocket` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:59-104`, `studies/aren-go-runtime-study/sources/runc/libcontainer/sync_unix.go:18-85`) plus log forwarding `ForwardLogs` (`studies/aren-go-runtime-study/sources/runc/libcontainer/logs/logs.go:17`) handle sync, but no generic stdout/stderr bounding or hung-pipe timeout exists. Cancellation during startup is best-effort `terminate()` (SIGKILL+Wait) in defers of `setnsProcess.start` and `initProcess.start` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:459-593`, `studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:778-821`). The design is Linux-only; no Windows job-object code exists and cross-platform orphan/hung-pipe tests are absent.

## Rating

**6/10**

runc demonstrates production-grade OS-level containment (PID namespace + cgroup.kill/freeze-kill, CLONE_INTO_CGROUP, Pdeathsig, exhaustive fd closing, zombie reaping) but as a reusable Go pattern for subprocess supervision it is narrow: Linux-only, no `context.Context` cancellation API, no output size/timeout bounding for arbitrary commands, no Windows equivalent, and no generic process-group abstraction. Timeout only exists for hook commands (`studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:595-633`) and mount-remapping (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:682-775`). Failure taxonomy is precise for container lifecycle, but not generalized.

## Answers to Dimension Questions

**Does cancelling the parent guarantee that descendants stop?**

No, not universally. Guarantee depends on PID namespace. If the container has a private PID namespace (`configs.NEWPID` private), killing init with `SIGKILL` from ancestor kills all other processes automatically per kernel semantics documented in `studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:445-448` and implemented as single `initProcess.signal(SIGKILL)` in `studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:472-489`. If PID namespace is shared/host (`!IsPrivate(NEWPID)`), parent-kill alone does NOT kill descendants; runc must enumerate cgroups. `Container.signal` explicitly branches to `signalAllProcesses(SIGKILL)` in `studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:452-468`, and `destroy` does the same in `studies/aren-go-runtime-study/sources/runc/libcontainer/state_linux.go:48-50`. `signalAllProcesses` itself has two tiers in `studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:688-696`: try `cgroup.kill` file, fallback to `Freeze→GetAllPids→Kill→Thaw`. When rootless cgroups are unavailable (`RootlessCgroups` true), the code warns and falls back to single-init kill, leaving orphans possible (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:454-458`, `studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:826-835`). ParentDeathSignal (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:652-654`) is skipped when parent is PID1 without NEWPID, further weakening guarantee. Integration test `testPidnsInitKill` in `studies/aren-go-runtime-study/sources/runc/libcontainer/integration/exec_test.go:1385-1427` verifies the shared-PID kill path.

**Can unread output deadlock process completion or exhaust memory?**

Partially. For the `runc init` control planes, deadlock is prevented: log forwarding uses a dedicated goroutine with `bufio.Scanner` in `studies/aren-go-runtime-study/sources/runc/libcontainer/logs/logs.go:19-49` and sync uses `SOCK_SEQPACKET` with `ReadPacket` sizing via `MSG_PEEK` in `studies/aren-go-runtime-study/sources/runc/libcontainer/sync_unix.go:45-65`. The parent drains `initSockParent` via JSON decode and `logPipeParent` via `ForwardLogs`. If those readers were absent, the child would block on `JSON.Marshal.Write` (`utils.WriteJSON` in `studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:507-508`). For container stdio, runc does NOT bound or drain; `Process.Stdout/Stderr` are caller-supplied `io.Writer` or pipes from `InitializeIO` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:1171-1208`). No size limit or timeout exists. Hook execution buffers unbounded `bytes.Buffer` (`studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:600`) and could exhaust memory if hook stdout/stderr is large. Hung pipes for exec fifo are mitigated by `Poll` with `pidfd_open` fallback (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:271-327`), so a dead init unblocks via EOF. No evidence of generic output-byte-limit for container processes.

**Which containment claims hold on each supported operating system?**

runc is Linux-only in practice. `go.mod:3` specifies `go 1.26` but all containment code is guarded `//go:build !windows` or Linux-specific (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils_unix.go:1`, `studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:1`). No Windows job-object, process-group, or descriptor logic exists outside vendor. Namespaces (`studies/aren-go-runtime-study/sources/runc/libcontainer/nsenter/nsexec.c:640-1232`), cgroups v1/v2 (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:131-165`), `CLONE_INTO_CGROUP` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:371-429`), seccomp (`studies/aren-go-runtime-study/sources/runc/libcontainer/seccomp/seccomp_linux.go:149`), AppArmor/SELinux, capabilities, and `CloseExecFrom/UnsafeCloseFrom` are Linux syscalls. The repo explicitly warns that rootless + shared PID without cgroup delegation is unsupported (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:832-835`). Cross-compilation to Windows would not provide containment.

**How are exit status, timeout, cancellation, setup failure, and cleanup failure distinguished?**

*Exit status*: `utils.ExitStatus` in `studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils.go:18` distinguishes signaled (128+signal) vs exited. `signals.go:reap` returns `exit{pid,status}` via `utils.ExitStatus(ws)` (`studies/aren-go-runtime-study/sources/runc/signals.go:122-125`). `Process.Wait` returns `*os.ProcessState` and often wraps non-success `Wait` as `*exec.ExitError` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:167-172`, `studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:602-608`).

*Timeout*: Only hook commands have first-class timeout. `Command.Run` in `studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:620-633` selects on `timerCh` → `Kill()` → `fmt.Errorf("hook ran past specified timeout of %.1fs")` with stdout/stderr appended. Mount-remapping thread has `context.WithTimeout(1*time.Minute)` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:692`) returning `context cancelled` errors.

*Setup failure*: Parent defers detect failure and annotate with OOM, terminate, and propagate via sync pipe. `initProcess.start` defer checks `manager.OOMKillCount()` and wraps `retErr` with `"container init was OOM-killed"` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:791-809`). `setnsProcess.start` annotates `possibly OOM-killed` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:470-473`). `startInitialization` sends `procError` JSON on sync socket (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:138-152`, `studies/aren-go-runtime-study/sources/runc/libcontainer/sync.go:42`). `parseSync` returns `initError` typed errors.

*Cancellation during startup*: No `context.Context` API; cancellation is simulated by startup error → `terminate()` (SIGKILL+Wait) in defers. Distinguished by `ignoreTerminateErrors` which swallows `ExitError/os.ErrProcessDone/Wait already called` (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:1206-1228`), so caller sees original setup error, not termination error.

*Cleanup failure*: `Container.signal` freeze/thaw warnings are logged but not returned unless `GetAllPids` fails (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:699-717`). `destroy` returns `unable to remove container's cgroup` (`studies/aren-go-runtime-study/sources/runc/libcontainer/state_linux.go:52-53`), `os.RemoveAll` error, and `runPoststopHooks` error (`studies/aren-go-runtime-study/sources/runc/libcontainer/state_linux.go:64`). Poststart hook failure kills container via `signal(SIGKILL)` then `wait()` in `postStart` defer (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:346-355`).

## Architectural Decisions

* **PID namespace as primary process-tree guarantee.** Use kernel property that killing PID 1 kills all in namespace (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:445-448`). Avoids manual tree walk when possible; fallback to cgroup walk for shared PID.
* **cgroup.kill preferred, freeze-enumerate-kill as fallback.** `signalAllProcesses` writes `cgroup.kill` atomically (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:689-695`) to avoid PID race; only on `ENOENT` does it `Freeze→GetAllPids→Kill`. Tradeoff: modern kernels get race-free kill, old kernels get freeze latency.
* **`CLONE_INTO_CGROUP` early join.** `prepareCgroupFD` opens cgroup FD and sets `SysProcAttr.UseCgroupFD` so `clone3` places child directly (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:368-444`). Prevents escape between `Start` and `AddPid`. Fallback to post-start `AddPid` if `clone3` fails.
* **Three-pipe synchronisation instead of Wait/PID alone.** `processComm` with `initSockPair` (bootstrap JSON), `syncSockPair` (SOCK_SEQPACKET JSON + SCM_RIGHTS), `logPipe` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:59-104`, `studies/aren-go-runtime-study/sources/runc/libcontainer/logs/logs.go:17`) decouples Go runtime scheduling from C `nsexec` stages, allowing pidfd_getfd seccomp forwarding and mountfd remapping.
* **`nsexec` three-stage C bootstrap.** `nsexec.c:725-1232` implements `STAGE_PARENT→STAGE_CHILD→STAGE_INIT` with `clone(CLONE_PARENT|SIGCHLD)` and `setns`/`unshare` ordering to handle user namespace mapping needing privileged parent. Rationale: preserve `CLONE_NEWUSER` SELinux/mqueue correctness and avoid `clone(CLONE_NEWPID|CLONE_PARENT)` bug on Linux 3.12.
* **Aggressive FD CLOEXEC closure.** `CloseExecFrom` via `close_range(CLOSE_RANGE_CLOEXEC)` with fallback loop (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils_unix.go:74-90`), and `UnsafeCloseFrom` skipping runtime poll fds before `Exec` (`studies/aren-go-runtime-study/sources/runc/libcontainer/standard_init_linux.go:292-305`). Mitigates `CVE-2024-21626` leaks.
* **Exeseal clone of /proc/self/exe.** `container_linux.go:541-646` clones binary via `exeseal.CloneSelfExe` using overlayfs/memfd to prevent container overwriting runc binary post-exec.
* **Logging via forwarded JSON pipe.** Child logrus output JSON over pipe; parent `ForwardLogs` collects fatals separately (`studies/aren-go-runtime-study/sources/runc/libcontainer/logs/logs.go:31-49`). Keeps init failures visible even after intermediate process death.

## Notable Patterns

* **Zipped exec.Cmd per start.** `setnsProcess.startWithCgroupFD` clones `exec.Cmd` via `cloneCmd(p.cmd)` before retry without cgroupfd (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:445-456`) because `exec.Cmd` cannot be reused after `Start`.
* **Per-controller cgroup path override.** `addIntoCgroupV1` clones `GetPaths` map and rewrites via `cgroups.WriteCgroupProc` for per-controller `SubCgroupPaths` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:258-292`); v2 only `""` key.
* **Pidfd + Poll multiplex for exec fifo.** `waitForFifoReady` probes `unix.PidfdOpen` then `Poll(FIFO, pidfd)` (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:271-303`) to avoid busy-wait and detect init death without timeout.
* **OOM annotation pattern.** Capture `OOMKillCount()` before start, compare after failure to disambiguate kernel OOM vs app failure (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:463-473`, `studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:791-809`).
* **Hook timeout with channel.** `Command.Run` buffers output, `cmd.Start` + goroutine `Wait`, select on `timerCh` (`studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:612-633`) — rare generic timeout pattern not applied to container init.
* **Seccomp fd passing via pidfd_getfd.** `pidGetFd` uses `PidfdOpen(pid)+PidfdGetfd(srcFd)` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:1106-1117`) to avoid trusting container-provided fd numbers.

## Tradeoffs

* **Kernel containment vs userspace polling.** cgroup.kill/freeze is atomic and kernel-enforced but requires cgroup delegation; fallback polling `waitForFifoReadyPolling` every 100ms (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:305-327`) trades latency for compatibility on pre-5.3 kernels without `pidfd_open`.
* **Freeze-to-kill reliability vs latency.** Freezing before `GetAllPids` prevents new forks between enumeration and kill, but freezes all processes including those that might be handling SIGTERM gracefully; runc only freezes for `SIGKILL` (`studies/aren-go-runtime-study/sources/runc/libcontainer/init_linux.go:688-699`, `studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:481-486`).
* **`close_range` fast path vs portability.** `haveCloseRangeCloexec` probes `F_DUPFD_CLOEXEC` then `CloseRange` (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils_unix.go:21-35`); fast O(1) syscall when available, fallback to `Readdirnames` loop O(n) otherwise.
* **CLONE_INTO_CGROUP atomicity vs kernel age.** Early join eliminates race but requires cgroup v2 and kernel ≥5.7; failure silently retries without (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:433-457`) making behavior kernel-dependent.
* **No output bounding vs simplicity.** Hook buffers unbounded (`studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:600`) and container stdio is caller-managed; runc avoids proxying overhead but leaves memory exhaustion to caller/contained process.
* **Rootless convenience vs kill guarantee.** `RootlessCgroups` flag silently ignores cgroup errors (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:349-353`) to allow rootless without delegation, but documented as leaky (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:832-835`).
* **Three-stage fork complexity vs SELinux correctness.** Maintains correct SELinux label order (user ns before others) at cost of extra processes, sync pipes, and zombie reaping logic (`studies/aren-go-runtime-study/sources/runc/libcontainer/nsenter/nsexec.c:800-845`).

## Failure Modes / Edge Cases

* **Orphaned descendants in shared PID without cgroup.** When `!IsPrivate(NEWPID)` and `RootlessCgroups` and no `cgroup.kill`, only init is signaled; other pids leak (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:452-459`, `studies/aren-go-runtime-study/sources/runc/libcontainer/state_linux.go:48-50`).
* **Frozen cgroup SIGKILL no-op.** For cgroup v1, `SIGKILL` to frozen cgroup does nothing until thaw; runc thaws only for `SIGKILL` in `signalInit` (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:481-489`) but not for other signals.
* **PID reuse attack.** `hasInit()` mitigates via `StartTime` comparison (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:938-952`) and `stateDir` freeze; still window if `ProcStat` fails.
* **Exec fifo already consumed or init died before write.** `readFromExecFifo` returns `"exec fifo is empty"` (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:329-339`) collapsing distinct cases (died with/without write) into one error; runc deletes fifo after read (`studies/aren-go-runtime-study/sources/runc/libcontainer/container_linux.go:263`).
* **Hung sync pipe.** `parseSync` blocks until `io.EOF` (`studies/aren-go-runtime-study/sources/runc/libcontainer/sync.go:189-203`); if child hangs after `procReady` without `procRun` ACK, parent blocks indefinitely — no timeout.
* **Descriptor leak via Go finalizer race.** Comments in `standard_init_linux.go:292-300` warn that closing fds under `*os.File` can cause reuse; mitigated by `UnsafeCloseFrom` skipping runtime poll fds (`studies/aren-go-runtime-study/sources/runc/libcontainer/utils/utils_unix.go:101-128`).
* **OOM vs setup error conflation.** OOM check is best-effort (`_ = OOMKillCount`); new OOM could be unrelated to container process but attributed to it (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:469-474`).
* **Mount source thread leak.** Context timeout closes `requestCh` via `AfterFunc` (`studies/aren-go-runtime-study/sources/runc/libcontainer/process_linux.go:692-694`); if caller never cancels, goroutine lives until container init completes.
* **Hook stdout/stderr unbounded.** `bytes.Buffer` accumulates hook output without limit (`studies/aren-go-runtime-study/sources/runc/libcontainer/configs/config.go:600`) — could OOM parent if hook emits GBs before timeout `Kill`.
* **nsexec syncfd race.** `nsexec.c:798` notes "TODO: Currently we aren't dealing with child deaths properly" — stage deaths before sync may leave parent blocked.
