## Summary

Ollama bounds its hottest paths through a scheduler-centric design: a single `Scheduler` multiplexes all inference via four bounded channels, a global `activeLoading` lock serializes model spawns, and each `llamaServerRunner` enforces per-model parallel slots with `semaphore.Weighted(numParallel)`. VRAM admission uses a predicted-then-verified pattern (`PredictServerVRAM` + log-parsed `MemorySize`) with 80% free-memory headroom, automatic `num_ctx`/`num_batch` step-down, LRU-like eviction, and a bounded OOM retry (`oomRetryAttempted` once). Streaming output is hard-capped at 8 MiB/line and `NumPredict` at `10 * NumCtx`. Transfer paths (`x/transfer`) separately bound blob parallelism (64) and body-bearing streams (default 4, fallback 1). Weaknesses are explicit: no process-wide disk quota, no Prometheus-class actionable metrics (only `slog`), no per-queue deadline or fairness policy, unbounded in-memory cache maps, and no saturation/steady-state benchmarks checked into the repo — overload behaviour is handled but not continuously measured.

## Rating

**6 / 10 — Moderate**

Rationale: Core inference resources (queued requests, loaded models, VRAM, parallel slots, stream buffers, transfer streams) are all bounded and testable. Pre-flight 80% checks, predicted→actual reconciliation, guaranteed release on failure/cancel, and bounded OOM retries demonstrate real accounting discipline. Points deducted because: (1) no global disk/history retention bound; (2) metrics are log lines not actionable counters/gauges with limits; (3) queue has no deadline/fairness or slow-consumer backpressure; (4) cache maps (`loaded`, `inferenceModelCache`, `modelListCache`, `modelShowCache`) grow without explicit capacity/TTL; (5) benchmarks exist as external `cmd/bench` benchstat tool, not as checked-in saturation/Soak load tests with hardware+memory assertions.

## Answers to Dimension Questions

**Which resources are bounded per run, per workspace, and process-wide?**

- *Per run (per-request against a loaded model):* `NumCtx` bounded to `[4, trainCtx]` (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:169-176`, `studies/aren-go-runtime-study/sources/ollama/llm/server.go:112-116`), `NumPredict` bounded to `10*NumCtx` (`studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:106-118`), `NumBatch` auto-stepped via `generationBatchFits` 80%+headroom (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:870-895`), context-shift prompt truncation limit `NumCtx - max((NumCtx-NumKeep)/2,1)` (`studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:321-331`). No per-run disk or memory quota beyond those.
- *Per model instance (per runner):* parallel slots `NumParallel = max(envconfig.NumParallel(),1)` capped per `llamaServerRunner.sem` (`studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:960`, `studies/aren-go-runtime-study/sources/ollama/envconfig/config.go:273-275`); device placement (`gpus []DeviceInfo`, `MainGPU`) bounds VRAM shard (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:972-1036`). Embedding models forced `numParallel=1` (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:501-502`), vision/multimodal arch list also forced serial (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:507-510`).
- *Process-wide:* `pendingReqCh`/`finishedReqCh`/`expiredCh`/`unloadedCh` capacity = `MaxQueue` (512) (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:91-96`, `studies/aren-go-runtime-study/sources/ollama/envconfig/config.go:278-279`); loaded models `MaxRunners` (0 = auto `3*GPUcount`) (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:226`, `studies/aren-go-runtime-study/sources/ollama/server/sched.go:280-291`); only-one `activeLoading` (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:70-73`); transfer `DefaultDownloadConcurrency=64`, `MaxTransferStreams=4` (`studies/aren-go-runtime-study/sources/ollama/x/transfer/transfer.go:104-107`, `studies/aren-go-runtime-study/sources/ollama/envconfig/config.go:285`); stream scanner 8 MiB (`studies/aren-go-runtime-study/sources/ollama/llm/server.go:160-162`). Caches (`modelCaches`, `inferenceModelCache`, `modelListCache`, `modelShowCache`) are process-wide but unbounded (`studies/aren-go-runtime-study/sources/ollama/server/model_caches.go:1-34`).
- *Per workspace:* Ollama has no workspace scoping; all models/blobs live in single `OLLAMA_MODELS` dir (`studies/aren-go-runtime-study/sources/ollama/envconfig/config.go:113-124`). Manifest- keyed layers are global, not partitioned.

**What happens before memory pressure becomes an out-of-memory crash?**

Multi-stage, explicit pressure handling:

1. *Prediction gate before spawn:* `availableMemoryForPlacement(...)*80/100` threshold; if `predictedForLoad > threshold` scheduler evicts before spawning (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:549-560`). `automaticGenerationBatch` downgrades batch `2048→1024→512` until fits (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:828-834`).
2. *mmap backoff under host pressure:* on Linux with discrete GPUs, if `modelSize+loadedMmapSize+headroom( max(8GiB,10% total) ) > FreeMemory` while VRAM fits, scheduler disables mmap (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:1200-1241`, `studies/aren-go-runtime-study/sources/ollama/server/sched.go:1255-1260`).
3. *Metal partial-offload and Windows-CUDA mmap defaults:* disable mmap heuristically to avoid thrashing (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:1158-1177`).
4. *load-time OOM correction:* if `WaitUntilRunning` returns OOM, `reduceAutoNumCtxForLoadOOM` steps context from e.g. 32768→4096 then retries once (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:649-663`, `studies/aren-go-runtime-study/sources/ollama/server/sched.go:757-783`); otherwise `evictAllAndWait` evicts all other runners and retries once (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:318-326`, `studies/aren-go-runtime-study/sources/ollama/server/sched.go:665-668`).
5. *Stall recovery:* `WaitUntilRunning` stall timeout `LoadTimeout` (5m) tracks `lastLoadActivity` from log parsing (`studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:1281-1293`, `studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:2770-2774`).
6. *Runtime OOM:* `expireRunnersForRuntimeOOM` on `Completion`/`Embedding` errors matching `outOfMemorySubstrings` expires all runners for next request (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:1632-1661`, `studies/aren-go-runtime-study/sources/ollama/llm/status.go:85-96`). `memoryParsingWriter` captures `using device X - Y MiB free` to avoid optimistic accounting (`studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:2733`, `studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:2620-2630`).
7. *No earlier GC/memory-pressure signal:* No cgroup pressure, `GOMEMLIMIT`, or explicit reclaim before 80% threshold; reliance is on prediction + eviction; slog warnings are the only headroom signal (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:551-558`).

**Are estimates reconciled with actual use and always released on failure?**

- *Reconciled:* Yes, predicted vs actual are reconciled. Initial estimate `PredictServerVRAM` (file size + KV formula, intentionally conservative `studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:2676-2698`) is replaced by parsed `buffer size` lines (`memTotal`, `memGPU`, `vramByDevice`) (`studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:2712-2850`). `updateFreeSpace` subtracts summed `VRAMByGPU` from `TotalMemory` to compute `FreeMemory` for next placement (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:1295-1335`). `waitForVRAMRecovery` blocks next load until 75% of `runner.vramSize` is reclaimed (up to 5s) to absorb driver lag (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:1441-1498`). `GetDeviceInfos` takes `min(accountedFree, systemFreeAtLoad-used)` to handle external consumers (`studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:2591-2632`).
- *Released on failure/cancellation:* Always, but with nuances. `Load` failure closes `activeLoading` and nils it (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:633-644`), and `pending` failure sends `req.errCh` and returns `false` (no extra eviction) (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:591-595`). `WaitUntilRunning` failure triggers `s.expiredCh <- runner` for cleanup (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:734-739`). Cancellation via `pending.ctx.Err()` skips scheduling (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:237-239`) and `useLoadedRunner` ties `finishedCh` to `pending.ctx.Done()` for ref-count decrement (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:487-491`). `stopProcess` kills subprocess and waits on `done` (`studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:2573-2589`). Transfer `download()` rolls back progress and conditionally keeps `.tmp` only for `>=64MiB` (`studies/aren-go-runtime-study/sources/ollama/x/transfer/download.go:192-198`). Gap: if a load OOM occurs after `activeLoading` set but before `loaded[modelKey]` insert, the retry path `evictAllAndWait` correctly excludes the not-yet-inserted key, but leaked `activeLoading` on non-OOM errors is cleared; OOM path relies on caller retry to clear (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:665-672`).

**Can one run monopolise workers, model memory, event buffers, or disk?**

- *Workers:* No. `activeLoading` serializes spawns so one model cannot starve load pipeline; per-model `sem` caps concurrent slots to `NumParallel` (default 1) so one request cannot consume >1 slot per model. However, if `NumParallel` is raised via `OLLAMA_NUM_PARALLEL` (e.g. 8), one model can hold 8 slots indefinitely (no per-request timeout beyond client context), starving other queued requests for that same model while other models remain runnable. Globally, `MaxRunners` prevents one model from evicting all others unless OOM forces `evictAll`.
- *Model memory:* Mostly no, with one exception. Normal case fits check + eviction prevents overcommit; large model with `num_ctx=128k` + `numParallel=4` => `effectiveCtx=512k` produces huge `PredictServerVRAM` and will be downgraded or rejected before spawn. But `MaxRunners=0` (unlimited) + many small models can accumulate until host `FreeMemory` pressure triggers mmap-off; without `GpuOverhead` set, predicted free uses driver-reported values that lag, allowing transient over-allocation. Single large `numParallel` also reserves KV for all slots (see `effectiveLlamaServerContext` `numCtx*numParallel` `studies/aren-go-runtime-study/sources/ollama/server/sched.go:793-795`).
- *Event buffers:* No. SSE scanner is per-connection with 8 MiB hard limit per line (`studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:1658-1661`); exceeding fails that request with `stream event exceeded 8 MB limit` without affecting others. API `streamResponse` flushes per chunk (`studies/aren-go-runtime-study/sources/ollama/server/routes.go:2097-2138`) but has no backpressure handling: it writes to `c.Writer` without `WriteTimeout`; slow consumer holds a `sem` slot for duration of stream (since `Completion` stream holds the slot until body close), thus one slow client can pin a worker slot for the full generation, but not buffers.
- *Disk:* Yes, can monopolise. Blobs under `OLLAMA_MODELS/blobs` and manifests are never quota-enforced; `PullModel`/`fixblobs` can fill disk without reservation accounting. `x/transfer` download keeps `.tmp` for >64MiB partials, and `download.summary` logs only rate not quota. No `manifest.Removelayers()` budget. A single `ollama push` with many large blobs could fill disk and block other pulls.
- *Caches/History:* `modelShowCache`, `modelListCache`, `inferenceModelCache` are unbounded maps keyed by digest/model name (`studies/aren-go-runtime-study/sources/ollama/server/model_inference_cache.go:20-21`); each unique model tag adds one entry retained until process restart (no LRU). Combined with unbounded `inferenceRequestLogger` file writes (if `OLLAMA_DEBUG_LOG_REQUESTS`) and `StatusWriter` 8 KiB cap (`studies/aren-go-runtime-study/sources/ollama/llm/status.go:18-18`), the only bounded history is error capture; request history itself is unbounded.

## Notable Patterns

- **Reserve→Spawn→Parse→Correct:** `PredictServerVRAM` reserves via `loadFn` decision → `startLlamaServer` spawns → `memoryParsingWriter.Write` parses → `updateFreeSpace` corrects `FreeMemory` for next admission. Unlike two-phase commit it never rolls back an over-admission except via next eviction.
- **Stale-while-revalidate caches:** `modelShowCache.GetCloudSWR` returns stale on read and triggers throttled (`5s`) background `refreshCloud` with bounded 4-worker hydrate (`studies/aren-go-runtime-study/sources/ollama/server/model_show_cache.go:176-185`, `studies/aren-go-runtime-study/sources/ollama/server/model_show_cache.go:229-274`). Same pattern for `modelListCache` hydration (`studies/aren-go-runtime-study/sources/ollama/server/model_list_cache.go:65-83`).
- **Singleflight coalescing:** `inferenceModelCache.loads.Do(loadKey)` avoids thundering herd when many requests miss the same digest (`studies/aren-go-runtime-study/sources/ollama/server/model_inference_cache.go:66-86`).

## Tradeoffs

- **Conservative overestimate vs throughput:** `PredictServerVRAM` overestimates (full file + KV) and 80% threshold plus batch downgrade sacrifice KV-cache performance to gain stability; small models may be unnecessarily throttled while large ones still risk driver lag.
- **Immediate fail vs queue wait:** `ErrMaxQueue` on full channel drops rather than queue-with-timeout; reduces memory but raises client retry burden; no `429 Retry-After` header.
- **Pessimistic `min` accounting vs accuracy:** Using `min(driverFree, accountedFree)` penalizes Metal/iGPU stacks where driver `free` is stale, pushing more CPU-offload than needed.
- **Single load lock vs parallel loads:** `activeLoading` prevents VRAM fragmentation from parallel spawns but serializes cold starts; not an issue for steady-state but adds tail latency during burst of distinct models.
- **Semaphore-per-runner vs global pool:** Fair per-model isolation but no global concurrency cap; `MaxRunners*NumParallel` total slots can be high (e.g. 3 GPUs *3 models *4 slots =36 concurrent generations) with no global throttle; mitigated only by VRAM gate.
- **Unbounded maps vs bounded LRU:** Simplicity and zero-eviction for hot models, at cost of unbounded heap proportional to unique model tags ever seen.
- **8 MiB stream cap vs fidelity:** Protects server from malicious large token (e.g. base64 image) but can error legitimate 8 MiB+ tool payloads; no chunked fallback.
- **No quota ledger:** Predict→actual reconciliation is per-GPU aggregate, not per-runner ledger with reserved/used distinction; preemption after OOM is reactive not proactive.

## Failure Modes / Edge Cases

- **Driver lag VRAM miscount:** If `systemFreeAtLoad` missing (platform without `using device - MiB free` line) accounting falls back to `TotalMemory - allocations` (`studies/aren-go-runtime-study/sources/ollama/llm/llama_server.go:2619`), overestimating free until next `updateFreeSpace`; speculative fit may succeed then crash. Covered by OOM retry but incurs user-visible error.
- **Ref-count leak on panic:** If `pending.ctx.Done()` never fires (e.g. handler never cancelled and `finishedReqCh` full), `refCount` stays >0 and `expiredCh` retry loop spins every 10ms forever (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:418-424`), retaining VRAM indefinitely; no watchdog.
- **Channel full deadlock on fast-fail:** `expiredCh` and `unloadedCh` are `MaxQueue` bounded; if all 512 slots fill with expired events while `processCompleted` is blocked on `waitForVRAMRecovery` 5s, new expirations block on `<-s.expiredCh` in `evictAllAndWait` (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:1614`). Risk low but `finishedReqCh` has same bound and `useLoadedRunner` blocks on send without select (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:486`).
- **OOM substring false positive:** `outOfMemorySubstrings` includes generic `allocation failed` (`studies/aren-go-runtime-study/sources/ollama/llm/status.go:85-96`); non-VRAM allocation failure (e.g. host RAM exhausted by mmap headroom) triggers full eviction then still fails, consuming one retry.
- **`waitForVRAMRecovery` timeout masking:** If driver never recovers to 75% within 5s, scheduler proceeds anyway (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:1491-1494`); next fit may immediately re-trigger eviction loop; observed as flapping in `findRunnerToUnload` picking shortest duration repeatedly.
- **Infinite keep-alive (`KeepAlive=-1` => MaxInt64) prevents eviction:** Models never expire; `MaxRunners` still forces eviction on new model, but `ByDurationAndName` picks longest-lived among infinite-duration set arbitrarily (lexicographic) causing surprising victim selection (`studies/aren-go-runtime-study/sources/ollama/server/sched.go:1561-1578`).
- **Disk exhaustion unhandled:** No check before `os.Create(tmp)` in transfer or `PullModel`; `ENOSPC` surfaces as generic download/load error, then `IsOutOfMemory` false so no eviction, leaving partial blobs retained; no cleanup quota.
- **Slow-consumer slot pinning:** One `Completion` holding `sem` during slow SSE write blocks that runner's slot for minutes (bounded only by client `ctx`); `NumParallel=1` models become fully unavailable to others.
- **Cache poison on GGUF scan failure:** `readModelListGGUF` failure leaves `modelListCache` entry stale (`studies/aren-go-runtime-study/sources/ollama/server/model_list_cache.go:202-205`), returning previous digest entry until pull; no metric to surface.

## Future Considerations

- **Explicit reservation ledger:** Replace 80% heuristic with per-GPU booked/reserved/committed counters (reserve on admission, commit on `MemorySize`, release on `unload`+VRAM recovery) to make overcommit impossible; expose as gauge for dashboards.
- **Queue deadlines & fairness:** Add per-request `queueTimeout` (e.g. 30s) with context deadline in `processPending.select`; emit `Retry-After`; implement fair queue (e.g. weighted fair by `modelKey` or caller IP) to prevent one client/model starving queue.
- **Actionable metrics export:** Export `ollama_scheduler_pending_queue`, `loaded_models`, `vram_free_bytes`, `vram_used_bytes{device}`, `runner_slots_in_use`, `oom_events_total`, `evictions_total` via `expvar` or Prometheus, with alerts tied to `freeMemory < headroom`.
- **Disk quota & retention:** Introduce `OLLAMA_MAX_DISK_BYTES`, LRU pruning of `blobs/` by `atime`, and reservation check before `downloadOnce`; integrate `fixblobs` accounting into scheduler.
- **Capacity-bound caches:** Give `inferenceModelCache`/`modelShowCache` an LRU with `maxEntries=128` or TTL (e.g. 10m) and memory-bound eviction; expose hit/miss metrics.
- **Slow-consumer backpressure:** Add `http.Server{ReadTimeout, WriteTimeout}` and per-stream write deadline; wrap `streamResponse` with `http.Flusher` timeout and release `sem` on `Write` failure without waiting for `ctx`.
- **Saturation & soak tests:** Add `integration/saturation_test.go` with matrix (1/4/16 clients, burst vs steady, 24h soak) asserting `p95 queue time`, `VRAM leak <5%`, `OOM retry count`, and retained Go heap; run nightly on pinned hardware spec (record `GPU model`, `driver`, `RAM`).
- **Global concurrency cap:** Introduce `OLLAMA_MAX_CONCURRENT_GENERATIONS` process-wide semaphore layered over per-runner semaphores to bound total GPU kernel contention.
- **Formal OOM taxonomy:** Replace substring scan with typed `ExitStatus` + `lastError` codes from llama-server JSON health, distinguishing host OOM vs device OOM vs KV overflow for targeted remediation (e.g. host OOM disables mmap, device OOM evicts, KV overflow reduces ctx).
