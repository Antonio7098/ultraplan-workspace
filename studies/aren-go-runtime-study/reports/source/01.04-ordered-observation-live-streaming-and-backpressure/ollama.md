## Summary

Ollama does not implement an ordered observation, replayable event log, or observer-isolation layer as envisioned by Aren Phase 1/4. Its "streaming" is a per-request, unidirectional NDJSON token feed from the llama-server subprocess to a single HTTP client. Ordering is implicit TCP byte order of newline-delimited JSON objects; there is no sequence number, event envelope, fan-out bus, bounded queue, slow-consumer policy, or reconnect cursor. The producer goroutine writes directly into an unbuffered `chan any` which is drained synchronously by `gin.Context.Stream`; a slow HTTP client therefore blocks the token callback, which in turn stalls the llama-server SSE reader. Backpressure is thus raw TCP flow control, not an application policy. Terminal truth is a final frame with `done:true`/`done_reason`, but exactly-once delivery is best-effort: client disconnect cancels the context and may suppress the terminal frame. Progress reporting for pull/push/create reuses the same mechanism with a distinct `ProgressResponse` type but identical streaming primitives. There is no retention, replay, dropped-event accounting, or coalescing. Non-streaming mode (`stream:false`) is a server-side accumulation that still buffers every intermediate delta in memory before returning one merged JSON object.

## Rating

**3/10**

Ollama satisfies the narrow requirement of live token streaming with ordered delivery over a single connection and with cancellation and context-length truncation, but it fails the dimension's core concerns: no isolation of slow observers (producer blocks on consumer), no bounded/dropped/coalesced policy beyond an 8 MB line limit, no sequence or cursor for reconnect, no durable lifecycle facts vs lossy deltas distinction, no fan-out to multiple observers, and no replay after disconnect. The 3 reflects competent single-stream NDJSON plumbing, not an observation subsystem.

## Answers to Dimension Questions

**Can one slow observer delay execution or other observers?**
Yes — one slow observer delays its own execution, because the design is single-observer per request but the producer is coupled. `GenerateHandler`/`ChatHandler` create an unbuffered `chan any` (`server/routes.go:649`, `server/routes.go:2745`). The llama-server reader goroutine calls `fn(resp)` synchronously inside `scanner.Scan()` loop (`llm/llama_server.go:1708`, `llm/llama_server.go:2035`): `fn` does `ch <- res` (`server/routes.go:733`, `server/routes.go:2890`), which blocks until `streamResponse`'s `c.Stream` callback reads (`server/routes.go:2100-2101`) and then `w.Write` blocks on TCP flow control (`server/routes.go:2137`). There is no background buffering, dropping, or separate goroutine per observer to decouple. Other concurrent requests have separate runner slots (`llm/llama_server.go:1538-1542` per-runner `sem.Acquire(1)` + `server/sched.go:93` pending queue), so they are not delayed by a slow peer on a different request, but within that request the generation paces to the slowest consumer. No evidence of fan-out isolation was found.

**What is bounded, dropped, coalesced, retained, or replayed under pressure?**
- **Bounded:** Only the per-line SSE buffer is bounded at 8 MB both directions (`llm/server.go:162`, `api/client.go:168`). Exceeding it errors (`llm/llama_server.go:1772-1778`, `llm/llama_server_test.go:357-428`). Scheduler admission queue is bounded by `maxQueue` (`server/sched.go:93`).
- **Dropped:** No drop policy. Every token callback result is sent through the channel exactly once; nothing is discarded on pressure.
- **Coalesced:** Only in non-streaming mode (`stream:false`), where the server concatenates `Thinking`+`Content` and accumulates `Logprobs` into one `c.JSON` response (`server/routes.go:754-786`, `server/routes.go:2388-2431`). Streaming mode does not coalesce — each `Content` chunk is a separate NDJSON line.
- **Retained:** No retention beyond the in-flight TCP write. No durable log, ring buffer, or snapshot.
- **Replayed:** Nothing is replayed. There is no cursor, sequence number, or `GET /events?since=` endpoint. Disconnect requires a new POST with a new prompt/context; history is reconstructed by the client resending `Messages`/`Context` (`api/types.go:81`, `server/routes.go:2656-2660`).

**How is exactly one terminal fact delivered after partial streaming?**
Terminal is not an envelope but a convention: a final frame with `done:true` (+ `done_reason` `"stop"`/`"length"`/`"unload"`/`"load"` and `Metrics`). In streaming mode that final frame is `fn(finalResp)` after closing the HTTP body (`llm/llama_server.go:1750`, `llm/llama_server.go:2059`) and then written as the last NDJSON line via `streamResponse` (`server/routes.go:2129-2140`). The handler sets `TotalDuration`/`LoadDuration` on that frame (`server/routes.go:709-710`, `server/routes.go:2802-2804`). In non-streaming mode the handler drains `ch` until close, coalesces into `r`, then `c.JSON(http.StatusOK, r)` (`server/routes.go:788`). Errors are sent as `gin.H{"error":...}` either as an HTTP error status if no bytes written yet, or as a `{"error":...}` JSON line if streaming already started (`server/routes.go:2109-2126`). Exactly-once is best-effort: a mid-stream client `ctx` cancellation (`server/routes.go:655-656`, `llm/llama_server.go:1669`, `llm/llama_server.go:1959`) aborts the scan loop and no terminal frame is sent; tests assert token-repeat aborts return `ctx.Err()` (`llm/llama_server.go:1698-1701`). No idempotency key or retry delivers the missed terminal.

**Does reconnect recover semantics or merely resume best-effort display data?**
Neither — there is no reconnect. `grep` for `cursor`, `sequence`, `reconnect`, `resume`, `since` across `api/`, `server/`, `llm/` finds none related to streaming (only `api/types.go:1042` context token integers which are prompt memory, not stream cursor). The client `stream` method (`api/client.go:170-267`) opens a fresh `POST`, scans NDJSON to EOF, and returns; it has no `Range`/`Last-Event-ID` or cursor header. Cloud/inference proxy (`server/cloud_proxy.go:480-503`) blindly copies bytes with flush and does not persist frames for replay. Reconnecting therefore restarts inference from scratch; it does not recover the prior run's token stream or its terminal `Metrics`/`Context` except that the client can resend the full conversation. No durable facts are distinguished from lossy display deltas — everything is volatile per-connection.

## Architectural Decisions

- **Per-request NDJSON over HTTP, not an observable event bus.** Each handler owns one `make(chan any)` and one `gin.Context.Stream` loop (`server/routes.go:649-793`, `server/routes.go:2745-2941`). There is no central `EventBus`/`SubscriptionManager`. This simplifies lifecycle (context cancel = stream cancel) but precludes multiple observers per execution, historical replay, or backpressure isolation. Verdict: intentional simplicity for a local model server; mismatched to a multi-observer control plane.
- **Unbuffered channel = implicit backpressure via blocking.** Choosing `make(chan any)` (cap 0) instead of buffered/dropping semantics means the runner's callback blocks (`server/routes.go:733`) until the HTTP writer drains. This is the simplest correctness choice (no loss) but couples generation throughput to network throughput. Verdict: correct for 1:1 streaming, expensive if adapted to shared execution.
- **Single max-line bound, no queue depth bound.** Fixing `llamaServerStreamMaxBufferSize = 8 MB` (`llm/server.go:162`) bounds memory per event but leaves total backlog unbounded (TCP). Protects against a `format.MegaByte`-scale JSON blow-up, not against a slow consumer accumulating gigabytes via TCP buffers. Verdict: partial bound.
- **Terminal as final `done` frame, not a separate control stream.** Reuses the same NDJSON framing for data and termination, with `DoneReason.String()` mapping (`llm/server.go:257-266`). On error before first byte, the handler elevates to an HTTP error status; after first byte, it falls back to `{"error":...}` line (`server/routes.go:2116-2123`). Verdict: pragmatic but fragile — a client cannot atomically distinguish "stream ended cleanly without done" from "connection dropped mid-stream" without an explicit end-of-stream sentinel or length.
- **Gin streaming primitive instead of SSE or WebSocket.** Uses `c.Header("Content-Type","application/x-ndjson")` + `c.Stream` (`server/routes.go:2098`, `api/client.go:204` `application/x-ndjson`), while the internal llama-server subprocess uses real `text/event-stream` SSE (`llm/llama_server.go:190`, `llm/llama_server_test.go:155-902`). Ollama normalizes SSE `data:` framing into NDJSON lines at the boundary. Verdict: coherent layering; NDJSON is simpler for `bufio.Scanner` client.
- **Cloud path does per-write Flush.** `copyProxyResponseBody` flushes after every `Write` (`server/cloud_proxy.go:493`), trading throughput for latency. Verdict: favors live token interactivity over batched throughput; documented with TODO to make conditional.

## Notable Patterns

- **Callback fan-in via `chan any`:** `r.Completion(ctx, req, func(cr){ ch <- api.GenerateResponse{...}})` (`server/routes.go:670-733`) is the sole bridging pattern between runner and HTTP, repeated in `r.Chat` (`server/routes.go:2786-2890`, `server/routes.go:2999-3024`) and `PullModel`/`PushModel` progress (`server/routes.go:1136-1137`, `server/routes.go:1188-1189`, `server/create.go:118-119`).
- **Parser-interposed emission gating:** `builtinParser.Add(content,done)` may suppress empty frames (`if res.Response!="" || ... { ch <- res }` — `server/routes.go:726-728`, `server/routes.go:2832-2837`, `server/routes.go:2890`), while still forwarding logprobs-only frames. This is the only filtering/coalescing in streaming path.
- **Tool-call accumulation across SSE chunks:** `toolCalls map[int]*llamaServerToolCallAccumulator` (`llm/llama_server.go:1953`) plus `accumulatedToolCalls` (`llm/llama_server.go:2098-2133`) reconstructs tool arguments fragmented across SSE deltas before emitting final `Done` frame — ordering hazard handled via per-index accumulator.
- **Structured-output two-pass via context cancellation:** Chat path cancels its own `Completion` mid-stream when `ReadyToApply` (`server/routes.go:2818-2829`, `server/routes.go:2897-2908`) then re-invokes `r.Completion` with a stitched prompt and a synthetic `<|end|><|start|>assistant<|channel|>final<|message|>` suffix (`server/routes.go:2931`), reusing the same `ch`.
- **Token-repeat abort as backpressure-adjacent guard:** `lastToken/tokenRepeat >30 => return ctx.Err()` (`llm/llama_server.go:1691-1701`) is a safety to terminate stuck generation, not backpressure.

## Tradeoffs

- **Simplicity vs isolation:** Zero observer-management state vs inability to observe an execution from two clients or keep a late joiner in sync. For a single-user local daemon this is acceptable; for Aren's multi-observer requirement it is insufficient.
- **Blocking honesty vs latency isolation:** Unbuffered channel guarantees no silent token loss but makes throughput equal to `min(runner_token_rate, client_tcp_drain_rate)`. A buffered+drop strategy would preserve runner progress at cost of fidelity; Ollama chooses fidelity.
- **8 MB line cap vs unbounded stream:** Protects memory per-event without throttling event rate or total stream size. A malicious or buggy model that emits millions of tiny tokens can still exert unbounded downstream queue via TCP.
- **NDJSON vs SSE for clients:** NDJSON gives trivial `bufio.Scanner` + `json.Unmarshal` per line (`api/client.go:217-227`) and avoids `Last-Event-ID` state; loses built-in browser `EventSource` reconnect semantics that real SSE would provide (Ollama deliberately does not want auto-reconnect).
- **Flush-every-write vs Nagle batching:** Cloud proxy's `flusher.Flush()` per 32 KB read (`server/cloud_proxy.go:493`) reduces token display latency by ~tens of ms at cost of extra syscalls/packets; non-cloud path relies on gin's chunked flush per NDJSON line.

## Failure Modes / Edge Cases

- **Slow consumer stalls generation (head-of-line blocking).** Unbuffered `ch` + synchronous `fn` means `scanner.Scan` loop cannot advance to next llama-server SSE event until prior `w.Write` returns. Under slow network, `EvalCount/EvalDuration` metrics will underreport runner capacity and `llamaServerStream*` goroutine holds semaphore (`llm/llama_server.go:1546-1553` sem) longer, reducing concurrency to `numParallel`.
- **Oversized token/line kills stream.** A single JSON line >8 MB (e.g., huge `tool_calls.arguments` blob) triggers `token too long` scanner error, surfaced as `llama-server ... stream event exceeded 8 MB limit` (`llm/llama_server.go:1772-1778`, `api/client.go:262-263`). The terminal `Done` is never sent; client sees an error, runner is closed via `s.Close()` on `unexpected EOF` (`llm/llama_server.go:1758-1760`), runner slot is lost until scheduler reload.
- **Mid-stream error loses framing.** If `json.Marshal` fails (`server/routes.go:2131`) or `w.Write` fails after streaming started, handler just `return false` (end stream) without an explicit `{"error"}` sentinel in some paths; client may receive truncated stream and `scanner.Err()==nil` with no `done:true`, indistinguishable from disconnect.
- **Cancellation race drops terminal `Metrics`/`Context`.** `ctx` cancellation from client disconnect races `finalResp` preparation; the deferred `fn(finalResp)` (`llm/llama_server.go:1750`, `llm/llama_server.go:2059`) may never execute if `res.Body.Close()` error path is taken first. Non-streaming accumulator suffers same race — `break` on `hasFinalResp` without draining further `gin.H` error.
- **Context-length overflow handled inconsistently.** `/completion` truncation (`llm/llama_server.go:278-331`) applies to Go-rendered prompts but native chat applies separate truncation via `truncateNativeChatMessages` (`server/routes.go:3040-3097`) then `ApplyChatTemplate`; callers that send too-large `Messages` without `Truncate` get `StatusError 400` only on some paths.
- **JSON split across TCP frames is safe (Scanner), but SSE colon-comments ignored.** Per-line `Scanner` assumes `...}\n` framing; `:` keepalive lines are skipped (`llm/llama_server.go:1676-1677`, `llm/llama_server.go:1965`). If llama-server changes to send `retry:` or multi-line SSE fields, parser would silently mis-frame.
- **No idempotency: duplicate terminal on retry.** If client retries after timeout, a new ` POST /api/generate` creates a new execution with fresh `CreatedAt`/`Context` tokens; no deduplication key prevents double-generation billing/side-effects for tool-calling workflows.
- **Resource leak on leaked `ch`.** Handlers `defer close(ch)` in goroutine (`server/routes.go:653`, `server/routes.go:2747`) but do not `defer cancel()` on the parent request context until goroutine exit via `context.WithCancel`; a client that never reads and never closes TCP leaves goroutine blocked on `ch <-` until `llama-server` idle timeout or server `LoadTimeout`.

## Future Considerations

- Introduce an event envelope `{seq, ts, kind, payload, done, dropped_count}` and a per-execution sequencer so late joiners can `GET /api/generate/{id}/events?since=seq` and detect gaps — currently no `seq` exists (`api/types.go:891-930`).
- Separate lifecycle facts (created/dispatching/terminal/metrics) from lossy token deltas; persist facts in a bounded ring or SQLite while allowing deltas to be dropped/coalesced with a `dropped` counter — today both share the same `chan any`.
- Replace unbuffered `chan any` with a bounded `chan Frame` (e.g., cap 256-1024) plus policy: `Block` for correctness, `DropOldest+count` for display, and `CloseWithDropped` metric; expose `dropped` in terminal frame.
- Add reconnect cursor: negotiate `Last-Event-ID` or `?cursor=` on stream open and support server-side replay from retained buffer; for Ollama this would require persisting the recent N frames per active execution (e.g., `progress/progress.go`-style) instead of volatile `chan`.
- Move backpressure off the runner critical path: have `r.Completion` write to an intermediate buffer goroutine that never blocks on consumer, and make HTTP writer the slow side that drains with drop/coalesce; isolate semaphore release from drain rate.
- Either enforce Exactly-Once terminal via an idempotency/execution-id table, or document at-least-once and provide a `GET /exec/{id}` that returns terminal truth irrespective of streaming — currently the only way to get `Metrics` after disconnect is to re-run.

## Questions / Gaps

- Is the semaphore-per-slot (`llm/llama_server.go:1546` `sem.Acquire(1)`) sized `numParallel` actually isolating slow-stream consumers from new requests, or does blocking the single `Completion` goroutine hold the slot and starve `numParallel-1` other slots? Code shows `sem` is per-runner, so a blocked stream holds that runner's slot but not the whole scheduler — verify with `routes_generate_test.go:148-226` scheduling.
- Does `close(ch)` before error `ch <- gin.H` ever race with `streamResponse`'s `val,ok:=<-ch` detecting closed channel as `false` and ending stream silently without error? The handler orders `defer close(ch)` after goroutine work, and errors are sent before close, so no race — but confirm no early return leaves `ch` unclosed (e.g., `parseAndValidateModelRef` early returns never create `ch`).
- Client `maxBufferSize` and server `llamaServerStreamMaxBufferSize` are independently set to 8 MB (`api/client.go:168`, `llm/server.go:162`) but via different constants (`format.MegaByte` vs literal). Are they kept in sync under compile-time divergent vs runtime `envconfig`? No evidence of drift handling.
- No evidence found for SSE reconnection semantics (`retry:` field, `Last-Event-ID`) anywhere; search of `*.go` for `Last-Event` returned zero hits. Confirm intended omission vs missing phase-4 roadmap.
- Memory bound for non-streaming aggregation is unbounded: `strings.Builder` + `[]api.Logprob` accumulation (`server/routes.go:754-786`) grows with output length until `c.JSON` serialize, with no cap. What is the failure mode for a 1M-token generation in `stream:false` mode?
