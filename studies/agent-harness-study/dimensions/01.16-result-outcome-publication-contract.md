# Dimension 01.16: Result and Outcome Publication Contract

## Purpose

Study how runtimes turn a work return, failure, cancellation, or runtime fault into one stable terminal outcome for concurrent and late consumers.

## Steps

1. Identify work-return, terminal-outcome, and wait or join types.
2. Separate successful values, failures, cancellation facts, and runtime faults.
3. Trace result and error combinations, including partial or ambiguous returns.
4. Determine when the outcome becomes immutable and safe to publish.
5. Inspect concurrent, repeated, and post-completion outcome access.
6. Check value ownership, aliasing, copying, and mutation after publication.
7. Trace error cause, panic, stack, and diagnostic preservation.
8. Inspect tests for exclusivity, stable access, and publication ordering.

## Evidence to Capture

- Work-function and invocation return types
- Terminal outcome, result, failure, and cancellation types
- Wait, join, future, promise, and run-handle APIs
- Result-and-error resolution rules
- Outcome construction and publication code
- Copying, freezing, ownership, and aliasing controls
- Concurrent and late waiter tests
- Cause, panic, stack, and diagnostic retention tests

## Questions

1. Is a work return distinct from the runtime's terminal outcome?
2. Which result, failure, cancellation, and runtime-fault combinations are valid?
3. What happens when work returns both a value and an error?
4. Can a terminal outcome expose a partial or mutable value?
5. Do concurrent, repeated, and late waiters observe the same committed facts?
6. Can waiting be cancelled without cancelling the run itself?
7. Who owns values and diagnostics after publication?
8. Does waiter release occur only after the complete outcome is visible?
