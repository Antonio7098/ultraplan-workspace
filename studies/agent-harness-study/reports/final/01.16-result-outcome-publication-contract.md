## Executive Summary

Across eight agent runtimes studied for Dimension 01.16, every framework exposes a *terminal outcome* separate from the work return — either as a typed result object, a status enum on a persistent row, or a dedicated history event — but they diverge sharply on whether that outcome is published through a shared handle that multiple waiters can join.

Four implementation archetypes emerge:

1. **Typed value-object with single-consumer handle** (agent-framework, openai-agents-sdk, pydantic-ai): work returns are wrapped into a stable terminal object (`WorkflowRunResult`, `RunResult`, `AgentRunResult`), then handed back via either a finalizer on a stream or a direct return. Cancellation of the waiter is coupled to the run.
2. **Event-sourced replay over a checkpointer** (langgraph, openhands, letta, temporal): the terminal outcome is a history event plus a status row; late observers read the same committed facts via durable query. Only temporal's `FutureImpl` provides a true multi-waiter broadcast primitive.
3. **Synchronous return + state field** (crewai): the terminal outcome is a `CrewOutput` returned synchronously, with `Task.output` mirroring the result. No Future/Promise; concurrent run on the same instance is racy.
4. **Durable DB row with explicit status lifecycle** (letta): the `Run` table is the publication point, and only via otid-based request token dedup and Redis SSE stream replay do late consumers observe committed facts.

Three findings stand out. First, exclusive `value XOR error` publication is universal — every source rejects simultaneous value+error as a terminal fact, sometimes encoding partial success at tool granularity (crewai, pydantic-ai) or via deferred/interrupt types (langgraph, openai-agents-sdk, pydantic-ai). Second, mutable aliasing of the returned value is the dominant pattern; only temporal (protobufs), agent-framework's checkpoint persistence, openhands' `Event` model, and pydantic-ai's streamed `deepcopy` provide any defensive copy. Third, waiter-vs-run cancellation is uniformly absent except in pydantic-ai (where `AgentStream.cancel()` stops the current response only) and temporal (where `FutureImpl.Get(ctx)` selects `ctx.Done()` independently of the underlying commit).

## Core Thesis

**The publication contract for agent runtimes is shaped less by "what work returned" than by "who gets to read it, when, and whether mutation is allowed afterward."** All eight sources separate work return from terminal outcome and enforce exclusive `value XOR error` publication. The critical differentiators are (a) whether the outcome is published through a broadcast primitive that supports concurrent/late waiters, (b) whether the published value is immutable or share-by-reference, and (c) whether cancelling a waiter cancels the run.

Temporal alone scores 8/10 because it provides a `FutureImpl` with CAS-fenced single-publication, channel-broadcast to all waiters, and durable replay via history events — covering both in-memory fan-out and late durable observation. The other seven sources cluster at 4–6/10 because they ship a typed terminal object but couple waiter cancellation to run cancellation, expose mutable aliases, and rely on either single-consumer streams or polling over a checkpoint/DB store.

## Approach Models

The eight sources fall into four distinct approach models for the result/outcome publication contract.

**A. Typed value-object + single-consumer stream handle.** Agent-framework (`WorkflowRunResult` + `ResponseStream[UpdateT, FinalT]` with `get_final_response()` cached after drain), openai-agents-sdk (`RunResult` / `RunResultStreaming` + `asyncio.Queue` with `QueueCompleteSentinel`), and pydantic-ai (`AgentRunResult` / `StreamedRunResult` materialized via `pydantic_graph`'s `End[FinalResult]`) all return a structured terminal object after work completes. They differ in publication gating: agent-framework runs cleanup hooks before finalizer (`python/packages/core/agent_framework/_types.py:3104-3141`), openai-agents-sdk joins the run_loop_task and awaits `event_queue.join()` (`src/agents/result.py:883-1026`), and pydantic-ai gates on `_marked_completed` (`pydantic_ai_slim/pydantic_ai/result.py:766-781`).

**B. Event-sourced BSP + checkpointer replay.** LangGraph (`PregelLoop.output` materialized after `read_channels` + `GraphOutput` value/interrupts split) and openhands (`ConversationExecutionStatus` enum on `ConversationState` plus append-only `EventLog` files) treat the run as a sequence of supersteps/events. Both rely on durable storage (Postgres/sqlite saver; FileStore per-event JSON) for late observation. OpenHands' lock-and-autosave pattern (`_sdk_inspect/sdk/conversation/state.py:380-420`) is the closest cousin to temporal's transactional close.

**C. Synchronous return + instance-field state.** CrewAI returns `CrewOutput` synchronously from `Crew.kickoff()` and mirrors it onto `Task.output` (`lib/crewai/src/crewai/crew.py:1919-1977`), with no Future handle. Letta returns the blocking `send_message` response, but persists a `Run` row as the durable terminal outcome and serves late observers via REST polling or Redis SSE replay (`letta/services/run_manager.py:94-130`, `letta/server/rest_api/routers/v1/runs.py:143-411`).

**D. Durable transactional close + broadcast primitive.** Temporal is the only source that pairs an append-only history event with a CAS-fenced `FutureImpl[T]` (`common/future/future_impl.go:11-19,66-84`) whose `close(readyCh)` broadcasts to 1024 concurrent waiters (`common/future/future_test.go:95-125`), plus durable replay via `GetWorkflowExecutionHistory` (`service/history/api/getworkflowexecutionhistory/api.go:220-279`) and `GetOrPollWorkflowMutableState` long-poll (`service/history/api/get_workflow_util.go:128-258`).

These models are not mutually exclusive. Agent-framework's streaming variants pair value-object publication with event-source channels; letta pairs synchronous return with durable DB; openai-agents-sdk's `RunState.to_state()` deep-copies checkpointed state (`src/agents/result.py:108-173`) but the live `RunResult` shares aliased lists. The model choice reflects whether the runtime is library-shaped (temporal, langgraph) or application-shaped (letta, openhands, crewai).

## Pattern Catalog

### Pattern: Exclusive per-task `value XOR error` publication

**Problem.** Allowing simultaneous value and error to be published by a single task conflates a partial success with a terminal fact and creates downstream consumer ambiguity.

**Sources.** All eight. LangGraph's `commit` if/elif chain at `libs/langgraph/langgraph/pregel/_runner.py:579-613` writes either `(RETURN, ...)` or `(ERROR, exc)` never both, and `map_output_updates` filters out `ERROR`/`INTERRUPT` tasks. Temporal's `ValidateCommandSequence` (`service/history/api/command_attr_validator.go:637-678`) enforces that exactly one close command is the last. OpenAI Agents SDK has no `Result[Value, Error]` dual; errors always raise. Pydantic-ai's `_apply_retry_wins` (`pydantic_ai_slim/pydantic_ai/_tool_execution.py:880-909`) wipes a winning `final_result` when a function tool produces a `RetryPromptPart`. CrewAI's `TaskOutput` (success) versus raised `TaskFailedEvent` (failure) at `lib/crewai/src/crewai/task.py:957-963`. Agent-framework's `WorkflowRunResult` (success) versus `raise` (failure) at `python/packages/core/agent_framework/_workflows/_workflow.py:606-628`.

**Why it works.** Forces callers to choose one path for terminal handling (`try/except` or success branch), keeps diagnostics typed and complete.

**When to copy.** Anywhere a unit-of-work may fail after producing a value (LLM calls, tool calls, network I/O). The pattern is universal because Python exception semantics make it natural.

**When overkill.** When partial success is meaningful at the business level — crewai's `ToolFailureRecord` demonstrates the alternative: keep success visible alongside accumulated failure records, but model that explicitly rather than as a value+error return.

**Evidence.** All eight reports document this; langgraph and temporal additionally enforce it at the command-sequence/validator level.

### Pattern: CAS-fenced single publication with broadcast

**Problem.** Multiple producers racing to publish a terminal outcome (or multiple consumers wanting to subscribe to the same completion) require synchronization that prevents torn reads, double-publication, and lost wakeups.

**Sources.** Temporal's `FutureImpl[T]` (`common/future/future_impl.go:11-19,66-84`) uses `pending→setting→ready` CAS with `close(readyCh)` for broadcast; tested with 1024 parallel `Get` (`common/future/future_test.go:95-125`). Agent-framework's `ResponseStream` uses a single-consumer `_consumed`/`_finalized` flag with cached `_final_result` (`python/packages/core/agent_framework/_types.py:2967-2981,3248-3271`). Pydantic-ai's `StreamedRunResult._marked_completed` provides idempotent completion gate (`pydantic_ai_slim/pydantic_ai/result.py:773-781`). OpenAI's `_active_stream_consumers` + `stream_consumers_stopped` event (`src/agents/result.py:654-657`) is a lightweight barrier.

**Why it works.** CAS fences eliminate data races; channel-close broadcast wakes all waiters at once; idempotent completion prevents double-publish.

**When to copy.** Whenever the runtime must guarantee that exactly one terminal state is published and all observers see the same committed value.

**When overkill.** Pure single-waiter synchronous return paths (crewai, openhands local) — they don't need the synchronization.

**Evidence.** Temporal's `TestSetGetReady_Parallel` proves the contract; agent-framework's `_finalize_events` finalizer exercises ordering.

### Pattern: Status enum + separate value payload

**Problem.** A terminal outcome needs both a small categorical status (for routing, alarms, dashboards) and a variable-size value (for the actual result payload).

**Sources.** Agent-framework's `WorkflowRunState` enum + `WorkflowEvent` payload (`python/packages/core/agent_framework/_workflows/_events.py:58-68,71-99`). CrewAI's `RunStatus` via `StopReasonType.run_status` mapping (`letta/schemas/letta_stop_reason.py:24-49`, mirrored in crewai at `lib/crewai/src/crewai/events/types/crew_events.py`). Letta's `RunStatus` + `StopReasonType` + `metadata["result"]` (`letta/schemas/enums.py:152-162`, `letta/services/run_manager.py:451-461`). LangGraph's `GraphOutput(value, interrupts)` discriminator (`libs/langgraph/langgraph/types.py:368-378`). Temporal's `WorkflowExecutionState × WorkflowExecutionStatus` 4×8 matrix with six terminal `Apply*` builders (`service/history/workflow/mutable_state_state_status.go:16-125`, `service/history/workflow/mutable_state_impl.go:4941-5160`). OpenHands' `ConversationExecutionStatus` enum (`_sdk_inspect/sdk/conversation/state.py:36-73`).

**Why it works.** Status is small, queryable, comparable; payload is detached and immutable. Status drives routing/UI; payload drives data flow.

**When to copy.** Any agent runtime where downstream observers care about the categorical reason (dashboard, retry policy, billing).

**When overkill.** Tiny single-step agents where status == "completed successfully" is the only valid state.

**Evidence.** Temporal's matrix is the most rigorous; letta's mapping table covers 11 stop reasons to 5 status values.

### Pattern: Effect-controller / commit barrier

**Problem.** In-memory waiter notification must happen *after* durable publication, not before — otherwise consumers race ahead of persisted state.

**Sources.** Temporal's `effect.Controller.OnAfterCommit` (`service/history/workflow/update/update.go:276,658,790`) gates `Set` on the accepted/outcome futures until after the history batch is durable. Agent-framework's `_run_cleanup` + finalizer ordering in `ResponseStream.get_final_response()` (`python/packages/core/agent_framework/_types.py:3165-3271`). CrewAI's `_drain_memory_writes()` + `crewai_event_bus.flush()` before `CrewKkickoffCompletedEvent` (`lib/crewai/src/crewai/crew.py:1962-1972`). Pydantic-ai's `_run_lifecycle_hooks` await `_wrap_task` and `_finalize_result` before yielding (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:182-344`). Letta's `update_run_by_id_async` commits DB session before dispatching callback (`letta/services/run_manager.py:336-479`).

**Why it works.** Separates "what happened in memory" from "what is durable"; observers either see the final committed state or no state at all.

**When to copy.** Any system where the in-memory and durable views can diverge (durable stores, distributed workers, replay-from-checkpoint).

**When overkill.** Pure in-memory, single-process agents where the only state is what the consumer is awaiting.

**Evidence.** Temporal tests the `accepted` future is `Set` only after the history event is durable; crewai's comment at `crew.py:1080` explicitly documents the drain-before-emit intent.

### Pattern: Truncate-at-finish / truncate-at-finish-error barrier

**Problem.** If a batch contains both a terminal signal (finish/cancel/error) and a subsequent non-terminal action, ambiguous partial states result.

**Sources.** OpenHands' `_ActionBatch._truncate_at_finish` (`_sdk_inspect/sdk/agent/agent.py:128-154`) discards tool calls after `FinishTool.name`. CrewAI's guardrail retry loop (`lib/crewai/src/crewai/task.py:1327-1380`) accumulates failures across attempts and re-exports. Temporal's `ValidateCommandSequence` rejects close + follow-up. LangGraph's `ERROR`/`INTERRUPT` filter in `map_output_updates` (`libs/langgraph/langgraph/pregel/_io.py:128-129`). Agent-framework's `OutputDesignation.classify` returning `None` drops hidden events (`python/packages/core/agent_framework/_workflow_context.py:364-366`).

**Why it works.** Single terminal per batch; no ambiguity about ordering.

**When to copy.** Whenever a tool call from an LLM may include a terminal signal alongside side-effects.

**When overkill.** Linear workflows where terminal is naturally last.

**Evidence.** OpenHands and crewai explicitly document the truncation logic; langgraph and temporal enforce it at the protocol layer.

### Pattern: Drain-then-emit completion fence

**Problem.** Async event handlers (memory writes, observability, callbacks) may not have processed side-effects when the terminal event is observed, leading to inconsistent views.

**Sources.** CrewAI's `_drain_memory_writes` + `flush` before `CrewKkickoffCompletedEvent` (`lib/crewai/src/crewai/crew.py:1887-1964`). Letta's `update_run_by_id_async` commits session before dispatching callback (`letta/services/run_manager.py:450-479`). OpenAI Agents SDK's `_wait_for_turn_event_consumption` joining `event_queue.join()` (`src/agents/result.py:867-882`). Pydantic-ai's `StreamedRunResult._marked_completed` set only after `stream_response` final yield (`pydantic_ai_slim/pydantic_ai/result.py:773-781`). Agent-framework's `_run_cleanup` + finalizer ordering (`python/packages/core/agent_framework/_types.py:3165-3271`).

**Why it works.** Guarantees that what the consumer sees (status, payload) is consistent with what the side effects (memory, callbacks) have produced.

**When to copy.** Anywhere async observers may attach.

**When overkill.** Pure synchronous pipelines.

**Evidence.** Crewai's comment at `crew.py:1080`; openai's `tests/test_run_error_details.py:40-48` confirms drain-then-raise ordering.

### Pattern: Diagnostic retention via carry-chain + string fallback

**Problem.** Errors must travel from the work site to the consumer without losing type fidelity, stack, or cause chain, but serialization may strip tracebacks.

**Sources.** Temporal's `Failure` carries `message`, `stack_trace`, `cause *Failure` verbatim (`service/history/historybuilder/event_factory.go:359-363`). LangGraph preserves `__cause__`/`__notes` via `exc.add_note` (`libs/langgraph/langgraph/pregel/_retry.py:642-643`); persisted as stringified `StateSnapshot.tasks[i].error`. Pydantic-ai's `RunCancelled.from_cancellation` walks `__cause__`/`__context__` (`pydantic_ai_slim/pydantic_ai/exceptions.py:343-362`). Agent-framework's `WorkflowErrorDetails.from_exception` formats traceback string (`python/packages/core/agent_framework/_workflows/_events.py:81-99`). CrewAI's `TaskFailedEvent.error_type` serializes `module:qualname` for cross-process type fidelity (`lib/crewai/src/crewai/events/types/task_events.py:54-72`). OpenAI Agents SDK redacts tracebacks for data safety (`src/agents/exceptions.py:149-156`).

**Why it works.** In-memory objects keep full fidelity; serialized events fall back to strings. The trade-off is privacy vs debuggability.

**When to copy.** Always — but choose redacted vs full fidelity based on whether the consumer is trusted.

**Evidence.** All eight sources provide some form of carry-chain + fallback; only pydantic-ai and temporal explicitly preserve cause chain across serialization boundaries.

## Key Differences

### Work-return vs terminal-outcome: where the line is drawn

Every source separates them but at different layers. Agent-framework draws it at `Executor.handle -> None` plus `ctx.yield_output` (work return is side-effect, not value). CrewAI collapses at crew scope (the agent's bare `str` becomes `TaskOutput` then `CrewOutput`) but keeps the distinction at task scope. LangGraph draws it between the node's dict return and `PregelLoop.output` after `read_channels`. OpenAI Agents SDK draws it between tool returns and `RunResult.final_output`. Pydantic-ai draws it at the graph's `End[FinalResult]` boundary, then synthesizes `AgentRunResult`. Temporal draws it at the command validator: the SDK payload (`CompleteWorkflowExecutionCommandAttributes.Result`) is distinct from the persisted `WorkflowExecutionCompletedEvent.Result`. Letta draws it between `LettaResponse` and the persisted `Run` row. OpenHands blurs it: `Agent.step()` returns `None`; the terminal signal is `FinishAction.message` interpreted as `FINISHED`, but no typed value object represents the finish payload.

The implication: frameworks that expose a typed value object (temporal, agent-framework, pydantic-ai, openai-agents-sdk) can attach diagnostics and usage metadata to it. Frameworks that conflate work return with status field (openhands, letta's status-only side) force consumers to scan history/events.

### Publication barrier: in-memory vs durable

Three layers of barrier exist:

1. **In-memory only**: agent-framework's `_is_running` flag, openai-agents-sdk's `_active_stream_consumers`, pydantic-ai's `_marked_completed`.
2. **DB row commit**: letta's `update_run_by_id_async` + session commit, temporal's `Context.UpdateWorkflowExecutionAsActive` transaction, openhands' `BASE_STATE` JSON write.
3. **History event durable**: temporal's `EventStore` append + `writeEventToCache` (`service/history/workflow/mutable_state_impl.go:4980`), langgraph's `_checkpointer_put_after_previous` gating (`libs/langgraph/langgraph/pregel/_loop.py:1515-1524`).

Letta's background path intentionally releases the conversation lock *before* the final commit (`letta/server/rest_api/redis_stream_manager.py:407-417`), which violates the "release only after complete outcome visible" invariant. Langgraph's `durability="async"`/`"exit"` modes have a similar gap. Temporal alone pairs in-memory broadcast (via `FutureImpl.Set` after `OnAfterCommit`) with durable history replay (via `GetWorkflowExecutionHistory`).

### Cancellation: wait vs run

| Source | Waiter-cancel without run-cancel? | Mechanism |
|--------|----------------------------------|-----------|
| agent-framework | No | `Runner.run_until_convergence` propagates `CancelledError` to iteration_task |
| crewai | No | `StreamingOutputBase.close()` does not interrupt daemon thread |
| langgraph | Partial | Sync-in-async leaves orphan thread (`tests/test_runtime.py:790-820`) |
| letta | No | `cancel_run` always cancels the run |
| openai-agents-sdk | No | `cancel("immediate")` cancels run_loop_task |
| openhands | No | `pause()` cancels the run |
| pydantic-ai | **Yes for streaming** | `AgentStream.cancel()` stops only current `StreamedResponse`; run continues |
| temporal | **Yes** | `FutureImpl.Get(ctx)` selects `ctx.Done()` independently |

Pydantic-ai and temporal are the only sources that decouple waiter cancellation from run cancellation. Pydantic-ai's `RunCancellation.cancel()` mechanism at `pydantic_ai_slim/pydantic_ai/_cancel.py:154-186` counts `Task.cancelling()` to discriminate first-party vs external, and `StreamedRunResult.cancel()` only stops the streaming response. Temporal's `Get(ctx)` (with `readyCh` channel) returns `ctx.Err()` only if the future is not yet ready (`common/future/future_impl.go:42-56,58-64`).

### Multi-waiter broadcast

| Source | Broadcast primitive? |
|--------|---------------------|
| agent-framework | No — single-consumer stream |
| crewai | No — synchronous return + late stream replay only |
| langgraph | No — internal `FuturesDict` for nodes, not for runs |
| letta | No — Redis SSE stream (multi-reader replay, not broadcast) |
| openai-agents-sdk | No — `asyncio.Queue` load-balances among consumers |
| openhands | No — single `FIFOLock` + remote WebSocket |
| pydantic-ai | No — `anyio.MemoryObjectStream` with max_buffer_size=0 (backpressured, not broadcast) |
| temporal | **Yes** — `close(readyCh)` broadcasts to all waiters |

Temporal is the only source with a true broadcast primitive. The others rely on either external coordination (Redis, DB polling) or single-consumer streams.

## Tradeoffs

| Tradeoff | Benefit | Cost | Best-fit | Failure mode |
|----------|---------|------|----------|--------------|
| **Typed value-object vs status-enum-only** | Pydantic-friendly; carries diagnostics and usage; mirrors data flow | Requires consumer to inspect fields; mutable aliasing risk | Library/SDK with diverse consumers | Caller mutates returned value, corrupts future reads (openhands, agent-framework) |
| **Mutable alias return vs defensive copy** | Zero-copy, fast for large messages | Caller-side mutation hazard | Streaming/large-payload scenarios | `MessageHistoryMutatedWarning` in pydantic-ai; corrupted `to_state()` replay |
| **Single-consumer stream vs broadcast** | Simpler invariant; no torn intermediate state | No multi-waiter fan-out | Synchronous single-caller agents | Consumers racing on `asyncio.Queue.get()` (openai-agents-sdk) |
| **Synchronous return vs Future/Promise** | Minimal cognitive load; no event-loop coupling | No composition, no timeout | CLI scripts, single-shot demos | Cannot cancel timeout without killing thread (crewai daemon threads) |
| **Drain-then-emit vs latency** | Guarantees visible-before-released | Slowest memory/handler blocks completion | Telemetry-rich deployments | Hung `drain_writes()` blocks indefinitely (crewai) |
| **Reference-share vs freeze on publish** | Preserves raw_representation and non-serializable refs (agent-framework) | Multi-consumer race hazard | Single-process libraries | Concurrent readers see different views |
| **CAS-fenced Future vs lock-based** | Detects double-set bugs early; lock-free reads | Panics in production if not paired with `SetIfNotReady` | High-throughput services | `FutureImpl.Set` panic on contention (temporal) |
| **Exclusive `value XOR error` vs partial success** | Clean terminal semantics | Tool-level partial success needs separate channel | Most workloads | Crewai's `ToolFailureRecord` shows the workaround |

## Decision Guide

**When to choose a typed value-object (agent-framework, openai-agents-sdk, pydantic-ai)**:

- The consumer wants Pydantic/dataclass ergonomics.
- Usage metrics, guardrail results, or interruption metadata must travel with the outcome.
- Cancellation discipline is "kill the run, kill the waiter" — simpler API.

**When to choose event-sourced BSP (langgraph, openhands, letta, temporal)**:

- Durability and resumability are required.
- Multiple late observers (UI dashboards, REST clients, recovery processes) must read the same committed facts.
- The framework can afford dual sources of truth (in-memory + durable).

**When to choose synchronous return + state field (crewai)**:

- The consumer is a single caller awaiting a one-shot outcome.
- No async runtime overhead is acceptable.
- The library is intended for batch/CLI use.

**When to choose durable transactional close (temporal)**:

- Multi-waiter broadcast is required.
- Strict ordering across history events, in-memory futures, and durable storage is mandatory.
- The runtime is a long-running service (server, not library).

**Rule of thumb**: if the runtime is a *library*, pick value-object with optional broadcast primitive; if it is a *server*, pick transactional close with dual in-memory + durable views; if it is a *CLI/script*, synchronous return suffices.

## Practical Tips

### Patterns to copy

- **Status enum + payload split.** Every observable status enum (WorkflowRunState, RunStatus, ConversationExecutionStatus, WorkflowExecutionStatus) gives downstream routing a small surface; pairing with a typed payload keeps data flow typed. Temporal's 4×8 matrix is the gold standard for the enum half.
- **Drain-then-emit completion fence.** CrewAI's `_drain_memory_writes` + `flush` before `CrewKickoffCompletedEvent` (`lib/crewai/src/crewai/crew.py:1962-1972`) and pydantic-ai's `_marked_completed` after stream final yield (`pydantic_ai_slim/pydantic_ai/result.py:773-781`) prove the pattern.
- **Tool failure as data, not control flow.** CrewAI's `ToolFailureRecord` (`lib/crewai/src/crewai/tools/tool_failure.py:118-119`) shows how to keep agent self-correction flowing without conflating success and failure.
- **Cancellation-aware stream wrapper.** Letta's `cancellation_aware_stream_wrapper` polls DB and `athrow(RunCancelledException)` (`letta/server/rest_api/streaming_response.py:153-229`) is a clean way to inject cancellation into an async generator.
- **Effect-controller commit barrier.** Temporal's `OnAfterCommit` gate on futures (`service/history/workflow/update/update.go:276,658,790`) is the cleanest decoupling of in-memory notification from durable publication.
- **Use typed `Future` for multi-waiter.** Only temporal demonstrates this; for any runtime that expects multiple waiters per run, expose a CAS-fenced future.

### Patterns to avoid or delay until needed

- **Single-consumer stream as the only waiter API.** Openai-agents-sdk's queue load-balances rather than broadcast; this fails concurrent-waiter tests by design.
- **Mutable aliasing of returned value.** All eight sources do it, but the lack of `freeze`/`deepcopy` is the #1 source of post-publication mutation hazards.
- **Daemon threads for task execution.** CrewAI's `threading.Thread(daemon=True)` (`lib/crewai/src/crewai/task.py:618`) cannot be cancelled, timed out, or bounded; `ThreadPoolExecutor` with structured concurrency is strictly better.
- **Status enum-only with no typed value.** OpenHands' `ConversationExecutionStatus` forces consumers to scan `EventLog` for the finish message; a typed `RunResult` would be cleaner.
- **Cancelling waiter == cancelling run.** Only pydantic-ai and temporal decouple; until you need to, coupling is simpler but prevents `asyncio.wait_for(..., shield_run=True)` patterns.

### Decision rules

- **Do you need multi-waiter broadcast?** Yes → temporal-style `FutureImpl`; No → any of the other patterns.
- **Is the run durable / long-running?** Yes → event-sourced with history; No → typed value-object.
- **Is the runtime a server or a library?** Server → transactional close + dual views; Library → value-object + optional broadcast.
- **Is partial success at tool granularity meaningful?** Yes → model as data (crewai's `ToolFailureRecord`); No → exclusive `value XOR error`.
- **Will consumers mutate the returned value?** Yes → freeze or defensive copy on publication (temporal protobufs, pydantic-ai streaming `deepcopy`); No → alias for zero-copy.

## Caution Signs

**The publication contract is becoming brittle when:**

- **Run-handle API is absent** and consumers are building their own polling loops. Letta, openhands, langgraph all rely on external polling because no `Future`/`JoinHandle` exists.
- **`_is_running` / "concurrent not allowed" exceptions appear.** Agent-framework, openhands, crewai all reject concurrent runs; this is a sign the contract is single-waiter.
- **Cancellation lacks a `waiter_only=True` flag.** All sources except pydantic-ai and temporal treat cancel-the-run and cancel-the-waiter as the same operation.
- **Multiple terminal states (`FAILED`/`CANCELLED`/`TERMINATED`/`TIMED_OUT`) appear in the enum but no path sets one of them.** Agent-framework's `WorkflowRunState.CANCELLED` is reserved but never produced (`python/packages/core/agent_framework/_workflows/_events.py:67`).
- **Diagnostic retention degrades at scale boundaries.** Temporal preserves `Failure.cause` across serialization; crewai drops it to `str(e)`; openhands keeps only `code`/`detail` strings.
- **Two sources of truth drift.** Temporal reconciles via `ReadyFutureImpl` reload (`service/history/workflow/update/registry.go:455-480`); letta has DB row + Redis stream + memory; langgraph has in-memory channel + checkpointer.
- **Tests don't assert late-waiter consistency.** Every source except temporal reports `No evidence of tests for two concurrent awaiters` — a sign the contract is single-waiter by design.
- **`copy.deepcopy` is missing on the publication path.** All eight except temporal's protobufs and openhands' EventLog JSON skip defensive copy; if mutation matters, this is a hazard.
- **`OnAfterCommit` / drain-fence is missing or skipped.** Langgraph's `durability="async"`, letta's background lock release, openhands' REST polling fallback all indicate the "release only after visible" invariant is not enforced.

## Notable Absences

- **No multi-waiter broadcast in any source except temporal.** Even pydantic-ai's `AgentStream` uses an `anyio.MemoryObjectStream` with `max_buffer_size=0` for backpressure, not broadcast.
- **No framework implements a true `Outcome[T, E]` discriminated union** (success + error in one object). All use exclusive `value XOR error` with errors as exceptions or as separate typed events.
- **No `freeze()` / `MappingProxy` on the returned terminal value** except temporal's protobufs (which are immutable by convention).
- **No documented waiter-vs-run cancellation separation** except pydantic-ai (`StreamedRunResult.cancel()`) and temporal (`FutureImpl.Get(ctx)`).
- **No defensive `bytes.Clone` / `proto.Clone` on `Payloads` / `Result` at the builder boundary** in temporal's `Create*WorkflowEvent` (`service/history/historybuilder/event_factory.go:344,361`); relies on protobuf immutability by convention.
- **No atomic transaction across value + status + metrics + callbacks** in any source except temporal's `Context.UpdateWorkflowExecutionAsActive` (`service/history/workflow/context.go:884-897`). Letta's `update_run_by_id_async` commits status first, then a separate metrics commit (`letta/services/run_manager.py:412-447`).
- **No `Future.share()` semantics for late joiners** — even temporal's `ReadyFutureImpl` returns a pre-computed copy, not a live share.

## Per-Source Notes

**agent-framework** — The two-track publication (Agent vs Workflow) is well-typed. `WorkflowErrorDetails.from_exception` retains traceback strings, but `WorkflowRunResult` mutably aliases published outputs. The `CANCELLED` state is reserved but unused by the core engine; only `WorkflowExecutor` references it (`python/packages/core/agent_framework/_workflows/_workflow_executor.py:627-630`).

**crewai** — Strongest tool-failure-as-data pattern (`ToolFailureRecord` with `frozen=True`). Drain-then-emit ordering is explicit and commented (`lib/crewai/src/crewai/crew.py:1080`). Daemon threads for async task execution (`lib/crewai/src/crewai/task.py:618`) make `cancel()` impossible.

**langgraph** — BSP superstep with `PregelLoop.output` synthesized after `read_channels` and the new `GraphOutput(value, interrupts)` wrapper for v2. `Durability` knob (`sync`/`async`/`exit`) is honest about visibility gap (`libs/langgraph/langgraph/pregel/main.py:3878-3888`). Error-handler routing via `_handled_exception_ids` is rigorous but loses exception type in persisted snapshot.

**letta** — Cleanest typed status enum mapping (`StopReasonType.run_status`) but background path violates the visibility-before-release invariant (`letta/server/rest_api/redis_stream_manager.py:407-417`). Redis SSE stream with `xadd` + `expire 10800s` gives 3-hour replay window. Otid-based request token dedup is a clever idempotency layer.

**openai-agents-sdk** — Sentinel-terminated async iterator with `_active_stream_consumers` rendezvous is a lightweight barrier. Redacted-error boundary (`_detach_data_redacted_error_traceback`) protects payload data at the cost of debuggability. No broadcast primitive — concurrent `stream_events()` consumers race on `queue.get()`.

**openhands** — `Event` is `frozen=True` but `Observation` payloads are mutable. `FIFOLock` + `__setattr__` autosave (`_sdk_inspect/sdk/conversation/state.py:380-420`) provides single-lock fairness. File-per-event append-only log is crash-safe but cross-file atomicity is not guaranteed.

**pydantic-ai** — Strongest cancellation discrimination via `RunCancellation.cancel()` + `Task.cancelling()` counting. Capability middleware (`wrap_run`/`on_run_error`/`after_run`) at `_run_lifecycle_hooks` enables durability providers (Temporal/DBOS/Prefect) without graph core changes. Mutable aliased `message_history` is the main hazard.

**temporal** — CAS-fenced `FutureImpl` with `pending→setting→ready` and `close(readyCh)` broadcast is the only true multi-waiter primitive. `ValidateCommandSequence` (`service/history/api/command_attr_validator.go:637-678`) enforces "close command last, alone" at the protocol level. `effect.Controller.OnAfterCommit` cleanly decouples in-memory notification from durable publication. No defensive Clone on `Payloads`/`Failure` at the event-factory boundary.

## Open Questions

1. **No multi-waiter broadcast primitive outside temporal.** Searches across seven sources found no `Future.share()` or pubsub for run outcomes. Is the multi-waiter case rare in practice, or are consumers building external coordination layers (Redis, DB polling)?

2. **CANCELLED state reserved but unused** in agent-framework. Does .NET host set it? Why is `WorkflowRunState.CANCELLED` in the public enum (`python/packages/core/agent_framework/_workflows/_events.py:67`) if no core path produces it?

3. **CrewAI's daemon-thread `Future[TaskOutput]`** is private to `_process_async_tasks` (`lib/crewai/src/crewai/crew.py:2005-2018`). Is there a deliberate decision not to expose it, or is it an oversight?

4. **LangGraph's `durability="async"`/`"exit"`** have documented read-after-write races (`libs/langgraph/langgraph/pregel/_loop.py:1515-1524`). Are these intended for high-throughput non-critical workloads only, or is a `wait_for_checkpoint(checkpoint_id)` API planned?

5. **Pydantic-ai's `RunCancellation` race on py3.10** (`pydantic_ai_slim/pydantic_ai/_cancel.py:142-144`): no `Task.cancelling()` available, so first-party wins. Is a fallback mechanism planned, or is py3.11+ the supported floor?

6. **Letta's inconsistent terminal guard**: `JobManager.safe_update_job_status_async` raises `ValueError` (`letta/services/job_manager.py:84-94`), but `RunManager.update_run_by_id_async` logs only (`letta/services/run_manager.py:342-356`). Is the inconsistency intentional to preserve `completed→cancelled` for `requires_approval`?

7. **OpenHands' `FinishAction.message`** is a `str` not a structured value. Is there a planned typed `RunResult` that surfaces it, or is the design "scan EventLog for FinishAction"?

8. **Temporal's `forceTerminateWorkflow`** can override the SDK's intended close outcome (`service/history/workflow/context.go:1406-1446`). Are downstream consumers expected to read history directly when status is `TERMINATED`, or is there a planned unified payload?
