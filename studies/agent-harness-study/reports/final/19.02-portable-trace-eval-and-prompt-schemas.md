## Executive Summary

Portability across these six systems is sharply uneven by artifact type. **Tool schemas are solved**: every source except langgraph converges on canonical JSON Schema generated from code (Pydantic/TypeAdapter) plus per-provider adapters — a pattern mature enough to copy verbatim. Traces, eval datasets, and prompts are not: only three systems speak OpenTelemetry natively on the wire, and none ships bulk migration tooling.

The strongest trace stories are `agent-framework` (vendor-neutral OTLP gRPC + HTTP/protobuf with env-var fidelity) and `pydantic-ai` (OTel GenAI semconv with `AGENTS.md:16` spec-guard and versioned instrumentation 2-6). Langfuse is dual-ingest (OTLP front door + Langfuse Zod envelope) but persists its own envelope, so export requires transformation. The other three are locked: LangGraph to LangSmith `LangChainTracer`, OpenAI Agents SDK to proprietary `{"object":"trace"}` dicts, OpenHands to Laminar despite `OTEL_*` env names.

Eval datasets and prompt registries barely exist as portable products. Only Langfuse and Pydantic AI offer versioned, file-serializable datasets (`unknown` JSON with `inputSchema` vs YAML/JSON `Case[InputsT,OutputT]`), and both still bind evaluators as code via registry — data migrates, logic does not. Prompts are a custom engine per system (Jinja2, Handlebars, mustache-lite, plain string, hosted reference); no two share a standard IR. The universal gap is migration ergonomics: zero sources provide `export_traces --format otlp|jsonl` or `dataset export --to hf|langsmith`.

Can you migrate without rewriting data? For tool calls: yes. For traces with OTel-native sources: mostly. For everything else: you will write translators.

## Core Thesis

**Tool portability has converged on "canonical JSON Schema + deferred provider transform"; trace/eval/prompt portability has not, because vendors face opposite constraints: observability platforms want ingestion standardization (OTel) while agent harnesses want execution fidelity (LangSmith/Laminar/custom dicts).**

What converges despite implementation divergence:
- All systems that offer cross-provider execution eventually centralize tool authoring on a single JSON Schema (Pydantic `model_json_schema()` or `LLMJSONSchema`) and postpone wire differences to adapters at request-build time — `agent-framework` across four adapters, `pydantic-ai` via `JsonSchemaTransformer`, `openhands` via triple adapters, `langfuse` via LangChain `bindTools`. This works because JSON Schema is the only stable shared type system across OpenAI, Anthropic, Bedrock, and Gemini.
- All systems that care about trace interop add OTel as a sidecar rather than replacing their internal envelope, accepting the cost of dual representation to keep existing queries working.

Why sources diverge is not quality alone but product shape:
- **Platform vs harness:** Langfuse (observability platform) stores a proprietary envelope and must translate OTLP *in*; harnesses (`agent-framework`, `pydantic-ai`) emit OTel and translate *out* — the direction of translation reflects who owns the query path.
- **Lifecycle maturity:** `agent-framework` and `pydantic-ai` explicitly version instrumentation (`gen_ai.*` semconv 2-6) with deprecation warnings; younger harness SDKs (OpenAI Agents, LangGraph) freeze a single vendor format because their trace consumers are single-vendor dashboards.
- **Library vs application:** Pydantic AI and Langfuse must standardize dataset files (YAML/JSON) for reproducibility; LangGraph/OpenHands/OpenAI SDK treat eval as external (LangSmith Studio / ad-hoc critics / absent), so they invest in runtime `Event`/`Message` persistence instead.
- **Template coupling:** Systems with strong Python typing (`pydantic-ai` Handlebars + `deps_type`, `openhands` Jinja2 + filesystem `prompt_dir`) trade cross-platform rendering for compile-time safety; systems with hosted prompts (OpenAI `ResponsePromptParam`) trade portability for governance.

## Approach Models

**Trace archetypes (3 clusters):**

- **OTel-native emit (agent-framework, pydantic-ai):** Internal spans are OTel semantic conventions from the start. `agent-framework` creates three-signal OTLP exporters for both `grpc` and `http/protobuf` with per-signal env var parsing (`observability.py:365-484`, `487-578`) and wires `TracerProvider`/`MeterProvider`/`LoggerProvider` via `ObservabilitySettings._configure` (`observability.py:830-948`). `pydantic-ai` normalizes `ModelRequest`/`ModelResponse` into `gen_ai.input.messages`/`gen_ai.output.messages` via `InstrumentationSettings.messages_to_otel_messages` (`models/instrumented.py:205-223`) and serializes via `safe_to_json` to `gen_ai.system_instructions` + `logfire.json_schema` (`models/instrumented.py:253-289`). Any OTLP collector ingests without translation.

- **Dual-ingest / translate-in (langfuse):** Accepts spec-compliant OTLP JSON + binary protobuf with gzip (`opentelemetry.yml:7-34`, `web/src/pages/api/public/otel/v1/traces/index.ts:78-114`) but persists the Zod-validated Langfuse envelope (`trace-create`/`span-create`/`generation-create` at `packages/shared/src/server/ingestion/types.ts:259-279,395-755`). Outbound to Jaeger/Honeycomb requires mapping `observation.type` (`SPAN|GENERATION|TOOL` at `ingestion.yml:147-158`) back to OTel span kinds. Migration is API-pulled (`GET /v2/traces`, `CoreDataS3ExportQueue` at `queues.ts:366`) not zero-copy.

- **Proprietary emit + pluggable export seam (openai-agents-sdk, openhands, langgraph):** Wire format is vendor-specific; portability is "write a processor." OpenAI SDK exports `{"object":"trace","id":trace_id,"workflow_name":...}` (`tracing/traces.py:568-575`) and `{"object":"trace.span", "span_data": ...}` (`tracing/spans.py:396-423`) with 13 `SpanData` subtypes (`span_data.py:28-452`) hardcoded to `https://api.openai.com/v1/traces/ingest` (`processors.py:44-50`); replacement is via `set_trace_provider`/`set_trace_processors` (`tracing/setup.py:27-66`, `docs/tracing.md:196-226` lists 27 adapters). OpenHands reads `OTEL_EXPORTER_*` keys (`observability/laminar.py:25-30`) then unconditionally imports `lmnr` and wraps `Laminar.start_span`/`use_span` in `RootSpan` (`observability/laminar.py:231-266`) and `@observe` via `lmnr.observe` (`observability/laminar.py:115-196`). LangGraph wraps every node as `RunnableCallable(..., trace=True)` emitting `LangChainTracer` runs with `trace_id`/`dotted_order`/`parent_run_id` (`_internal/_runnable.py:400-426, 529-553`) and no OTEL path (`tests/test_graph_callbacks.py:283` monkey-patch comment only).

**Eval dataset archetypes (2 clusters + absent):**

- **File-serializable generic data + code registry (pydantic-ai, langfuse, partially agent-framework):** `pydantic-ai` `Dataset[InputsT,OutputT,MetadataT]` is YAML/JSON with `from_file`/`to_file` inferring extension plus `$schema` sidecar (`dataset.py:177-246, 556-634, 747-794`) and `NamedSpec` short-form (`_spec.py:50-111`); evaluators require `custom_evaluator_types` on load (`dataset.py:686-740`). Langfuse `DatasetItem {input: unknown, expectedOutput: unknown, metadata: unknown}` (`dataset-items.yml:63-74`) with optional `inputSchema`/`expectedOutputSchema` on the dataset (`datasets.yml:79-84`), temporal `?version=ISO8601` (`dataset-items.yml:24-40`), and `validFrom`/`validTo` bitemporal rows (`repositories/dataset-items.ts:1680-1705`). `agent-framework` has the same ambition with `EvalItem(conversation, tools, context)` (`_evaluation.py:181-297`) and `Evaluator` protocol + `LocalEvaluator` (`_evaluation.py:682-725, 1036-1280`) but dataset I/O is only in-memory plus Foundry-specific JSONL with `{{item.query_messages}}` mapping (`foundry/_foundry_evals.py:898-944`) and `AgentEvalConverter` (`_evaluation.py:732-927`).

- **Absent / runtime-only (langgraph, openai-agents-sdk, openhands):** No `Dataset`/`Eval` types; langgraph redirects to LangSmith Studio (`redirects.json:123`), openai-agents-sdk greps empty for `eval|dataset`, openhands evaluates live `list[Event]` via `CriticBase` (`critic/base.py:65-83`) and `CriticMixin` modes (`agent/critic_mixin.py:34-73`).

**Prompt archetypes (4 clusters):**

- **Filesystem Jinja2/Handlebars (openhands, pydantic-ai):** `openhands` `render_template(prompt_dir, template_name, **ctx)` via `FlexibleFileSystemLoader` + `FileSystemBytecodeCache` (`context/prompts/prompt.py:16-45, 57-114`) with 10+ `.j2` files plus `model_specific/` overrides; `pydantic-ai` `TemplateStr` via optional `pydantic-handlebars` with `deps_type` validation (`template.py:16-49, 50-84`). Both are standard engines, copy-portable as files, but variable contracts are implicit.

- **Custom mustache-lite + composition (langfuse):** `MUSTACHE_REGEX = /{{([^{}]*)}}/g` (`utils/stringChecks.ts:10-12`) with lenient `compileTemplateString` preserving `{{var}}` (`worker/src/features/utils/utilities.ts:5-22`) vs strict `compileChatMessages` throwing on missing (`server/llm/compileChatMessages.ts:40-50`), plus typed `Placeholder` messages (`server/llm/types.ts:189-198`) and `@@@langfusePrompt:name=...@@@` recursive resolution with `MAX_PROMPT_NESTING_DEPTH=5` (`services/PromptService/index.ts:234-379`) and epoch cache (`PromptService/index.ts:20-46, 177-232`).

- **String/registry-less (agent-framework, langgraph):** `Agent(instructions: str)` (`_agents.py:600-650`), experimental `kind: Prompt` YAML (`declarative-agents/agent-samples/openai/OpenAI.yaml:1-28`), or `Prompt = str | SystemMessage | Callable | Runnable` via `_get_prompt_runnable` (`chat_agent_executor.py:121-126, 137-170`) — ephemeral, with callable prompts unserializable.

- **Hosted reference (openai-agents-sdk):** `Prompt = {"id": str, "version"?: str, "variables"?: ...}` wrapping `ResponsePromptParam` (`prompts.py:23-34`) resolved via `PromptUtil.to_model_input` (`prompts.py:56-82`); rejected on Chat Completions (`openai_chatcompletions.py:85-102`).

**Tool schema archetypes (converged):**

- Single canonical JSON Schema produced from code (Pydantic `model_json_schema()` or Zod `LLMJSONSchema`) with per-provider adapters at build time. Strength varies only by coverage: `agent-framework` (OpenAI/Anthropic/Bedrock/Gemini), `pydantic-ai` (canonical `ToolDefinition.parameters_json_schema` at `tools.py:544-554` + `JsonSchemaTransformer` at `_json_schema.py:59`), `openhands` (`to_mcp_tool`/`to_openai_tool`/`to_responses_tool` at `tool/tool.py:379-498`), `langfuse` (`LLMToolDefinitionSchema` at `server/llm/types.ts:45-50` via LangChain `bindTools` at `fetchLLMCompletion.ts:467-710`), `openai-agents-sdk` (Pydantic + `ensure_strict_json_schema` at `strict_schema.py:115`), `langgraph` (partial — `BaseTool` + OpenAI vs Anthropic branch at `chat_agent_executor.py:202-210`).

## Pattern Catalog

**1. Canonical JSON Schema + Deferred Provider Transform**

- *Problem:* One tool definition must run on multiple model providers whose wire shapes differ (`FunctionToolParam` vs `input_schema` vs `inputSchema.json` vs `FunctionDeclaration`).
- *Sources:* agent-framework (`_tools.py:784-826`, `openai/_chat_client.py:890-935`, `anthropic/_chat_client.py:890-896`, `bedrock/_chat_client.py:200-210`, `gemini/_chat_client.py:320-360`), pydantic-ai (`tools.py:268-274, 544-554`, `_json_schema.py:15-59, 226-233`, `tools.py:104-163`), openhands (`tool/schema.py:70-198, 201-239`, `tool/tool.py:379-498`), langfuse (`server/llm/types.ts:16-50`, `fetchLLMCompletion.ts:467-710, 802-827`), openai-agents-sdk (`function_schema.py:22-45, 296-489`, `strict_schema.py:115-405`).
- *Why it works:* Pydantic/Zod gives a single auditable source of truth; `$ref`/`anyOf` normalization and `strict` handling happen once at request-build time, not at authoring time.
- *When to copy:* Always if you target 2+ providers. Use `agent-framework`'s `normalize_tools` (`_tools.py:941-1005`) plus `FunctionTool.parameters()` caching as the reference, and `pydantic-ai`'s `JsonSchemaTransformer.walk` + `prepare_tool_def` hooks for edge providers.
- *When to overkill/risky:* Single-provider product with only hosted tools — strict inlining (`additionalProperties:false`, `anyOf` stripping) can degrade valid schemas; `openhands` circular-ref fallback to `{"type":"object"}` (`schema.py:64-67`) silently loses structure.
- *Evidence:* `python/packages/core/agent_framework/_tools.py:784-826` (canonical), `pydantic_ai_slim/pydantic_ai/_json_schema.py:59` (transformer), `_sdk_inspect/sdk/tool/tool.py:413-498` (triple adapters).

**2. Spec-Guarded OTel Module (OTel GenAI semconv as the only trace contract)**

- *Problem:* Internal spans drift into proprietary attributes that collectors cannot index.
- *Sources:* pydantic-ai (`_otel_messages.py:1-4`, `AGENTS.md:16` policy, `models/instrumented.py:78-79, 154-164, 253-289`, `_instrumentation.py:284-303, 370-395`), agent-framework (`observability.py:176-314` `OtelAttr` enum with `gen_ai.operation.name`, `gen_ai.tool.*`, `mcp.*`, `workflow.*`).
- *Why it works:* `_otel_messages.py` is typed-only, implements only spec-defined variants (`TextPart`/`ToolCallPart`/`MediaUrlPart`/`ThinkingPart`), and `handle_messages` emits `gen_ai.input.messages`/`gen_ai.output.messages`/`gen_ai.system_instructions` consistently; versioned instrumentation (2-6) evolves without breaking collectors.
- *When to copy:* If traces must survive backend switches (Jaeger ↔ Honeycomb ↔ Datadog) — adopt the `AGENTS.md:16` "spec-only in `_otel_*.py`" rule and publish the instrumentation version.
- *When overkill:* Vendor-locked SaaS whose trace UI owns the query path (OpenAI dashboard) — custom `span_data.type` is richer short-term.
- *Evidence:* `pydantic_ai_slim/pydantic_ai/_otel_messages.py:1-4`, `pydantic_ai_slim/pydantic_ai/AGENTS.md:16`, `python/packages/core/agent_framework/observability.py:176-314`.

**3. Pluggable Tracer / Processor Seam (escape hatch over standard format)**

- *Problem:* No standard covers all vendor fields (reasoning blocks, `responses_reasoning_item`, provider details).
- *Sources:* openai-agents-sdk (`processor_interface.py:9-142`, `provider.py:222-298`, `setup.py:27-66`, `SynchronousMultiTracingProcessor` at `provider.py:117-175`, `BatchTraceProcessor` at `processors.py:541-718`), pydantic-ai (`models/instrumented.py:145` pluggable `TracerProvider`, `otel/_context_in_memory_span_exporter.py:85-169` fallback), langfuse queue optional fields (`server/queues.ts:72-73`, `ingestion/types.ts:31-33`).
- *Why it works:* `DefaultTraceProvider` fan-out with per-processor error isolation plus `BatchTraceProcessor` queue (`maxsize=8192`, `schedule_delay=5.0`, `export_trigger_ratio=0.7` at `processors.py:548-669`) makes adding a backend a 20-line class; 27 community processors in `docs/tracing.md:196-226` prove leverage.
- *When to copy:* When you must support vendor-specific span data but still allow migration — expose `TracingExporter.export(items)` and `BatchTraceProcessor` as the integration point.
- *When risky:* Abstraction without a canonical export schema (`openai-agents-sdk` `TraceImpl.export()` has no `version` field at `traces.py:568`) drifts silently; `queue.Full` drops (`processors.py:597-621`) lose traces under burst.
- *Evidence:* `src/agents/tracing/provider.py:93`, `src/agents/tracing/processors.py:541`, `docs/tracing.md:196-226`.

**4. Versioned / Bitemporal Dataset & Prompt Storage**

- *Problem:* Eval reproducibility and prompt rollback require point-in-time snapshots.
- *Sources:* langfuse (`repositories/dataset-items.ts:1680-1705` distinct `valid_from`, `buildDatasetItemsAtVersionQuery` at `1082-1158`, `GET /dataset-items?version=ISO8601` at `dataset-items.yml:24-40`, `PromptService` epoch `prompt:{projectId}:{epoch}:{name}:{version|label}` at `index.ts:201-206`), pydantic-ai (`Dataset.to_file/from_file` with `$schema` sidecar at `dataset.py:747-794`, `_DatasetModel` `extra='forbid'` at `99-108`), agent-framework (`EvalResults` with `per_evaluator`/`sub_results` at `_evaluation.py:372-643`).
- *Why it works:* Surrogate version rows (`validFrom`/`validTo`) and epoch cache rotation (`invalidateCache` rotates epoch at `index.ts:228`) give branch-friendly history without deleting keys (Redis `NX` safe).
- *When to copy:* Any platform with production prompts or eval datasets — temporal queries beat ad-hoc `label: production` tags.
- *When overkill:* Prototype harness with ephemeral datasets — `agent-framework` `EvalItem` in-memory suffices.
- *Evidence:* `packages/shared/src/server/repositories/dataset-items.ts:1680-1705`, `pydantic_evals/pydantic_evals/dataset.py:747`.

**5. Serialization Protocol with Injectable Non-Serializables**

- *Problem:* `Message`/`FunctionTool` histories must round-trip through JSON without persisting callables or clients.
- *Sources:* agent-framework (`_serialization.py:137-588` `SerializationMixin.to_dict`/`from_dict(dependencies=...)` with `INJECTABLE`, `make_json_safe`, `Content`/`Message` `SerializationProtocol` at `_types.py:1378-1412`), pydantic-ai (`messages.py:2769-2772` `ModelMessagesTypeAdapter` with `ser_json_bytes='base64'`, `run.py:176`/`result.py:556` via `dump_json`, alias handling at `messages.py:2694-2701`), openhands (`conversation/event_store.py:132-145` `model_dump_json` per `event-{idx:05d}-{id}.json`, `model_validate_json` at `105-112`).
- *Why it works:* `from_dict(dependencies={"function_tool":{"func": fn}})` injects `func` at hydrate time, keeping JSON clean; `ser_json_bytes='base64'` preserves binary losslessly; discriminated `kind` (`DiscriminatedUnionMixin` at `event/base.py:20-23`) routes polymorphism.
- *When to copy:* If you persist trajectories for replay — adopt the injectable pattern plus `sanitize_messages` stripping `STANDING_PROMPT_PLANTED_KEY` (`messages.py:3376`).
- *When risky:* `kind` registry skew across SDK versions breaks `model_validate_json`; `mimetypes.guess_type` platform variance (`messages.py:898`) alters `BinaryContent.format`.
- *Evidence:* `python/packages/core/agent_framework/_serialization.py:392-560`, `pydantic_ai_slim/pydantic_ai/messages.py:2769-2772`.

**6. Typed Placeholder + Composition for Prompt Reuse**

- *Problem:* One placeholder should expand to many messages; prompts should compose without copy-paste.
- *Sources:* langfuse (`server/llm/types.ts:189-198` `PlaceholderMessage {type:"placeholder", name}`, `server/llm/compileChatMessages.ts:34-63` `expandPlaceholder`, `features/prompts/parsePromptDependencyTags.ts:3` `@@@langfusePrompt:name=...@@@` with `PromptService/index.ts:234-379` recursion guards `MAX_PROMPT_NESTING_DEPTH=5`), openhands `render_template` with `FlexibleFileSystemLoader` (`prompt.py:16-45`) and `instruction` `sorted`/`join` (`messages.py:1778-1787`).
- *Why it works:* Placeholder-as-message lets a single array slot expand to N messages; `escapeRegex` + cycle detection prevents injection/loop.
- *When to copy:* Prompt libraries with shared system instructions — model it as `ChatMessage | PlaceholderMessage` not string replacement.
- *When overkill:* Single-agent product with one system prompt — flat `instructions: str` is simpler.
- *Evidence:* `packages/shared/src/server/llm/types.ts:189-198`, `packages/shared/src/server/llm/compileChatMessages.ts:34-63`.

## Key Differences

**Trace portability — emit vs ingest, standard vs seam:**
`agent-framework` and `pydantic-ai` emit OTel-native and are movable without translation (`observability.py:365-484` OTLP dual protocol; `models/instrumented.py:253` OTel attributes). Langfuse ingests OTel but stores Langfuse-native, so moving *out* needs mapping (`ingestion/types.ts:259-279` vs `opentelemetry.yml:7-34`). OpenAI SDK, OpenHands, LangGraph emit proprietary and rely on code seams (`set_trace_provider`, `lmnr` import, `LangChainTracer`) — migration rewrites the exporter, not just the endpoint.

**Dataset portability — generic `unknown` vs typed generics:**
Langfuse stores `input`/`expectedOutput` as `unknown` JSON validated optionally against `inputSchema` on the dataset (`datasets.yml:79-84`), maximizing cross-system consumption via `GET /dataset-items`. Pydantic AI stores typed `Case[InputsT,OutputT,MetadataT]` validated via `Dataset.model_json_schema_with_evaluators` (`dataset.py:797-844`) — stronger local safety, weaker interop without Python. `agent-framework` core `EvalItem.conversation: list[Message]` (`_evaluation.py:181-297`) preserves modality (text/image/tool_call) but cloud `FoundryEvals` rewrites to Foundry JSONL (`foundry/_foundry_evals.py:898-944`).

**Prompt portability — filesystem standard vs platform-registry vs hosted reference:**
OpenHands and Pydantic AI are filesystem-standard (Jinja2 `.j2` vs Handlebars `TemplateStr` with `deps_type`), copy-portable but engine-coupled and without versioning/registry API. Langfuse is registry-standard (version, label, `commitMessage`, `resolutionGraph` at `prompts.yml:10-33, 152-168`, Zod `CreatePromptSchema` at `features/prompts/types.ts:58-61`) but custom rendering with two compilers that disagree on missing variables (`worker/src/features/utils/utilities.ts:15` preserve vs `server/llm/compileChatMessages.ts:40-43` throw). OpenAI SDK is hosted-reference only (`ResponsePromptParam` at `prompts.py:23-34`) — no portable IR.

**Tool schema handling — owned adapters vs delegated:**
`agent-framework` and `openhands` own every translation (4 providers vs 3 targets with `to_mcp_tool`/`to_openai_tool`/`to_responses_tool`); `langfuse` delegates to LangChain `bindTools` (`fetchLLMCompletion.ts:802-827`) trading control for coverage (six adapters at `467-710`); `pydantic-ai` owns via `JsonSchemaTransformer` but defers provider quirks to `prepare` hooks (`tools.py:512-529`); `langgraph` branches ad-hoc for only two providers (`chat_agent_executor.py:202-210`), leaving Google/Bedrock unhandled.

**Operational safeguards:**
Only `agent-framework` (`enable_sensitive_data` opt-in at `observability.py:1075-1166`, sticky disable at `829-948`), `openai-agents-sdk` (`BatchTraceProcessor` retry/backoff at `processors.py:158-221`, `OPENAI_AGENTS_DISABLE_TRACING` at `provider.py:346-352`), and `langfuse` (ingestion version gate `>4` at `web/.../otel/v1/traces/index.ts:152-160`, `allowPartialSuccess` for CSV import at `repositories/dataset-items.ts:537-665`) document operational controls. LangGraph/OpenHands/Pydantic AI lean on `SerializerProtocol`/`FileStore` durability, not trace ops.

## Tradeoffs

**Single canonical schema vs provider-fidelity loss:** Canonical JSON Schema (`FunctionTool.parameters()` / `ToolDefinition.parameters_json_schema`) lets one decorator cover every provider, but `additionalProperties:false` over-strictness (`_tools.py:1112-1115`, `strict_schema.py:115-405`), `oneOf`/`anyOf` stripping (`tool/schema.py:70-170`), and circular-ref collapse (`schema.py:64-67` → `{"type":"object"}`) degrade expressive schemas. Alternative: preserve raw schema per provider (LangGraph branch) — keeps fidelity but leaks provider specifics into harness and omits new providers. Best-fit: canonical if you target ≥3 providers; raw per-provider if single-provider.

**OTel-native emit vs vendor-rich custom spans:** OTel GenAI (`gen_ai.input.messages`, `gen_ai.tool.definitions` at `_instrumentation.py:370-395`) guarantees any OTLP collector works, but spec-guard (`AGENTS.md:16`) forces framework concepts (deferred tools, approvals, `STANDING_PROMPT_PLANTED_KEY`) onto generic attributes or dropped entirely (`messages.py:3376`). Custom dicts (`span_data.type` at `span_data.py:28-452`, Langfuse `observation.type`) carry richer LLM data (`reasoning_content`, `responses_reasoning_item` at `llm/message.py:278-722`) but need bespoke adapters per backend. Best-fit: OTel for platform products; custom for harness demos that need reasoning fidelity.

**Pluggable processor seam vs standard wire format:** Replacing `TraceProvider`/`TracingProcessor` (OpenAI SDK `setup.py:27-66`, `provider.py:93`) is trivial and proves ecosystem velocity (27 processors). Cost is each consumer rewrites translation from custom dict rather than consuming OTLP directly, and queue overflow (`queue.Full` at `processors.py:603`) silently drops. Standard wire (OTLP protobuf) would give zero-translation migration. Best-fit: seam when you must ship fast with many backends; standard wire when durability and zero-copy matter.

**Filesystem templates vs registry:** `.j2`/Handlebars files (`prompt.py:57-114`, `template.py:61`) are copy-portable and offline, with `FileSystemBytecodeCache` (`prompt.py:62-66`) avoiding reparsing, but variable contracts are implicit (`system_prompt.j2:79-88` expects `security_policy_filename` etc.) and migration to Mustache/dotprompt rewrites `{{ }}` + `{% include %}`. Registry (Langfuse `PromptService` epoch cache, `labels` regex at `features/prompts/types.ts:108-160`) gives versioning, tags, and `@@@` composition (`index.ts:234-379`) at the cost of a service dependency and divergent compiler semantics (`utilities.ts:15` vs `compileChatMessages.ts:28` unescaped `RegExp`). Best-fit: filesystem for library consumers; registry for SaaS with non-code prompt editing.

**Data-only dataset vs code-bound evaluators:** Data-only (Langfuse `unknown` JSON, Pydantic AI data side) migrates without Python, but evaluator logic still requires `custom_evaluator_types` (`dataset.py:686-740`) or Langfuse worker `compileEvalPrompt` (`evalRuntime.ts:14-26`). Code-bound (`NamedSpec` short-form at `_spec.py:50-111`, `LocalEvaluator` + `@evaluator` at `_evaluation.py:1036-1280`) keeps dataset files tiny and type-safe but prevents zero-code interop (Python class must be shipped). Failure mode: loading dataset without registration raises listing valid names (`_spec.py:223`) — a silent migration break.

## Decision Guide

**Choosing a trace approach:**

- Pick **OTel-native emit** (`agent-framework` model: `OtelAttr` enum + `_create_otlp_exporters` dual protocol at `observability.py:176-314, 365-484`) if traces must survive vendor churn, if you need Honeycomb/Jaeger/Datadog interchange, or if compliance requires `OTEL_EXPORTER_OTLP_*` fidelity (`PROTOCOL`, `HEADERS`, `METRICS/LOGS_ENDPOINT`). Gate on `InstrumentationSettings(version=6)` and publish the version.
- Pick **dual-ingest platform** (Langfuse model: Zod envelope at `ingestion/types.ts:395-755` + OTLP route at `web/.../otel/v1/traces/index.ts:78-114`) if you own the query path and want to accept arbitrary OTel while keeping app-SDK ergonomics — accept the outbound-mapping cost.
- Pick **pluggable seam** (OpenAI SDK `TracingProcessor` at `processor_interface.py:9-142` + `SynchronousMultiTracingProcessor` at `provider.py:93`) if you must ship many backends fast and can tolerate custom translation plus lack of standard `version` field.

**Choosing an eval dataset approach:**

- Pick **typed file dataset** (Pydantic AI `Dataset.to_file` at `dataset.py:556-634` + `NamedSpec` at `_spec.py:50-111`) if your evaluators are Python logic (LLM-as-judge, `SpanTree`) and you need type safety plus `$schema` validation — accept that consumers must supply `custom_evaluator_types`.
- Pick **generic versioned dataset** (Langfuse `input: unknown` + `inputSchema` at `datasets.yml:79-84`, temporal queries at `dataset-items.yml:24-40`) if datasets are shared across teams/tools (Hugging Face, LangSmith, Evidently) — accept weaker type guarantees and `z.any()` looseness (`ingestion/types.ts:390-393` CPU warning).
- Delay investing in dataset infrastructure (LangGraph/OpenHands/OpenAI SDK absent pattern) until you have reproducible eval snapshots; do not build a registry for ephemeral sweeps.

**Choosing a prompt approach:**

- Pick **filesystem + standard engine** (OpenHands `FlexibleFileSystemLoader` or Pydantic AI `TemplateStr`) if prompts are authored by engineers and must be copy-portable — explicitly choose Jinja2 vs Handlebars and commit `v._source` (`template.py:111`).
- Pick **registry + composition** (Langfuse `PromptService` + `@@@` tags at `index.ts:234-379`) if non-engineers edit prompts, you need `production` label routing, or composition reuse — enforce one compiler (see Tips) and validate `template_engine` field.
- Avoid **hosted-reference-only** (OpenAI `ResponsePromptParam` at `prompts.py:23-34`) unless you are OpenAI-only; it fails closed on other providers (`openai_chatcompletions.py:85-102` `UserError`).

**Choosing a tool-schema approach:**

- Default to **canonical + deferred transform** (generate once via `model_json_schema()`, transform at build via `JsonSchemaTransformer.walk` at `_json_schema.py:59`). If you need MCP + Chat + Responses parity, copy OpenHands triple adapters (`tool/tool.py:379-498`); if you need 4+ providers, copy `agent-framework` per-client translators (`openai/_chat_client.py:890-935` etc.). Add `strict_json_schema=False` escape hatch for open-object schemas.

## Practical Tips

**Patterns to copy:**

- **Generate JSON Schema once, translate per-provider at the edge.** Keep `ToolDefinition.parameters_json_schema: ObjectJsonSchema` canonical (`tools.py:544-554`, `_tools.py:784-826`) and apply `JsonSchemaTransformer` rewrites (`_json_schema.py:59`) or explicit `to_mcp_tool`/`to_openai_tool`/`to_responses_tool` adapters only when building the request. Add snapshot tests per adapter (Langfuse `fetchLLMCompletion.ts:469-710` has six branches — test each).
- **Guard telemetry with spec-only types and versioning.** Isolate `gen_ai.*` attributes in `_otel_messages.py` (`_otel_messages.py:1-4`) behind the `AGENTS.md:16` rule, version instrumentation (`version: Literal[2,3,4,5,6]` at `models/instrumented.py:78-79`), and emit both `gen_ai.provider.name` + deprecated `gen_ai.system` (`_instrumentation.py:284-303`) for backward compat.
- **Make histories round-trippable via `TypeAdapter` + injectables.** Use `ModelMessagesTypeAdapter = TypeAdapter(list[ModelMessage], ser_json_bytes='base64')` (`messages.py:2769-2772`) for `all_messages` (`run.py:176`, `result.py:556`) and `SerializationMixin.from_dict(dependencies=...)` (`_serialization.py:392-560`) to avoid persisting callables. Always run `sanitize_messages` (`messages.py:2954`) and `redact_binary_content` (`_instrumentation.py:141-168`) before export.
- **Use bitemporal/epoch versioning for datasets and prompts.** Langfuse `validFrom`/`validTo` (`repositories/dataset-items.ts:1082-1158`) and `prompt_cache_epoch:{projectId}` + `NX` init (`PromptService/index.ts:201-232`) give reproducible snapshots without key deletion races.
- **Preserve dual tool-call IDs.** OpenHands `MessageToolCall.id` + `responses_item_id` (`llm/message.py:24-40`) through both `to_chat_dict()`/`to_responses_dict()` keeps prefix-cache hits across replay — copy this if you support both Completions and Responses.

**Patterns to avoid or delay:**

- **Do not hand-roll two compilers for the same `{{var}}` syntax.** Langfuse `compileTemplateString` (preserve) vs `compileChatMessages.replaceTextVariables` (throw, with unescaped `RegExp` at `compileChatMessages.ts:28`) diverges silently. Delay a second compiler until you add a `strict` flag or `{compiled, missing: string[]}` return.
- **Do not name env vars `OTEL_*` unless you honor the OTel exporter contract.** OpenHands `maybe_init_laminar()` (`observability/laminar.py:57-112`) reading `OTEL_EXPORTER_OTLP_*` then importing only `lmnr` misleads operators; Pydantic AI does not — wire to `TracerProvider` generically.
- **Do not ship `z.any()` for `input`/`output` at ingestion without downstream validation.** Langfuse `ingestion/types.ts:390-393` trades CPU for looseness; malformed arrays pass Zod and break ClickHouse queries. Validate at dataset write time.
- **Do not treat prompt strings as portable artifacts without declaring `template_engine` and variable schema.** All six systems omit this; start with `prompt.template_engine: handlebars|jinja|mustache` and a `variables_json_schema` before building a registry.

**Caution-phase guidance:**

- If trace attribute names start diverging per provider (`provider_details` blob at `messages.py:1898-1916` carrying `callable` merge deltas that serialize as `null`), add a sanitized `export(sanitize=true)` mode now rather than after consumers depend on opaque fields.
- If dataset size crosses CSV export thresholds, add `listDatasetVersions` + `?format=jsonl|hf` translators before the S3 export (`CoreDataS3ExportQueue` at `queues.ts:366`) becomes the only bulk path.

## Anti-Patterns / Caution Signs

- **OTEL env-var masquerade:** Declaring `_OBSERVABILITY_ENV_KEYS = {OTEL_EXPORTER_OTLP_TRACES_ENDPOINT, ...}` (`observability/laminar.py:25-30`) while `maybe_init_laminar()` branches only to `lmnr.Laminar` (`observability/laminar.py:90-112`) — indicates trace portability claims are config-level only. Watch for `no opentelemetry.trace import` despite `opentelemetry-api==1.39.1` in lockfile (`pyproject.toml:64-65`).

- **Missing export `version` field:** OpenAI SDK `TraceImpl.export()` (`traces.py:568-575`) emits `{"object":"trace"}` without `version` — consumers cannot detect breaking dict changes during migration. Similarly langgraph debug payloads (`types.py:142-219` `TaskPayload`, `types.py:262-351` `StreamPart`) have no OTLP mapping.

- **Two-compiler divergence + RegExp injection:** `new RegExp(\`{{\\s*${varName}\\s*}}\`)` with unescaped `varName` (`compileChatMessages.ts:28`) safe only via `isValidVariableName` filter (`utils/stringChecks.ts:20-22`). Reuse with raw user keys throw `Invalid regular expression`. Additionally `String(value)` (`utilities.ts:13`) vs `parseUnknownToString` (`evalRuntime.ts:18-22`) render `[object Object]` differently per call site.

- **Silent trace drops:** `BatchTraceProcessor` `queue.Full` (`processors.py:597-621`) drops with single warning; LangGraph `trace=False` on internal helpers (`pregel/_read.py:48`, `pregel/_write.py:64`, `graph/_branch.py:134`) silently hides child runs; instrumented `include_content=false` redaction walking nested `ToolReturn` (`_instrumentation.py:170`) may still leak if `include_binary_content` flips.

- **Circular schema collapse:** `_process_schema_node` shallow fallback to `{"type":"object"}` (`schema.py:64-67, 114-120`) for recursive tools loses type fidelity in `to_mcp_schema` without error — tree/graph tools silently degrade.

- **Sticky observability + console leak:** `disable_instrumentation()` `_user_disabled` surviving `enable_instrumentation` without `force=True` (`observability.py:829-948`) is correct but surprising; `enable_sensitive_data=True` + `enable_console_exporters=True` dumps `gen_ai.input.messages`/`tool.arguments` to stdout (`observability.py:864-869`).

- **Unversioned prompt registry + implicit variables:** `CreatePromptSchema` validates structure not variable syntax (`features/prompts/types.ts:28-61`), so `{{  bad-var }}` can be stored and surfaced only as later lint/preserve (`utilities.ts:15` try/catch returning original template). OpenHands `system_prompt.j2:79-88` expects `security_policy_filename`/`llm_security_analyzer` without schema — migration misses variables silently.

## Notable Absences

- **Zero dedicated migration tooling across all six sources.** No `export_traces --format otlp|opentelemetry-json|parquet`, no `import_dataset --from langsmith|hf`, no `migrate_prompts --from langchain --to ...` CLI. The closest are generic `to_dict`/`from_dict` (`_serialization.py:137-588`), Langfuse public REST (`GET /prompts`, `GET /dataset-items`), and OpenHands zip `export_conversation` (`app_conversation_service.py:160-189`, `live_status_app_conversation_service.py:2845-2915`) — all data-plane, none cross-platform converters. Pydantic AI notes `TODO(v3): default to version 6` (`models/instrumented.py:157`) rather than a migration shim.

- **No prompt standard IR.** Despite Jinja2, Handlebars, Mustache options, none adopts `dotprompt` or `PromptTemplate {template_engine, variables_json_schema, prompt_version}` as a portable envelope; langfuse `config: jsonSchema` (`prompts.yml:114`) is opaque, and registry `provider: OpenAI` (`OpenAI.yaml:1-28`) is provider-locked.

- **No evaluator decoupling from code.** Only Langfuse `unknown` JSON and Pydantic AI data side are data-only; evaluators remain `NamedSpec` registry entries (`_spec.py:50-111`), `@evaluator` callables (`_evaluation.py:1284-1352`), or `CriticBase` plugins (`critic/base.py:65-83`). No source ships a declarative evaluator spec (e.g., `llm-as-judge: {rubric, model}` as JSON that is executable without the original Python).

- **No trace-file persistence for harnesses.** `FileHistoryProvider`/`InMemoryHistoryProvider` (`_sessions.py:96-120`) store `Message` not OTel spans; `Telemetry` writes `ModelResponse.model_dump` JSON to local files (`llm/utils/telemetry.py:288-402`) not OTLP; OTEL file exporters are unconfigured despite `opentelemetry-exporter-otlp-proto-grpc==1.39.1` in lockfiles.

- **No cross-provider tool schema conformance tests.** No source asserts `openai` and `anthropic` receive logically identical tool definitions from the same canonical source — `_should_bind_tools` (`chat_agent_executor.py:202-210`) covers only two providers, and provider `modelParameters` (`ingestion/types.ts:318-324`) leaks opaque options.

## Per-Source Notes

**agent-framework (5/10)** — Best OTel + tool story, weakest prompt/eval dataset story. `OtelAttr` (`observability.py:176-314`) and `_create_otlp_exporters` HTTP base-url `/v1/{signal}` handling (`observability.py:606-610`) are reference-grade for harness authors. Prompts have no template engine; declarative YAML (`OpenAI.yaml:1-28`) is not a registry.

**langfuse (6/10)** — Platform-grade dataset/prompt persistence; trace portability is ingress-strong, storage-locked. Copy `inputSchema`/`expectedOutputSchema` optional JSON Schema (`datasets.yml:79-84`) plus `createManyDatasetItems` compile-once `DatasetItemValidator` (3800x speedup at `repositories/dataset-items.ts:537-665` preserving `itemIndex`) and `PromptService` epoch caching (`PromptService/index.ts:177-232`). Budget for OTLP→Langfuse-envelope outbound mapping before claiming zero-copy migration.

**langgraph (3/10)** — Coupled by design to LangSmith for traces (`_internal/_runnable.py:69-102, 400-426, 651-692`), unserializable prompts (`chat_agent_executor.py:121-126` `Callable` union), and external datasets (`redirects.json:123`). Its only portable pattern is checkpoint state versioning (`pregel/main.py:1135-1143` `TASKS` channel migration, `JsonPlusSerializer` at `checkpoint/serde/jsonplus.py:82-131` with `allowed_msgpack_modules`) — useful for state, not for 19.02. Treat LangGraph traces as non-migratable without collector rewrite.

**openai-agents-sdk (3/10)** — Most explicit pluggability, least out-of-box portability. `TracingProcessor`/`TraceProvider`/`BatchTraceProcessor` (`processor_interface.py:9-142`, `provider.py:222-298`, `processors.py:541-718`) plus ~27 community adapters (`docs/tracing.md:196-226`) prove the seam works, but wire format is `{"object":"trace.span"}` proprietary (`spans.py:396-423`) with `strict` tool schemas (`strict_schema.py:115-405`, `tool.py:452-599`) that reject open objects per `additionalProperties:false`. Use it if you will write the exporter; otherwise expect rewrites.

**openhands (5/10)** — Strong tool multi-target, weak trace/eval/prompt registry. `Schema` dual direction (`schema.py:201-239`) + `ToolDefinition` triple adapters (`tool/tool.py:379-498`) plus `MessageToolCall` dual-ID preservation (`llm/message.py:24-119`) are exemplary for MCP↔OpenAI interop. Discount `OTEL_*` portability — observability is `lmnr` (`observability/laminar.py:57-112, 231-266`); eval is `CriticBase` live only (`critic/base.py:65-83`); export is `event-*.json` zip (`conversation/persistence_const.py:4-9`, `live_status_app_conversation_service.py:2845-2915`) not OTel.

**pydantic-ai (6/10)** — Most disciplined OTel fidelity; best dataset file ergonomics with a code-bound tail. Copy spec-guard (`_otel_messages.py:1`, `AGENTS.md:16`), versioned instrumentation (`models/instrumented.py:78-79, 154-164`), `ModelMessagesTypeAdapter` round-trip (`messages.py:2769-2772`), and `Dataset.to_file` with `$schema` sidecar (`dataset.py:747-794`). Plan to vendor `custom_evaluator_types` and ship `pydantic-handlebars` if migrating `TemplateStr` prompts (`template.py:16-49`), and sanitize `provider_details` (`messages.py:1898-1916`) before cross-provider moves.
