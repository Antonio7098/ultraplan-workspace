## Executive Summary

The eleven sources span five orders of magnitude of boundary rigor. At the disciplined end (agent-framework, pydantic-ai, opa, openai-agents-sdk, temporal), boundaries are explicit, defended by both social convention *and* mechanical safeguards (compiler-enforced `internal/` visibility, dependency-bound validators, curated `__all__` lists, lazy-facade re-exports). In the middle (langfuse, langgraph, openhands), the model is sound but enforcement is partial: declarations describe intent better than reality at one or two seams. At the fragile end (letta), the layering exists as directory taxonomy but is violated in practice. The empty `reports` source represents a pipeline gap, not an architectural verdict.

The dimension's litmus question — *"Can you use the tool system without pulling in the entire runtime?"* — is answered differently across sources, and the difference tracks cleanly with packaging strategy:

- **Yes, cleanly** when the tool layer is a separate distribution with a thin dep on core: agent-framework (`agent-framework-tools` with only `agent-framework-core`), pydantic-ai (`pydantic-graph` standalone, `pydantic-ai-slim` lean).
- **Yes, with caveats** when tools are extracted but depend on private internals: langgraph's `langgraph-prebuilt` (publishes a wheel that cannot actually be used alone), opa's `v1/rego` (lean core, but wasm planner leaks transitively), temporal's `chasm` library (top-level placement but imports `service/history/tasks`).
- **No, partly by design** when the tool contract lives inside the framework wheel: crewai (`BaseTool` in `crewai`, tools extra pulls chromadb/lancedb/openai), letta (`letta.schemas.tool` transitively pulls llm_api+orm+services), openhands (in-repo `app_server` modules assume full server context).
- **Not applicable** to the empty `reports` source.

## Core Thesis

**Boundary quality is determined by whether separation is enforced at a level the compiler or build system can verify, not by how many packages exist.** Sources that rely on packaging alone (multiple wheel distributions) score no higher than sources that rely on internal layering plus `internal/` visibility — what matters is whether the boundary holds when a contributor is inattentive. The strongest sources (agent-framework, pydantic-ai) combine *both* multiple packages *and* per-package internal layering with tests; the weakest (letta) have neither. The middle band (langfuse, langgraph, openhands) gets most of the way with package boundaries and lint, then loses ground at one or two seams where the team's stated model diverges from actual code.

## Approach Models

Sources cluster into four approach models for handling package and module boundaries:

### Cluster A: Multi-package monorepo with per-package internal layering

**Sources**: agent-framework (8), pydantic-ai (8)

Both ship multiple independently versioned distributions *and* discipline each package's internal layout (abstractions/core → implementations → hosting). Boundaries are defended at two levels: the package manager refuses to resolve upward references at install time, and per-package conventions (`__all__`, underscore-prefixed private modules, curated barrels) protect the public surface. Both run CI matrices that exercise each package's tests in isolation against declared-only deps.

### Cluster B: Multi-package monorepo with convention-only enforcement

**Sources**: crewai (5), langfuse (6), langgraph (6), openhands (6)

Package boundaries exist and are documented, but enforcement is weak: no import-linter, no automated cycle detection, no cross-package boundary tests. The graph may even contain undeclared cycles (langgraph prebuilt↔core, openhands event↔app_conversation↔sandbox) that are only held together by lazy imports. Internal layering within each package is often disciplined, but the seams between packages are where these sources lose points.

### Cluster C: Single-package or single-module with compiler-enforced or curated boundaries

**Sources**: opa (7), openai-agents-sdk (7), temporal (7)

These accept the convenience of a single distribution (one wheel or one Go module) and compensate with strong *internal* boundary mechanisms: Go's `internal/` path visibility (opa, temporal), explicit private zones (`run_internal/` in openai-agents-sdk), curated `__all__` lists, and lazy optional-dependency loading. Public API lives in separate modules (opa's API in `v1/`, temporal's in `go.temporal.io/api`/`sdk`). The tradeoff is real: cycles within the module are possible (opa's five bidirectional mid-stack pairs) and there is no machine-enforced dep direction rule.

### Cluster D: Single-package with no enforcement

**Sources**: letta (4)

The conceptual layering is legible from directory names alone (`schemas/`, `orm/`, `services/`, `server/`), but nothing prevents upward imports. Static analysis showed bidirectional edges at nearly every layer pair, with ~627 deferred function-level imports holding cycles together. The product surface is the HTTP API and external SDK, not the Python library.

### Cluster E: Empty / placeholder

**Sources**: reports (1)

Contains zero files; this is a pipeline gap, not an architectural verdict.

## Pattern Catalog

### P1. Abstractions-first layering (Recurs in: agent-framework, opa, pydantic-ai)

**Problem**: prevent evaluation/loop logic from coupling to provider implementations; let providers and hosting be replaced independently.

**Mechanism**: a leaf package with near-zero dependencies defines the contract; all implementations program against those interfaces. agent-framework's `Microsoft.Agents.AI.Abstractions` references only `Microsoft.Extensions.AI.Abstractions` (`dotnet/src/Microsoft.Agents.AI.Abstractions/Microsoft.Agents.AI.Abstractions.csproj:33`); opa's `v1/ast` and `v1/topdown` form the core, with `v1/rego` and `v1/sdk` as user-facing compositions; pydantic-ai's `pydantic-graph` package has no pydantic-ai import anywhere except a docstring comment (`pydantic_graph/pydantic_graph/_utils.py:116-122`).

**Why it works**: the abstractions package is consumed by *everyone*, so any temptation to add a convenience that imports a concrete provider is immediately visible. The compiler/build step refuses to resolve the convenience.

**When to copy**: any system where multiple implementations (providers, hosts, engines) must be pluggable. Worth the cost when at least two implementations are expected within the first year.

**When it is overkill**: single-tenant, single-vendor tools where provider pluggability is hypothetical. A simple interface in one file is sufficient.

### P2. Lazy namespace facades with actionable errors (Recurs in: agent-framework, crewai, openai-agents-sdk, pydantic-ai)

**Problem**: keep the top-level package importable without pulling every optional dep, while preserving stable import paths.

**Mechanism**: agent-framework's `azure/__init__.py` exposes a `_IMPORTS: dict[str, tuple[str, str]]` map and a module `__getattr__` that raises `ModuleNotFoundError` naming the pip package to install (`python/packages/core/agent_framework/azure/__init__.py:11-33`). openai-agents-sdk applies the same shape across seven optional providers (`src/agents/extensions/sandbox/__init__.py:1-209`) and asserts the error messages name the correct extra in tests (`tests/extensions/memory/test_memory_imports.py:1-154`). pydantic-ai's `infer_provider_class` and `infer_model` lazily import each provider module inside an `if model_kind == ...` branch (`pydantic_ai_slim/pydantic_ai/providers/__init__.py:147-267`).

**Why it works**: import-time cost is paid only for what the user actually uses; error messages tell them exactly which extra to install. The `__getattr__` indirection makes the failing attribute access the surface that surfaces the missing dep, so the error happens at the moment the user calls a feature, not at the top-level import.

**When to copy**: any package with several heavy optional integrations (provider SDKs, vector DB clients, cloud storage backends). Particularly valuable when the core experience must remain importable in test harnesses or minimal Docker images.

**When it is overkill**: a system with two or fewer optional integrations; a single `try/except ImportError` at the call site is enough.

### P3. Explicit private zone with docstring/discoverability markers (Recurs in: openai-agents-sdk, langgraph, opa, agent-framework)

**Problem**: signal that certain symbols are unstable without breaking the package layout.

**Mechanism**: openai-agents-sdk reserves `src/agents/run_internal/` as the sole sanctioned private zone, marks every module with a "internal and not part of the public SDK" docstring (`src/agents/run_internal/run_loop.py:1-3`), excludes it from the MkDocs nav (verified by grep on `mkdocs.yml`), and codifies the rule in `AGENTS.md:20-24`. langgraph mirrors this with `langgraph._internal` and a stability disclaimer (`libs/langgraph/langgraph/_internal/__init__.py:1-4`). agent-framework uses `[Experimental("MAAI001")]` on .NET and `ExperimentalFeature` enums on Python (`python/packages/core/agent_framework/_feature_stage.py:55-70`); opa uses uniform `// Deprecated:` doc comments on 34/34 v0 shim packages with staticcheck configured to keep deprecation noise out of `v1/`.

**Why it works**: contributors can recognize the zone instantly (folder name, decorator, or docstring), and consumers can grep for "internal" or `Deprecated` to know what is unstable. The cost is purely social.

**When to copy**: any project with internal helpers that need to be shareable across sub-modules but should not become de-facto public API.

**When it is overkill**: small libraries with no shared internals; the natural package structure already signals visibility.

### P4. Compiler-enforced `internal/` visibility (Recurs in: opa, temporal)

**Problem**: prevent external consumers from depending on shared kernel code without maintaining a separate package.

**Mechanism**: Go's `internal/` path rule prevents any import from outside the parent module's subtree. opa uses it for 38 shared subpackages (`internal/rego/opa/engine.go:51` unreachable externally); temporal uses it for `proto/internal` and `temporaltest/internal` only. Both treat it as a strong boundary but use it sparingly — temporal notes "near-zero use of Go's `internal/` visibility mechanism outside two directories" (`temporal`, "Evidence" table).

**Why it works**: the compiler refuses the import at build time. There is no way to "accidentally" expose internal code because external code cannot reference it.

**When to copy**: any Go module where shared kernel code should be invisible to embedders; any Python project willing to use a `_private/` naming convention and accept that it is social.

**When it is overkill**: small Go programs with no embedding story; the package-level visibility already enforces a tight boundary.

### P5. Boundary identity tests (Recurs in: agent-framework; partially in openai-agents-sdk)

**Problem**: prove that a facade actually delegates to the real package object rather than silently shadowing it.

**Mechanism**: agent-framework's `tests/core/test_azure_namespace.py:7-9` asserts `assert azure.CosmosHistoryProvider is CosmosHistoryProvider`, proving the facade re-exports the real distribution object identity. openai-agents-sdk's `tests/test_exception_exports.py:1-30` asserts every `AgentsException` subclass is re-exported from the top level.

**Why it works**: a failed identity test catches the exact failure mode that lazy facades are meant to prevent — accidental copies, stale re-exports, or drifted signatures.

**When to copy**: any project with multiple facade/shim layers. Especially valuable when facades are hand-maintained (agent-framework's ADR 0008 explicitly accepts the maintenance cost).

**When it is overkill**: when facades are auto-generated; the generator is the test.

### P6. Graph-driven dependency tooling (agent-framework)

**Problem**: detect declared-dependency drift and runtime resolution failures across many packages.

**Mechanism**: agent-framework's `validate_dependency_bounds.py` parses every workspace `pyproject.toml` into an internal graph (`_build_internal_graph` at `_dependency_bounds_upper_impl.py:551-574`), then runs each package's test+pyright suite at both `lowest-direct` and `highest` resolutions in isolated uv environments (`validate_dependency_bounds.py:243-244`). The tool hard-fails the workspace if any suite breaks under strict resolution extremes.

**Why it works**: it converts dependency contracts into an executable invariant. Each package's lower bound must match its declared need; each upper bound must hold against current ecosystem versions.

**When to copy**: any Python monorepo with more than ~5 packages or with regular coordinated releases. The tool is non-trivial to write but cheap to maintain.

**When it is overkill**: small Python projects with one or two packages.

### P7. DI/composition root with nested graphs (Recurs in: openhands, temporal)

**Problem**: decouple service wiring from service implementation without a circular import.

**Mechanism**: temporal uses uber-fx nested DI graphs (`temporal/fx.go:498-602`) where each service exposes an `fx.Options` module consumed only by the top-level assembly. Services never import each other directly; inter-service calls go through `client.Factory` (`client/clientfactory.go:28-50`). openhands uses a similar pattern with `AppServerConfig` and `Injector[T]` (`openhands/app_server/services/injector.py:13-40`), with env-driven implementation selection through `get_impl(cls, impl_name)` (`openhands/app_server/utils/import_utils.py:43-78`).

**Why it works**: services depend on abstract types, not concrete implementations. Swapping a database or sandbox requires only a config change, not a code change. The DI graph fails loudly at startup if a binding is missing.

**When to copy**: any system with multiple deployable configurations (OSS/enterprise, lite/full, dev/prod) that share most services but differ in a few. The overhead is real — temporal's authors flag the `GetCommonServiceOptions` workaround as "not ideal" (`temporal/fx.go:386-393`) — but the alternative is reach-in coupling.

**When it is overkill**: monolithic single-purpose services with one deployment configuration.

### P8. PEP 420 implicit namespace composition (langgraph)

**Problem**: let several separately distributed libraries expose one coherent import tree without a top-level `__init__.py`.

**Mechanism**: langgraph ships eight libraries that all contribute subtrees under `langgraph.*` (no root `__init__.py` in any of the seven Python libs). `from langgraph.checkpoint import X` resolves to whichever wheel is installed.

**Why it works**: libraries can evolve and release independently while presenting one coherent API surface. Users see `langgraph.checkpoint`, `langgraph.prebuilt`, `langgraph_sdk` as siblings.

**When to copy**: multi-package Python libraries where the runtime, persistence layer, and SDK want to share a namespace but evolve independently.

**When it is risky**: nothing prevents one lib from writing into another's subtree (langgraph's prebuilt reaches into core's private `_internal`). This is exactly how the prebuilt↔core cycle was created.

### P9. Curated `__all__` at every public module (Recurs in: openai-agents-sdk, pydantic-ai, crewai, langgraph)

**Problem**: make the public surface greppable, diffable, and reviewable.

**Mechanism**: openai-agents-sdk's top-level `agents/__init__.py` enumerates 240+ symbols across section comments (`src/agents/__init__.py:340-585`). pydantic-ai's slim package re-exports 100+ symbols in the same shape (`pydantic_ai_slim/pydantic_ai/__init__.py:166-341`). langgraph's `graph/__init__.py:5-12`, `pregel/__init__.py:2`, `prebuilt/__init__.py:14-23`, `stream/__init__.py:28-44`, and `sdk-py/__init__.py:1-7` all carry curated lists.

**Why it works**: an `__all__` list is a single source of truth for "what is public". A reviewer can read it and ask "should this be public?"; a downstream user can `from package import *` and get only the curated set.

**When to copy**: any library with more than ~20 public symbols. Worth the maintenance cost when the surface is reviewed as part of every PR.

**When it is overkill**: tiny libraries with fewer than ~10 public symbols; the implicit namespace already serves.

### P10. Versioned deprecation ladder (Recurs in: langgraph, pydantic-ai, opa)

**Problem**: give consumers machine-readable migration signals rather than free-form warnings.

**Mechanism**: langgraph defines `LangGraphDeprecatedSinceV05/V10/V11` warning classes each encoding `since` and `expected_removal` versions (`libs/langgraph/langgraph/warnings.py:51-69`). pydantic-ai exposes `PydanticAIDeprecationWarning` and uses module-level `__getattr__` to route old names to new ones (`pydantic_ai_slim/pydantic_ai/__init__.py:348-370`). opa applies 91 `Deprecated:` markers on individual symbols inside v1 packages (`v1/ast/builtins.go:332`).

**Why it works**: consumers can write code that switches behavior based on deprecation version. A future major release can remove all symbols marked for v2 in one PR.

**When to copy**: any library expecting API evolution over years. Especially valuable when the library has a stable contract to maintain across major versions.

### P11. Per-package CI isolation (Recurs in: agent-framework, langgraph, pydantic-ai)

**Problem**: prove each package installs and tests independently.

**Mechanism**: agent-framework's dependency-bounds validator runs each package's test+pyright suite in an isolated uv env with only declared deps (`validate_dependency_bounds.py:153-175`). langgraph's CI matrix runs lint+tests per lib dir with `uv sync --frozen --group test --no-dev` across Python 3.10–3.14, plus a clean-worktree assertion (`.github/workflows/_test.yml:45,50,53-56`).

**Why it works**: a package that fails in isolation has undeclared dependencies or hidden cross-package coupling. The matrix makes this visible per release.

**When to copy**: any multi-package monorepo with independently versioned distributions.

### P12. Conformance library instead of trust (langgraph)

**Problem**: third-party implementations of a contract should be testable for conformance.

**Mechanism**: langgraph's `langgraph-checkpoint-conformance` package exposes a `validate()` function that programmatically checks any `BaseCheckpointSaver` subclass against required and auto-detected extended capabilities (`libs/checkpoint-conformance/langgraph/checkpoint/conformance/validate.py:45`).

**Why it works**: third-party checkpointer authors run the suite locally; CI catches drift. The contract becomes executable instead of documentary.

**When to copy**: any system with a stable storage/serialization/plugin contract and multiple expected implementations. Especially valuable when community extensions matter.

## Key Differences

### Why some sources have stronger boundaries than others

**Sources with the cleanest boundaries (agent-framework, pydantic-ai, opa, openai-agents-sdk) all share three properties**: (1) they document the boundary model in a single file (ADR, AGENTS.md, or dimension spec), (2) they have at least one *mechanical* safeguard (compiler-enforced `internal/`, dependency-bounds validator, curated `__all__` enforced by tests), and (3) they run per-package CI isolation. The mechanical safeguard is the load-bearing element — without it, drift accumulates silently between documentation and code.

**Sources with mid-tier boundaries (crewai, langfuse, langgraph, openhands, letta) share a different shape**: they have *one* of these properties — usually the documentation or the package split — but not all three. langfuse documents well but uses Next.js server/client stripping rather than a `server-only` lint guard; crewai has a six-package split but no layering tests; langgraph has per-lib CI but the prebuilt↔core cycle slipped past review. Each mid-tier source fails at a *specific* point, not at the model itself.

**opa and temporal** sit at the boundary of cluster B/C: they are Go modules with no package-level boundaries (one `go.mod`), but they use Go's `internal/` and `temporaltest/internal` to achieve compiler-enforced visibility on the things that matter. They score 7 despite "only" being one module because the boundaries that matter most (public API surface, test harness) are mechanically protected.

### Divergence drivers

Sources diverge in boundary quality for reasons that are not quality differences but product-shape differences:

1. **Public-API-distributed libraries vs. application monoliths**. OPA and temporal are server-grade Go modules whose public API is in *external* modules (`go.temporal.io/api`, `go.temporal.io/sdk`). This shifts the boundary problem outward; the in-repo module can be looser because it is not the contract surface. Letta, by contrast, is an application — its "public surface" is the HTTP API and external client SDK, not the Python library — so the in-repo Python can be loose without breaking consumers.

2. **Single-tenant vs. multi-tenant portability**. agent-framework, pydantic-ai, and openai-agents-sdk ship to thousands of consumers who must mix-and-match providers, memory backends, and toolsets. The boundary discipline is paid for by consumer portability. Langfuse is internally consumed by its own web+worker pair; the cost of looser boundaries is internal refactoring pain rather than user-facing breakage.

3. **Library vs. application shape**. Application-shaped sources (letta, openhands) have weaker internal layering because the natural unit of deployment is the process, not the module. Library-shaped sources (agent-framework, pydantic-ai, openai-agents-sdk) have stronger layering because the natural unit is the package the user imports.

4. **Maturity**. Temporal's rating is held below 8 by a shared-kernel inversion (`common/persistence → service/history/tasks`) that has accumulated incrementally as the codebase grew. This is a *trajectory* problem: even sources that started with discipline can erode without mechanical enforcement.

5. **Stack constraints**. Python lacks `internal/` visibility; sources compensate with `_internal` naming conventions and tests (openai-agents-sdk's `run_internal/`, langgraph's `_internal/`). Go has it natively and uses it (opa, temporal). JavaScript/TypeScript has no native equivalent and relies on `package.json` `exports` maps (langfuse) or barrel conventions.

## Tradeoffs

### T1. Multi-package monorepo vs. single-package

**Benefit (multi)**: compile-time / install-time enforcement of layer boundaries; independent versioning; can ship a lean core with optional extras.

**Cost (multi)**: release coordination overhead (lockstep pins in crewai, exact pins in openhands `pyproject.toml:249-251`); facade maintenance (agent-framework's ADR 0008 explicitly accepts the cost); risk of undeclared cycles (langgraph prebuilt↔core, openhands `app_server` subpackages).

**Best fit**: libraries consumed by many users with mixed needs (agent-framework, pydantic-ai).

**Failure mode**: facade drift, version-skew bugs across packages, lockstep releases that defeat the purpose of separate versioning.

**Alternative**: single package with curated `__all__` and explicit private zones (openai-agents-sdk) — simpler operations, weaker enforcement.

### T2. Convention vs. mechanical enforcement

**Benefit (mechanical)**: drift fails at build/CI time, not in review.

**Cost (mechanical)**: tooling overhead, false positives on legitimate cross-package references, need for curated allowlists.

**Best fit**: any codebase with multiple contributors and a long expected lifetime.

**Failure mode (convention-only)**: langfuse's vestigial `@langfuse/ee` package contradicts directory reality and no one noticed; langgraph's prebuilt/core cycle slipped past review because no import-linter caught it.

**Alternative**: documented + lint-only is the practical middle ground (langfuse, openhands), but explicit `allowlist` + `denylist` rules in CI scale further.

### T3. DI/composition root vs. direct wiring

**Benefit (DI)**: services depend on abstractions; concrete implementations are swappable via config; inter-service cycles broken mechanically.

**Cost (DI)**: indirection tax; propagation workarounds (temporal's `GetCommonServiceOptions`); config sprawl.

**Best fit**: systems with multiple deployment configurations or plugin architectures (temporal, openhands).

**Failure mode**: workaround proliferation, stringly-typed config that bypasses type checking (openhands's `OPENHANDS_CONFIG_CLS`).

**Alternative**: lean on package boundaries alone; accept the cross-package import cost (most Python sources).

### T4. Strict layering vs. lazy import cycle-breakers

**Benefit (lazy imports)**: ships faster; doesn't require restructuring when cross-layer reach-ins are needed.

**Cost (lazy imports)**: obscures the real dependency graph; defers breakage from import time to call time; encourages additional cycles (letta's 627 deferred function-level imports).

**Best fit**: prototyping and small projects where the cycle count is bounded.

**Failure mode**: import-order sensitivity, partial-init bugs at runtime (letta explicitly cites this as the dominant failure mode).

**Alternative**: cycle-breaking by extracting a leaf subpackage (opa's `loader/filter`, `loader/extension`).

### T5. Comprehensive `__all__` curation vs. implicit exports

**Benefit (`__all__`)**: single source of truth for public surface; greppable; reviewer-friendly.

**Cost (`__all__`)**: maintenance overhead; risk of drift between actual exports and the list (mitigated by snapshot tests in pydantic-ai's spirit).

**Best fit**: libraries with large or evolving public surfaces (openai-agents-sdk's 240+ symbols, pydantic-ai's 100+).

**Alternative**: implicit exports work for small surfaces or for libraries that maintain publicness through other means (langfuse's `exports` map).

### T6. `internal/` vs. `_private` naming

**Benefit (`internal/` in Go)**: compiler-enforced, zero social cost.

**Cost (`internal/` in Go)**: cannot be partially opened; must use sibling packages with public visibility for any cross-team need.

**Best fit (Go)**: any module with shared kernel code (opa, temporal).

**Best fit (Python)**: `_private` or `run_internal` naming + curated `__all__` + tests is the closest equivalent (openai-agents-sdk, langgraph).

**Alternative**: PEP 561 `py.typed` + semantic versioning + deprecation policy; relies on consumer discipline (pydantic-ai).

## Decision Guide

### When to choose a multi-package monorepo

Choose multi-package if:
- Multiple consumer profiles exist (some need only the tool layer, some need the full stack) — *agent-framework, pydantic-ai*.
- Independent versioning is real (different packages release on different cadences) — *langgraph, pydantic-ai*.
- Provider/library pluggability is a first-class requirement — *agent-framework, pydantic-ai*.

Stay single-package if:
- The product is an application with one deployment shape — *letta, openhands in-repo*.
- The "public surface" is the HTTP API, not the Python library — *letta*.
- Release coordination overhead would dominate — *crewai's lockstep pins are a sign this was a mistake*.

### When to use lazy facades

Use lazy facades (`_IMPORTS` map + module `__getattr__`) when:
- There are 5+ optional integrations with non-trivial deps — *agent-framework's azure/openai/anthropic/google/foundry, openai-agents-sdk's seven sandbox backends*.
- The core import path must remain stable even as code moves between packages — *agent-framework's ADR 0008*.
- User error messages should name the exact extra to install — *openai-agents-sdk's `tests/extensions/memory/test_memory_imports.py`*.

Use a simpler `try/except ImportError` when:
- 1–3 optional integrations exist.
- The optional path is rarely used.

### When to use a DI/composition root

Use DI/fx/DI-container composition when:
- Multiple deployment configurations exist (OSS/enterprise, lite/full) — *temporal, openhands*.
- Services must be swappable via config without code changes — *openhands's `get_impl(SettingsStore, server_config.settings_store_class)`*.
- Inter-service cycles would otherwise make the build impossible — *temporal solves service↔service cycles through `client.Factory`*.

Skip DI when:
- Wiring is straightforward and one-shot.
- The overhead of explaining DI to new contributors exceeds the boundary benefit.

### When to use an abstractions-only leaf package

Use an abstractions-only package when:
- More than two implementations of the contract are expected within a year — *agent-framework's `Microsoft.Agents.AI.Abstractions`, opa's `v1/ast`*.
- The contract is large enough that drift between implementations would be costly — *agent-framework's 17 consumer projects*.
- The package name itself signals the contract convention — *agent-framework's `...Abstractions` suffix following Microsoft.Extensions conventions*.

Skip when:
- The contract is one or two interfaces — *temporal's `Factory` is one interface, no separate package needed*.

## Practical Tips

### Patterns to copy

1. **Adopt a curated `__all__` discipline early.** Even a short list (`agent_framework/__init__.py:342`) is better than none. Add snapshot tests asserting the list is non-empty and matches the actual exports.

2. **Use lazy `__getattr__` for optional integrations.** A 30-line shim buys you import-time stability and user-friendly error messages for free. Wire the error messages to name the exact extra to install.

3. **Promote a "private zone" subpackage.** Whether it's `run_internal/` (openai-agents-sdk), `_internal/` (langgraph), or `internal/` (opa, temporal in Go), the single folder name signals "don't import from outside" without an import-linter rule.

4. **Document the boundary model in one file.** agent-framework's `docs/decisions/0008-python-subpackages.md`, pydantic-ai's `agent_docs/pydantic-ai-slim.md`, langfuse's `AGENTS.md:45-49` — all are short, link to specific pyproject/package.json entries, and serve as the canonical reference during review.

5. **Add boundary identity tests.** For any facade/re-export, `assert facade.X is real.X` proves no shadowing. openai-agents-sdk's exception-export test catches re-export drift.

6. **Run per-package CI isolation.** Even a single matrix dimension — does each package install + test with only declared deps? — catches undeclared cycles and hidden coupling.

7. **Use `package.json#exports` maps.** langfuse's `packages/shared/package.json:17-66` whitelists entrypoints; combined with two-tier barrels (client-safe vs server-only) it gives the same effect as Go's `internal/` for JS.

### Patterns to avoid or delay until needed

1. **Don't introduce lazy facades for one or two optional integrations.** A simple `try/except ImportError` at the call site is enough.

2. **Don't add a `core → ui → adapters` three-tier model if you only have one UI.** A single directory with one interface serves until you need a second.

3. **Don't ship exact pins (`==X.Y.Z`) for cross-package deps unless you have a coordinated release pipeline.** crewai's `==1.14.8a2` lockstep pins mean `crewai-files` cannot be consumed at a different version — defeating the purpose of separate packages. Use `>=X,<Y` ranges where the cycle is bounded.

4. **Don't build a DI composition root for a single deployable.** temporal's fx graph and openhands's `AppServerConfig` are excellent but expensive; only adopt when you have a real second configuration.

5. **Don't rely on Next.js `getServerSideProps` stripping for client/server separation.** langfuse uses this convention; it works only because of framework bundling behavior. Adopt `server-only` lint rules or a `server` barrel convention from the start.

6. **Don't tolerate cycles "held together by lazy imports".** letta's 627 deferred function-level imports are evidence of a layering problem, not a solution. Each cycle should be broken by extracting a leaf subpackage or by inverting the relationship.

7. **Don't expose a `run_internal`/`_internal` zone in the public docs.** openai-agents-sdk explicitly excludes it from MkDocs nav; this is the cheapest possible signal.

### Decision rules for choosing the main approaches

| If your project is... | Then... |
|-----------------------|---------|
| A library with many provider optional integrations | Multi-package monorepo + lazy facades + curated `__all__` (agent-framework, pydantic-ai) |
| An application with one deployment | Single package + directory taxonomy + HTTP API as contract (letta) |
| A Go service with multiple deployment configurations | Single module + `internal/` + uber-fx or similar DI (temporal) |
| A library with a stable contract to evolve over years | v0/v1 split with deprecation shims (opa) or PEP 420 implicit namespaces (langgraph) |
| A monorepo with internal services that need to swap implementations | Composition root with env-driven `get_impl` (openhands) |
| An evolving codebase that needs to migrate public surface gradually | Deprecation-as-`__getattr__` + versioned deprecation warnings (pydantic-ai, langgraph) |

## Anti-Patterns / Caution Signs

### AC1. Boundary model documented but not enforced

**Symptom**: an AGENTS.md or ADR describes the layering perfectly, but no import-linter, no depguard, no boundary test exists.

**Examples**: langfuse (`AGENTS.md:45-49` documents the DAG, but no automated cycle detection), openhands (the four `app_server` cycles are patched by lazy imports, no machine rule), crewai (six packages, zero layering tests).

**Why it fails**: drift accumulates silently. The first PR that violates the boundary passes review because "it works" — the model stays in the doc but stops matching reality.

### AC2. Undeclared circular dependency between packages

**Symptom**: package A imports B in code but doesn't declare it; package B imports A in code and *does* declare it.

**Examples**: langgraph prebuilt → core (no declaration), langgraph core → prebuilt (declared). openhands cycle between `event`, `app_conversation`, `sandbox` patched by ~55 lazy imports.

**Why it fails**: works in monorepo dev (editable installs resolve siblings), breaks for fresh consumers installing published wheels (prebuilt cannot be imported without core). The cycle is invisible to packaging tooling.

**Detection**: an import-boundary linter (import-linter for Python, depguard for Go, eslint `no-restricted-imports` for JS) configured to fail on undeclared cross-package imports.

### AC3. Single-package layering held together by 600+ deferred imports

**Symptom**: a single wheel with directory taxonomy (schemas/, orm/, services/, server/) where each layer imports upward into the layer above, broken mechanically by `from package.foo import Bar` calls inside functions instead of at module top level.

**Examples**: letta has ~627 deferred imports holding bidirectional cycles across schemas ↔ functions ↔ llm_api ↔ interfaces ↔ server.

**Why it fails**: import order becomes semantically significant; the runtime can fail with partially-initialized-module errors; the real dependency graph is invisible to tooling.

**Detection**: a count of function-level cross-layer imports; a regression test that asserts all modules import successfully in any order (rare in practice).

### AC4. Cross-package private-module import

**Symptom**: package A reaches into package B's `_underscore_prefixed` module to use a private symbol.

**Examples**: agent-framework's foundry imports `agent_framework_openai._chat_client` (`python/packages/foundry/agent_framework_foundry/_agent.py:34`); langgraph prebuilt imports `langgraph._internal._runnable` (`tool_node.py:85-89`).

**Why it fails**: any refactor of the private module breaks the consumer despite semver compatibility. The `_underscore` privacy convention is meant to prevent exactly this.

**Detection**: a lint rule banning cross-distribution imports of underscore modules; agent-framework does not have one.

### AC5. Convention-based server/client separation

**Symptom**: a Next.js (or similar framework) project relies on bundling behavior (e.g., Next.js stripping `getServerSideProps` code from client bundles) to keep server-only imports out of client code.

**Examples**: langfuse's `web/src/pages/trace/[traceId].tsx:6,21` imports `prisma` at module level, safe only because Next strips gSSP code.

**Why it fails**: a refactor that moves the call out of `getServerSideProps` would silently bundle `prisma` for the client. Detection currently comes from build errors, not rules.

**Detection**: a `server-only` import (Next.js convention) or a `no-restricted-imports` rule banning `db`/`prisma` outside `pages/api/**` and server-only directories.

### AC6. Vestigial dependency that contradicts reality

**Symptom**: a package is declared in `package.json`/`pyproject.toml` but nothing actually imports it.

**Examples**: langfuse's `web/package.json:56` declares `@langfuse/ee: workspace:*`, but `grep -r "from '@langfuse/ee'" web/src` returns nothing.

**Why it fails**: forces a useless build step, misleads newcomers about the architecture, and accumulates as dead code over time.

**Detection**: periodic dependency-usage audits; turbo's `^build` chain builds the unused package on every change.

### AC7. Stringly-typed extension point

**Symptom**: implementation selection by fully-qualified class name resolved at import or runtime via `getattr(import_module(...), ...)`.

**Examples**: openhands's `get_impl(cls, impl_name)` (`openhands/app_server/utils/import_utils.py:43-78`), validated only as a subclass check.

**Why it fails**: typo'd class names fail at startup, not at code-write time; valid-but-wrong-class matches pass validation but cause runtime confusion.

**Detection**: entry-point groups (Python's `importlib.metadata.entry_points()`) or typed config objects validated at startup with actionable errors.

### AC8. Tests reach into the private zone

**Symptom**: unit tests routinely import from `run_internal`/`_internal`/underscore-prefixed modules.

**Examples**: openai-agents-sdk's `tests/sandbox/capabilities/test_apply_patch_tool.py:15-16`, `tests/memory/test_session_persistence_sanitize.py:8`, `tests/extensions/experimental/codex/test_codex_tool.py:31-33`.

**Why it fails**: tests set the precedent. If a test can import from `run_internal`, contributors assume the zone is more permeable than the docstring says.

**Detection**: a lint rule forbidding private-zone imports from tests, or a `tests/internal/` subpackage that is the only place allowed to break the boundary (and is clearly labeled as such).

### AC9. Duplicate entrypoints

**Symptom**: two packages register the same console script or CLI command.

**Examples**: crewai's `crewai` console script defined in both `crewai` (`lib/crewai/pyproject.toml:146-147`) and `crewai-cli` (`lib/cli/pyproject.toml`).

**Why it fails**: ownership ambiguity; if either package is uninstalled, the other inherits; if both are installed with different versions, resolution is undefined.

**Detection**: package metadata audits; explicit CI check for unique `[project.scripts]` entries across the workspace.

## Notable Absences

### NA1. No source has fully mechanical import-direction enforcement

Every source lacks at least one of: import-linter (Python), depguard (Go), or `no-restricted-imports` + boundaries plugin (JS/TS). agent-framework comes closest with a dependency-bounds validator, but it catches *declared* bound failures, not undeclared cross-package private imports. opa and temporal rely on Go's `internal/` for the boundary that matters most but do not lint the rest.

### NA2. No source has architectural unit tests on .NET / Go / JS

agent-framework explicitly notes "no dedicated architecture/boundary unit tests on .NET were found" — only conventions and package naming. langfuse similarly lacks separation tests; enforcement is lint/typecheck/convention. The strongest evidence of boundary health is a CI matrix that runs each package's tests in isolation (agent-framework, langgraph), but that proves install-time independence, not directional enforcement.

### NA3. No source has both abstractions-first *and* runtime DI

These are complementary patterns but rarely co-occur. agent-framework has abstractions-first but composition is via plain DI through Microsoft.Extensions; pydantic-ai has abstractions but no runtime DI; temporal has fx DI but no separate abstractions package. The closest to combining both is openai-agents-sdk with `Session` as a `@runtime_checkable` Protocol and `Model`/`ModelProvider` as ABCs, but no DI container.

### NA4. Duck typing in lieu of optional-dep declarations

Temporal's `RedisCache` accepts `redis: Any` (`libs/checkpoint/langgraph/cache/redis/__init__.py:11-16`) — actually, this is langgraph — to keep the base lib lean at the cost of static checking on the client object. langgraph also uses duck-typed `redis: Any` in `cache/redis/__init__.py:12-16`. This trades runtime correctness for install footprint, but no source combines duck typing with a documented contract test.

### NA5. No published architecture diagram as part of CI

Pydantic-ai's `agent_docs/pydantic-ai-slim.md:7-17` is a textual ownership map; langfuse's `AGENTS.md:45-49` is a textual DAG; both are static documents. None of the sources generate an import graph at CI time (e.g., via pydeps, pyan, or madge) and publish it as part of the docs.

### NA6. Empty `reports` source

The `reports` source is an empty directory tree (`sources/reports/source/24.01-public-api-surface/` exists but contains no files). This represents a pipeline gap, not an architectural verdict. A pre-flight guard in the study runner should refuse to dispatch against a zero-file source.
