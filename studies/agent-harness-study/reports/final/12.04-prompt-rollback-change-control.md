## Executive Summary

Only one of the two sources can answer the headline question affirmatively at the mechanism level — and even it does so without a first-class workflow.

**langfuse (6/10)** implements a production-grade substrate for prompt change control: prompts are immutable versioned rows (`@@unique([projectId,name,version])` in `packages/shared/prisma/schema.prisma:830-857`), deployment is a movable label pointer (`production`, `latest`) updated in an atomic Postgres transaction with `FOR UPDATE` (`web/src/features/prompts/server/actions/updatePrompts.ts:26-44`), and visibility is near-real-time via a Redis epoch rotation (`packages/shared/src/server/services/PromptService/index.ts:177-190`). Rollback is a label move that is technically <1s. Every observation carries `prompt_id/name/version` (`packages/shared/prisma/schema.prisma:462-475`), aggregated by `getObservationMetricsForPrompts` (`packages/shared/src/server/repositories/observations.ts:1436-1565`), and every mutation is audit-logged with before/after (`web/src/features/audit-logs/auditLog.ts:84-121`). Yet there is no `rollback` verb, no required reviewer, and no drift monitor — a bad `production` move is one authorized `setLabels` call away (`web/src/features/prompts/server/routers/promptRouter.ts:801-995`), and detection is manual.

**agent-framework (2/10)** is the null case by design: it is a client-side SDK, not a prompt host. Prompts are plain `instructions: str` constructor args (`python/packages/core/agent_framework/_agents.py:669,744,759`) and declarative YAML fields (`python/packages/declarative/agent_framework_declarative/_models.py:835-860`) with no registry, no version, no deployment pipeline distinct from code, and no rollback API. Reverting requires `git revert` + a `python-*` tag release (`python-release.yml:13-57`) and consumer redeploy — minutes to hours, not seconds. Telemetry can emit raw `gen_ai.system_instructions` (`observability.py:238`) only when `SENSITIVE_DATA_ENABLED=true`, but emits no hash or version; evaluation results (`_evaluation.py:1-340`) are not keyed to a prompt version; history providers (`_sessions.py:166-262`) replay messages without storing the prompt that produced them.

Convergence: neither source monitors drift, neither gates promotion on an evaluation threshold, and neither treats a prompt change as distinct from its surrounding artifact in review. Divergence is entirely product-shape-driven: the source whose product *is* prompt management invests in immutability, labels, transactions, and linkage; the library delegates all lifecycle to the consumer's code-review and release process.

## Core Thesis

**Prompt rollback maturity depends on whether the system treats a prompt as data (a row) or as a value (a string).** That single modeling choice determines every 12.04 capability.

When a prompt is a row (langfuse), the system gets version identity, atomic promotion, audit history, and run correlation almost for free: `createPrompt` appends `version = max+1` immutably (`web/src/features/prompts/server/actions/createPrompt.ts:87-90,141-156`), `setLabels`/`updatePromptLabels` move labels transactionally (`web/src/features/prompts/server/utils/updatePromptLabels.ts:17-41`), `PromptService.invalidateCache` rotates an epoch so SDK fetches (`PromptService.getPrompt` at `packages/shared/src/server/services/PromptService/index.ts:47-79`) see the rollback after one cache miss, and `Observation.prompt_id/name/version` (`packages/shared/src/server/repositories/observations.ts:186-189`) makes post-incident slicing trivial. The remaining gaps — no approval state machine, no `POST .../rollback`, no automated drift alert — are workflow thinness on top of a solid substrate, rated 6/10 rather than 9/10 because the substrate is present but the workflow is fragile.

When a prompt is a value (agent-framework), there is nowhere for lifecycle to attach. `ChatOptions.instructions: str` (`_types.py:3412-3413`) carries no version, hash, or deployment metadata; `_merge_options` concatenates overrides with `\n` (`_agents.py:125-130`) without bumping anything; `PromptAgent.from_dict` dispatches on `kind=="Prompt"` (`_models.py:512-526`) like any other agent kind, with no lifecycle hook; `python-release.yml` builds whole packages, not prompts (`python-release.yml:1-62`). The only review is generic code review (`.github/pull_request_template.md:1-43`, `merge-gatekeeper.yml:1-14`, `CODEOWNERS:1-7`), which validates code correctness, not prompt behavior; the only linkage is raw text in an opt-in OTel attribute; the only rollback is version control. The delegation is intentional for a portable SDK — but against the dimension's operational tests (reviewed, observable, reversible, linked) it is absent (2/10).

Two corollaries sharpen the lesson. First, **authorization is not review**: langfuse's protected-label RBAC (`promptProtectedLabels:CUD` at `web/src/features/rbac/constants/projectAccessRights.ts:38`, checked via `checkHasProtectedLabels.ts:3-25`) limits *who* can move `production` but not *whether peer verification happened*; agent-framework's `CODEOWNERS` similarly limits who owns `azurefunctions`/`durabletask`, not who approves `instructions:` edits. Second, **privacy gating without an identifier destroys forensics**: agent-framework's `SENSITIVE_DATA_ENABLED` default-off (`observability.py:1075-1103,682-812`) removes the only built-in prompt→trace path exactly in production, where it is needed most — a gap langfuse avoids by stamping `prompt_name`/`prompt_version` columns that carry no content.

## Approach Models

Clustering by how prompts are modeled for change control yields two distinct archetypes:

### Model A — Prompt-as-Value (Library / SDK) — agent-framework

*Problem framed as:* keep the SDK minimal and host-agnostic; prompts are caller-supplied strings.

*Where implemented:* `python/packages/core/agent_framework/_agents.py:669-770` (`Agent.instructions` in `default_options`), `_types.py:3412-3413` (`ChatOptions.instructions: str`), `python/packages/declarative/agent_framework_declarative/_models.py:512-526,820-860` (`PromptAgent.instructions` via `AgentDefinition.from_dict`), `_sessions.py:253-262,166-262` (session instruction injection and history).

*Main mechanism:* prompts travel with code. There is no prompt store; `Agent(client, instructions="...")` or YAML load is the deployment. Release is `python-release.yml:1-62` on `release.published` tag `python-*`; CI is `python-tests.yml:1-22` / `python-merge-tests.yml` running `poe test`. Rollback is `git revert` + retag.

*Supporting mechanisms:* generic PR template (`pull_request_template.md:1-43`), `merge-gatekeeper.yml:1-14`, `CODEOWNERS:1-7`, `observability.py:238` `SYSTEM_INSTRUCTIONS` attribute (opt-in), `evaluate_agent`/`LocalEvaluator` (`_evaluation.py:1-340`) scoring runs but not prompt versions, `SkillsProvider._create_instructions` (`_skills.py:1943-2025`) in-code templating, PowerFx eval for declarative instructions (`_models.py:51-80`).

*Operational contract:* source-of-truth is git; audit source is git log; observability requires `ENABLE_SENSITIVE_DATA=true`; no hot-swap, no canary, no hash.

### Model B — Prompt-as-Row with Label Indirection (Platform / Registry) — langfuse

*Problem framed as:* multiple consumers share prompts across environments; production must be movable without redeploy, and history must stay reproducible.

*Where implemented:* `packages/shared/prisma/schema.prisma:830-857` (Prompt table, `@@unique([projectId,name,version])`, `labels String[]`), `web/src/features/prompts/server/actions/createPrompt.ts:74-234` (append-only create), `web/src/features/prompts/server/routers/promptRouter.ts:801-995` + `web/src/features/prompts/server/actions/updatePrompts.ts:16-166` + `web/src/features/prompts/server/utils/updatePromptLabels.ts:3-43` (label moves), `packages/shared/src/server/services/PromptService/index.ts:26,44,177-232` (epoch cache), `web/src/features/audit-logs/auditLog.ts:27-28,84-121` + `promptChangeEventSourcing.ts:14-56` (audit + webhooks), `packages/shared/src/server/repositories/observations.ts:1436-1565` + `promptRouter.ts:251-276,1275-1325` (metrics).

*Main mechanism:* immutable insert-only versions; deployment is a label row-update, not a content mutation. Creating appends `version = latest+1` with `labels = [...labels, 'latest']` and strips old holders in the same `$transaction` (`createPrompt.ts:171-184`), preventing split-brain `production`. Fetching resolves via `getPrompt` by `label` or `version` (`PromptService/index.ts:47-128`).

*Supporting mechanisms:* `FOR UPDATE` locking (`updatePrompts.ts:26-44`), `checkHasProtectedLabels` + `promptProtectedLabels:CUD` scope + `prompt-protected-labels` entitlement (`checkHasProtectedLabels.ts:3-25`, `projectAccessRights.ts:38,108,163`, `promptRouter.ts:1369-1491`), `LATEST` unprotectable (`promptRouter.ts:1414-1419`), `EntityChangeJob` queue (`queues.ts:274-291`), `resolutionGraph` + dependency validation (`createPrompt.ts:117-139`, `PromptService/index.ts:234-379`), `deletePrompt` reattaching `latest` (`deletePrompt.ts:94-119`).

*Operational contract:* content never mutates; labels are unique per prompt name enforced transactionally; cache coherence is epoch-based (project-scoped, 7-day TTL); `production` can be empty if its version is deleted without reassignment.

**Why the split is not a quality ranking:** SDKs optimize for embeddability (no required infra, portable across OpenAI/Azure/Bedrock, privacy-safe defaults) and thus under-invest in registry machinery that would add Postgres/Redis/queue cost. The platform optimizes for fleet governance and pays that cost because its users demand it as a feature. Both choices are valid for their product shapes — but only Model B can answer the dimension's headline question at the mechanism level.

## Pattern Catalog

### P1: Immutable version + mutable label pointer (the core rollback primitive)

- *Problem:* prompts must iterate freely while production stays stable and history stays reproducible; rollback must be instant and non-destructive.
- *Demonstrated by:* langfuse — only complete implementation; agent-framework shows the failure mode (no identity, so rollback is code revert).
- *Why it works:* immutability makes every historical version reproducible; labels decouple *what exists* from *what serves* — promotion is a metadata patch while ingest-time pinning keeps run history exact regardless of later moves.
- *When to copy:* multiple consumers share prompts across deployments; you need audit, rollback, or staged rollout.
- *When overkill:* single application owns a handful of prompts in-repo — git history plus identifier stamping covers most needs.
- *Evidence:* `web/src/features/prompts/server/actions/createPrompt.ts:141-156` (immutable create), `web/src/features/prompts/server/actions/updatePrompts.ts:108-132` + `web/src/features/prompts/server/utils/updatePromptLabels.ts:17-41` (atomic strip-and-set), `web/src/features/prompts/server/handlers/promptVersionHandler.ts:6-34` → `prompt-api-service.ts:81-130` (API label add), `packages/shared/prisma/schema.prisma:841-847`.

### P2: Atomic label transaction with row-level locking

- *Problem:* concurrent creators or label-movers must not produce two `production` holders or duplicate versions.
- *Demonstrated by:* langfuse.
- *Why it works:* `SELECT ... FOR UPDATE` inside `$transaction` serializes label ownership; `removeLabelsFromPreviousPromptVersions` finds all `labels hasSome` holders and strips them in the same transaction as the target update.
- *When to copy:* whenever labels/aliases govern production routing.
- *Risk:* concurrent creates on the same name can still race on version number — langfuse surfaces `P2002` unique-constraint violation as `InvalidRequestError` with a retry hint (`prompt-api-service.ts:51-66`); callers must serialize or back off.
- *Evidence:* `web/src/features/prompts/server/actions/updatePrompts.ts:26-44` (`FOR UPDATE`), `web/src/features/prompts/server/actions/createPrompt.ts:171-184` + `web/src/features/prompts/server/utils/updatePromptLabels.ts:3-43`, `web/src/features/prompts/server/routers/promptRouter.ts:868-905` (dependency guard before removal).

### P3: Epoch-based cache invalidation (project-scoped)

- *Problem:* SDKs cache resolved prompts; a label move must become visible within seconds without per-key deletes.
- *Demonstrated by:* langfuse.
- *Why it works:* rotating `prompt_cache_epoch:{projectId}` (7-day TTL) moves all reads to a fresh Redis namespace; old keys expire via `LANGFUSE_CACHE_PROMPT_TTL_SECONDS`; `getCacheKey` embeds the epoch so a single `SET` invalidates the whole project.
- *When to copy:* resolved prompts may include transitive dependencies (langfuse's `resolutionGraph`), so per-label invalidation is insufficient without dependency tracking.
- *Cost:* thundering herd — one label move invalidates unrelated prompts in the same project; degraded Redis or `LANGFUSE_CACHE_PROMPT_ENABLED=false` leaves stale caches until TTL expiry (`PromptService/index.ts:180`).
- *Evidence:* `packages/shared/src/server/services/PromptService/index.ts:177-232`, `web/src/__tests__/server/promptCache.servertest.ts:186-238`.

### P4: Observation→prompt linkage with per-version metrics (the forensic join)

- *Problem:* "which prompt produced this trace?" and "did quality regress after the promotion?" must be answerable post-incident.
- *Demonstrated by:* langfuse (strong); agent-framework (absent — contrast).
- *Why it works:* every `Observation` stamps `prompt_id/name/version` at ingestion (`packages/shared/src/server/repositories/observations.ts:186-189`, `packages/shared/src/server/repositories/definitions.ts:585-587`), and `promptRouter.metrics`/`versionMetrics` aggregate `observationCount`, `firstUsed`/`lastUsed`, `medianTokens/cost/latency`, and scores per version over a time window.
- *When to copy:* always, even in libraries — hash or version stamping is one column.
- *Evidence (positive):* `packages/shared/prisma/schema.prisma:462-475,830-857`, `web/src/features/prompts/server/routers/promptRouter.ts:251-276,1275-1325`, `packages/shared/src/server/repositories/observations.ts:1436-1565`, `web/src/__tests__/server/prompts.v2.servertest.ts:414-484`.
- *Evidence (negative):* `python/packages/core/agent_framework/observability.py:238` (`gen_ai.system_instructions` without hash/version), `python/packages/core/agent_framework/_types.py:3412-3413`, `python/packages/core/agent_framework/_evaluation.py:1-340` (no prompt-version field), `python/packages/core/agent_framework/_sessions.py:166-262` (history without prompt snapshot).

### P5: Protected-label RBAC + audit-log as governance minimum

- *Problem:* restrict who can affect `production` and leave an auditable trail without building a full approval workflow.
- *Demonstrated by:* langfuse; agent-framework has the code-review analogue without prompt scoping.
- *Why it works:* `Owner/Admin` scopes + `throwIfNoEntitlement` checks gate every `create/delete/setLabels` touching a protected label; `auditLog` writes `resourceType`, `action`, `before/after`, and actor (`USER` or `API_KEY`) for forensics; `promptChangeEventSourcing` enqueues `EntityChangeJob` for webhooks.
- *When to copy:* as the first governance step before 4-eyes; works with existing RBAC.
- *Limitation:* deny/permission check, not verification — a single authorized user can still push a bad prompt to `production` without peer review; `commitMessage` (`packages/shared/src/features/prompts/types.ts:40,54`) remains free-text up to 500 chars (`constants.ts:3`).
- *Evidence:* `web/src/features/rbac/constants/projectAccessRights.ts:38,108,163`, `web/src/features/prompts/server/utils/checkHasProtectedLabels.ts:3-25`, `web/src/features/prompts/server/routers/promptRouter.ts:306-320,801-995,1369-1491`, `web/src/features/audit-logs/auditLog.ts:27-28,84-121`, `web/src/features/prompts/server/promptChangeEventSourcing.ts:14-56`, `packages/shared/src/server/queues.ts:274-291`.

### P6: Privacy-gated capture without an identifier — the broken tradeoff (anti-pattern to invert)

- *Problem:* prompts may contain secrets; dumping text into telemetry by default is unsafe.
- *Demonstrated by:* agent-framework (negative) vs langfuse (fix).
- *Why it fails:* gating `SYSTEM_INSTRUCTIONS` behind `SENSITIVE_DATA_ENABLED=false` (`observability.py:682-812,1075-1103`) removes the run→prompt trail exactly where incidents happen. Four sources in sibling dimension 12.01 show the same wall.
- *Fix pattern implied by evidence:* capture identity always, capture content conditionally. Langfuse stamps `prompt_name`/`prompt_version` with no privacy concern because they reference rows, not text; agent-framework's own future-work proposes emitting a hash (`gen_ai.prompt.version`) alongside the gated text.
- *Evidence:* `python/packages/core/agent_framework/observability.py:238,762-780,806-812,1075-1103`, `python/packages/core/agent_framework/_agents.py:1493-1499`, `python/packages/declarative/agent_framework_declarative/_models.py:51-80`.

## Tradeoffs

- **Immutable rows + labels vs value co-versioned with code.** *Benefit of rows (langfuse):* non-destructive rollback, reproducible history, audit, and run binding fall out of `Prompt` being a row (`schema.prisma:830-857`). *Cost:* Postgres tables, Redis epoch logic, lock handling, and queue integration — infrastructure a thin framework cannot justify. *Alternative seen in agent-framework:* bundling prompts with releases guarantees code-prompt atomicity but prevents low-latency iteration (one-line instruction tweak requires `poe build` + tag + release). *Best fit:* rows when a second consumer (another service, environment, or point in time) shares the prompt; values when one app owns its prompts in-repo.

- **Authorization (protected labels) vs verification (approval workflow).** *Benefit of auth (langfuse `promptProtectedLabels:CUD`):* cheap to implement, blocks accidental `production` moves by junior roles; paired with `auditLog` it is auditable (`promptRouter.ts:1369-1491`, `auditLog.ts:27-28`). *Cost:* single authorized user can still ship a bad prompt — no 4-eyes, no draft state, no required second approver. *Alternative:* agent-framework's generic PR approval is verification for code but not prompt-behavior (no eval gate, no canary). *Failure mode today:* immediate atomic switch with no staged rollout; production incident depends on operator detection, which is unautomated.

- **Epoch invalidation (single SET) vs per-key deletes.** *Benefit (langfuse):* correct for dependency graphs (`PromptService/index.ts:208-212` comment), one Redis write, no key enumeration. *Cost:* thundering herd — all prompts in a project miss at once; `LANGFUSE_CACHE_PROMPT_TTL_SECONDS` fallback if Redis down (`PromptService/index.ts:180`) serves stale prompts. *Alternative (agent-framework):* no cache, no staleness — but no sharing.

- **Privacy-gated text vs unconditional identifier.** *Benefit of gating (agent-framework `ENABLE_SENSITIVE_DATA=false`):* prevents accidental prompt leakage. *Cost:* removes forensics exactly in production. *Alternative demonstrated by langfuse:* `prompt_name`/`prompt_version` columns carry no content and can be emitted unconditionally; agent-framework's future-work proposes hashing `instructions` into `gen_ai.prompt.version` while keeping the text gated.

- **Atomic uniqueness vs retry burden.** *Benefit of langfuse transactions (`FOR UPDATE` + `$transaction`):* no split-brain `production`. *Cost:* `P2002` on concurrent creates requires client-side delay/retry (`prompt-api-service.ts:51-66`); dependency guards (`promptRouter.ts:868-905`, `668-729`) block legitimate cleanup until dependents are rewired. *Alternative (agent-framework):* no concurrency issue because there is no shared mutable label — but also no fleet-wide consistency primitive.

- **Tags converge, labels diverge (langfuse).** Tags are spread to all versions (`createPrompt.ts:186-200`, `promptRouter.ts:1107-1118` via `updateMany`), simplifying filtering but destroying per-version tag history; labels preserve per-version pointers but require careful `hasSome` queries (`updatePromptLabels.ts:17-41`). Copy deliberately: use labels for deployment pointers, not tags.

## Decision Guide

Use this when deciding how much prompt change-control to build:

1. **You ship a library/SDK others embed** → Stay on Model A (prompt-as-value) but add the two cheap provenance fixes agent-framework lacks: (a) hash `instructions` (or full template + variables) and emit `gen_ai.prompt.version` / `gen_ai.prompt.name` unconditionally alongside the gated `SYSTEM_INSTRUCTIONS` (`observability.py:238`); (b) snapshot `default_options["instructions"]` into `AgentSession`/`AgentResponse.additional_properties` so replays are reproducible without enabling sensitive capture. Do not build a registry — document that prompt lifecycle is consumer-owned.

2. **You ship a product/platform where prompts are shared across services, environments, or time** → Adopt Model B (langfuse blueprint): append-only `Prompt` rows with `@@unique([projectId,name,version])`, label indirection, `$transaction` label moves, `prompt_cache_epoch` rotation, `audit_log` with before/after, and `Observation.prompt_id/name/version` stamping. Integration-test the failure paths langfuse does (`promptCache.servertest.ts:186-238`, `prompts.v2.servertest.ts:414-484`) — Redis outage, concurrent creates, dependent-label guards.

3. **You already have git-versioned prompts and the team is <10 people** → Keep YAML/Markdown in-repo (pydantic-ai style) but treat it as Model B-lite: add a `PromptSpec` with `name` + `version` + `commitMessage` fields, validate at load, and emit the version/hash on every run. The decision rule from 12.01 holds: if you cannot name who consumes a prompt besides the code that loads it, values suffice; the moment a second consumer appears, you need identity.

4. **Do you need fleet-wide rollback without redeploy?** → You need label indirection. Do not block on building approval workflow — ship protected labels + audit first (langfuse's 6/10 is already enough to roll back in seconds), then add `POST .../labels/production/rollback` as a thin wrapper over `setLabels` that moves `production` to `version-1` (or explicit target) and records a `rollback_reason`.

5. **Do you gate `production` today with only one authorized writer?** → Add the approval layer langfuse notes as future work: `PromptLabelApproval` table with `pending → approved` states, required second approver when moving `production`, reusing the existing `promptProtectedLabels` gate but adding verification. Until then, at minimum require that `setLabels` touching `production` references a linked `audit_log` entry and a passing `versionMetrics` check over the last window.

Decision rule distilled from the two extremes: **`instructions: str` is a deployment strategy, not just a type — if rollback must be <60s, that string must be a pointer, not content. The cheapest pointer is a hash; the operational pointer is a label.**

## Practical Tips

**Patterns to copy now (low cost, high signal):**

- Stamp identity on every run — even without a registry. A content hash or integer version alongside `gen_ai.system_instructions` converts gated text capture into ungated correlation (one column; agent-framework future-work proposes exactly this).
- Persist prompt snapshot per run/session. `InMemoryHistoryProvider`/`FileHistoryProvider` (`_sessions.py:166-262`) replay messages without the `instructions` that produced them — store `default_options["instructions"]` hash into session history or `AgentResponse` metadata.
- Make label/alias moves atomic and unique-per-name. Use `removeLabelsFromPreviousPromptVersions` inside the same `$transaction` as the target update (`updatePromptLabels.ts:3-43`) and test concurrent creates (`prompt-api-service.ts:51-66`).

## Anti-Patterns / Caution Signs

- **Dormant or superficial versioning.** Agent-framework's declarative `instructions` with PowerFx indirection and no version field (`_models.py:835-860`, `_try_powerfx_eval` at `_models.py:51-80`) looks versioned but is stringly-typed value evolution — `grep rollback|prompt.*version` returns zero hits. Langfuse's `commitMessage` free-text without enforcement (`types.ts:40`, `constants.ts:3`) is the subtler variant: history exists but carries no review signal.
- **Authorization masquerading as review.** `promptProtectedLabels:CUD` (`projectAccessRights.ts:38`) and `CODEOWNERS:1-7` limit *who* can write, not *whether* peer review happened. A single `Owner` can still atomically promote a bad prompt to `production`.
- **Silent fallbacks that degrade prompt content.** `Agent(instructions=...)` without versioning, `FileHistoryProvider` replay after prompt change, MCP `load_prompts` on `notifications/prompts/list_changed` (`_mcp.py:1261-1335`) reloading remote prompts without review — each propagates bad content without signal.
- **In-place mutation destroying history.** Langfuse avoids this by never updating content rows, but its `updateTags` (`promptRouter.ts:1107-1118`) mutates all versions via `updateMany` — a rare cross-version write that can race with concurrent creates; agent-framework's session replay without prompt versioning has the same forensic loss.
- **Protected surface with an intentional hole.** `LATEST_PROMPT_LABEL='latest'` explicitly unprotectable (`promptRouter.ts:1414-1419`) — by design prevents lockout, but means any `prompts:CUD` holder can always move `latest`, which some consumers treat as production.
- **Cache coherence by hope.** `invalidateCache` early-returns when `!cacheEnabled` (`PromptService/index.ts:180`) and Redis SET errors are logged but only `invalidateCache` rethrows — stale `production` can serve until TTL expiry after a failed invalidation.
- **No staged rollout or canary.** Both sources deploy/promote atomically — agent-framework via package release, langfuse via label switch. There is no progressive `5% → 50% → 100%` or automated canary metric gate; `versionMetrics` (`promptRouter.ts:1275-1325`) must be polled manually.
