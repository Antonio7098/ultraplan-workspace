## Executive Summary

No source in this cohort offers a mature, durable third-party plugin system with dynamic discovery, lifecycle management, sandbox isolation, and versioned stability guarantees (the 9-10 band). The best sources (opa 7, pydantic-ai 7) present clear, tested interface models with operational safeguards but still require compile-time linking and share the host process. The middle band (agent-framework 6, openhands 6, temporal 6, crewai 5, langgraph 5, openai-agents-sdk 5) exposes broad, typed seams — tools, providers, memory, middleware/hooks, MCP — all answerable as "add a new tool *instance* without touching core: yes; add a new tool *kind*/provider/eval without touching core: usually no." The low band (letta 3, langfuse 2) is intentionally or incidentally non-pluggable: Langfuse routes extensibility to REST/OTEL/webhooks outside the process; Letta exposes two string-target slots behind an env var.

Convergence: every extensible source uses explicit Go interfaces or Python `ABC`/`Protocol` per concern, not a single `Plugin` manifest, and wires extensions in code via constructor injection or builder. Divergence is driven by product shape, not quality ranking: agent SDKs optimize for type-checked, copy-paste composition in a single-process harness; infrastructure servers (opa, temporal) optimize for compile-time DI with `Validate→New`, status observability, and fail-fast validation at the cost of rebuilds; OpenHands optimizes for marketplace distribution (git clone + last-wins merge) at the cost of sandboxing and determinism.

## Core Thesis

The studied ecosystem has converged on **inheritance/composition over registry**: typed interfaces per capability are the de facto plugin model, and that suffices for trusted, first-party-owned deployments where developers control the process. Sources diverge on *how* those interfaces are collected — direct injection (langgraph, pydantic-ai), workspace/extra lazy imports (agent-framework, openai-agents-sdk), global factories with discovery reconfiguration (opa), functional options over Fx (temporal), or fetched bundle merging (openhands) — because harness SDKs must stay dependency-free and testable while servers must enforce lifecycle and readiness. The missing piece everywhere is **isolation and versioned discovery**: no source sandboxes plugins, no source offers `entry_points`-style auto-discovery with capability negotiation, and most newer surfaces are explicitly experimental, so third-party durability requires pinning the whole binary. Copy the typed-per-concern interfaces and two-phase lifecycle where you need it; do not copy a universal plugin manager until you have out-of-process isolation to justify it.

## Approach Models

Three approach families emerged; membership is functional, not a quality ranking.

**A. Code-wired composition (no central plugin manager) — agent SDKs/harnesses.** Extension is passing an object that satisfies an `ABC`/`Protocol` to a constructor or `Agent(...)`/`StateGraph.compile(...)`. Discovery is `import` + explicit argument; lifecycle is per-object methods; isolation is none beyond per-run copies where offered. Members: agent-framework, crewai, langgraph, openai-agents-sdk, pydantic-ai. Variance within the family is about dispatch shape: agent-framework uses three parallel middleware pipelines (`AgentMiddleware` vs `ChatMiddleware` vs `FunctionMiddleware` at `python/packages/core/agent_framework/_middleware.py:465`); crewai unifies legacy + new hooks in a generic `dispatch` over `InterceptionPoint` (`lib/crewai/src/crewai/hooks/dispatch.py:40`); pydantic-ai collapses everything into one `AbstractCapability` ordered middleware chain (`pydantic_ai_slim/pydantic_ai/capabilities/combined.py:46`); langgraph distributes across 9 separate ABCs (`BaseChannel`/`BaseCheckpointSaver`/`BaseStore`/`StreamTransformer`); openai-agents-sdk spreads across 8+ discrete interfaces (`Model`/`MCPServer`/`Session`/`TracingProcessor`).

**B. Compile-time registry + lifecycle manager — infra servers.** Extension is `RegisterPlugin(name, factory)` at init, validated then instantiated by a lifecycle manager that supports `Start`/`Stop`/`Reconfigure` and exposes status. Members: opa (`runtime.RegisterPlugin` at `v1/runtime/runtime.go:94` plus `Manager` at `v1/plugins/plugins.go:192` and discovery `getPluginSet` at `v1/plugins/discovery/discovery.go:619`), temporal (`ServerOption.apply` at `temporal/server_option.go:25` over Fx `ServerOptionsProvider` at `temporal/fx.go:94`), langfuse internal (`ToolRegistry.register` flat `Map` at `web/src/features/mcp/server/registry.ts:75`), and letta as a degenerate case (2-entry `DEFAULT_PLUGINS` dict at `letta/plugins/plugins.py:15`). All require rebuilding the binary to add a new plugin kind; hot behavior is limited to reconfiguration of already-linked factories via discovery/config reload.

**C. Fetched-bundle marketplace — distribution-centric.** Extension is a directory (`plugin.json` + `skills/` + `hooks/` + `.mcp.json` + `agents/`) fetched by git clone into a per-conversation sandbox and merged with last-wins semantics. Single member: openhands (`PluginSource` at `_sdk_inspect/sdk/plugin/types.py:14`, `MarketplaceRegistration` at `openhands/app_server/settings/settings_models.py:75`, `load_plugins()` at `_sdk_inspect/sdk/plugin/loader.py:28`, proxy `POST /api/skills` at `openhands/app_server/app_conversation/skill_loader.py:614`). This is the only source with real dynamic loading at runtime, but loading is conversation-start scoped, not hot-reload, and merging is concatenation/override rather than isolated mounting.

Why divergence is valid: harness SDKs (A) serve library consumers who own the process and value dependency minimalism (workspace-per-provider at `python/pyproject.toml:71`, extras at `openai-agents-sdk/pyproject.toml:37`, lenient fallback via LiteLLM at `lib/crewai/src/crewai/llm.py:494`); servers (B) serve operators who need readiness gating (`runtime.waitPluginsReady` at `v1/runtime/runtime.go:1057`, `HealthSignalAggregator` at `temporal/fx.go:163`) and deterministic startup ordering; OpenHands (C) serves marketplace scale where authenticated git rewrite (`skill_loader.py:511`) and org enumeration caps (`_MAX_ORG_CANDIDATES=30`) matter more than type strictness.

## Pattern Catalog

**1. Explicit typed interface per concern.**
Problem: allow third parties to add a new capability without monkey-patching core. Sources: all except langfuse public API. Why it works: static dispatch, IDE autocomplete, testable fakes (`InMemorySaver` at `libs/checkpoint/langgraph/checkpoint/memory/__init__.py:33`, `InMemoryStore`, `Fake` session). When to copy: any SDK/server expecting sustained third-party implementation. When risky/overkill: small single-team tool where a callback suffices; proliferation of narrow interfaces (langgraph's 9 ABCs, openai-agents-sdk's 8+) raises discoverability cost. Evidence: `SupportsAgentRun` Protocol at `python/packages/core/agent_framework/_agents.py:188`, `StorageBackend` Protocol at `lib/crewai/src/crewai/memory/storage/backend.py:44`, `BaseChannel` ABC at `libs/langgraph/langgraph/channels/base.py:19`, `Authorizer` interface at `common/authorization/authorizer.go:53`, `AbstractCapability` at `pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:162`.

**2. Tool as the universal first plugin.**
Problem: can a third party add a new tool type without core change? Sources: agent-framework (`FunctionTool` at `python/packages/core/agent_framework/_tools.py:243` + `@tool` at `_tools.py:1179` + `MCPTool` at `_mcp.py:333`), crewai (`BaseTool` at `lib/crewai/src/crewai/tools/base_tool.py:103` + `CrewStructuredTool` at `structured_tool.py:189`), openai-agents-sdk (`FunctionTool` at `src/agents/tool.py:440` + `MCPServer` at `mcp/server.py:543`), pydantic-ai (`FunctionToolset` at `pydantic_ai_slim/pydantic_ai/toolsets/function.py:113` + `AbstractToolset` at `toolsets/abstract.py:76`), langgraph (`ToolNode` at `libs/prebuilt/langgraph/prebuilt/tool_node.py:622`). Why it works: tools are the highest-churn surface and naturally side-effect free. When to copy: always expose `@tool`-style wrapping plus a class-based ABC with JSON-schema generation. When overkill: when wire-format for hosted/native tools requires core serialization (`HostedMCPTool` still needs `openai_responses.py` changes).

**3. Workspace-per-provider / extras-gated lazy loading.**
Problem: keep core light while letting third parties publish providers. Sources: agent-framework workspace members at `python/pyproject.toml:71` with `__getattr__` lazy `importlib.import_module` (`python/packages/core/agent_framework/azure/__init__.py:27`), openai-agents-sdk `_LAZY_EXPORTS` at `src/agents/extensions/memory/__init__.py:54`, crewai fallback to LiteLLM at `lib/crewai/src/crewai/llm.py:494`. Why it works: `pip install agent-framework-myprovider` without forking core. When to copy: multi-provider SDKs. Cost: discoverability hides behind first attribute access; no `pip list` of available providers.

**4. Middleware/hook pipeline as the second universal extension.**
Problem: cross-cutting concerns (logging, retry, PII, compaction). Sources: agent-framework `AgentMiddlewarePipeline.execute()` at `python/packages/core/agent_framework/_middleware.py:843`, crewai `dispatch()` over 10 `InterceptionPoint` at `lib/crewai/src/crewai/hooks/dispatch.py:40`, pydantic-ai `CombinedCapability` chain at `pydantic_ai_slim/pydantic_ai/capabilities/combined.py:46`, temporal chained interceptors at `temporal/server_option.go:190`. Why it works: decorator + registry + context-mutation pattern is composable. Copy when: you need prompt/policy injection or tool guarding. Risk: shared mutable contexts (`LLMCallHookContext.messages` at `lib/crewai/src/crewai/hooks/llm_hooks.py:88`, `FunctionInvocationContext.tools` at `python/packages/core/agent_framework/_middleware.py:287`) — one mutator corrupts all downstream; ordering becomes a silent contract.

**5. Per-run copy for logical isolation.**
Problem: make concurrent runs safe without true sandbox. Sources: pydantic-ai `for_run` returning `replace(self,...)` at `pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:309` and `CombinedCapability.for_run` at `combined.py:101`; crewai `scoped_hooks` at `lib/crewai/src/crewai/hooks/dispatch.py:159` and `scoped_handlers` at `events/event_bus.py:832`; agent-framework `InMemoryHistoryProvider.before_run/after_run` at `python/packages/core/agent_framework/_sessions.py:506`. Why it works: cheap logical isolation. When to copy: any async agent with shared middleware. Not a substitute for untrusted-code sandboxing.

**6. Registry with duplicate-name guard.**
Problem: fail fast on collisions. Sources: langfuse `ToolRegistry.register()` throwing on duplicate feature/tool at `web/src/features/mcp/server/registry.ts:85`, crewai `_TOOL_TYPE_REGISTRY` at `lib/crewai/src/crewai/tools/base_tool.py:51`, temporal archiver provider caching at `common/archiver/provider/provider.go:123`. Why it works: deterministic startup. When overkill: when last-wins is intentionally desired for overrides (openhands deliberately uses last-wins at `_sdk_inspect/sdk/plugin/plugin.py:159`).

**7. Two-phase Validate→New / factory adapter.**
Problem: reject bad config without leaked construction. Sources: opa `Factory.Validate` then `Factory.New` at `v1/plugins/plugins.go:89`, temporal `CustomHistoryArchiverFactoryFunc` adapter at `common/archiver/provider/provider.go:65`, pydantic-ai `get_serialization_name`/`from_spec` at `pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:261`. Why it works: lets discovery/config pre-flight without side effects. Copy for any server that hot-reconfigures from untrusted config.

**8. Spec/manifest-driven deserialization.**
Problem: declare an agent/extension without code changes. Sources: pydantic-ai `AgentSpec.from_file`/`Agent.from_spec` with `CAPABILITY_TYPES` at `pydantic_ai_slim/pydantic_ai/agent/spec.py:33`, langgraph `langgraph.json` `graphs`/`auth`/`store` at `libs/cli/langgraph_cli/config.py:368`, openhands `PluginManifest`/`PluginSpec` at `_sdk_inspect/sdk/plugin/types.py:209`/`app_conversation_models.py:71`. Why it works: YAML/JSON is auditable, versionable. Cost: anything holding a closure/callable becomes non-serializable (`capability.py:105` returns `None`).

**9. Filter/mapper as lightweight extension.**
Problem: expose narrow customization without a new interface. Sources: openai-agents-sdk `ToolFilter`/`HandoffInputFilter`/`CallModelInputFilter` at `src/agents/mcp/util.py:92`/`src/agents/handoffs/__init__.py:125`/`src/agents/run_config.py:76`, pydantic-ai `FilteredToolset`/`PrefixedToolset` at `pydantic_ai_slim/pydantic_ai/toolsets/wrapper.py:15` and `WrapperToolset` family. Why it works: composition via closures. Risk: opaque runtime behavior vs. discoverable registry.

**10. MCP / external server as the sandboxed escape hatch.**
Problem: run untrusted tool code out-of-process. Sources: agent-framework `MCPTool` at `_mcp.py:333`, crewai `BaseAgent.mcps` at `lib/crewai/src/crewai/agents/agent_builder/base_agent.py:397`, openai-agents-sdk `MCPServer` at `src/agents/mcp/server.py:543`, openhands `mcp_config` via `_merge_custom_mcp_config` at `live_status_app_conversation_service.py:1511`, pydantic-ai `MCPToolset` at `pydantic_ai_slim/pydantic_ai/mcp.py:716`. Why it works: network boundary replaces process sandbox for tools. Copy whenever you must run third-party code but cannot sandbox the harness.

## Key Differences

- **Granularity of the contract.** Pydantic-ai bets on one fat `AbstractCapability` (50+ hooks) vs. crewai/openai-agents-sdk/langgraph splitting into many narrow ABCs/Protocols. The fat interface enables reordering and per-run rebind via `CapabilityOrdering` (`pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:116`) and single registration; the narrow approach improves discoverability via `@tool`/`BaseTool` vs. `BaseLLM` vs `Session` but scatters governance across 3+ registries.

- **Where validation lives.** Opa and temporal validate before construction (`Factory.Validate` at `v1/plugins/plugins.go:89`, `ServerOptionsProvider` co-requirement check at `temporal/fx.go:274`). Harness SDKs validate late (agent-framework `_raise_duplicate_tool_name` at `_tools.py:896`, crewai `validate_tools` at `lib/crewai/src/crewai/agents/agent_builder/base_agent.py:526`). OpenHands validates at composition write path (`validate_source` at `openhands/app_server/settings/settings_models.py:168`) but coerces-and-skips at load path (`marketplace_composition.py:195`), silently dropping bad rows.

- **Lifecycle richness.** Opa is the only source with full `Validate→New→Start→Stop→Reconfigure` plus discovery-driven hot-swap without restart (`v1/plugins/discovery/discovery.go:740`). Temporal ties lifecycle to Fx `StartStopHook` (`temporal/fx.go:393`). Pydantic-ai has two-phase `bind_capabilities_tier` (`pydantic_ai_slim/pydantic_ai/capabilities/combined.py:857`) and `for_agent`/`for_run`. Openhands is conversation-scoped (`load_plugins` only during `LocalConversation` construction). Letta has only `reset_*` helpers for tests (`letta/plugins/plugins.py:65`).

- **Dynamic loading spectrum.** No source does hot `entry_points` discovery. The closest are: openhands fetching git + merge at conversation start (`_sdk_inspect/sdk/plugin/loader.py:28`), langgraph CLI rewriting `langgraph.json` dotted paths to container imports (`libs/cli/langgraph_cli/config.py:827`), letta env-var `plugin_register` split on `;`/`=` (`letta/settings.py:496`) and pydantic-ai `AgentSpec.from_file` (`pydantic_ai_slim/pydantic_ai/agent/spec.py:33`). Langfuse is static-only by design (11 features `toolRegistry.register()` in `bootstrap.ts:34`).

- **Documentation maturity inversion.** Pydantic-ai docs are the most complete for extension authoring (`docs/capabilities/custom.md`, `docs/extensibility.md`) despite no stable version promise; opa's `docs/docs/extensions.md` is the strongest for server plugins; agent-framework/crewai/langgraph/openai-agents-sdk document per-interface docstrings but not a unified `EXTENDING.md`; langfuse consumer README (`web/src/features/mcp/README.md`) documents how to *call* tools, not author them; letta's 22-line README (`letta/plugins/README.md:7`) contradicts code (`"default"` vs `"target"`).

## Tradeoffs

- **Typed per-concern interfaces vs. single Plugin manifest.** Benefit: precise contracts, IDE support, no supply-chain manifest parsing. Cost: no unified catalog; cross-cutting concerns span 3+ registries (e.g., crewai's tool + memory + event bus). Best-fit: libraries serving trusted developers who own the process (agent-framework, langgraph, openai-agents-sdk). Failure mode: ordering/collision surprises when contexts are shared mutably. Alternative seen: single `McpFeatureModule` or `AbstractCapability` that bundles tools+hooks+instructions — more governable but inherits fat-interface versioning risk.

- **Global registry vs. instance-scoped wiring.** Benefit of global (`_TOOL_TYPE_REGISTRY`, `registeredPlugins`): deserialization of checkpoints via dotted paths, singleton status loop. Cost: import-order dependence, multi-tenant leakage (`crewai set_memory_storage_factory` at `memory/storage/factory.py:33`, letta singleton globals at `letta/plugins/plugins.py:45`). Instance-scoped wiring (pydantic-ai `for_run`, crewai `scoped_hooks`) mitigates but not universally applied.

- **In-process execution vs. out-of-process isolation.** Benefit of in-process: zero IPC overhead, shared `RunContext`/`Store`/`Session`. Cost: no blast-radius containment; a buggy `FunctionMiddleware` aborts the chain (`python/packages/core/agent_framework/_middleware.py:998`), a slow `TracingProcessor` blocks `SynchronousMultiTracingProcessor` (`src/agents/tracing/provider.py:117`). Alternative seen: MCP/external server delegation (used by 5 sources) and tool sandbox (`HyperlightCodeActProvider`, `SandboxType.E2B`/`MODAL`). No source sandboxes *plugins* themselves.

- **Workspace/extra minimalism vs. discoverability.** Benefit: core stays install-small, lazy imports (`__getattr__` import_module) defer heavy deps. Cost: no `entry_points` auto-discovery; users must know package names. Alternative seen: opa/temporal Fx supply graph makes plugins explicit at startup but requires rebuilding.

- **Fail-open vs. fail-closed hooks.** Crewai swallows non-`HookAborted` exceptions (`lib/crewai/src/crewai/hooks/dispatch.py:284`) so a buggy hook never crashes the crew — useful for observability plugins, dangerous because failures hide. Langfuse/temporal/opa fail closed (throw on duplicate registration, `logger.Fatal` on invalid custom datastore at `common/persistence/client/fx.go:207`). OpenAI SDK splits the difference (try/except per processor at `src/agents/tracing/provider.py:117` but keeps poisoned processor registered).

- **Experimental velocity vs. stable contract.** Gating new surfaces behind `@experimental` (`python/packages/core/agent_framework/_feature_stage.py:43`) or `experimental` flags (`temporal/server_option.go:145`) lets iteration without SemVer, but every such surface (SKILLS, HARNESS, EVALS, DeltaChannel beta) is an explicit breaking-change risk for third-party authors.

## Decision Guide

Use these rules when choosing how to expose extension points in a new harness or server.

- **If you are a library/SDK consumed by developers who control the full process**: copy the **code-wired narrow interfaces** pattern. Expose `BaseTool`/`@tool`, `BaseLLM`/`Provider`, `Session`/`Store` as `ABC`/`Protocol` with both decorator and class forms, and wire via constructor (`Agent(tools=[...], model=...)`). Add extras-gated lazy imports to keep install size small. Do not add a plugin registry until you need deserialization or cross-process sharing.

- **If you need to run untrusted or high-churn tool code**: copy **MCP/external server** as the first-class extension. Let third parties publish an MCP server URL rather than a Python package. Keep in-process `FunctionTool` for trusted tools only.

- **If you need ordered cross-cutting behavior (instructions, guards, compaction, PII)**: prefer a **single middleware chain** over scattered hook points. Pydantic-ai's `AbstractCapability` + `CapabilityOrdering` (`pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:116`) or crewai's `InterceptionPoint` enum (`lib/crewai/src/crewai/hooks/dispatch.py:40`) both work; choose one chain to avoid the 3-pipeline tax seen in agent-framework. Make ordering deterministic and document it.

- **If you are an infra server needing readiness and hot-reconfig without restart**: copy **opa's Factory + Manager + discovery** shape. Require `Validate` before `New`, expose `Reconfigure` for discovery-driven updates, and report per-plugin `StateOK/Err/Warn` (`v1/plugins/plugins.go:127`). Accept the rebuild cost for new plugin *kinds*.

- **If you need distribution/marketplace at scale**: copy **openhand's fetched-bundle + proxy** shape. Use `PluginManifest` + `MarketplaceRegistration` with auth-rewritten git URLs, cap org enumeration, pin via `ResolvedPluginSource` commit SHA, and expose a kill switch. Do not use last-wins silently — emit metrics on override counts.

- **If you need persistence-store pluggability**: copy **temporal's factory-per-scheme + opaque config** (`CustomDatastoreConfig` at `common/config/config.go:468`) for maximum flexibility, but add a `ValidateConfig(map[string]any) error` hook so typos fail fast at `Config.Validate()` rather than at first factory call. Otherwise copy opa's `storage.Store` indirection.

- **Avoid a plugin manager when**: single-team deployment, <5 extension points, and all extensions live in the same repo. The harness sources at score 5-6 demonstrate that explicit wiring scales better than a registry until you cross that threshold.

- **Avoid dynamic filesystem discovery / `entry_points` when**: you lack a sandbox and version-negotiation story. None of the 10 sources do this safely; the one source that tried minimal env discovery (letta) shows fragile parsing and security concerns (arbitrary `importlib.import_module` at `letta/plugins/plugins.py:34`).

## Practical Tips

**Patterns to copy now:**

- Expose every major seam as an explicit `ABC` or `@runtime_checkable Protocol` with a minimal `InMemory`/`Fake` reference impl and a Pydantic/dataclass `ToolType` `name`→ dotted-path registry for checkpoint serde (`tool_type` at `lib/crewai/src/crewai/tools/base_tool.py:203`, `CAPABILITY_TYPES` at `pydantic_ai_slim/pydantic_ai/capabilities/__init__.py:72`).
- Keep one decorator form and one class form (openai-agents-sdk does this for `FunctionTool`, pydantic-ai for `Tool`). Auto-infer JSON schema from the function signature.
- Put providers and optional stores behind extras/workspaces with lazy `__getattr__` and a helpful `pip install ...[extra]` error (`src/agents/extensions/memory/__init__.py:64`).
- Document ordering. Use a topological sort (`sort_capabilities` at `pydantic_ai_slim/pydantic_ai/capabilities/combined.py:61`) or a fixed pipeline order and forbid instance-identity `wraps` refs that break after `for_run` copies (`abstract.py:138`).
- Adopt `Validate→New` and validate at startup. For custom archivers/stores, include `ErrUnknownScheme` delegation so built-ins remain reachable after custom lookup fails (`common/archiver/provider/provider.go:52`).
- For distribution, cross the network boundary: expose MCP servers, not in-process plugins, for anything untrusted. Cache ar chivers/providers with double-checked locking (`common/archiver/provider/provider.go:123`) and pin git refs to SHA on fetch.

**Patterns to delay or avoid until needed:**

- A universal `Plugin` manifest / marketplace — unless you ship distribution infrastructure (clone, auth rewrite, caps, truncation guards) like openhands, it adds supply-chain and drift risk without value.
- Filesystem plugin directories or `entry_points` scanning — no source does this safely; defer until you have per-plugin version negotiation and `apiVersion` checks.
- Per-plugin subprocess/VM sandboxing — valuable for multi-tenant hosting, but none of the 10 sources implement it for plugins; start with MCP sandboxing for tools first.
- Loader file-extension registration (`loader/extension.RegisterExtension` at `v1/loader/extension/extension.go:23` and opa's warning that it "may go away") — keep as internal only.

**Caution checklist — revisit your design when you see:**

- `shared mutable state is the extension contract` (e.g., `context.tools[:] = merged` at `python/packages/core/agent_framework/_middleware.py:322`, docs saying "Modify in-place… Do NOT replace the list" at `lib/crewai/src/crewai/hooks/llm_hooks.py:44`) — copy-on-write or freeze after dispatch.
- `global mutable factory` or `ThreadPoolExecutor(max_workers=10)` shared by all handlers (`lib/crewai/src/crewai/events/event_bus.py:179`) — introduce per-run scoping and timeouts.
- `@experimental` on every new surface with no `ReleaseCandidate` promotion path (`python/packages/core/agent_framework/_feature_stage.py:68` empty) — establish a stability tier table and deprecation window.
- `extra="allow"` on manifests (`_sdk_inspect/sdk/plugin/types.py:225`) — replace with `"forbid"` + `model_config` after initial velocity period.
- `logger.Fatal` on invalid custom config (`common/persistence/client/fx.go:207`) — consider structured error propagation for hosted multi-tenant servers.

## Anti-Patterns / Caution Signs

- **Shared-mutable context mutation as the hook contract.** Evidence: crewai `LLMCallHookContext.messages` is a live reference to `executor.messages` (`lib/crewai/src/crewai/hooks/llm_hooks.py:88`) and `tool_input` is the live dict (`lib/crewai/src/crewai/hooks/tool_hooks.py:39`); agent-framework `FunctionInvocationContext.tools` mutably drives next iteration. Sign: docstrings warn "do not reassign" but code does not enforce. Consequence: one hook corrupts all downstream.

- **Fail-open silent swallow.** Crewai `dispatch` catches all non-`HookAborted` exceptions and returns `False` (`lib/crewai/src/crewai/hooks/dispatch.py:284`), verbose-only warning. Consequence: buggy hook appears to have run; tests must set `verbose=True` to see it.

- **Global singleton leakage in multi-tenant processes.** Crewai `set_memory_storage_factory` (`lib/crewai/src/crewai/memory/storage/factory.py:33`), openai-agents-sdk `GLOBAL_TRACE_PROVIDER` (`src/agents/tracing/setup.py:11`), letta `_experimental_checker`/`_summarizer` globals (`letta/plugins/plugins.py:45`). Sign: factory says "call once at startup."

- **Last-wins silent override.** Openhands `skills_by_name[skill.name] = skill` with only `logger.warning` (`_sdk_inspect/sdk/plugin/plugin.py:159`), `mcpServers` shallow merge. Consequence: plugin quietly disables another.

- **Params ferried as unstructured text.** Openhands appends `"Plugin Configuration Parameters:\n- city: Tokyo"` to the first message (`enterprise/doc/design-doc/plugin-launch-flow.md:343`) because `PluginSource` has no params field. Consequence: no validation, parsing fragile to whitespace.

- **Doc/code drift as a signal of unstability.** Letta README uses `"default"` (`letta/plugins/README.md:18`) while code uses `"target"` (`letta/plugins/plugins.py:19`); experimental checker captured at decoration time (`letta/helpers/decorators.py:27`) so late swaps require `reset_*`. When you cannot trust docs, freeze the contract before inviting third parties.

- **Unbounded or unbounded-by-default limits.** Agent-framework `max_invocations=None` runs `DEFAULT_MAX_ITERATIONS=40` (`python/packages/core/agent_framework/_tools.py:90`), openhands `max_skills=100` raises instead of truncating, langgraph `DeltaChannel` with no saver history breaks reconstruction silently (`libs/checkpoint/langgraph/checkpoint/base/__init__.py:340`).

- **Experimental gating without promotion.** Agent-framework `ExperimentalWarning` on every new surface (`python/packages/core/agent_framework/_feature_stage.py:383`), temporal `experimental` tag on `WithCustomDataStoreFactory`, langfuse `MCP_SERVER_VERSION="0.3.0-unstable"`. Hardening signal: a stable extension guide should exist before third parties build on it.

## Notable Absences

- **No runtime dynamic discovery via `entry_points` or filesystem scan.** Searched across agent-framework, crewai, langgraph, letta, openai-agents-sdk, pydantic-ai with grep for `entry_points`/`importlib.metadata` — only mypy plugin and transitive deps. No source supports `pip install my-plugin && auto-discovered`.

- **No plugin isolation/sandboxing.** Zero sources run plugins in a process, VM, or capability Sandbox. Tool sandbox exists (agent-framework `HyperlightCodeActProvider`, letta `SandboxType.E2B`/`MODAL`, openai-agents-sdk 7 sandbox clients under `src/agents/extensions/sandbox/`, pydantic-ai MCP transport), but *plugins* remain in-process with full `Store`/`Config`/`mcp_config` access (opa `Manager` at `v1/plugins/plugins.go:192`, openhands shared `AgentContext`/`mcp_config`).

- **No versioned stable plugin API with deprecation policy.** No source publishes a `CHANGELOG` for extension contracts, SemVer on `Factory`/`Capability`/`ToolSet`, or `apiVersion` negotiation. Pydantic-ai hints at `get_serialization_name` stability; opa uses `v1/` import path; langfuse self-describes `"0.3.0-unstable"`.

- **No install/enable/disable/update lifecycle outside opa/temporal/startup.** Openhands SDK exposes `install_plugin`/`enable_plugin`/`disable_plugin` in `_sdk_inspect/sdk/plugin/installed.py` but `openhands/app_server/` never calls them; letta has only `reset_*` test helpers.

- **No first-class eval/prompt/policy/UI extension registries in most sources.** Langgraph reports no `BaseEvaluator`/`BasePrompt`/`Policy` (`Q.Impact` gaps at `langgraph.md:159`); crewai notes no OSS `PolicyExtension` despite `plus_api.py`; letta `ToolType` closed enum requires core edits; langfuse keeps `ActionTypeSchema` and `QueueName` closed unions (`packages/shared/src/domain/automations.ts:43`, `queues.ts:342`).

- **No per-plugin observability.** No source records per-plugin latency/error/override counts; only global metrics (temporal persistence `HealthSignalAggregator`, openhands warning on skill override, crewai `HookDispatchedEvent` at `lib/crewai/src/crewai/hooks/dispatch.py:224`).
