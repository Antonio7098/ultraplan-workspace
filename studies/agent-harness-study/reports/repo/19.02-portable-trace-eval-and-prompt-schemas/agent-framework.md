## Summary

Agent Framework is strongest on trace and tool portability, weaker on eval/prompt dataset portability and zero on explicit migration tooling. Traces are natively OpenTelemetry with GenAI semantic conventions, OTLP gRPC/HTTP exporters, and standard `OTEL_*` env vars — fully vendor-agnostic and movable to any OTLP collector. Tool schemas are canonical JSON Schema produced from Pydantic via `FunctionTool.parameters()` and translated per-provider (OpenAI `FunctionToolParam`, Anthropic `input_schema`, Bedrock `inputSchema.json`, Gemini `FunctionDeclaration`) so the same `@tool` definition runs across OpenAI/Anthropic/Bedrock/Gemini/Ollama without rewrite. Eval is intentionally provider-agnostic at the core (`Evaluator` protocol, `EvalItem`/`LocalEvaluator`/`AgentEvalConverter`) but the only cloud implementation is `FoundryEvals` tied to the OpenAI Evals API + Foundry `azure_ai_*` data sources, and prompt templates are limited to plain `instructions: str` on `Agent` and experimental declarative YAML `kind: Prompt` (not Jinja/Mustache/LangChain standard). No export/import or migration CLI exists to move traces/evals/prompts between platforms as bulk assets.

## Rating

**5/10** — Present but inconsistent, weakly documented, and fragile for migration. Trace format is mature and durable (OTel + OTLP dual protocol with env-var fidelity). Tool schemas are portable via JSON Schema + per-provider adapters. Eval core is clean and testable but cloud path is Foundry-locked; datasets are in-memory `EvalItem` objects with ad-hoc JSONL file-content mapping, not a stable portable file schema. Prompt templating has no standard library, no versioning, and MCP prompts are thin wrappers. No `export_traces`/`import_eval_dataset`/`migrate_prompts` tooling; migration is manual `to_dict`/`from_dict` or copy-paste YAML.

## Answers to Dimension Questions

**1. Can traces be moved between platforms?**
Partially — **yes for telemetry, no for history.** The framework emits vendor-neutral OTel traces (GenAI semconv: `gen_ai.operation.name`, `gen_ai.tool.*`, `gen_ai.usage.*` in `python/packages/core/agent_framework/observability.py:176-314`) and supports both OTLP/gRPC and OTLP/HTTP/protobuf via `_create_otlp_exporters` (`python/packages/core/agent_framework/observability.py:365-484`) with standard env vars (`OTEL_EXPORTER_OTLP_ENDPOINT`, per-signal overrides, HTTP `/v1/{signal}` handling at `python/packages/core/agent_framework/observability.py:606-610`). Any OTLP collector (Jaeger, Tempo, Honeycomb, Azure Monitor, Datadog) can ingest them without rewrite, and `propagate.inject` pushes trace context into MCP calls (`python/packages/core/agent_framework/_mcp.py:294`). However, conversation history is not a trace: `AgentSession`/`HistoryProvider` serializes via `Message.to_dict` to JSONL/memory (`python/packages/core/agent_framework/_sessions.py:96-120`) with no OTel-to-LangSmith/Langfuse trace importer/exporter helper, and `evaluate_traces(trace_ids=...)` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:975-1063`) assumes traces already in Azure App Insights via `azure_ai_traces` datasource — no `trace.export(format="opentelemetry-json")` tool exists.

**2. Can eval datasets be reused across systems?**
Weakly. Core types are portable: `EvalItem(conversation, tools, context, expected_output, expected_tool_calls, split_strategy)` (`python/packages/core/agent_framework/_evaluation.py:200-216`) is provider-agnostic, `ConversationSplit.LAST_TURN/FULL` plus custom `ConversationSplitter` protocol (`python/packages/core/agent_framework/_evaluation.py:76-136`) decouples query/response boundaries, `LocalEvaluator` runs pure-Python checks (`keyword_check`, `tool_called_check` at `python/packages/core/agent_framework/_evaluation.py:1061-1150`) with no cloud, and `AgentEvalConverter.convert_messages` normalizes `Content` to `{"type":"text"|"tool_call"|"input_image"}` (`python/packages/core/agent_framework/_evaluation.py:742-830`). Reuse requires manual conversion: `FoundryEvals._evaluate_via_dataset` builds Foundry-specific dicts with `query_messages`/`response_messages`/`tool_definitions` JSONL and `data_mapping: "{{item.query_messages}}"` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:898-944`) keyed to `azure_ai_evaluator` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:225-306`). No HuggingFace `datasets`, LangSmith `Dataset`, or Evidently adapter, no `EvalDataset.save(path, format="jsonl"|"csv"|"hf")`, and `EvalItem` has no `to_dict`/`from_dict` dataset serializer — the only `to_dict` is on `Message`/`Content` level. `AgentEvalConverter.to_eval_item` (`python/packages/core/agent_framework/_evaluation.py:883-927`) is the closest bridge but still Foundry-oriented.

**3. Can prompts be migrated?**
Barely. Runtime prompts are `Agent(instructions="You are...")` strings (`python/packages/core/agent_framework/_agents.py:604`) — portable as raw text but with no template engine (no Jinja, Mustache, Handlebars, or `PromptTemplate` class), no variable contract (`{{variable}}` parsing), and no version registry. Declarative YAML adds `kind: Prompt` (`declarative-agents/agent-samples/openai/OpenAI.yaml:1-7`) with `instructions`, `model.provider`, `outputSchema` but is experimental, provider-locked, and lacks `prompt_version`/`prompt_registry` semantics. MCP prompts are converted to `FunctionTool`s via `_get_input_model_from_mcp_prompt` (`python/packages/core/agent_framework/_mcp.py:133`) and callable via `get_prompt` (`python/packages/core/agent_framework/_mcp.py:2208`) — usable but not a portable prompt library format (no LangChain Hub, PromptLayer, or dotprompt interop). No `prompt.export(format="jinja")` or `prompt.import` helpers found.

**4. Are tool schemas provider-independent?**
Yes — strongest pillar. Authoring is single-source: `FunctionTool` generates JSON Schema from Pydantic `model_json_schema()` (cached at `python/packages/core/agent_framework/_tools.py:784-807`) or accepts raw dict schema via `@tool(schema=...)` (`python/packages/core/agent_framework/_tools.py:1135-1185`) and exposes uniform `parameters()` + `to_json_schema_spec()` (`python/packages/core/agent_framework/_tools.py:869-883`). `normalize_tools` (`python/packages/core/agent_framework/_tools.py:941-1005`) collapses callables/dicts/`MCPTool`/collections into `FunctionTool` list. Each provider client translates identically-sourced JSON Schema to its wire idiom: OpenAI `FunctionToolParam(name, parameters, description)` (`python/packages/core/agent_framework/openai/_chat_client.py:920-926`), Anthropic `{"type":"custom","input_schema": tool.parameters()}` (`python/packages/anthropic/agent_framework_anthropic/_chat_client.py:891-896`), Bedrock `{"inputSchema":{"json": tool.parameters()}}` (`python/packages/bedrock/agent_framework_bedrock/_chat_client.py:206-210`), Gemini `FunctionDeclaration(parameters=tool.parameters())` (`python/packages/gemini/agent_framework_gemini/_chat_client.py:330-350`), Ollama `FunctionTool` passthrough (`python/packages/ollama/agent_framework_ollama/_chat_client.py:120-150`). Limitations remain: `tool_choice`/`allow_multiple_tool_calls`/`allowed_tools` semantics differ per provider (e.g., Anthropic warns `allowed_tools is not supported` at `python/packages/anthropic/agent_framework_anthropic/_chat_client.py:933`), and hosted tools (MCP/OpenAPI/code_interpreter) are provider-executed, not local `FunctionTool.invoke` parity.

## Architectural Decisions

- **OTel as trace lingua franca** (`python/packages/core/agent_framework/observability.py:176-314`; `docs/decisions/0003-agent-opentelemetry-instrumentation.md:58-75`): Chose delegating `OpenTelemetryAgent`-style instrumentation following `Microsoft.Extensions.AI` with GenAI/MCP semconv, keeping telemetry optional and non-invasive; trades explicit `configure_otel_providers` call for zero overhead when disabled.
- **JSON Schema as tool canonical form** (`python/packages/core/agent_framework/_tools.py:869-903` + `docs/decisions/0002-agent-tools.md:395`): All paths converge on `{"type":"function","parameters": JSON Schema}` so one decorator covers every Chat Client; dict-schema escape hatch avoids Pydantic lock-in.
- **Provider-agnostic `Evaluator` + cloud adapter** (`python/packages/core/agent_framework/_evaluation.py:682-725` + `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:728-840`): Core protocol lives in `agent_framework`; `FoundryEvals` adapts to OpenAI Evals API (`custom` vs `azure_ai_source` scenarios) — keeps core testable with `LocalEvaluator` while delegating hosted evaluation to Foundry.
- **Conversation as eval source-of-truth** (`python/packages/core/agent_framework/_evaluation.py:182-216`): `EvalItem.conversation` + `ConversationSplitter` avoids separate query/response columns; `split_messages` is pluggable for per-turn or pre-memory slices, enabling `per_turn_items` without duplicating data.
- **Declarative `kind: Prompt` as file-format rather than SDK API** (`declarative-agents/agent-samples/openai/OpenAI.yaml:1-7`; `python/packages/declarative/agent_framework_declarative/__init__.py:1-14`): Experimental YAML loading via `AgentFactory` favors file portability over in-code templating; defers Jinja/Handlebars standardization to future.
- **MCP prompts → `FunctionTool`** (`python/packages/core/agent_framework/_mcp.py:133-158`): Reuses tool invocation pipeline for prompts, keeping `FunctionInvocationContext` propagation uniform; trades prompt semantics (messages) for tool-call ergonomics.

## Notable Patterns

- **Sticky disable for observability** (`python/packages/core/agent_framework/observability.py:829-948`): `disable_instrumentation()` sets `_user_disabled` flag that survives `enable_instrumentation`/`enable_sensitive_telemetry` without `force=True` — prevents auto-setup from re-enabling user-opt-out telemetry.
- **HTTP base-url compensation** (`python/packages/core/agent_framework/observability.py:542-552`): Replicates OTel SDK `/v1/{signal}` append for `http/protobuf` when `OTEL_EXPORTER_OTLP_ENDPOINT` is a base URL but leaves signal-specific env vars verbatim — env-var fidelity pattern.
- **`SerializationMixin` dependency injection** (`python/packages/core/agent_framework/_serialization.py:392-560`): `from_dict(dependencies={"function_tool":{"func": fn}})` injects non-serializable `func`/`client` at deserialize time via `INJECTABLE` set, allowing `Message`/`FunctionTool` to round-trip without persisting callables.
- **Allowlist-from-schema for MCP** (`python/packages/core/agent_framework/_mcp.py:115-125` + `243-313`): Tool args filtered to `inputSchema.properties` + `additional_tool_argument_names`, `_MCP_FRAMEWORK_DENYLIST` stripped even if declared — prevents server-declared `thread`/`conversation_id` clobbering.
- **`@evaluator` function-wrapper pattern** (`python/packages/core/agent_framework/_evaluation.py:1284-1352`): `_resolve_function_args` inspects `fn` signature to inject `query/response/conversation/tools/context` by name, `_coerce_result` accepts `bool|float|CheckResult|dict{score,passed}` — minimal boilerplate for custom checks.

## Tradeoffs

- **OTel vendor-neutral vs optional SDK**: Core depends on `opentelemetry-api` only; `opentelemetry-sdk` + `opentelemetry-exporter-otlp-*` are extras (`python/scripts/dependencies/_dependency_bounds_runtime.py:33-34`). Traces are portable once SDK is installed, but cold environments without extras silently drop spans (tests `skipif` at `python/packages/core/tests/core/test_observability.py:1009`).
- **Single JSON Schema vs provider fidelity**: Canonical schema defers provider edge cases to per-client translators; system-instruction placement, `tool_choice: allowed_tools`, `disable_parallel_tool_use`, and hosted MCP/OpenAPI execution still differ and require conditional code.
- **Conversational eval truth vs dataset standards**: Storing `Message`/`Content` preserves modality (text/image/tool_call) and enables `split_before_memory` custom splitters, but lacks Arrow/Parquet/HF Datasets schema, `DatasetInfo`, or `Evaluator` registry — interop with LangSmith/Evidently is manual.
- **YAML Prompt portability vs feature depth**: Declarative `kind: Prompt` migrates across filesystems via `AgentFactory.create_agent_from_yaml_path` but locks `model.provider` and `connection` to env-var PowerFx `=Env.*` expressions and experimental parsing — no variable typing, no A/B routing, no Hub import.
- **Prompt-as-tool reuse**: Mapping MCP `Prompt` to `FunctionTool` unifies invocation and sampling guardrails but loses prompt-specific semantics (template rendering, list of messages) downstream of `parse_prompt_results`.
- **No migration tooling vs surface area**: Avoiding `agent-framework migrate --traces` keeps the package lean, but users must hand-roll OTLP-to-file export, JSONL dataset reshaping, and prompt-variable extraction.

## Failure Modes / Edge Cases

- **Traces never exported when extras missing**: Importing `opentelemetry.exporter.otlp.proto.grpc.*` raises `ImportError` with helpful message (`python/packages/core/agent_framework/observability.py:420-424`) but `OBSERVABILITY_SETTINGS._executed_setup` stays `False`; subsequent `configure_otel_providers` without SDK silently no-ops after warning — `SENSITIVE_DATA_ENABLED` checks pass but spans are no-ops.
- **Sensitive data leak on console exporter**: `enable_sensitive_data=True` + `enable_console_exporters=True` dumps `gen_ai.input.messages`/`tool.arguments` to stdout (`python/packages/core/agent_framework/observability.py:864-869`); sticky disable is only defense if called early.
- **Tool schema `additionalProperties: false` over-strict**: `_validate_arguments_against_schema` rejects unexpected fields (`python/packages/core/agent_framework/_tools.py:1112-1115`) — a server evolution adding optional args breaks previously-valid calls unless schema is updated; `oneOf`/`anyOf` not enforced so some invalid payloads pass.
- **MCP `additionalProperties: true` requires explicit allowlist**: Tool with no `properties` forwards zero args unless `additional_tool_argument_names` is configured (`python/packages/core/AGENTS.md` MCPTool notes) — model may supply correct args but they are dropped, causing silent tool misfire.
- **Eval item split on wrong message**: `_split_last_turn` searches for last `role=="user"` (`python/packages/core/agent_framework/_evaluation.py:156-164`); conversations ending with `tool` or `assistant` still split at prior user, but multi-turn tool-heavy trajectories evaluated with `LAST_TURN` may misattribute earlier tool calls to current response; custom splitter required.
- **Foundry eval polling timeout**: `_poll_eval_run` returns `EvalResults(status="timeout")` after `timeout` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:383-424`) — `raise_for_status` then raises `EvalNotPassedError` masking partial `per_evaluator` counts unless `fetch_output_items=True` was paginated before timeout.
- **Rubric dimension key drift**: `_RUBRIC_DIMENSION_KEYS = ("dimension_scores","rubric_scores")` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:450-458`) — handles preview `rubric_scores` vs GA `dimension_scores`, but future renaming breaks `_extract_rubric_scores` returning `None` and `assert_dimension_score_at_least` silently skipping non-applicable dimensions unless `require_applicable=True`.
- **Deserialization without registered state type**: `AgentSession.from_dict` relies on `_STATE_TYPE_REGISTRY` (`python/packages/core/agent_framework/_sessions.py:42-90`); Pydantic models not pre-registered via `register_state_type` deserialize as plain dicts on cold start, losing `to_dict` behavior for eval context round-trips.

## Future Considerations

- Ship a **`PromptTemplate` + registry** (Jinja/Mustache with typed variables, `prompt_version`, `prompt_hub://` URI) as stable core — decouple `instructions` from `Agent` and make declarative `kind: Prompt` provider-agnostic with `template_engine` field.
- Add **portable trace file export** (`tracer.export(format="otlp-json"|"parquet", path=...)`) and **history exporter** (`HistoryProvider.export(format="langsmith"|"langfuse"|"otel")`) alongside current OTLP live export, with matching `import` that rehydrates `Message` via `SerializationMixin.from_dict`.
- Introduce **`EvalDataset` abstraction** with stable schema (`id, query, response_messages, context, ground_truth, tool_definitions`) and helpers `EvalDataset.from_hf`, `to_jsonl`, `to_langsmith`, plus validation against `_build_item_schema` to decouple dataset creation from `FoundryEvals` internals.
- Provide **`Evaluator` adapters** beyond Foundry (e.g., `LangSmithEvaluator`, `EvidentlyEvaluator`, `LocalLLMJudgeEvaluator`) demonstrating `convert_messages` → provider API mapping pattern from `AgentEvalConverter`.
- Generate **prompt + dataset migration CLI** (`python -m agent_framework migrate --from langchain --to agent-framework`) covering `@tool` decorator retention, `ChatPromptTemplate` → `PromptTemplate`, and `Dataset` → `EvalItem` batch conversion with dry-run validation.
- Extend `_get_input_model_from_mcp_prompt` to emit full `PromptTemplate` metadata (role, message sequence) instead of collapsing to `FunctionTool`, and document `parse_prompt_results` contract for round-tripping MCP prompt results as portable `Message[]`.
- Unify rubric score ingestion to single canonical key (`dimension_scores`) once Foundry GA is confirmed and add contract test against live `OutputItemListResponse` to catch future `properties.*` renames.
