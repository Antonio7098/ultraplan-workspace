## Summary

Temporal exposes a layered public API with three distinct surfaces. (1) Application developers speak to the server through two wire-level services — `WorkflowService` and `OperatorService` — defined in the *external* proto module `go.temporal.io/api` and registered on the frontend gRPC listener (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:479-483`). Those same two services are mirrored over HTTP/JSON through a grpc-gateway mux that calls them in-process via an inline `ClientConn` (`studies/agent-harness-study/sources/temporal/service/frontend/http_api_server.go:146-175`), and an OpenAPI 2.0 / 3.0 spec is served from the same listener with per-API rate limiting (`studies/agent-harness-study/sources/temporal/service/frontend/openapi_http_handler.go:33-67`). (2) Operators use the `temporal-server` CLI built by `cmd/server`, which exposes `start`, `render-config`, and `validate-dynamic-config` subcommands (`studies/agent-harness-study/sources/temporal/cmd/server/main.go:80-246`) plus `tdbg` (`studies/agent-harness-study/sources/temporal/tools/tdbg/app.go:34`) for cluster debugging. (3) Embedders — code that wants to launch a Temporal server inside another binary — call `temporal.NewServer(opts...)` and get back a minimal three-method `Server` interface (`studies/agent-harness-study/sources/temporal/temporal/server.go:15-19,44-46`); the test-server companion package `temporaltest` documents its Go-API backwards-compatibility promise explicitly (`studies/agent-harness-study/sources/temporal/temporaltest/README.md:5-8`).

The boundary between public and internal is *structural at the wire level* but only *conventional at the Go level*. Frontend-facing protos come from `go.temporal.io/api v1.62.15-0.20260615235047-378792ab2240` (`studies/agent-harness-study/sources/temporal/go.mod:67`), while inter-service protos (history, matching, internal admin) live in `proto/internal` and get generated into `api/` (`studies/agent-harness-study/sources/temporal/proto/internal/buf.yaml:9-14` and `api/adminservice/v1/service.pb.go:1`). The contributor doc formalises the rule: "Either in the `api` repo (for frontend) or here in `proto/internal` (for history/matching)" (`studies/agent-harness-study/sources/temporal/docs/development/new-rpcs.md:6-8`). However, every Go package ships in one module and is importable by consumers — there is no `internal/` directory enforcing the boundary except in `temporaltest/internal` (`studies/agent-harness-study/sources/temporal/temporaltest/internal/lite_server.go:1` and `studies/agent-harness-study/sources/temporal/temporal/fx.go:156` exporting `NewServerFx`). The project compensates with module retracts for accidentally-published versions (`studies/agent-harness-study/sources/temporal/go.mod:5-8`), explicit "experimental" labels on four server options (`studies/agent-harness-study/sources/temporal/temporal/server_option.go:146,160,168,176`), and dynamic-config feature gates on every unfinished RPC (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:167-243`). One concrete accidental leak exists: the production `client.Factory` interface requires a `testhooks.TestHooks` parameter even in non-test builds (`studies/agent-harness-study/sources/temporal/client/clientfactory.go:23,45`), which means test plumbing is part of the stable Go surface for anyone implementing `WithClientFactoryProvider`.

## Rating

**7 / 10** — Clear model with explicit interfaces and operational safeguards.

Rationale: The wire API is disciplined and durable. The external `go.temporal.io/api` module is pinned by pseudo-version (`studies/agent-harness-study/sources/temporal/go.mod:67`), generated wrappers for every new RPC mechanically route through quotas/interceptors (`studies/agent-harness-study/sources/temporal/client/frontend/client.go:1-2`), per-RPC dynamic-config gating keeps unfinished RPCs out of the default surface (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:167-243`), and a contributor checklist enforces the seven-step "add a new RPC" path (`studies/agent-harness-study/sources/temporal/docs/development/new-rpcs.md:6-16`). Health-based draining shutdown gives clients a stable lifecycle contract (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:514-559`). The package loses points because: (a) the Go-level boundary is conventional only — no `internal/` partition outside `temporaltest/internal`, and test hooks leak into production signatures (`studies/agent-harness-study/sources/temporal/client/clientfactory.go:23,45`); (b) only the `temporaltest` package carries an explicit stability policy (`studies/agent-harness-study/sources/temporal/temporaltest/README.md:5-8`); no `stable|stability|compat|public api|experimental` matches exist in `CONTRIBUTING.md`, `AGENTS.md`, or `docs/README.md`; (c) runnable embedder examples are off-repo, with the only in-repo usage being `cmd/server/main.go:222-234`.

## Answers to Dimension Questions

**1. What is the intended public API surface?**

Three tiers. (a) For application developers: the frontend's gRPC `WorkflowService` and `OperatorService` registered at `studies/agent-harness-study/sources/temporal/service/frontend/service.go:479,481`, duplicated over HTTP/JSON via the in-process gateway (`studies/agent-harness-study/sources/temporal/service/frontend/http_api_server.go:159-175`) with an OpenAPI spec for discoverability (`studies/agent-harness-study/sources/temporal/service/frontend/openapi_http_handler.go:56-67`). The Nexus HTTP routes — `/namespaces/{namespace}/nexus-services` and `/nexus/callback` — extend that HTTP API but are explicitly flagged experimental (`studies/agent-harness-study/sources/temporal/docs/architecture/nexus.md:22`). Workflow/activity authoring happens via out-of-repo language SDKs (`studies/agent-harness-study/sources/temporal/README.md:64`). (b) For operators: the `temporal-server` binary (`start`, `render-config`, `validate-dynamic-config`; `studies/agent-harness-study/sources/temporal/cmd/server/main.go:80-246`), the YAML config templates under `studies/agent-harness-study/sources/temporal/config/`, and the `tdbg` CLI built from `tools/tdbg/app.go:34`. (c) For embedders/test authors: `temporal.NewServer` + options (`studies/agent-harness-study/sources/temporal/temporal/server.go:44`) and the `temporaltest` package with its stability policy (`studies/agent-harness-study/sources/temporal/temporaltest/server.go:132`, `temporaltest/README.md:5-8`).

**2. Is the stable API easy to distinguish from internal implementation details?**

At the wire level, yes — structurally. Public frontend protos live in the external `go.temporal.io/api` module while inter-service RPCs are generated from in-tree `proto/internal` (`studies/agent-harness-study/sources/temporal/docs/development/new-rpcs.md:6-8`, `studies/agent-harness-study/sources/temporal/proto/internal/buf.yaml:7-14`); the `AdminService` is registered on the same listener as public APIs (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:480`) but its import path `go.temporal.io/server/api/adminservice/v1` marks it as server-owned. At the Go level, no: a single module ships every package, stability prose exists only for `temporaltest` (`studies/agent-harness-study/sources/temporal/temporaltest/README.md:5-8`), and nothing in `CONTRIBUTING.md`, `docs/README.md`, or `AGENTS.md` states a compatibility policy for `go.temporal.io/server` (grep for `stable|stability|compat|public api|experimental|backward` returns zero matches in those files; only `temporaltest/README.md` mentions `backward`). Experimental labels exist but only on four of ~19 options (`studies/agent-harness-study/sources/temporal/temporal/server_option.go:146-176`); `chasm/`, a large framework that re-defines core abstractions, carries no stability marker on its root files and is used by production services (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:12-14`) while still being importable by anyone who finds the path.

**3. Does the API expose the right level of abstraction for agent harness users?**

Mostly yes. The embedding API hides all service wiring behind narrow extension interfaces — `Authorizer` (`studies/agent-harness-study/sources/temporal/common/authorization/authorizer.go:54-56`), `ClaimMapper`, `JWTAudienceMapper`, data-store factories, chained frontend interceptors, metrics handler (`studies/agent-harness-study/sources/temporal/temporal/server_option.go:97-214`) — and the `Server` interface is deliberately tiny (`Start() error` / `Stop() error`; `studies/agent-harness-study/sources/temporal/temporal/server.go:15-19`). Two leaks reduce quality: `NewServerFx(topLevelModule fx.Option, ...)` puts the uber-fx container type into an exported signature (`studies/agent-harness-study/sources/temporal/temporal/fx.go:156-168`), and `WithClientFactoryProvider(client.FactoryProvider)` hands embedders an interface whose `NewFactory` method takes test infra alongside production dependencies (`studies/agent-harness-study/sources/temporal/client/clientfactory.go:38-50`). Feature gating via dynamicconfig (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:167-243`) is the right mechanism for evolving RPCs without breaking clients, but inflates the exported `Config` to ~200 fields that are themselves part of the embedding surface (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:30-247`).

**4. Are examples sufficient to use the API correctly without reading internals?**

For wire-API consumers, yes indirectly: the OpenAPI spec is served by the server itself (`studies/agent-harness-study/sources/temporal/service/frontend/openapi_http_handler.go:56-67`) and the official samples/CLI docs are linked from the README (`studies/agent-harness-study/sources/temporal/README.md:42-56`). For embedders, marginal: the only in-repo usage example is `cmd/server/main.go:222-234`, and there is no runnable embedding example directory. For test authors, `temporaltest/server.go:132-171` is its own minimal example. Documentation snippets are extracted from source comments via `@@@SNIPSTART`/`@@@SNIPEND` markers (`studies/agent-harness-study/sources/temporal/common/authorization/authorizer.go:21,52`; `claim_mapper.go:15,27`; `roles.go:5,23`; `common/config/config.go:665`), which keeps the published docs synchronized with the implementation but requires reading source layout to know which interfaces are meant to be implemented.

## Architectural Decisions

1. **Public protocol lives in a separate repository/module.** All frontend-facing types come from `go.temporal.io/api v1.62.15-...` pinned by pseudo-version (`studies/agent-harness-study/sources/temporal/go.mod:67`), letting the wire API evolve on an independent versioning cadence from server internals.
2. **Internal protocols vendored and generated in-tree.** Inter-service protos live under `proto/internal` and are generated into `api/` with `DO NOT EDIT` headers (`studies/agent-harness-study/sources/temporal/proto/internal/buf.yaml:7-14`, `studies/agent-harness-study/sources/temporal/api/adminservice/v1/service.pb.go:1`), refreshed via `make proto` / `make update-go-api` (`studies/agent-harness-study/sources/temporal/Makefile:27,341`).
3. **One listener, tiered services.** The frontend gRPC endpoint co-serves public (Workflow/Operator), semi-public (Admin), and infrastructure (health, reflection) APIs (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:478-483`), relying on authz/rate-limiting interceptors rather than network separation.
4. **HTTP as a projection of gRPC.** Rather than a second hand-written API, the JSON gateway binds generated handlers to an inline in-process `ClientConn` (`studies/agent-harness-study/sources/temporal/service/frontend/http_api_server.go:146-163`), guaranteeing parity between gRPC and HTTP semantics.
5. **Feature flags over forks.** New RPCs ship dark behind dynamicconfig keys and named experiments (`EnableChasm`, `EnableDeployments`, `ChasmSchedulerExperiment`; `studies/agent-harness-study/sources/temporal/service/frontend/service.go:167-186`, `experiments.go:5-6`), keeping the default API surface stable.
6. **Docs embedded in source.** Snippet markers in authorization/config code feed the documentation site so published excerpts cannot drift from implementation (`studies/agent-harness-study/sources/temporal/common/authorization/authorizer.go:21,52`; `common/config/config.go:665`).
7. **Retraction as a recovery tool.** Accidental publishes are handled with Go module retracts rather than pretend-they-didn't-happen (`studies/agent-harness-study/sources/temporal/go.mod:5-8`).

## Notable Patterns

- **Functional-options API** for both the real server (`studies/agent-harness-study/sources/temporal/temporal/server_option.go:35-211`) and the test server (`studies/agent-harness-study/sources/temporal/temporaltest/options.go:23-50`), giving one idiom across surfaces.
- **Generated wrapper/interceptor layer per service**: each new RPC mechanically gains metric scoping, timeouts, and quota routing via `genrpcwrappers` output and a documented modification checklist (`studies/agent-harness-study/sources/temporal/client/frontend/client.go:1-2`; `studies/agent-harness-study/sources/temporal/docs/development/new-rpcs.md:6-16`).
- **Graceful-drain shutdown contract**: health status flips first, peers detect failure, then gRPC/HTTP drain for a configured window before hard stop (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:514-559`) — the lifecycle side of the API that clients actually observe.
- **Go `internal/` used surgically**: `temporaltest/internal.LiteServer` is compiler-hidden from consumers while the public wrapper remains stable (`studies/agent-harness-study/sources/temporal/temporaltest/server.go:16`; `studies/agent-harness-study/sources/temporal/temporaltest/internal/lite_server.go:1`).
- **Back-compat carve-outs stated explicitly**: e.g., `WithBaseServerOptions` is exempted from the otherwise strict `temporaltest` compatibility promise (`studies/agent-harness-study/sources/temporal/temporaltest/README.md:5-8`).
- **Deprecated-but-functional flags**: old CLI flags remain wired with explicit warnings for backward compatibility (`studies/agent-harness-study/sources/temporal/cmd/server/main.go:45-67,130-162`).
- **Doc-snippet markers**: `@@@SNIPSTART`/`@@@SNIPEND` blocks guarantee that excerpted documentation tracks code without manual copy (`studies/agent-harness-study/sources/temporal/common/authorization/authorizer.go:21,52`).

## Tradeoffs

- **Single-module convenience vs enforced boundaries.** Everything importable means fast internal refactoring and simple releases, but consumers can (and do) bind to internals; the project compensates culturally (docs, labels) rather than structurally, evidenced by the need to retract releases (`studies/agent-harness-study/sources/temporal/go.mod:5-8`).
- **Co-hosted admin API vs blast radius.** Registering `AdminService` next to public APIs simplifies deployment (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:480`) but means a misconfigured authorizer exposes destructive cluster operations on the public port; mitigation lives in interceptor/authz layers rather than topology.
- **Feature-gate richness vs configuration explosion.** Dynamicconfig gating lets unfinished RPCs ship safely, but the exported frontend `Config` spans ~200 tunables including keep-alive, deletion, and CHASM rollout knobs (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:30-247`), which is itself a public-ish surface embedders must navigate.
- **Source-embedded doc snippets vs doc completeness.** Snippets guarantee accuracy for the excerpted interfaces (`studies/agent-harness-study/sources/temporal/common/authorization/authorizer.go:21,52`) but leave non-snippetted packages (e.g., `chasm/`) with thin guidance despite being architecturally significant (`studies/agent-harness-study/sources/temporal/docs/architecture/chasm.md:1-40` describes intent, not stability).

## Failure Modes / Edge Cases

- **Accidental publish of unstable versions**: already happened twice per retract comments ("Contains retractions only", "Published accidentally"; `studies/agent-harness-study/sources/temporal/go.mod:5-8`). Consumers pinning those versions break on upgrade.
- **Test concerns coupled to production signatures**: any change to `testhooks.TestHooks` ripples through `client.Factory`, its mock, and `WithClientFactoryProvider` users (`studies/agent-harness-study/sources/temporal/client/clientfactory.go:23,45,85`; `studies/agent-harness-study/sources/temporal/client/client_factory_mock.go:169-180`), turning test refactors into breaking API changes.
- **Silent behavioral divergence between gRPC and HTTP paths**: the gateway forwards only matched headers plus configured extras (`studies/agent-harness-study/sources/temporal/service/frontend/http_api_server.go:52-57,130-143`); unconfigured custom headers vanish, which callers may only notice in production auth flows.
- **Deprecated flags still accepted**: `--services` (hidden) silently overrides `--service` with a warning path (`studies/agent-harness-study/sources/temporal/cmd/server/main.go:130-162`); scripts relying on it will fail when removed, and nothing enforces migration.
- **Unlabeled experimental frameworks**: `chasm/` packages are imported by production services today (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:12-14`) yet carry no stability annotation, so external importers get no warning before churn; the chasm `Registry` itself comments that some methods are "NOT CHASM library developers" but still ships them in the same package (`studies/agent-harness-study/sources/temporal/chasm/registry.go:114-202`).
- **Health-check-driven drain depends on peer detection timing**: stop sequence sleeps for `ShutdownFailHealthCheckDuration` before draining (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:523-531`); mis-tuned values either drop in-flight requests or extend deploy time.

## Future Considerations

- Introduce `internal/` package partitioning (as done for `temporaltest/internal`) or a lint-enforced allowlist of consumer-safe packages to make the Go-level boundary mechanical rather than conventional.
- Add stability statements for `go.temporal.io/server` top-level packages (`temporal/`, `temporaltest/` precedent shows the team can write these policies).
- Stabilize or de-experimentalize the four flagged server options; document a graduation process from `AllowedExperiments` gating to default-on (`studies/agent-harness-study/sources/temporal/service/frontend/service.go:252-260,416-417`).
- As CHASM grows new wire APIs (an `api/chasm` tree already exists alongside scheduler/deployment experiments, `studies/agent-harness-study/sources/temporal/api/chasm/v1/message.pb.go:1`), decide whether they graduate into the external `go.temporal.io/api` module and apply the same pseudo-version discipline.
- Provide an in-repo embedding example (beyond `cmd/server/main.go:222-234`) demonstrating authorizer, custom data-store factory, and interceptor wiring end-to-end.
