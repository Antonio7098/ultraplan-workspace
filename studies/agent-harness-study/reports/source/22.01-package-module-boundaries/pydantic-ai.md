## Summary

pydantic-ai is a `uv` workspace containing four published packages (`pydantic-ai`, `pydantic-ai-slim`, `pydantic-evals`, `pydantic-graph`) plus a CLI (`clai`) and examples package (`examples`). The package boundaries are well-defined: `pydantic-graph` is the low-level graph library with no pydantic-ai dependency; `pydantic-ai-slim` is the slim agent framework that depends on `pydantic-graph`; `pydantic-evals` depends on `pydantic-ai-slim`; the meta-package `pydantic-ai` re-exports all of the above plus all optional provider groups. Inside `pydantic-ai-slim/pydantic_ai/`, modules are organized by responsibility (`agent/`, `models/`, `providers/`, `profiles/`, `toolsets/`, `tools.py`, `messages.py`, `capabilities/`, `native_tools/`, `embeddings/`, `ui/`, `durable_exec/`, `common_tools/`, `ext/`, `_cli/`). A clear public/private separation is enforced through leading-underscore file naming (`_agent_graph.py`, `_output.py`, `_messages.py`-style private modules are absent, but underscore-prefixed symbols dominate `_utils.py`), explicit `__all__` tuples, `py.typed` markers, and module-level `__getattr__` deprecation shims. Dependencies flow strictly in one direction (`graph ← slim ← evals`, `core ← ui ← adapters`, `tools/native_tools ↔ toolsets/capabilities` via wrappers), and circular imports are documented and resolved through TYPE_CHECKING blocks and lazy imports.

## Answers to Dimension Questions

### 1. Are modules cleanly separated?

Yes — by responsibility and dependency direction. The ownership map (`agent_docs/pydantic-ai-slim.md:7-17`) puts `Agent` in `agent/__init__.py`, the loop in `_agent_graph.py`, tool mechanics in `tool_manager.py`/`tools.py`/`toolsets/`, output in `output.py`/`_output.py`, the message protocol in `messages.py`, provider wiring in `models/`/`providers/`, capability facts in `profiles/`, cross-cutting behavior in `capabilities/`, durable adaptations in `durable_exec/`, and UI protocol translations in `ui/`. Optional concerns sit behind their own subpackage: `embeddings/`, `native_tools/`, `common_tools/`, `ext/`, `_cli/`. The split is reinforced by per-subpackage `AGENTS.md` files.

### 2. Do dependencies flow in one direction?

Yes, at the package level. `pydantic-graph` has no pydantic-ai dependency (`pydantic_graph/pyproject.toml:48-53`); `pydantic-ai-slim` declares `pydantic-graph = { workspace = true }` as a required dep (`pydantic_ai_slim/pyproject.toml:164-165`); `pydantic-evals` declares `pydantic-ai-slim = { workspace = true }` as a required dep (`pydantic_evals/pyproject.toml:71-72`); the meta `pydantic-ai` aggregates everything via `[tool.hatch.metadata.hooks.uv-dynamic-versioning]` (`pyproject.toml:48-64`). Inside `pydantic-ai-slim`, `agent/` depends on `models/`, `tools/`, `toolsets/`, `capabilities/`, `messages/`, etc., but those leaf modules do not import back from `agent/` (verified by the absence of `from ..agent` imports in those leaves; reverse references go through `TYPE_CHECKING` blocks — `pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:26-34`, `pydantic_ai_slim/pydantic_ai/agent/__init__.py:103-109`).

### 3. Can modules be used independently?

Mostly yes. The slim package ships a minimal core deps list (`pydantic_ai_slim/pyproject.toml:55-65`) so a user can install `pydantic-ai-slim` and use only `models.test.TestModel`, `models.function.FunctionModel`, `messages`, `usage`, `exceptions`, `RunContext`, `Tool`, `ToolDefinition`, the toolset wrappers, etc., without pulling any provider SDK. Each provider requires only its named extra (`pydantic_ai_slim/pyproject.toml:67-89`). `pydantic-graph` is fully standalone (no pydantic-ai import anywhere except a comment noting `Unset` was copied — `pydantic_graph/pydantic_graph/_utils.py:116-122`). `pydantic-evals` can be used independently with arbitrary user-defined task functions, only requiring `pydantic-ai-slim` for the LLM-as-judge and dataset generation helpers (`pydantic_evals/pydantic_evals/evaluators/llm_as_a_judge.py:10-12`, `pydantic_evals/pydantic_evals/generation.py:16-17`).

The one caveat: heavy in-process use of `Agent` pulls the whole slim runtime, including `pydantic_graph`, opentelemetry, genai-prices, and griffelib — there is no "agent-without-tracing" sub-distribution.

### 4. Are public APIs distinguished from internal ones?

Yes, via several complementary mechanisms:

- **Underscore-prefixed modules** hold internals (`_agent_graph.py`, `_output.py`, `_function_schema.py`, `_parts_manager.py`, `_tool_search.py`, `_ssrf.py`, `_otel_messages.py`, `_enqueue.py`, `_history_processor.py`, `_system_prompt.py`, `_instructions.py`, `_deferred_capabilities.py`, `_instrumentation.py`, `_deprecated_callable.py`, `_json_schema.py`, `_template.py`, `_thinking_part.py`, `_uuid.py`, `_warnings.py`, `_griffe.py`, `_cli/`, `_mcp.py`).
- **`__all__` tuples** on every public namespace (`pydantic_ai_slim/pydantic_ai/__init__.py:166-341`, `pydantic_ai_slim/pydantic_ai/capabilities/__init__.py:97-151`, `pydantic_ai_slim/pydantic_ai/toolsets/__init__.py:22-39`, `pydantic_ai_slim/pydantic_ai/embeddings/__init__.py:22-34`, `pydantic_graph/pydantic_graph/__init__.py:97-136`, `pydantic_evals/pydantic_evals/__init__.py:13-19`).
- **`py.typed` markers** ship with each published package (`pydantic_ai_slim/pydantic_ai/py.typed`, `pydantic_evals/pydantic_evals/py.typed`, `pydantic_graph/pydantic_graph/py.typed`).
- **Module-level `__getattr__` deprecation shims** route old names to new ones without keeping the old attribute in the namespace (`pydantic_ai_slim/pydantic_ai/__init__.py:348-370`, `pydantic_ai_slim/pydantic_ai/capabilities/__init__.py:154-169`, `pydantic_ai_slim/pydantic_ai/mcp.py:3079-3089`, `pydantic_graph/pydantic_graph/__init__.py:66-94`).
- **`builtin_tools/`** is a deprecation-only module that re-exports nothing from the new `native_tools/` namespace (`pydantic_ai_slim/pydantic_ai/builtin_tools/__init__.py:1-30`).
- **Strict pyright + ruff config** (`pyproject.toml:243-273`) prevents private symbols leaking into the public API contract.

## Architectural Decisions

- **Two-tier distribution** (`pydantic-ai-slim` for minimal-deps installs, `pydantic-ai` as the aggregated meta package): enables deployment scenarios that only need one or two providers, while still giving users a single-command "all batteries included" install (`pyproject.toml:48-64`).
- **Separate `pydantic-graph` package**: graph primitives ship independently so users can build non-agent graphs, and the agent loop can use a stable graph API. The graph package avoids `pydantic_ai` imports entirely (`pydantic_graph/pyproject.toml:48-53`).
- **Capability model replaces deprecated kwargs**: a single composable list (`Agent(capabilities=[...])`) replaces ad-hoc per-feature constructor arguments. The `CombinedCapability` and `CAPABILITY_TYPES` registry pattern enables serialization and lazy resolution (`pydantic_ai_slim/pydantic_ai/capabilities/__init__.py:62-92`).
- **Wrapper composition for toolsets**: every cross-cutting toolset feature is a subclass of `WrapperToolset` (`pydantic_ai_slim/pydantic_ai/toolsets/wrapper.py:14-50`), so any toolset can be wrapped with approval/filtering/prefixing/renaming without modifying the base — a deliberate choice that keeps the base classes lean (`agent_docs/pydantic-ai-slim.md:9`).
- **Per-file providers and models**: a single provider class per file lets each integration evolve independently and lets `infer_provider`/`infer_model` lazily import on demand (`pydantic_ai_slim/pydantic_ai/providers/__init__.py:147-267`, `pydantic_ai_slim/pydantic_ai/models/__init__.py:1099-1158`).
- **Capability facts in `profiles/` not in `models/`**: keeps `models/<provider>.py` focused on wire-format translation and pushes structured-output defaults, native-tool support, and schema quirks into `profiles/<family>.py` (`pydantic_ai_slim/pydantic_ai/profiles/__init__.py:41-180`).
- **Durable exec as compatibility tests**: `durable_exec/temporal/`, `durable_exec/dbos/`, `durable_exec/prefect/` are explicitly framed as compatibility targets rather than peripheral adapters (`pydantic_ai_slim/pydantic_ai/durable_exec/AGENTS.md`).
- **UI adapters translate normalized messages**: `ui/ag_ui/`, `ui/vercel_ai/`, `ui/_web/` each implement one protocol but reuse the same message/event/builder primitives (`pydantic_ai_slim/pydantic_ai/ui/__init__.py:1-31`, `pydantic_ai_slim/pydantic_ai/ui/_adapter.py`, `pydantic_ai_slim/pydantic_ai/ui/_event_stream.py`).
- **Examples as separate workspace member**: avoids polluting slim's `pyproject.toml` deps with example-only requirements (`pyproject.toml:84-90`).

## Notable Patterns

- **Provider/model class-via-dispatch**: `infer_provider_class` and `infer_model` use a single function with chained `if model_kind == '...'` branches and lazy `from .<file> import ...` inside each branch. Avoids loading every SDK at import time (`pydantic_ai_slim/pydantic_ai/providers/__init__.py:114-267`, `pydantic_ai_slim/pydantic_ai/models/__init__.py:1060-1158`).
- **`__init_subclass__` registration**: `AbstractNativeTool.__init_subclass__` (`pydantic_ai_slim/pydantic_ai/native_tools/__init__.py:85-87`) and similar patterns for capabilities populate module-level registries without explicit registration calls. Combined with `Annotated[..., pydantic.Tag(kind)]` unions (`pydantic_ai_slim/pydantic_ai/native_tools/__init__.py:100-105`), this gives discriminated-union deserialization for free.
- **Capability wrapper pattern**: `WrapperCapability` and `Capability` (the convenience dataclass) compose instructions, descriptions, function tools, and toolsets without subclassing (`pydantic_ai_slim/pydantic_ai/capabilities/capability.py:14-100`).
- **Toolset wrapper pattern**: `WrapperToolset` + concrete subclasses (`ApprovalRequiredToolset`, `FilteredToolset`, `PrefixedToolset`, `RenamedToolset`, `PreparedToolset`, `SetMetadataToolset`, `IncludeReturnSchemasToolset`) — the same composability rule, applied to tool collections (`pydantic_ai_slim/pydantic_ai/toolsets/wrapper.py:14-50`).
- **Deprecation-as-`__getattr__`**: legacy symbols (`BuiltinToolCallPart`, `Graph`, `GraphRun`, `MCPServerConfig`, etc.) are kept importable but emit `PydanticAIDeprecationWarning` and route to the new path (`pydantic_ai_slim/pydantic_ai/__init__.py:348-370`, `pydantic_ai_slim/pydantic_ai/capabilities/__init__.py:154-169`, `pydantic_graph/pydantic_graph/__init__.py:66-94`, `pydantic_ai_slim/pydantic_ai/mcp.py:3079-3089`).
- **Provider name normalization centralized**: `gateway/google-vertex` → `google-cloud`, `google-gla` → `google`, `vertexai` → `google-vertex` all live in `infer_provider_class` with inline deprecation warnings (`pydantic_ai_slim/pydantic_ai/providers/__init__.py:114-156`).

## Tradeoffs

- **`pydantic-graph` is required** by `pydantic-ai-slim` (`pydantic_ai_slim/pyproject.toml:60`), so users who don't want the graph dep still get it pulled in. The graph dep is small, but the choice does mean `pydantic-ai-slim` cannot ship without `pydantic-graph`.
- **Two known circular seams** (`tools.py` ↔ `native_tools`, plus the `OpenAICompaction`/`AnthropicCompaction` carve-out from `CAPABILITY_TYPES`) require forward-reference tricks or runtime registration, which complicates static type inference for downstream users (`pydantic_ai_slim/pydantic_ai/capabilities/__init__.py:94-95`, `pydantic_ai_slim/pydantic_ai/capabilities/_tool_search.py:25-28`).
- **Large central `__init__.py`**: `pydantic_ai/__init__.py` re-exports 100+ symbols (`pydantic_ai_slim/pydantic_ai/__init__.py:166-341`). This is a deliberate "one-import" UX but means `import pydantic_ai` triggers loading of every subpackage (`agent`, `models`, `providers`, `profiles`, `toolsets`, `capabilities`, `native_tools`, `embeddings`, `messages`, `output`, `ui`, `tools`, `_agent_graph`, etc.).
- **Per-file model providers**: scales well, but some branches in `infer_model` (`pydantic_ai_slim/pydantic_ai/models/__init__.py:1060-1158`) and `infer_provider_class` (`pydantic_ai_slim/pydantic_ai/providers/__init__.py:114-267`) are long if/elif chains rather than a registry table, making them slightly harder to extend than a data-driven approach.
- **Hard 100% coverage gate**: `tool.coverage.report.fail_under = 100` (`pyproject.toml:382`) means new modules must be fully covered or excluded in `tool.coverage.run.omit` (`pyproject.toml:351-363`), which can make boundary additions expensive.
- **`_agent_graph.py` is heavily imported but private**: many modules reference `pydantic_ai._agent_graph` symbols (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:39-47`, `pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:27`), so while it is private by convention, the de-facto seam is "any module can read from `_agent_graph`". A future refactor to make `_agent_graph` public-but-stable (e.g. `pydantic_ai._agent_graph` becoming the documented `pydantic_ai.agent.graph`) would tighten this.
- **`pydantic_evals` duplicates small utility classes** (e.g. `Unset` is "Copied from pydantic_ai/_utils.py", `pydantic_evals/pydantic_evals/_utils.py:14-21`) to avoid importing from pydantic_ai's runtime; this duplicates code intentionally to preserve the `pydantic-graph → pydantic-ai-slim → pydantic-evals` dependency direction.

## Failure Modes / Edge Cases

- **Lazy import errors**: when a user names a provider without installing the matching extra, the message is explicit and names the install group (`pydantic_ai_slim/pydantic_ai/providers/openai.py:7-14`), but the error is only raised on first model use, not at `Agent(model='openai:...')` construction time if `defer_model_check=True` (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:289,412-415`).
- **Circular-import resolution during dataclass-spec generation**: `ToolSearch.__init__` uses forward-string references to `ToolDefinition`, and the resolution depends on `ToolDefinition` being present in the `capabilities/_tool_search.py` module globals at `get_type_hints` time (`pydantic_ai_slim/pydantic_ai/capabilities/_tool_search.py:25-28`). Reordering imports in either `tools.py` or `native_tools/_tool_search.py` could break this resolution silently.
- **`CAPABILITY_TYPES` omission**: classes that would close a cycle are intentionally excluded from the registry, so `AgentSpec.model_dump()` round-trip for agents using `OpenAICompaction`/`AnthropicCompaction` requires a manual `custom_capability_types` argument on `Agent.from_spec` (`pydantic_ai_slim/pydantic_ai/capabilities/__init__.py:94-95`). This is documented but easy to miss.
- **`py.typed` requires users to enable it**: PEP 561 only delivers types if downstream code installs with `pip install pydantic-ai` (not, e.g., via a non-PEP-561 channel). The marker files exist, but a strict type checker will not benefit unless the package is installed normally.
- **`uv-dynamic-versioning` and metadata**: dependencies are dynamic, generated at build time from git. This means the dep graph shown in `pyproject.toml:48-64` is only correct in a built wheel; reading the source alone can mislead (`pyproject.toml:8-11`).
- **Hatch build selection bypass**: `[tool.hatch.build.targets.wheel] bypass-selection = true` plus `exclude = ["/pydantic_ai_slim/pydantic_ai/.agents"]` (`pyproject.toml:164-166`) keeps internal skills out of the published wheel, but if a contributor accidentally puts a public-API module under `.agents/`, it would be silently excluded.
- **Workspace-only examples and docs**: `examples/` and `docs/` are workspace members but not published packages. CI must build them in-tree; downstream forks that drop the workspace context may lose the separation.
- **Gateway namespace conflict**: `gateway/google-vertex` and `google-vertex` both map to `GoogleCloudProvider`, but only the gateway-prefixed path is supposed to suppress the second deprecation warning (`pydantic_ai_slim/pydantic_ai/providers/__init__.py:134-145`). If `came_from_gateway` is ever mis-set, users could see duplicate deprecation messages.

## Future Considerations

- **Promote `_agent_graph.py` to a documented internal API**: today many modules depend on `_agent_graph` symbols (`pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:27`, `pydantic_ai_slim/pydantic_ai/run.py:11`), but the leading underscore discourages third-party reuse. A `pydantic_ai._agent_graph` (still underscore, still documented as internal-but-stable) or `pydantic_ai.agent.graph` public surface would formalize the boundary.
- **Registry-driven provider/model dispatch**: replace the chained `if model_kind == ...` branches in `infer_model` (`pydantic_ai_slim/pydantic_ai/models/__init__.py:1060-1158`) and `infer_provider_class` (`pydantic_ai_slim/pydantic_ai/providers/__init__.py:114-267`) with a module-level registry similar to `CAPABILITY_TYPES` (`pydantic_ai_slim/pydantic_ai/capabilities/__init__.py:70-92`) and `NATIVE_TOOL_TYPES` (`pydantic_ai_slim/pydantic_ai/native_tools/__init__.py:33-37`).
- **Consolidate `Unset` copies**: `pydantic_graph/_utils.py:116-122` and `pydantic_evals/_utils.py:14-21` both re-declare `Unset` to preserve one-way deps. A shared `pydantic-settings`-style utility package (or a single `pydantic_ai_common` extra) could remove the duplication.
- **Module-level boundary tests**: today there are tests for individual toolset composition (`tests/test_toolsets.py:389-510`) but no test that asserts, e.g., `pydantic_ai_slim` can import without pulling provider SDKs. A boundary test suite that asserts the install footprint (e.g. `pip install pydantic-ai-slim` does not require `openai`) would harden the optional-group separation.
- **v2 cleanup of deprecation shims**: `pydantic_ai/__init__.py:348-370`, `pydantic_ai/capabilities/__init__.py:154-169`, `pydantic_graph/__init__.py:66-94`, `pydantic_ai/mcp.py:3079-3089` are all scheduled for removal in v2 (`pydantic_ai_slim/pydantic_ai/_warnings.py`, `pydantic_graph/pydantic_graph/_warnings.py`). Documenting the v1→v2 removal matrix would help downstream maintainers plan their migrations.

## Questions / Gaps

- **No automated boundary tests**: `tests/` contains no test that fails if, e.g., `pydantic_ai_slim/pydantic_ai/providers/openai.py` started importing from `pydantic_evals` (which would violate the dep direction). The direction is enforced socially/by review, not by CI.
- **No enforced import-order linter**: the circular-import comments (`pydantic_ai_slim/pydantic_ai/capabilities/__init__.py:94-95`, `pydantic_ai_slim/pydantic_ai/capabilities/_tool_search.py:25-28`) document known seams, but ruff/import-linter rules are not visible in `pyproject.toml:191-229` to catch new cycles.
- **`pydantic_graph/_utils.py` docstring claims `Unset` is "Copied from pydantic_ai/_utils.py"** (`pydantic_graph/pydantic_graph/_utils.py:119`), but there's no automated check that the copy stays in sync. If `pydantic_ai/_utils.py`'s `Unset` semantics change, `pydantic_graph` would silently diverge.
- **`pydantic-ai` wheel pulls every optional group** (`pyproject.toml:48-64`). The split between slim and full is clear at install time but not at runtime — a single `import pydantic_ai` loads every model adapter's namespace via the lazy `infer_model` paths only on use, but the registration machinery still walks all `NATIVE_TOOL_TYPES` at import time.
- **No published architecture diagram**: `agent_docs/pydantic-ai-slim.md:7-17` is a textual ownership map but there is no generated graph. A rendered import graph (e.g. via pydeps/pyan) would help future maintainers see the boundary at a glance.
- **`common_tools/` and `ext/` are empty/placeholder namespaces**: `pydantic_ai_slim/pydantic_ai/common_tools/__init__.py` is empty, `pydantic_ai_slim/pydantic_ai/ext/__init__.py` is empty, while `common_tools/duckduckgo.py`, `exa.py`, `tavily.py`, etc. are present but only `common_tools/duckduckgo.py`, `exa.py`, etc. exist.
