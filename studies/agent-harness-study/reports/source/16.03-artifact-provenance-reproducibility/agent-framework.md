## Summary

`agent-framework` implements strong **execution provenance for workflows** via versioned, content-preserving checkpoints (`WorkflowCheckpoint`) and durable-history/session serialization, plus extensive OpenTelemetry instrumentation. Build-level reproducibility is addressed by a committed `uv.lock` with fully-pinned transitive hashes and constraint/override dependency guards. However, **artifact-level provenance is fragmentary**: `ChatResponse`/`AgentResponse` and `WorkflowRunResult` carry usage, timestamps, model-id and workflow graph hashes, but do not bind a final artifact (message, hosted file, or workflow output event) to the complete set of contributing factors — prompt/instructions, resolved chat options (`seed`, `temperature`, `tools`, `model`), context-provider inputs, tool call payloads/results, and approval decisions — in a single queryable record. Replay is possible for the deterministic workflow control-plane (superstep iteration, message routing, state), but not for the generative data-plane: LLM non-determinism, unrecorded external tool side-effects, and no seed-default mean identical inputs do not deterministically reproduce identical text artifacts, and no CI job tests reproducibility end-to-end.

## Rating

**5 / 10 — Present but inconsistent, weakly documented, or fragile**

Checkpoints, session serialization, `uv.lock`, and OTel spans provide a credible substrate for tracing and re-execution. Gaps — no unified artifact envelope linking prompt + model-version + seed + tools + approvals + usage, no artifact input-hash, deterministic replay not covering LLM sampling, and no CI reproducibility gate — prevent a higher score. Operational safeguards exist but are not closed-loop.

## Answers to Dimension Questions

**1. Can every artifact be traced to its inputs? — Partially (No).**
Workflow artifacts (`WorkflowRunResult` outputs, checkpoint chain) trace to `workflow_name`, `graph_signature_hash`, `previous_checkpoint_id`, `iteration_count`, and `WorkflowMessage` routing. Session artifacts trace to `session_id` + `AgentSession.state` history via `FileHistoryProvider` JSONL (each `Message.to_dict()` line with attribution `additional_properties._attribution`). LLM artifacts (`AgentResponse.text`) trace to `response_id`/`created_at`/`usage_details` but lack a unified lineage: the concrete `ChatOptions` (`model`, `seed`, `temperature`, `instructions`, resolved `tools` list, `response_format`), aggregated conversation messages (history + context-provider injections), tool call `call_id`/`arguments`/`result`, and approval decision are not co-located on the artifact. `observability.py:191-244` captures many of these as span attributes, but spans are not linked back to a persistent artifact ID by default. Hosted data-plane outputs (e.g., file-store writes via `FileAccessProvider`) have no artifact receipt binding them to the turn that created them (*`python/packages/core/agent_framework/_harness/_file_access.py` toolset lists files but does not emit provenance receipts*).

**2. Is reproduction deterministic? — No for generative artifacts; Yes for workflow control-plane under constraints.**
Build reproduction is deterministic: `uv.lock` + `constraint-dependencies`/`override-dependencies` (`python/pyproject.toml:59-63`, `python/uv.lock:1-28`) guarantee bit-identical installs per marker. File checkpoint writes are atomic (`os.replace` in `python/packages/core/agent_framework/_workflows/_checkpoint.py:317-321`), and `State` commit semantics are deterministic (`python/packages/core/agent_framework/_workflows/_state.py:90-100`). However, end-to-end artifact reproduction is non-deterministic: LLM sampling is stochastic by default (`seed` is optional, `python/packages/core/agent_framework/_agents.py:765`), tool side-effects (shell, MCP, file-store) are not virtualized, wall-clock `timestamp`/`created_at` and UUID `checkpoint_id`/`response_id` introduce entropy, and `python/uv.lock` resolution covers three platforms but not environmental hermeticity (no container digest pin beyond resolver). No test asserts `run(prompt) == run(prompt)` across two fresh processes.

**3. Are all contributing factors recorded? — No.**
Recorded: workflow graph topology (hash), workflow name/description, checkpoint version/timestamp/iteration/metadata chain (`python/packages/core/agent_framework/_workflows/_checkpoint.py:70-88`), message payloads and `PendingRequestInfoEvents`, session `state` (including `_executor_state`), OTel `REQUEST_MODEL`/`RESPONSE_MODEL`/`SEED`/`TEMPERATURE`/`SYSTEM_INSTRUCTIONS`/`TOOL_*` attributes (`python/packages/core/agent_framework/observability.py:191-244`), and `UsageDetails` token counts. Not recorded in a durable, artifact-bound way: effective merged `ChatOptions` map per turn (history shows `default_options` but not the per-call override after `_merge_options`), full tool registry versions (`FunctionTool` schemas are not versioned/hashed), context-provider contributions beyond message attribution, approval rule `server_label` boundary (in-memory only), and external provider identity (e.g., which Foundry/OpenAI deployment served the request). `WorkflowCheckpoint.metadata` is free-form (`dict[str,Any]`) but not populated with model/config by default (`python/packages/core/agent_framework/_workflows/_runner_context.py:370-395` stores only runner state + `iteration_count`).

**4. Is reproducibility tested in CI? — Minimally, not for artifact determinism.**
CI tests provenance-adjacent properties: checkpoint save/load/list/delete/get_latest, round-trip type fidelity (datetime, dataclass, tuple, bytes), and trace-context serialization (`python/packages/core/tests/workflow/test_checkpoint.py:339-1304`, `python/packages/core/tests/workflow/test_workflow_observability.py:438-470`, `python/packages/core/tests/workflow/test_sub_workflow.py:574-610`). No workflow in `.github/workflows/` executes a fixed-seed artifact reproducibility gate (e.g., re-running a canned workflow + `seed=0` and asserting output hash stability), nor validates `uv.lock` reproducibility via `--frozen` install or Nix-style hermetic rebuild. Dependency maintenance validates lock coherence after bounds refresh (`python-dependency-maintenance.yml:58,281,312`) but does not test that artifacts remain reproducible.

## Notable Patterns

- **Shallow checkpoint envelope + deep content fidelity:** `WorkflowCheckpoint.to_dict` is shallow by design (`python/packages/core/agent_framework/_workflows/_checkpoint.py:90-98` comment), while `encode_checkpoint_value` recurses over dicts/lists and pickles leaf non-primitives — balances human-readable JSON with Python object fidelity.
- **Allowlist-gated deserialization with colon-qualname:** `allowed_checkpoint_types` strings use `"module:qualname"` (`_type_to_key` at `python/packages/core/agent_framework/_workflows/_checkpoint_encoding.py:309-311`) for both framework and OpenAI SDK types; call sites must spell the exact type key.
- **Tracer-propagating workflow messages:** `WorkflowMessage.trace_contexts: list[dict[str,str]]` supports fan-in aggregation; backward-compat single `.trace_context` accessor at `python/packages/core/agent_framework/_workflows/_runner_context.py:54-57`.
- **History attribution watermarking:** `SessionContext.extend_messages` copies messages and injects `additional_properties._attribution = {"source_id", "source_type"}` at `python/packages/core/agent_framework/_sessions.py:220-251`; downstream filters use this for `store_context_from` scoping.
- **Atomic checkpoint chain linking:** Each `RunnerContext.create_checkpoint` sets `previous_checkpoint_id` from prior checkpoint, enabling linear history browsing (`python/packages/core/agent_framework/_workflows/_runner_context.py:370-395`; chain tested in `python/packages/core/tests/workflow/test_checkpoint.py:285-336`).
- **Sensitive-data gated telemetry:** `INNER_RESPONSE_TELEMETRY_CAPTURED_FIELDS` contextvar + `enable_sensitive_telemetry()` opt-in ensures tool arguments/results are only captured when explicitly allowed.

## Tradeoffs

- **Pickle fidelity vs. security:** Using `pickle.HIGHEST_PROTOCOL` preserves tuples, datetimes, dataclasses, and custom types without migration code, but forces a trusted-storage security model (`python/packages/core/agent_framework/_workflows/_checkpoint_encoding.py:17-44` warns allowlist is not a boundary and that `builtins:getattr` must remain allowed for enums).
- **Single `uv.lock` vs. per-package locks:** Coherent cross-package resolution and one diff to review on Dependabot, at cost of larger blast radius when a single provider's transitive pins churn the shared lockfile.
- **In-memory deep-copy vs. atomic file JSON:** `InMemoryCheckpointStorage` uses `copy.deepcopy` (`python/packages/core/agent_framework/_workflows/_checkpoint.py:201`) — fastest and type-exact but not crash-durable; `FileCheckpointStorage` is durable but pays JSON+base64 overhead and requires `allowed_types` at load time.
- **Trace-first, artifact-second provenance:** Provenance signals flow to OTel (ephemeral) rather than being stamped into `AgentResponse.raw_representation` or hosted-file receipts; cheap to emit, but offline artifact audits require joining traces to artifacts out-of-band.
- **Superstep committed-only checkpointing:** `State.export_state()` excludes pending writes (`python/packages/core/agent_framework/_workflows/_state.py:106-111`), so failed supersteps do not pollute checkpoints deterministically, but debugging mid-superstep pending values requires separate logging.

## Failure Modes / Edge Cases

- **Non-deterministic artifact replay despite identical prompt:** Without an explicit `seed`, two `Agent.run("Write a haiku")` calls yield different `AgentResponse.text` even though workflow checkpoint replay succeeds — tests in `python/packages/core/tests/workflow/test_workflow_observability.py:438-470` only assert trace-context survival, not text equality.
- **Pickle payload drift / tamper:** Corrupted `__pickled__` base64 or `__type__` mismatch raises `WorkflowCheckpointException` (`python/packages/core/agent_framework/_workflows/_checkpoint_encoding.py:257-278`, `300-306`) — but because `RestrictedUnpickler` still executes reconstruction for allowlisted types, a malicious checkpoint in a compromised store could abuse `getattr` paths despite type verification being post-deserialization.
- **Corrupted checkpoint file silently skipped on listing:** `FileCheckpointStorage.list_checkpoints` logs `WARNING` and continues on decode failure (`python/packages/core/agent_framework/_workflows/_checkpoint.py:372-388`), while `load` raises — a listing may appear healthier than the underlying store.
- **Graph drift on restore:** Restoring a checkpoint into a workflow whose `graph_signature_hash` changed fails validation (hash recorded at build time at `python/packages/core/agent_framework/_workflows/_workflow.py:332-333`); no migration path is offered — caller must rebuild topology or discard the checkpoint chain.
- **Missing `allowed_checkpoint_types` at restore:** A dataclass stored under `test_checkpoint:_TestCustomData` round-trips only if `FileCheckpointStorage(allowed_checkpoint_types=[...])` is configured (`python/packages/core/tests/workflow/test_checkpoint.py:1051-1074`); otherwise `RestrictedUnpickler` blocks on decode and the entire checkpoint is unloadable.
- **Conversation ID missing with `require_per_service_call_history_persistence`:** `PerServiceCallHistoryPersistingMiddleware._finalize_response` warns when `service_stores_history` yet `response.conversation_id is None` (`python/packages/core/agent_framework/_sessions.py:682-688`) — cross-turn history may silently fail to resume, breaking artifact continuity.
- **In-flight messages block new run:** `Workflow._run_core` raises `RuntimeError("Cannot start a new run with 'message' while in-flight executor messages remain ... there is no in-process recovery path")` at `python/packages/core/agent_framework/_workflows/_workflow.py:803-810` — a crash mid-superstep without a checkpoint requires manual checkpoint rollback, not automatic replay.
- **Tool approval chain not durably bound:** `function_approval_response` content is stored in session history, but the final artifact (`WorkflowRunResult.get_outputs()` at `python/packages/core/agent_framework/_workflows/_workflow.py:125-131`) does not embed which rule/approver authorized the tool — audit trails depend on joining history + artifacts.
- **Platform-specific lock resolution:** `python/uv.lock:4-23` enumerates darwin/linux/win32 markers; building on an unsupported platform (e.g., musl) may resolve differently, breaking bit-for-bit build reproducibility.

## Future Considerations

- Emit a **canonical artifact envelope**: on each `AgentResponse` / `WorkflowRunResult` output event, stamp a hashed `inputs_fingerprint` (messages + merged `ChatOptions` + tool registry versions + context-provider versions + `graph_signature_hash`) alongside `model`, `seed`, `response_id`, `trace_id`, `usage_details`, and `approval_decisions` so offline verification does not require trace joins.
- Add a **deterministic replay mode** gated by `seed` + tool virtualization: when `ChatOptions(seed=...)` and deterministic mock tools are provided, assert `hash(outputs)` stable across N replays in a dedicated CI job ( complements existing `test_checkpoint.py` round-trip tests ).
- Populate `WorkflowCheckpoint.metadata` with `model`, `seed`, `instructions` hash, and tool hashes at superstep boundaries (currently only runner emits `superstep` info); this makes checkpoints self-describing without consulting external traces.
- Persist **build provenance** as artifact attestations: record `uv.lock` hash + resolved `graph_signature_hash` into published packages/images (e.g., SLSA-style attestation or `dist-info` provenance file) rather than only in VCS.
- Introduce **history receipt chaining** for hosted file-store writes: each `file_access_save` mutation should emit a content-addressable receipt linked to the originating `response_id`/`checkpoint_id`, closing the gap where data-plane file artifacts are untracked.
- Document and enforce `allowed_checkpoint_types` for every custom state type in a registry test, preventing unloadable checkpoints after refactors.
