## Summary

OpenHands exposes a **marketplace-centric plugin model** plus four first-class extension surfaces that all funnel through the agent-server at conversation start: **skills** (markdown prompts with triggers), **hooks** (`hooks.json` shell handlers), **MCP servers** (`mcp_config`/`MCPServer`), and **agent profiles/subagents**. Remote plugins are described by `PluginSpec`/`PluginSource` (`openhands/app_server/app_conversation/app_conversation_models.py:71` and `_sdk_inspect/sdk/plugin/types.py:14`) and resolved via `MarketplaceRegistration` (`openhands/app_server/settings/settings_models.py:75`). The app-server is a thin proxy that composes marketplaces (`openhands/app_server/settings/marketplace_composition.py:206`), authenticates git URLs (`openhands/app_server/app_conversation/skill_loader.py:511`), and proxies to `POST /api/skills` and `POST /api/hooks` on the agent-server (`openhands/app_server/app_conversation/skill_loader.py:614` and `openhands/app_server/app_conversation/hook_loader.py:43`). The SDK canonical loader `load_plugins()` (`_sdk_inspect/sdk/plugin/loader.py:28`) fetches, loads, and merges skills/MCP/hooks with last-wins semantics; lifecycle is conversation-scoped (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:2409`). No dynamic in-conversation plugin registry, no per-plugin sandboxing, and no stable versioned public API doc exist — extension is powerful but coupled to the external SDK and documented via an internal design doc (`enterprise/doc/design-doc/plugin-launch-flow.md:1`).

## Rating

**Rating: 6 / 10 — Present but inconsistent, weakly documented, fragile**

Rationale: Explicit typed interfaces (`PluginSpec`, `MarketplaceRegistration`, `PluginManifest`, `HookConfig`, `MCPServer`, `EventCallbackProcessor`) and a single call-site merge (`load_plugins` / `load_skills_from_agent_server`) plus operational safeguards (traversal guards, dedup, concurrency caps, kill switch, auth rewrite) meet the bar for a clear model. Downgraded because (a) isolation is absent (shared `AgentContext`/`mcp_config`, no plugin sandbox), (b) lifecycle is only conversation-start with no enable/disable/update hooks in the app-server, (c) terminology is split across V0 microagents / V1 skills / Claude-compat plugins requiring SDK, and (d) extension points are not published as a stable, versioned public API — the canonical flow is an enterprise design doc, not user-facing reference docs.

## Answers to Dimension Questions

### 1. What can be extended via plugins?

**Broad marketplace-driven bundle plus four orthogonal surfaces, all SDK-defined.**

- **Plugins (Claude-compat bundle)** — a directory `plugin-name/` with `.claude-plugin/plugin.json` (`PluginManifest` at `_sdk_inspect/sdk/plugin/types.py:209`), optional `commands/` (`CommandDefinition` at `_sdk_inspect/sdk/plugin/types.py:228`), `skills/`, `hooks/hooks.json` (`HookConfig` at `_sdk_inspect/sdk/plugin/plugin.py:439`), `.mcp.json` (`mcp_config` at `_sdk_inspect/sdk/plugin/plugin.py:460`), `agents/` (`AgentDefinition` at `_sdk_inspect/sdk/plugin/plugin.py:491`). `PluginSource` (`_sdk_inspect/sdk/plugin/types.py:14`) points at `github:owner/repo` / any git URL / local path with optional `ref` + `repo_path`.
- **Marketplaces** — `MarketplaceRegistration` (`openhands/app_server/settings/settings_models.py:75`) registers a git source containing many plugins; composition (`openhands/app_server/settings/marketplace_composition.py:206`) merges instance/org/personal scopes with name-keyed precedence.
- **Skills** — `Skill` (`openhands/app_server/app_conversation/skill_loader.py:56`) with `KeywordTrigger`/`TaskTrigger` injected into `AgentContext.skills` (`_sdk_inspect/sdk/context/agent_context.py:59`). Load order: public → user → org → project → marketplace auto-load (`openhands/app_server/app_conversation/app_conversation_service_base.py:108-118`).
- **Hooks** — `HookConfig` (`_sdk_inspect/sdk/plugin/loader.py:34`) shell scripts running at `PreToolUse`, `PostToolUse`, `Stop`, etc., fetched via `POST /api/hooks` (`openhands/app_server/app_conversation/hook_loader.py:43`).
- **MCP servers / tools** — `MCPServer` (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:129`) via `AgentSettings.mcp_config`; plugins contribute `mcpServers` that are shallow-merged (`_sdk_inspect/sdk/plugin/plugin.py:199-234`). Built-in FastMCP tools (`create_pr`, `create_mr`, `create_bitbucket_pr`, etc.) are themselves an extension point at `openhands/app_server/mcp/mcp_router.py:147`.
- **Agent profiles & subagents** — `AgentProfiles` (`openhands/app_server/settings/agent_profiles.py:64`) referencing `llm_profile_ref` + `mcp_server_refs`; `AgentDefinition` for delegate subagents wired via `tool_module_qualnames`/`agent_definitions` (`_sdk_inspect/sdk/conversation/request.py:117-132`).
- **Event callbacks** — `EventCallbackProcessor` (`openhands/app_server/event_callback/event_callback_models.py:40`) for post-event processing (e.g., `SetTitleCallbackProcessor`).
- **Not extensible without core change** — adding a brand-new *tool type* (beyond MCP) still requires modifying the SDK tool registry; the `ToolError`-derived FastMCP surface is the closest third-party tool extension.

### 2. Can plugins be loaded at runtime?

**Conversation-start dynamic, not in-conversation dynamic; no hot-reload.**

- **Marketplace auto-load**: `MarketplaceRegistration.auto_load=True` causes `load_skills_from_agent_server` to include `registered_marketplaces` in `POST /api/skills` (`openhands/app_server/app_conversation/skill_loader.py:669-673`). Resolved at `LiveStatusAppConversationService._resolve_registered_marketplaces()` (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:2207`) and authenticated via `authenticate_marketplace_sources()` (`openhands/app_server/app_conversation/skill_loader.py:511`).
- **Per-conversation explicit plugins**: `AppConversationStartRequest.plugins: list[PluginSpec]` (`openhands/app_server/app_conversation/app_conversation_models.py:254`) is supplied on `POST /api/v1/app-conversations` (`enterprise/doc/design-doc/plugin-launch-flow.md:273`). The frontend `/launch` route base64-encodes `PluginSpec[]` from the Plugin Directory (`enterprise/doc/design-doc/plugin-launch-flow.md:194-211`) and the app-server strips `parameters` to `PluginSource` before forwarding to `StartConversationRequest.plugins` (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:2412` and `_sdk_inspect/sdk/conversation/request.py:133`).
- **Fetch is cached git clone**: `Plugin.fetch(source, ref, repo_path)` (`_sdk_inspect/sdk/plugin/plugin.py:237`) clones/pulls to `~/.openhands/cache/plugins/`; `ResolvedPluginSource` pins the commit SHA for pause/resume (`_sdk_inspect/sdk/plugin/types.py:109`).
- **No mid-conversation plugin injection observed** — `load_plugins()` is only called during `LocalConversation` construction (`_sdk_inspect/sdk/plugin/loader.py:28`); tests cover start-time loading (`tests/unit/app_server/test_live_status_app_conversation_service.py:1`). Adding a plugin requires starting a new conversation. The kill switch `ENABLE_MARKETPLACE_PLUGIN_LOADING` (`openhands/app_server/settings/marketplace_composition.py:41`) gates the whole path but is env-level, not per-plugin hot toggle.

### 3. Are plugins isolated from each other?

**No per-plugin isolation; isolation is at the sandbox/conversation layer only.**

- **Shared mutable merges**: `Plugin.add_skills_to()` builds `skills_by_name: dict[str, Skill]` where "last plugin wins" (`_sdk_inspect/sdk/plugin/plugin.py:159-163`) with only a `logger.warning` on collision; `add_mcp_config_to()` similarly overwrites `mcpServers` by name (`_sdk_inspect/sdk/plugin/plugin.py:220-223`). `HookConfig.merge()` concatenates hooks (`_sdk_inspect/sdk/plugin/loader.py:114`) so ordering matters but all hooks execute in the same agent process.
- **No sandbox-per-plugin**: The design doc notes plugins run "inside the sandbox" for hook/MCP filesystem isolation (`enterprise/doc/design-doc/plugin-launch-flow.md:557`), but that sandbox is the single conversation sandbox shared by all plugins and the agent — `openhands/app_server/app_conversation/live_status_app_conversation_service.py:2018` configures one `mcp_config` dict per conversation.
- **No capability/permission boundary**: No plugin manifest declares capabilities; MCP `headers`/`env`/`auth` secrets are expanded via `expand_mcp_variables` with a shared `get_secret` callback (`_sdk_inspect/sdk/plugin/loader.py:107`), so a plugin can read any secret the conversation holds.
- **Namespace soft protection**: Commands are namespaced via `"/{plugin}:{cmd}"` (`_sdk_inspect/sdk/plugin/types.py:337`), but skills from `skills/` retain their raw `skill.name` and can still collide.
- **Failure isolation is weak**: Any `PluginFetchError`/`FileNotFoundError` or `max_skills` breach in `load_plugins()` propagates to the conversation start and, via the app-server wrapper (`openhands/app_server/app_conversation/app_conversation_service_base.py:174-177`), degrades to empty skills only in the proxy layer — SDK callers see the exception.

### 4. Are extension points documented and stable?

**Interfaces are typed and internally well-documented; public stability guarantee is absent.**

- **Typed contracts present**: Every surface has an explicit Pydantic model with validators (`MarketplaceRegistration.validate_source` at `openhands/app_server/settings/settings_models.py:168`, `PluginSource.validate_repo_path` at `_sdk_inspect/sdk/plugin/types.py:50`, `PluginManifest` at `_sdk_inspect/sdk/plugin/types.py:209`). Composition precedence and name-keyed identity are specified in module docstrings (`openhands/app_server/settings/marketplace_composition.py:1-15`).
- **Internal docs exist**: `skills/README.md:1-160` documents V0/V1 skill loading, frontmatter triggers, and public vs repo sources; `enterprise/doc/design-doc/plugin-launch-flow.md:1-598` is the most complete end-to-end spec with payload examples for every hop; `.openhands/microagents/glossary.md:15` and `AGENTS.md:327` define microagents vs skills.
- **Not a stable public API**: The launch flow doc lives under `enterprise/doc/` (not `docs/`), references SDK PR numbers (`#1651`, `#1647`, `#2230`), and notes "V1 UI and app server have not yet been released" (`skills/README.md:9`) — indicating an evolving contract. `PluginManifest` uses `extra="allow"` (`_sdk_inspect/sdk/plugin/types.py:225`), and `PluginSource`/`MarketplaceRegistration` validators are stricter in the app-server than the SDK with a comment about staying a subset (`openhands/app_server/settings/settings_models.py:83-87`), implying forward-compatible but not formally versioned. No `CHANGELOG`/deprecation policy for `plugin.json` / `hooks.json` / `Skill` schemas was found in-repo (`No clear evidence found` for `docs/`-level plugin API reference).
- **Discoverability**: `skills/` is discoverable; marketplace registration is via `POST /api/v1/settings` (`openhands/app_server/settings/settings_router.py:264-303`) with `GET /api/v1/settings` composition rendering (`openhands/app_server/settings/settings_router.py:202-208`), but plugin author guidance beyond the design doc is sparse.

## Architectural Decisions

| Decision | Rationale / Tradeoff | Evidence |
|----------|----------------------|----------|
| **App-server as thin proxy; SDK owns loading** | Keeps git cloning and skill merging inside the sandbox where filesystem is available; avoids duplicating SDK logic. Tradeoff: app-server cannot validate skill content, and SDK version skew can break `POST /api/skills` (see 422 handling). | `openhands/app_server/app_conversation/skill_loader.py:1-11`, `614` |
| **Marketplace composition name-keyed Instance<Org<User** | Additive precedence with override for instance→org and drop for user shadowing simplifies multi-tenant policy. Tradeoff: user cannot override org marketplace of same name even if they need a different `auto_load` value. | `openhands/app_server/settings/marketplace_composition.py:206-247`, `236-245` |
| **Authenticated git URL rewrite at proxy** | `authenticate_marketplace_sources` swaps `github:owner/repo` for a token-embedded URL so the agent-server can clone private marketplaces without holding tokens. Tradeoff: credentials transit through agent-server payload (wire-only, never persisted — comment at `openhands/app_server/app_conversation/skill_loader.py:523-529`). | `openhands/app_server/app_conversation/skill_loader.py:511-591`, `openhands/app_server/app_conversation/app_conversation_service_base.py:146-151` |
| **Plugin params via message text block** | `PluginSpec.parameters` appended as `"Plugin Configuration Parameters:\n- city: Tokyo"` (`enterprise/doc/design-doc/plugin-launch-flow.md:345`) because `PluginSource` has no params field; avoids schema change in SDK. Tradeoff: agent must parse unstructured text, and params are not typed or validated. | `enterprise/doc/design-doc/plugin-launch-flow.md:343-392`, `openhands/app_server/app_conversation/app_conversation_models.py:94-107` |
| **Claude-compat plugin layout** (`.claude-plugin/plugin.json`, `commands/`, `skills/`, `hooks/`) | Reuses ecosystem; `Plugin.load()` checks `[".plugin", ".claude-plugin"]` prioritized. Tradeoff: inherits `extra="allow"` lax manifest and mixed V0/V1 terminology. | `_sdk_inspect/sdk/plugin/plugin.py:34-36`, `365-402`, `_sdk_inspect/sdk/plugin/types.py:225` |
| **Last-wins merge for skills/MCP, concat for hooks** | Simple deterministic merge (`skills_by_name` dict, `mcpServers` spread). Tradeoff: no conflict detection, silent override of prior plugin's capability. | `_sdk_inspect/sdk/plugin/plugin.py:151-234`, `_sdk_inspect/sdk/plugin/loader.py:98-114` |

Tradeoff: large org membership may silently truncate marketplaces. | `openhands/app_server/app_conversation/skill_loader.py:272-374` |
| **Env kill switch `ENABLE_MARKETPLACE_PLUGIN_LOADING`** | Operational guard to disable marketplace loading without code deploy. Tradeoff: all-or-nothing, not per-marketplace. | `openhands/app_server/settings/marketplace_composition.py:41-59` |

## Notable Patterns

- **Proxy-and-delegate pattern**: App-server builds `OrgConfig`/`SandboxConfig`/`MarketplaceRegistration` with auth, then `POST`s to agent-server; agent-server does actual cloning/merging. See `skill_loader.load_skills_from_agent_server` at `openhands/app_server/app_conversation/skill_loader.py:614` and `hook_loader.fetch_hooks_from_agent_server` at `openhands/app_server/app_conversation/hook_loader.py:43`.
- **Discriminated unions for extensibility**: `AgentSettingsConfig` (`OpenHandsAgentSettings` vs `ACPAgentSettings`) at `openhands/app_server/settings/settings_models.py:41`, `ACPEnabledAgent` at `_sdk_inspect/sdk/conversation/request.py:37`, and `EventCallbackProcessor` at `openhands/app_server/event_callback/event_callback_models.py:40` use `DiscriminatedUnionMixin` / `kind_of` for future variants.
- **Composition over configuration**: `ComposedMarketplaces` dataclass with `.all` property (`openhands/app_server/settings/marketplace_composition.py:63-75`) and `duplicate_marketplace_names()` pre-write validator (`openhands/app_server/settings/marketplace_composition.py:171-192`) enforce invariants at write path, not load path, to avoid locking users out.
- **Secret redaction / LookupSecret pattern**: `"**********"` redaction in `dump_mcp_config` (`openhands/app_server/settings/settings_models.py:288-307`) with `LookupSecret` resolution at sandbox via `X-Session-API-Key` (`enterprise/doc/design-doc/plugin-launch-flow.md:527` doc note) — consistent with SDK's per-conversation secret expansion (`_sdk_inspect/sdk/plugin/loader.py:107-110`).
- **Frontmatter-driven skills**: Markdown + YAML frontmatter (`triggers: ["/city-weather:now"]`) parsed by `Skill.load(..., strict=False)` allowing Claude plugin compatibility while `AgentContext` stays strictly typed (`_sdk_inspect/sdk/plugin/plugin.py:404-434`).

## Tradeoffs

- **Power vs safety**: The SDK plugin bundle (skills + hooks + MCP + agents + commands) is very expressive (a single `PluginSource` can add tools, prompts, and agents), but there is no capability manifest, permission scoping, or per-plugin resource limit beyond `max_skills=100` (`_sdk_inspect/sdk/plugin/loader.py:32`).
- **Flexibility vs determinism**: `ResolvedPluginSource` pinning exists for determinism (`_sdk_inspect/sdk/plugin/types.py:109`), yet the app-server's `PluginSpec` still accepts bare `ref: "main"` and fetches latest on each conversation start unless the caller pins — easy to get drift.
- **Operability vs coupling**: Marketplace composition, auth rewrite, and caching are robust for SaaS scale (concurrency caps, truncation warnings, degraded-to-empty on failure at `openhands/app_server/settings/marketplace_composition.py:221-232` and `openhands/app_server/app_conversation/app_conversation_service_base.py:174`), but depend on the external `software-agent-sdk` repo for the actual load (`_sdk_inspect/` is a read-only inspection copy, not vendored) — SDK upgrades must stay wire-compatible.
- **User experience vs explicitness**: Auto-load marketplaces are convenient (`auto_load=True`), but the "params as message text" ferrying breaks type safety and makes plugin inputs invisible to the SDK's typed `PluginSource` (`enterprise/doc/design-doc/plugin-launch-flow.md:536-587`).

## Failure Modes / Edge Cases

- **Validation rejects at write, not load**: `MarketplaceRegistration.validate_source` rejects absolute/local traversal (`openhands/app_server/settings/settings_models.py:182-191`), but `_coerce()` in composition logs-and-skips invalid entries (`openhands/app_server/settings/marketplace_composition.py:195-203`) so a bad legacy row doesn't lock the user out — silent data loss if operator typos instance env var (warning at `openhands/app_server/settings/marketplace_composition.py:141-147`).
- **Org enumeration truncation**: More than 30 candidate skill repos are truncated with only a warning (`openhands/app_server/app_conversation/skill_loader.py:346-351`); users in many orgs quietly lose skills.
- **Private marketplace clone failure**: `authenticate_marketplace_sources` falls back to original source on `get_authenticated_git_url` failure (`openhands/app_server/app_conversation/skill_loader.py:558-564`) — `Plugin.fetch` then fails on unauthenticated clone, bubbling as `PluginFetchError` or falling back to empty skill list depending on path (`openhands/app_server/app_conversation/app_conversation_service_base.py:174` vs `_sdk_inspect/sdk/plugin/loader.py:88` re-raises).
- **Skill name collision silent override**: `skills_by_name[skill.name] = skill` last-wins with just `logger.warning` (`_sdk_inspect/sdk/plugin/plugin.py:162`); no error, no namespacing enforcement beyond commands.
- **MCP secret double-expansion bug avoided via deferral**: `Plugin._load_mcp_config` loads with `expand_defaults=False` (`_sdk_inspect/sdk/plugin/plugin.py:477`) so `${VAR:-default}` survives until `expand_mcp_variables(..., expand_defaults=True)` with per-conversation secrets (`_sdk_inspect/sdk/plugin/loader.py:108`). If the flag were flipped, secrets would bind to defaults at load time.
- **422 on explicit `null` registered_marketplaces**: `load_skills_from_agent_server` omits the key when `None` (`openhands/app_server/app_conversation/skill_loader.py:669-673`) because older agent-servers reject `null` — a missed guard would drop all skills.
- **Param block parsing fragility**: Agent reads `"Plugin Configuration Parameters:\n- city: Tokyo"` from message text (`enterprise/doc/design-doc/plugin-launch-flow.md:501-514`); malformed block or extra whitespace breaks tool invocation with no schema validation.
- **Max skills DoS guard**: `add_skills_to(..., max_skills=100)` raises `ValueError` (`_sdk_inspect/sdk/plugin/plugin.py:165`) if total exceeds cap — a marketplace with many skills can block conversation start rather than gracefully truncating.
- **Hook script injection surface**: `hooks.json` entries are arbitrary `command: str` executed in the sandbox (`_sdk_inspect/sdk/plugin/plugin.py:439`); no allowlist or timeout beyond per-hook `timeout: int = 60` (`openhands/app_server/app_conversation/app_conversation_models.py:352`) — malicious plugin can run arbitrary shell.

## Future Considerations

- **Per-plugin isolation**: Namespace skills by `plugin_id` prefix (beyond commands), isolate MCP env per plugin, and optionally run hooks in a subprocess with a tighter seccomp/timeout budget rather than shared agent process.
- **Typed plugin parameters**: Promote `PluginSpec.parameters` from `dict[str,Any]` to a JSON Schema validated against `plugin.json` `parameters` definition (already described in `enterprise/doc/design-doc/plugin-launch-flow.md:57-78`) and pass as structured `AgentContext` field instead of message text.
- **Dynamic plugin registry**: Add `POST /api/v1/conversations/{id}/plugins` to hot-load/unload plugins mid-conversation with `load_plugins()` re-entry and `disabled_skills` mutation, rather than requiring a new conversation.
- **Stable plugin API versioning**: Publish `plugin.json` / `hooks.json` / `Skill` schemas with semver and a deprecation window; move the launch flow doc from `enterprise/doc/` to versioned `docs/plugins/` and add migration tests.
- **Observability**: Emit per-plugin load latency, cache hit rate, and override-count metrics from `Plugin.fetch`/`Plugin.load` and `load_plugins` merge warnings to make the "last-wins" behavior observable.
- **Ref resolution pinning at app-server**: Have `_resolve_registered_marketplaces` resolve `ref` to `resolved_ref` (SHA) before forwarding, and persist it via `ResolvedPluginSource` so pause/resume is deterministic even for `ref=main` marketplaces.
- **Fine-grained marketplace kill switch**: Replace boolean `ENABLE_MARKETPLACE_PLUGIN_LOADING` with per-marketplace or per-scope toggles and an allowlist for `INSTANCE_DEFAULT_MARKETPLACES` parsing errors that currently degrade to empty.
