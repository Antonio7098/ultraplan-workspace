## Summary

Langfuse exposes a **layered, source-classified error taxonomy** built from five orthogonal classification systems that converge at API boundaries:

1. **A flat HTTP-aligned `BaseError` hierarchy** in `packages/shared/src/errors/` — `BaseError` (root) plus 11 subclasses carrying `name`, `httpCode`, and `isOperational` (`packages/shared/src/errors/BaseError.ts:1-27`). The hierarchy maps to HTTP semantics (400/401/403/404/405/409/422/500/501/503), not to source subsystem.
2. **Domain-specific source-classified classes** that *do* encode source: `ClickHouseResourceError` (with `MEMORY_LIMIT|OVERCOMMIT|TIMEOUT` discriminator table, `packages/shared/src/server/repositories/clickhouse.ts:36-99`); `LLMCompletionError` (with `responseStatusCode`, `isRetryable`, and an inferred `EvaluatorBlockReason`, `packages/shared/src/server/llm/errors.ts:31-67`); `SlackApiError` (carries `slackErrorCode`, `packages/shared/src/server/services/SlackService.ts:21-29`); `UnrecoverableError` and `ObservationNotFoundError` (`worker/src/errors/UnrecoverableError.ts:1-17`, `worker/src/errors/ObservationNotFoundError.ts:1-22`); `CodeEvalExecutionError` and `CodeEvalDispatcherError` with 11 `CodeEvalDispatcherErrorCode` values (`packages/shared/src/server/evals/codeEvalExecution.ts:78`, `packages/shared/src/server/evals/codeEvalDispatcherTypes.ts:124-142`); redirect-fetch errors `RedirectValidationError` / `MaxRedirectsExceededError` / `CircularRedirectError` (`packages/shared/src/server/outbound-url/fetch.ts:15,31,46`); and the MCP module's `UserInputError` (4xx-equivalent) vs `ApiServerError` (5xx-equivalent) pair (`web/src/features/mcp/core/errors.ts:19-63`).
3. **A persistence-layer source enum** `EvaluatorBlockReason` (`packages/shared/prisma/schema.prisma:1037-1044`) with six values (`LLM_CONNECTION_AUTH_INVALID`, `LLM_CONNECTION_MISSING`, `DEFAULT_EVAL_MODEL_MISSING`, `EVAL_MODEL_CONFIG_INVALID`, `EVAL_MODEL_UNAVAILABLE`, `PROVIDER_ACCOUNT_NOT_READY`), paired with `EvaluatorBlockSource` (`packages/shared/src/server/services/blockEvaluatorConfigs.ts:14-22`) and metadata-driven resolution paths (`packages/shared/src/features/evals/evalConfigBlocking.ts:59-138`).
4. **A public-API error code enum** for the unstable evaluators API (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-25`) — 18 machine-readable codes including `authentication_failed`, `access_denied`, `invalid_request`, `invalid_query`, `invalid_body`, `rate_limited`, `unprocessable_content`, `resource_not_found`, `evaluator_preflight_failed`. Documented in `fern/apis/server/definition/unstable/errors.yml`.
5. **A `RateLimitResource` source taxonomy** for rate-limited subsystems (`packages/shared/src/interfaces/rate-limits.ts:4-17`) — `ingestion`, `media-upload`, `public-api`, `prompts`, `legacy-ingestion`, `datasets`, etc.

Classification is **actively used for dispatch and routing** in five well-tested sites: the unstable public API `toUnstablePublicApiError()` (100-line `instanceof` switch mapping every `BaseError` subclass + `ClickHouseResourceError` + Zod to typed `code` + `httpCode` at `web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`); the MCP `formatErrorForUser()` (`web/src/features/mcp/core/error-formatting.ts:27-104`); the tRPC `withErrorHandling` middleware (`web/src/server/api/trpc.ts:175-215`); the REST `withMiddlewares` (`web/src/features/public-api/server/withMiddlewares.ts:82-200`); and the worker queues (`worker/src/queues/evalQueue.ts:118-271`, `experimentQueue.ts:24-49`, `codeEvalQueue.ts:17-92`) which branch on `isLLMCompletionError(e) && e.isRetryable` to schedule a delayed retry vs `isUnrecoverableError(e)` to suppress BullMQ retry vs default to rethrow.

Documentation is present but **fragmented**: `web/AGENTS.md:179-183` codifies the tRPC + REST error-handling playbook; `.agents/skills/backend-dev-guidelines/references/middleware-guide.md:552-633` documents the four-way tRPC and five-way REST dispatch; the Fern `errors.yml` (`fern/apis/server/definition/unstable/errors.yml:192-269`) gives per-code recovery prose; the Prisma `EvaluatorBlockReason` enum has a full `EVALUATOR_BLOCK_METADATA` table with user-facing message + shortLabel + resolution path; the MCP `errors.ts:1-7` cites the "Sentry MCP pattern". There is no single central taxonomy document.

## Rating

**8 / 10** — Clear two-track model with source-classified domain errors, exhaustive `instanceof`-based dispatch at five well-tested sites, documented error codes and recovery paths. You can tell from the error type whether to retry (`LLMCompletionError.isRetryable`, `UnrecoverableError` → stop), escalate (`EvaluatorBlockReason` → block config + admin email), or stop (404/409 → terminal). Deductions: (a) the L0 `BaseError` is organized by **HTTP code**, not source — the "model | provider | tool | validation | policy | context | user | infrastructure | timeout" axis is split across `ClickHouseResourceError`, `LLMCompletionError`, `EvaluatorBlockReason`, and MCP's binary split, not encoded in a single `category` field; (b) enforcement is informal — no lint rule requires `BaseError` subclasses, and dozens of sites throw bare `new Error(...)` (`worker/src/scripts/verifyClickhouseRecords/index.ts:300-948`, `packages/shared/src/encryption/encryption.ts:20-42`, `worker/src/queues/monitorQueue.ts:24`); (c) `BaseError.isOperational` is set but never read by any dispatch site (vestigial); (d) `name`-based type guards (`isLLMCompletionError`, `isUnrecoverableError`) don't survive subclassing — they check `e.name === "<ClassName>"` rather than `instanceof`; (e) `EvaluatorBlockReason` only spans eval/evaluator failures, not ingestion, storage, or other subsystems; (f) the public-API `code` enum is contractual — adding a code requires Fern regeneration and is a breaking change for SDKs.

Yes — the answer to "Can you tell from the error type whether to retry, escalate, or stop?" is **yes** at the domain-error layer (`LLMCompletionError.isRetryable`, `UnrecoverableError`, `ObservationNotFoundError`) and **partial** at the `BaseError` layer (HTTP code + `isUserError()` give retry/log hints, but no explicit `retryable` flag).

## Answers to Dimension Questions

1. **Are errors classified by source?** — Yes, partially and across multiple layers. The L0 `BaseError` hierarchy (`packages/shared/src/errors/BaseError.ts:1-27`) classifies by **HTTP code, not source**. Source classification lives in: (a) **infrastructure** → `ClickHouseResourceError` with `MEMORY_LIMIT|OVERCOMMIT|TIMEOUT` discriminator table (`packages/shared/src/server/repositories/clickhouse.ts:36-99`); (b) **model / provider** → `LLMCompletionError` with `responseStatusCode`, `isRetryable`, inferred `EvaluatorBlockReason` (`packages/shared/src/server/llm/errors.ts:31-67`); (c) **policy / blocking** → `EvaluatorBlockReason` Prisma enum with 6 source categories (`packages/shared/prisma/schema.prisma:1037-1044`); (d) **tool / external** → `SlackApiError.slackErrorCode` (`packages/shared/src/server/services/SlackService.ts:21-29`); (e) **queue terminal vs transient** → `UnrecoverableError` + `ObservationNotFoundError` (`worker/src/errors/UnrecoverableError.ts:1-17`, `worker/src/errors/ObservationNotFoundError.ts:1-22`); (f) **validation** → `ZodError` + `InvalidRequestError` + `QueryBuilderError`; (g) **MCP user vs server** → binary `UserInputError` (4xx) vs `ApiServerError` (5xx) split (`web/src/features/mcp/core/errors.ts:19-63`); (h) **code-eval dispatcher** → 11 `CodeEvalDispatcherErrorCode` values split into `RETRYABLE_ERROR_CODES` / `USER_ERROR_CODES` / `INTERNAL_CODE_EVAL_ERROR_CODES` sets. So "classified by source" is true at the **domain-error** layer and the **public-contract** layer but **not at the L0 layer**.

2. **Is the taxonomy used for handling?** — Yes, extensively at five well-defined dispatch sites: (a) `toUnstablePublicApiError()` maps every `BaseError` subclass + `ClickHouseResourceError` + `ZodError` to a typed public-API `code` + `httpCode` (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`); (b) `formatErrorForUser()` maps every `BaseError` + MCP error to `McpError` codes (`web/src/features/mcp/core/error-formatting.ts:27-104`); (c) the tRPC `withErrorHandling` preserves `httpCode` and message via `resolveError` and selects log level by `httpStatus` bucket (`web/src/server/api/trpc.ts:140-215`); (d) the REST `withMiddlewares` drives response shape and log level from `isUserError()` (`web/src/features/public-api/server/withMiddlewares.ts:65-200`); (e) the worker queue processors branch on `isLLMCompletionError(e) && e.isRetryable` for delayed retry, `isLLMCompletionError(e) || isUnrecoverableError(e)` for terminal `JobExecutionStatus.ERROR`, default to BullMQ exponential-backoff retry (`worker/src/queues/evalQueue.ts:118-363`, `experimentQueue.ts:24-49`, `codeEvalQueue.ts:17-92`); `evalService.ts:901-923` calls `LLMCompletionError.shouldBlockConfig()` and `getEvaluatorBlockReason()` to trigger `blockEvaluatorConfigs()` with the inferred `EvaluatorBlockReason`; the Slack router switches on `slackErrorCode` to map upstream codes onto user-friendly messages (`web/src/features/slack/server/router.ts:345-374`).

3. **Are error categories documented?** — Yes, in multiple places but **not centralized**. (a) `web/AGENTS.md:179-183` codifies the tRPC + REST error-handling playbook in three bullets; (b) `.agents/skills/backend-dev-guidelines/references/middleware-guide.md:552-633` documents the per-class routing for tRPC and REST with worked code examples; (c) the Fern `errors.yml` (`fern/apis/server/definition/unstable/errors.yml:192-269`) gives per-code docs and recovery guidance for the public contract; (d) the MCP `errors.ts:1-7` cites the "Sentry MCP pattern" for the `UserInputError` / `ApiServerError` split; (e) `packages/shared/src/features/evals/evalConfigBlocking.ts:59-138` documents the full `EvaluatorBlockReason` table with user-facing message + shortLabel + resolution path; (f) inline JSDoc in worker retry helpers (`worker/src/features/utils/retry-handler.ts:11-29`, `worker/src/features/evaluation/retryObservationNotFound.ts:13-30`). There is **no single central taxonomy document** — the documentation is fragmented across the AGENTS.md playbook, the backend skill reference, the Fern contract, and inline code comments.

4. **Can new error types be added without breaking existing handling?** — Yes, with caveats. New `BaseError` subclasses can be added in `packages/shared/src/errors/`, exported from `packages/shared/src/errors/index.ts:1-13`, and consumed by the four middleware dispatch sites — but each dispatch site would need a new branch, and there is no central "registry" that auto-routes new types. The web AGENTS.md says "Extend the `BaseError` or its subclasses in `packages/shared/src/errors/` as needed" (`web/AGENTS.md:181-183`) but does not specify a single dispatch point. The `EvaluatorBlockReason` extension pattern is the cleanest example: add a value to the Prisma enum, add an `EvaluatorBlockMetadata` entry, and the resolution-path switch will fall through to the default `/evals` route until extended. `MonitorNotFoundError extends LangfuseNotFoundError` (`packages/shared/src/features/monitors/service/types.ts:17`) shows the simple extension pattern. Caveat: many sites still throw bare `new Error(...)` and would not benefit from any new `BaseError` subclass. Caveat: name-based type guards (`isLLMCompletionError`, `isUnrecoverableError`) check `e.name === "<ClassName>"` rather than `instanceof`, so a subclass would not be detected by the existing guard.

## Architectural Decisions

- **Two-track taxonomy**: a flat HTTP-aligned `BaseError` family (`packages/shared/src/errors/`) plus per-source domain classes (`ClickHouseResourceError`, `LLMCompletionError`, `SlackApiError`, `UnrecoverableError`, `ObservationNotFoundError`, `CodeEvalDispatcherError`). Decision is implicit — each track was added as a need arose (web needed HTTP semantics for public API, worker needed retryable/terminal semantics for BullMQ, MCP needed user/server split).
- **`BaseError` carries `isOperational` but it's vestigial**: the constructor accepts it (`packages/shared/src/errors/BaseError.ts:17`) but no dispatch site reads it. The taxonomy is operational/observability-aware in intent but the runtime never uses that field.
- **`httpCode` is the primary discriminator**, not a `category` enum. The four middleware sites branch on `instanceof BaseError` and then read `error.httpCode` for status, `error.isUserError()` for log level. This couples the taxonomy to HTTP semantics.
- **`EvaluatorBlockReason` is the most disciplined source taxonomy**: six enum values stored as a Postgres column, paired with a metadata table for user-facing message + shortLabel + resolution path (`packages/shared/src/features/evals/evalConfigBlocking.ts:59-138`). Dispatch is deterministic — `LLM_CONNECTION_AUTH_INVALID` and `LLM_CONNECTION_MISSING` route to settings; missing template id falls back to `/evals`.
- **Public-API `code` enum is the SDK-facing contract** (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-25`) and is the only taxonomy that escapes internal classification — SDKs are told to "branch on `code` rather than parsing the human-readable `message`" (`fern/apis/server/definition/unstable/errors.yml:5-8`). This is the taxonomy's primary extensibility point for SDK consumers.
- **Worker has its own worker-local errors** (`UnrecoverableError`, `ObservationNotFoundError`) — the worker does **not** reuse `BaseError`. They live in `worker/src/errors/`. Justified because the worker is on BullMQ, not HTTP, so HTTP codes don't apply; the worker cares about retry/no-retry semantics.
- **MCP has its own MCP-local errors** (`UserInputError`, `ApiServerError`) — also bypassing `BaseError`. Justified by the comment "Following Sentry MCP pattern" (`web/src/features/mcp/core/errors.ts:1-7`): errors classify as user-fixable (4xx, show original message) vs server (5xx, log + show generic), then mapped onto `McpError` codes in `formatErrorForUser`.
- **`isRetryable` is set by the source**, not the handler: `fetchLLMCompletion` builds `LLMCompletionError` with `isRetryable` already filled in based on `responseStatusCode` + name + cause-chain inspection (`packages/shared/src/server/llm/fetchLLMCompletion.ts:880-928`). The retry handler just reads it.
- **Each source class carries structured metadata** for its domain — `SlackApiError.slackErrorCode`, `ClickHouseResourceError.errorType + tags`, `LLMCompletionError.responseStatusCode + isRetryable + blockReason`, `ObservationNotFoundError.observationId`. This is the operational-category data that `BaseError` lacks.

## Notable Patterns

- **Discriminator table for ClickHouse error types**: `ERROR_TYPE_CONFIG` is a `Record<ErrorType, { discriminators: string[] }>` (`packages/shared/src/server/repositories/clickhouse.ts:36-51`), and `wrapIfResourceError()` iterates over `Object.entries` to classify an arbitrary error message into one of three typed outcomes (`MEMORY_LIMIT` / `OVERCOMMIT` / `TIMEOUT`). Clean extensibility pattern for adding new resource-limit types.
- **Cause-chain walking for LLM error messages**: `findNonRetryableCauseMessage` and `extractCleanErrorMessage` (`packages/shared/src/server/llm/fetchLLMCompletion.ts:890-892`) walk `.cause` chains because Anthropic/OpenAI/Azure SDKs wrap fetch errors as `APIConnectionError { cause: original }`. The same walk determines both the user-visible message and the `isRetryable` classification.
- **Decision-tree comment in eval-queue processor**: the `catch (e)` block in `worker/src/queues/evalQueue.ts:179-201` is preceded by an ASCII decision tree showing exactly which error type → which retry strategy. Only place in the codebase where the dispatch is documented inline in the code.
- **Barrel + helper + translator trio for public API**: the public-API error contract is split into (a) Zod schema (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-25`), (b) error class + factory functions (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:33-141`), (c) unknown-to-typed translator (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`). Same pattern in MCP: Zod + helper + formatErrorForUser + wrapErrorHandling.
- **Two-track tests**: dedicated test files assert both that error formatting produces the right shape (`web/src/__tests__/server/mcp-error-formatting.servertest.ts:32-449`; `web/src/__tests__/server/trpc-error-formatting.servertest.ts:21-133`; `web/src/__tests__/server/unit/unstable-public-api-error-contract.servertest.ts:5-49`; `web/src/__tests__/server/unit/create-authed-project-api-route-auth-errors.servertest.ts:154-258`) and that source-classified errors carry the right fields (`worker/src/__tests__/fetchLLMCompletionTimeout.test.ts:104-310`; `worker/src/__tests__/fetchLLMCompletionErrors.test.ts:37-156`; `worker/src/__tests__/fetchLLMCompletionReasoning.test.ts:52-104`; `worker/src/features/utils/retry-handler.test.ts:32-79`).
- **Custom Prisma enum + metadata table** for `EvaluatorBlockReason` (`packages/shared/prisma/schema.prisma:1037-1044` + `packages/shared/src/features/evals/evalConfigBlocking.ts:59-99`) — the cleanest source-classified taxonomy in the codebase, with parallel `EvaluatorBlockSource` for the trigger (`packages/shared/src/server/services/blockEvaluatorConfigs.ts:14-22`).
- **Stable-name type guard via `Error.name`** instead of `instanceof`: `isLLMCompletionError`, `isUnrecoverableError`, `isObservationNotFoundError`, `isApiServerError` / `isUserInputError` all check `e instanceof Error && e.name === "<ClassName>"`. Robust against `instanceof` failures across module boundaries but does **not** survive subclassing — a subclass of `LLMCompletionError` would not be detected by `isLLMCompletionError` because `e.name` would be the subclass's name.
- **5xx → traceException, 4xx → logger.warn/info**: the log level is selected by `httpStatus` bucket (`web/src/server/api/trpc.ts:150-172`; `web/src/features/public-api/server/withMiddlewares.ts:65-80`). Runtime signal of "should the on-call look at this?" answered by `BaseError.isUserError()`.

## Tradeoffs

- **`BaseError` is HTTP-shaped, not source-shaped**: the L0 hierarchy classifies errors by HTTP semantics, so "model" vs "provider" vs "tool" vs "validation" vs "policy" vs "context" vs "user" vs "infrastructure" vs "timeout" is **not** expressed at the L0. That classification is in the domain-error layer (`LLMCompletionError.responseStatusCode` for provider/model, `ClickHouseResourceError.errorType` for infrastructure/timeout, `EvaluatorBlockReason` for provider/policy). A caller that wants "is this a model error?" has to check `instanceof LLMCompletionError` or `error.code === "evaluator_preflight_failed"`, not read a single `category` field.
- **No central "category" attribute**: `BaseError` has `name`, `httpCode`, `isOperational` but no `category`. The taxonomy's source information lives in the secondary classes, so logs and traces have to inspect the type chain to recover it.
- **Two-track enforcement is informal**: there is no lint rule, no test rule, no type-level rule that says "throw `BaseError` or `LLMCompletionError`, not bare `Error`". Numerous sites throw bare `Error` and bypass every dispatch site. Only the `BaseError`/`ClickHouseResourceError`/`LLMCompletionError` throws participate in middleware routing; bare errors get the default 500.
- **`isOperational` is vestigial**: set by every `BaseError` constructor to `true` (`packages/shared/src/errors/BaseError.ts:17`) but never read by dispatch or middleware. The intent was to mark "real" errors vs programmer errors, but the dispatch sites ignore it.
- **`name`-based type guards don't survive subclassing**: `isLLMCompletionError` matches `e.name === "LLMCompletionError"`, so a future `OpenAICompletionError extends LLMCompletionError` would **not** be detected. If subclasses are introduced later, the guards need to switch to `e instanceof LLMCompletionError` or check `name` against a prefix/suffix.
- **`EvaluatorBlockReason` only spans eval/evaluator failures**: the six enum values are all about the LLM-judge evaluator subsystem. They do **not** classify ingestion errors, dashboard errors, or storage errors.
- **`isRetryable` is hard-coded to defaults**: `LLMCompletionError` defaults `isRetryable` to `false` (`packages/shared/src/server/llm/errors.ts:45`) and the source decides based on status code + name. There is no per-caller override; if a particular LLM provider treats 503 as terminal, that decision has to be made in `fetchLLMCompletion`, not at the call site.
- **Public-API `code` is contractual** — adding a new `code` value is a breaking change for any SDK that `switch`es on `code`. Documented as the contract surface (`fern/apis/server/definition/unstable/errors.yml:5-8`) but means the public taxonomy grows slowly and is gated by Fern regeneration.
- **MCP and worker errors don't share a base**: `UserInputError`/`ApiServerError` and `UnrecoverableError`/`ObservationNotFoundError` are local to their packages. A future MCP+worker unification would have to introduce a new shared `BaseError` or accept the inconsistency.

## Failure Modes / Edge Cases

- **`name`-based guard vs `instanceof` mismatch** across module boundaries: the package boundaries between `packages/shared/src/server` (which exports `LLMCompletionError`, `ClickHouseResourceError`) and `worker` (which exports `UnrecoverableError`, `ObservationNotFoundError`) mean a function that imports both should be fine, but if `LLMCompletionError` were re-exported via a different module path (e.g., `@langfuse/shared` vs `@langfuse/shared/src/server`), `instanceof` could fail. The codebase uses `name`-based guards to avoid this, but as noted the guards don't survive subclassing.
- **`BaseError` with `httpCode >= 500` reclassified by translator**: in `toUnstablePublicApiError` (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:249-255`), a generic `BaseError` is rewritten to `"internal_error"` if `httpCode >= 500`, else `"invalid_request"`. So a `BaseError` with `httpCode = 401` becomes `"invalid_request"`, not `"authentication_failed"`. The dedicated `UnauthorizedError` branch handles this correctly, but the fallback loses fidelity.
- **Bare `Error` thrown with a 5xx-shaped message**: throws like `worker/src/queues/webhooks.ts:88` (`"Failed to generate webhook signature"`) use `InternalServerError`, which is correct, but throws like `worker/src/scripts/verifyClickhouseRecords/index.ts:300-948` use bare `Error` and the middleware can only treat them as unknown → 500 "Internal Server Error". The error message is leaked to the client (sanitized only for the public API's 4xx branch in `trpc.ts:198-210`).
- **ClickHouse error wrapping can wrap non-resource errors**: `ClickHouseResourceError.wrapIfResourceError()` matches message substrings (`packages/shared/src/server/repositories/clickhouse.ts:42-50`) including `"Timeout"`, `"timeout"`, `"timed out"`. A legitimate non-ClickHouse error message that contains the word "timeout" would be wrapped. Discriminator list is small enough that this is unlikely, but the heuristic is not bounded.
- **`UnrecoverableError` suppresses BullMQ retry but still updates jobExecution to ERROR with the message** (`worker/src/queues/evalQueue.ts:252-257`) — the user-visible error message can include internal model names ("Invalid LLM response format from model gpt-4o-2024-08-06") because the worker doesn't sanitize for end-users the way the tRPC middleware does.
- **`ObservationNotFoundError` retry policy is "manual, with max attempts"**: `retryObservationNotFound` (`worker/src/features/evaluation/retryObservationNotFound.ts:31`) returns a boolean; if `false`, the dataset-upsert processor logs warn and silently completes (`worker/src/queues/evalQueue.ts:73-85`). The eval job for that observation is **silently dropped**, which is the desired behavior (the observation will arrive eventually via ingestion) but is not visible in the job-execution status.
- **`UnrecoverableError` and `LLMCompletionError` short-circuit before logging**: in `worker/src/queues/evalQueue.ts:259`, `if (isLLMCompletionError(e) || isUnrecoverableError(e)) return;` — neither type is logged to `logger.error` and neither calls `traceException`. Production-side, terminal LLM/eval failures don't show up in error tracking.
- **`SlackApiError` always maps to `BAD_REQUEST` regardless of underlying code**: even `token_revoked` (which is a credential issue, conceptually `401`) is mapped to `BAD_REQUEST`/`400` at `web/src/features/slack/server/router.ts:371-373`. The router prefers a uniform 400 with a clear message over the more semantically correct status code.

## Future Considerations

- **Add a `category` field to `BaseError`**: e.g. `'auth' | 'validation' | 'policy' | 'resource' | 'upstream' | 'infrastructure' | 'unknown'`. Would let middleware sites branch on `category` for retry/log/alert policy without needing per-class `instanceof` chains. Today the same info is scattered across `BaseError.httpCode` + `instanceof ClickHouseResourceError` + `instanceof LLMCompletionError` + `EvaluatorBlockReason`.
- **Promote `UnrecoverableError` to `@langfuse/shared`**: worker-local placement (`worker/src/errors/UnrecoverableError.ts`) is fine for today but means the worker is the only consumer; if the web app ever needs to mark an error as "do not retry" (e.g., a webhook flow), it would have to invent its own class. Moving it to `packages/shared/src/errors/UnrecoverableError.ts` and exporting via `index.ts` would prevent divergence.
- **Make `isOperational` actually used**: set on every `BaseError` constructor (`packages/shared/src/errors/BaseError.ts:17`) but no dispatch site reads it. Either remove it (vestigial) or wire it into the log/tracing policy (e.g., `isOperational === false` → page on-call).
- **Lint rule against bare `throw new Error(...)`**: a project-local ESLint rule (or grep-based CI check) that flags any `throw new Error(...)` outside of test/seed/CLI code would push all runtime errors through the `BaseError` taxonomy. Today dozens of sites bypass it.
- **Centralize the four dispatch sites into one router**: `toUnstablePublicApiError` (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`), `formatErrorForUser` (`web/src/features/mcp/core/error-formatting.ts:27-104`), `withErrorHandling` (`web/src/server/api/trpc.ts:175-215`), and `withMiddlewares` (`web/src/features/public-api/server/withMiddlewares.ts:82-200`) all do the same `instanceof BaseError` → httpCode/message logic with slight variations. A single `translateToSurfaceError(error, surface: 'tRPC' | 'public-api' | 'mcp')` helper would unify them.
- **Extend the `EvaluatorBlockReason` metadata table to cover ingestion/storage errors**: today the enum only spans LLM-judge eval failures. Ingestion failures (e.g., schema validation, duplicate keys) and storage failures (e.g., S3 unavailability) don't have a parallel metadata table.
- **Make `LLMCompletionError` block reason observable**: today `blockReason` is read at the catch site in `worker/src/features/evaluation/evalService.ts:908-911` to call `blockEvaluatorConfigs`. Setting it as a span attribute on the OpenTelemetry trace would let postmortem dashboards show "evaluators blocked because: PROVIDER_ACCOUNT_NOT_READY" without re-running the code.
- **Switch `name`-based type guards to `instanceof` once module boundaries are sealed**: `isLLMCompletionError` and friends check `e.name === "LLMCompletionError"`, which doesn't survive subclassing. Once the codebase settles on `@langfuse/shared/src/server` as the only import path, `e instanceof LLMCompletionError` is safer.
- **Document the bare-`Error` sites**: the dozens of `throw new Error(...)` in `worker/src/scripts/verifyClickhouseRecords/index.ts`, `packages/shared/src/encryption/encryption.ts`, etc., are by design (these are CLI/seeder environments, not request-time code). An inline comment or `AGENTS.md` note explaining "these scripts intentionally throw bare `Error` because they don't run through the web/worker middleware" would prevent future contributors from mistakenly trying to route them.
- **Wire `BlockReason` defaults for new enum values**: when a new `EvaluatorBlockReason` value is added to the Prisma enum, the `EVALUATOR_BLOCK_METADATA` table (`packages/shared/src/features/evals/evalConfigBlocking.ts:59-93`) and the resolution-path switch (`packages/shared/src/features/evals/evalConfigBlocking.ts:101-120`) silently fall through. A test that asserts every `EvaluatorBlockReason` has metadata and a resolution path would catch missing entries.

## Questions / Gaps

- **Is `BaseError.isOperational` used anywhere?** Set by every `BaseError` constructor (`packages/shared/src/errors/BaseError.ts:17`), but no grep hit in `packages/`, `web/`, or `worker/` shows a dispatch site reading it. **No clear evidence found** that it informs retry/log/alert policy.
