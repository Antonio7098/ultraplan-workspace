## Summary

Langfuse maintains a **two-track, source-classified error taxonomy**:

1. **A flat HTTP-aligned `BaseError` hierarchy** in `packages/shared/src/errors/` (12 subclasses plus `BaseError`) that classifies operational failures by HTTP semantics — `InvalidRequestError` (400), `UnauthorizedError` (401), `ForbiddenError` (403), `LangfuseNotFoundError` (404), `MethodNotAllowedError` (405), `LangfuseConflictError` (409), `PayloadTooLargeError` (422), `ApiError` (variable), `InternalServerError` (500), `NotImplementedError` (501), `ServiceUnavailableError` (503). `BaseError` itself carries `httpCode`, `isOperational`, and a derived `isUserError()` predicate (`packages/shared/src/errors/BaseError.ts:1-27`). It is *not* organized by source subsystem.
2. **A set of domain-specific error classes** that *are* organized by source: `ClickHouseResourceError` for the analytics store, classified into `MEMORY_LIMIT` / `OVERCOMMIT` / `TIMEOUT` (`packages/shared/src/server/repositories/clickhouse.ts:36-99`); `LLMCompletionError` with `responseStatusCode`, `isRetryable`, and an inferred `EvaluatorBlockReason` (`packages/shared/src/server/llm/errors.ts:12-67`); `SlackApiError` with `slackErrorCode` (`packages/shared/src/server/services/SlackService.ts:21-29`); `UnrecoverableError` and `ObservationNotFoundError` in the worker (`worker/src/errors/UnrecoverableError.ts:1-17`; `worker/src/errors/ObservationNotFoundError.ts:1-22`); `CodeEvalExecutionError` and `CodeEvalDispatcherError` (`packages/shared/src/server/evals/codeEvalExecution.ts:78`; `packages/shared/src/server/evals/codeEvalDispatcherTypes.ts:142`); `QueryBuilderError`, `MonitorNotFoundError`; outbound-URL fetch errors `RedirectValidationError` / `MaxRedirectsExceededError` / `CircularRedirectError` (`packages/shared/src/server/outbound-url/fetch.ts:15-46`); and the MCP module's own `UserInputError` (4xx-equivalent) and `ApiServerError` (5xx-equivalent) pair (`web/src/features/mcp/core/errors.ts:19-63`).
3. **A persistence-layer source enum** `EvaluatorBlockReason` (`packages/shared/prisma/schema.prisma:1037-1044`) with six source categories (`LLM_CONNECTION_AUTH_INVALID`, `LLM_CONNECTION_MISSING`, `DEFAULT_EVAL_MODEL_MISSING`, `EVAL_MODEL_CONFIG_INVALID`, `EVAL_MODEL_UNAVAILABLE`, `PROVIDER_ACCOUNT_NOT_READY`), paired with `EvaluatorBlockSource` (`packages/shared/src/server/services/blockEvaluatorConfigs.ts:14-22`, four triggers) and metadata-driven resolution paths (`packages/shared/src/features/evals/evalConfigBlocking.ts:59-138`).
4. **A public-API error code enum** for the unstable evaluators API (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-25`; documented in `fern/apis/server/definition/unstable/errors.yml:3-27`) with 18 machine-readable codes such as `authentication_failed`, `access_denied`, `invalid_request`, `invalid_query`, `invalid_body`, `invalid_filter_value`, `invalid_json_path`, `invalid_variable_mapping`, `missing_variable_mapping`, `duplicate_variable_mapping`, `resource_not_found`, `name_conflict`, `evaluator_preflight_failed`, `conflict`, `unprocessable_content`, `rate_limited`, `method_not_allowed`, `internal_error`.

**Classification drives dispatch** in multiple well-tested sites. The unstable public API contract `toUnstablePublicApiError()` (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`) branches on `instanceof` for every `BaseError` subclass plus `ClickHouseResourceError` and ZodError, mapping each to a typed `code` + `httpCode` pair. The MCP `formatErrorForUser()` (`web/src/features/mcp/core/error-formatting.ts:27-104`) does the same kind of dispatch into McpError codes. The tRPC `withErrorHandling` middleware (`web/src/server/api/trpc.ts:175-215`) splits `ClickHouseResourceError` (advice message, UNPROCESSABLE_CONTENT) from `BaseError` (preserve httpCode) from "everything else" (sanitize to "Internal error"). The REST `withMiddlewares` (`web/src/features/public-api/server/withMiddlewares.ts:82-200`) layers `BaseError` → `ClickHouseResourceError` → Zod → Prisma → unknown, with `logBaseError()` selecting `info`/`warn`/`error` by `isUserError()` (`web/src/features/public-api/server/withMiddlewares.ts:65-80`). The worker's `evalQueue.ts` (`worker/src/queues/evalQueue.ts:178-269`) and `experimentQueue.ts` (`worker/src/queues/experimentQueue.ts:24-49`) branch on `isLLMCompletionError(e) && e.isRetryable` to schedule a delayed retry, vs `isLLMCompletionError(e) || isUnrecoverableError(e)` to suppress BullMQ retry, vs default to rethrow-and-retry. `evalService.ts:902-923` calls `LLMCompletionError.shouldBlockConfig()` and `getEvaluatorBlockReason()` to decide whether to call `blockEvaluatorConfigs()` with the inferred `EvaluatorBlockReason`. The Slack integration router (`web/src/features/slack/server/router.ts:352-369`) switches on `SlackApiError.slackErrorCode` to map upstream codes (`channel_not_found`, `not_in_channel`, `is_archived`, `invalid_auth`, `token_revoked`) onto user-friendly messages.

**Documentation is present but fragmented.** `web/AGENTS.md:179-183` codifies the tRPC + REST error-handling playbook ("Throw `BaseError` subclasses … let them bubble up … extend the `BaseError` or its subclasses in `packages/shared/src/errors/`"). `.agents/skills/backend-dev-guidelines/references/middleware-guide.md:552-633` documents the four-way tRPC and five-way REST error routing with worked examples. The Fern public API errors file (`fern/apis/server/definition/unstable/errors.yml:192-269`) gives recovery prose for each public `code`. The Prisma `EvaluatorBlockReason` enum has a full `EVALUATOR_BLOCK_METADATA` table with user-facing message + shortLabel + resolution path (`packages/shared/src/features/evals/evalConfigBlocking.ts:59-138`). The MCP errors file (`web/src/features/mcp/core/errors.ts:1-7`) explicitly cites the "Sentry MCP pattern" for its `UserInputError`/`ApiServerError` pair.

## Rating

**7 / 10** — Two-track, source-aware taxonomy. The HTTP-aligned `BaseError` family gives every handler a stable, `instanceof`-dispatchable type that maps cleanly to an HTTP code and is used consistently in three middlewares (tRPC, public REST, MCP). The domain-specific classes (`ClickHouseResourceError`, `LLMCompletionError`, `SlackApiError`, `ObservationNotFoundError`, `UnrecoverableError`, `EvaluatorBlockReason`) carry source-of-failure fields (`errorType`, `responseStatusCode`, `isRetryable`, `blockReason`, `slackErrorCode`) and are used at clear dispatch points to drive retry-vs-stop and user-facing message selection. The unstable-public-API `code` enum is documented in Fern and is the SDK-facing contract.

Deductions:
- The `BaseError` tree is organized by **HTTP code, not by source subsystem**, so it does not directly answer "model, provider, tool, validation, policy, context, user, infrastructure, timeout" — that classification lives in the *secondary* (domain) classes and in the `EvaluatorBlockReason` Prisma enum, not in the L0 hierarchy.
- The taxonomy is **not uniform across packages**: `web` uses `BaseError` + `ClickHouseResourceError` + Zod; `worker` uses `BaseError` + `LLMCompletionError` + `UnrecoverableError` + `ObservationNotFoundError`; MCP has its own `UserInputError`/`ApiServerError` pair; the public API has a separate Zod-error contract; and several files still throw bare `new Error(...)` (e.g. `worker/src/queues/monitorQueue.ts:24`, `worker/src/scripts/verifyClickhouseRecords/index.ts:300-948`, `packages/shared/src/encryption/encryption.ts:20-42`). There is no enforcement that every throw uses the hierarchy.
- The taxonomy is **not fully observable**: `isOperational` is set on `BaseError` but unused in dispatch; `isRetryable` is consumed only in worker queues; the HTTP code is the only thing that crosses the wire (no category attribute, no log span tag).
- The **leading dimension question** "Can you tell from the error type whether to retry, escalate, or stop?" is partially answered: yes for `LLMCompletionError` (via `isRetryable`), `UnrecoverableError` (do not retry), and `ClickHouseResourceError` (advice + 422), but no for the `BaseError` HTTP-aligned subclasses — those carry only the HTTP code, and retry policy is decided by the caller.

## Answers to Dimension Questions

1. **Are errors classified by source?** — Partially. The `BaseError` L0 hierarchy (`packages/shared/src/errors/BaseError.ts:1-27` and its 12 subclasses) is classified by **HTTP code, not by source subsystem** — it does not directly map to "model, provider, tool, validation, policy, context, user, infrastructure, timeout". Source classification lives in the *secondary* classes: `ClickHouseResourceError` carries `MEMORY_LIMIT | OVERCOMMIT | TIMEOUT` (`packages/shared/src/server/repositories/clickhouse.ts:36-99`); `LLMCompletionError` carries `responseStatusCode` + `isRetryable` + inferred `EvaluatorBlockReason` (`packages/shared/src/server/llm/errors.ts:12-67`); `SlackApiError` carries `slackErrorCode` (`packages/shared/src/server/services/SlackService.ts:21-29`); MCP has `UserInputError` (4xx) vs `ApiServerError` (5xx) (`web/src/features/mcp/core/errors.ts:19-49`); the Prisma `EvaluatorBlockReason` enum (`packages/shared/prisma/schema.prisma:1037-1044`) provides six source categories for paused evaluators; and the public-API `code` enum (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-25`) provides 18 source/category codes. So "classified by source" is true at the *domain-error* layer and at the *public-contract* layer, but not at the `BaseError` L0 layer.

2. **Is the taxonomy used for handling?** — Yes, extensively. The `BaseError` HTTP subclass tree is consumed by `toUnstablePublicApiError()` (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`) to map every `BaseError` subclass to a typed public-API `code` + `httpCode`; by `formatErrorForUser()` (`web/src/features/mcp/core/error-formatting.ts:27-104`) to map every `BaseError` + `MCP` error to an `McpError`; by the tRPC `withErrorHandling` (`web/src/server/api/trpc.ts:175-215`) to preserve `httpCode` and message; and by `withMiddlewares` (`web/src/features/public-api/server/withMiddlewares.ts:82-200`) to drive the response shape and log level. The LLM classification drives BullMQ retry vs terminal decisions in three queue processors (`worker/src/queues/evalQueue.ts:178-363`; `worker/src/queues/experimentQueue.ts:24-49`) and triggers `blockEvaluatorConfigs()` (`worker/src/features/evaluation/evalService.ts:901-923`). The `EvaluatorBlockReason` drives resolution-path routing (`packages/shared/src/features/evals/evalConfigBlocking.ts:101-120`). The Slack `slackErrorCode` drives user-message selection (`web/src/features/slack/server/router.ts:352-369`). The `ClickHouseResourceError.errorType` is passed through to OpenTelemetry traces (`packages/shared/src/server/repositories/clickhouse.ts:265-617`) and surfaced to the user as advice.

3. **Are error categories documented?** — Yes, in multiple places. `web/AGENTS.md:179-183` documents the tRPC + REST playbook in three bullets. `.agents/skills/backend-dev-guidelines/references/middleware-guide.md:552-633` documents the per-class routing for tRPC and REST with worked code. The Fern `errors.yml` (`fern/apis/server/definition/unstable/errors.yml:192-269`) gives per-error docs and recovery guidance for the public contract. The MCP `errors.ts:1-7` cites the "Sentry MCP pattern" as the model for the `UserInputError` / `ApiServerError` split. `packages/shared/src/features/evals/evalConfigBlocking.ts:59-138` documents the full `EvaluatorBlockReason` table with user-facing message + shortLabel + resolution path. There is **no single central taxonomy doc** — the documentation is fragmented across the web AGENTS.md playbook, the backend skill reference, the Fern contract, and inline code comments.

4. **Can new error types be added without breaking existing handling?** — Yes, but with caveats. New `BaseError` subclasses can be added in `packages/shared/src/errors/`, exported from `packages/shared/src/errors/index.ts:1-13`, and consumed by the four middleware dispatch sites (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`, `web/src/features/mcp/core/error-formatting.ts:27-104`, `web/src/server/api/trpc.ts:175-215`, `web/src/features/public-api/server/withMiddlewares.ts:82-200`) — but each dispatch site would need a new branch, and there is no central "registry" that auto-routes new types. The web AGENTS.md says "Extend the `BaseError` or its subclasses in `packages/shared/src/errors/` as needed" (`web/AGENTS.md:181-183`), but does not specify a single dispatch point. The `EvaluatorBlockReason` extension pattern is the cleanest example: add a value to the Prisma enum (`packages/shared/prisma/schema.prisma:1037-1044`), add a `EvaluatorBlockMetadata` entry (`packages/shared/src/features/evals/evalConfigBlocking.ts:59-93`), and the resolution-path switch (`packages/shared/src/features/evals/evalConfigBlocking.ts:101-120`) will leave it on the default `/evals` route until extended. `MonitorNotFoundError extends LangfuseNotFoundError` (`packages/shared/src/features/monitors/service/types.ts:17`) shows the simple extension pattern. Caveat: many sites still throw bare `new Error(...)` and would not benefit from any new `BaseError` subclass.

## Architectural Decisions

- **Two-track taxonomy**: a flat HTTP-aligned `BaseError` family (`packages/shared/src/errors/`) plus per-source domain classes (`ClickHouseResourceError`, `LLMCompletionError`, `SlackApiError`, `UnrecoverableError`, `ObservationNotFoundError`). Decision is implicit — each track was added as a need arose (web needed HTTP semantics for public API, worker needed retryable/terminal semantics for BullMQ).
- **`BaseError` carries `isOperational` but it's vestigial**: the constructor accepts it (`packages/shared/src/errors/BaseError.ts:1-22`) but no dispatch site reads it. The taxonomy is operational/observability-aware in intent but the runtime never uses that field.
- **`httpCode` is the primary discriminator**, not a `category` enum. The four middleware sites branch on `instanceof BaseError` and then read `error.httpCode` for status, `error.isUserError()` for log level. This couples the taxonomy to HTTP semantics.
- **`EvaluatorBlockReason` is the most disciplined source taxonomy**: six enum values stored as a Postgres column, paired with a metadata table for user-facing message + shortLabel + resolution path (`packages/shared/src/features/evals/evalConfigBlocking.ts:59-138`). The dispatch is deterministic — `LLM_CONNECTION_AUTH_INVALID` and `LLM_CONNECTION_MISSING` route to settings; missing template id falls back to `/evals`.
- **Public-API `code` enum is the SDK-facing contract** (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-25`) and is the *only* taxonomy that escapes the internal classification — SDKs and agents are told to "branch on `code` rather than parsing the human-readable `message`" (`fern/apis/server/definition/unstable/errors.yml:5-8`). This is the taxonomy's primary extensibility point for SDK consumers.
- **Worker has its own worker-local errors** (`UnrecoverableError`, `ObservationNotFoundError`) — the worker does *not* reuse `BaseError`. They live in `worker/src/errors/`. This is because the worker is on BullMQ, not HTTP, so the HTTP codes don't apply; the worker cares about retry/no-retry semantics.
- **MCP has its own MCP-local errors** (`UserInputError`, `ApiServerError`) — also bypassing `BaseError`. Justified by the comment "Following Sentry MCP pattern" (`web/src/features/mcp/core/errors.ts:1-7`): these errors classify errors as user-fixable (4xx, show original message) vs server (5xx, log + show generic), and are then mapped onto `McpError` codes in `formatErrorForUser` (`web/src/features/mcp/core/error-formatting.ts:27-104`).
- **`isRetryable` is set by the source**, not by the handler: `fetchLLMCompletion` builds `LLMCompletionError` with `isRetryable` already filled in based on `responseStatusCode` + name + cause-chain inspection (`packages/shared/src/server/llm/fetchLLMCompletion.ts:880-928`). The retry handler just reads it.
- **Each source class carries structured metadata** for its domain — `SlackApiError.slackErrorCode` (`packages/shared/src/server/services/SlackService.ts:24`), `ClickHouseResourceError.errorType + tags` (`packages/shared/src/server/repositories/clickhouse.ts:58-69`), `LLMCompletionError.responseStatusCode + isRetryable + blockReason` (`packages/shared/src/server/llm/errors.ts:32-35`), `ObservationNotFoundError.observationId` (`worker/src/errors/ObservationNotFoundError.ts:4-10`). This is the operational-category data that `BaseError` lacks.

## Notable Patterns

- **Discriminator table for ClickHouse error types**: `ERROR_TYPE_CONFIG` is a `Record<ErrorType, { discriminators: string[] }>` (`packages/shared/src/server/repositories/clickhouse.ts:36-51`), and `wrapIfResourceError()` iterates over `Object.entries` (`packages/shared/src/server/repositories/clickhouse.ts:82-95`) to classify an arbitrary error message into one of three typed outcomes (`MEMORY_LIMIT` / `OVERCOMMIT` / `TIMEOUT`). The "table of patterns → typed outcome" is a clean extensibility pattern for adding new resource-limit types.
- **Cause-chain walking for LLM error messages**: `findNonRetryableCauseMessage` and `extractCleanErrorMessage` (`packages/shared/src/server/llm/fetchLLMCompletion.ts:890-892`) walk `.cause` chains because Anthropic/OpenAI/Azure SDKs wrap fetch errors as `APIConnectionError { cause: original }`. The same walk determines both the user-visible message and the `isRetryable` classification.
- **Decision-tree comment in eval-queue processor**: the `catch (e)` block in `worker/src/queues/evalQueue.ts:179-201` is preceded by an ASCII decision tree showing exactly which error type → which retry strategy. This is the only place in the codebase where the dispatch is documented inline in the code.
- **Barrel + helper + translator trio for public API**: the public-API error contract is split into (a) Zod schema (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-25`), (b) error class + factory functions (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:33-141`), and (c) unknown-to-typed translator (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`). Same pattern in the MCP module: Zod + helper + formatErrorForUser + wrapErrorHandling.
- **Two-track tests**: dedicated test files assert both that error formatting produces the right shape (`web/src/__tests__/server/mcp-error-formatting.servertest.ts:32-449`; `web/src/__tests__/server/trpc-error-formatting.servertest.ts:21-133`; `web/src/__tests__/server/unit/unstable-public-api-error-contract.servertest.ts:5-49`; `web/src/__tests__/server/unit/create-authed-project-api-route-auth-errors.servertest.ts:154-258`) and that the source-classified errors carry the right fields (`worker/src/__tests__/fetchLLMCompletionTimeout.test.ts:104-310`; `worker/src/__tests__/fetchLLMCompletionErrors.test.ts:37-156`; `worker/src/__tests__/fetchLLMCompletionReasoning.test.ts:52-104`; `worker/src/features/utils/retry-handler.test.ts:32-79`).
- **Custom Prisma enum + metadata table** for `EvaluatorBlockReason` (`packages/shared/prisma/schema.prisma:1037-1044` + `packages/shared/src/features/evals/evalConfigBlocking.ts:59-99`) — the cleanest source-classified taxonomy in the codebase, with parallel `EvaluatorBlockSource` for the trigger (`packages/shared/src/server/services/blockEvaluatorConfigs.ts:14-22`).
- **Stable-name type guard via `Error.name`** instead of `instanceof`: `isLLMCompletionError` (`packages/shared/src/server/llm/errors.ts:65-67`), `isUnrecoverableError` (`worker/src/errors/UnrecoverableError.ts:15-17`), `isObservationNotFoundError` (`worker/src/errors/ObservationNotFoundError.ts:18-22`), `isApiServerError` / `isUserInputError` (`web/src/features/mcp/core/errors.ts:54-63`) — all check `e instanceof Error && e.name === "<ClassName>"`. This is robust against `instanceof` failures across module boundaries but does *not* survive subclassing (e.g., a subclass of `LLMCompletionError` would not be detected by `isLLMCompletionError` because `e.name` would be the subclass's name).
- **5xx → traceException, 4xx → logger.warn/info**: the log level is selected by `httpStatus` bucket (`web/src/server/api/trpc.ts:150-172`; `web/src/features/public-api/server/withMiddlewares.ts:65-80`). This is a runtime signal of "should the on-call look at this?", answered by `BaseError.isUserError()`.

## Tradeoffs

- **`BaseError` is HTTP-shaped, not source-shaped**: the L0 hierarchy classifies errors by HTTP semantics, so "model" vs "provider" vs "tool" vs "validation" vs "policy" vs "context" vs "user" vs "infrastructure" vs "timeout" is *not* expressed at the L0. That classification is in the domain-error layer (`LLMCompletionError.responseStatusCode` for provider/model, `ClickHouseResourceError.errorType` for infrastructure/timeout, `EvaluatorBlockReason` for provider/policy). A caller that wants "is this a model error?" has to check `instanceof LLMCompletionError` or `error.code === "evaluator_preflight_failed"`, not read a single `category` field.
- **No central "category" attribute**: `BaseError` has `name`, `httpCode`, `isOperational` but no `category`. The taxonomy's source information lives in the secondary classes, so logs and traces have to inspect the type chain to recover it.
- **Two-track enforcement is informal**: there is no lint rule, no test rule, no type-level rule that says "throw `BaseError` or `LLMCompletionError`, not bare `Error`". Numerous sites (`worker/src/scripts/verifyClickhouseRecords/index.ts:300-948`, `packages/shared/src/encryption/encryption.ts:20-42`, `worker/src/queues/monitorQueue.ts:24`) throw bare `Error` and bypass every dispatch site. This means the "taxonomy" is partial — only the `BaseError`/`ClickHouseResourceError`/`LLMCompletionError` throws participate in middleware routing; bare errors get the default 500.
- **`isOperational` is vestigial**: set by every `BaseError` constructor to `true` (`packages/shared/src/errors/BaseError.ts:17`) but never read by dispatch or middleware. The intent was to mark "real" errors vs programmer errors, but the dispatch sites ignore it.
- **`name`-based type guards don't survive subclassing**: `isLLMCompletionError` matches `e.name === "LLMCompletionError"`, so a future `OpenAICompletionError extends LLMCompletionError` would *not* be detected. If subclasses are introduced later, the guards need to switch to `e instanceof LLMCompletionError` or check `name` against a prefix/suffix.
- **`EvaluatorBlockReason` only spans eval/evaluator failures**: the six enum values are all about the LLM-judge evaluator subsystem. They do *not* classify ingestion errors, dashboard errors, or storage errors. A user-facing "what went wrong?" message is only as good as the enum.
- **`isRetryable` is hard-coded to defaults**: `LLMCompletionError` defaults `isRetryable` to `false` (`packages/shared/src/server/llm/errors.ts:45`) and the source decides based on status code + name. There is no per-caller override; if a particular LLM provider treats 503 as terminal, that decision has to be made in `fetchLLMCompletion`, not at the call site.
- **Public-API `code` is contractual** — adding a new `code` value is a breaking change for any SDK that `switch`es on `code`. This is documented as the contract surface (`fern/apis/server/definition/unstable/errors.yml:5-8`) but does mean the public taxonomy grows slowly and is gated by Fern regeneration.
- **MCP and worker errors don't share a base**: `UserInputError`/`ApiServerError` and `UnrecoverableError`/`ObservationNotFoundError` are local to their packages. A future MCP+worker unification would have to introduce a new shared `BaseError` or accept the inconsistency.

## Failure Modes / Edge Cases

- **`name`-based guard vs `instanceof` mismatch** across module boundaries: the package boundaries between `packages/shared/src/server` (which exports `LLMCompletionError`, `ClickHouseResourceError`) and `worker` (which exports `UnrecoverableError`, `ObservationNotFoundError`) mean a function that imports both should be fine, but if `LLMCompletionError` were re-exported via a different module path (e.g., `@langfuse/shared` vs `@langfuse/shared/src/server`), `instanceof` could fail. The codebase uses `name`-based guards to avoid this, but as noted the guards don't survive subclassing.
- **`BaseError` with `httpCode >= 500` reclassified by translator**: in `toUnstablePublicApiError` (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:249-255`), a generic `BaseError` is rewritten to `"internal_error"` if `httpCode >= 500`, else `"invalid_request"`. So a `BaseError` with `httpCode = 401` becomes `"invalid_request"`, not `"authentication_failed"`. The dedicated `UnauthorizedError` branch (lines 190-196) handles this correctly, but the fallback loses fidelity. This is intentional but undocumented at the call site.
- **Bare `Error` thrown with a 5xx-shaped message**: throws like `worker/src/queues/webhooks.ts:88` (`"Failed to generate webhook signature"`) use `InternalServerError`, which is correct, but throws like `worker/src/scripts/verifyClickhouseRecords/index.ts:300-948` use bare `Error` and the middleware can only treat them as unknown → 500 "Internal Server Error". The error message is leaked to the client (sanitized only for the public API's 4xx branch in `trpc.ts:198-210`).
- **ClickHouse error wrapping can wrap non-resource errors**: `ClickHouseResourceError.wrapIfResourceError()` matches message substrings (`packages/shared/src/server/repositories/clickhouse.ts:42-50`) including `"Timeout"` and `"timeout"` and `"timed out"`. A legitimate non-ClickHouse error message that contains the word "timeout" would be wrapped. The discriminator list is small enough that this is unlikely, but the heuristic is not bounded.
- **`UnrecoverableError` suppresses BullMQ retry but still updates jobExecution to ERROR with the message** (`worker/src/queues/evalQueue.ts:252-257`) — the user-visible error message can include internal model names ("Invalid LLM response format from model gpt-4o-2024-08-06") because the worker doesn't sanitize for end-users the way the tRPC middleware does.
- **`ObservationNotFoundError` retry policy is "manual, with max attempts"**: `retryObservationNotFound` (`worker/src/features/evaluation/retryObservationNotFound.ts:31`) returns a boolean; if `false`, the dataset-upsert processor logs warn and silently completes (`worker/src/queues/evalQueue.ts:73-85`). The eval job for that observation is *silently dropped*, which is the desired behavior (the observation will arrive eventually via ingestion) but is not visible in the job-execution status.
- **`UnrecoverableError` and `LLMCompletionError` short-circuit before logging**: in `worker/src/queues/evalQueue.ts:259`, `if (isLLMCompletionError(e) || isUnrecoverableError(e)) return;` — neither type is logged to `logger.error` and neither calls `traceException`. Production-side this means terminal LLM/eval failures don't show up in error tracking.
- **`SlackApiError` always maps to `BAD_REQUEST` regardless of underlying code**: even `token_revoked` (which is a credential issue, conceptually `401`) is mapped to `BAD_REQUEST`/`400` at `web/src/features/slack/server/router.ts:371-373`. The router prefers a uniform 400 with a clear message over the more semantically correct status code.

## Future Considerations

- **Add a `category` field to `BaseError`**: e.g. `'auth' | 'validation' | 'policy' | 'resource' | 'upstream' | 'infrastructure' | 'unknown'`. Would let middleware sites branch on `category` for retry/log/alert policy without needing per-class `instanceof` chains. Today the same info is scattered across `BaseError.httpCode` + `instanceof ClickHouseResourceError` + `instanceof LLMCompletionError` + `EvaluatorBlockReason`.
- **Promote `UnrecoverableError` to `@langfuse/shared`**: the worker-local placement (`worker/src/errors/UnrecoverableError.ts`) is fine for today but means the worker is the only consumer; if the web app ever needs to mark an error as "do not retry" (e.g., a webhook flow), it would have to invent its own class. Moving it to `packages/shared/src/errors/UnrecoverableError.ts` and exporting it via `index.ts` would prevent the divergence.
