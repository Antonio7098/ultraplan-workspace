## Summary

The OpenAI Agents SDK maintains a **deliberately small, single-rooted, source-classified exception tree** rooted at `AgentsException` (`src/agents/exceptions.py:46`). The L1 taxonomy is organized by **subsystem of origin**, not by HTTP code or operational category: model (`ModelBehaviorError`, `ModelRefusalError`), user (`UserError`), validation/policy (the four `*TripwireTriggered` classes plus `ToolInput/OutputGuardrailTripwireTriggered`), tool runtime (`ToolTimeoutError`, `MCPToolCancellationError`), and run control (`MaxTurnsExceeded`). The taxonomy is **the only one** in the package — there is **no separate `SandboxError` family**; sandbox uses a parallel, *independent* structured-error system (`src/agents/sandbox/errors.py:76`) with an `ErrorCode` enum that does not derive from `AgentsException` (`src/agents/sandbox/errors.py:12-56`). A voice-specific exception (`STTWebsocketConnectionError`) extends the same `AgentsException` root (`src/agents/voice/exceptions.py:4`).

The taxonomy is **used for handling at well-defined dispatch sites** rather than every catch site: (1) the run loop tags every `AgentsException` with `RunErrorDetails` (`src/agents/run_internal/run_loop.py:1175-1187`); (2) `MaxTurnsExceeded` and `ModelRefusalError` are routed through a **typed dispatch in `resolve_run_error_handler_result`** keyed by `"max_turns"` / `"model_refusal"` strings (`src/agents/run_internal/error_handlers.py:128-166`); (3) `_should_attach_generic_agent_error` excludes `ModelBehaviorError | InputGuardrailTripwireTriggered | OutputGuardrailTripwireTriggered` from span-error attachment (`src/agents/run_internal/run_loop.py:261-265`); (4) the MCP util passes `UserError` and `MCPToolCancellationError` through the FunctionTool failure pipeline while wrapping unknown errors in `AgentsException` (`src/agents/mcp/util.py:711-734`); (5) the tool failure pipeline (`_FailureHandlingFunctionToolInvoker`, `src/agents/tool.py:526-568`) routes *every* raised tool exception through `failure_error_function`/`on_handled_error` unless the caller explicitly opts out via `failure_error_function=None`.

The taxonomy is **partially documented**: there is a curated prose summary in `docs/running_agents.md:555-564`, a release note for the `ModelRefusalError` introduction (`docs/release.md:72-84`), and API reference pages `docs/ref/exceptions.md` and `docs/ref/run_error_handlers.md` (both are single-line `::: agents.exceptions` / `::: agents.run_error_handlers` directives that auto-render the class docstrings). There is **no machine-readable enumerator** (no `class ErrorKind(StrEnum)`) — the only enum-style artefact is the **sandbox-local** `ErrorCode` enum (`src/agents/sandbox/errors.py:12-56`). Tests guard the public contract by introspecting every `AgentsException` subclass and asserting it is re-exported from `agents.__init__` and `agents.__all__` (`tests/test_exception_exports.py:16-30`).

## Rating

**8 / 10** — A coherent, single-rooted, source-classified hierarchy with a real root (`AgentsException`), L1 leaves classified by subsystem (model / user / policy / tool / runtime), a **typed handler-dispatch** for `MaxTurnsExceeded` and `ModelRefusalError`, a tracing-aware branch (`_should_attach_generic_agent_error`), and an explicit re-export test that prevents silent extension breaks. Deductions: (a) the taxonomy **does not encode operational intent** (retry vs. escalate vs. stop) — that knowledge lives in prose and in `retry.py:ModelRetryNormalizedError` (`src/agents/retry.py:50-89`) which is decoupled from `AgentsException`; (b) the `SandboxError` family is **outside** the root and **does not share** any of the dispatch infrastructure, so the sandbox side of the SDK effectively has a second, parallel error vocabulary; (c) `ToolTimeoutError` is the only timeout-classified exception in the core tree but is *not* included in `_should_attach_generic_agent_error`’s exclusion list; (d) there is **no canonical "policy" or "validation" L1 parent** — guardrail tripwires are four flat siblings rather than a `GuardrailTripwireTriggered` parent that callers could `except` against; (e) `ModelRefusalError` is *not* a candidate for the typed error-handler dispatch until release `0.15.0` (`docs/release.md:72-84`), and there is no comparable dispatch for `InputGuardrailTripwireTriggered`, `OutputGuardrailTripwireTriggered`, or `ToolTimeoutError` — those still rely on `except` at call sites; (f) the public docs are intentionally short (`docs/running_agents.md:555-564` lists 7 of the 10 exception types and omits `ModelRefusalError`, `MCPToolCancellationError`, and `STTWebsocketConnectionError`).

## Answers to Dimension Questions

1. **Are errors classified by source?** Yes. The L1 taxonomy is organised by subsystem of origin: `ModelBehaviorError` / `ModelRefusalError` (model), `UserError` (caller code), the four `*TripwireTriggered` classes (policy/validation), `ToolTimeoutError` and `MCPToolCancellationError` (tool runtime), and `MaxTurnsExceeded` (run control). Each leaf carries a domain-specific payload (`refusal`, `tool_name`+`timeout_seconds`, `guardrail_result`, etc.). The L0 root is `AgentsException`. The `SandboxError` family is **not** part of this tree — it lives outside `AgentsException` and uses a code-enum classification (`ErrorCode`) plus a `retryable` field (`src/agents/sandbox/errors.py:76-95`).

2. **Is the taxonomy used for handling?** Partially. Handling is concentrated at well-defined dispatch sites rather than scattered across catch blocks:
   - **Typed run-error dispatch** for `MaxTurnsExceeded` and `ModelRefusalError` via `resolve_run_error_handler_result` and `RunErrorHandlers` (`src/agents/run_internal/error_handlers.py:128-166`; `src/agents/run_error_handlers.py:50-55`).
   - **`RunErrorDetails` injection** at the top of the streaming run loop for any `AgentsException` (`src/agents/run_internal/run_loop.py:1175-1187`).
   - **Tracing-aware branch** that excludes `ModelBehaviorError`, `InputGuardrailTripwireTriggered`, `OutputGuardrailTripwireTriggered` from generic span error attachment (`src/agents/run_internal/run_loop.py:261-265`).
   - **MCP pass-through** for `UserError` and `MCPToolCancellationError` so the FunctionTool failure pipeline sees them as first-class (`src/agents/mcp/util.py:711-734`).
   - **Tool failure pipeline** that converts *any* raised exception inside a function tool into either a model-visible error string or a re-raised exception based on `failure_error_function` (`src/agents/tool.py:526-568`).
   - **Output guardrail dispatch** that explicitly re-raises `OutputGuardrailTripwireTriggered` and `asyncio.CancelledError` but logs and re-raises everything else (`src/agents/run_internal/run_loop.py:380-388`).
   - **Sandbox retry classifier** (`_should_retry_in_isolated_session`) is operational, but the operation is keyed off the sandbox `SandboxError.retryable` field, **not** the `AgentsException` family (`src/agents/mcp/server.py:1500-1530`; `src/agents/sandbox/errors.py:94-103`).
   - **The retry module** (`src/agents/retry.py`) classifies via `ModelRetryNormalizedError` facts (`status_code`, `error_code`, `is_network_error`, `is_timeout`) rather than via `AgentsException` subclasses — these two classification systems are **decoupled**.

3. **Are error categories documented?** Partially. There is a curated prose overview in `docs/running_agents.md:555-564`, two API reference pages (`docs/ref/exceptions.md`, `docs/ref/run_error_handlers.md`), guardrail/tripwire mentions in `docs/guardrails.md`, the timeout mapping in `docs/tools.md:481-504`, the `ModelRefusalError` introduction note in `docs/release.md:72-84`, and *per-class docstrings* on every exception (`src/agents/exceptions.py:46-174`). There is **no central table** mapping each exception to its operational implication (retry vs. escalate vs. stop). The sandbox family has *no* analogous `docs/ref/sandbox/errors.md`.

4. **Can new error types be added without breaking existing handling?** Mostly yes, with caveats:
   - Adding a new `AgentsException` subclass to `agents.exceptions` is **detected automatically** by `test_all_public_exception_classes_are_reexported` (`tests/test_exception_exports.py:16-30`), so forgetting to re-export fails the test suite.
   - Adding a new L1 leaf does **not** require touching any catch site because the run loop only catches the **base** `AgentsException` (`src/agents/run_internal/run_loop.py:1175`).
   - To participate in the typed handler dispatch, the new type must extend the union on `RunErrorHandlerInput.error` (`MaxTurnsExceeded | ModelRefusalError`, `src/agents/run_error_handlers.py:30`), add a key to `RunErrorHandlers` (`src/agents/run_error_handlers.py:50-55`), and add the lookup in `resolve_run_error_handler_result` (`src/agents/run_internal/error_handlers.py:128-166`). There is no registry that would catch a missed branch — only a `test_exception_exports` test.
   - `_should_attach_generic_agent_error` must be edited if the new type should be **excluded** from span error attachment (`src/agents/run_internal/run_loop.py:261-265`). There is no extensibility hook.
   - **Caveat**: `ToolTimeoutError`, the two tool-level tripwire classes, and the three L2 tripwire classes (`InputGuardrailTripwireTriggered`, `OutputGuardrailTripwireTriggered`, `ModelRefusalError`, `ToolTimeoutError`, `MCPToolCancellationError`) are *all* caught individually in many test sites (`tests/test_agent_runner_streamed.py`, `tests/test_function_tool.py`, `tests/test_max_turns.py`), so they form an implicit "typed catch" contract — adding a *parallel* sibling type would not break those tests, but introducing a *behavioural change* to an existing leaf (e.g., re-routing `ToolTimeoutError` into a new parent) would.

## Architectural Decisions

- **Single L0 root, multiple L2 leaves with rich payloads.** `AgentsException` is intentionally small (it carries `run_data: RunErrorDetails | None`); subsystem-specific data lives on each leaf (`src/agents/exceptions.py:46-174`). This means callers can `except AgentsException` to capture the entire SDK and inspect `exc.run_data`, *or* `except ModelBehaviorError` to capture only model-class errors.
- **Subsystem-of-origin taxonomy.** Each leaf is named for the *thing that caused the error* (`ModelBehaviorError`, `UserError`, `ToolTimeoutError`, `InputGuardrailTripwireTriggered`). This is a source-of-truth contract — code reviews enforce that `UserError` is used for SDK misuse, `ModelBehaviorError` for malformed model output, and `*TripwireTriggered` for guardrail halts. There is no `class ConfigError` or `class NetworkError` parent — those would be the conventional operational categories.
- **No operational-classifier L1.** The SDK deliberately does *not* classify exceptions by "retry / escalate / stop". That decision is deferred to `RetryPolicy` (`src/agents/retry.py:231-358`) which classifies *normalized error facts* (`status_code`, `is_network_error`, `is_timeout`), not exception subclasses. The `SandboxError.retryable: bool | None` is the **only** operational-classifier field in the codebase.
- **Typed dispatch via `RunErrorHandlers`.** Two exception types — `MaxTurnsExceeded` and `ModelRefusalError` — are routed through a string-keyed `TypedDict` (`src/agents/run_error_handlers.py:50-55`). Adding a third requires editing the dict, the union on `RunErrorHandlerInput.error`, and the `resolve_run_error_handler_result` dispatch (`src/agents/run_internal/error_handlers.py:128-166`).
- **`_should_attach_generic_agent_error` as a small, intentional exclusion list.** Only three exception types are excluded from span error attachment — and those are *exactly* the three that should not surface as agent failures to the trace viewer (`src/agents/run_internal/run_loop.py:261-265`). This is the strongest piece of evidence that the taxonomy is operational, not just descriptive.
- **Sandbox error family is parallel, not subordinate.** `SandboxError(Exception)` is deliberately outside the `AgentsException` hierarchy. It carries `error_code: ErrorCode` and `retryable` fields, and is the only place in the SDK with a **string enum** error vocabulary (`src/agents/sandbox/errors.py:12-95`). The rationale (read from the dataclass docstring) is that sandbox errors are *user-facing, structured, machine-readable* — not the exception-as-control-flow pattern used by the run loop.
- **Tool failure pipeline swallows all exceptions by default, not just SDK exceptions.** `_FailureHandlingFunctionToolInvoker.__call__` (`src/agents/tool.py:526-568`) catches `Exception`, not `AgentsException`. Tool authors can raise any subclass — including BCL types like `ValueError` — and the pipeline routes it through `failure_error_function` or re-raises. Opt-out is `failure_error_function=None` (`docs/tools.md:512-518`).
- **Stream-drain signal piggybacks on exceptions.** `_mark_error_to_drain_stream_events` (`src/agents/exceptions.py:22-27`) sets a private `bool` attribute on the error so the streaming run loop drains queued events before propagating. This is a control-flow signal on the *same* exception object, not a new exception type — the SDK avoids "control-flow exceptions" as a pattern.
- **Tests act as the documentation contract for re-exports.** `test_exception_exports.py` walks `agents.exceptions`, finds every `AgentsException` subclass, and asserts it is reachable from the top-level `agents` namespace and listed in `agents.__all__`. This is the mechanism that prevents a forgotten re-export from breaking downstream `from agents import NewError` imports.

## Notable Patterns

- **Single-root tree with rich leaf payloads.** The `ModelRefusalError(refusal)`, `ToolTimeoutError(tool_name, timeout_seconds)`, and `*TripwireTriggered(guardrail_result)` constructor patterns embed the diagnostic context in the exception object itself (`src/agents/exceptions.py:78-86, 109-118, 121-144, 147-174`).
- **`RunErrorDetails` as a post-hoc run-state snapshot.** `streamed_result` is captured into `RunErrorDetails` only when an `AgentsException` is about to escape (`src/agents/run_internal/run_loop.py:1175-1187`). The dataclass includes `input`, `new_items`, `raw_responses`, `last_agent`, `context_wrapper`, and both guardrail result lists — so callers can reconstruct the full run state for diagnostics from the exception alone.
- **`_should_attach_generic_agent_error` as a trace-aware classification predicate.** Returning False for `ModelBehaviorError | InputGuardrailTripwireTriggered | OutputGuardrailTripwireTriggered` (`src/agents/run_internal/run_loop.py:261-265`) is a clean declarative pattern: "these exceptions are expected semantics, not failures."
- **String-keyed `TypedDict` for handler dispatch.** `RunErrorHandlers` uses `total=False` plus `RunErrorHandler[TContext]` callbacks (`src/agents/run_error_handlers.py:50-55`). Users provide `error_handlers={"max_turns": ..., "model_refusal": ...}` and the dispatch uses `error_handlers.get("max_turns")` (`src/agents/run_internal/error_handlers.py:137-142`).
- **Sandbox uses *both* an exception class and an enum code.** `SandboxError` carries `error_code: ErrorCode` and the `ErrorCode` enum is a stable, machine-readable vocabulary (`src/agents/sandbox/errors.py:12-56`). This is more rigorous than the agents-side taxonomy.
- **Async-cancellation is normalised, not raised.** `_FunctionToolCancelledError` is an internal adapter that lets the `ToolErrorFunction` signature see a cancellation as an `Exception` (`src/agents/tool.py:1657-1664`). Cancellation never escapes the SDK as a bare `asyncio.CancelledError` from the run loop — it is converted and routed.
- **Fail-fast vs. fail-soft dichotomy via `failure_error_function=None`.** Tool docs explicitly explain "If you explicitly pass `None`, then any tool call errors will be re-raised for you to handle" (`docs/tools.md:512-518`). The same exception is the dispatch signal; the *policy* is per-tool.
- **`__all__`-as-contract.** `agents.__all__` lists every public exception name (`src/agents/__init__.py:388-403`), and the test suite enforces that any new exception appears in both `agents.exceptions` and `agents.__all__` (`tests/test_exception_exports.py:16-30`).

## Tradeoffs

- **No operational parent → callers write ad-hoc retry logic.** The taxonomy does not include `RetryableError`, `TransientError`, `FatalError`, or any L1 classifier that says "retry me". The SDK punts this to `RetryPolicy` (`src/agents/retry.py`), which is decoupled from the exception class and works on normalized provider error facts. Consequence: code that wants "retry this user-visible error" must implement its own `except` ladder.
- **Guardrail tripwires are flat, not nested.** The four `*TripwireTriggered` classes (`InputGuardrailTripwireTriggered`, `OutputGuardrailTripwireTriggered`, `ToolInputGuardrailTripwireTriggered`, `ToolOutputGuardrailTripwireTriggered`) all derive directly from `AgentsException` with no `GuardrailTripwireTriggered` parent (`src/agents/exceptions.py:121-174`). Callers must enumerate all four to catch every guardrail failure.
- **`ToolTimeoutError` is not in the typed-handler dispatch.** Only `MaxTurnsExceeded` and `ModelRefusalError` participate in `RunErrorHandlers` (`src/agents/run_error_handlers.py:50-55`). A user who wants to *handle* `ToolTimeoutError` without re-raising must `try/except` at the call site — there is no `error_handlers={"tool_timeout": ...}` hook.
- **`SandboxError` outside `AgentsException`.** The sandbox side of the SDK uses an entirely separate classification system (`src/agents/sandbox/errors.py`). A caller using `except AgentsException` will *not* catch `SandboxError`, even when sandbox runs are embedded inside an agent. There is **no `SandboxError` re-raised inside `except AgentsException`** boundary — sandbox failures surface to the caller as `SandboxError`, not as a subclass.
- **`_should_attach_generic_agent_error` is a closed allow-list, not a classifier.** It is hard-coded to three exception types (`src/agents/run_internal/run_loop.py:261-265`). A new exception type is *attached* to the span unless explicitly added here. There is no test that the list is up-to-date.
- **`docs/running_agents.md:555-564` omits `ModelRefusalError`, `MCPToolCancellationError`, and the two tool-level guardrail classes.** The prose overview is incomplete. A user reading the docs will not learn that `ModelRefusalError` exists until they read `docs/release.md:72-84` or the API reference.
- **`RunErrorDetails` is mutated on `AgentsException` after construction.** `exc.run_data = RunErrorDetails(...)` (`src/agents/run_internal/run_loop.py:1178-1186`) mutates a slot that was initialised to `None` in `__init__`. This is intentional but means `AgentsException.run_data` is `None` until the exception passes through the run loop — a unit test that constructs the exception outside the loop will see `None` (`src/agents/exceptions.py:53`).
- **`ToolTimeoutError` is raised by `invoke_function_tool` only for the `timeout_behavior="raise_exception"` path** (`src/agents/tool.py:1830-1835`). The default `error_as_result` returns a model-visible message instead. So `ToolTimeoutError` only appears when the user explicitly opts in.
- **Stream-drain signal is private.** `_mark_error_to_drain_stream_events` uses `_DRAIN_STREAM_EVENTS_ATTR = "_agents_drain_queued_stream_events"` (`src/agents/exceptions.py:19`), an underscore-prefixed attribute. It is internal but observable to anyone catching the exception.

## Failure Modes / Edge Cases

- **A `ModelBehaviorError` raised by a *user-side* bug (e.g., wrapping a tool that returns malformed JSON) is indistinguishable from a *model-side* bug.** Both flow through the same class. There is no `ToolsideBehaviorError`.
- **`ToolTimeoutError` and `asyncio.CancelledError` look similar at the type level** but are routed differently. Cancellation is normalised through `_FunctionToolCancelledError` (`src/agents/tool.py:1657-1664`); timeout is constructed explicitly (`src/agents/tool.py:1830-1835`). If the user cancels a tool from outside (e.g., `task.cancel()`), the SDK may surface it as an internal `MCPToolCancellationError` (for MCP) or as a `_FunctionToolCancelledError` (for function tools).
- **`SandboxError` cannot be caught by `except AgentsException`.** Sandbox failures (`src/agents/sandbox/errors.py:77`) inherit only from `Exception`. A blanket `except AgentsException` in caller code will leak sandbox errors.
- **`run_data` is `None` for `AgentsException` constructed outside the run loop.** Tests and direct constructors do not populate it (`src/agents/exceptions.py:53`).
- **`ModelRefusalError` cannot be raised on structured-output retries.** Before `0.15.0`, refusal-only responses for structured-output agents would *retry* until `MaxTurnsExceeded`; now they raise `ModelRefusalError` directly (`docs/release.md:72-84`). Code that expected `final_output == ""` will now see an exception.
- **`AgentsException` carries no `log_level` knob** (unlike Microsoft Agent Framework's `AgentFrameworkException`). Every `AgentsException` logs at the same default level. Control-flow-like signals (`_mark_error_to_drain_stream_events`) are attribute flags, not log-suppressing exceptions.
- **`pytest.raises(ModelBehaviorError)` may swallow the JSON-decode inner cause.** The SDK uses `raise ModelBehaviorError(...) from exc` for parsing errors (`src/agents/tool.py:1590-1596`), but the chain is preserved as `__cause__`, not as `args`. Tests must inspect `exc.__cause__` to see the underlying `json.JSONDecodeError`.

## Future Considerations

- **Promote the four `*TripwireTriggered` classes to a `GuardrailTripwireTriggered` parent** so callers can `except GuardrailTripwireTriggered` once instead of enumerating four. The existing `guardrail_result`/`output` payload fields are not uniform, so this requires deciding on a payload contract (`src/agents/exceptions.py:121-174`).
- **Add `tool_timeout` to `RunErrorHandlers`** so `ToolTimeoutError` can be handled at the run level instead of via per-tool `try/except` (`src/agents/run_error_handlers.py:50-55`). This requires editing the union, the dict, and the dispatch (`src/agents/run_internal/error_handlers.py:128-166`).
- **Bridge `SandboxError` to `AgentsException`.** Either (a) make `SandboxError(AgentsException)` so the base catch works, or (b) define a parallel `__init__.py` re-export for the sandbox family and document the boundary explicitly.
- **Expose `retryable` on `AgentsException`.** The SDK already has the concept (`src/agents/sandbox/errors.py:94-103`) but only for sandbox. A `retryable: bool | None = None` slot on `AgentsException` would let callers write `retry_if_retryable(exc)` without inspecting class names.
- **Auto-attach new exclusions to span errors.** Replace the hard-coded `_should_attach_generic_agent_error` allow-list (`src/agents/run_internal/run_loop.py:261-265`) with a class attribute on each exception (e.g., `attach_to_span: bool = True`) so new L1 leaves opt in correctly by default.
- **Update `docs/running_agents.md:555-564`** to include `ModelRefusalError`, `MCPToolCancellationError`, `ToolInputGuardrailTripwireTriggered`, `ToolOutputGuardrailTripwireTriggered`, and `STTWebsocketConnectionError`. The current list covers 7 of 10.
- **Add an explicit operational-category reference** (e.g., a "retry / escalate / stop" column in the docs table) so callers don't have to read release notes and source to learn which exceptions are retryable.
- **Promote `retry_policies.network_error()` and friends to know about `AgentsException` subtypes** so a `ModelBehaviorError` raised from a transient network glitch isn't blindly retried by a policy that only inspects `is_network_error`.

## Questions / Gaps

- The exception taxonomy does not include a `ContextWindowExceededError` or `TokenLimitExceededError`. When the model's context is too long, the SDK currently relies on the underlying provider's exception bubbling up and being treated as a generic `Exception`. There is no evidence of a typed surface for this in `src/agents/`.
- `docs/running_agents.md:555-564` does not mention `STTWebsocketConnectionError` (voice), `MCPToolCancellationError` (MCP), `ToolInputGuardrailTripwireTriggered` (per-tool input guardrails), or `ToolOutputGuardrailTripwireTriggered` (per-tool output guardrails). No evidence found of a complete reference page that enumerates every subclass.
- There is no public `agents.errors` namespace — exceptions live in `agents.exceptions` (`src/agents/__init__.py:20-33`). A namespace change is a breaking change but could improve discoverability.
- The `_agents_drain_queued_stream_events` attribute protocol (`src/agents/exceptions.py:19-27`) is undocumented in `docs/`. The SDK relies on it internally but never tells callers about it.
- The `voice.exceptions` module (`src/agents/voice/exceptions.py:1-8`) follows the `AgentsException` convention but is not surfaced in `docs/running_agents.md:555-564`. No evidence found of a voice-specific error reference page beyond `docs/ref/voice/exceptions.md:1-3` (mkdocstrings directive).
- The retry-pipeline (`src/agents/retry.py`) and the exception taxonomy (`src/agents/exceptions.py`) are **not** connected by any code path I could find. `ModelRetryNormalizedError` inspects exception types indirectly (via `_should_attach_generic_agent_error`-style branches in `models/openai_responses.py` and friends), but no central dispatcher maps `AgentsException` subclasses to retry decisions. This is a gap that future work could close.
