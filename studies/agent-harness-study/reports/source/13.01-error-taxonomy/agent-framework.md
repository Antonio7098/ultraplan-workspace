## Summary

The repository is a **dual-stack** agent framework (Python + .NET) maintained by Microsoft. The Python side carries a **mature, single-rooted, domain-scoped error taxonomy** rooted at `AgentFrameworkException` (`python/packages/core/agent_framework/exceptions.py:15`). The .NET side has **no equivalent central taxonomy**; each sub-package (`Microsoft.Agents.AI.Purview`, `Microsoft.Agents.AI.Workflows.Declarative`, `Microsoft.Agents.AI.DurableTask`, `Microsoft.Agents.AI.LocalCodeAct`) defines its own ad-hoc subclass of `System.Exception`, and the rest of the codebase uses built-in .NET exceptions (`InvalidOperationException`, `ArgumentException`, `ArgumentNullException`, `NotSupportedException`). Because the dimension prompt scopes to "the selected source" (the whole repo), the score reflects the union.

The Python taxonomy is organized by **subsystem of origin**, not by HTTP code or by operational category, and the documentation in `python/CODING_STANDARD.md:205-302` codifies a parallel set of leaf classes per L1 branch (`InvalidAuth`, `InvalidRequest`, `InvalidResponse`, `ContentFilter`) so that callers can handle the same failure mode uniformly across subsystems. The base class `AgentFrameworkException` carries an optional `inner_exception` and a configurable `log_level` (`python/packages/core/agent_framework/exceptions.py:21-38`) — meaning the taxonomy is the **first-class logging surface**, not just a marker for control flow. The `inner_exception` semantics were hardened in PR #5167 (`python/CHANGELOG.md:251`).

Handling is concentrated at well-defined dispatch sites rather than scattered. The OpenAI chat client maps raw SDK errors to typed exceptions via `_handle_request_error` (`python/packages/openai/agent_framework_openai/_chat_client.py:598-611`); the workflow runner re-raises `WorkflowCheckpointException` and wraps lower errors with `from` chaining (`python/packages/core/agent_framework/_workflows/_runner.py:296-300, 309-312`); `MiddlewareTermination` is caught at loop boundaries to signal control-flow termination (`python/packages/core/agent_framework/_middleware.py:917, 1082`); `AgentFrameworkException` is caught by the Foundry hosting layer to extract OAuth consent URLs (`python/packages/foundry_hosting/agent_framework_foundry_hosting/_responses.py:497-513`); `ToolException` is re-raised through the MCP context-manager entry path (`python/packages/core/agent_framework/_mcp.py:2285-2289`).

Extensibility works through **subclassing** the AF root or a branch root. Purview maps HTTP-status-like failures (401/402/403/429) to specific subclasses of `IntegrationException` / `IntegrationInvalidAuthException` (`python/packages/purview/agent_framework_purview/_exceptions.py:15-32`). OpenAI's content-filter exception extends `ChatClientContentFilterException` and adds severity enums (`python/packages/openai/agent_framework_openai/_exceptions.py:13-90`). MCP adds an internal `_MCPTaskAbandoned(ToolExecutionException)` marker (`python/packages/core/agent_framework/_mcp.py:244-248`). The taxonomy is also used as a tracing signal: `observability.capture_exception` stamps the OpenTelemetry `error.type` attribute with `type(exception).__name__` (`python/packages/core/agent_framework/observability.py:2278-2282`), so the class name is the operational classifier for telemetry.

Documentation is strong on the Python side: a full ASCII tree diagram and a 12-row "When to Use AF Exceptions vs Built-ins" table in `python/CODING_STANDARD.md:205-302`, with `python/packages/core/agent_framework/exceptions.py:5-7` explicitly pointing readers there. The .NET side has **no** central exception-hierarchy document; sub-package docs are minimal.

## Rating

**7 / 10** — Python: clear single-rooted taxonomy, documented, used in dispatch, extensible through subclassing, and tested. Deductions: (a) the taxonomy is **not** an operational-intent taxonomy — it does not encode "retry / escalate / stop" decisions; that knowledge is in prose, in the OpenAI client dispatch (`_handle_request_error`), and in MCP's task-abandonment subclass (`_MCPTaskAbandoned`), but there is **no** machine-readable `Retryable` flag or `ErrorKind` enum; (b) one class documented in the standard (`MiddlewareTermination`) actually lives in `_middleware.py:72`, not `exceptions.py` — a small split; (c) `DeclarativeLoaderError` and `ProviderLookupError` extend `AgentException` rather than `WorkflowException` (`python/packages/declarative/agent_framework_declarative/_loader.py:127-134`), which is a debatable classification; (d) `SettingNotFoundError` is the only non-domain leaf and is a flat sibling of `AgentFrameworkException` rather than a child of a "Settings" L1 branch (`python/packages/core/agent_framework/exceptions.py:228-231`); (e) the .NET side has **no central taxonomy**, **no** documentation, and uses built-in `System.Exception`-derived classes inconsistently across packages — dragging the union score down from the Python 8-9 range; (f) only a single Python test file (`python/packages/core/tests/core/test_exceptions.py:1-27`) exercises the **base class itself** — the leaf tests live in feature test files (e.g., `python/packages/core/tests/core/test_settings.py:235-282`, `python/packages/azure-cosmos/tests/test_cosmos_checkpoint_storage.py:222-247`, `python/packages/copilotstudio/tests/test_acquire_token.py:189-206`).

Yes — you can tell from the error type whether to retry, escalate, or stop, but only by reading the prose table in `CODING_STANDARD.md:273-291` plus the runtime dispatch in `_handle_request_error` (`_chat_client.py:598-611`) and the `_MCPTaskAbandoned` marker (`_mcp.py:244-248`). The answer is not encoded in the class.

## Answers to Dimension Questions

1. **Are errors classified by source?** Yes on the Python side; no on the .NET side.
   - Python L1 taxonomy is organised by subsystem of origin: agent (`AgentException`), chat client (`ChatClientException`), integration (`IntegrationException`), content (`ContentError`), tool (`ToolException`), middleware (`MiddlewareException`), setting (`SettingNotFoundError`), workflow (`WorkflowException`). Each L1 branch carries a parallel set of leaves (`InvalidAuth`, `InvalidRequest`, `InvalidResponse`, `ContentFilter`) so the same failure mode is named the same way across subsystems (`python/CODING_STANDARD.md:215-217`).
   - Sub-package extensions stay on-source: Purview extends `IntegrationException` / `IntegrationInvalidAuthException` (`python/packages/purview/agent_framework_purview/_exceptions.py:15-32`); OpenAI extends `ChatClientContentFilterException` (`python/packages/openai/agent_framework_openai/_exceptions.py:56-90`); MCP extends `ToolExecutionException` (`python/packages/core/agent_framework/_mcp.py:244-248`); declarative workflows extend `WorkflowException` (`python/packages/declarative/agent_framework_declarative/_workflows/_errors.py:18-38`).
   - Notable departures: `DeclarativeLoaderError` extends `AgentException` (`python/packages/declarative/agent_framework_declarative/_loader.py:127`) — debatable; `SettingNotFoundError` is a flat sibling of the L1 branches rather than a child of a "Settings" branch (`python/packages/core/agent_framework/exceptions.py:228-231`).
   - .NET has **no central classification**; each sub-package defines its own ad-hoc `System.Exception` subclass with no shared root, and the rest of the codebase uses built-in BCL exceptions (`InvalidOperationException`, `ArgumentException`, `ArgumentNullException`, `ArgumentOutOfRangeException`, `NotSupportedException`). The Purview sub-tree is the most structured (7 leaves by HTTP-status-equivalent: 401/402/403/429/etc.) but it is **not** the framework root — it is a parallel island (`dotnet/src/Microsoft.Agents.AI.Purview/Exceptions/*.cs`).

2. **Is the taxonomy used for handling?** Yes on the Python side, at well-defined dispatch sites; minimal on the .NET side.
   - **Python dispatch sites**:
     - `_handle_request_error` in OpenAI client maps raw `BadRequestError(code="content_filter")` → `OpenAIContentFilterException`, all other errors → `ChatClientException` (`python/packages/openai/agent_framework_openai/_chat_client.py:598-611`).
     - Workflow runner re-raises `WorkflowCheckpointException` unchanged and wraps lower `Exception` as `WorkflowCheckpointException(...) from e` (`python/packages/core/agent_framework/_workflows/_runner.py:296-312`).
     - `MiddlewareTermination` is the control-flow signal that short-circuits the middleware loop; `contextlib.suppress(MiddlewareTermination)` lets it bubble at three loop sites (`python/packages/core/agent_framework/_middleware.py:917, 1082`; `python/packages/core/agent_framework/_harness/_loop.py:547`).
     - Foundry hosting catches `AgentFrameworkException` and inspects inner exceptions for OAuth consent URLs (`python/packages/foundry_hosting/agent_framework_foundry_hosting/_responses.py:497-513`).
     - MCP context-manager entry re-raises `ToolException` unchanged, wraps other `Exception` in `ToolExecutionException(..., inner_exception=ex) from ex` (`python/packages/core/agent_framework/_mcp.py:2282-2289`).
     - `observability.capture_exception` tags spans with `error.type = type(exception).__name__` so the class name is the operational classifier for telemetry (`python/packages/core/agent_framework/observability.py:2278-2282`).
   - **.NET dispatch sites**: the only handling dispatch found is in the Workflows.Declarative sub-package tests, which assert default / message / inner-exception constructors (`dotnet/tests/Microsoft.Agents.AI.Workflows.Declarative.UnitTests/DeclarativeWorkflowExceptionTest.cs:1-51`). The main Microsoft.Agents.AI package uses `throw new InvalidOperationException(...)` / `throw new ArgumentException(...)` directly without any dispatch by type.

3. **Are error categories documented?** Yes on the Python side, with a comprehensive hierarchy diagram and a 12-row decision table; **no** on the .NET side.
   - Python: ASCII tree (`python/CODING_STANDARD.md:227-271`), When-to-use table (`python/CODING_STANDARD.md:273-291`), branch-selection rule (`python/CODING_STANDARD.md:292-302`), docstring policy (`python/CODING_STANDARD.md:455-456`), module-docstring policy (`python/CODING_STANDARD.md:25-26`). The `exceptions.py` module docstring explicitly points readers to `python/CODING_STANDARD.md § Exception Hierarchy` (`python/packages/core/agent_framework/exceptions.py:5-7`).
   - .NET: no central documentation; per-class XML doc summaries (`<summary>`) are present on every exception class but no hierarchy diagram or decision table exists.

4. **Can new error types be added without breaking existing handling?** Yes on the Python side, partially; limited on the .NET side.
   - Python additions are detected by the existing test suites catching the new type by class name (e.g., `pytest.raises(PurviewAuthenticationError)` proves subclassing works without changing the root contract — `python/packages/purview/tests/purview/test_exceptions.py:29`).
   - Adding a new `AgentException` / `ChatClientException` / `IntegrationException` leaf does **not** require changing any catch site because the dispatch functions either catch the base (`WorkflowCheckpointException` re-raise path, `AgentFrameworkException` in Foundry hosting) or pattern-match on specific shapes (HTTP `code` in OpenAI, validation enum in workflow).
   - Adding a **new L1 branch** requires editing `python/packages/core/agent_framework/exceptions.py` and `python/CODING_STANDARD.md` (the documented hierarchy diagram), but no catch site change.
   - Adding to the OpenAI dispatch requires editing `_handle_request_error` (no registry, no central handler).
   - .NET: `DeclarativeWorkflowException` is `public class ... : Exception` (not sealed) so external packages can subclass (`dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Exceptions/DeclarativeWorkflowException.cs:10`), but the lack of a central contract means additions are ad-hoc and undocumented.

## Architectural Decisions

- **Single root, parallel leaves**: All AF-specific Python exceptions inherit from `AgentFrameworkException` (`python/packages/core/agent_framework/exceptions.py:15`); the three "transport"-style branches (`AgentException`, `ChatClientException`, `IntegrationException`) share parallel leaves (`InvalidAuth`, `InvalidRequest`, `InvalidResponse`, `ContentFilter`) so callers can handle the same failure mode uniformly across subsystems (`python/CODING_STANDARD.md:215-217`).
- **Built-ins for validation**: Parameter / state validation errors use `ValueError`, `TypeError`, `RuntimeError`, `KeyError`; AF-specific exceptions are reserved for domain-level failures (`python/CODING_STANDARD.md:218-220`). This is enforced in code, e.g., `_tools.py:400-402, 489`, `_settings.py:159, 215`, `_middleware.py:300-313`.
- **No compatibility aliases**: Renamed or removed exceptions are not kept as aliases — a deliberate trade-off for hierarchy clarity over backward compatibility (`python/CODING_STANDARD.md:221-222`).

## Notable Patterns

- **Subsystem-scoped leaves**: The taxonomy maps cleanly to subsystem boundaries (Agent/ChatClient/Integration/Content/Tool/Middleware/Setting/Workflow) rather than to HTTP codes or operational categories — matches the dimension prompt's intent for source-classified errors.
- **Parallel leaf pattern**: `Agent*Exception` and `Chat*Exception` and `Integration*Exception` all share `InvalidAuth`, `InvalidRequest`, `InvalidResponse`, `ContentFilter` siblings — a documented design principle (`python/CODING_STANDARD.md:215-217`).
- **Domain payload via subclass attributes**: `UserInputRequiredException.contents` carries the user-input-request Content items (`python/packages/core/agent_framework/exceptions.py:197-209`); `OpenAIContentFilterException` carries `param`, `content_filter_code`, `content_filter_result` (`python/packages/openai/agent_framework_openai/_exceptions.py:56-90`); `WorkflowValidationError` carries `validation_type` plus per-subclass fields (`edge_id`, executor IDs, type lists) (`python/packages/core/agent_framework/_workflows/_validation.py:30-82`); `AgentNotRegisteredException.AgentName` carries the missing agent name (`dotnet/src/Microsoft.Agents.AI.DurableTask/AgentNotRegisteredException.cs:40`).
- **Control-flow exceptions as subclasses**: `MiddlewareTermination(MiddlewareException)` is a control-flow exception (not an error) that propagates to signal loop termination — distinguished by `log_level=None` and `result` attribute (`python/packages/core/agent_framework/_middleware.py:72-79`).
- **`inner_exception` chaining**: AF root propagates `inner_exception` through `super().__init__`, so the standard Python `__cause__` chain works (`python/packages/core/agent_framework/exceptions.py:35-37`).
- **Logging at exception construction**: `AgentFrameworkException.__init__` calls `logger.log(log_level, message, exc_info=inner_exception)` so exceptions are logged when raised, not when caught (`python/packages/core/agent_framework/exceptions.py:33-34`).
- **Taxonomy used as tracing classifier**: `error.type` attribute on OpenTelemetry spans is the class name, so the AF taxonomy is the tracing taxonomy (`python/packages/core/agent_framework/observability.py:2278-2282`).
- **MCP pass-through vs wrap**: MCP module re-raises `ToolException` unchanged (pass-through) and wraps unknown `Exception` as `ToolExecutionException(..., inner_exception=ex) from ex` — a clean "preserve taxonomy when known, classify when unknown" rule (`python/packages/core/agent_framework/_mcp.py:2282-2289`).

## Tradeoffs

- **Source-classification over operational-intent**: The taxonomy tells you *where* the error came from, not *what to do* about it. Retry / escalate / stop decisions are encoded in prose (`python/CODING_STANDARD.md:273-291`), in `_handle_request_error` (`_chat_client.py:598-611`), and in `_MCPTaskAbandoned` (`_mcp.py:244-248`), not in the class.
- **Parallel leaves trade flexibility for verbosity**: Three subsystems × four parallel leaves = 12 leaf classes just for the "transport" trio; adding a new failure mode (e.g., `QuotaExceeded`) requires touching three branches unless the new mode is subsystem-specific.
- **Built-ins for validation trade clarity for type safety**: Using `ValueError` / `TypeError` / `KeyError` for validation keeps Python idiomatic but means callers cannot dispatch on "is this an AF configuration error" without checking message strings or wrapping.
- **No retry classifier**: There is no `Retryable` flag, no `ErrorKind` enum, no central retry policy table. Retry semantics live in callers (e.g., `chatkit/_converter.py:165-388`, `bedrock/_chat_client.py:244-371`).
- **.NET language-conventional design**: BCL exceptions are idiomatic in .NET; the absence of a central root is consistent with .NET culture, but the lack of documentation means callers cannot reason about cross-package error handling.
- **Module split for `MiddlewareTermination`**: The standard shows it under `MiddlewareException` (`python/CODING_STANDARD.md:268`), but it lives in `_middleware.py:72`, not `exceptions.py`. Importing from `.exceptions` would create a layering inversion (middleware imports from base types, not the other way around).
- **No compatibility aliases**: The "no compatibility aliases" rule (`python/CODING_STANDARD.md:221-222`) means renames break callers, but the rule is explicit and documented.
- **Declarative loader uses `AgentException`**: `DeclarativeLoaderError(AgentException)` (`python/packages/declarative/agent_framework_declarative/_loader.py:127`) — a YAML parsing failure is not really an "agent runtime" failure; using `AgentException` here is a debatable choice that makes the `AgentException` catch site in Claude / CopilotStudio / GitHub Copilot noisier than it should be.

## Failure Modes / Edge Cases

- **`inner_exception` loss**: Historical bug — fixed in PR #5167 (`python/CHANGELOG.md:251`). Test `test_exception_with_inner_exception` (`python/packages/core/tests/core/test_exceptions.py:8-13`) guards the contract.
- **`MiddlewareTermination` swallowed by `contextlib.suppress`**: Three call sites deliberately suppress it (`python/packages/core/agent_framework/_middleware.py:917, 1082`; `python/packages/core/agent_framework/_harness/_loop.py:547`); if a future refactor adds an unintended `except Exception:` around the suppression target, control flow breaks silently.
- **MCP "connection lost; task state unknown"**: A dropped connection before `task_id` is known raises `ToolExecutionException("connection lost; task state unknown")` — an explicit non-retry path to prevent double-execution of side-effecting tools (`python/packages/core/AGENTS.md:91-92`).
- **OpenAI content-filter detection**: `_handle_request_error` only treats `BadRequestError` with `code == "content_filter"` as a content filter; other content-filter paths in the OpenAI SDK may not be classified (`python/packages/openai/agent_framework_openai/_chat_client.py:598-604`).
- **`AddingItemMismatch` re-raised to swallow**: `_types.py:1911, 1963` `except (AdditionItemMismatch, ContentError):` — content-mismatch errors are silently swallowed in two places, which may hide bugs.
- **Declarative `AgentException` saturation**: Because `DeclarativeLoaderError` extends `AgentException`, callers who broadly `except AgentException:` in Claude / CopilotStudio / GitHub Copilot agent code will also catch declarative YAML errors that have nothing to do with those agent runtimes.
- **.NET no central contract**: External packages extending `DeclarativeWorkflowException` (which is `public class ... : Exception`, not sealed — `dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Exceptions/DeclarativeWorkflowException.cs:10`) have no documented hierarchy contract; cross-package error handling in .NET is ad-hoc.
- **`_handle_request_error` in OpenAI**: Called at four streaming/non-streaming sites (`python/packages/openai/agent_framework_openai/_chat_client.py:667, 709, 723, 746`); adding a new failure mode requires touching all four.

## Future Considerations

- **Operational-intent metadata**: Adding a `Retryable` bool (or `ErrorKind` enum) to the AF root would let callers decide retry / escalate / stop from the exception itself, not from prose. This is the biggest gap versus a fully observable taxonomy.
- **Central handler registry in Python**: The OpenAI `_handle_request_error` function (`python/packages/openai/agent_framework_openai/_chat_client.py:598-611`) could be lifted to `agent_framework.exceptions` as a `_dispatch_handler_registry` so each subclass can register a handler; new failure modes would not require editing four call sites.
- **Unify `MiddlewareTermination` location**: Move the class from `_middleware.py:72` to `exceptions.py` so the documented hierarchy (`python/CODING_STANDARD.md:268`) matches the implementation; or update the documentation to show the split.
