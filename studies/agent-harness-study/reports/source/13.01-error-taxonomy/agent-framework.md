## Summary

The Microsoft Agent Framework (MAF) maintains a **deliberately structured, source‑based exception hierarchy on the Python side** that is *not* mirrored on the .NET side. Python defines a single `AgentFrameworkException` base in `python/packages/core/agent_framework/exceptions.py:15` with seven L1 branches (`AgentException`, `ChatClientException`, `IntegrationException`, `ContentError`, `ToolException`, `MiddlewareException`, `WorkflowException`) plus a flat `SettingNotFoundError`. The branches are organized by *source subsystem*, not HTTP code. The `Agent*`/`ChatClient*`/`Integration*` trios share a parallel set of leaves (`InvalidAuth`, `InvalidRequest`, `InvalidResponse`, `ContentFilter`) so a caller can apply the same handling rule across domains (`python/CODING_STANDARD.md:213-217`). Taxonomy *is* used for dispatch in a few narrow but well‑documented sites: the OpenAI client's `_handle_request_error` (`python/packages/openai/agent_framework_openai/_chat_client.py:598-611`) classifies `BadRequestError` by `code == "content_filter"` and reroutes to `OpenAIContentFilterException`; the function‑calling loop in `python/packages/core/agent_framework/_tools.py:1554-1555, 1630-1631` re‑raises `UserInputRequiredException` so it bypasses the "Error: Function failed" generic fallback; the middleware pipeline at `python/packages/core/agent_framework/_middleware.py:72-79, 911-1082` uses `MiddlewareTermination` as a control‑flow exception, with `contextlib.suppress` distinguishing it from real failures; and `WorkflowInterrupted` (`python/packages/core/agent_framework/_workflows/_functional.py:87-93`) deliberately inherits from `BaseException` to defeat user `except Exception` handlers. The taxonomy is **documented in the coding standard** (`python/CODING_STANDARD.md:205-303`) and partially mirrored in a public design doc (`docs/features/vector-stores-and-embeddings/README.md:236-238`), but the .NET side has **no equivalent base class** — its custom exceptions (`PurviewException`, `DeclarativeWorkflowException`, `CodeValidationException`, `AgentNotRegisteredException`, `DockerNotAvailableException`, `ShellCommandRejectedException`, etc.) are *ad‑hoc* and rooted directly at `System.Exception` or `InvalidOperationException`. The Python design is intentional ("No compatibility aliases" — `python/CODING_STANDARD.md:221`) so adding a new error type is a non‑breaking change for callers that catch the L0/L1 base. **Caveats**: there is no central "retry vs. escalate vs. stop" policy mapping the exception types to operational outcomes, no OpenTelemetry/category tag on exceptions, and no equivalent documented hierarchy in the .NET tree, so behavior diverges between the two language SDKs.

## Rating

**7 / 10** — Clear, source‑scoped, parallel four‑leaf structure across the three principal domains (`Agent*`/`ChatClient*`/`Integration*`) on the Python side; used for routing at a few well‑isolated dispatch points; documented in the coding standard and in design docs; tests assert exception types and that consumers can extend the hierarchy (Purview subclasses, OpenAI subclasses, MCP private `_MCPTaskAbandoned`). Deductions: the taxonomy does *not* map to operational categories (retry/escalate/stop) so callers still write ad‑hoc handling; the .NET side has no equivalent structure, so the "framework" as a whole is inconsistent; the taxonomy is *not* observable (no span tag, no category attribute) so logs and traces have to parse `str(exc)` to recover the class; and the user‑facing distinction between "agent error" and "chat client error" is enforced by code review and the coding standard rather than by the type system. It is a strong taxonomy on Python, not a mature one across the whole multi‑language framework.

## Answers to Dimension Questions

1. **Are errors classified by source?** — Yes on the Python side, partially on the .NET side. Python uses a single L0 base (`AgentFrameworkException`) and L1 branches by *subsystem* (agent, chat client, integration, content, tool, middleware, workflow, settings) — not by HTTP code or generic "error vs. warning" category (`python/packages/core/agent_framework/exceptions.py:15-258`, `python/CODING_STANDARD.md:213-225`). .NET does not have a MAF‑level base; it has a Purview‑local hierarchy and a Declarative‑workflow‑local hierarchy plus ad‑hoc custom exceptions (e.g. `AgentNotRegisteredException`, `CodeValidationException`, `DockerNotAvailableException`, `ShellCommandRejectedException`) that each root at `System.Exception` (`dotnet/src/Microsoft.Agents.AI.Purview/Exceptions/PurviewException.cs:10`, `dotnet/src/Microsoft.Agents.AI.DurableTask/AgentNotRegisteredException.cs:8`).

2. **Is the taxonomy used for handling?** — Yes, in narrow but well‑isolated dispatch points on the Python side. Five concrete examples: (a) `OpenAIChatClient._handle_request_error` switches on the OpenAI error code and reroutes to `OpenAIContentFilterException` vs. `ChatClientException` (`python/packages/openai/agent_framework_openai/_chat_client.py:598-611`); (b) the function‑calling loop re‑raises `UserInputRequiredException` separately from generic exceptions so the parent agent gets HITL/oauth content instead of "Error: Function failed" (`python/packages/core/agent_framework/_tools.py:1554-1555, 1630-1631`); (c) the middleware pipeline distinguishes `MiddlewareTermination` from real failures via `contextlib.suppress` and result‑extraction (`python/packages/core/agent_framework/_middleware.py:917, 997, 1082`, `python/packages/core/agent_framework/_harness/_loop.py:547-548`); (d) the `foundry_hosting` Responses handler catches the L0 base and inspects it via `consent_url_from_error` to emit `OAuthConsentRequestOutputItem` instead of failing the request (`python/packages/foundry_hosting/agent_framework_foundry_hosting/_responses.py:497-514`); (e) `WorkflowInterrupted` deliberately escapes the L0 hierarchy by inheriting `BaseException` so user `except Exception` handlers cannot swallow it (`python/packages/core/agent_framework/_workflows/_functional.py:87-93`). **No evidence found** of a uniform "retry vs. escalate vs. stop" policy that maps each leaf to an action.

3. **Are error categories documented?** — Yes for the Python taxonomy. The coding standard has a 100‑line section with a full ASCII tree, a use‑table for AF vs. built‑in exceptions, and a decision guide for choosing between `Agent*`/`ChatClient*`/`Integration*` (`python/CODING_STANDARD.md:205-302`). The docstring convention requires `Raises:` blocks that name AF‑specific exceptions (`python/CODING_STANDARD.md:455-459`, `python/.github/skills/python-development/SKILL.md:64-66`). The vector‑stores design doc explicitly says new exceptions go under `IntegrationException` or a new branch (`docs/features/vector-stores-and-embeddings/README.md:236-238`). **No evidence found** of a comparable document for the .NET side.

4. **Can new error types be added without breaking existing handling?** — Yes, by design. The base `AgentFrameworkException` is the documented broad catch (`python/CODING_STANDARD.md:207-209`); the "No compatibility aliases" rule (line 221) means old names are not kept after renaming, so callers should target a base or the L0. Purview (`python/packages/purview/agent_framework_purview/_exceptions.py:15-31`) and OpenAI (`python/packages/openai/agent_framework_openai/_exceptions.py:55-90`) both add provider‑local leaves that re‑root at the appropriate L1 base, and tests assert the polymorphic relationship (`python/packages/purview/tests/purview/test_exceptions.py:23, 29, 35, 41, 47`). The MCP module's private `_MCPTaskAbandoned(ToolExecutionException)` shows the pattern can be extended even with sub‑L2 leaves without forcing a parallel public type (`python/packages/core/agent_framework/_mcp.py:244-251`).

## Architectural Decisions

- **L0 base, parallel L1 branches by subsystem, parallel L2 leaves where the same failure mode exists across subsystems.** Decision documented at `python/CODING_STANDARD.md:213-225`. The `InvalidAuth` / `InvalidRequest` / `InvalidResponse` / `ContentFilter` four‑leaf pattern is shared across `AgentException`, `ChatClientException`, and `IntegrationException` (lines 215-217).
- **Built‑in Python exceptions are used for validation, not AF types.** `ValueError` / `TypeError` for missing/invalid constructor args, `RuntimeError` for "object in wrong state" (`python/CODING_STANDARD.md:218-220`). This keeps the AF hierarchy focused on domain failures callers actually want to catch.
- **Domain choice is by subsystem, not by error mechanism.** `Agent*` for agent‑level logic, `ChatClient*` for the LLM provider connection, `Integration*` for non‑chat external services (`python/CODING_STANDARD.md:294-302`).
- **No compatibility aliases.** When an exception is renamed/removed, the old name is *not* kept as a back‑compat shim. Documented as a deliberate trade‑off for hierarchy clarity over backward compatibility (`python/CODING_STANDARD.md:221-222`).
- **Auto‑logging at construction.** `AgentFrameworkException.__init__` calls `logger.log(log_level, message, exc_info=inner_exception)`. Control‑flow exceptions opt out by passing `log_level=None` (`python/packages/core/agent_framework/exceptions.py:33-38`; `UserInputRequiredException` at `exceptions.py:197-208`; `MiddlewareTermination` at `_middleware.py:78`).
- **Subclass pattern is open and documented as the extension point.** Purview, OpenAI, Redis, MCP, and the declarative package all subclass L1 or L2 leaves to encode provider‑specific data (e.g. `OpenAIContentFilterException` carries `param`, `content_filter_code`, `content_filter_result` — `python/packages/openai/agent_framework_openai/_exceptions.py:55-90`).
- **One control‑flow exception intentionally escapes the L0 hierarchy.** `WorkflowInterrupted` inherits `BaseException` so user `except Exception` cannot swallow the HITL pause signal (`python/packages/core/agent_framework/_workflows/_functional.py:87-93`); this is a deliberate escape hatch, documented inline.
- **Public API surface is curated.** Only a subset of the hierarchy is exported from `agent_framework/__init__.py:332-340, 488, 557-569`. Provider‑specific leaves (e.g. `OpenAIContentFilterException`) are exposed via lazy `__getattr__` in provider `__init__.py` files (`python/packages/core/agent_framework/openai/__init__.py:29`).
- **.NET side is the inverse**: no MAF‑level base, two provider‑local mini‑hierarchies (Purview, Declarative), ad‑hoc custom exceptions everywhere else, and *workflow errors are delivered as events* (`dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowErrorEvent.cs:13-18`), not as a type parallel to Python's `WorkflowException`.

## Notable Patterns

- **Branch‑parallel four‑leaf pattern** across `Agent*` / `ChatClient*` / `Integration*` (`python/packages/core/agent_framework/exceptions.py:50-72, 85-106, 126-147`).
- **`ValidationTypeEnum` discriminator on `WorkflowValidationError`** — leaves carry a `validation_type` so consumers can `match` on the failure mode (e.g. `EDGE_DUPLICATION`, `TYPE_COMPATIBILITY`, `GRAPH_CONNECTIVITY`) without isinstance chains (`python/packages/core/agent_framework/_workflows/_validation.py:19-82`).
- **Provider subclass that adds structured data**: `OpenAIContentFilterException` carries `param: str | None`, `content_filter_code: ContentFilterCodes`, `content_filter_result: dict[str, ContentFilterResult]`, each populated from the upstream `BadRequestError.body.innererror` (`python/packages/openai/agent_framework_openai/_exceptions.py:55-90`). This is a useful template for adding telemetry‑rich leaves.
- **Control‑flow exception with a result payload**: `MiddlewareTermination(message, *, result: Any = None)` — pipelines can suppress it and recover the result (`python/packages/core/agent_framework/_middleware.py:72-79, 1611-1629`).
- **`contextlib.suppress(MiddlewareTermination)` at every pipeline boundary** so the same exception can be raised by any middleware without being logged as a real failure (`python/packages/core/agent_framework/_middleware.py:917, 997, 1082`).
- **`BaseException` escape hatch for HITL**: `WorkflowInterrupted` — a class‑level pattern signal that a new failure mode does not belong in the normal L0/L1 hierarchy (`python/packages/core/agent_framework/_workflows/_functional.py:87-93`).
- **Auto‑logging via `log_level` arg** on `AgentFrameworkException.__init__` (`python/packages/core/agent_framework/exceptions.py:25-38`) — control‑flow exceptions pass `log_level=None` to opt out.
- **Provider exception files co‑locate with the provider package** (`python/packages/openai/agent_framework_openai/_exceptions.py`, `python/packages/purview/agent_framework_purview/_exceptions.py`, `python/packages/declarative/agent_framework_declarative/_workflows/_errors.py`) — keeps the hierarchy extensible without touching `core`.
- **Tests assert polymorphic isinstance** for the Purview taxonomy (`python/packages/purview/tests/purview/test_exceptions.py:23, 29, 35, 41, 47`) — these are the contract that lets a caller `except IntegrationInvalidAuthException` and catch `PurviewAuthenticationError`.
- **.NET workflow errors as events, not types** — `WorkflowErrorEvent` / `ExecutorFailedEvent` / `SubworkflowErrorEvent` carry an `Exception?` payload, so the error *type* is whatever the executor raised (`dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowErrorEvent.cs:13-18`, `ExecutorFailedEvent.cs:12`, `SubworkflowErrorEvent.cs:12`). This is a *different* taxonomy discipline from the Python side and a useful contrast.

## Tradeoffs

- **No compatibility aliases** (`python/CODING_STANDARD.md:221-222`): renaming a leaf is a breaking change for any caller that imports the old name. This favors hierarchy clarity over backward compatibility, and is consistent with the framework's release model.
- **Validation errors use Python built‑ins** (`python/CODING_STANDARD.md:218-220`): callers that wrap every call in `try/except AgentFrameworkException` will *miss* `ValueError` / `TypeError` / `RuntimeError` raised during construction. The trade‑off is that "real bugs" surface as `ValueError` and only domain failures get the AF type, which matches Python convention.
- **L0 base is silent on operational category**: there is no `Retryable`/`Escalatable`/`Terminal` flag on the exception or any documented mapping. Callers must decide by leaf, which means the taxonomy *cannot* answer "retry or stop?" from the type alone — you need to read the leaf's contract. The dimension's leading question "Can you tell from the error type whether to retry, escalate, or stop?" is partially answered: yes for content filter (stop / change prompt) and for invalid auth (escalate / rotate credentials), but no for the long tail.
- **Curated `__all__` for the public API surface** (`python/packages/core/agent_framework/__init__.py:332-340`): the L0 and selected L1s are public, but most L1s and L2s must be imported from `agent_framework.exceptions` or the provider package. This is a small friction tax for callers that want a specific leaf.
- **.NET and Python diverge on the L0 question**: the Python tree has a single MAF base, the .NET tree has none. A user writing cross‑language code cannot rely on a uniform `except AgentFrameworkException` pattern.
- **Auto‑logging at construction is double‑edged**: helpful for observability, but it can create noise for control‑flow exceptions unless the caller remembers `log_level=None`. The framework's own `UserInputRequiredException` and `MiddlewareTermination` do this correctly, but it's a footgun for new leaves.
- **`WorkflowInterrupted` as `BaseException`**: clean separation, but *incompatible* with `except AgentFrameworkException` handling. If a workflow is wrapped in such a handler, the HITL pause will propagate uncaught. This is a *known* trade‑off, not a bug.

## Failure Modes / Edge Cases

- **Catch‑all masking**: A caller that writes `except Exception` inside a `@workflow` will not catch `MiddlewareTermination` (it suppresses) and *cannot* catch `WorkflowInterrupted` (it inherits `BaseException`). The test at `python/packages/core/tests/workflow/test_functional_workflow.py:997-1008` exists specifically to lock this behavior in.
- **MCP transient vs. abandonment confusion**: `_MCPTaskAbandoned` is private and the only way for a caller to distinguish "remote task may still be running" from "remote task failed" is to know that `ToolExecutionException` is the public form (`python/packages/core/agent_framework/_mcp.py:244-251, 1991-1997`). The docs make the contract clear but the name is private.
- **`OpenAIContentFilterException` shape depends on Azure's `innererror` payload** — if Azure changes the body shape, the dataclass may degrade to `RESPONSIBLE_AI_POLICY_VIOLATION` defaults without raising (`python/packages/openai/agent_framework_openai/_exceptions.py:81-90`). There is no schema validation against Azure's contract.
- **`UserInputRequiredException.contents` is untyped** (`python/packages/core/agent_framework/exceptions.py:198-209`): `list[Any]` — providers are trusted to attach well‑shaped `user_input_request` content. There is no schema enforced at the exception boundary.
- **`IntegrationInitializationError` is declared but not raised anywhere in the workspace** — declared at `python/packages/core/agent_framework/exceptions.py:120-123` with no other `IntegrationInitializationError` references in the package tree. Dead code, or a reserved name.
- **Foundry hosting re‑wraps consent errors but only the *URL* branch** — other `AgentFrameworkException` types re‑raise (`python/packages/foundry_hosting/agent_framework_foundry_hosting/_responses.py:499-514`). If a future change adds a non‑consent recoverable error type, the dispatch logic must be updated, but there is no plugin point.
- **.NET side: no cross‑provider catch‑all** — a caller wanting to catch all MAF errors must write `catch (Exception ex)` because there is no MAF base, which means *BCL* exceptions thrown by the framework are caught too. This blurs the contract that the Python side enforces.
- **`SettingNotFoundError` is a single L1 class with no leaves**, so distinguishing "endpoint not set" from "credential not set" requires message parsing, not type checking (`python/packages/core/agent_framework/exceptions.py:228-231`).
- **No telemetry/category tag** on the L0 base. Observability tools cannot group failures by class without parsing the Python class name, and .NET has no equivalent structure at all.

## Future Considerations

- **Add a `Retryable` / `Terminal` policy on the L0 base.** Even a `policy: Literal["retry", "escalate", "stop"] = "escalate"` field (defaulting to a per‑leaf value) would let callers ask the dimension's leading question directly. The infrastructure already exists: `__init__` accepts a `log_level` arg, so adding another kwarg is cheap.
- **Add an OTel/category attribute.** `AgentFrameworkException` could set a `category` attribute (e.g. `agent.invalid_request`, `chat_client.content_filter`) so logs/traces can group by class without parsing. This would close the observability gap noted in "Failure Modes".
- **Mirror the Python L0 base on the .NET side**, or formally document that .NET will use BCL exceptions + provider‑local bases (Purview, Declarative) and that the two languages are intentionally divergent. The current state is silent.
- **Promote `IntegrationInitializationError` from declared to actually raised** (`python/packages/core/agent_framework/exceptions.py:120-123`), or remove the dead declaration.
- **Split `SettingNotFoundError` into leaves** (`EndpointNotSet`, `CredentialNotSet`, `IndexNotSet`) so callers can handle the three failure modes by type instead of message parsing.
- **Add `IntegrationTimeoutException` and `ChatClientTimeoutException`** — the dimension's first sentence calls out timeout as a category. Today there is no L1 or L2 for timeouts; the framework relies on the underlying `asyncio.TimeoutError` / `requests`/`httpx` library to surface them, so callers cannot ask "is this a timeout?" from the type.
- **Formalize `_MCPTaskAbandoned` as a public leaf** (e.g. `ToolTaskAbandonedException`) so external callers can distinguish "tool failed" from "tool may still be running and needs cancellation".
- **Add a `RequestErrorCode` enum** to `IntegrationInvalidRequestException` (similar to `OpenAIContentFilterException.content_filter_code`) so the L1 leaf can carry a structured provider error code, not just a message.
- **Add a public `MiddlewareErrorCode` enum** on `MiddlewareException` so the L1 leaf can be used for telemetry without parsing messages.
- **Cross‑language documentation** of which leaves exist on which side, so a Python user migrating to .NET can find the equivalent. Today the `AGENTS.md` files do not enumerate this.
