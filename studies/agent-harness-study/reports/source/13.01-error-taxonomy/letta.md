## Summary

Letta maintains a **two-track error taxonomy organized by source**:

1. **A typed exception hierarchy rooted in `LettaError`** (`letta/errors.py:27-46`) that carries a `code: Optional[ErrorCode]` field plus a `details: Optional[Dict]` field. The `ErrorCode` enum (`letta/errors.py:11-24`) defines 11 wire-level codes (`NOT_FOUND`, `UNAUTHENTICATED`, `PERMISSION_DENIED`, `INVALID_ARGUMENT`, `INTERNAL_SERVER_ERROR`, `CONTEXT_WINDOW_EXCEEDED`, `RATE_LIMIT_EXCEEDED`, `TIMEOUT`, `CONFLICT`, `EXPIRED`, `PAYMENT_REQUIRED`). The Python class hierarchy is organized **by source subsystem**, not by HTTP code: a separate base class exists for LLM providers (`LLMError` at `letta/errors.py:259-260`), MCP servers (`LettaMCPError` at `letta/errors.py:208-209`), and message validation (`LettaMessageError` at `letta/errors.py:386-406`); tool creation (`LettaToolCreateError` at `letta/errors.py:126-132`), tool name conflicts (`LettaToolNameConflictError` at `letta/errors.py:135-143`), configuration (`LettaConfigurationError` at `letta/errors.py:155-160`), agent export (`AgentFileExportError` at `letta/errors.py:442-451`), and agent import (`AgentFileImportError` at `letta/errors.py:474-475`) each have their own class. A separate, smaller `letta/orm/errors.py:1-37` file holds DB-infrastructure errors (`NoResultFound`, `UniqueConstraintViolationError`, `ForeignKeyConstraintViolationError`, `DatabaseLockNotAvailableError`, `DatabaseTimeoutError`, `DatabaseDeadlockError`) that deliberately do not extend `LettaError` so that the SQLAlchemy layer stays framework-agnostic.

2. **An `LLMError` sub-hierarchy** (`letta/errors.py:259-314`) with provider-agnostic subclasses — `LLMConnectionError`, `LLMRateLimitError`, `LLMBadRequestError`, `LLMInsufficientCreditsError`, `LLMAuthenticationError`, `LLMPermissionDeniedError`, `LLMNotFoundError`, `LLMUnprocessableEntityError`, `LLMServerError`, `LLMEmptyResponseError` (subclass of `LLMServerError` for empty-response cases), `LLMTimeoutError`, `LLMProviderOverloaded` — that every provider client maps to via a per-provider `handle_llm_error(e, llm_config)` abstract method (`letta/llm_api/llm_client_base.py:368-397`). Local-LLM has its own parallel hierarchy (`LocalLLMError`, `LocalLLMConnectionError`, `LLMJSONParsingError` at `letta/errors.py:338-349, 331-335`), and Bedrock has two provider-only errors (`BedrockPermissionError`, `BedrockError` at `letta/errors.py:317-328`).

**Source classification drives dispatch in four well-defined places.**

- The FastAPI `app.py` registers ~30 exception handlers (`letta/server/rest_api/app.py:557-794`) keyed by exception type, each returning a typed HTTP status + JSON body. Examples: `LettaInvalidArgumentError → 400`, `LettaExpiredError → 410`, `LettaMCPTimeoutError → 408`, `LettaMCPConnectionError → 502`, `LLMTimeoutError → 504`, `LLMRateLimitError → 429`, `LLMInsufficientCreditsError → 402`, `LLMAuthenticationError → 401`, `LLMBadRequestError → 400`, `LLMError → 500`, `LLMProviderOverloaded → 503`, `ConcurrentUpdateError → 409`, `DatabaseLockNotAvailableError → 409` (with `Retry-After: 1`), `DatabaseDeadlockError → 409` (with `Retry-After: 1`), `DatabaseTimeoutError → 503`, `IncompatibleAgentType → 400` with extra `expected_type`/`actual_type` fields (`letta/server/rest_api/app.py:651-664`).
- The streaming adapters wrap every LLM exception through `self.llm_client.handle_llm_error(e, llm_config=...)` (`letta/adapters/letta_llm_stream_adapter.py:144-146, 170-172`; `letta/adapters/simple_llm_stream_adapter.py:165-170, 191-195`; `letta/adapters/simple_llm_request_adapter.py:59-61`).
- The agent loops branch on source: `ContextWindowExceededError` triggers summarization-and-retry up to `max_summarizer_retries` (`letta/agents/letta_agent_v2.py:563`; `letta/agents/letta_agent_v3.py:1218`); `(LLMRateLimitError, LLMServerError, LLMProviderOverloaded)` triggers the routing-client circuit breaker / fallback-handle swap (`letta/agents/letta_agent_v3.py:1183-1211`); `LLMError` maps to `StopReasonType.llm_api_error`; `SystemPromptTokenExceededError` (a `ContextWindowExceededError` subclass) maps to `StopReasonType.context_window_overflow_in_system_prompt` (`letta/agents/letta_agent_v3.py:656-662`); bare `Exception` maps to `StopReasonType.error` (`letta/agents/letta_agent_v3.py:662`).
- The summarizer retries with a fallback provider on `(LLMProviderOverloaded, LLMRateLimitError)` but not on other errors (`letta/services/summarizer/summarizer.py:760-775`).
- The Redis stream manager serializes non-`LettaError` exceptions into a `LettaErrorMessage` with a string `error_type` (`letta/server/rest_api/redis_stream_manager.py:296-298, 355-357, 382-384`); the SSE error event only carries three string categories — `stream_incomplete`, `stream_task_cancelled`, `internal_error` — losing the richer Python classification.

**The streaming-protocol `error_type` field is a parallel taxonomy on the wire.** `LettaErrorMessage` (`letta/schemas/letta_message.py:386-403`) defines `error_type: str`, `message: str`, `detail: Optional[str]`, `run_id: str`; the OpenAPI generator (`create_letta_error_message_schema()` at `letta/schemas/letta_message.py:515-539`) exposes it via `fern/openapi-overrides.yml:618` and `fern/openapi.json:40255, 40292`. The `StopReasonType` enum (`letta/schemas/letta_stop_reason.py:9-49`) is the *companion* taxonomy — it has 13 values (`end_turn`, `error`, `llm_api_error`, `invalid_llm_response`, `invalid_tool_call`, `max_steps`, `max_tokens_exceeded`, `no_tool_call`, `tool_rule`, `cancelled`, `insufficient_credits`, `requires_approval`, `context_window_overflow_in_system_prompt`) and the `.run_status` property (`letta/schemas/letta_stop_reason.py:24-49`) explicitly classifies each into `RunStatus.completed` / `failed` / `cancelled`. That mapping is the durable retry-vs-stop policy on the run record.

**Documentation is internal-docstring only.** No user-facing taxonomy doc was found; class hierarchy, retry behavior, and stop-reason classification are communicated via (a) per-class docstrings, (b) the `LettaStopReason.run_status` property, and (c) a dedicated error-handling regression test (`tests/adapters/test_letta_llm_stream_adapter_error_handling.py`).

**Errors are added without breaking existing handling** because the dispatch is `instanceof`-based against the *base* class and the `LLMError` base (`letta/server/rest_api/app.py:782-793`; `letta/adapters/letta_llm_stream_adapter.py:144-145`). New `LLMError` subclasses inherit HTTP 500 by default until a handler is registered, and new `LettaError` subclasses inherit the generic 500 handler (`letta/server/rest_api/app.py:435-473`) plus the Sentry capture path.

## Rating

**8 / 10** — Clear source-classified taxonomy, exhaustive per-provider mapping, dedicated dispatch sites, and a durable `StopReasonType` policy enum. The Python hierarchy is *the* answer to "model, provider, tool, validation, policy, context, user, infrastructure, timeout" — every source in the dimension checklist has at least one named class, and each is `isinstance`-dispatched at the FastAPI boundary.

Deductions:
- **Two-track inconsistency**: `letta/orm/errors.py` errors do NOT extend `LettaError` (`letta/orm/errors.py:1-37`) — they are caught and re-wrapped by handlers in `app.py:567-584`, 622-650, 666-675, but the seam is implicit. `MCPTimeoutError` (`letta/functions/mcp_client/exceptions.py:1-6`) does NOT extend `LettaMCPError` — it's a separate `RuntimeError`; the `LettaMCPTimeoutError` class at `letta/errors.py:232-237` exists but the MCP layer's own timeout is not bridged to it in the searched code.
- **The streaming-protocol `error_type` is a coarser second taxonomy** (`stream_incomplete`, `stream_task_cancelled`, `internal_error` at `letta/server/rest_api/redis_stream_manager.py:298, 357, 384`) that discards the rich Python classification when sending SSE to clients.
- **Several sites raise bare `ValueError`, `RuntimeError`, or `NotImplementedError`** (e.g. `letta/functions/composio_helpers.py:52-83`, `letta/functions/helpers.py:22,80`, `letta/functions/mcp_client/types.py:271`, `letta/sandbox/modal_executor.py:66-117`, `letta/agent.py:411, 413, 1061-1120`) which bypass the taxonomy and rely on the generic 400/500 handlers in `app.py:564, 435-473`.
- **No single documentation file** enumerates the taxonomy. The hierarchy, retry policy, and stop-reason mapping are scattered across `letta/errors.py`, `letta/schemas/letta_stop_reason.py`, the dispatch sites in `app.py`, and the agent loops.
- **`isRetryable` is implicit**, not a field — callers must know that `ContextWindowExceededError` is retryable via compaction while other `LLMError`s trigger fallback, and that `(LLMRateLimitError, LLMServerError, LLMProviderOverloaded)` are the only ones that engage the circuit breaker (`letta/agents/letta_agent_v3.py:1183-1211`).
- **The leading dimension question** "Can you tell from the error type whether to retry, escalate, or stop?" is answered yes for HTTP routing (yes via `app.py`), yes for agent-loop retry-vs-fallback (yes via `isinstance` branches in `letta_agent_v3.py`), and yes for run persistence (yes via `StopReasonType.run_status`); but on the SSE wire the answer is *no* — clients see only three string codes.

## Answers to Dimension Questions

1. **Are errors classified by source?** **Yes.** The Python hierarchy (`letta/errors.py:11-492`) is organized by source subsystem: LLM provider (`LLMError` subtree, `LocalLLMError` subtree, `BedrockError`), tool (`LettaToolCreateError`, `LettaToolNameConflictError`, `LettaToolNameSchemaMismatchError`), validation (`LettaInvalidArgumentError`, `LettaMessageError` subtree, `EmbeddingConfigRequiredError`), policy (`LettaConfigurationError`, `InsufficientCreditsError`), context (`ContextWindowExceededError` with `SystemPromptTokenExceededError` subclass), user (`LettaAgentNotFoundError`, `LettaUserNotFoundError`, `LettaUnsupportedFileUploadError`), infrastructure (`LettaServiceUnavailableError`, the `letta/orm/errors.py` DB classes), timeout (`LLMTimeoutError`, `LettaMCPTimeoutError`), concurrency (`ConversationBusyError`, `MemoryRepoBusyError`, `PendingApprovalError`, `ConcurrentUpdateError`, `NoActiveRunsToCancelError`), MCP (`LettaMCPError` subtree), message validation (`LettaMessageError` subtree), and JSON parsing (`LLMJSONParsingError`). Each carries an `ErrorCode` plus structured `details` for retry/observability context.

2. **Is the taxonomy used for handling?** **Yes — three places.** (a) FastAPI dispatch in `letta/server/rest_api/app.py:557-794` registers ~30 typed handlers keyed by exception class, each returning a typed HTTP status + JSON body. (b) Agent loops in `letta/agents/letta_agent_v2.py:556-573`, `letta/agents/letta_agent_v3.py:1175-1218`, and `letta/agents/letta_agent_v3.py:649-662` branch on `isinstance` to decide retry (compaction, fallback handle swap, stop_reason classification). (c) The summarizer's provider-fallback decision (`letta/services/summarizer/summarizer.py:760-775`) explicitly retries only on `(LLMProviderOverloaded, LLMRateLimitError)`.

3. **Are error categories documented?** **Partially.** No single taxonomy doc exists. Categories are documented via (a) per-class docstrings in `letta/errors.py`, (b) the OpenAPI `LettaErrorMessage` schema in `fern/openapi.json:40255, 40292`, (c) `StopReasonType` + `.run_status` property in `letta/schemas/letta_stop_reason.py:9-49`, (d) the regression test in `tests/adapters/test_letta_llm_stream_adapter_error_handling.py` which doubles as executable spec. The streaming-protocol `error_type` string has no source-aware enumeration — only three literal values (`stream_incomplete`, `stream_task_cancelled`, `internal_error`).

4. **Can new error types be added without breaking existing handling?** **Yes, but with caveats.** Adding a new `LLMError` subclass is safe: the catch-all `LLMError → 500` handler (`letta/server/rest_api/app.py:782-793`) returns 500 until a specific handler is registered, and `isinstance(e, LLMError)` branches in the adapters (`letta/adapters/letta_llm_stream_adapter.py:144-145`) short-circuit before generic handling. Adding a new `LettaError` subclass falls through to the generic `Exception → 500` handler (`letta/server/rest_api/app.py:435-473`) which also captures to Sentry. The caveat: bare `ValueError`, `RuntimeError`, `NotImplementedError` outside `letta/errors.py` will also be caught by the `ValueError → 400` and `Exception → 500` handlers, but they bypass the typed `details`/`code` payload contract — clients won't see the `ErrorCode` field.

## Architectural Decisions

- **Two-track taxonomy (Python class + `ErrorCode` enum)** at `letta/errors.py:11-46`. The Python class carries structural meaning (which subsystem, what context), the enum carries wire meaning (HTTP code). Both are required for full routing.
- **Provider-agnostic LLM taxonomy with per-provider mappers** at `letta/llm_api/llm_client_base.py:368-397` (`@abstractmethod handle_llm_error`) implemented by `openai_client.py`, `anthropic_client.py`, `chatgpt_oauth_client.py`, `google_vertex_client.py`, `google_ai_client.py`, `baseten_client.py`, `azure_client.py`, and the provider schemas in `letta/schemas/providers/`. All provider-specific exceptions normalize into the same ~12-class taxonomy.
- **Centralized heuristics** in `letta/llm_api/error_utils.py:8-41` so `ContextWindowExceededError` and `LLMInsufficientCreditsError` are detected the same way regardless of provider.
- **Companion `StopReasonType` enum** at `letta/schemas/letta_stop_reason.py:9-49` is the durable on-record classification that pairs with `RunStatus` (`letta/schemas/letta_stop_reason.py:24-49`). The Python exception taxonomy is *runtime*, the stop-reason taxonomy is *persisted*.
- **Two-tier exception files**: `letta/errors.py` (application taxonomy) and `letta/orm/errors.py` (DB infrastructure). The split keeps SQLAlchemy errors framework-agnostic and bridges them at the FastAPI boundary in `app.py`.
- **Background-task safety net** at `letta/server/global_exception_handler.py:14-108` for any exception that escapes the request context (sys.excepthook + threading.excepthook + asyncio exception handler).
- **SSE error contract is intentionally minimal** (`LettaErrorMessage` with `error_type: str` at `letta/schemas/letta_message.py:386-403`) — only three string values are emitted (`stream_incomplete`, `stream_task_cancelled`, `internal_error`), accepting loss of granularity on the wire in favor of a stable contract.

## Notable Patterns

- **`is_byok` field in `details`** at `letta/errors.py:40-41` — `__str__` appends `[BYOK]`; used by `LLMRateLimitError` and `LLMInsufficientCreditsError` handlers in `app.py:706-740` to swap the user-facing message.
- **Provider-trace logging on every error path** at `letta/adapters/letta_llm_stream_adapter.py:142, 166` and `letta/adapters/simple_llm_stream_adapter.py:166, 189` — `error_type=type(e).__name__`, `error_msg=str(e)`, plus `latency_ms` are passed to `log_provider_trace_async` for ClickHouse telemetry.
- **Polymorphic retry decision via `isinstance` chain** at `letta/agents/letta_agent_v3.py:1175-1218` — the order of `except` blocks encodes priority (rate-limit/overloaded before generic `LLMError` before generic `Exception`) which lets the routing-client fallback handle take precedence.
- **Retry-After headers on retryable infra errors** at `letta/server/rest_api/app.py:619-628` for `DatabaseLockNotAvailableError` and `DatabaseDeadlockError` — concrete `Retry-After: 1` header signals to clients.
- **`__letta_context__` attribute convention** at `letta/exceptions/logging.py:109-137` — structured context attached to an exception is picked up by the global handler.
- **`StopReasonType` is the durable answer to "retry vs. stop"** at `letta/schemas/letta_stop_reason.py:24-49` — it has a `run_status` property that classifies into `RunStatus.completed`/`failed`/`cancelled`.

## Tradeoffs

- **Two parallel taxonomies (`ErrorCode` for HTTP, `StopReasonType` for run lifecycle) increase API surface** but each is independently versioned — clients can ignore one if they don't care about run persistence.
- **Python exception richness is lost on the SSE wire** (`letta/server/rest_api/redis_stream_manager.py:296-298`) — only three string codes cross the boundary, so an SSE consumer cannot distinguish `ContextWindowExceededError` from `LLMRateLimitError`. Clients that need granularity must use the run-record `StopReasonType` instead.
- **Catch-all `LLMError → 500` handler** at `letta/server/rest_api/app.py:782-793` is the safety net for unhandled LLM subclasses but means a missing per-class handler produces a generic 500 instead of the correct HTTP code.
- **`ValueError → 400`** at `letta/server/rest_api/app.py:564` is broad — any tool-side `raise ValueError` (e.g., `letta/functions/ast_parsers.py:21-86`, `letta/sandbox/modal_executor.py:66-117`) surfaces as 400 even if the underlying cause is provider-side. This is pragmatic but mixes "user input is wrong" with "we couldn't parse user input".
- **Per-provider mapping code is duplicated** across `openai_client.py`, `anthropic_client.py`, `chatgpt_oauth_client.py`, `google_vertex_client.py`, `baseten_client.py`, `azure_client.py`, and `letta/schemas/providers/*.py`. New providers must re-implement the full mapping; the shared heuristics (`error_utils.py`) only cover context overflow and insufficient credits.

## Failure Modes / Edge Cases

- **Streaming `httpx.ReadError`/`WriteError`/`ConnectError` mid-stream** — caught in `letta/llm_api/chatgpt_oauth_client.py:102` and re-mapped to `LLMConnectionError` only after `MAX_RETRIES=3`; mid-stream disconnects during a long generation can still leave the SSE stream incomplete (`stream_incomplete` emitted at `letta/server/rest_api/redis_stream_manager.py:296`).
- **`LLMEmptyResponseError` (a `LLMServerError` subclass)** — the streaming interface raises it on empty content (`letta/interfaces/anthropic_streaming_interface.py:600-604`), preserving the `LLMServerError` retry semantics. Without it, an empty Anthropic response would be misclassified as `end_turn`.
- **`OpenAI Streaming `ResponseErrorEvent`** — mapped to bare `LLMError` at `letta/interfaces/openai_streaming_interface.py:1527-1536`, losing the provider-specific classification that the request path produces. The `LLMError → 500` fallback handler is the only response.
- **MCP `MCPTimeoutError` vs `LettaMCPTimeoutError`** — `letta/functions/mcp_client/exceptions.py:1-6` defines `MCPTimeoutError(RuntimeError)` separately from `letta/errors.py:232-237` `LettaMCPTimeoutError(LettaMCPError)`. The seam is not bridged in the searched code; the MCP layer's own timeout may not produce the typed `ErrorCode.TIMEOUT` payload.
- **DB deadlock during request** — handled via `DatabaseDeadlockError` → 409 + `Retry-After: 1` at `letta/server/rest_api/app.py:622-629`; `DBAPIError` with `asyncpg.DeadlockDetectedError` orig is also caught and re-routed (`letta/server/rest_api/app.py:631-641`).
- **BYOK rate-limit vs. managed rate-limit** — `LLMRateLimitError.details["is_byok"]` switches the message (`letta/server/rest_api/app.py:706-723`) so the user knows whether their own key is exhausted.
- **`agent.py` (legacy V1 agent) raises bare `RuntimeError("Finish reason was length ...")`** at `letta/agent.py:411` and `Exception("Retries exhausted ...")` at `letta/agent.py:420, 442` — not in the taxonomy; falls through to the generic 500 handler.

## Future Considerations

- **Bridge `MCPTimeoutError` → `LettaMCPTimeoutError`** so MCP-side timeouts surface with `ErrorCode.TIMEOUT` and the 408 handler in `app.py`.
- **Make `isRetryable` an explicit field** on `LLMError` subclasses so the agent-loop retry branches (`letta/agents/letta_agent_v3.py:1183-1211`) and the summarizer fallback (`letta/services/summarizer/summarizer.py:763-766`) can iterate over a single attribute instead of `isinstance` chains.
- **Promote SSE `error_type` from string to enum** (e.g., `SSEErrorType.stream_incomplete | stream_task_cancelled | internal_error | context_window_exceeded | rate_limited | insufficient_credits | llm_timeout | mcp_timeout | ...`) so SSE clients can switch on the type without parsing prose.
- **Centralize provider mapping** — the `handle_llm_error` implementations across 6+ files duplicate boilerplate (BYOK detection, `__cause__` capture, structured `details`). A single base mapping function or table-driven approach would shrink the per-provider code.
- **Replace bare `RuntimeError`/`ValueError` raises** in `letta/functions/composio_helpers.py`, `letta/functions/helpers.py`, `letta/sandbox/modal_executor.py`, `letta/agent.py` with `LettaError` subclasses so the typed-error contract is preserved end-to-end.
- **Promote `StopReasonType` to the SSE wire** as the canonical stop reason and deprecate the `LettaErrorMessage.error_type` string field, so SSE consumers see the same taxonomy as the run record.
