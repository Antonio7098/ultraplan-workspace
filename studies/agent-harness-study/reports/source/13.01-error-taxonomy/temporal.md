## Summary

Temporal Server's error taxonomy is split across two layers and classifies errors by **functional cause + gRPC code**, not by a uniform "source" tag (model / provider / tool / validation / policy / context / user / infrastructure / timeout).

- **RPC wire layer.** The general-purpose service errors (`Canceled`, `NotFound`, `Unavailable`, `Internal`, `ResourceExhausted`, `DeadlineExceeded`, `InvalidArgument`, `FailedPrecondition`, etc.) come from the shared `go.temporal.io/api/serviceerror` package, with their gRPC code fixed by that contract.
- **Server-specific service errors.** Ten Go types live in `common/serviceerror/`, each backed by a proto detail message declared in `proto/internal/temporal/server/api/errordetails/v1/message.proto:1-61` and generated into `api/errordetails/v1/message.pb.go:29-513`. The ten types are: `CurrentBranchChanged`, `TaskAlreadyStarted`, `ShardOwnershipLost`, `RetryReplication`, `SyncState`, `StickyWorkerUnavailable`, `ObsoleteDispatchBuildId`, `ObsoleteMatchingTask`, `ActivityStartDuringTransition`, `StalePartitionCounts`.
- **Workflow-history layer.** A separate `common/failure/failure.go:1-91` constructs proto `Failure` objects with oneof `FailureInfo` variants — `ServerFailureInfo`, `ResetWorkflowFailureInfo`, `TimeoutFailureInfo` (plus the externally generated `ApplicationFailureInfo`, `ActivityFailureInfo`, `ChildWorkflowExecutionFailureInfo`, `NexusFailureInfo`).
- **Dispatch.** A single `FromStatus` switch in `common/serviceerror/convert.go:11-57` rehydrates errors from gRPC wire form using (gRPC code, detail proto type). Predicates `IsServiceClientTransientError` (`common/util.go:311-327`), `IsServiceHandlerRetryableError` (`common/util.go:329-347`), `IsContextDeadlineExceededErr` / `IsContextCanceledErr` (`common/util.go:298-309`), `IsStickyWorkerUnavailable` (`common/util.go:353-359`), `IsResourceExhausted` (`common/util.go:361-368`), `IsInternalError` / `IsNotFoundError` (`common/util.go:370-380`) form the routing vocabulary.
- **Documentation.** Only `docs/architecture/retry.md:1-55` discusses the model (and only briefly). There is no central taxonomy doc; each error type carries a Go doc comment but nothing in `docs/` enumerates them or their classification by source.

## Rating

**7 / 10** — Clear, durable taxonomy with explicit per-error Go structs (`common/serviceerror/*.go`), proto-backed details (`proto/internal/temporal/server/api/errordetails/v1/message.proto:12-61`), a single rehydration switch (`common/serviceerror/convert.go:11-57`), round-trip tests (`common/serviceerror/convert_test.go:11-26`, `common/failure/failure_test.go:10-87`), and live routing usage (redirect via `client/history/redirector.go:79-85` and `client/history/caching_redirector.go:118,200`, partition retry via `client/matching/partition_counts.go:133-136`, masking/header propagation via `common/rpc/interceptor/frontend_service_error.go:40-58`, healthy-error check via `common/rpc/interceptor/health_check.go:208-225`, dc redirection via `common/rpc/interceptor/dc_redirection_policy.go:177-183`). Deductions: classification is by **function + gRPC code**, not by an explicit source category (no `ErrorSource` tag distinguishing model/provider/tool/policy/context/user/infrastructure/timeout); the `FromStatus` switch (`common/serviceerror/convert.go:18-54`) is a hand-maintained dispatch table that silently falls through to the generic `serviceerror.FromStatus` for any error not in the table, which is a fragile extensibility surface; server-specific retry policy lives in `common/util.go:311-347` as a type switch over the same fixed set (forgetting to update it when adding an error will silently miss transient classification); documentation is one paragraph (`docs/architecture/retry.md:14-33`); there is no error-type registry or single source of truth enumerating the taxonomy; and most error types have no dedicated unit test beyond `ShardOwnershipLost` round-trip (`common/serviceerror/convert_test.go:11-26`).

## Answers to Dimension Questions

1. **Are errors classified by source?** Partially. There is no single "source category" enum (model/provider/tool/validation/policy/context/user/infrastructure/timeout). Errors are classified by **functional cause + gRPC code + presence of a typed detail proto**. The functional clustering is observable — e.g., persistence/replication errors are `codes.Aborted` with detail (`ShardOwnershipLost`, `RetryReplication`, `SyncState`, `StalePartitionCounts`); routing/unavailability is `codes.Unavailable` (`StickyWorkerUnavailable`, masked `ShardOwnershipLost`); validation is `codes.InvalidArgument` + `codes.AlreadyExists` + `codes.FailedPrecondition` (`CurrentBranchChanged`, `TaskAlreadyStarted`, `ObsoleteMatchingTask`, `ActivityStartDuringTransition`, `ObsoleteDispatchBuildId`); workflow-history layer has its own source-tag (`failureSourceServer = "Server"` in `common/failure/failure.go:11`).
2. **Is the taxonomy used for handling?** Yes — extensively. Routing predicates are listed in `common/util.go:298-380`; redirector/partition-count/frontend/health/dc-redirection all branch on typed errors (see Evidence Collected). Both server (`RetryableInterceptor`) and client (`RetryableClient`) retry paths consume a single classifier (`common.IsServiceClientTransientError`) wired through DI (`common/resource/fx.go:286-302`).
3. **Are error categories documented?** Lightly. `docs/architecture/retry.md:14-33` documents the contract (api-go vs. server-specific split, retry wiring) and references the retry classifier. There is no central taxonomy document enumerating categories; the only per-type documentation is Go doc comments at the top of each file in `common/serviceerror/`.
4. **Can new error types be added without breaking existing handling?** Yes for read paths (any error matching no detail type falls back to `serviceerror.FromStatus`), but routing/retry is fragile: a new error requires (a) a proto detail message in `proto/internal/temporal/server/api/errordetails/v1/message.proto`, (b) regeneration via `make proto`, (c) a Go struct in `common/serviceerror/`, (d) a `newXxx` case in `common/serviceerror/convert.go:18-54`, and (e) potentially an entry in `common.IsServiceClientTransientError` (`common/util.go:311-327`) and/or `IsServiceHandlerRetryableError` (`common/util.go:329-347`). Forgetting any of (d)/(e) does not break compilation but silently misclassifies the error as non-retryable / non-routable.

## Architectural Decisions

- **Two-layer taxonomy.** RPC errors (`common/serviceerror/`) are separated from workflow-history failures (`common/failure/`). The former carry control signals over gRPC; the latter are persisted into event histories and surfaced to user workflows.
- **Proto-backed details.** Each server-specific error has a typed proto detail (`proto/internal/temporal/server/api/errordetails/v1/message.proto:12-61`). The dispatcher in `common/serviceerror/convert.go:18-54` keys on (gRPC code, detail proto type) to rehydrate the typed Go error on the receiving side. This makes the wire contract explicit and lets handlers carry structured payloads (branch tokens, owner host, partition counts).
- **gRPC codes are part of the taxonomy.** Each error type pins a specific gRPC code (`codes.Aborted` for persistence failures, `codes.FailedPrecondition` for obsolete tasks, `codes.Unavailable` for sticky-worker / shard-lost, etc.), so retry policies can be authored as gRPC-code-aware classifiers.
- **Source-tag on workflow failures.** `failureSourceServer = "Server"` (`common/failure/failure.go:11`) is the only literal "source" tag in the system — used to distinguish server-emitted failures from SDK/user-emitted ones in workflow history.
- **Hand-maintained switch over auto-registration.** The rehydration switch (`common/serviceerror/convert.go:18-54`) is intentionally a hand-written table; the codebase relies on convention plus code review rather than reflection or registration. This keeps the wire contract auditable but trades extensibility.
- **Retry predicate as a single function.** `common.IsServiceClientTransientError` (`common/util.go:311-327`) is the central classifier for client retries and is injected via `common/resource/fx.go:286-302`. The same pattern exists on the server side via `IsServiceHandlerRetryableError` (`common/util.go:329-347`) consumed by `RetryableInterceptor` (`common/rpc/interceptor/retry.go`).
- **Deprecated error types are kept but marked.** `ObsoleteDispatchBuildId` is annotated `Deprecated. [cleanup-old-wv]` (`common/serviceerror/obsolete_dispatch_build_id.go:15, 22`) and `ObsoleteDispatchBuildIdFailure` carries the same marker (`proto/internal/temporal/server/api/errordetails/v1/message.proto:48`). This signals intent to retire the type but keeps wire-compat alive.

## Notable Patterns

- **Error struct + ctor + `Error()` + `Status()` + private rehydrate** — uniform across every file in `common/serviceerror/` (`shard_ownership_lost.go:11-57`, `sync_state.go:12-96`, `stale_partition_counts.go:9-44`, etc.). Adding a new type means mirroring this shape verbatim.
- **`Equal` helpers on data-heavy errors.** `RetryReplication.Equal` (`common/serviceerror/retry_replication.go:72-80`) and `SyncState.Equal` (`common/serviceerror/sync_state.go:73-80`) provide deep field equality for idempotency checks. Most other types do not.
- **Detail-type tagging + typed switch.** The dispatcher in `common/serviceerror/convert.go:18-54` uses `switch errDetails.(type)` over proto pointer types, then constructs the Go error from fields. Round-trip preserved by `common/serviceerror/convert_test.go:11-26`.
- **Header propagation for `ResourceExhausted`.** `common/rpc/interceptor/frontend_service_error.go:45-55` attaches `X-Resource-Exhausted-Cause` and `X-Resource-Exhausted-Scope` headers — making the cause/scope visible to clients that read headers, since the gRPC code alone (`ResourceExhausted`) is too coarse.
- **Error masking with hash.** `MaskInternalErrorDetailsInterceptor` (`common/rpc/interceptor/mask_internal_error.go:67-112`) replaces `Unknown`/`Internal` with a hashed neutral message so internal failures do not leak details to clients, while still logging the original. `common.ErrorHash` (`common/util.go:382-387`) is the hash function.
- **DPanic for invariants.** `NewInternalErrorWithDPanic` (`common/serviceerror/service_error_with_dpanic.go:8-12`) logs a development-mode panic on top of returning an `Internal` error, used where a programmer invariant is violated.

## Tradeoffs

- **Hand-written switch vs. registry.** The hand-written switch in `common/serviceerror/convert.go:18-54` is auditable and explicit but creates a maintenance burden — each new error type must be added in two places (`convert.go` and either `IsServiceClientTransientError` or `IsServiceHandlerRetryableError`). The codebase offsets this with tests for the most consequential types (`ShardOwnershipLost` round-trip at `convert_test.go:11-26`; redirector tests at `client/history/redirector_test.go:123-160` and `client/history/caching_redirector_test.go:226-286`; partition-count retry at `client/matching/partition_counts_test.go:118,143`).
- **gRPC-code-as-classifier vs. source-tag.** Classifying by gRPC code (cheap, ubiquitous, transport-aware) is robust across processes but discards the dimension's requested source tag (model/provider/tool/policy/context/user/infrastructure/timeout). To recover source, callers must inspect the Go type — there is no metadata field.
- **Server-side vs. client-side retry policy reuse.** Both `RetryableInterceptor` (`common/rpc/interceptor/retry.go:19-44`) and `RetryableClient` (`client/.../retryable_client.go`) call `backoff.ThrottleRetryContext` with an injected `IsRetryable`. Two retry paths multiply per RPC; the architecture notes this in `docs/architecture/retry.md:52-55`.
- **Fallback to shared api-go package.** The codebase depends on `go.temporal.io/api/serviceerror` (e.g., `common/serviceerror/convert.go:4`, `common/rpc/interceptor/frontend_service_error.go:6`) and only adds server-specific extensions. This is cheaper than re-implementing general types but couples versioning to the api-go release cadence.
- **No central enum/discriminator.** Each error type carries its own fields and no uniform "kind" tag exists. A log-search or trace has to enumerate the 10 types or fall back to gRPC code, which is acceptable but increases the surface area for forgotten classifications.

## Failure Modes / Edge Cases

- **Silent misclassification on forgotten updates.** Adding a new error without updating `common/util.go:311-347` or `common/serviceerror/convert.go:18-54` compiles cleanly and routes via the fallback (`convert.go:56`), but the error becomes non-retryable / non-routable in production until someone notices.
- **Masking strips context.** `MaskInternalErrorDetailsInterceptor` (`common/rpc/interceptor/mask_internal_error.go:67-112`) replaces `Unknown`/`Internal` with a hashed neutral message. If a server-specific error escapes as `Unknown` or `Internal` (e.g., through a path that does not set its proper code), clients lose the detail and cannot distinguish "transient" from "permanent".
- **`ShardOwnershipLost` masking at frontend.** `common/rpc/interceptor/frontend_service_error.go:41-42` rewrites `ShardOwnershipLost` to a plain `Unavailable` before returning from frontend, so external clients cannot recover `OwnerHost` and self-redirect — they must rely on the server's internal redirector.
- **Partition-count trailer parsing.** `parsePartitionCountsFromTrailer` (`client/matching/partition_counts.go:83-89`) silently sets `newPc` to zero on parse error and logs `Info` — a retry-on-stale invariant depends on the trailer being well-formed; a corrupt trailer would not raise.
- **`StalePartitionCounts` retry is bounded to one attempt.** `client/matching/partition_counts.go:133-136` only retries when `attempt == 0`; if the second response is also stale (or stale only on attempt 1+), the error propagates.
- **Workflow-failure truncation drops detail.** `Truncate`/`TruncateWithDepth` (`common/failure/failure.go:48-91`) keeps only `ApplicationFailureInfo` and `ServerFailureInfo` (for `NonRetryable`). Other failure-info variants are dropped, so timeout / activity / child-workflow failures lose structured detail when truncated for storage.
- **Deprecated types still routable.** `ObsoleteDispatchBuildId` and the matching failure detail (`proto/internal/temporal/server/api/errordetails/v1/message.proto:48`) are marked deprecated but still routed in `common/serviceerror/convert.go:47-49` and re-emitted in `common/serviceerror/obsolete_dispatch_build_id.go:23-27`. The `[cleanup-old-wv]` annotation is the only signal.
- **No panic-safety on `serviceerror.NewInternalf` paths.** Errors that bubble up via `serviceerror.NewInternal(...)` (`common/util.go:452, 738`) carry no context — the message is the only thing. Combined with masking (`mask_internal_error.go`), debugging depends on the pre-mask log line.

## Future Considerations

- **Introduce an `ErrorKind` discriminator.** A single enum on a common interface (e.g., `Kind() ErrorKind` returning `KindPersistence`, `KindValidation`, `KindRouting`, `KindTimeout`, `KindInfrastructure`, `KindUser`, `KindPolicy`) would unify logging, retry, and tracing without breaking the existing gRPC-code/type-dispatch path.
- **Centralize the registry.** Move the `(gRPC code, detail type) → ctor` map from the hand-written switch in `common/serviceerror/convert.go:18-54` to a registry initialized in `init()` blocks per file. Would make "forgot to add to registry" a compile error rather than a silent misroute.
- **Expand round-trip tests.** `common/serviceerror/convert_test.go:11-26` covers only `ShardOwnershipLost`. Adding round-trip tests for each of the 10 types plus tests asserting they reach `IsServiceClientTransientError` / `IsServiceHandlerRetryableError` would catch silent fallthroughs.
- **Extend documentation in `docs/architecture/`.** A dedicated `error-taxonomy.md` enumerating the 10 server-specific errors, the proto detail message backing each, and the routing points where each is consumed would replace the implicit "read the code" knowledge.
- **Mark `Obsolete*` errors more aggressively.** The `Deprecated. [cleanup-old-wv]` comment (`obsolete_dispatch_build_id.go:15`, `proto/.../errordetails/v1/message.proto:48`) is the only signal. Adding a lint rule or a registry entry that warns when these types are constructed would make the cleanup deadline actionable.
- **Surface partition-count trailer parse errors.** `client/matching/partition_counts.go:124-126` logs `parseErr` at `Info`. If the trailer is the only mechanism for refreshing stale counts, a parse error should bump a metric so an operator can see when clients silently lose retry capability.

## Questions / Gaps

- **Source isolation check.** No evidence was found for a single taxonomy document or a central "error kind" enum that maps onto the dimension's source categories (model/provider/tool/validation/policy/context/user/infrastructure/timeout). The classification lives implicitly in the gRPC code + detail-type matrix in `common/serviceerror/convert.go:18-54` and the predicates in `common/util.go:298-380`.
- **Are server-specific `*serviceerrors` types exported anywhere user-facing?** Search was restricted to the selected source; the public surface for end users is in `go.temporal.io/api/serviceerror` (shared package), which is imported but not vendored in `sources/temporal/`. Direct answers about user-facing contract rely on the api-go module rather than this repository's code.
- **Coverage of failure variants.** `common/failure/failure.go:14-46` only constructs three of the proto oneof variants (`ServerFailureInfo`, `ResetWorkflowFailureInfo`, `TimeoutFailureInfo`). Whether `ApplicationFailureInfo`, `ActivityFailureInfo`, `ChildWorkflowExecutionFailureInfo`, `NexusFailureInfo` are produced elsewhere was not exhaustively confirmed within source isolation rules.
- **Test coverage of dispatch fallthrough.** No test asserts that an unknown gRPC error passes through `common/serviceerror/convert.go:56` (`return serviceerror.FromStatus(st)`) — only that `ShardOwnershipLost` round-trips (`common/serviceerror/convert_test.go:11-26`).
- **Telemetry classification.** `common/rpc/interceptor/telemetry_test.go:414` injects a `ShardOwnershipLost` error for testing, but the production telemetry interceptor's treatment of error types (beyond masking) was not fully traced.
