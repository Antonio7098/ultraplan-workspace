## Summary

LangGraph's error model is **structurally explicit but source-scoped rather than uniformly classified**. The single source of truth for framework error types is `libs/langgraph/langgraph/errors.py:1-241`, which defines 11 named error classes plus an `ErrorCode` enum (`libs/langgraph/langgraph/errors.py:34-40`) used to brand channel-update and recursion-limit failures with documentation URLs. The hierarchy is partitioned by *runtime role*, not by domain (model/provider/tool/etc.): a `GraphBubbleUp` superclass (`libs/langgraph/langgraph/errors.py:50-51`) collects "control" exceptions that must propagate rather than be treated as fatal (`GraphInterrupt`, `GraphDrained`, `ParentCommand`); three "node-attributable" types (`NodeCancelledError`, `NodeTimeoutError`, plus the `NodeError` dataclass that wraps a node + exception for error handlers) cover lifecycle-level failures; and four "validation/infrastructure" types (`InvalidUpdateError`, `EmptyInputError`, `EmptyChannelError`, `TaskNotFound`) cover invalid inputs and runtime absence. The taxonomy *is* used for dispatch: `PregelRunner._panic_or_proceed` (`libs/langgraph/langgraph/pregel/_runner.py:650-697`) inspects exception type via `isinstance(exc, GraphInterrupt)` to decide whether to collect interrupts vs. panic; `BackgroundExecutor.done`/`AsyncBackgroundExecutor.done` (`libs/langgraph/langgraph/pregel/_executor.py:77-88`, `libs/langgraph/langgraph/pregel/_executor.py:171-181`) recognize `GraphBubbleUp` and drop those futures from the re-raise set on exit; `run_with_retry`/`arun_with_retry` (`libs/langgraph/langgraph/pregel/_retry.py:632-634, 773-776`) re-raise `GraphBubbleUp` immediately and convert user-raised `asyncio.CancelledError` into `NodeCancelledError` so it surfaces as a normal node failure (`libs/langgraph/langgraph/pregel/_retry.py:635-640, 777-794`); and `commit` (`libs/langgraph/langgraph/pregel/_runner.py:574-613`) branches on `GraphInterrupt` vs. `GraphBubbleUp` vs. "everything else" to decide whether to persist `(INTERRUPT, ...)` writes, error-source markers, or nothing. New error categories can be added **without breaking handling** because dispatch keys on inheritance from `GraphBubbleUp` (control-flow) or absence-of-inheritance (fatal) — a new fatal subclass automatically follows the panic path, a new control-flow subclass only needs to be added to the `GraphBubbleUp` family. Documentation exists only as docstring-level troubleshooting URLs (`libs/langgraph/langgraph/errors.py:73-76, 93-97, 3018-3026`) and `docs/redirects.json:259-262` pointers to docs.langchain.com pages; there is no single in-repo taxonomy reference document. Three notable gaps: there is no model/provider/tool/validation/policy/context/user/infrastructure/timeout classification — `NodeTimeoutError` is the only "infrastructure"-flavored class and it lives next to lifecycle classes without an explicit category tag; the retry layer's `default_retry_on` (`libs/langgraph/langgraph/_internal/_retry.py:1-29`) classifies third-party exceptions (httpx, requests) by HTTP status but uses an allowlist/denylist rather than a taxonomy; and `RemoteException` (`libs/langgraph/langgraph/pregel/remote.py:112-115`) is a flat wrapper without subclasses, so remote errors are not source-discriminated at the receiving boundary.

## Rating

**6 / 10** — A named, single-file error hierarchy (`libs/langgraph/langgraph/errors.py:34-241`) with explicit `ErrorCode` branding (`libs/langgraph/langgraph/errors.py:34-40`) and a real dispatch protocol: `GraphBubbleUp` controls control-flow vs. fatal routing at every level (`libs/langgraph/langgraph/pregel/_executor.py:81-86, 171-181`, `libs/langgraph/langgraph/pregel/_runner.py:585-602`, `libs/langgraph/langgraph/pregel/_retry.py:632-640, 773-794`); `NodeError` (a dataclass, not an exception) carries `(node, error)` to per-node handlers (`libs/langgraph/langgraph/errors.py:148-165`, `libs/langgraph/langgraph/pregel/_algo.py:1110-1248`); tests cover default-retry classification (`libs/langgraph/tests/test_retry.py:172-247`) and handler-resume-on-crash (`libs/langgraph/tests/test_retry.py:2691-2746`). Deductions: classification is **role-based (control vs. node vs. validation)** rather than **source-based (model/provider/tool/validation/policy/context/user/infrastructure/timeout)** as the dimension asks — no class names a model, provider, tool, policy, or context failure; `NodeTimeoutError` is the only timeout class and `NodeCancelledError` is the only cancellation class, so timeout/cancel coverage is sparse; remote errors are flat (`libs/langgraph/langgraph/pregel/remote.py:112-115`); documentation is only docstrings + URL fragments, no in-repo taxonomy reference; and the system has no "category" attribute on exceptions so log/tracing systems must inspect `type(exc).__name__` (`libs/langgraph/langgraph/pregel/_retry.py:387-388`). It is a real taxonomy — not vibes — but it is engineered around control-flow vs. fatal-vs.-handler-routing, not around the model/provider/tool/source categories the dimension targets.

## Answers to Dimension Questions

1. **Are errors classified by source?** — **Partially.** LangGraph classifies errors by *runtime role*, not by *source* (model/provider/tool/validation/policy/context/user/infrastructure/timeout). The role axis splits into control-flow (`GraphBubbleUp` family — `GraphInterrupt`, `GraphDrained`, `ParentCommand`, `NodeInterrupt`), node-attributable lifecycle (`NodeError` (dataclass), `NodeCancelledError`, `NodeTimeoutError`), validation/infrastructure (`InvalidUpdateError`, `EmptyInputError`, `EmptyChannelError`, `TaskNotFound`), and resource exhaustion (`GraphRecursionError`). There is **no class that names "model failure" or "provider failure" or "tool failure" or "policy failure" or "context failure"** — model/provider failures surface as their underlying third-party exceptions (`httpx.HTTPStatusError`, `openai.APIError`, etc.) and are classified only by `default_retry_on`'s (`libs/langgraph/langgraph/_internal/_retry.py:1-29`) allowlist/denylist of common exception types. Tool failures get their own taxonomy only in the prebuilt library (`ToolInvocationError` at `libs/prebuilt/langgraph/prebuilt/tool_node.py:339`) which is not registered in `errors.py`.

2. **Is the taxonomy used for handling?** — **Yes, consistently.** Dispatch happens in five places: (a) `BackgroundExecutor.done` / `AsyncBackgroundExecutor.done` recognise `GraphBubbleUp` and drop those tasks from the re-raise set (`libs/langgraph/langgraph/pregel/_executor.py:77-88, 171-181`); (b) `run_with_retry` / `arun_with_retry` re-raise `ParentCommand` and `GraphBubbleUp` immediately, convert user-raised `CancelledError` into `NodeCancelledError`, and otherwise consult `retry_policy.retry_on` (`libs/langgraph/langgraph/pregel/_retry.py:618-640, 753-794`); (c) `_panic_or_proceed` collects `GraphInterrupt` instances and re-raises everything else (`libs/langgraph/langgraph/pregel/_runner.py:650-697`); (d) `commit` writes `(INTERRUPT, ...)` vs. `(ERROR, ...)` vs. `(ERROR_SOURCE_NODE, ...)` based on `isinstance` (`libs/langgraph/langgraph/pregel/_runner.py:574-613`); (e) `prepare_node_error_handler_task` builds a `NodeError(node, error)` payload and injects it into `CONFIG_KEY_NODE_ERROR` so per-node handlers can dispatch on type (`libs/langgraph/langgraph/pregel/_algo.py:1236-1238`).

3. **Are error categories documented?** — **Weakly.** Documentation exists at three levels: docstrings on each error class with troubleshooting URLs (`libs/langgraph/langgraph/errors.py:67-86, 90-99, 190-199`), URL fragments embedded via `create_error_message` (`libs/langgraph/langgraph/errors.py:42-47`), and `docs/redirects.json:231-276` which maps each `ErrorCode` enum value to a docs.langchain.com page. There is **no single in-repo document** that names the categories (control-flow, node, validation, infrastructure) or tells a caller "if you want to retry, catch `NodeTimeoutError` or one of the third-party types in `default_retry_on`; if you want to escalate, re-raise `GraphInterrupt`; if you want to stop, let `BaseException` propagate". A user has to read `_retry.py` and `_runner.py` to recover the dispatch table.

4. **Can new error types be added without breaking existing handling?** — **Yes.** The dispatch protocol keys on inheritance from `GraphBubbleUp` (control-flow) or absence-of-inheritance (fatal) — a new fatal subclass automatically follows the panic path through `_panic_or_proceed`, `commit`, and the executor `done` callbacks. A new control-flow subclass only needs to inherit from `GraphBubbleUp` to be excluded from re-raise in the executor and to bubble through retry. The `NodeError` dataclass (`libs/langgraph/langgraph/errors.py:148-165`) is open: any `(str, BaseException)` pair is a valid payload, and handlers dispatch on their own. The `ErrorCode` enum is the only rigid part — adding a new error code is a non-breaking change for existing callers because it only affects `create_error_message` URL formatting (`libs/langgraph/langgraph/errors.py:42-47`). The risk is that new subclasses *inadvertently* inherit from `BaseException` directly rather than `GraphBubbleUp` and so get re-raised when they should bubble — but the tests at `libs/langgraph/tests/test_retry.py:1729-1793` (using `raise ParentCommand(...)` inside nodes) prove the protocol works for explicit subclassing.

## Architectural Decisions

- **Single-file registry.** All framework error classes are co-located in `libs/langgraph/langgraph/errors.py:1-241` and exposed via `__all__` (`libs/langgraph/langgraph/errors.py:16-31`). This makes the taxonomy easy to discover but means runtime errors and validation errors share a single namespace.
- **Control-flow superclass.** `GraphBubbleUp(Exception)` (`libs/langgraph/langgraph/errors.py:50-51`) is the central design choice — every exception that *should not* be treated as a fatal node failure inherits from it. The alternative (a separate marker protocol or a `kind` enum on a single class) was rejected in favor of using the exception type system as the dispatch key.
- **`NodeError` is a dataclass, not an exception.** At `libs/langgraph/langgraph/errors.py:148-165`, `NodeError` is a frozen dataclass with `(node: str, error: BaseException)`. This decouples "error context passed to a handler" from "exception raised by the framework" — handlers don't catch `NodeError`, they receive it as an injected parameter. The injection point is `CONFIG_KEY_NODE_ERROR` (`libs/langgraph/langgraph/_internal/_constants.py:77-80`).
- **Distinct timeout error type.** `NodeTimeoutError(Exception)` deliberately does **not** inherit from `TimeoutError(OSError)` (`libs/langgraph/langgraph/errors.py:190-199`) so that the default retry policy treats it as retryable. `default_retry_on` (`libs/langgraph/langgraph/_internal/_retry.py:1-29`) explicitly excludes `OSError` from retry, so inheriting from `TimeoutError(OSError)` would have made timeouts non-retryable by default. This is a load-bearing design choice.
- **Distinct cancellation error type.** `NodeCancelledError(Exception)` (`libs/langgraph/langgraph/errors.py:168-187`) is used to distinguish user-raised `asyncio.CancelledError` (which should surface as a node failure) from framework-initiated `CancelledError` (which is silent tear-down). The detection uses `asyncio.Task.cancelling() == 0` (`libs/langgraph/langgraph/pregel/_retry.py:315-334, 790-794`).
- **Per-source-node write key for handler routing.** `ERROR_SOURCE_NODE` is a reserved write key (`libs/langgraph/langgraph/_internal/_constants.py:15-17`) used to mark the failing node when an error handler exists, so a later `commit()` can decide whether to append it (`libs/langgraph/langgraph/pregel/_runner.py:597-603`).
- **`ErrorCode` enum is the documentation bridge.** Each channel-update validation raises `InvalidUpdateError` with a `create_error_message(..., error_code=ErrorCode.X)` payload (`libs/langgraph/langgraph/channels/last_value.py:60-64, binop.py:120-124, delta.py:167-171`) so the failure mode is brand-tagged with a URL. This is how langgraph closes the "what error is this and what do I do" loop without in-repo docs.
- **Default error handler is auto-generated.** When `StateGraph.set_node_defaults(error_handler=...)` is used, an internal `__default_error_handler__` node is created (`libs/langgraph/langgraph/graph/state.py:98, 1280-1297`) and every regular node's `error_handler_node` is set to it. This avoids each user node having to declare its own handler but means the error handling layer is implicit — there is no error category the handler dispatches on; it gets `(state, NodeError)` and decides.

## Notable Patterns

- **Inheritance-based dispatch** (no string tags): the entire control-flow vs. fatal split uses `isinstance(exc, GraphBubbleUp)` rather than an enum attribute on a single exception class. Every dispatch site uses this pattern (`libs/langgraph/langgraph/pregel/_executor.py:81-86, 176-177`, `libs/langgraph/langgraph/pregel/_runner.py:585-602, 682-687`, `libs/langgraph/langgraph/pregel/_retry.py:632-634, 773-776`).
- **Handler payload via configurable injection** (`libs/langgraph/langgraph/_internal/_constants.py:77-80`, `libs/langgraph/langgraph/pregel/_algo.py:1236-1238`): the error context reaches the handler through `config["configurable"][CONFIG_KEY_NODE_ERROR]` rather than through closure capture or global state, which is what makes resume-after-crash work — the handler can be re-invoked on a different process and still see the original error.
- **Observable attempts, not observable errors**: `_AttemptEvent` (`libs/langgraph/langgraph/pregel/_retry.py:110-126`) carries `error_type=type(error).__name__` and `error_message=str(error)` per attempt, so downstream observers (langgraph-server) get the class name and message but not a category tag. This is consistent with the lack of a category attribute on the errors themselves.
- **Heuristic user-cancellation detection** (`libs/langgraph/langgraph/pregel/_retry.py:315-334`): `asyncio.Task.cancelling()` is the single signal that distinguishes a user-raised `CancelledError` from a peer-failure cancellation. The function is named `_is_user_raised_cancelled` and is the entire detection mechanism — there is no opt-in flag, no marker exception.
- **Reserved write keys as the error channel**: `ERROR`, `ERROR_SOURCE_NODE`, `INTERRUPT`, `RESUME`, `NO_WRITES` (`libs/langgraph/langgraph/_internal/_constants.py:9-22`) are the mechanism by which error state survives across supersteps and into checkpoints. Errors are first-class persistent data, not just runtime exceptions.

## Tradeoffs

- **Role-based rather than source-based taxonomy.** The dimension asks for classification by *source* (model, provider, tool, validation, policy, context, user, infrastructure, timeout). LangGraph classifies by *runtime role* (control-flow, node, validation, infrastructure). This means a caller who wants to know "is this a model error or a tool error?" must inspect `type(error.error).__name__` after unwrapping `NodeError`, not the outer exception's type. The trade-off: simpler inheritance-based dispatch (only one axis to check), but less direct information for callers.
- **`ErrorCode` enum couples to external docs.** Every code is a string that resolves to a `docs.langchain.com` URL via `create_error_message` (`libs/langgraph/langgraph/errors.py:42-47, 3018-3026`). This is good for end-users but means the enum and the docs must be kept in sync by convention — `libs/checkpoint` adds its own `EmptyChannelError` (`libs/checkpoint/langgraph/checkpoint/base/__init__.py:745-749`) which is re-exported from `langgraph.errors` (`libs/langgraph/langgraph/errors.py:10, 17`) but has no `ErrorCode` member and no troubleshooting URL.
- **`NodeError` is not an exception, which is good and bad.** It's good because handlers can't accidentally `except NodeError` and treat it as fatal; it's bad because `isinstance(exc, NodeError)` never matches anywhere — a debugger or tracer can't tell from the type alone that the value is an error context.
- **Remote errors are flat.** `RemoteException(Exception)` (`libs/langgraph/langgraph/pregel/remote.py:112-115`) has no subclasses, so a remote 401 and a remote 500 both arrive as the same exception. The SDK (`libs/sdk-py/langgraph_sdk/errors.py:13-136`) has a real HTTP-style taxonomy but the runtime side does not.
- **Default retry classification is brittle.** `default_retry_on` (`libs/langgraph/langgraph/_internal/_retry.py:1-29`) allowlists `ConnectionError` and 5xx HTTP and denylists a fixed set of common Python exceptions. Anything not in either list is retried by default. This means a *new* exception type added by a third-party library (e.g. `openai.RateLimitError`, `anthropic.APIStatusError`) is retried by default unless the user opts in with `RetryPolicy(retry_on=...)`. The trade-off is more permissive retries out of the box; the cost is silent retry storms.
- **Cancellation classification depends on Python 3.11+** (`libs/langgraph/langgraph/pregel/_retry.py:51-56, 315-334`). On Python 3.10 the `asyncio.Task.cancelling()` API is unavailable, so `_is_user_raised_cancelled` returns `False` and user-raised `CancelledError` is silently swallowed — same behaviour as pre-LSD-1507. The test gate `NEEDS_TASK_CANCELLING` (`libs/langgraph/tests/test_retry.py:79-83`) is explicit about this fallback.

## Failure Modes / Edge Cases

- **User-raised `CancelledError` is swallowed on Python 3.10** (`libs/langgraph/langgraph/pregel/_retry.py:329-334`): no-op fallback for `_is_user_raised_cancelled`; user node that calls `raise asyncio.CancelledError()` reports as success.
- **Channel errors are local, not propagated** (`libs/langgraph/langgraph/channels/base.py:55-85`): `EmptyChannelError` is caught in `is_available()` and `checkpoint()` and never reaches the runner; a node that depends on an empty channel and uses `get()` instead of `is_available()` will surface `EmptyChannelError` as a generic `Exception` — not classified as a validation error at the runner level.
- **Handler routing excludes handlers from being handlers** (`libs/langgraph/langgraph/pregel/_runner.py:171-174, 1280-1331`): `_should_route_to_error_handler` returns `False` for tasks in `error_handler_nodes`, and the spec loop (`libs/langgraph/langgraph/graph/state.py:1300-1308`) ensures handlers are not assigned to handlers. So a handler that crashes will panic the run, not route to another handler. This is correct but means handler crashes are surfaced as raw `RuntimeError`, not `NodeError`.
- **Error handler is concurrent with siblings** (`libs/langgraph/tests/test_retry.py:2749-2810`): if multiple nodes fail in the same superstep, their handlers run in parallel. A handler that mutates shared state can race with in-flight siblings.
- **`default_retry_on` is the only source-classification heuristic** (`libs/langgraph/langgraph/_internal/_retry.py:1-29`): any new exception type is retryable by default unless explicitly denylisted; any new domain (e.g. an `anthropic.APIStatusError` added in 2025) requires no code change but silently retries 4xx errors as if they were transient.
- **Error round-tripping through checkpointer loses type** (`libs/langgraph/tests/test_retry.py:2742-2746`): on resume, the error stored in `(ERROR, ...)` writes is deserialized as a string representation in some cases; `NodeError.error` is no longer the original exception type, just `str(original)`.
- **`GraphInterrupt` aggregate merges interrupts across tasks** (`libs/langgraph/langgraph/pregel/_runner.py:688-690`): multiple simultaneous `GraphInterrupt`s are flattened into one `GraphInterrupt(tuple(i for exc in interrupts for i in exc.args[0]))` — the original task attribution is lost.
- **Retry-vs-timeout interaction**: `NodeTimeoutError` is retryable (`libs/langgraph/langgraph/_internal/_retry.py:1-29`), so a node that always times out will be retried until `max_attempts` and then surface as `NodeTimeoutError` after exhaustion — the original timeout duration is preserved (`libs/langgraph/langgraph/errors.py:208-241`) so callers can distinguish "first attempt timed out at 1s" from "third attempt timed out at 1s after backoff".

- **Extend `default_retry_on` allowlist.** Today (`libs/langgraph/langgraph/_internal/_retry.py:1-29`) only `httpx` and `requests` are HTTP-aware; new providers (anthropic, google-genai, cohere) each have their own exception types and are silently retryable by default.
