## Summary

OpenHands delegates responsibility to the human user/operator by design: every conversation is owned via `created_by_user_id`, every event carries a typed `source` (`agent`/`user`/`environment`/`hook`), and a pluggable `ConfirmationPolicy` (`NeverConfirm`/`ConfirmRisky`/`AlwaysConfirm`) can gate risky tool execution with `WAITING_FOR_CONFIRMATION` and a persisted `UserRejectObservation`. The actionable accountability primitives are therefore present — who started what, which agent or hook produced which event, and whether a human rejected vs a hook blocked an action. However the model is opt-in and weakly governed: `confirmation_mode` defaults off, there is no model-output disclaimer or watermark (only a soft prompt instruction to add disclosure when posting externally), tool decisions are attributed only to `tool_call_id`/`action_id` without a principal or policy reference, human approvals are recorded anonymously or via a nullable `user_id` (`None` in OSS/admin contexts), and no formal RACI, accountability runbook, or `ACCOUNTABILITY.md` exists — the `LICENSE:28` MIT disclaimer explicitly disclaims liability. Observability attribution via `get_user_email()` for Laminar tracing is documented as PII-sensitive fallback logic, not as a non-repudiable audit log.

## Rating

**4/10 — Present but inconsistent, weakly documented, or fragile**

Rationale: Ownership (`created_by_user_id`, `sandbox_id`, `Event.source`), typed event sourcing (`ActionEvent`/`ObservationEvent`/`UserRejectObservation` with `rejection_source`), and the `ConfirmationPolicy` + `SecurityAnalyzer` gate provide a partial answer to "who is responsible for this action?" and are exercised in code (`_select_confirmation_policy`, `blocked_actions`, `WAITING_FOR_CONFIRMATION`). But model outputs carry no built-in disclaimer/watermark, tool attribution lacks tool-author and approver identity, human rejections are only durably tied to a nullable `user_id`/`event_id` chain, confirmation is disabled by default, and accountability is undocumented beyond the MIT "AS IS" disclaimer and a `CODE_OF_CONDUCT` note about community-leader enforcement. No tests assert accountability invariants, and persistence is file-backed `InMemoryFileStore` fallback by default, making the audit trail non-durable/non-observable in OSS single-node deploys.

## Answers to Dimension Questions

### 1. Who is responsible for agent actions?

**The user/operator (and deploying organization), not the model, runtime author, or tool author.** There is no file that declares "OpenHands Inc. is responsible for agent outputs." Instead the codebase encodes three delegations: (a) legal: `LICENSE:28` `AS IS` disclaimer disclaims author liability; (b) data: `AppConversationInfo.created_by_user_id:115` and `AppConversationStartTask.created_by_user_id:316` bind every conversation to a nullable principal, with `UserContext.get_user_email():30` used only for observability tracing (`live_status_app_conversation_service.py:391` falls back to internal id in OSS); (c) runtime: `SourceType: types.py:5` labels every event (`agent`/`user`/`environment`/`hook`) so forensic walk can say *what subsystem* emitted the action, and `ACPAgentSettings` provenance tags (`agentprofileid`, `acpserver`) record *which profile* launched the run. None of this is a governed RACI — `ADMIN = SpecifyUserContext(user_id=None):67` permits anonymous starts, `confirmation_mode` defaults false (`model.py:574` → `NeverConfirm()`), and the MIT license's "sole responsibility" language at ` CREDITS.md:268` (Apache-2.0 excerpt) reinforces operator liability. A reviewer can answer "which user started conversation X?" via `app_conversation_info_service` but cannot answer "which organization policy authorizes tool Y for role Z" from code alone.

### 2. Is model output attributed?

**No — only an external-posting disclosure instruction exists, not a systemic disclaimer or watermark.** Internal agent outputs (`ActionEvent.thought:23`, `ActionEvent.summary:74`, `MessageEvent` content) carry `source="agent"` and `llm_response_id`, but no `generated_by`, `model`, `disclaimer`, or cryptographic provenance field is injected. The sole disclosure mechanism is a natural-language instruction in `system_prompt.j2:105` requiring the agent to add `_This comment was created by an AI agent (OpenHands) on behalf of [user]._` when posting to Slack/GitHub/GitLab/PRs/emails via tool or MCP — unenforced by code (no transformer, no validation, no test asserts the footer). Git commits optionally add `Co-authored-by: openhands <openhands@all-hands.dev>` (`system_prompt.j2:41`), but this depends on the LLM obeying the prompt and on `git config` presence, not on a runtime watermark. Search for `disclaimer`/`watermark` across `_sdk_inspect/sdk/event` and `openhands/app_server` returns only the OAuth consent banner (`llm/auth/openai.py:52`) and license text. Frontend chat rendering (`HANDLED_ACTIONS` in `chat-slice.ts` per `AGENTS.md`) does not badge messages as AI-generated.

### 3. Are tool decisions attributed?

**Partially — fully traceable to an LLM tool call, not to a principal/policy or tool author.** The attribution chain is: LLM `Message.tool_calls[]` → `ActionEvent(tool_name, tool_call_id, tool_call, llm_response_id, security_risk: _sdk_inspect/sdk/event/llm_convertible/action.py:41)` → persisted `EventLog` → `ObservationEvent(tool_name, action_id, tool_call_id, source="environment")` or `UserRejectObservation(rejection_source="user"|"hook")`. Log coloring by `event_source: utils/logger.py:141` and the paginated `EventService.search_events(kind__eq, sort_order): event_service.py:26` let an operator reconstruct "tool X was invoked with args Y at timestamp T by llm_response_id R producing observation O." What is missing: (a) no `tool_author`/`plugin_source` field on the event (marketplace `source` lives only in `PluginSpec: app_conversation_models.py:71` and is not copied to `ActionEvent`); (b) no `approved_by` principal on the `ActionEvent`; (c) `ConfigurableToolExecutor`/`Delegate`/`TaskManager` delegation (`tools/delegate/impl.py:44`, `tools/task/manager.py:40`) carries `confirmation_handler: Callable[[str, list[ActionEvent]], bool]` but not an auditable delegation record. So the system answers "which LLM output triggered which tool execution" but not "which human, role, or policy approved that tool decision" nor "which marketplace publisher authored the tool."

### 4. Are human approvals recorded?

**Yes — as persisted rejection/block records and checkpointed status, but without durable identity.** The gate is `ConversationExecutionStatus.WAITING_FOR_CONFIRMATION: state.py:52` + `ConversationState.confirmation_policy:121`. When `confirmation_mode==true` (`config.template.toml:228`), `_select_confirmation_policy: app_conversation_service_base.py:677` chooses `ConfirmRisky` (if `security_analyzer=="llm"`) else `AlwaysConfirm`; the agent loop checks `state.confirmation_policy.should_confirm(risk): sdk/agent/agent.py:640` and, if gated, awaits user confirmation. Two durable outcomes exist: (a) user rejects → `UserRejectObservation(rejection_source="user", rejection_reason): observation.py:83` is appended to `EventLog` and surfaces to the LLM as `Action rejected: ...`; (b) hook blocks → same type with `rejection_source="hook"` and `state.blocked_actions[action_id]=reason: state.py:449`. `get_unmatched_actions: state.py:474` identifies pending-confirmation actions by scanning for missing `ObservationEvent`/`UserRejectObservation`. Approval *to proceed* is not reified as a distinct `HumanApprovalEvent`; it is inferred from the absence of a rejection and the next `ObservationEvent` appearing. Identity gaps: the reject event stores `action_id`/`tool_call_id` but not `approved_by_user_id`; conversation-level owner `created_by_user_id` may be `None` (admin/OSS), and `get_user_email()` is optional PII excluded by default. Export via `event_service.iter_events_for_export:51` can emit the chain, but there is no signed approval log or retention policy.

### 5. Is accountability documented?

**Weakly — no dedicated accountability documentation; only a license disclaimer, a conduct note, and inline code comments.** `grep` for `ACCOUNTABILITY`, `RACI`, `audit log`, `runbook` across `openhands/` and `_sdk_inspect/` yields no files. The only accountability-adjacent artifacts are: `LICENSE:1` splitting enterprise vs MIT scope; `AGENTS.md` contributor/migration guidance (not operational accountability); `CODE_OF_CONDUCT.md:24,42` assigning `responsibility to apologize / enforce standards` to community leaders; and docstrings such as `UserContext.get_user_email:30` warning "considered PII and may be forwarded to third-party observability services." There is no `docs/accountability.md`, no RACI matrix mapping `Operator`/`Model Provider`/`Tool Author`/`Enterprise Org` to actions, and no runbook describing who must sign off on `CONFIRM_RISKY` vs `ALWAYS_CONFIRM`, how `JwtService`/`session_api_key` scoping enforces delegation, or how long `EventLog`/`AppConversationInfo` retention must be for compliance. The closest operational contract is `THREAT_MODEL.md` in `langgraph` — no analogue exists in `openhands`.

## Architectural Decisions

|----------|----------|--------------------------|

## Notable Patterns

- **Ownership-as-tag provenance pattern** — `LiveStatusAppConversationService._build_start_conversation_request_for_user` stamps `tags[AGENT_PROFILE_ID_TAG_KEY]`/`AGENT_PROFILE_REVISION_TAG_KEY`/`ACP_SERVER_TAG_KEY`/`ARCHIVE_WORKSPACE_PATH_TAG_KEY` at `live_status_app_conversation_service.py:546-582` and projects them via `@computed_field` accessors (`acp_server:142`, `launched_agent_profile:158`). Reuses resolved `profile_user` rather than re-fetching, avoiding double resolution cost but coupling provenance to settings resolution state.

- **Hook-vs-user rejection discrimination** — `UserRejectObservation.rejection_source="user"|"hook": observation.py:83` plus `ConversationState.blocked_actions:141` / `blocked_messages:147` / `pop_blocked_action:451` gives a durable, queryable split between "human said no" and "policy hook said no" without scanning raw log text.

- **Three-state confirmation gating** — `NeverConfirm` / `ConfirmRisky(threshold=HIGH)` / `AlwaysConfirm` at `confirmation_policy.py:27,35,43` combined with `ConversationExecutionStatus.WAITING_FOR_CONFIRMATION: state.py:52` and `ConversationState.get_unmatched_actions:474` creates a clear lifecycle: `RUNNING → WAITING_FOR_CONFIRMATION → (ObservationEvent | UserRejectObservation)`, detectable via `state.events`.

- **Event-callback audit sink** — `EventCallbackProcessor: event_callback_models.py:40` + `EventCallbackService` + `SetTitleCallbackProcessor: set_title_callback_processor.py:83` demonstrates a general pattern for attaching post-event side effects (logging, title polling, future audit export) keyed by `event_kind`, persisted with `ACTIVE/DISABLED` lifecycle, though only logging/title are built-in.

- **Soft security analyzer injection** — `_set_security_analyzer_from_settings: app_conversation_service_base.py:690` is best-effort (`if session_api_key is None: return` and skips API call when analyzer is `None`) — deliberately does not block conversation start if analyzer cannot be set, trading accountability (risk labeling) for availability.

## Tradeoffs

| Tradeoff | Pro | Con |
|----------|-----|-----|
| **Opt-in confirmation vs always-gated** — `confirmation_mode=false` → `NeverConfirm()` default | Low friction for autonomous coding agents; matches "self-hosted developer control center" UX; no human bottleneck | Accountability log may contain zero human decisions to audit; failure is silent (no `WAITING_FOR_CONFIRMATION` ever emitted) so reviewers cannot distinguish "operator intentionally disabled gating" from "misconfiguration". |
| **File/Memory persistence vs DB durability** — SDK `LocalFileStore` with `InMemoryFileStore` fallback | Zero infra for quickstarts/tests; portable across backends (local, docker, cloud) | Audit trail durability is deployer-dependent; `python -m openhands ...` without `persistence_dir` loses event history on restart, breaking chain of custody; no checksumming or tamper-evidence on `BASE_STATE.json`. |
| **Prompt disclosure vs enforced watermark** — `system_prompt.j2:105` natural-language mandate | Model-agnostic, zero latency, covers all external channels (GH/Slack/Linear/Jira/MCP) | No enforcement: tests do not assert footer presence; internal UI chat and exported patches carry no disclaimer, so third-party recipients outside the posting path see unmarked AI output. |
| **Nullable `created_by_user_id` vs required identity** — `str \| None` on both info and start task | Supports OSS, CLI, and webhook-triggered automations without auth plumbing (`ADMIN` context) | Anonymous conversations create an accountability hole: `created_by_user_id=None` plus `get_user_email()=None` yields an event stream with no principal at all, only `source`. |
| **PII caution vs auditable principal** — `UserContext.get_user_email` flagged as PII, Laminar uses `email or user_id` fallback | GDPR-conscious, minimal data forwarded to third-party observability (`laminar_user_id:391` comment) | Core accountability question "which person approved tool X?" cannot be answered from the durable `EventLog` without enabling PII forwarding; deployer must choose between privacy and non-repudiation. |
| **Tag-based provenance vs dedicated columns** — `tags` dict with squashed keys (`agentprofileid`) and `@computed_field` projection | Zero-migration, shared with `agent-canvas`; provenance round-trips through DB `tags` column for free | Tags are mutable user-supplied-adjacent (`AppConversationUpdateRequest:275` allows updating `title`/`public`/`repo` — not tags, but tags remain writable via start); no signature so `agentprofileid` could be replayed. |
| **Redaction filters vs complete audit** — `SensitiveDataFilter` + `redact_text_secrets` + `SensitiveDataFilter` on every handler | Prevents secret leakage into `openhands.log`, `llm/`, and uvicorn access logs (`RedactURLParamsFilter:549`) | Over-redaction can hide accountable context (which secret/provider was used) — `SensitiveDataFilter:251` scans env var names containing `SECRET/_KEY/_CODE/_TOKEN` and replaces values with `******`, so post-incident forensics lose the binding between a leaked secret and a responsible principal. |

## Failure Modes / Edge Cases

- **Anonymous approval loophole**: `AppConversationInfo.created_by_user_id=None` plus `UserRejectObservation` storing only `action_id`/`tool_call_id` means a `RESUME`/`ObservationEvent` following `WAITING_FOR_CONFIRMATION` carries no `approved_by` principal. If two operators share a server, their approvals are indistinguishable in `get_state_history()`; `ADMIN` context further normalizes to `None`.

- **Confirmation disabled by default**: New installs with `confirmation_mode=false` (template and `ConversationSettings._build_confirmation_policy:574`) never enter `WAITING_FOR_CONFIRMATION`; the audit log contains no `UserRejectObservation` rows, so an auditor cannot tell whether the operator consciously risk-accepted autonomous tool execution or simply missed the toggle.

- **LLM-ignores-disclosure**: Because disclosure at `system_prompt.j2:105` is prompt-level, a jailbroken or truncated context can omit the footer when posting via `github`, `gitlab`, `slack`, or MCP integrations (`openhands/app_server/integrations/...`). No post-tool validator checks outgoing `TextContent` for the disclaimer before `POST /repos/{owner}/{repo}/issues`.

- No output disclaimer or model-output watermark is implemented — `grep -i disclaimer` across `openhands/app_server` and `_sdk_inspect/sdk/event` yields only `llm/auth/openai.py:67` OAuth consent and `LICENSE` boilerplate; cannot verify AI provenance from `Event` alone.
- No formal accountability documentation — no `ACCOUNTABILITY.md`, `RACI.md`, `AUDIT.md`, or policy manifest maps `Model`/`Tool Author`/`User`/`Operator`/`Organization` responsibilities to enforcement points; the closest is the MIT license's liability disclaimer.
- Human decision logs lack durable principal identity — `UserRejectObservation:71` and `ConversationState.blocked_actions:141` record *that* approval happened and *what* value but not *who* (no `approved_by_user_id` field); `created_by_user_id` may be `None`.
