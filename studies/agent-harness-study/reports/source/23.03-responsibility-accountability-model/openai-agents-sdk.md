## Summary

openai-agents-sdk is a provider-agnostic library, not a deployed agent service. Responsibility is implicitly delegated to the deployer/developer/organization — the MIT license (`LICENSE:1-21`) disclaims all warranties and the SDK provides no RACI, policy file, or `accountability.md` mapping model/runtime/tool-author/user/operator/organization to actions. Technical attribution is fragmented but durable for two axes: tool execution (via `ToolOrigin`, `RunItem.agent`, `ToolCallItem.call_id`, namespaced lookup keys, and trace spans) and human decisions (via `RunContextWrapper._approvals`/`_tool_invocations` + `RunState.approve()/reject()` + serialized `interruptions`). Model output carries no disclaimer or watermark; generation spans record `model`/`model_config`/`usage` internally but do not surface a user-facing "AI-generated by X" label. The system can answer *what* ran (tool name + origin + agent + call_id + span) and *whether a human approved this call_id*, but cannot answer *who* (principal identity) is ultimately responsible without external application code.

## Rating

**4/10 — Present but inconsistent, weakly documented, fragile**

Rationale: `ToolOrigin` (`src/agents/tool.py:285`) + `RunItem.agent` (`src/agents/items.py:99`) + namespaced lookup keys (`src/agents/_tool_identity.py:13`) give execution-level attribution, and the HITL ledger (`src/agents/run_context.py:57`, `src/agents/run_state.py:1285`) with durable JSON serialization is tested and schema-versioned — lifting the score above "absent" (1-3). However the dimension's core question "who is responsible for this action?" remains unanswerable in policy terms: no output disclaimer/watermark exists (grep for `disclaimer`/`watermark`/`AI-generated` returns zero hits in `src/agents`), no tool-author identity is stored, no organization/operator principal is bound to approvals (approval records are keyed by tool name/call_id, not user_id), and no accountability doc defines the responsibility chain. Tracing is opt-out and sampling-configurable, so the audit trail is not tamper-evident or mandated.

## Answers to Dimension Questions

### 1. Who is responsible for agent actions?

**Implicitly the deploying developer/operator/organization — not the model, runtime author, or SDK.** No code object or doc assigns responsibility among the six principals. `LICENSE:15` ("THE SOFTWARE IS PROVIDED AS IS ... IN NO EVENT SHALL THE AUTHORS ... BE LIABLE") transfers liability to the licensee. `src/agents/agent.py:296` defines an agent as "AI model configured with instructions, tools, guardrails, handoffs" but never states who is answerable when a tool mutates state. `docs/human_in_the_loop.md:42-53` implies the application owner must implement the `interruptions → approve/reject → resume` loop. Tracing provides forensic *what/when* (`AgentSpanData.name` at `src/agents/tracing/span_data.py:44`, `GenerationSpanData.model` at `src/agents/tracing/span_data.py:183`) but binds no `user_id`/`operator_id`/`organization_id` principal — approval keys are `tool_name`/`call_id`/`namespace` (`src/agents/_tool_identity.py:607`). The SDK is correctly a library: the operator who chooses the model, registers tools, and implements approval UX is the de-facto responsible party, with no SDK-enforced RACI.

### 2. Is model output attributed?

**No user-facing disclaimer; attribution exists only as internal trace metadata (weak).** `src/agents/items.py:169` `MessageOutputItem` returns raw `ResponseOutputMessage` text verbatim — no `"Generated by gpt-4o"` prefix, no watermark field, no `AI-generated` flag. Search for `disclaimer`/`watermark`/`AI-generated` across `src/agents` returns zero hits. Internally, `GenerationSpanData` at `src/agents/tracing/span_data.py:169` records `model`/`model_config`/`usage` and `ResponseSpanData` at `src/agents/tracing/span_data.py:212` records `response_id`, but these live in the tracing pipeline (exported via `TraceProvider`/`BatchTraceProcessor` at `docs/tracing.md:144-152`) and are disabled when `OPENAI_AGENTS_DISABLE_TRACING=1` or `RunConfig.tracing_disabled=True` (`docs/tracing.md:7-11`). An end-user receiving `result.final_output` at `src/agents/result.py:323` has no in-band signal that content is model-generated unless the application adds one.

### 3. Are tool decisions attributed?

**Partially — execution attribution is mature, principal attribution is absent.** Every tool execution is tied to: (a) `ToolCallItem.tool_name` + `call_id` (`src/agents/items.py:404-417`), (b) `RunItemBase.agent` (`src/agents/items.py:99`) indicating which agent's turn produced it, (c) `tool_origin: ToolOrigin` (`src/agents/items.py:397`, `src/agents/tool.py:285`) distinguishing `FUNCTION` vs `MCP` vs `AGENT_AS_TOOL` with `mcp_server_name`/`agent_name` (`src/agents/tool.py:298-300`), (d) collision-free `FunctionToolLookupKey` (`src/agents/_tool_identity.py:13`) and qualified `namespace.name` (`src/agents/_tool_identity.py:129`), and (e) `FunctionSpanData.name`/`mcp_data` in traces (`src/agents/tracing/span_data.py:135`). The `_ToolInvocationRecord` ledger at `src/agents/run_context.py:45` fingerprints invocation identity and enforces `call_id` uniqueness (`src/agents/run_context.py:344-351`). What is missing: no `tool_author_id`, `deployed_by`, or `approved_by` principal on the tool definition; `FunctionTool.qualified_name` at `src/agents/tool.py:574` is a syntactic name, not an identity. The model’s decision to call a tool is inferred from the `ModelResponse.output` tool-call item, not recorded as an explicit "model chose tool X because Y" audit event.

### 4. Are human approvals recorded?

**Yes — fully persisted, versioned, and resumable; this is the strongest sub-system.** Approvals are recorded in `RunContextWrapper._approvals` (`src/agents/run_context.py:89`) as `_ApprovalRecord` entries (`src/agents/run_context.py:57`) keyed by tool name/namespace/lookup key or `HostedMCPApprovalKey` (`src/agents/_tool_identity.py:21`), with per-call (`list[call_id]`) vs sticky (`bool` + `sticky_scope`/`sticky_rejection_message`) semantics. `RunState.approve()`/`reject()` at `src/agents/run_state.py:1285` mutate this ledger, including delegation to nested `Agent.as_tool()` states (`src/agents/run_state.py:1289-1293`). The ledger survives `RunState.to_json()`/`from_json()` via `_serialize_approvals()`/`_serialize_tool_invocations()` (`src/agents/run_state.py:1330-1368`) and is covered by schema-version notes (`SCHEMA_VERSION_SUMMARIES` at `src/agents/run_state.py:196` includes 1.9 "tool origin metadata", 1.14 "hosted MCP approvals", 1.15 "tool invocation identity"). The canonical ledger also tracks `executed`/`completed` per `call_id` (`src/agents/run_context.py:49`). Custom `rejection_message` per rejection (`src/agents/run_state.py:1300`) and `ToolErrorFormatter` (`src/agents/run_config.py` via `docs/human_in_the_loop.md:56-60`) allow distinct model-visible denial feedback. Gaps: no human principal (who approved — no `user_id` on `_ApprovalRecord`), no timestamp, no signature; the record answers *what decision for which call_id* not *who/when*.

### 5. Is accountability documented?

**Weakly — HITL guide and tracing guide exist, but no unified accountability model.** The only accountable workflow doc is `docs/human_in_the_loop.md:1-205` (HITL pause/approve/resume, including nested agent-as-tool) and `docs/tracing.md:1-226` (trace/span hierarchy, `flush_traces()`, custom processors). `README.md:12-20` lists "Human in the loop" and "Tracing" as core concepts without framing them as accountability controls. `SECURITY.md:1-5` covers vulnerability disclosure, not action audit. No file maps action classes (LLM generation, tool execution, handoff, memory write, human approval) to responsible principals or retention policy; no `GET /accountability` equivalent; no append-only audit-log spec. Retention relies on the caller persisting `RunState` JSON (with sensitive `context` potentially included — warning at `src/agents/run_state.py:197-202` to treat `RunContextWrapper.context` as persisted data and avoid secrets). Tracing is treated as optional observability (can be globally disabled), not a mandatory accountability ledger.

## Architectural Decisions

- **Library-not-service posture** (`LICENSE:1`, `src/agents/__init__.py` exports): Decisions push accountability to the host application — correct for provider-agnostic SDK but leaves organizational responsibility undefined. File: `LICENSE:1`, `README.md:3-4`.
- **`ToolOrigin` as origin discriminator** (`src/agents/tool.py:285`): Minimal 3-variant enum plus optional `mcp_server_name`/`agent_name` fields; serializable via `to_json_dict`. Decision keeps item payload small while surviving resume, but omits author/operator identity. File: `src/agents/tool.py:287-337`.
- **`RunItemBase.agent` weak-ref pattern** (`src/agents/items.py:98-149`): Every item retains its `Agent` via strong ref + weak-ref fallback for `release_agents()` lifecycle. Decision preserves attribution even when caller drops result references, at cost of `agent` becoming `None` after GC if `release_agents(release_new_items=True)` was called (`src/agents/result.py:385-404`).
- **Dual-key approval model: sticky vs per-call** (`src/agents/run_context.py:57-68`, `src/agents/run_state.py:1285`): `always_approve`/`always_reject` persists sticky `bool` surviving serialization; per-call appends `call_id` to list. Decision enables both "trust this tool forever" and "approve exactly this invocation" but conflates them in one `_ApprovalRecord` dict keyed only by name — two principals cannot hold distinct policies for the same tool.
- **Tool invocation fingerprinting** (`src/agents/_tool_invocation.py` + `src/agents/run_context.py:304`): `tool_invocation_identity_and_scope` digests invocation type/scope/fingerprint to detect `call_id` reuse (`ModelBehaviorError` at `src/agents/run_context.py:328`). Decision prevents model from hijacking a prior `call_id` with different arguments — strong anti-replay for accountability, but error message is generic ("Use a unique call ID").
- **Tracing as the execution ledger** (`src/agents/tracing/traces.py:195`, `src/agents/tracing/spans.py:289`): `AgentSpanData`/`GenerationSpanData`/`FunctionSpanData`/`HandoffSpanData` plus `TraceState` persisted in `RunState` (`src/agents/run_state.py:861-863`). Decision gives excellent forensic replay via OpenAI Traces dashboard or custom processors, but ties accountability to an opt-out, sampling-configurable pipeline — if tracing is disabled, tool attribution is only in ephemeral `RunResult.new_items`.
- **Context-as-persisted-data for approvals** (`src/agents/run_state.py:1542-1653`, `src/agents/run_context.py:117-131`): `_copy_for_run_state()` deep-copies `usage`/`_approvals`/`_tool_invocations`; `RunState.to_json()` warns that non-mapping contexts need `context_serializer`/`context_override`. Decision correctly isolates checkpoint forks but documents that secrets in `RunContextWrapper.context` travel with serialized state (`docs/human_in_the_loop.md:197-202`).

## Notable Patterns

- **Durable interruption as accountability primitive**: `RunResult.interruptions` (`src/agents/result.py:516`) + `RunState._current_step: NextStepInterruption` (`src/agents/run_state.py:846`) + `ToolApprovalItem` (`src/agents/items.py:556`) reifies pending human consent as first-class state, serializable to JSON/string (`src/agents/run_state.py:1774`) with schema versioning (`CURRENT_SCHEMA_VERSION = "1.17"` at `src/agents/run_state.py:191`).
- **Namespace-qualified tool identity**: `tool_qualified_name(name, namespace)` (`src/agents/_tool_identity.py:129`) + `get_function_tool_lookup_key()` + `resolve_tool_name_collisions()` (`src/agents/_tool_identity.py:503`) prevents two tools/hand-offs from colliding on bare name while keeping approval keys collision-free — a stronger identity primitive than flat `tool.name`.
- **Invocation-type scoped approval keys**: `get_function_tool_approval_keys()` (`src/agents/_tool_identity.py:607`) produces distinct approval buckets for `bare`/`namespaced`/`deferred_top_level` and legacy deferred alias, preventing a bare-name `always_approve` from implicitly authorizing a namespaced tool with same bare name.
- **Nested agent-tool approval bubbling**: `RunState._find_nested_approval_state()` (`src/agents/run_state.py:1127`) walks `Agent.as_tool()` nested `RunState`s so outer `state.approve(interruption)` routes to the inner state that owns the interruption — delegation without losing accountability (`src/agents/agent.py:679`, `src/agents/run.py` approval routing).
- **Weak-ref agent attribution with deterministic serialization**: `_serialize_agent_reference()` (`src/agents/run_state.py:2482`) emits `{name, identity}` for duplicate-name agents, paired with `_build_agent_identity_keys_by_id()` to disambiguate clones after `Agent.clone()` — allows post-hoc correlation of which agent instance produced an item.

## Tradeoffs

- **Forensic vs user-facing attribution**: Generation and function spans capture `model`/`input`/`output` internally (`src/agents/tracing/span_data.py:169`, `src/agents/tracing/span_data.py:135`) but `result.final_output` (`src/agents/result.py:323`) surfaces no model label — keeps outputs clean for composition at cost of downstream misattribution if the application republishes without adding a disclaimer.
- **Lightweight `ToolOrigin` vs full provenance**: Three-type enum plus optional server/agent names is cheap and JSON-stable, but cannot answer "who authored tool X" or "which operator approved policy Y" — a dedicated `Responsibility` value object (actor/model/tool_author/organization) would be heavier and require auth integration the SDK intentionally avoids.
- **Sticky approvals: ergonomics vs least privilege**: `always_approve=True` persists across serialization and silently authorizes future `call_id`s without re-prompting — convenient for trusted tools (`docs/human_in_the_loop.md:45`) but risks over-authorization if the same `tool_name` is later reused for a more sensitive variant; no TTL or scope narrowing (e.g., "always approve for this namespace only" is implicit via key, not explicit in policy).
- **Tracing as mandatory vs optional ledger**: `RunConfig.tracing_disabled` and `OPENAI_AGENTS_DISABLE_TRACING` (`docs/tracing.md:7-11`) let operators disable tracing for ZDR; when disabled, the only remaining attribution is `RunResult.new_items`/`RunState` — ephemeral unless the caller persists it. Tradeoff favors privacy/compliance over guaranteed audit trail.
- **Context captured in checkpoint**: Serializing `RunContextWrapper.context` with approvals/usage in same `RunState` JSON simplifies resume (`src/agents/run_state.py:1780-1825`) but mingles application data with SDK audit metadata; `strict_context` + `context_serializer` mitigations exist (`src/agents/run_state.py:1535`) yet many callers will place secrets or PII in context unknowingly.

## Failure Modes / Edge Cases

- **No principal binding on approvals**: `_ApprovalRecord` at `src/agents/run_context.py:57` stores `approved`/`rejected` as `bool|list[str]` with no `approved_by`, `approved_at`, or signature — concurrent operators approving the same `RunState` fork produce silent divergence (last writer wins after `from_json`); no concurrent-approval conflict detection.
- **Tracing disabled erases tool ledger**: If `tracing_disabled=True`, `Trace` becomes `NoOpTrace` (`src/agents/tracing/traces.py:407`) and `Span` becomes `NoOpSpan` (`src/agents/tracing/spans.py:216`); tool attribution survives only in `RunResult` which is not automatically persisted — a crash before the application persists `RunState` loses the record.
- **ContextVar scope loss in async generators**: `_finish_on_generator_exit` at `src/agents/tracing/traces.py:18` and `src/agents/tracing/spans.py:31` handles `GeneratorExit` token resets — but token misuse across tasks still loses trace lineage; `Scope.set_current_trace` is task-local, so approvals recorded in one task may not correlate to spans started in another if the caller mis-threads context.
- **`call_id` reuse across nested runs**: `_tool_invocation_status` at `src/agents/run_context.py:344` raises `ModelBehaviorError` on reuse — correct for malice/bugs, but a legitimate model retry that reuses `call_id` with identical fingerprint after a transient `ToolTimeoutError` (`src/agents/tool.py:1944`) would be rejected; caller must generate fresh `call_id` via model, which they do not control for hosted MCP approvals.
- **Hosted MCP `require_approval: always` without `on_approval_request`** (`src/agents/tool.py:1087-1099`): If the application never handles `interruptions` (e.g., fire-and-forget `Runner.run_sync`), the run dead-ends at `NextStepInterruption` with no timeout; `RunState` sits serialized forever — liveness failure with durable but orphaned approval record (`hosted_mcp` identity at `src/agents/_tool_identity.py:21`).
- **`always_approve` surviving code changes**: Sticky approvals stored under string key (`src/agents/run_state.py:1335`) survive `to_json`/`from_json` and remain valid even if the tool's `needs_approval` semantics change in a new SDK version — doc warns to store version marker (`docs/human_in_the_loop.md:203-205`) but enforcement is caller-side, so stale sticky state can auto-approve a newly sensitive tool.
- **Tool error formatter masks attribution**: `maybe_invoke_function_tool_failure_error_function` at `src/agents/tool.py:1964` converts tool exceptions into model-visible `str` via `default_tool_error_function` (`src/agents/tool.py:1863`); the original exception and its tool identity are attached only to the current span (`src/agents/tool.py:1804` `attach_error_to_current_span`), not to the `ToolCallOutputItem.raw_item` — downstream consumers of `final_output` cannot distinguish "tool X errored" from "model hallucinated error text" without reading traces.
- **Weak-ref GC hides agent identity**: `RunItemBase.release_agents()` at `src/agents/items.py:124` and `RunResult.release_agents()` at `src/agents/result.py:385` drop strong refs for memory; after GC, `item.agent` resolves to `None` (`src/agents/items.py:144-149`) — post-hoc analysis of serialized items (`RunState._serialize_item` at `src/agents/run_state.py:2013` only serializes `agent.name`) cannot distinguish two agents with same name without the duplicate-identity key added in schema 1.7 (`src/agents/run_state.py:203-206`).

## Future Considerations

- Add an explicit, versioned `Responsibility` contract (e.g., `ResponsibilitySnapshot { trace_id, turn, agent_name, agent_identity_key, model, tool_name, qualified_name, tool_origin, call_id, fingerprint, approval_decision, approval_scope, raw_response_id }`) persisted per action and exposed via `RunState.get_responsibility_log()` — would make "who is responsible for this action?" a first-class query instead of a multi-join across items/spans/approvals.
