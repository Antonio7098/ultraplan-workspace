## Summary

agent-framework implements workflow lifecycle events as a first-class, strongly typed surface in both language stacks, but the two stacks model them differently. The Python side uses a single unified generic class, `WorkflowEvent[DataT]`, discriminated by a `type` field constrained by a `WorkflowEventType` Literal union (`python/packages/core/agent_framework/_workflows/_events.py:104-130`, `python/packages/core/agent_framework/_workflows/_events.py:146-194`), constructed exclusively through factory methods (`python/packages/core/agent_framework/_workflows/_events.py:255-342`). The .NET side instead uses a class hierarchy rooted at an abstract `WorkflowEvent` base with one subclass per event kind and JSON polymorphic serialization declared via `[JsonDerivedType]` attributes (`dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowEvent.cs:11-25`).

Both stacks cover the core lifecycle — started, in-progress/pending-request status transitions, idle/idle-with-pending-requests terminal states, failure (with structured error details), superstep start/completion, and executor invoked/completed/failed bookkeeping. Ordering is implicit rather than explicit: Python events flow through an `asyncio.Queue` drained by the runner (`python/packages/core/agent_framework/_workflows/_runner_context.py:289`, `python/packages/core/agent_framework/_workflows/_runner.py:103-114`), and .NET events flow through a FIFO `Channel<WorkflowEvent>` (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:39-44`). Neither stack stamps events with sequence numbers or timestamps in the core schema; timestamps and sequence numbers appear only at the DevUI presentation layer (`python/packages/devui/agent_framework_devui/_mapper.py:476-486`). Events carry partial context linkage (`executor_id`, `request_id`, `source_executor_id`, superstep iteration/StepNumber) but no run/session/workflow IDs; correlation to runs exists only through OpenTelemetry spans. Event versioning is absent from the event schema itself; only the checkpoint envelope that persists pending `request_info` events carries a version field.

Cancellation is the weakest lifecycle point: Python defines `WorkflowRunState.CANCELLED` but nothing emits it, and .NET cancellation simply cancels run-loop tokens without emitting any terminal event.

## Rating

**Score: 6 / 10**

Rationale against the rubric:

- **Typed (strong):** Explicit `WorkflowEventType` Literal union in Python (`python/packages/core/agent_framework/_workflows/_events.py:104-130`) and a sealed-ish class hierarchy with polymorphic JSON contracts in .NET (`dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowEvent.cs:11-18`). Factory methods enforce well-formed construction (`python/packages/core/agent_framework/_workflows/_events.py:255-342`), and accessor properties raise on malformed access (`python/packages/core/agent_framework/_workflows/_events.py:348-406`).
- **Ordered (implicit only):** FIFO queue/channel ordering plus coarse superstep counters (`iteration` at `python/packages/core/agent_framework/_workflows/_runner.py:101,146`; `StepNumber` at `dotnet/src/Microsoft.Agents.AI.Workflows/SuperStepEvent.cs:12-17`). No monotonic per-event sequence numbers.
- **Timestamped (absent in core):** No timestamp fields on any event class; added only downstream in DevUI (`python/packages/devui/agent_framework_devui/models/_openai_custom.py:65-67`).
- **Versioned (absent on events):** Only the checkpoint envelope has `version = "1.0"` (`python/packages/core/agent_framework/_workflows/_checkpoint.py:88`); event deprecation is handled via warnings, not schema versioning.
- **Lifecycle (mostly comprehensive, cancellation gap):** Creation, progress, pending-request halts, completion-by-idle, and failure are all represented and tested (`python/packages/core/tests/workflow/test_workflow_states.py:187-220`). Cancellation produces no event in either stack.

This lands the source squarely in "present but inconsistent" territory for the ordering/timestamp/version dimensions while the typing dimension alone would score 7–8; the composite is 6.

## Answers to Dimension Questions

**1. Are events typed and versioned?**
Typed, yes — rigorously in both stacks. Python constrains event kinds with a `WorkflowEventType` Literal union and a generic payload parameter (`python/packages/core/agent_framework/_workflows/_events.py:104,146`), with runtime guards that raise `RuntimeError` when type-specific accessors are misused (`python/packages/core/agent_framework/_workflows/_events.py:359-361`). .NET uses nominal subclasses with `[JsonDerivedType]` discriminators for wire compatibility (`dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowEvent.cs:11-18`). Versioned, no. No event class in either stack carries a schema-version field. The only version signal adjacent to events is the checkpoint envelope's `version: str = "1.0"` covering persisted pending `request_info` events (`python/packages/core/agent_framework/_workflows/_checkpoint.py:88`). Deprecation of the `data` event type is communicated via `DeprecationWarning` at construction time (`python/packages/core/agent_framework/_workflows/_events.py:288-294`) — a social, not mechanical, versioning mechanism.

**2. Are events ordered and timestamped?**
Ordering is real but implicit. Python preserves emission order through a FIFO `asyncio.Queue` (`python/packages/core/agent_framework/_workflows/_runner_context.py:315-341`) and list order in non-streaming `WorkflowRunResult(list[WorkflowEvent])` (`python/packages/core/agent_framework/_workflows/_workflow.py:101`); the runner interleaves live draining with iteration progress using a 50 ms poll timeout (`python/packages/core/agent_framework/_workflows/_runner.py:107-114`). .NET relies on channel FIFO semantics with epoch-guarded halt signals to prevent stale completions confusing consumers (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:218-234`). Coarse ordering context comes from `iteration` (Python) and `StepNumber` (.NET) on superstep events. However, there are **no per-event sequence numbers and no timestamps** anywhere in the core schemas of either stack. Both appear only after translation in DevUI (`python/packages/devui/agent_framework_devui/_mapper.py:476-486`, `python/packages/devui/agent_framework_devui/models/_openai_custom.py:65-67`).

**3. Do events carry sufficient context?**
Partially. Events identify their producing executor (`executor_id` at `python/packages/core/agent_framework/_workflows/_events.py:209`; `dotnet/src/Microsoft.Agents.AI.Workflows/ExecutorEvent.cs:15`), correlate HITL requests (`request_id` + `source_executor_id` at `python/packages/core/agent_framework/_workflows/_events.py:211-212`), attribute origin (framework vs user code, `python/packages/core/agent_framework/_workflows/_events.py:203,224`), and carry structured failures including traceback and executor id (`python/packages/core/agent_framework/_workflows/_events.py:74-78`). What they do **not** carry: run IDs, session IDs, workflow instance IDs, wall-clock timestamps, or span/trace IDs. The workflow instance UUID exists (`python/packages/core/agent_framework/_workflows/_workflow.py:329`) and the .NET `SessionId` exists (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:71-72`), but both are attached only to OpenTelemetry spans, so reconstructing which events belong to which run requires joining against external trace infrastructure rather than reading the event stream.

**4. Are lifecycle events comprehensive?**
Mostly, with two material gaps. Covered: creation (`started`, Python `python/packages/core/agent_framework/_workflows/_workflow.py:530`; .NET `dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:108`), progress/status transitions (`status` events mirroring a 7-state machine, `python/packages/core/agent_framework/_workflows/_events.py:58-67`), failure (`failed` with structured details, `python/packages/core/agent_framework/_workflows/_workflow.py:606-619`; `WorkflowErrorEvent`, `dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:168`), executor-level invoked/completed/failed in both stacks, and replay bypass bookkeeping (`executor_bypassed`, `python/packages/core/agent_framework/_workflows/_functional.py:518`). Gaps: (a) **cancellation** — Python's `CANCELLED` state is never emitted (only read defensively at `python/packages/core/agent_framework/_workflows/_workflow_executor.py:627`), and .NET cancellation terminates streams silently via token cancellation (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:238-241,300`); (b) **completion as a public event** — .NET signals completion only through the internal `InternalHaltSignal` filtered from consumers (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:228-259`); callers infer completion from stream termination plus `GetStatusAsync()` polling, whereas Python exposes an explicit terminal `status(IDLE)` event.

## Architectural Decisions

1. **Unified discriminated event type (Python) vs class hierarchy (.NET).** Python deliberately mirrors its `Content` class pattern — one generic class, many factory methods, one Literal discriminator (`python/packages/core/agent_framework/_workflows/_events.py:147-154`) — making event sets extensible without breaking imports. .NET follows idiomatic nominal typing with polymorphic JSON (`dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowEvent.cs:11-18`). Consequence: cross-stack parity is maintained by convention, not by a shared contract; the .NET hierarchy has no public `status`/completed event analog to Python's `status(IDLE)` stream event.
2. **Control plane separated from data plane in results.** Non-streaming runs strip `started` (telemetry-only) and divert `status` events into a dedicated timeline accessible via `status_timeline()`/`get_final_state()`, keeping the main event list data-only unless `include_status_events=True` (`python/packages/core/agent_framework/_workflows/_workflow.py:838-863`).
3. **Origin attribution via context variable.** Rather than threading an origin flag through every call site, framework code wraps emissions in `_framework_event_origin()` and the ContextVar default attributes everything else to EXECUTOR (`python/packages/core/agent_framework/_workflows/_events.py:38-55`) — cheap, correct attribution without API churn.
4. **Push-based streaming over pull-based storage.** Python queues events immediately (`add_event` docs: "stream them in real time instead of waiting for superstep boundaries", `python/packages/core/agent_framework/_workflows/_runner_context.py:315-321`) and .NET uses an unbounded channel so producers never block (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:37-44`). Events are transient delivery vehicles, not durable records — only pending `request_info` events survive into checkpoints.
5. **Type-safe accessors over nullable-field sprawl (Python).** Type-specific payloads use private fields behind raising properties (`python/packages/core/agent_framework/_workflows/_events.py:348-406`), converting misuse into loud runtime errors.
6. **Boundary filtering as policy, not convention.** The `AGENT_FORWARDED_EVENT_TYPES` frozenset centralizes which event classes leak across the workflow→agent abstraction boundary (`python/packages/core/agent_framework/_workflows/_events.py:133-143`), preventing diagnostic/lifecycle noise from reaching agent consumers.

## Notable Patterns

- **Factory-method construction discipline:** every lifecycle event has exactly one constructor path (`WorkflowEvent.started()`, `.status()`, `.failed()`, etc., `python/packages/core/agent_framework/_workflows/_events.py:255-342`), keeping field usage consistent per event type.
- **Deep-copy capture of inputs:** `executor_invoked` snapshots the pre-handler message via `copy.deepcopy` so post-mutation handler state cannot falsify the event record (`python/packages/core/agent_framework/_workflows/_executor.py:274-277`).
- **Failure-event draining before propagation:** on exception the workflow first drains queued events (so `executor_failed` surfaces before the run-level `failed` event) and then re-raises (`python/packages/core/agent_framework/_workflows/_workflow.py:606-615`; same discipline in the runner at `python/packages/core/agent_framework/_workflows/_runner.py:122-130`) — preserving causal order under failure.
- **Epoch-guarded stream consumption (.NET):** consumers snapshot `_completionEpoch` and ignore stale halt signals, avoiding race conditions where buffered completions from prior iterations end new streams prematurely (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:217-234`).
- **Handled-response suppression:** `request_info` events for which responses were provided up-front are withheld from the caller-visible stream (`python/packages/core/agent_framework/_workflows/_workflow.py:821-830`) — an event-stream-level idempotency nicety.
- **Presentation-layer enrichment:** DevUI wraps raw events into protocol objects adding `sequence_number` (per-stream counter) and `created_at` (Unix timestamp) (`python/packages/devui/agent_framework_devui/_mapper.py:200,422,476-486`).

## Tradeoffs

- **Transient events vs durable audit log.** Because events live in queues/channels and only pending requests are checkpointed, a crash loses all lifecycle history except what OTel captured. Reconstruction across restarts is impossible from events alone (`python/packages/core/agent_framework/_workflows/_checkpoint.py:81` persists only `pending_request_info_events`). This keeps the hot path fast but sacrifices forensic value.
- **Implicit ordering vs explicit sequencing.** FIFO transport gives correct in-process ordering for free, but downstream consumers cannot detect drops, duplicates, or reorderings — there is no sequence number to check (`python/packages/core/agent_framework/_workflows/_events.py:194-234` shows the full field list; no seq). The DevUI counter is per-connection and resets (`python/packages/devui/agent_framework_devui/_mapper.py:461`), so it cannot serve as a global ordering guarantee.
- **Unified class flexibility vs exhaustiveness.** Python's single-class-plus-Literal design makes adding event types easy but means the compiler cannot force handling of every case in consumer `match` statements the way a sum type would; unknown-type tolerance depends on each consumer.
- **OTel-based correlation vs self-contained events.** Keeping run/span linkage out of events avoids bloating every object and duplicating trace context, but makes event streams unusable offline without exported traces (`python/packages/core/agent_framework/_workflows/_workflow.py:512-522`; `dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:70-72`).
- **Silent cancellation vs cancellation events.** Token-based cancellation is simple and prompt, but consumers observing a stream end cannot distinguish "completed", "cancelled", and "crashed" without consulting out-of-band state (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:238-241` vs the Idle/Ended statuses at `:248-256`).

## Failure Modes / Edge Cases

- **Cancelled runs leave no trace in the event stream (both stacks).** A cancelled Python workflow propagates `CancelledError` through `_run_workflow_with_tracing`'s `except Exception` — note `asyncio.CancelledError` does not inherit from `Exception` in Python 3.8+, so even the `failed` event may not fire; `CANCELLED` status is never yielded. In .NET, `OperationCanceledException` during shutdown is swallowed as "expected" (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:142-145`).
- **Stale buffered events after checkpoint restore (.NET).** Restoring a checkpoint discards all buffered channel events because they belong to a superseded timeline (`ClearBufferedEvents`, `dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:283-295`) — correct, but it means event continuity across restore depends entirely on re-emitted `RepublishPendingEventsAsync` output (`:64-66`).
- **Malformed serialized events fail loudly:** `from_dict` raises `KeyError` on missing fields and `TypeError` on request-data/type mismatch (`python/packages/core/agent_framework/_workflows/_events.py:428-448`); accessing `request_id` on a non-request_info event raises `RuntimeError` (`:359-361`).
- **Serialization asymmetry:** `to_dict()` works only for `request_info` events and raises `ValueError` otherwise (`python/packages/core/agent_framework/_workflows/_events.py:417-418`) — lifecycle events cannot be persisted or replayed from their own schema.
- **Unbounded event buffering:** the .NET unbounded channel guarantees producers never block (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:37-39`), meaning a slow/stalled consumer accumulates unbounded memory during long supersteps.
- **Missing-status edge:** `get_final_state()` raises if no status event was emitted, forcing entry-point usage rather than returning a guess (`python/packages/core/agent_framework/_workflows/_workflow.py:149-160`).
- **Convergence failure is exception-only:** exceeding max iterations raises `WorkflowConvergenceException` (`python/packages/core/agent_framework/_workflows/_runner.py:152-153`) which flows into the standard failed-event path — no distinct lifecycle type distinguishes "diverged" from "crashed".

## Future Considerations

- Add optional `timestamp` and monotonically increasing `sequence_number` fields to the core event schemas in both stacks; the DevUI mapper already demonstrates the demand and the mechanics (`python/packages/devui/agent_framework_devui/_mapper.py:476-486`).
- Stamp events (or at least lifecycle events) with run/session identifiers, mirroring what is currently placed only on telemetry activities (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:71-72`).
- Introduce a public cancellation lifecycle event and emit `status(CANCELLED)` on the Python side; today the enum value is dead code (`python/packages/core/agent_framework/_workflows/_workflow_executor.py:627-631`).
- Promote .NET completion from the internal `InternalHaltSignal` to a public terminal event (or document stream-end + `RunStatus` polling as the contract) for parity with Python's explicit `status(IDLE)` (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs:332-336`).
- Generalize `to_dict`/`from_dict` beyond `request_info` events, and fold event payloads under the checkpoint envelope's existing `version` field so future schema evolution has a migration hook (`python/packages/core/agent_framework/_workflows/_checkpoint.py:88`).
