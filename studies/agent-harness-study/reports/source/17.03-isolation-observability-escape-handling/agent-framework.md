## Summary

`agent-framework` treats isolation as a tiered deployment choice rather than a unified observable-control plane. Shell and code execution are split across three tiers: `LocalShellTool` (host subprocess, no isolation, approval-gated), `DockerShellTool` (OCI container with hardened defaults), and `HyperlightCodeActProvider.execute_code` (WASM microVM, no kernel/shell). Each tier has distinct observability, but none provides a first-class sandbox audit log, escape-attempt taxonomy, or operator alerting. The strongest “policy violation” machinery lives in the experimental FIDES `PolicyEnforcementFunctionMiddleware` (integrity/confidentiality labeling) with an in-memory `audit_log` and `logger.warning` — unrelated to container/microVM breakout. Shell-level filtering via `ShellPolicy` is explicitly documented as a UX pre-filter, not a security boundary, with no default denylist and enumerated trivial bypasses. Escape prevention relies on construction-time flag blocking (`_BLOCKED_EXTRA_RUN_FLAGS` in `DockerShellTool`) and Hyperlight/Monty microVM boundaries, not runtime detection. Observability reuses the global OpenTelemetry layers (`AgentTelemetryLayer`/`ChatTelemetryLayer`/`FunctionTool` telemetry) and per-command `ShellResult` metrics plus an optional `on_command` callback that callers must wire to a SIEM. The answer to “would the system know if an agent tried to escape?” is: only if the operator built it — the framework logs the attempt as a normal tool call/command, blocks known bad Docker flags at init time, and otherwise trusts the container runtime or microVM.

## Rating

**Rating: 4 / 10**

Present but inconsistent, weakly documented, and fragile for the dimension. Isolation primitives are concrete (Docker hardened flags, Hyperlight microVM, tool-registry allow-lists), yet sandbox actions lack structured audit logs, policy-violation detection is confined to FIDES data-flow labels (not isolation escapes), escape- monitoring is limited to a static Docker arg blocklist with no runtime breakout detection, and alerting is `logger.warning` + a user-supplied `on_command` hook — no alerting rules, thresholds, or escalation paths. The framework’s own docs/tests state that `ShellPolicy` is not a boundary.

## Answers to Dimension Questions

**1. Are sandbox actions observable?**
Partially. Every command produces a structured `ShellResult` (`stdout`/`stderr`/`exit_code`/`duration_ms`/`truncated`/`timed_out`) and, when wired via `FunctionTool`, inherits the framework-wide OpenTelemetry traces (`AgentTelemetryLayer`/`ChatTelemetryLayer`/`FunctionTool` span + histogram) (`python/packages/core/agent_framework/observability.py:78-92`, `python/packages/core/tests/core/test_tools.py:525-556`; `docs/decisions/0024-codeact-integration.md:169`). For audit, both shell tools expose an `on_command: Callable[[str],None]` hook fired for every policy-allowed command with `logger.exception` on hook failure (`python/packages/tools/agent_framework_tools/shell/_tool.py:251-255`, `python/packages/tools/agent_framework_tools/shell/_docker.py:452-456`), and persistent sessions emit `logger.info` on container start (`python/packages/tools/agent_framework_tools/shell/_docker.py:626-630`) and `logger.warning/error` on kill/rm failures (`python/packages/tools/agent_framework_tools/shell/_docker.py:542-571`, `python/packages/tools/agent_framework_tools/shell/_docker.py:657-673`). There is no out-of-the-box structured audit log, SIEM sink, immutable store, or per-user sandbox trail — operators must implement `on_command` + log aggregation themselves. No evidence found of a central sandbox audit service, log retention policy, or queryable audit index.

**2. Are policy violations detected?**
Two distinct mechanisms, neither covering sandbox escapes: (a) `ShellPolicy` (`python/packages/tools/agent_framework_tools/shell/_policy.py:70-121`) evaluates allow/deny regex + custom callback **before approval/execution** and raises `ShellCommandError` (`python/packages/tools/agent_framework_tools/shell/_tool.py:248-250`). It is *explicitly not* a security boundary, ships with no patterns, and is documented as trivially bypassable (`python/packages/tools/tests/test_security.py:124-164`); (b) `PolicyEnforcementFunctionMiddleware` (`python/packages/core/agent_framework/security.py:1681-1836`) enforces FIDES integrity/confidentiality labels (untrusted-context + `max_allowed_confidentiality`) and records each violation via `_log_violation` to an in-memory `audit_log` plus `logger.warning` (`python/packages/core/agent_framework/security.py:1904-1913`). No detector correlates shell/container escapes, filesystem jailbreaks, or network egress with a policy engine. Shell bypasses and Docker flag mutations are caught only at policy-evaluation or construction time, not as runtime violation events.

**3. Are escape attempts handled?**
Preventively, not detectively. `DockerShellTool` hardens the container (`--network none`, `--user 65534:65534`, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--read-only`, `pids/memory caps` — `python/packages/tools/agent_framework_tools/shell/_docker.py:174-199`) and *rejects at construction* any `extra_run_args` that would dismantle those defaults via `_BLOCKED_EXTRA_RUN_FLAGS` (`python/packages/tools/agent_framework_tools/shell/_docker.py:73-125`, validated in `python/packages/tools/tests/test_docker_shell_tool.py:144-170`). Hyperlight CodeAct declares “model-generated code is treated as untrusted… the selected backend provides the primary isolation boundary” (`docs/decisions/0024-codeact-integration.md:24`) and runs in a WASM microVM with no kernel/shell (`python/packages/tools/README.md:167-171`). Persistent shell sentinels use per-call random `secrets.token_hex(4)` suffixes so the model cannot spoof completion (`python/packages/tools/agent_framework_tools/shell/_session.py:211-212`). No evidence found of runtime escape monitoring (syscall filtering alerts, container breakout detection, seccomp violations, anomalous mount/privilege escalation traps), kill-on-escape, or post-escape forensic capture. `LocalShellTool` explicitly has *no* handling — docs say to use a sandboxed tier instead.

**4. Are violations alerted to operators?**
No dedicated alerting. Violations surface as (i) `logger.warning("Policy violation detected: …")` and `logger.warning("BLOCKED: …")` in `PolicyEnforcementFunctionMiddleware` (`python/packages/core/agent_framework/security.py:1913`, `python/packages/core/agent_framework/security.py:1771-1775`), (ii) `logger.warning/error` from Docker lifecycle failures, (iii) whatever the consumer does inside `on_command`. There are no alerting rules, severity routing, paging/webhook integration, SIEM schema, or threshold/correlation configuration in the studied source. The `audit_log` is an in-process list returned by `get_audit_log()` (`python/packages/core/agent_framework/security.py:1915-1922`) — not persisted, not exported via OTel, not tied to an alert. OpenTelemetry spans/metrics can be forwarded if the operator configures `OTEL_EXPORTER_OTLP_*`, but no isolation-specific alert is defined there.

## Architectural Decisions

- **Tiered isolation by executor, not by policy engine.** The framework offers `ShellExecutor` protocol (`python/packages/tools/agent_framework_tools/shell/_executor_base.py:40-65`) with two concrete executors (host vs container) and a separate CodeAct microVM lane, letting the caller choose the trust boundary per tool instance rather than enforcing a global sandbox. Tradeoff: flexibility and provider-agnosticism at the cost of no uniform audit/escape contract.
- **Empty-by-default `ShellPolicy` to avoid false safety.** Deliberate decision to ship no regex denylists after surveying peer frameworks (`python/packages/tools/agent_framework_tools/shell/_policy.py:23-29`; docstring citing LangChain/AutoGen/OpenAI SDK removals). Violations only exist if the operator supplies patterns; otherwise every non-empty command is allowed (`python/packages/tools/agent_framework_tools/shell/_policy.py:109-121`).
- **Approval-in-the-loop as the host-tier boundary for `LocalShellTool`.** Requires `approval_mode="always_require"` by default and `acknowledge_unsafe=True` to disable (`python/packages/tools/agent_framework_tools/shell/_tool.py:157-165`), validated by `python/packages/tools/tests/test_security.py:99-113`. For `DockerShellTool`, `never_require` is allowed without ack because the container is deemed the boundary (`python/packages/tools/agent_framework_tools/shell/_docker.py:318-320`).
- **FIDES experimental security as data-flow labels, not container isolation.** `PolicyEnforcementFunctionMiddleware` + `LabelTrackingFunctionMiddleware` + `SecureAgentConfig` implement taint/confidentiality propagation for prompt-injection defense, with optional `approval_on_violation` (`python/packages/core/agent_framework/security.py:1560-1620`, `python/packages/core/agent_framework/security.py:1928-2010`). Not wired to shell/container telemetry.
- **Randomized sentinel + persistent reader tasks for stateless-faithful shell sessions.** Mitigates protocol spoofing and stream interleaving bugs (`python/packages/tools/agent_framework_tools/shell/_session.py:83-89`, `python/packages/tools/agent_framework_tools/shell/_session.py:384-409`).

## Notable Patterns

- **Opt-in observability via callback, not built-in sink:** `on_command` hook pattern in both shell tools makes audit pluggable but also optional — identical to middleware `on_command`-as-Siem bridge; no default file/OTel span.
- **Construction-time isolation validation:** Docker escape prevention happens once in `__init__` (`_validate_extra_run_args`) rather than per-command, so runtime tampering of container flags must be via the dedicated constructor args (`network`, `user`, `memory`, etc.) — documented as the safe override path.
- **Per-run snapshotting for CodeAct:** Provider snapshots tool registry, mounts, domains, and approval mode per `execute_code` invocation (`python/packages/hyperlight/agent_framework_hyperlight/_execute_code_tool.py:55-87`), isolating concurrent runs but also isolating violation context per run.
- **Single-session ownership everywhere:** `ShellSession`, `ShellExecutor`, `DockerShellTool`, and `LocalShellTool` all declare “owned by exactly one conversation / one user” (`python/packages/tools/agent_framework_tools/shell/_session.py:11-19`, `python/packages/tools/agent_framework_tools/shell/_executor_base.py:15-30`, `python/packages/tools/agent_framework_tools/shell/_docker.py:27-40`). Prevents cross-tenant leakage but pushes multi-tenant isolation to the deployer.

## Tradeoffs

- **Regex pre-filter vs robust filter:** Choosing no defaults avoids “security theater” but forces every operator to reinvent denylists; tests prove denylists remain bypassable via obfuscation (`python/packages/tools/tests/test_security.py:152-164`), so the gap is honest but unresolved.
- **Pluggable audit vs mandatory audit:** `on_command` avoids opinionated storage/retention and keeps the tool dependency-free, but guarantees many deployments will have zero sandbox logs unless they add one — the opposite of secure-by-default for observability.
- **Container as boundary vs kernel-level telemetry:** Relying on Docker’s `no-new-privileges`/`cap-drop`/`read-only` is strong for the threat, but without runtime detection, a zero-day breakout or misconfigured `podman`/`docker` daemon produces no signal in the framework.
- **FIDES audit_log vs process audit:** The only structured violation store (`audit_log`) tracks data-flow policy, not shell/container behavior — two observability planes that do not join, so a shell escape driven by tainted content would appear in neither or only one.

## Failure Modes / Edge Cases

- **Silent `on_command` failure:** Hook exceptions are caught and logged (`logger.exception`) but not propagated or counted (`python/packages/tools/agent_framework_tools/shell/_tool.py:254-255`); an audit pipeline outage looks like success to the agent.
- **`extra_run_args` blocklist is substring-flag, not semantic:** Only flags starting with “-” are checked, and only the prefix before “=” is matched (`python/packages/tools/agent_framework_tools/shell/_docker.py:111-117`); a non-flag positional payload or a novel isolation-relevant flag not in the 18-entry tuple would pass. No runtime re-validation after `build_run_argv`.
- **Policy bypass via shell expansion:** Documented bypasses (`\r\m -rf /`, `${RM:=rm} -rf /`, `python -c "import os;os.system(...)"`, base64/printf smuggling — `python/packages/tools/agent_framework_tools/shell/_policy.py:15-21`) are not detected and still execute if approval was granted.
- **Timeout teardown leaks:** If `docker kill` or `docker rm -f` hangs/returns non-zero, stateless and persistent paths fall back and ultimately `logger.error` that the container may be leaked and require manual cleanup (`python/packages/tools/agent_framework_tools/shell/_docker.py:522-572`, `python/packages/tools/agent_framework_tools/shell/_docker.py:654-673`; `python/packages/tools/agent_framework_tools/shell/_session.py:269-290`). No health-check reconciler.
- **Sentinel overflow recovery loses output:** `_SentinelOverflow` triggers interrupt + `close()` and returns truncated `ShellResult` with `truncated=True` (`python/packages/tools/agent_framework_tools/shell/_session.py:291-307`); the next call gets a fresh subprocess, but the overflow cause (runaway output) is not alerted as a violation.
- **In-memory `audit_log` loss:** Process crash or `clear_audit_log()` discards evidence; no persistence, rotation, or export (`python/packages/core/agent_framework/security.py:1923-1925`).
- **Missing `context_label` ⇒ silent pass:** If `LabelTrackingFunctionMiddleware` is not first, `PolicyEnforcementFunctionMiddleware` logs a warning and calls `await call_next()` with no check (`python/packages/core/agent_framework/security.py:1703-1710`), failing open.

## Future Considerations

- Add a mandatory structured audit event for every sandbox invocation (timestamp, session/user, command hash, `ShellPolicy` decision, approval outcome, `ShellResult` summary, container id) and ship a default `OTel span` for `LocalShellTool`/`DockerShellTool`/`execute_code` rather than relying on the optional `on_command` + generic `FunctionTool` telemetry. Define a stable event schema for SIEM ingestion.
- Introduce an isolation-escape detector interface (e.g., `on_escape_attempt` signal from Docker/Hyperlight) wired to `logger.warning` + `audit_log` + optional `approval_on_violation` style approval request, plus a persisted alert sink (OTel log record or webhook) — currently only construction-time `ValueError` exists.
- Unify FIDES `audit_log` with shell audit by joining `context_label` + `ShellRequest`/`ShellResult` into a single violation record, and persist it via an `AgentSession`-backed store or OTel log exporter instead of an in-process list.
- Consider a “default audit logger” (e.g., `logging.getLogger("agent_framework.shell.audit")` with JSON formatter) enabled out-of-the-box so deployments without `on_command` still produce searchable sandbox logs, while keeping `on_command` as the enrichment hook.
- Extend `DockerShellTool` tests and docs to cover Podman/rootless, daemon-not-available, and leaked-container reconciliation playbooks; add an integration test that asserts a flagged escape try (`--privileged`) emits an auditable event, not just a `ValueError`.
- Document the `isolation_key`/`x-agent-*-isolation-key` session scoping (`docs/specs/002-python-hosting-channels.md:21-88`) as explicitly *not* a sandbox — current naming invites conflation with execution isolation.
