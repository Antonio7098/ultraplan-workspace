## Summary

OPA is not an agent harness with OS-level sandboxes; its "sandbox" is the Rego evaluation engine and plugin host. Observability is achieved through comprehensive decision logging, status reporting, metrics, tracing, and structured server logging rather than kernel/container escape detection. Every policy decision can be emitted as a structured `EventV1` containing decision ID, bundles, input/result, error, metrics, request context, and custom fields, routed to console, remote HTTP service (`/logs`), or a custom `Logger` plugin (`v1/plugins/logs/plugin.go:38-76`, `v1/plugins/logs/plugin.go:715-821`). The `http.send` builtin is the primary explicit escape vector from pure evaluation; it is confined via `Capabilities.AllowNet` (`v1/ast/capabilities.go:94-101`, `v1/topdown/http.go:374-400`) and also via Wasm ABI versioning. Policy "violations" are modeled as deny decisions (data-dependent), not centrally detected exceptions, but errors, requeue failures, and resource-limit breaches are detected and counted. Violations do not trigger operator alerts directly — they propagate as decision-log upload status (`v1/plugins/logs/status/status.go:22-51`) into the status plugin (`v1/plugins/status/plugin.go:312-315`, `v1/plugins/status/plugin.go:395-405`) which then pushes to a status service, console, or Prometheus, leaving alerting to external systems. There is no syscall/seccomp/nsenter/container-escape monitor because OPA does not claim an agent sandbox boundary.

## Rating

**7 / 10** — Clear, tested observability model for the actual isolation boundary OPA provides (policy evaluation). Decision logs, status forwarding, metrics counters, and AllowNet confinement are explicit, interfaced, and exercised by tests. Downgraded from 9-10 because (a) the "sandbox" is language/builtin-level, not OS-level, so classic escape-attempt monitoring (syscall anomalies, filesystem breakout) is absent and not applicable, and (b) there are no built-in alerting rules/webhooks — alerting is delegated to downstream consumers of status/metrics.

## Answers to Dimension Questions

### 1. Are sandbox actions observable?
**Yes — thoroughly for the policy-evaluation boundary.** Every decision is reified as `EventV1` (`v1/plugins/logs/plugin.go:49-76`) with decision_id, path/query, input/result, bundles, revision, timestamps, metrics, request context, and custom fields. The event is generated inside `Plugin.Log` (`v1/plugins/logs/plugin.go:715-821`) from `server.Info` (which itself is built with `DecisionIDFromContext` at `v1/server/server.go:3134`) and then (a) masked/dropped via Rego (`v1/plugins/logs/plugin.go:1048-1141`), (b) optionally logged to console as structured JSON (`v1/plugins/logs/plugin.go:1164-1171`, `v1/plugins/logs/plugin.go:1295-1371`), (c) buffered (`v1/plugins/logs/plugin.go:466-473`) and reliably uploaded (`v1/plugins/logs/plugin.go:1143-1162`) with retry/backoff (`v1/plugins/logs/plugin.go:902-961`), and (d) forked to a custom `Logger` plugin (`v1/plugins/logs/plugin.go:800-821`). Server-wide observability is complemented by `logging` (`v1/logging/logging.go:30-40`), `tracing` (`v1/tracing/tracing.go:30-54`), and `metrics` (`v1/metrics/metrics.go:51-60`). There is no OS-level syscall audit because the sandbox is not an OS container — observability is at the decision-API layer, which is the correct abstraction for OPA.

### 2. Are policy violations detected?
**Partially — by design, "violation" is a data-plane concept, not a control-plane alarm.** OPA distinguishes three outcomes: `allow`/`deny` (normal results in `Result`), `undefined` (no rule matched), and evaluation `Error` (`v1/plugins/logs/plugin.go:66`, `v1/plugins/logs/plugin.go:781-783`). A policy that denies access still produces a regular result; detection of the violation is the caller's responsibility to evaluate `result`. Evaluation errors (type errors, undefined builtins) are surfaced as `EventV1.Error` and as bundle-status errors (`v1/plugins/status/plugin.go:41-48`). Resource/contention violations are detected as rate-limit drops (`decision_logs_dropped_rate_limit_exceeded` at `v1/plugins/logs/plugin.go:274`), buffer-size drops (`v1/plugins/logs/plugin.go:275-276`), and encoding failures (`v1/plugins/logs/plugin.go:277`). There is no standalone "policy violation detector" that pages an operator when `allow == false` — that would be application logic built on top of decision logs.

### 3. Are escape attempts handled?
**Narrowly — the only modeled escape from pure evaluation is `http.send` (and Wasm interop), and it is confined via capabilities.** Verification is at `v1/topdown/http.go:374-400`: if `Capabilities.AllowNet != nil`, the requested host must be allowlisted; otherwise `unallowed host` error is returned and evaluation fails (or yields `{"error": {"code": "eval_http_send_network_error"}}` when `raise_error: false` at `v1/topdown/http.go:159-178`). Redirects are re-checked (`v1/topdown/http.go:667-670`). Wasm execution is gated by ABI version (`v1/ast/capabilities.go:88`, `capabilities.json`, `v1/version/wasm.go:9-11`) and by a `with`-statement guard (`v1/topdown/resolver.go:117`). There is no monitoring for container breakout, file-system traversal, or syscall anomalies — those threat models are out of scope for a library/policy-engine; the operational deployment (e.g., Envoy sidecar, Kubernetes) is expected to provide OS containment. No evidence of anomaly detection on attempted `http.send` to disallowed hosts beyond the immediate error.

### 4. Are violations alerted to operators?
**Indirectly — via status propagation, not via native alerting rules.** Decision-log upload failures call `setStatus` (`v1/plugins/logs/plugin.go:1373-1382`) which pushes `lstat.Status{Code: "decision_log_error", HTTPCode, Message}` (`v1/plugins/logs/status/status.go:32-51`) into the status plugin's `decisionLogsCh` (`v1/plugins/status/plugin.go:312-315`). The status plugin then emits an `UpdateRequestV1{DecisionLogs, Metrics, Plugins}` (`v1/plugins/status/plugin.go:41-48`, `v1/plugins/status/plugin.go:537-552`) to one or more sinks: remote `POST /status` (`v1/plugins/status/plugin.go:498-511`), console (`v1/plugins/status/plugin.go:554-568`), or Prometheus (`v1/plugins/status/plugin.go:570-596`). Counters for degraded delivery are incremented via `PushFIFO` (`v1/util/channel.go:13-27`) and visible in both logs and status snapshots (`v1/plugins/logs/plugin_test.go:1240-1478`). There are no embedded alerting rules (no webhook, pagerduty, slack, or severity routing) — alerting is left to the consumer of the status endpoint or metrics scrape. E2E tests assert the mapping from HTTP 500 to status code/message (`v1/plugins/logs/plugin_test.go:1148-1154`), proving the pipeline but also showing it stops at reporting.

## Architectural Decisions

- **Decision log as structured audit bus** (`v1/plugins/logs/plugin.go:49-76`, `v1/plugins/logs/plugin.go:715-821`): OPA treats every evaluation as an auditable event rather than sampling exceptions. This makes the "sandbox" fully observable at the API boundary and enables downstream SIEM/DW analysis. Tradeoff: volume, hence rate-limiting and size-bounded buffers (`v1/plugins/logs/plugin.go:283-293`).
- **Dual sinks + pluggable logger** (`v1/plugins/logs/plugin.go:304-317`, `v1/plugins/logs/plugin.go:800-821`): `service`, `console`, and `plugin` are orthogonal. Lets operators run air-gapped (console only), remote-only, or fan-out without forking. The `plugins.LoggerPlugin` → `slog.Handler` bridge (`v1/plugins/logs/plugin.go:824-847`, `v1/logging/logging.go:296-365`) provides forward-compatible extensibility.
- **Rego-native log governance** (`v1/plugins/logs/plugin.go:272-273`, `v1/plugins/logs/plugin.go:1048-1141`): Masking and dropping are themselves Rego queries (`/system/log/mask`, `/system/log/drop`) prepared once and invalidated on compiler update (`v1/plugins/logs/plugin.go:894-900`). This keeps PII/redaction policy versioned with other bundles instead of in operator YAML.
- **AllowNet as capability, not firewall** (`v1/ast/capabilities.go:94-101`, `v1/topdown/http.go:374-400`): Network egress is restricted at evaluation time by comparing the host against a static allowlist baked into capabilities. Simple, deterministic, and testable (`v1/topdown/net_test.go:165-195`), but coarse (host-level only, no path/port/payload inspection).
- **Status aggregation instead of inline alerting** (`v1/plugins/status/plugin.go:52-72`, `v1/plugins/logs/plugin.go:1373-1382`): Decision-log health is folded into a unified status update alongside bundles/discovery/plugins. Decouples delivery health from evaluation and reuses the same console/service/Prometheus plumbing. Means alerting requires external correlation.

## Notable Patterns

- **Validated, default-injected config builder** (`v1/plugins/logs/plugin.go:319-464`, `v1/plugins/logs/plugin.go:521-597`): `ConfigBuilder.WithBytes/WithServices/WithPlugins/WithTriggerMode.Parse()` validates mutual exclusivity of `buffer_size_limit_bytes` vs `max_decisions_per_second`, enforces min/max delays, clamps upload limits, and selects `size` vs `event` buffer. Prevents misconfiguration from silently degrading observability.
- **Two-level caching for http.send** (`v1/topdown/http.go:790-873`, `v1/topdown/http.go:1451-1486`): Intra-query `httpSendCache` (per-evaluation) and optional inter-query `InterQueryBuiltinCache` (insert-with-expiry, cache-control aware at `v1/topdown/http.go:1282-1280`). Observable via `counter`/`timer` metrics (`v1/metrics/metrics.go:22-43`, `v1/topdown/http.go:98-100`) and `tracing`.
- **Graceful degradation with explicit counters** (`v1/plugins/logs/plugin.go:274-277`, `v1/util/channel.go:13-27`, `v1/plugins/logs/plugin_test.go:1371-1478`): Buffer overflow and rate-limit drops are not silent; they increment `counter_decision_logs_dropped_*` and are asserted in status-update tests, giving operators a quantifiable signal that audit coverage was lost.
- **Compiler-triggered query invalidation** (`v1/plugins/logs/plugin.go:894-900`, `v1/plugins/logs/plugin.go:631`): `RegisterCompilerTrigger(plugin.compilerUpdated)` drops `preparedMask`/`preparedDrop`, ensuring log governance stays in sync with policy changes without restart.
- **Shutdown flush with deadline awareness** (`v1/plugins/logs/plugin.go:664-713`): On `Stop(ctx)` with deadline, attempts `flushDecisions` via 1s-retry loop; otherwise logs `Plugin stopped with decisions possibly still in buffer`. Exhibits durability reasoning often missing in ad-hoc loggers.

## Tradeoffs

- **Completeness vs volume**: Full decision capture (`v1/plugins/logs/plugin.go:49-76` includes input, result, bundles, metrics) is powerful for forensics but forces buffer sizing, compression, and rate-limit tradeoffs (`v1/plugins/logs/plugin.go:283-293`). Default `buffer_size_limit_bytes=0` (unlimited) and `upload_size_limit_bytes=32768` can be overwhelmed under burst.
- **In-band error reporting vs fail-closed**: Evaluation errors surface as `EventV1.Error` and status `decision_log_error` but do not fail the overall OPA process; bundles/status continue. This favors availability, but a silent misconfiguration in `allow_net` or masking policy could be missed if status consumers are not watched.
- **Host-level AllowNet vs fine-grained egress policy**: Simple to configure and verify (`v1/topdown/http.go:379`), but cannot restrict by URL path, method, or payload, and cannot distinguish confused-deputy via redirects except by re-checking host. Operators needing path-level confinement must do it outside OPA.
- **Periodic status vs real-time alert**: Status updates are debounced/batched (`v1/plugins/status/plugin.go:351-431`) and `PushFIFO` drops oldest on overflow (`v1/util/channel.go:13-27`). Good for throughput, but a burst of decision-log failures may coalesce or be dropped (`counter_status_dropped_buffer_limit_exceeded` at `v1/plugins/status/plugin.go:30`).

## Failure Modes / Edge Cases

- **Decision-log loss under backpressure**: If remote `/logs` is slow/5xx, `doOneShot` retries with exponential backoff (`v1/plugins/logs/plugin.go:915-924`) but drops new events when `buffer_size_limit_events/bytes` is exceeded (`v1/plugins/logs/plugin_test.go:1249-1369`) or when `max_decisions_per_second` is exceeded (`v1/plugins/logs/plugin_test.go:776-917`). Counters signal loss but audit gap is not recoverable.
- **Mask/drop query errors are swallowed**: `maskEvent`/`dropEvent` log `Log drop decision failed` / `Log event masking failed` at Error level and return `nil` (`v1/plugins/logs/plugin.go:767-788`) — the original decision is still logged (possibly unmasked) rather than failing the request. A buggy `/system/log/mask` could therefore leak PII without failing evaluation.
- **Console fallback when service unset**: `ParseConfig` returns `nil` config when no service/plugin/console configured (`v1/plugins/logs/plugin.go:587-590`), causing decision logs to be silently disabled. No warning is emitted at parse time; callers must ensure at least one sink.
- **AllowNet nil vs empty confusion**: `AllowNet == nil` means allow any host; `AllowNet == []` means deny all (`v1/topdown/http.go:374-384`). Tests at `v1/topdown/net_test.go:165-195` document this, but operator YAML with `allow_net: []` could accidentally deny all `http.send` calls and break policy that depends on external data.
- **Redirect allowlist bypass risk if AllowNet changes mid-request**: Verification is per-request (`v1/topdown/http.go:459-462`, `667-670`); if capabilities are reloaded mid-flight, in-progress evaluations still use the capabilities snapshot from `BuiltinContext`, which is correct but could be surprising if operators expect immediate revocation.
- **Status channel drops**: `statusBufferLimit = 1` (`v1/plugins/status/plugin.go:28`) and `PushFIFO` pattern mean rapid status flaps can drop intermediate states; the final `snapshot()` (`v1/plugins/status/plugin.go:537-552`) reflects last-known, not full history.
- **Wasm + `with` incompatibility** (`v1/topdown/resolver.go:117`): Policies using `with` cannot be evaluated against Wasm-compiled bundles; error is emitted at evaluation time with no dedicated escape-alert metric, just a generic builtin error in `EventV1.Error`.

## Future Considerations

- **Add explicit egress audit field**: Include `http.send` attempts (allowed and denied) as structured fields or counters inside `EventV1`/`Metrics` (e.g., `counter_http_send_allow_net_denied`) so escape attempts are observable without parsing error strings. Current evidence requires matching `unallowed host: ...` at `v1/topdown/http.go:383`.
- **Alerting hook/plugin**: Introduce a status-consumer alert adapter (webhook with severity routing) or document recommended Prometheus alert rules for `decision_log_error` and `counter_decision_logs_dropped_*`. Today operators must build this externally (`v1/plugins/status/plugin.go:570-596` only exposes Prometheus gauges).
- **Per-decision trace linkage**: Decision logs already carry `trace_id`/`span_id` (`v1/plugins/logs/plugin.go:53-54`) populated from `server.Info`; ensure consistently set via `distributedtracing` (`internal/distributedtracing/distributedtracing.go:229-316`, `v1/tracing/tracing.go:30-54`) and extend to `http.send` spans so cross-service escape investigations can correlate.
- **Fine-grained egress policy**: Extend `AllowNet` to support CIDR, port, and path prefixes, or provide a Rego-native egress policy hook evaluated before `http.send`, enabling detection of confused-deputy and data-exfiltration attempts.
- **Durable audit guarantee option**: Add a fail-closed mode where `Plugin.Log` returns error to the server handler when buffering fails (today it returns `nil` after logging at `v1/plugins/logs/plugin.go:767-788`), for deployments that require no-audit-gap guarantees.

## Questions / Gaps

- No evidence of OS-level sandbox escape detection (seccomp audit, namespace breakout, file-system guard) — intentionally out of scope for OPA's threat model; confirmed by absence of `seccomp|namespace|seccomp` matches in `v1/` and only signal handling in `cmd/test.go:188`.
- No evidence of anomaly-based escape-attempt detection (e.g., frequency of `http.send` to disallowed hosts, payload entropy); `http.send` network error is treated as builtin error, not security event.
- No built-in alerting rule engine; whether `status` service is highly available or has its own retry/DLQ is deferred to operator infrastructure (`v1/plugins/status/plugin.go:498-511` does single POST without retried backoff visible in this file).
- Wasm evaluation observability beyond `traceWasm` (`v1/topdown/eval.go:318-319`) is minimal; no dedicated metrics for Wasm VM pool pressure (`internal/wasm/sdk/internal/wasm/pool.go:84-134` does have `wasm_pool_acquire` timer, but not surfaced as alertable threshold).
- Data-plane policy "violation" (deny) has no canonical `violation_detected` counter or alert — consumers must derive it from `Result` in decision logs; worth confirming whether sample policies ship with `violation` output convention.
