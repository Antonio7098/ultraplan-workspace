## Summary

OpenHands isolates agents in Docker or remote Kubernetes runtimes (gVisor default, sysbox optional) but observability of that isolation boundary is thin. Sandbox lifecycle is logged via structured `openhands_logger` (`openhands/app_server/utils/logger.py:379`) with JSON mode (`openhands/app_server/utils/logger.py:30`), sensitive-data redaction (`openhands/app_server/utils/logger.py:248`), and URL-param redaction (`openhands/app_server/utils/logger.py:549`), while agent actions are durably persisted as events (`openhands/app_server/event/event_service.py:61`, `openhands/app_server/event/event_service_base.py:190`) and exportable as trajectories (`openhands/app_server/app_conversation/app_conversation_service.py:161`, `openhands/app_server/app_conversation/live_status_app_conversation_service.py:2895`). This gives full audit of *what the agent did* inside the sandbox but almost no telemetry on the sandbox boundary itself: no syscall/seccomp/AppArmor audit, no filesystem breakout detection, no network-egress anomaly monitor. Runtime confinement is delegated to infrastructure: `runtime_class=gvisor` (`openhands/app_server/sandbox/remote_sandbox_service.py:1089`) or `sysbox-runc` (`openhands/app_server/sandbox/remote_sandbox_service.py:491`), `privileged=false` by default (`config.template.toml:341`), `init=True` for zombie reaping (`openhands/app_server/sandbox/docker_sandbox_service.py:498`). Policy-violation detection exists at the *action* layer via a defense-in-depth SDK stack — `SecurityAnalyzerBase` (`_sdk_inspect/sdk/security/analyzer.py:15`), `SecurityRisk` (`_sdk_inspect/sdk/security/risk.py:13`), `PatternSecurityAnalyzer` (`_sdk_inspect/sdk/security/defense_in_depth/pattern.py:140`), `PolicyRailSecurityAnalyzer` (`_sdk_inspect/sdk/security/defense_in_depth/policy_rails.py:147`), `EnsembleSecurityAnalyzer` (`_sdk_inspect/sdk/security/ensemble.py:22`) — catching `rm -rf`, `dd of=/dev/`, `mkfs`, `curl | bash`, injection overrides, with fail-closed `HIGH` on analyzer error (`_sdk_inspect/sdk/security/analyzer.py:108`, `_sdk_inspect/sdk/security/ensemble.py:84`). That gates execution via `ConfirmRisky`/`AlwaysConfirm`/`NeverConfirm` (`_sdk_inspect/sdk/security/confirmation_policy.py:27`, `openhands/app_server/app_conversation/app_conversation_service_base.py:677`) and an LLM-assessed `HIGH` for privileged ops (`_sdk_inspect/sdk/agent/prompts/security_risk_assessment.j2:17`) — but it is a *pre-execution* gate, not post-violation detection. Classic container-escape attempts (nsenter, cgroup escape, `/proc` breakout, host-network exfiltration) would not be detected or alerted; host-network mode is even warn-only (`openhands/app_server/sandbox/docker_sandbox_service.py:390`). Violations trigger log lines (`_logger.warning` at `openhands/app_server/sandbox/sandbox_service.py:209`, `openhands/app_server/sandbox/sandbox_service.py:229`) and UI confirmation, but there are no operator alerting rules, no Prometheus/Sentry/PagerDuty hooks, and dev compose explicitly runs `privileged: true` (`containers/dev/compose.yml:4`).

## Rating

**4 / 10** — Present but inconsistent and fragile. Agent-action audit (event persistence + trajectory export + JSON logging) and deterministic pre-execution policy rails are explicit, interfaced, and tested. Downgraded because (a) sandbox-boundary observability is limited to sparse lifecycle logs, not a structured audit bus; (b) escape handling is confined to action-pattern matching, with no syscall/filesystem/network escape monitor and with insecure defaults reachable (`host_network` warn-only, `privileged` toggle, `KVM` passthrough); (c) no violation-to-operator alert pipeline — HIGH risk only pauses for user confirmation, and sandbox `ERROR` only emits a warning log without metric or webhook.

## Answers to Dimension Questions

### 1. Are sandbox actions observable?
**Partially — agent actions are, sandbox boundary is not.** Every agent `ActionEvent` is persisted via `EventService` (`openhands/app_server/event/event_service.py:61`) with `FilesystemEventService`/`AwsEventService`/`GoogleCloudEventService` backends and is iterable for export (`openhands/app_server/event/event_service.py:48`, `openhands/app_server/app_conversation/app_conversation_service.py:161`). Sandbox lifecycle emits structured logs when `LOG_JSON=true` (`openhands/app_server/utils/logger.py:30`, `openhands/app_server/utils/logger.py:336`) with secret and URL-param redaction (`openhands/app_server/utils/logger.py:248`, `openhands/app_server/utils/logger.py:549`) and lifecycle warnings for error/timeout/assignment (`openhands/app_server/sandbox/sandbox_service.py:209`, `openhands/app_server/sandbox/sandbox_service.py:229`, `openhands/app_server/sandbox/remote_sandbox_service.py:510`, `openhands/app_server/app_conversation/live_status_app_conversation_service.py:956`). Observability metadata for LLM tracing is injected at conversation creation (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:1587`). What is *missing* is a dedicated sandbox audit log — there is no syscall trace, no containerd/Kubernetes audit event stream, no filesystem-change journal, and status is inferred via polling (`poll_agent_servers` at `openhands/app_server/sandbox/remote_sandbox_service.py:880`) rather than streamed. An operator can replay what the agent executed, but cannot answer "did the container touch `/proc` or open a raw socket" from first-party logs.

### 2. Are policy violations detected?
**Yes at the action layer, no at the isolation boundary.** The SDK security stack detects canonical violations before execution: `PatternSecurityAnalyzer` (`_sdk_inspect/sdk/security/defense_in_depth/pattern.py:140`) flags `rm -rf`/`mkfs`/`dd`/`eval`/`curl|sh`, `PolicyRailSecurityAnalyzer` (`_sdk_inspect/sdk/security/defense_in_depth/policy_rails.py:147`) catches composed `fetch-to-exec` and `catastrophic-delete` of `/`/`~`/`/etc`, `LLMSecurityAnalyzer` (`_sdk_inspect/sdk/security/llm_analyzer.py:10`) propagates the LLM's `security_risk`, and `EnsembleSecurityAnalyzer` (`_sdk_inspect/sdk/security/ensemble.py:22`) fail-closes to `HIGH` on error. Normalization (`_sdk_inspect/sdk/security/defense_in_depth/utils.py:310`) defeats zero-width/fullwidth evasion. App-server binds this to `confirmation_mode` via `_select_confirmation_policy` (`openhands/app_server/app_conversation/app_conversation_service_base.py:677`) and sets it on the agent-server over HTTP (`openhands/app_server/app_conversation/app_conversation_service_base.py:690`). What is *not* detected is a successful escape *after* execution — e.g., writing outside `/workspace`, escalating via `privileged` docker-in-docker, or exfiltrating via `host_network`. Those are policy-configurable toggles (`config.template.toml:341`, `openhands/app_server/sandbox/docker_sandbox_service.py:49`, `openhands/app_server/sandbox/docker_sandbox_service.py:59`) without runtime violation sensors.

### 3. Are escape attempts handled?
**Narrowly and pre-emptively, not as runtime escape containment.** `HIGH` risk forces user confirmation (`_sdk_inspect/sdk/security/analyzer.py:72`, `_sdk_inspect/sdk/security/confirmation_policy.py:53`) and blocks execution until confirmed; `MEDIUM` can be gated by `ConfirmRisky(threshold=MEDIUM)`. Supply-chain rules (`_sdk_inspect/sdk/agent/prompts/security_risk_assessment.j2:24`) escalate untrusted repo content that writes registry configs or adds lifecycle hooks. Delegated isolation via `gvisor`/`sysbox-runc` (`openhands/app_server/sandbox/remote_sandbox_service.py:491`, `openhands/app_server/sandbox/remote_sandbox_service.py:1089`) and non-privileged default (`config.template.toml:341`) provides kernel-boundary hardening, but OpenHands itself does not handle escape attempts with quarantine, kill, seccomp violation traps, or read-only rootfs — the Docker create in `openhands/app_server/sandbox/docker_sandbox_service.py:484` sets only `init=True`, `volumes`, and `network_mode` without `security_opt`, `cap_drop`, `read_only`, or `pids_limit`. A crafted `docker run --privileged` inside a `privileged=true` sandbox would succeed with only a warning log.

### 4. Are violations alerted to operators?
**No.** Violations surface as (a) an in-session confirmation dialog (`frontend/src/components/shared/risk-alert.test.tsx:3`, `frontend/src/components/features/alerts/alert-banner.tsx:26`) for the conversing user, and (b) `_logger.warning`/`_logger.exception` lines (`openhands/app_server/sandbox/sandbox_service.py:209`, `openhands/app_server/sandbox/remote_sandbox_service.py:143`) that land in `logs/openhands.log` or stdout JSON. There is no alerting pipeline: no status plugin forwarding `decision_log_error` as in OPA, no Prometheus counter for `security_risk=HIGH`, no webhook/PagerDuty/Slack hook, no severity routing. The answer to "would the system know if an agent tried to escape its sandbox?" is: it would know a user saw a confirmation prompt and an operator could `grep` logs, but no automated alert would fire and no SOC/operator dashboard is populated.

## Architectural Decisions

- **Event persistence as audit bus** (`openhands/app_server/event/event_service.py:18`, `openhands/app_server/event/event_service_base.py:32`): Abstract `EventService` with filesystem/S3/GCS backends makes every action durable and re-exportable as a trajectory zip. Trades local simplicity for operational burden — operators must configure `bucket_name` and lifecycle, and there is no bounded buffer/drop counter as in OPA's decision logs.
- **Pre-execution deterministic rails + LLM risk** (`_sdk_inspect/sdk/security/defense_in_depth/pattern.py:70`, `_sdk_inspect/sdk/security/defense_in_depth/policy_rails.py:68`, `_sdk_inspect/sdk/security/llm_analyzer.py:20`): Fast regex confinement without network call, complemented by LLM judgment. Keeps the hot path local but creates a double-source-of-truth (pattern vs LLM) that can disagree; `EnsembleSecurityAnalyzer` resolves via max-severity (`_sdk_inspect/sdk/security/ensemble.py:78`) rather than explicit conflict logging.
- **Delegated isolation to gVisor/sysbox** (`openhands/app_server/sandbox/remote_sandbox_service.py:1089`, `openhands/app_server/sandbox/remote_sandbox_service.py:491`): Leverages kernel-enforced sandbox instead of re-implementing seccomp/namespaces. Simplifies OpenHands code at the cost of visibility — escape telemetry, if any, lives in the runtime provider, not in OpenHands logs.
- **Redaction-first logging** (`openhands/app_server/utils/logger.py:248`, `openhands/app_server/utils/logger.py:549`): `SensitiveDataFilter` and `RedactURLParamsFilter` are installed on both `openhands_logger` and uvicorn handlers to prevent `session_api_key` and `llm_api_key` leakage. Correct for privacy but also masks the very values an escape investigation would need to correlate (keys are replaced with `******` without a correlation ID).
- **Workspace archive before delete** (`openhands/app_server/sandbox/remote_sandbox_service.py:731`, `openhands/app_server/sandbox/remote_sandbox_service.py:690`): Per-conversation `archive_workspace` before `delete_sandbox` preserves forensics even if the sandbox is reaped. Honor `archive_required()` to block delete — trades availability for durability.

## Notable Patterns

- **Two-corpus scanning** (`_sdk_inspect/sdk/security/defense_in_depth/pattern.py:5`, `_sdk_inspect/sdk/security/defense_in_depth/utils.py:75`): Executable fields (`tool_name`, `tool_call.arguments` leaves) vs text fields (`thought`, `reasoning_content`, `summary`) prevents `thought about rm -rf /` from triggering a shell-destructive alert while still catching injection in reasoning — a precise scope control rarely seen in ad-hoc guardrails.
- **Segment-aware rail evaluation** (`_sdk_inspect/sdk/security/defense_in_depth/policy_rails.py:68`): Per-segment (`_extract_exec_segments`) check prevents `thought: curl` + `tool: ls` from falsely firing `fetch-to-exec`; a flat-string check would false-positive.
- **Invisible-character normalization** (`_sdk_inspect/sdk/security/defense_in_depth/utils.py:310`, `_sdk_inspect/sdk/security/defense_in_depth/utils.py:244`): Compiled regex stripping ~200 zero-width/BIDI/C0/C1/variation-selector chars plus NFKC fullwidth folding before matching — hardened against Unicode evasion (informed by `navi-sanitize`).
- **Fail-closed ensemble** (`_sdk_inspect/sdk/security/ensemble.py:84`, `_sdk_inspect/sdk/security/analyzer.py:108`): Analyzer exception → `SecurityRisk.HIGH`; ensemble with `propagate_unknown` option — broken detector degrades to confirmation rather than silent allow.
- **Hard-cap extraction** (`_sdk_inspect/sdk/security/defense_in_depth/utils.py:41`, `_sdk_inspect/sdk/security/defense_in_depth/utils.py:85`): `_EXTRACT_HARD_CAP=30_000` bounds regex runtime/memory, explicitly documenting that content beyond the cap is invisible — a disclosed bypass ceiling.
- **Idempotent retry for runtime reads** (`openhands/app_server/sandbox/remote_sandbox_service.py:134`): `GET`/`HEAD` to runtime API retried once on `TimeoutException` — acknowledges pooled-DB stalls without blindly retrying mutations.

## Tradeoffs

- **Durability vs bounded audit**: Full event persistence guarantees replay but requires unbounded storage and Redis-locked export (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:153`, `openhands/app_server/app_conversation/live_status_app_conversation_service.py:2864`). No drop counter or rate limiter means burst agents can OOM the store rather than gracefully degrade with a `dropped` metric.
- **Privacy vs investigability**: Aggressive redaction (`openhands/app_server/utils/logger.py:248`) protects keys but removes the ability to correlate which `session_api_key` accessed which secret; session-key hashing (`openhands/app_server/sandbox/remote_sandbox_service.py:76`) is stored as SHA-256 but not emitted as a correlation ID in logs.
- **Delegated hardening vs observability**: Relying on `gvisor`/`sysbox` offloads kernel isolation but also offloads escape telemetry — OpenHands has no hook to ingest runtime seccomp violations or `dmesg` container-escape alerts, so the app-server logs under-report boundary health.
- **Warn-only toggles vs enforce**: `use_host_network` with `max_num_sandboxes > 1` only warns (`openhands/app_server/sandbox/docker_sandbox_service.py:390`), `privileged` is a config toggle (`config.template.toml:341`), and `KVM` passthrough is a boolean — operators can silently widen the attack surface without a policy gate.
- **Polling vs streaming**: `poll_agent_servers` (`openhands/app_server/sandbox/remote_sandbox_service.py:880`) syncs conversation state on `sleep_interval` (default 15s) with tight DB-session scoping; simple and robust for local dev but introduces detection lag and misses transient escape-relevant errors between polls.

## Failure Modes / Edge Cases

- **Hard-cap bypass**: Content beyond `_EXTRACT_HARD_CAP=30_000` (`_sdk_inspect/sdk/security/defense_in_depth/utils.py:41`) is silently truncated; a long obfuscated payload can push a `curl | sh` past the cap and evade detection — documented but unmitigated.
- **Host-network port collision as DoS**: With `use_host_network=true` and `max_num_sandboxes>1`, multiple sandboxes bind the same host ports (`openhands/app_server/sandbox/docker_sandbox_service.py:442`); only a warning is emitted, no admission control — sandbox start can fail with `APIError` and surface as generic `SandboxError` (`openhands/app_server/sandbox/docker_sandbox_service.py:515`).
- **Privileged dev escape**: `containers/dev/compose.yml:4` runs `privileged: true`; an agent executing `docker run --privileged` inside that container can break out to the host without triggering `PolicyRailSecurityAnalyzer` (which scans agent actions, not container capabilities).
- **Recursive `_walk_json_strings` fallback**: `RecursionError` on deeply nested `tool_call.arguments` falls back to scanning the raw JSON string (`_sdk_inspect/sdk/security/defense_in_depth/utils.py:106`); the fallback is correct but could reintroduce field-boundary confusion that segment-aware rails sought to avoid.
- **Cyrillic/combining-mark evasion**: `_normalize` (`_sdk_inspect/sdk/security/defense_in_depth/utils.py:310`) explicitly documents it does *not* cover Cyrillic homoglyphs or combining-mark evasion (deferred as xfails) — `rm` written with Cyrillic `r` would not match `\\brm\\b`.
- **Status loss on delete retry**: `RemoteSandboxService.delete_sandbox` invalidates `session_api_key_hash` then attempts `POST /stop`; on transient `HTTPError` it commits the invalidation but raises `SandboxDeleteRetryError` (`openhands/app_server/sandbox/remote_sandbox_service.py:646`) — the sandbox remains running but the key is already revoked, breaking the caller's transaction assumption.
- **Silent `privileged` enablement**: `config.template.toml:341` defaults `privileged=false` commented out; an operator un-commenting to `true` for docker-in-docker gets no runtime warning or metric, unlike the host-network path which at least warns.

## Future Considerations

- **Sandbox syscall/file audit stream**: Add a dedicated `sandbox_audit` event type (eBPF/seccomp or sidecar `falco` feed) with allowlisted syscalls and `workspace_root` confinement checks; surface as structured `EventKind.SANDBOX_VIOLATION` alongside existing `EventService` so trajectory export covers escapes without new infrastructure.
- **Egress confinement parity with OPA**: Introduce an `AllowNet`-style egress allowlist verified per `http.send`/`tool` network call (host + port + path) with per-request host verification and redirect re-check, plus `counter_http_send_allow_net_denied` in metrics.
- **Container security hardening at create**: Set `security_opt` (seccomp=RuntimeDefault), `cap_drop: [ALL]`, `cap_add: [NET_BIND_SERVICE]` only where needed, `read_only: true` with tmpfs for `/tmp`, `pids_limit`, `mem_limit` in `DockerSandboxService.start_sandbox` (`openhands/app_server/sandbox/docker_sandbox_service.py:484`); gate `privileged`, `use_host_network`, and `kvm_enabled` behind an explicit `SandboxSecurityPolicy` admission check that fails-closed instead of warn-only.
- **Alerting sink for HIGH/ERROR**: Extend `EventCallbackService` or add a `SecurityAlertPlugin` that on `SecurityRisk.HIGH` or `SandboxStatus.ERROR` emits a webhook/PagerDuty/Slack event and increments `counter_sandbox_escape_attempt` / `counter_policy_violation` Prometheus metrics; document recommended Prometheus alerts for `rate(counter_sandbox_escape_attempt[5m]) > 0`.
- **Correlation ID without secret leakage**: Emit a truncated `session_api_key_hash[:8]` as `sandbox_key_fingerprint` in JSON logs alongside lifecycle events so investigators can correlate without exposing the raw key.
