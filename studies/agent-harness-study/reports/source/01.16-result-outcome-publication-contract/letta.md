## Summary

Letta separates ephemeral work returns (`LettaResponse` from `AgentLoop.step/stream`) from the durable terminal outcome persisted as a `Run`/`Job` row. The work return is a Pydantic value object carrying `messages`, `stop_reason` (`LettaStopReason`), and `usage`; the terminal outcome is a DB-backed `Run` record with `RunStatus` (`created|running|completed|failed|cancelled`), `StopReasonType`, `completed_at`, `metadata` (including frozen `result: LettaResponse` dump and error payloads), and timing metrics. Publication occurs strictly through `RunManager.update_run_by_id_async` / `JobManager.update_job_by_id_async`, which merges metadata, writes terminal status inside an `async_session` transaction, then outside the transaction dispatches callbacks and releases Redis conversation locks. Consumers poll `GET /runs/{run_id}`, `GET /runs/{run_id}/messages|usage|steps`, or attach to a Redis SSE stream (`GET /runs/{run_id}/stream`). There is no first-class Future/Promise/Join handle — concurrency control relies on Redis locks + otid deduplication + SSE replay, not on an in-process promise. Diagnostics are summarized as stringified errors in `metadata["error"]` / `LettaErrorMessage.detail`; full tracebacks are logged but not durably attached to the terminal outcome. Immutability is advisory (log-error on re-transition) rather than enforced, and background path intentionally releases the lock before final DB commit, creating a narrow race window.

## Rating

**5/10**

Rationale: Work-return vs terminal-outcome types are cleanly distinct and consistently typed (Pydantic + enum exhaustiveness). Terminal status derives deterministically from `StopReasonType.run_status` and from streaming error branches. However publication lacks a formal immutable-commit barrier: no DB constraint preventing re-transition after terminal, no promise abstraction guaranteeing single publication + fan-out to concurrent/late waiters, no defensive copy/freeze of `LettaResponse` values, and error cause chains are truncated to `str(e)`. Concurrent access is mediated by Redis distributed lock (with intentional early release) rather than by an outcome-publication ordering guarantee, so waiter-release-before-visible-outcome is possible under race. Tests cover status transitions and cancellation idempotence but not cross-consumer publication ordering or late-waiter consistency.

## Answers to Dimension Questions

**1. Is a work return distinct from the runtime's terminal outcome?**
Yes, explicitly. The work return is `LettaResponse` (`letta/schemas/letta_response.py:52`, `letta/agents/letta_agent_v2.py:204` — fields `messages`, `stop_reason: LettaStopReason`, `usage`). The terminal outcome is the DB-persisted `Run` (`letta/schemas/run.py:17`, `letta/orm/run.py:22`) carrying `RunStatus` (`letta/schemas/enums.py:152`), `StopReasonType` (`letta/schemas/letta_stop_reason.py:9`), `completed_at`, `metadata`, `callback_*`, and timing metrics, plus `Job/BatchJob` (`letta/schemas/job.py:46`). Publication embeds the work return as `metadata["result"] = result.model_dump()` (`letta/services/run_manager.py:460`) so tools can answer dimension question 3: the two are never conflated as a bare `value|error` return.

**2. Which result, failure, cancellation, and runtime-fault combinations are valid?**
Runtime validates via canonical mapping `StopReasonType.run_status` (`letta/schemas/letta_stop_reason.py:24-49`): valid `RunStatus` values are only `created|running|completed|failed|cancelled` (`letta/schemas/enums.py:152-162`); `JobStatus` adds `pending|expired` (`letta/schemas/enums.py:133-149`). Combinations observed:
- Success: `RunStatus.completed` + `StopReasonType.end_turn|max_steps|tool_rule|requires_approval` + `LettaResponse` with messages/usage.
- Failure: `RunStatus.failed` + `StopReasonType.error|invalid_tool_call|no_tool_call|invalid_llm_response|llm_api_error|max_tokens_exceeded|context_window_overflow_in_system_prompt|insufficient_credits` + `metadata["error"]` / `LettaErrorMessage.detail`.
- Cancellation: `RunStatus.cancelled` + `StopReasonType.cancelled` + denial tool returns injected (`letta/services/run_manager.py:662-667`).
- Runtime fault: same as failure with `error_type` `stream_incomplete|stream_task_cancelled|internal_error|llm_timeout|llm_rate_limit` (`letta/services/streaming_service.py:617-774`, `letta/server/rest_api/redis_stream_manager.py:295-392`).
No cross-product where `failed` carries a valid `LettaResponse` messages — error paths still yield a `stop_reason` SSE chunk but `LettaResponse` is synthesized server-side, not from LLM. Invalid `completed+error` is prevented by mapping, but not by DB CHECK constraint.

**3. What happens when work returns both a value and an error?**
Letta never returns both simultaneously as a tuple. Blocking `AgentLoop.step` returns `LettaResponse` on success; on exception the router `except` sets `run_update_metadata={"error": str(e)}` and `run_status=failed` and re-raises HTTP 409/500 (`letta/server/rest_api/routers/v1/agents.py:1801-1810`). Streaming `_create_error_aware_stream` on error yields both a `LettaStopReason` chunk (`stop_reason=error|llm_api_error`) and an `event: error` chunk carrying `LettaErrorMessage` (`letta/services/streaming_service.py:652-773`) followed by `[DONE]`—so consumers see the failure diagnostic but do not receive a partial `LettaResponse` message list; the `result` in metadata is built from whatever messages were accumulated before failure, but `RunStatus.failed` signals consumers to ignore it. Background path synthesizes the same two chunks into Redis (`letta/server/rest_api/redis_stream_manager.py:302-391`). This is effectively error-dominates-value.

**4. Can a terminal outcome expose a partial or mutable value?**
Partial: Yes in principle. If the stream ends without `[DONE]`/`event:error` the service synthesizes `"Stream ended unexpectedly without [DONE]"` + `error` and marks `failed` (`letta/services/streaming_service.py:610-629`), leaving any already-persisted `response_messages` in the synthesized `LettaResponse` (`metadata["result"]`). Mid-stream tool results are flushed per-step to DB via `AgentLoop` checkpointing, so `get_run_messages` after failure can return the prefix of messages that were checkpointed. The terminal `Run` itself (status/stop_reason) is not partial.
Mutable: Yes. `LettaResponse` is a plain Pydantic `BaseModel` with no `frozen=True` (`letta/schemas/letta_response.py:52`), and `Run.metadata["result"]` is a bare dict produced by `model_dump()` (`letta/services/run_manager.py:460`). `get_run_messages` re-queries DB each call and re-creates `LettaMessageUnion` objects (`letta/services/run_manager.py:567-570`), so no shared alias exists, but there is no explicit `copy.deepcopy` or `freeze` enforcement. A consumer holding a reference to the `LettaResponse` returned from a blocking `send_message` call could mutate it without affecting the DB-persisted terminal outcome; conversely the mutable dict stored in `metadata` could be mutated after publication if code retains the reference (shallow merge at `letta/services/run_manager.py:374` copies at top level only).

**5. Do concurrent, repeated, and late waiters observe the same committed facts?**
Concurrent: Partially. Runs are isolated per `run_id`; concurrent `GET /runs/{run_id}` readers hit the same DB row and will eventually converge, but there is no explicit read-after-write fence documented. For the `agent_id`/`conversation_id` lock domain, `StreamingService.create_agent_stream` enforces single flight via `acquire_conversation_lock` + otid dedup (`derive_request_token`, `set_otid_run_mapping`) (`letta/services/streaming_service.py:276-347`); the second waiter either gets `ConversationBusyError` (409) enriched with `run_id` (`letta/errors.py:81-98`) or, if background + same otid, is attached as a read-only Redis SSE reader (`try_recover_duplicate_request` at `letta/services/streaming_service.py:283-295`). No test proves concurrent readers of the *same* run_id see identical `LettaResponse`/error payload; tests for concurrent conversation messages only assert serialization and eventual ability to send next message (`tests/integration_test_conversations_sdk.py:559-617`) and a streaming race test (`tests/integration_test_conversations_sdk.py:1712-1858`).
Repeated: `get_run_by_id` is idempotent — same `Run` + `metadata` returned each time, with Lettuce external sync refreshing only non-terminal runs (`letta/services/run_manager.py:104-130`). `get_run_messages` is also repeatable (cursor-based pagination stable).
Late: After completion, `retrieve_run` (`letta/server/rest_api/routers/v1/runs.py:143`) and `retrieve_stream_for_run` (Redis `xrange` from start or `starting_after` cursor) (`letta/server/rest_api/redis_stream_manager.py:463-525`) replay the persisted stream + DB row. However Redis TTL is 3h (`stream_ttl_seconds=10800` at `letta/server/rest_api/redis_stream_manager.py:42` + expiry check at `letta/server/rest_api/routers/v1/runs.py:371`) so late readers >3h lose SSE replay; DB row remains. No evidence of cache invalidation bug — but no waiter-count or barrier ensures all consumers have seen the commit before the next run starts (see Q8).

**6. Can waiting be cancelled without cancelling the run itself?**
No. Letta has no "cancel wait / detach" primitive distinct from "cancel run." Cancellation is always of the run: `POST /{agent_id}/messages/cancel` resolves to `RunManager.cancel_run` which does `update_run_by_id_async(status=cancelled)` on the `Run` row (`letta/services/run_manager.py:619-667`). Streaming waiters are cancelled cooperatively via `cancellation_aware_stream_wrapper` (`letta/server/rest_api/streaming_response.py:153-229`) or via task cancellation (`asyncio.CancelledError`), but that only interrupts the SSE delivery; the background processor handles `CancelledError` by inspecting DB `status==cancelled` to decide whether to write `cancelled` vs `error` (`letta/server/rest_api/redis_stream_manager.py:324-377`). Client HTTP disconnect (which raises `CancelledError` in `StreamingResponseWithStatusCode._protected_stream_response` at `letta/server/rest_api/streaming_response.py:358-363`) is logged and, unless explicit `cancel_run` was called, is treated as a transient disconnect — the stream is not closed for other Redis readers when `background=True` because the background processor continues. There is no `abort wait but leave run running` API shown.

**7. Who owns values and diagnostics after publication?**
Publisher owns DB persistence; consumer owns the deserialized view. After publication, the `LettaResponse` dict is stored in `Run.metadata["result"]` (`letta/services/run_manager.py:460`, `letta/services/streaming_service.py:610-629` synthesis path) and the run message rows (`Message.run_id`) are durably stored; ownership for GC is the DB (SQLAlchemy) + Redis stream (TTL). Consumers receive defensive re-materialization: `get_run_messages`/`get_run_usage` re-query DB and construct new Pydantic objects each call (`letta/services/run_manager.py:542-575`), so they own a copy. No ownership transfer or move semantics; no explicit aliasing guard — but since the stored form is JSON-dumped (`model_dump(mode="json")`) and reloaded, aliasing is broken by serialization. Diagnostics: `error_type/message/detail` in `LettaErrorMessage` and `metadata["error"]` (`letta/services/streaming_service.py:644-665`) are owned by the `Run` row (and optionally Redis error chunk). No separate diagnostic store; `capture_sentry_exception(e)` (`letta/services/streaming_service.py:776`) and `log_event` send to observability but not to the terminal outcome.

**8. Does waiter release occur only after the complete outcome is visible?**
No — background path intentionally violates this. `create_background_stream_processor` releases the conversation lock *before* the final `update_run_by_id_async` that derives `final_stop_reason -> run_status` and writes it, with an explicit comment: "Release the conversation lock BEFORE run status bookkeeping ... If we hold the lock through the DB commit, the client hits a 409 race (~1-2s window)" (`letta/server/rest_api/redis_stream_manager.py:407-445`). Foreground streaming path is safer: `update_run_by_id_async` in `StreamingService.create_agent_stream` finally block (`letta/services/streaming_service.py:462-469`) and in `_create_error_aware_stream` finally (`letta/services/streaming_service.py:801-810`) runs before SSE `[DONE]` is sent and before lock release (the `StreamingService` scheduled background processor is the outlier). For DB consumers, `update_run_by_id_async` does hold the `async_session` until commit (`no_commit=True` then context-manager commit at `letta/services/run_manager.py:383`), so `completed_at` + `status` + `metadata` become visible atomically before callback dispatch (`letta/services/run_manager.py:450-479`); but no explicit waiter-notify barrier (e.g., `asyncio.Event` per run) exists besides Redis stream `complete=true` flag (`letta/server/rest_api/redis_stream_manager.py:119`, `197`) and SSE `[DONE]` (`letta/services/streaming_service.py:626,655`). Late pollers therefore must retry; they may observe `completed` without `metadata["result"]` briefly if they race the separate metrics update (`num_steps/tools_used` at `letta/services/run_manager.py:412-447`) which happens in a second transaction after the status commit.

## Architectural Decisions

- **DB-row as terminal outcome (Run/Job) with enum exhaustiveness**: `RunStatus` + `StopReasonType.run_status` (`letta/schemas/enums.py:152`, `letta/schemas/letta_stop_reason.py:24`) makes the mapping from LLM-level reason to runtime status explicit and centralized; downside is ad-hoc extensions (`requires_approval` only from completed) require changing both enum and mapper.
- **Lean work return (LettaResponse) vs fat terminal outcome (Run)**: Keeps hot loop allocation small (messages+usage) while durable fields (callback, metrics, Redis cursor) live only on `Run`; `RunUpdate.metadata["result"] = result.model_dump()` bridges them (`letta/services/run_manager.py:460`) at publish time.
- **No Future/Join abstraction, polls + SSE replay instead**: Simplifies cross-process fanout (DB + Redis Streams) but pushes waiter-coordination burden to clients and to the Redis lock/otid dedup layer (`letta/services/streaming_service.py:276-347`).
- **Redis lock + otid request-token dedup for concurrency**: `derive_request_token(hash(otids))` + `set_otid_run_mapping` + `try_recover_duplicate_request` (`letta/services/streaming_service.py:64-118`) gives idempotent background retry without duplicate runs; tradeoff is extra Redis metadata and hash-collision risk (16-hex truncation).
- **Streaming error synthesis inside `_create_error_aware_stream` + `create_background_stream_processor`**: Every fault class (LLM timeout/rate/auth/empty, `SystemPromptTokenExceeded`, generic) is mapped to a `LettaStopReason` + `LettaErrorMessage` + `[DONE]` triple (`letta/services/streaming_service.py:639-774`, `letta/server/rest_api/redis_stream_manager.py:284-392`) so clients always see a terminal marker; but the mapping is repetitive (copy-pasted yields).
- **Log-only terminal-state guard, not DB-enforced**: `RunManager.update_run_by_id_async` merely `logger.error` on re-transition from `completed/failed/cancelled` (`letta/services/run_manager.py:342-356`), whereas `JobManager.safe_update_job_status_async` raises `ValueError` (`letta/services/job_manager.py:84-94`); inconsistency leaves Run open to accidental rollback.
- **Early lock release for background runs**: Prioritizes tail latency / 409 avoidance over strict waiter-release-after-visible-outcome (`letta/server/rest_api/redis_stream_manager.py:407-417`).

## Notable Patterns

- **Adapter pattern for LLM I/O**: `LettaLLMRequestAdapter` vs `LettaLLMStreamAdapter` injected into `LettaAgentV2._step` (`letta/agents/letta_agent_v2.py:247-257`, `347-367`) decouples work execution from publication; streaming reuse same `_step` core.
- **SSE-as-publication-channel with Redis persistence**: `RedisSSEStreamWriter` pipelines `xadd` + `expire` (`letta/server/rest_api/redis_stream_manager.py:132-157`), `redis_sse_stream_generator` supports cursor `starting_after` replay (`letta/server/rest_api/redis_stream_manager.py:463`), and keepalive wrapper `add_keepalive_to_stream` (`letta/server/rest_api/streaming_response.py:51`) prevents load-balancer timeouts — all cooperating to give late joiners the same chunks.
- **Explicit cancellation injection (`athrow`)**: `cancellation_aware_stream_wrapper` injects `RunCancelledException` into the generator (`letta/server/rest_api/streaming_response.py:202-203`, `letta/services/streaming_service.py:168-173`) so inner `except RunCancelledException` handlers can mark `run_status=None` and emit `[DONE]` without being mis-classified as `failed`.
- **Dual-commit publish (status + metrics)**: `update_run_by_id_async` splits into status/metrics + callback status as two separate `async_session` commits (`letta/services/run_manager.py:386-479`), and `RunMetrics` is a separate table (`letta/services/run_manager.py:412-447`) — spreads publication across two rows.
- **Otids as idempotency keys**: Every `MessageCreate` carries `otid` (`letta/schemas/letta_message.py:79-95`) hashed into `request_token`; duplicates never acquire lock (`letta/services/streaming_service.py:283-295`) and instead attach as `redis_sse_stream_generator` readers.

## Tradeoffs

- **DB row + Redis stream vs in-memory promise**: Gains durability, cross-pod fanout, and cursor replay at cost of consistency complexity (two stores, TTL mismatch, eventual convergence) and no single atomic "publish + wake waiters" primitive.
- **Shallow metadata merge vs overwrite**: Preserves `run_type` set at creation when error payload added later (`letta/services/run_manager.py:372-374`) but risks unbounded growth and key collisions; no schema validation on `metadata`.
- **Per-tool `ToolExecutionResult.success_flag` vs whole-run status**: Tool-level errors (`status=error`) are surfaced as `ToolReturn.status=error` within a successful run (`StopReasonType.end_turn`) rather than failing the whole run; useful for agent autonomy but obscures partial failure from outcome consumers who only check `RunStatus`.
- **Timeouts at SSE layer vs DB**: Keepalive (`keepalive_interval`) + `max_stream_silence=1800s` (`letta/server/rest_api/streaming_response.py:51-56`) prevents connection hangs, but true LLM timeout (`LLMTimeoutError`) is still mapped to `failed` independently (`letta/services/streaming_service.py:639-655`) — double timeout layers can disagree.
- **Inconsistent terminal guard**: Jobs have strict `safe_update` guard (`letta/services/job_manager.py:84`), Runs have log-only guard — trades backward compatibility (allowing `completed->cancelled` for `requires_approval` at `letta/services/run_manager.py:348-352`) for risk of accidental status regression.

## Failure Modes / Edge Cases

- **Late waiter after Redis TTL**: `GET /runs/{run_id}/stream` on >3h run raises `LettaExpiredError` (`letta/server/rest_api/routers/v1/runs.py:371`) even though DB row + messages still exist — SSE late join fails while poll late join succeeds; requires client to branch on endpoint.
- **Lock released before metrics commit**: Background path may let next `send_message` for same conversation succeed while previous `RunMetrics.num_steps/tools_used/run_ns` update (`letta/services/run_manager.py:412-447`) is still in flight; observer of aggregated metrics (e.g., `list_runs` step_count filter) may see incomplete metrics for a moment.
- **Message in SSE content mimicking terminal marker**: Prior bug where `"data: [DONE]"` inside message text could prematurely flip `saw_done`; mitigated by checking `"\ndata: [DONE]" or chunk.startswith` (`letta/services/streaming_service.py:603`, `letta/server/rest_api/redis_stream_manager.py:244`) but still fragile.
- **Cancellation race**: `cancel_run` is idempotent when `run.stop_reason not in [requires_approval]` is already set (`letta/services/run_manager.py:651`), but if cancellation and normal completion race, `update_run_by_id_async` logs but does not prevent last-writer-wins overwrite of `status` — final status depends on commit order, not happens-before.
- **Missing stop_reason synthesis**: If upstream generator ends without `[DONE]`/`error` and without `stop_reason`, foreground `_create_error_aware_stream` and background `create_background_stream_processor` both synthesize `error` + `failed` (`letta/services/streaming_service.py:610-629`, `letta/server/rest_api/redis_stream_manager.py:284-315`); however if `final_stop_reason` remains `None` and `saw_done` already true, fallback treats `DONE without stop_reason as error` (`letta/server/rest_api/redis_stream_manager.py:422-426`) — correct but noisy `logger.warning`.
- **Cursor replay after truncation**: `RedisSSEStreamWriter` trims with `maxlen=10000 approximate` (`letta/server/rest_api/redis_stream_manager.py:146`) — a late waiter with `starting_after` beyond trimmed range silently loses prefix chunks with no error signal.
- **Error payload truncation**: `JobManager`/`RunManager` store `str(e)` / `repr(e)` (`letta/services/streaming_service.py:762`, `letta/server/rest_api/redis_stream_manager.py:356`) dropping traceback; full `traceback.format_exc()` only in `log_event` attributes (`letta/interfaces/openai_streaming_interface.py:301`) — downstream debuggers see limited cause.
- **Duplicate run_id handling for non-idempotent messages**: If clients omit `otid`, `derive_request_token` returns random UUID (`letta/services/streaming_service.py:77-78`) so dedup never fires; retries create duplicate runs.
