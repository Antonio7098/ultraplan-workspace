## Summary

Pydantic-ai separates *work returns* (model text/tool-call parts, validated via `OutputSchema`/`OutputValidator`, tool function return values) from the *terminal outcome* which is a stable `AgentRunResult[OutputDataT]` (or `StreamedRunResult`/`AgentStream` handle that eventually materializes it) or a terminal exception (`RunCancelled`, `UnexpectedModelBehavior`, `UsageLimitExceeded`, `ModelHTTPError`, etc.). Publication happens through `pydantic_graph`'s `GraphRun`/`End[FinalResult]` then `Agent.run()`/`Agent.iter()` which re-wraps the graph result via `_run_lifecycle_hooks` capability middleware (`wrap_run`/`on_run_error`/`after_run`). Immutability is not enforced by the runtime – `AgentRunResult.all_messages()` returns the live `message_history` list aliased, `output` is stored by reference, and only streaming caches `deepcopy` before yielding – relying on convention and `MessageHistoryMutatedWarning`. Concurrent waiters are not a primary contract: there is no broadcast `Future[AgentRunResult]`; concurrency is limited to tool-call parallelism and a throttled `AgentStream` shared iterator. Cancellation has two levels: `StreamedRunResult.cancel()`/`AgentStream.cancel()` tears down only the current `StreamedResponse` (non-terminal) while `AgentRun.cancel()`/`RunContext.cancel()` via `RunCancellation` cancels the driving task and publishes `RunCancelled` as the terminal outcome with a detached history snapshot.

## Rating

**6/10**

Rationale: The work-return → terminal-outcome mapping is explicit (`FinalResult` dataclass, `AgentRunResult` vs `ModelResponse`, `AgentStream` with `final_result_event`, durable `GraphAgentState` history) and cancellation vs external `CancelledError` discrimination via `RunCancellation` counting `Task.cancelling()` is rigorous. Error-cause preservation (`__cause__`, `__context__`, `add_note`) and retry-budget gating are systematic. However publication does not provide a multi-waiter `Future` handle (late/repeated access depends on re-reading aliased message history), does not freeze or copy the terminal value (mutable `output` and `message_history` alias), and supporter docs/tests do not exercise concurrent `await agent.run()` sharing or waiter-only cancellation detachment.

## Answers to Dimension Questions

### 1. Is a work return distinct from the runtime's terminal outcome?

**Yes, strictly distinct, with a layered translation.**

- **Work return** = (a) what a tool function returns (`Any` → `ToolReturn`/`ToolDenied`/`ModelRetry`/`ToolFailed` handled in `pydantic_ai_slim/pydantic_ai/_tool_execution.py:64-117` and `pydantic_ai_slim/pydantic_ai/_tool_execution.py:654-735`), (b) raw model text/image/parts in `ModelResponse`, and (c) validated structured data via `OutputSchema`/`BaseOutputProcessor.validate` + `call` (`pydantic_ai_slim/pydantic_ai/_output.py:360-650`) with per-invocation `output_validators`.
- **Terminal outcome** = either `AgentRunResult[OutputDataT]` containing `output`, `run_id`, `conversation_id`, `usage`, and the detached (but aliased) `GraphAgentState.message_history` (`pydantic_ai_slim/pydantic_ai/run.py:593-733`), or a terminal exception (`RunCancelled` with detached snapshot `pydantic_ai_slim/pydantic_ai/exceptions.py:315-446`, `UnexpectedModelBehavior` `pydantic_ai_slim/pydantic_ai/exceptions.py:478-504`, `UsageLimitExceeded`, `ModelHTTPError`, `IncompleteToolCall`). The graph layer uses `End[FinalResult[OutputDataT]]` (`pydantic_ai_slim/pydantic_ai/result.py:1031-1045`) as the internal commit marker: `pydantic_graph/pydantic_graph/graph.py:737-751` sets `_next_node = End(task.value)` and asserts before returning.
- `Agent.run()` synthesizes the terminal result only after the graph has produced `End`, via `_run_lifecycle_hooks` capability middleware (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:182-344`): `before_run` → `wrap_run(handler=_do_run)` → `after_run`/`on_run_error`. A tool’s `return_value` never escapes directly; it is embedded in a `ToolReturnPart` and only later, if it is the winning output tool call, becomes `FinalResult.output` → `AgentRunResult.output`.

### 3. What happens when work returns both a value and an error?

By construction the step chooses one.

- If a single output-tool call both validates (`args_valid=True`) and then execution fails with `ToolRetryError`, the `_OutputCallResult` is interpreted as `retry_part` not `final_result` (`pydantic_ai_slim/pydantic_ai/_tool_execution.py:515-528`). The caller either records the retry as the step’s message (`ModelRequest(RetryPromptPart)`) and retries, or – when max retries exceeded – raises `UnexpectedModelBehavior` only if no other output won (`pydantic_ai_slim/pydantic_ai/_tool_execution.py:538-579`).
- If a model response contains both an output-tool call and function-tool calls, the strategy decides: under `end_strategy='early'` a schema-validated text/image output wins and function calls are stubbed as `skipped` (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:2118-2140`); under `graceful`/`exhaustive`, function tools run and a function `RetryPromptPart` triggers retry-wins which nulls the winning output (`pydantic_ai_slim/pydantic_ai/_tool_execution.py:880-909`).
- A tool cannot atomically return both value and error via Python; `_call_tool` either returns `ToolReturnPart` (`outcome='failed'` only when `ToolFailed`/`RunCancelled` wrapper, still a value the model sees) or `RetryPromptPart` (`pydantic_ai_slim/pydantic_ai/_tool_execution.py:654-715`). Throwing `ModelRetry` from inside `execute_output_function` is caught and re-wrapped to `ToolRetryError` so the model sees a correction prompt, not a dual return (`pydantic_ai_slim/pydantic_ai/_output.py:386-395`).

### 4. Can a terminal outcome expose a partial or mutable value?

**Partial:** No via normal `Agent.run()` (graph commits via `GraphRunResult` only after `End`), but **yes** via streaming mid-flight partials. `AgentStream.stream_output` yields with `allow_partial=True` using Pydantic partial validation, explicitly allowed to be incomplete; the final yield is `allow_partial=False` and cached (`pydantic_ai_slim/pydantic_ai/result.py:74-102`). A cancelled/interrupted stream records `state='interrupted'` with whatever parts had arrived (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:1309-1330`).

**Mutable:** Yes – no freeze is applied to the successful value. `AgentRunResult.output` is stored by reference; callers receive the live object. Only streaming getters `deepcopy` (`pydantic_ai_slim/pydantic_ai/result.py:76-77`, `101-102`, `233-242`). `all_messages()`/`message_history` is aliased: `AgentRunResult.all_messages()` returns `self._state.message_history` directly (`pydantic_ai_slim/pydantic_ai/run.py:636-650`), and `StreamedRunResult.all_messages()` returns `self._all_messages` (`pydantic_ai_slim/pydantic_ai/result.py:527-542`) with no defensive copy. In-place mutation is only warned, not prevented (`MessageHistoryMutatedWarning` `pydantic_ai_slim/pydantic_ai/exceptions.py:668-685`, stale `gen_ai.input.messages` span cache). Callers who mutate `result.output` (e.g., `result.output.append(...)` when `output_type=list[Foo]`) will observe shared state on subsequent reads.

### 5. Do concurrent, repeated, and late waiters observe the same committed facts?

**Concurrent waiters on the same run:** Not a first-class contract. There is no shared `Future[AgentRunResult]`. Concurrency primitives serve internal steps, not fan-out of the terminal outcome:
- `AgentStream` serializes multiple `__aiter__`/`stream_text` consumers onto one `events_iterator` via `anyio.Lock` (`pydantic_ai_slim/pydantic_ai/result.py:68-69`, `385-442` `_pull_shared`). Concurrent iteration works but yields the same events, not independent results.
- `AgentRunEvents` has exactly one background `asyncio.Task[AgentRunResult]` and one `MemoryObjectReceiveStream` with `max_buffer_size=0` (backpressured, not broadcast) (`pydantic_ai_slim/pydantic_ai/agent/abstract.py:282-309`). A second waiter would need its own `run_stream_events` call which starts a separate run.
- Tests such as `tests/test_agent.py` exhaustion/ordering assert single-consumer ordering; no test asserts two coroutines `await same_run` see identical `AgentRunResult`.

**Repeated waiters (idempotent poll after completion):** Yes, via re-derivation. `AgentRun.result` reconstructs `AgentRunResult` from `graph_run.output.output` and current `GraphAgentState` on each access (`pydantic_ai_slim/pydantic_ai/run.py:144-161`), so repeated `agent_run.result` calls return equal values (though new instances). `StreamedRunResult.is_complete` guards `_marked_completed` so second `get_output()` returns `deepcopy(self._cached_output)` idempotently (`pydantic_ai_slim/pydantic_ai/result.py:232-242`, `773-781`).

**Late waiters:** Yes, via history re-read. After completion `all_messages()`/`new_messages()`/`all_messages_json()` re-read the detached list (`pydantic_ai_slim/pydantic_ai/run.py:636-699`, `pydantic_ai_slim/pydantic_ai/result.py:527-542`), and after cancellation `RunCancelled.all_messages()` is a frozen snapshot (`pydantic_ai_slim/pydantic_ai/exceptions.py:364-385`) suitable for resume (`message_history=exc.all_messages()`). There is no built-in “wait for checkpoint to become durable” gate beyond the task join inside `Agent.run()`/`Agent.iter()`.

### 6. Can waiting be cancelled without cancelling the run itself?

**Yes, for streaming; no detached waiter handle for non-streaming.**

- **Waiter-only cancel:** `AgentStream.cancel()` and `StreamedRunResult.cancel()` only tear down the in-flight `StreamedResponse` (`await self._raw_stream_response.cancel()`) and record `state='interrupted'` while returning (`pydantic_ai_slim/pydantic_ai/result.py:158-168`, `782-810`). Docstring: “This stops only the current model response; the run continues. To end the whole run, use `AgentRun.cancel()`” (`pydantic_ai_slim/pydantic_ai/result.py:783-794`). The graph then proceeds to the next node (retry or next attempt).
- **Run cancel:** `AgentRun.cancel()`/`RunContext.cancel()` → `RunCancellation.cancel()` which cancels the driving `asyncio.Task` (`pydantic_ai_slim/pydantic_ai/_cancel.py:154-186`). This is terminal: `run.py:559-584` notes hooks may observe but cannot recover the run into a successful result. `CancellationToken` can fan cancellation to many runs but still terminates each run.
- **Non-streaming `await agent.run()` has no separate waiter token:** there is no `join_handle.cancel(waiter_only=True)`; externally cancelling the awaiting task with `task.cancel()` is treated as external cancellation and propagates as `CancelledError` (with history attached via `AgentRunEvents._attach_run_state` `pydantic_ai_slim/pydantic_ai/agent/abstract.py:246-262` or `RunCancelled.from_cancellation` `pydantic_ai_slim/pydantic_ai/exceptions.py:321-362`).

### 7. Who owns values and diagnostics after publication?

- **Values:** Caller logically owns the returned `AgentRunResult` snapshot but the runtime retains an aliased `GraphAgentState.message_history` (same list object that `capture_run_messages` hands to the graph `pydantic_ai_slim/pydantic_ai/_agent_graph.py:530-543`). No move semantics; caller mutation reflects into library state unless they deepcopy. `StreamedRunResult` caches and `deepcopy`s on every read, so caller-owned copy is isolated from internal cache. `RunCancelled` owns a detached `list(messages)` copy (`pydantic_ai_slim/pydantic_ai/exceptions.py:307`), so post-cancellation mutation does not feed back.
- **Diagnostics (errors, stacks):** In-memory exception objects retain `__cause__`/`__context__` chains (`_OutputCallResult.raise_exc` `pydantic_ai_slim/pydantic_ai/_tool_execution.py:500-504`, `WrappedPrompt` → `ToolRetryError`). `RunCancelled.from_cancellation` walks both chains (`pydantic_ai_slim/pydantic_ai/exceptions.py:343-362`). Persisted diagnostics (checkpoints/message history) retain only serialized message parts (`ToolReturnPart`, `RetryPromptPart`, `ModelResponse.provider_details`); no traceback is serialized. Ownership transfers to the caller: `all_messages_json()` serializes via `ModelMessagesTypeAdapter.dump_json` into caller-owned `bytes`.

### 8. Does waiter release occur only after the complete outcome is visible?

**For non-streaming `Agent.run()` – Yes.** The run task joins before `GraphRunResult` is returned (`pydantic_graph/pydantic_graph/graph.py:150-158` drains `async for _node in graph_run: pass` then asserts `graph_run.result is not None`; `pydantic_ai_slim/pydantic_ai/agent/__init__.py:182-344` `_run_lifecycle_hooks` awaits `_wrap_task` and `_finalize_result` before `yield` returns). `_append_response` increments usage and checks `usage_limits` before `message_history.append(response)` (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:1779-1796`), so any post-run `all_messages()` sees the committed cost. `RunCancellation.finish()` marks finished after exit, so no late `cancel()` races in (`pydantic_ai_slim/pydantic_ai/_cancel.py:194-202`).

**For streaming – Gated by `is_complete`/`_marked_completed`.** `AgentStream.stream_response` always yields a final snapshot with `state='complete'`/`'interrupted'` after the temporal group iterator drains (`pydantic_ai_slim/pydantic_ai/result.py:103-122`); `StreamedRunResult.stream_*` call `_marked_completed` only after that final yield and only then set `is_complete=True` and append to `all_messages` (`pydantic_ai_slim/pydantic_ai/result.py:592-614`, `647-675`, `773-781`). `AgentStream.get_output` drains the whole stream before validating and caching (`pydantic_ai_slim/pydantic_ai/result.py:232-242`). Premature `_receive_one` in `SyncStreamBridge` blocks until a pump completes (`pydantic_ai_slim/pydantic_ai/_sync_stream.py:314-401`), but the sync wrapper does not publish durability beyond task join; there is no cross-process durability gate.

**Gap:** No `wait_for_durable` handle exists; a caller that persists `all_messages` externally must join the `Agent.run()` task itself. The visibility invariant is “in-process join”, not “externally durably visible”.

## Architectural Decisions

| Decision | Rationale / Evidence | Consequence |

## Notable Patterns

- **Exclusive commit per step:** `_prepare_request` / `_prepare_resume_request` clear and reserve history, `CallToolsNode._run_stream` branches `is_empty` → `allows_none` → tool_calls → text/image → retry (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:1893-2062`); `process_tool_calls` never co-publishes `final_result` + `RetryPromptPart` as winning terminal for same step.
- **Retry-wins dominance:** `_apply_retry_wins` replaces the winning `ToolReturnPart` content in place (`pydantic_ai_slim/pydantic_ai/_tool_execution.py:880-909`) ensuring retry prompt is visible to model next round.
- **Two-level streaming chain:** `model_request`/`model_request_stream` stitch `suspended→complete` continuation loop (Anthropic `pause_turn`/OpenAI background) via `merge_responses` before graph sees a response (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:858-1042`).
- **`CancellationToken` fan-out + `RunBinding` lazy attach:** One token can cancel many runs thread-safely (`pydantic_ai_slim/pydantic_ai/_cancel.py:42-90`); `AgentRunEvents` owns binding before GraphRun exists and `provide_run_binding`/`take_run_binding` propagate it (`pydantic_ai_slim/pydantic_ai/_cancel.py:260-293`, `pydantic_ai_slim/pydantic_ai/agent/abstract.py:282-309`).
- **`is_complete` gate + idempotent `_marked_completed`:** Guards double-append and `on_complete` invocation regardless of which streaming accessor (`stream_output`, `stream_text`, `stream_response`, `get_output`) finishes first (`pydantic_ai_slim/pydantic_ai/result.py:773-781`).

## Tradeoffs

| Tradeoff | Pro | Con |
|----------|-----|-----|
| **Single `AgentRunResult` return vs broadcast Future** | Simple await/iterator mental model; aligns with `asyncio` ergonomic | No natural multi-waiter sharing; composing parallel agent runs requires external `asyncio.gather` on separate `agent.run()` coroutines |
| **Aliased history + no copy-on-return** | Zero-copy, O(1) latency for large histories | Caller can break OTel `gen_ai.input.messages` cache or future steps if they mutate history in place; mitigated only by warning |
| **`deepcopy` only for cached output in streaming** | Isolates common mutation target (structured output) where cost is localized | Inconsistent: `ModelResponse.parts[0].content = ...` mutates cached state and published history without guard |
| **`durability` via in-process task join, no external durable gate** | Low latency for non-durable agents; durability providers opt in via capabilities | No `await checkpoint_durable(checkpoint_id)` handle for persistence-backed late readers; streaming publication is process-local |
| **Py3.11+ `cancelling()` discrimination** | Correctly prioritizes external cancel (timeout) over first-party | Needs fallback behavior on py3.10; race window if caller `uncancel()`s first-party cancel remains (issue #7240 comment `pydantic_ai_slim/pydantic_ai/_cancel.py:142-144`) |

## Failure Modes / Edge Cases

- **Mutating published `all_messages()` corrupts future inputs:** `all_messages()` alias is later used as `message_history` slice assignment in next `UserPromptNode.run` (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:539` `messages[:] = _clean_message_history(...)`). A caller that appended to the returned list will see stale spans (`MessageHistoryMutatedWarning` `pydantic_ai_slim/pydantic_ai/exceptions.py:668-685`).
- **Retrying past `max_output_retries`:** `consume_output_retry` raises `UnexpectedModelBehavior` wrapping original `ModelRetry` (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:362-380`); in streaming path `validate_response_output` re-raises without `wrap_validation_errors` → surfaces as `UnexpectedModelBehavior` to caller instead of retry, even though history already contains failed tool status parts.
- **Cancelled stream with `suspended` job:** `_resolve_interrupted_stream_state` must `cancel_suspended_job` for non-`GeneratorExit` errors, otherwise provider-leaked job persists (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:209-230`, `996-1009`). Bug: if `_agent_graph_sleep` inter-poll delay raises, job is cancelled before propagate – but failure to await cancellation is best-effort.
- **External cancel absorbed by user hook:** `_RunLifecycle._do_run` deliberately sets `_run_error = exc` and drains `_ready_waiter`/`_wrap_task` with `cancel_and_drain` if a durable step swallows `CancelledError`, then `_finalize_result` re-asserts `raise_if_cancelling()` (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:240-284`, `276-284`). Missed re-assert would falsely publish success.
- **Streaming waiter teardown race:** `AgentStream.aclose_events` cancels `_pull_scopes` and shields `_anext_lock` (`pydantic_ai_slim/pydantic_ai/result.py:403-422`); if consumer yields after interrupt, `scope.cancel_called` returns cleanly instead of leaking blocked `anext`.
- **Resume with duplicate `tool_call_id`:** `_duplicate_tool_call_ids` check in `process_tool_calls` (`pydantic_ai_slim/pydantic_ai/_tool_execution.py:404-412`) rejects ambiguous resume bindings rather than mis-routing results.

## Future Considerations

- Expose a **broadcast `RunHandle[OutputDataT]`** (`Future[AgentRunResult]`) with `wait()`/`share()` and `cancel(waiter_only=True | run=True)` to formalize concurrent and late waiters, similar to `FutureDict` for nodes but at the run level.
- **Freeze or copy on publication:** Offer `AgentRunResult(output=deepcopy(...), message_history=tuple(...))` or opt-in `freeze=True` / `MappingProxy` for `output` so publication is stable across callers; at minimum copy `all_messages()` return.
- **Durability-gated waiter API:** `await agent.wait_for_persisted(run_id)` or `checkpointer.wait(checkpoint_id)` wrapper over `_delta_write_futs` for durable-execution agents, fixing the “return before checkpoint visible” gap.
- **Structured error persistence:** Store `error.type`/`traceback` alongside stringified message in `CheckpointTask.error` / `StateSnapshot` so `get_state_history` late readers retain fidelity beyond `NodeError.__class__` injection.
- **Uniform waiter-cancel handle:** Return `AgentRunResultEvent | RunCancelled` discriminator directly from `await AgentRunEvents.__anext__` style handle so streaming consumers can cancel subscription without affecting graph.

## Questions / Gaps

- No evidence of a **multi-waiter broadcast handle** or test asserting two coroutines `await` the same `AgentRunResult` handle; search for `Future[AgentRunResult]`, `waiter`, `join` in `pydantic_ai_slim/pydantic_ai/*.py` returns only internal `FuturesDict` for node tasks (`pydantic_ai_slim/pydantic_ai/_tool_execution.py:791-849`) and `pydantic_graph` runner internals.
