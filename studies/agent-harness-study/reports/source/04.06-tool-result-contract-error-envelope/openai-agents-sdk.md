## Summary

The OpenAI Agents SDK ships an unusually mature tool-result contract for a Python agent harness. Every tool result — success or failure, scalar or structured — is funneled through a small set of explicit types (`ToolOutputText` / `ToolOutputImage` / `ToolOutputFileContent`, the `ToolCallOutputItem` wrapper, the `FunctionToolResult` internal struct) and a configurable error pipeline that turns `Exception` into either a model-visible string or an `AgentsException` that aborts the run. The model can always distinguish success from failure: every error is converted to a string reply attached to a `function_call_output` (`type="function_call_output"`, `call_id`, `output`) or to a synthetic `_call_output` item, and run-level failures raise `AgentsException` subclasses (`MaxTurnsExceeded`, `ModelBehaviorError`, `ModelRefusalError`, `UserError`, `MCPToolCancellationError`, `ToolTimeoutError`, `*GuardrailTripwireTriggered`) with an attached `RunErrorDetails` snapshot. Stack traces are hidden from the model by default — internal exceptions are routed through `default_tool_error_function` (`src/agents/tool.py:1609-1618`), which returns `"An error occurred while running the tool. Please try again. Error: …"` — but raw error text never reaches the LLM traces; `_debug.DONT_LOG_TOOL_DATA` (default `True`, `src/agents/_debug.py:12-17`) and the `trace_include_sensitive_data` toggle gate both span error fields (`src/agents/util/_tool_errors.py:1-8`) and full output serialization (e.g. `src/agents/run_internal/tool_actions.py:188-189`). Large tool outputs are handled at three layers: per-call `max_output_length` for shell (`src/agents/run_internal/tool_execution.py:1001-1005`, `:926-963`), span-level JSON-byte truncation by the tracing exporter (`src/agents/tracing/processors.py:243-424`), and the pluggable `ToolOutputTrimmer` extension (`src/agents/extensions/tool_output_trimmer.py:1-309`) that prunes `function_call_output` / `tool_search_output` items from older turns. Tool outputs are also replayable: `ToolCallOutputItem.to_input_item` (`src/agents/items.py:421-448`) and `RunItemBase.to_input_item` (`src/agents/items.py:144-153`) reconstruct Responses-API-shaped input items, and `RunState` schema `1.11` (`src/agents/run_state.py:131`) persists interruption/interrupt payloads across resumes.

The single weakness is that the envelope is *text-by-convention* rather than a discriminated union: a successful tool return and a failure-message return look identical at the protocol level — both are `function_call_output` with a `str` `output`. The signal that "the tool crashed" is encoded only inside the string content (the prefix `"An error occurred while running the tool."`), inside span-level `SpanError` annotations, or as an `AgentsException` that aborts the run. There is no machine-readable `{ ok: false, error: { kind, message, retryable } }` envelope the model can branch on. Whether a failed call is "useful feedback rather than a crash" depends entirely on which `failure_error_function` the user wires in (default — text-in-disguise — vs. `None` — exception). With the default the failure becomes an in-band retry hint; with `None` the run halts. Artifacts (image / file outputs) are first-class — `ToolOutputImage` / `ToolOutputFileContent` survive the round-trip via `_convert_tool_output` (`src/agents/items.py:802-875`) — but local tool outputs are not URL-addressable; a model that wants to refer back to a previous tool artifact must have it included in the truncated/summarized item, not by reference.

## Rating

**8 / 10** — Clear, documented, and exercised by tests. Tool outputs are strongly typed (`ToolOutputText`/`ToolOutputImage`/`ToolOutputFileContent`), every failure has an explicit funnel (`failure_error_function` per tool, `tool_error_formatter` per run, `timeout_error_function` for timeouts, `ToolErrorFormatter` for approvals / tool-not-found), stack traces are redacted by default (`get_trace_tool_error` + `DONT_LOG_TOOL_DATA`), large outputs are bounded at three layers (per-call `max_output_length`, span-field byte-budget, `ToolOutputTrimmer`), and outputs are replayable through `to_input_item()` and `RunState`. Pulls back from 9/10 because (a) the in-band envelope is text-only — no discriminated `ok`/`error` discriminator — so the model cannot programmatically distinguish "succeeded with value X" from "failed with text X" without parsing the string, (b) failures do not carry a retryable / kind tag in the wire payload, and (c) large artifacts are summarized but not linked — there is no `artifact_ref` / `uri` slot that survives replay independently of the inline payload.

## Answers to Dimension Questions

1. **Is every tool result structured?** Yes, for the local tool path: the canonical output types are `ToolOutputText` / `ToolOutputImage` / `ToolOutputFileContent` (`src/agents/tool.py:190-262`), validated by a Pydantic `TypeAdapter` (`src/agents/tool.py:265-267`), and serialized via `ItemHelpers._convert_tool_output` into a Responses-API `ResponseFunctionCallOutputItemListParam` (`src/agents/items.py:801-875`). Non-Pydantic / non-list output falls back to `str(output)`. The result is wrapped in a `ToolCallOutputItem` (`src/agents/items.py:390-448`) whose `raw_item` always carries `type="function_call_output"`, `call_id`, and `output`. Hosted tools (shell / apply_patch / custom / computer) emit their own typed raw items (`shell_call_output`, `apply_patch_call_output`, `custom_tool_call_output`, `computer_call_output`) via the action executors (`src/agents/run_internal/tool_actions.py:539-606`, `:689-737`, `:882-938`, `:137-196`). The "structured" envelope is the wire item — there is no separate `Ok` / `Err` union on the model-visible path.

2. **Can the model distinguish success from failure?** Partially. (a) In the **in-band success path** the model sees `function_call_output` with the stringified result. (b) In the **default in-band failure path** the model also sees `function_call_output`, but the content starts with `"An error occurred while running the tool. Please try again. Error: …"` (`src/agents/tool.py:1618`) or `"An error occurred while parsing tool arguments. …"` (`src/agents/tool.py:1613-1617`). The prefix is convention, not protocol — the model has to parse the string. (c) When `failure_error_function=None` is configured, the SDK raises the underlying exception and aborts the run (`src/agents/tool.py:526-568`), and the model is informed via the run-level exception (`AgentsException` subclasses in `src/agents/exceptions.py:46-174`). (d) Approvals / tool-not-found / timeouts each have their own canonical strings (`DEFAULT_APPROVAL_REJECTION_MESSAGE` in `src/agents/tool.py:181`, `_default_tool_not_found_message` in `src/agents/run_internal/turn_resolution.py:213-214`, `default_tool_timeout_error_message` in `src/agents/tool.py:1627-1629`). So: in-band the answer is "by string convention"; out-of-band the answer is "by exception type, but the model never sees the exception directly — only its `RunErrorDetails` snapshot (`src/agents/exceptions.py:30-44`)."

3. **Are stack traces hidden from users/models?** Yes by default. The SDK ships two independent redaction layers: `_debug.DONT_LOG_TOOL_DATA` (default `True`, env-var driven at `src/agents/_debug.py:12-17`) gates *log*-level disclosure of tool input/output and `RunConfig.trace_include_sensitive_data` (default `True`, env-var driven at `src/agents/run_config.py:41-44`) gates span-field disclosure. Errors flowing into spans are normalized via `get_trace_tool_error` (`src/agents/util/_tool_errors.py:1-8`), which substitutes the literal `REDACTED_TOOL_ERROR_MESSAGE = "Tool execution failed. Error details are redacted."` when sensitive data is off — and this is asserted by tests for function (`tests/test_run_step_execution.py:642-710`), shell (`tests/test_shell_tool.py:314-345`), apply_patch (`tests/test_apply_patch_tool.py:176-210`), computer (`tests/test_computer_action.py:703-740`), and MCP (`tests/mcp/test_mcp_tracing.py:220-235`). `_parse_function_tool_json_input` is careful to raise `ModelBehaviorError` *outside* the `except` block when `DONT_LOG_TOOL_DATA` is set, so the original `JSONDecodeError.doc` (which carries the raw payload) is not attached as `__context__` / `__cause__` and cannot leak through `repr(exc)` (`src/agents/tool.py:1585-1590`). `default_tool_error_function` writes a short, generic message rather than `repr(traceback)`. Caveat: the in-band `function_call_output` *does* include `f"Error: {str(error)}"` from the default formatter, so a careless tool that embeds a stack trace in its `Exception` message can still surface that to the model. There is no scrubbing of `str(error)` itself — only of the span, log, and JSON-decode payload.

4. **Are large results handled safely?** Yes, at three layers, plus a fourth knob per shell call. (a) Shell outputs are bounded by `max_output_length` from the model action (`src/agents/run_internal/tool_execution.py:646-655`), normalized to `>= 0` (`src/agents/run_internal/tool_execution.py:1001-1005`), then truncated by `truncate_shell_outputs` (`src/agents/run_internal/tool_execution.py:926-963`). (b) Span fields exported to traces are capped by JSON-byte budget (`_truncate_span_field_value`, `_truncate_string_for_json_limit`, `_truncate_mapping_for_json_limit`, `src/agents/tracing/processors.py:243-424`). (c) The `ToolOutputTrimmer` extension (`src/agents/extensions/tool_output_trimmer.py:1-309`) replaces `function_call_output` items from older turns (older than `recent_turns` user messages) with a compact preview when the output exceeds `max_output_chars`. The trimmer also structurally prunes `tool_search_output.tools` (strips `description`/`title`/`$comment`/`examples` from JSON schema, keeps the shape) — see `_trim_tool_search_tool` and `_trim_json_schema` (`src/agents/extensions/tool_output_trimmer.py:266-302`). (d) `call_model_input_filter` is pluggable (`src/agents/run_config.py:298-306`) so users can add their own trimmer. There is **no** automatic token-budget or model-context budget enforcement on the function-tool path itself; the trimmer is opt-in.

5. **Can tool results be replayed?** Yes — both within a single run and across runs. (a) `ToolCallOutputItem.to_input_item` (`src/agents/items.py:421-448`) round-trips the raw item, sanitizing shell output fields (`status`, `shell_output`, `provider_data`) that the Responses API does not yet accept. `RunItemBase.to_input_item` (`src/agents/items.py:144-153`) does the same for output items generally. (b) `RunState` persists the run with `CURRENT_SCHEMA_VERSION = "1.11"` (`src/agents/run_state.py:131`), and `_serialize_approvals` round-trips per-call / sticky approval decisions and rejection messages (`src/agents/run_state.py:359-379`). (c) On resume, `RunState` is deserialized and `_rebuild_approvals` (`src/agents/run_context.py:447-468`) restores the approval store so the model sees the same interruptions it would have seen in a fresh run. (d) Approval errors are replayed as real `function_call_output` items via `_build_function_tool_call_for_approval_error` (`src/agents/run_internal/approvals.py:24-102`), so a rejected tool call can be repeated in a resumed run without special handling. Forward-compatibility is *fail-fast* — older SDKs reject newer schema versions (`src/agents/run_state.py:128-130`), which limits blind cross-version replay.

## Architectural Decisions

1. **Single uniform wire item, with a separate failure funnel.** Every tool result, success or failure, surfaces as a `function_call_output` (or its hosted-tool variant) attached to a `ToolCallOutputItem`. The "this is a failure" signal is encoded inside the string content, the span, and (when severe) a raised exception — not as a wire-level discriminator. This makes replay simple (one item type per call type) but forces consumers to either trust the prefix or wire a `failure_error_function` to inject structured data into the string.

2. **Tool failures are not run failures by default.** `FunctionTool` is constructed with `failure_error_function` defaulting to `default_tool_error_function` (`src/agents/tool.py:1899-1937`), so most tool exceptions are demoted to a string reply and the run continues. The model can retry. This is the right default for usability but does mean tool bugs look like model-visible strings unless the developer wires `failure_error_function=None` to escalate.

3. **Stack traces are scrubbed at two layers (log + trace) but not in the model-visible string.** The SDK deliberately keeps `str(error)` (often a short `Exception` message) in the `function_call_output` so the model can reason about what went wrong, but it scrubs the full span and the structured JSON-decode payloads. This matches the contributor guidance in `AGENTS.md` (which calls out that `raise ... from None` is not enough if the exception object still carries sensitive input) — but the SDK does not actively redact `str(error)` itself, only the bytes that go into traces / logs.

4. **Large-output handling is layered and pluggable.** Per-call shell limits (`max_output_length`), span-byte budgets (`_truncate_span_field_value`), pluggable `call_model_input_filter` (`src/agents/run_config.py:298-306`), and a built-in `ToolOutputTrimmer` (`src/agents/extensions/tool_output_trimmer.py:1-309`) compose. There is no single "max tool output" setting — different layers address different failure modes (model context overflow vs. trace exporter overflow vs. shell-buffer overflow).

5. **Run errors carry a replayable snapshot.** Every `AgentsException` subclass has a `run_data: RunErrorDetails | None` field (`src/agents/exceptions.py:46-53`), populated by `Runner.run` (`src/agents/run.py:1505-1517`) and `RunResultStreaming._check_errors` (`src/agents/result.py:781-836`). Error handlers (`src/agents/run_error_handlers.py:1-*`) receive this snapshot via `RunErrorHandlerInput` and can return a structured `RunErrorHandlerResult(final_output, include_in_history)` — so a `MaxTurnsExceeded` or `ModelRefusalError` can be recovered, not just re-raised.

6. **Tool-not-found is configurable between fail-fast and fail-soft.** `RunConfig.tool_not_found_behavior: "raise_error" | "return_error_to_model"` (`src/agents/run_config.py:66`, `:332-338`) lets callers decide whether a missing function-tool is a `ModelBehaviorError` that aborts the run or a `function_call_output` string that the model can reason about. `_build_tool_not_found_output_items` (`src/agents/run_internal/turn_resolution.py:259-281`) builds the failure output, and the run continues.

7. **Approvals are a first-class pause unit with their own envelope.** Approval rejections produce a real `function_call_output` (`_build_function_tool_call_for_approval_error` at `src/agents/run_internal/approvals.py:24-102`) — not a synthetic error string — so a rejected tool call is replayable in a resumed run and survives `RunState` round-tripping (`CURRENT_SCHEMA_VERSION = "1.11"`, `src/agents/run_state.py:131`).

## Notable Patterns

- **Per-tool / per-run / per-formatter separation of concerns.** `_failure_error_function` lives on the tool, `timeout_error_function` lives on the tool, `tool_error_formatter` lives on the `RunConfig`, and `ToolErrorFormatterArgs` is shared by approval rejections and tool-not-found (`src/agents/run_config.py:69-92`). This lets different error categories be customized at different scopes.

- **Span-level error annotations are independent of wire-level errors.** A successful tool call can carry a `SpanError` ("Error running tool (non-fatal)" via `_build_handled_function_tool_error_handler`, `src/agents/tool.py:1519-1572`), and a failed call that becomes an in-band string can carry a `SpanError` ("Error running tool") with a redacted error. The model sees a string; traces see a typed error.

- **`call_model_input_filter` as the extension point for output shaping.** `ToolOutputTrimmer` is just one implementation of the `CallModelInputFilter` protocol (`src/agents/run_config.py:64`). Users can implement arbitrary filters (`tests/test_call_model_input_filter.py`, `tests/test_call_model_input_filter_unit.py`).

- **`to_input_item` replay sanitization is a stable contract.** Every replay path strips SDK-only fields (`status`, `shell_output`, `provider_data` for shell outputs; `created_by` for tool-search items) — see `ToolCallOutputItem.to_input_item` (`src/agents/items.py:421-448`) and `_tool_search_item_to_input_item` (`src/agents/items.py:194-206`). The wire payload stays API-compatible across SDK versions.

- **Pretty-printer is a separate module.** `pretty_print_run_error_details` (`src/agents/util/_pretty_print.py:42-51`) gives a one-line summary so `str(exc)` is safe to log without exposing `repr(traceback)`.

- **Pluggable `custom_data_extractor` per tool.** `FunctionTool.custom_data_extractor` / `CustomTool.custom_data_extractor` / `ComputerTool.custom_data_extractor` / `ApplyPatchTool.custom_data_extractor` add SDK-only metadata to `ToolCallOutputItem.custom_data` that is *not* sent back to the model (`src/agents/tool.py:84-179`). This is the closest the SDK gets to an artifact-reference slot.

- **Failure error formatter is also cancellation-aware.** `asyncio.CancelledError` is wrapped in `_FunctionToolCancelledError` (`src/agents/tool.py:1657-1665`) before being passed to a `failure_error_function`, so user formatters always see an `Exception` (per their contract), and the runtime has a separate path to treat cancellation specially (`src/agents/run_internal/tool_execution.py:1801-1823`).

## Tradeoffs

- **Text-by-convention envelope vs. discriminated union.** The default `function_call_output` does not carry a `status` / `kind` / `error_code` discriminator. The model can only branch on a successful vs. failed tool call by parsing the prefix or by noticing `AgentsException` exceptions in the run metadata. This keeps the wire format small and replay simple, but it pushes parsing onto the LLM.

- **`failure_error_function=None` is opt-in escalation.** Default behavior (`default_tool_error_function`) returns a generic string and continues the run. To get fail-fast behavior, the developer must remember to pass `failure_error_function=None` (`src/agents/tool.py:1899-1937`). This favors "let the model retry" over "fail loudly", which is the right default for agent loops but means silent tool bugs.

- **Redaction is partial.** Logs and spans are scrubbed, but the model-visible string still contains `f"Error: {str(error)}"` (`src/agents/tool.py:1618`). A tool that puts a credential in its `Exception` message would still leak it to the model. The SDK ships `DONT_LOG_TOOL_DATA` for logs and `trace_include_sensitive_data=False` for spans, but no automatic scrub of the model-visible string.

- **Large-output trimming is opt-in.** `ToolOutputTrimmer` (`src/agents/extensions/tool_output_trimmer.py:1-309`) is only active if wired into `RunConfig.call_model_input_filter`. The default runner sends full tool outputs to the model, which can blow context budgets. This is a deliberate design choice — the SDK prefers defaults that preserve fidelity — but it means production users must wire a trimmer or accept context overflow.

- **Artifacts are inline-only.** `ToolOutputImage` / `ToolOutputFileContent` serialize inline (`image_url`, `file_data`, `file_url`, `file_id`) into the `function_call_output` payload (`src/agents/items.py:844-875`). There is no out-of-band `artifact_ref` slot — once trimmed, the original artifact is gone. The `file_id` slot allows the model to *refer* to a previously uploaded file, but local tool artifacts are not uploadable by the SDK.

- **`failure_error_function` returns a string, not a structured envelope.** The default formatter returns a plain string (`src/agents/tool.py:1609-1618`). A user who wants a structured `{ ok: false, kind, message, retryable }` envelope must encode it as JSON inside the string and rely on the model parsing it back out.

- **`shell_call_output` and `apply_patch_call_output` carry SDK-only fields.** The raw items include `status`, `shell_output`, `provider_data`, and `max_output_length` (`src/agents/run_internal/tool_actions.py:585-596`). The Responses API does not yet accept `status`, so `to_input_item` strips it on replay (`src/agents/items.py:432-446`). A future Responses API change that *does* accept `status` would need a coordinated update.

## Failure Modes / Edge Cases

- **CancelledError propagation.** Sibling cancellation uses a priority queue (`_select_function_tool_failure`, `src/agents/run_internal/tool_execution.py:252-268`); `BaseException` wins over `Exception`, which wins over `asyncio.CancelledError`. The chosen failure is the one re-raised (`_raise_failure_after_draining_siblings`, `src/agents/run_internal/tool_execution.py:1480-1509`), with late-failure merge via `_merge_late_function_tool_failure` (`:271-289`). Background-task exceptions are reported through `loop.call_exception_handler` (`_consume_function_tool_task_result`, `:217-240`), so they do not crash the runner but they are also not surfaced as tool errors — they go to the asyncio loop's exception handler.

- **`failure_error_function=None` on a tool inside a batch.** When one tool in a parallel batch raises and has `failure_error_function=None`, the sibling tools are cancelled (`_raise_failure_after_draining_siblings`, `src/agents/run_internal/tool_execution.py:1480-1509`), and the failure is re-raised. This is intentional — confirmed by `test_multiple_tool_calls_still_raise_when_sibling_failure_error_function_none` (`tests/test_run_step_execution.py:613-638`).

- **`failure_error_function` survives `dataclasses.replace` / `copy.copy`.** `_FailureHandlingFunctionToolInvoker` and the per-tool `_failure_error_function` are designed to round-trip through copy operations (`src/agents/tool.py:513-523`, `:649-664`; `tests/test_function_tool.py:649-705`). Without this, agent-as-tool cloning would silently drop the failure policy.

- **JSONDecodeError special-case.** Bad tool arguments do not leak the original payload into `ModelBehaviorError.__cause__` / `__context__` when `DONT_LOG_TOOL_DATA` is set (`src/agents/tool.py:1585-1590`), but they *do* when logging is enabled (so developer debugging keeps the payload visible) — see `test_function_tool_bad_json_includes_payload_when_tool_logging_enabled` (`tests/test_function_tool.py:817-844`).

- **Manual `FunctionTool` (no decorator) uses the default formatter.** `_use_default_failure_error_function = True` by default means even hand-rolled `FunctionTool` instances get the generic-string envelope unless the developer wires one in (`src/agents/tool.py:1648-1654`, `tests/test_function_tool.py:621-645`).

- **Tool-not-found defaults to raise.** `RunConfig.tool_not_found_behavior` defaults to `"raise_error"` (`src/agents/run_config.py:332`), so a hallucinated tool name from the model is a `ModelBehaviorError`, not a string reply. Setting `"return_error_to_model"` produces a real `function_call_output` (`src/agents/run_internal/turn_resolution.py:1958-1970`, `:259-281`).

- **Empty / None outputs.** `default_tool_error_function` returns the literal "An error occurred" string when `str(error)` is empty (`src/agents/tool.py:1618`). For shell tools, `format_shell_error` (`src/agents/run_internal/tool_execution.py:1008-1017`) returns the class name if `str(error)` is empty.

- **Trimmer on a borderline-sized output.** `ToolOutputTrimmer` skips trimming when the `[Trimmed: …]` summary would be longer than the original (`src/agents/extensions/tool_output_trimmer.py:215-220`, `:259-261`, tested at `tests/extensions/test_tool_output_trimmer.py:577-597`).

- **Trimmer does not mutate input.** New items are shallow copies when modified (`src/agents/extensions/tool_output_trimmer.py:115-147`); the original turn state is left intact, which is critical for replay consistency.

- **`max_output_length` clamp.** `normalize_max_output_length` clamps negative values to 0 (`src/agents/run_internal/tool_execution.py:1001-1005`); when 0, `truncate_shell_outputs` emits empty stdout/stderr but keeps the outcome / command / provider_data (`src/agents/run_internal/tool_execution.py:930-940`).

## Future Considerations

- **Discriminated success/failure envelope.** Adding a machine-readable `status: "ok" | "error"` field to `function_call_output` (or a parallel error item) would let the model branch without parsing the string. The wire-format change is non-trivial because Responses API does not currently accept such a discriminator, but the SDK already has the SDK-only `status` field on `shell_call_output` (`src/agents/run_internal/tool_actions.py:589`), which suggests the team is open to this extension.

- **Artifact reference slots.** Today, `ToolOutputImage.file_id` allows the model to refer to *uploaded* files but the SDK never uploads tool artifacts. A `tool_output_artifact_id` slot returned alongside `output` would let a trimmer replace the payload with a reference rather than a preview, preserving fidelity for the model.

- **Token-budget-driven trimming.** `ToolOutputTrimmer` operates on character count (`max_output_chars`); an opt-in token-budget variant using the same engine would let users target model context windows directly.

- **Active scrub of `str(error)`.** The SDK redacts spans and logs but lets `f"Error: {str(error)}"` flow to the model. A hook for tool authors to mark a tool as "exception-safe" (so its `Exception` message is scrubbed) would close the partial-redaction gap.

- **Schema-versioned error envelope.** `RunErrorDetails` is opaque Python; an explicit `RunErrorSchema` with versioned fields would let error-handler consumers reason about the snapshot across SDK upgrades without parsing strings.

- **Tool-call streaming errors.** `RunItemStreamEvent` does not currently emit a distinct `tool_failed` event — failures look identical to successes (`tool_output` for both, `src/agents/stream_events.py:29-43`). A typed event would let streaming consumers filter failures.

## Questions / Gaps

- **No clear evidence** of a wire-level `kind` / `status` discriminator on `function_call_output`. The SDK is consistent in treating success and failure as text payloads; the only place a status lives is the SDK-only `shell_call_output.status` field.

- **No clear evidence** of automatic token-budget enforcement on tool outputs. `ToolOutputTrimmer` is character-based and opt-in.

- **No clear evidence** of artifact persistence independent of the model-visible payload. `ToolCallOutputItem.custom_data` is attached to the item but is not surfaced to the model and is not separately addressable in `RunState`.

- **No clear evidence** that `failure_error_function` results are validated for non-string returns before going to the wire; the contract is `Callable[..., MaybeAwaitable[str]]` (`src/agents/tool.py:183`) but `_FailureHandlingFunctionToolInvoker` (`src/agents/tool.py:526-568`) just passes the result through. A `None` return value would crash the Responses API.

- **No clear evidence** that the redacted span error message ("Tool execution failed. Error details are redacted.") is also the in-band model-visible text in the same code path. The model-visible default uses `f"Error: {str(error)}"` (`src/agents/tool.py:1618`), which is *not* the redacted text — meaning the model sees the unredacted message while the trace sees the redacted one. This is a partial-redaction gap worth confirming with the contributor team.
