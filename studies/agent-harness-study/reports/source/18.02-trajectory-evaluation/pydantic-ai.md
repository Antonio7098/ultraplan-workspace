## Summary

`pydantic-ai` treats trajectory evaluation as span-tree evaluation. `pydantic_evals` captures an OpenTelemetry `SpanTree` per `Case` via `context_subtree` during `Dataset.evaluate()` and exposes it through `EvaluatorContext.span_tree`. A dedicated agentic evaluator family (`ToolCorrectness`, `TrajectoryMatch`, `ArgumentCorrectness`, `MaxToolCalls`, `MaxModelRequests`, `HasMatchingSpan`) scores intermediate tool choices deterministically against that tree, with configurable handling of failed/retried attempts and both v2 (`running tool`) and v3+ (`execute_tool {name}`) instrumentation formats. `LLMJudge`/`GEval` provide rubric-based output scoring orthogonal to trajectory. General-purpose trajectory scoring exists and is well-tested, but context-usage measurement and recovery-from-failure evaluation are ad-hoc: token counts are collected as metrics but not scored, and retry/retrial awareness is reduced to an `include_failed` flag rather than a first-class recovery signal.

## Rating

**6 / 10** — Present with clear interfaces and thorough trajectory/tool-choice coverage, but inconsistent across the four dimension questions: strong on intermediate-step and tool-choice evaluation (deterministic, span-typed, extensively tested), partial on trajectory scoring (F1-based `TrajectoryMatch` + bool assertions, averaged in reports), and absent/weak on context-usage and recovery behavior (no evaluator for context window utilization or error-recovery quality, only `include_failed` and `run_on_errors` hooks).

## Answers to Dimension Questions

**1. Are intermediate steps evaluated? Yes, strongly.** The primary trajectory mechanism is the captured `SpanTree`. Every case built by `_run_task` ( `pydantic_evals/pydantic_evals/dataset.py:965-1010` ) yields `EvaluatorContext._span_tree` via `context_subtree` (`pydantic_evals/pydantic_evals/otel/_context_subtree.py`), and callers can also attach custom spans inside the task. `HasMatchingSpan` (`pydantic_evals/pydantic_evals/evaluators/common.py:341-355`) evaluates any `SpanQuery` against the tree (name, attributes, status, timing, parent/child relations — `pydantic_evals/pydantic_evals/otel/span_tree.py:29-404`). The agentic evaluators in `pydantic_evals/pydantic_evals/evaluators/agentic.py:1-35` explicitly document that all of them read `ctx.span_tree` and degrade to a failing `EvaluationReason` if Logfire/instrumentation is not configured (`_NO_SPAN_TREE_REASON` at `pydantic_evals/pydantic_evals/evaluators/agentic.py:182`). This directly answers "good path even if final answer wrong": a wrong `ctx.output` plus a correct `TrajectoryMatch` F1=1.0 is representable because evaluators are independent and run concurrently per case (`pydantic_evals/pydantic_evals/dataset.py:1152-1163`). Tested exhaustively in `tests/evals/test_agentic_evaluators.py`.

**2. Is tool selection quality measured? Yes, with three complementary evaluators.** `ToolCorrectness` (`pydantic_evals/pydantic_evals/evaluators/agentic.py:189-244`) scores multiset correctness (order-insensitive, duplicate-sensitive) with `allow_extra` to distinguish missing vs extra. `TrajectoryMatch` (`pydantic_evals/pydantic_evals/evaluators/agentic.py:286-366`) scores ordering quality via LCS F1 (`in_order`) or multiset F1 (`any_order`) plus an `exact` boolean mode, reporting overlap/LCS, precision, recall, F1 in `reason`. `ArgumentCorrectness` (`pydantic_evals/pydantic_evals/evaluators/agentic.py:384-502`) scores argument quality (`subset` default vs `exact`, top-level key comparison) with `occurrence` selection (`first`/`last`/int) and JSON-parse failure handling. `MaxToolCalls`/`MaxModelRequests` cap call/request counts as cost correlates of tool selection. All handle v2/v3 span name differences and discriminating output functions vs tools (`pydantic_evals/pydantic_evals/evaluators/agentic.py:71-81` constants + `_is_tool_call_span` at `pydantic_evals/pydantic_evals/evaluators/agentic.py:105-136`). Gaps: no semantic tool-choice relevance scoring (e.g., did the agent pick the *best* tool among plausible alternatives); only membership/sequence/argument checks.

**3. Is context usage evaluated? No — collected but not evaluated.** Context-adjacent signals are *reported* as `ReportCase.metrics`/`attributes` and as OTel span attributes, but no evaluator scores them. `_task_run.extract_span_tree_metrics` (`pydantic_evals/pydantic_evals/_task_run.py:59-75`) extracts `requests`, `cost`, `gen_ai.usage.*` (prompt/completion/cached tokens) from span attributes — visible in `EvaluatorContext.metrics` (`pydantic_evals/pydantic_evals/evaluators/context.py:81-84`) and final report tables (`pydantic_evals/pydantic_evals/reporting/__init__.py:101-102`). Users can manually publish custom context metrics via `increment_eval_metric`/`set_eval_attribute` (`pydantic_evals/pydantic_evals/dataset.py:1263-1284`), but the framework ships no `ContextUtilization`, `CacheHitRate`, `RetrievedDocsPrecision`, or `PromptCompression` evaluator. `MaxModelRequests` (`pydantic_evals/pydantic_evals/evaluators/agentic.py:545-582`) and `MaxDuration` (`pydantic_evals/pydantic_evals/evaluators/common.py:177-188`) bound turns/time, not context window fullness or truncation quality. `LLMJudge`/`GEval` could approximate this with a custom rubric but do not natively inspect span-tree context fields. Search boundary: grepped `context.*usage`, `token`, `usage`, `cache` across `pydantic_evals/` — only metric extraction and display, no evaluator.

**4. Is recovery behavior measured? Weakly / indirectly.** Three mechanisms exist but none evaluate recovery *quality*: (a) `include_failed` on `ToolCorrectness`/`TrajectoryMatch`/`ArgumentCorrectness` (default `False`, `MaxToolCalls` default `True`) filters spans with `status=='error'` vs `ModelRetry` retrials (`pydantic_evals/pydantic_evals/evaluators/agentic.py:161-174,204-208`). Tests in `tests/evals/test_agentic_evaluators.py:243-303` verify that one errored + one successful attempt collapses to a single logical call by default and expands to two when `include_failed=True`. (b) `HasMatchingSpan` with `has_status='error'` or `some_descendant_has` can assert that an error span appeared, but not that the agent compensated. (c) `OnlineEvaluator.run_on_errors` (`pydantic_evals/pydantic_evals/online.py:253-261`) and `retry_task`/`retry_evaluators` (`pydantic_evals/pydantic_evals/dataset.py:288-293`) address evaluator dispatch on task failure and flaky evaluator retries, not agent recovery logic (e.g., self-correction, fallback tool, graceful degradation). No evaluator like `RecoverySuccess` or `ErrorRecoverySteps` exists; no dataset fixture covers a multi-turn failure-then-success trajectory. Deferred calls (`ApprovalRequired`/`CallDeferred` via `_TOOL_DEFERRAL_NAME_ATTR` at `pydantic_evals/pydantic_evals/evaluators/agentic.py:85`) are explicitly *never* counted, which is correct for non-execution but removes visibility into authorization-recovery paths.

## Architectural Decisions

- **OTel SpanTree as trajectory source of truth** (`pydantic_evals/pydantic_evals/otel/span_tree.py:467-575`, `pydantic_evals/pydantic_evals/_task_run.py:35-77`). Pro: decouples evaluation from agent SDK internals; any span producer (Logfire or raw OTel) works; enables offline re-evaluation via serialized `SpanTree`. Con: ties correctness to instrumentation naming stability — mitigated by duplicating v2/v3 constants locally (`pydantic_evals/pydantic_evals/evaluators/agentic.py:65-89`) and spanning both attribute keys (`tool_arguments` vs `gen_ai.tool.call.arguments`).
- **EvaluatorContext as sole evaluator input** (`pydantic_evals/pydantic_evals/evaluators/context.py:30-103`). Pro: uniform sync/async evaluator interface; evaluators can read `inputs`, `output`, `expected_output`, `metadata`, `metrics`, `span_tree` without per-evaluator plumbing. Con: context is built once per case; incremental step scoring inside a long-running agent requires external instrumentation rather than evaluator callbacks mid-run.
- **Deterministic span evaluators + LLM judges as separate families** (`pydantic_evals/pydantic_evals/evaluators/agentic.py:1-14` vs `pydantic_evals/pydantic_evals/evaluators/common.py:224-339`). Pro: cheap, reproducible trajectory scores (no LLM) compose with rubric scores in one `Dataset.evaluate()` run. Con: two mental models; users must decide when F1 on tool names suffices vs. when an `LLMJudge` rubric is needed for semantic correctness.
- **F1-based partial credit for trajectories** (`pydantic_evals/pydantic_evals/evaluators/agentic.py:252-284`). Pro: avoids brittle exact-match scoring; `in_order` (LCS) rewards correct sequencing while penalizing extras/misses, `any_order` (multiset intersection) tolerates reordering. Con: LCS can over-score when irrelevant tools happen to appear in order; no weighting by tool importance.
- **Report as typed aggregation** (`pydantic_evals/pydantic_evals/reporting/__init__.py:181-392`). `ReportCase` separates `scores` / `assertions` / `labels` by `EvaluationScalar` type; `ReportCaseAggregate` averages numerically with baseline diff rendering. Pro: trajectory scores surface as numeric averages and per-case rows. Con: aggregation is uniform averaging — no per-evaluator weighting or composite trajectory health score.

## Notable Patterns

- **Graceful degradation to `EvaluationReason` on missing telemetry.** Every agentic evaluator catches `SpanTreeRecordingError` and returns `value=False` or `value=0.0` with `_NO_SPAN_TREE_REASON` (`pydantic_evals/pydantic_evals/evaluators/agentic.py:222-226,324-328`), keeping dataset runs green when Logfire is not installed but surfacing failures in reports via `EvaluatorFailure` (`pydantic_evals/pydantic_evals/evaluators/_run_evaluator.py:97-105`).
- **Start-timestamp ordering of trajectories.** `_extract_tool_calls` sorts `tool_spans` by `start_timestamp` before comparison (`pydantic_evals/pydantic_evals/evaluators/agentic.py:165-169`), making order evaluation deterministic regardless of span parentage and immune to insertion order in fixtures (validated in `tests/evals/test_agentic_evaluators.py:198-209`).
- **Dual-version span compatibility without private imports.** Constants are duplicated from `pydantic_ai._instrumentation.InstrumentationNames` with an explicit comment on version drift (`pydantic_evals/pydantic_evals/evaluators/agentic.py:65-70`), allowing `pydantic-evals` to work across instrumentation versions without a hard dependency.
- **Typed `SpanQuery` as evaluator DSL.** `HasMatchingSpan` turns arbitrary step assertions into data: `SpanQuery` (`pydantic_evals/pydantic_evals/otel/span_tree.py:29-89`) enables predicates like `some_descendant_has`, `min_child_count`, `has_status='error'` without writing a custom evaluator — essentially a step-level rule engine over the trajectory graph.

## Tradeoffs

- **Determinism vs semantic depth.** Pure span-based evaluators give bitwise-reproducible scores without LLM cost, but cannot judge *why* a tool was chosen or whether its output was actually used. `LLMJudge`/`GEval` could fill the gap with a rubric referencing `ctx.span_tree` indirectly, but that coupling is manual and not exemplified in docs.
- **Local-tool visibility vs provider-native tools.** Explicit note that "provider-native or server-side builtin tools do not create local spans and will not be counted" (`pydantic_evals/pydantic_evals/evaluators/agentic.py:16-19`). Tradeoff favors clean local-execution accounting and avoids double-counting, at the cost of blind spots for hosted RAG/search tools.
- **Simple `include_failed` boolean vs explicit retry model.** Treating error spans as filtered or counted is easy to reason about and covers the `ModelRetry` case, but conflates user-code exceptions, validation retries, and transient failures. A recovery evaluator would need to distinguish "failed attempt then correct retry" from "multiple failed attempts" — currently indistinguishable without `has_status` queries.
- **Async-first with sync shim.** `Evaluator.evaluate` may be `def` or `async def`, dispatched via `evaluate_sync`/`evaluate_async` and `run_until_complete` (`pydantic_evals/pydantic_evals/evaluators/evaluator.py:214-251`), and dataset execution runs evaluators concurrently via `task_group_gather` (`pydantic_evals/pydantic_evals/dataset.py:1155-1163`). Tradeoff: uniform evaluator authoring at the cost of threading/async edge cases in online path (`pydantic_evals/pydantic_evals/online.py:638-645`).

## Failure Modes / Edge Cases

- **Silent non-counting of non-local tools.** Provider-native tools, web-search, and output functions (`running output function` / `logfire.msg` prefix `running output function:`) are filtered by `_is_tool_call_span` (`pydantic_evals/pydantic_evals/evaluators/agentic.py:105-136`) and related tests (`tests/evals/test_agentic_evaluators.py:211-252`). A user expecting `ToolCorrectness` to count hosted search will get false failures.
- **Deferred calls invisible to all trajectory evaluators.** `ApprovalRequired`/`CallDeferred` spans carrying `pydantic_ai.tool.deferral.name` are never counted (`pydantic_evals/pydantic_evals/evaluators/agentic.py:83-85,121-122`). Authorization-recovery workflows cannot be scored without custom span queries.
- **Arguments unavailable when `include_content=False`.** `ArgumentCorrectness` returns a failing `EvaluationReason` with "include_content may be disabled" (`pydantic_evals/pydantic_evals/evaluators/agentic.py:446-453`), tested for both v2/v3 spans (`tests/evals/test_agentic_evaluators.py:820-831`). Batch runs with privacy-mode instrumentation will systematically fail this evaluator.
- **No span tree degrades differently by evaluator.** `ToolCorrectness` fails as `bool False`, `TrajectoryMatch` as `float 0.0` with same reason string (`pydantic_evals/pydantic_evals/evaluators/agentic.py:222-226 vs 324-328`). Mixed-type filtering in reports (`pydantic_evals/pydantic_evals/reporting/__init__.py:104-112` separates scores/assertions) can surface surprising averages if many cases lack instrumentation.
- **LCS F1 can mask ordering bugs when alphabet is small.** Repeated tool names (e.g., `['search','search','format','format']` vs `['search','format']` yields F1=0.667 in `tests/evals/test_agentic_evaluators.py:518-540`) means an agent looping a tool may still score >0.5. Multiset `any_order` vs `in_order` choice changes score materially without guidance on which to use when.
- **Nested-agent tool calls counted globally.** `_extract_tool_calls` iterates all nodes (`pydantic_evals/pydantic_evals/evaluators/agentic.py:165-169` comment at line 33-34: "including tool calls made by nested sub-agents"). Sub-agent tool noise inflates counts relative to top-level intent unless the user scopes via `HasMatchingSpan` on parent attributes.
- **Metrics present but unevaluated.** Token totals extracted under `gen_ai.usage.*` keys (`pydantic_evals/pydantic_evals/_task_run.py:64-74`) never feed an evaluator; a run that exceeds context would pass all shipped evaluators if tool sequence is correct.

## Future Considerations

- **Context-usage evaluator.** A `ContextUtilization` evaluator reading `ctx.metrics` (`prompt_tokens`, `cached_input_tokens`, `context_limit`) or span attributes (`gen_ai.usage.*`) and scoring proximity to window, truncation, or cache hit rate would close the largest gap. Design note: derive from `HasMatchingSpan` + metric check to avoid a new SpanTree scan.
- **Recovery-quality evaluator.** A dedicated evaluator that distinguishes `status='error'` spans followed by a correcting span (same `tool_name` with different arguments, or a compensating tool) and scores recovery latency/attempts would make `include_failed` semantics first-class. Could combine `SpanNode` ancestor/descendant queries with the existing `retry`/`run_on_errors` plumbing.
- **Weighted trajectory scoring.** Allow per-tool weights or a required-vs-optional partition in `TrajectoryMatch`/`ToolCorrectness` so critical tools (e.g., `commit_transaction`) dominate F1 versus utility tools (e.g., `log_event`).
- **Provider-native tool bridging.** Optionally emit synthetic spans for hosted tools via model response parsing (where available) so trajectory evaluators remain unified; document the boundary explicitly in report output.
- **Deferred-aware mode.** Add `include_deferred` or a separate `DeferredCorrectness` evaluator so authorization flows can be tested without conflating them with executed tools.

## Questions / Gaps

- **No evidence of step-level scoring API.** Searched for per-step callbacks or mid-run evaluator hooks in `pydantic_evals/` — none found. Evaluators only see the final `EvaluatorContext` after the task completes (`pydantic_evals/pydantic_evals/dataset.py:1083-1146`). Incremental trajectory feedback during a long agent loop would require custom instrumentation outside `pydantic_evals`.
- **No dataset fixture for recovery.** Grepped `recovery`, `retry`, `include_failed`, `run_on_errors` — no case in `tests/evals/` asserts a "failed then recovered" happy path via trajectory score. The `ModelRetry` path is unit-tested at span level (`tests/evals/test_agentic_evaluators.py:243-286`) but not as an end-to-end `Dataset.evaluate(agent.run)` scenario.
- **No context-window evaluator despite metric collection.** `tests/evals` and `pydantic_evals/evaluators/` contain no evaluator that reads `gen_ai.usage.*` totals as a score. Token counts are averages on report tables, not pass/fail signals.
- **Trajectory + output independence not benchmarked.** Whether a high trajectory score correlates with correct `ctx.output` is left to user composition of `TrajectoryMatch` + `EqualsExpected`/`LLMJudge`; no built-in correlation view (e.g., scatter of trajectory F1 vs output score) is provided in `reporting/analyses.py`.
