## Summary

Letta is a stateful agent framework (formerly MemGPT) centered on persistent memory, multi-step agent loops, and provider-agnostic LLM orchestration — not a trajectory-evaluation harness. The codebase provides rich **observability and execution-tracking primitives** for intermediate steps (persistent `Step`/`StepMetrics` models, `StepProgression` state machine, OTEL `trace_method` spans, provider traces, `ContextWindowOverview` token breakdowns, and human `feedback` on steps) but **contains no evaluators that score intermediate reasoning, tool-choice quality, context usage efficiency, or recovery behavior**. All five rubric elements — step-by-step eval code, tool-choice evaluators, context-usage metrics as quality signals, recovery eval cases, and aggregated trajectory scoring — are absent. What exists is telemetry and status bookkeeping that *could* be composed into a trajectory evaluator, but is never composed. The closest proxy to trajectory judgment is the binary `feedback: positive|negative` field on `Step` and the `StepStatus` enum (`pending/success/failed/cancelled`), both of which record outcome, not path quality.

## Rating

**2 / 10 — Absent / Implicit**

Rationale: No directory matching `eval*`, `benchmark*`, or `trajectory` exists; `grep` for `trajectory|step.*eval|evaluat.*step` returns only false positives (e.g., tool-rule allowlist evaluation). No LLM-as-judge, rubric, or step-reward code was found. `StepMetrics` tracks latency (`llm_request_ns`, `tool_execution_ns`, `step_ns`) not quality, and `MetricRegistry` exposes performance counters/histograms, not trajectory scores. Human per-step `feedback` and `StepStatus.FAILED` provide outcome labels but no automated assessment of whether the agent took a good path when the final answer was wrong. Recovery is implemented as retry/compaction logic, not measured as a scored behavior.

## Answers to Dimension Questions

**1. Are intermediate steps evaluated?**
No. Intermediate steps are *tracked* in detail — each LLM turn creates a `Step` row (`studies/agent-harness-study/sources/letta/letta/services/step_manager.py:181-248`) with `status`, `stop_reason`, `completion_tokens/prompt_tokens`, `trace_id`, and linked `StepMetrics` latency (`studies/agent-harness-study/sources/letta/letta/schemas/step_metrics.py:19-23`) and `ProviderTrace` request/response (`studies/agent-harness-study/sources/letta/letta/schemas/provider_trace.py:46-48`). OTEL spans are emitted via `trace_method` (`studies/agent-harness-study/sources/letta/letta/otel/tracing.py:228-435`). However, no code evaluates whether a step's reasoning was sound, whether the tool call was appropriate, or whether the step contributed to goal progress. The only qualitative signal is an optional human `feedback` field (`studies/agent-harness-study/sources/letta/letta/schemas/step.py:57-58`) set through `PATCH /v1/steps/{step_id}/feedback` (`studies/agent-harness-study/sources/letta/letta/server/rest_api/routers/v1/steps.py:120-131`), which is binary and unaggregated. No automated step-level scorer, rubric, or LLM-as-judge exists.

**2. Is tool selection quality measured?**
No. Tool execution is counted and timed (`MetricRegistry.tool_execution_counter:106-116`, `tool_execution_time_ms_histogram:144-155` in `studies/agent-harness-study/sources/letta/letta/otel/metric_registry.py`) and each tool invocation can be reconstructed from `ProviderTrace.response_json` and message `tool_calls`/`tool_returns` in `Message` (`studies/agent-harness-study/sources/letta/letta/schemas/message.py:267-292`). `ToolType` and tool-rule logic (`studies/agent-harness-study/sources/letta/letta/helpers/tool_rule_solver.py:55`) constrain which tools *may* be called, but there is no retrospective measurement of precision (did the agent pick the right tool?), recall (did it miss a needed tool?), redundancy (did it call tools unnecessarily?), or argument correctness. Tests such as `integration_test_builtin_tools` exercise tool execution, but assert functional outcome, not choice quality.

**3. Is context usage evaluated?**
No, as an evaluation dimension. Context usage is *measured structurally* with high fidelity: `ContextWindowOverview` (`studies/agent-harness-study/sources/letta/letta/schemas/memory.py:23-60`) tokenizes every section (`system_prompt`, `core_memory`, `memory_filesystem`, `tool_usage_rules`, `directories`, `external_memory_summary`, `summary_memory`, `messages`, `functions_definitions`) via `ContextWindowCalculator.calculate_context_window` (`studies/agent-harness-study/sources/letta/letta/services/context_window_calculator/context_window_calculator.py:249-384`) and `TokenCounter` backends. The breakdown is exposed via `get_context_window` (`studies/agent-harness-study/sources/letta/letta/agent.py:1204-1278`) and the `GET /v1/agents/{agent_id}/context` endpoint (`studies/agent-harness-study/sources/letta/letta/server/rest_api/routers/v1/agents.py:588-601`), and is used operationally to trigger summarization when `total_tokens > memory_warning_threshold * context_window` (`studies/agent-harness-study/sources/letta/letta/agent.py:957-959`). But no evaluator scores context efficiency, e.g., tokens wasted, relevant vs. irrelevant recall, or compression fidelity — it is infrastructure for execution, not a metric for trajectory quality.

**4. Is recovery behavior measured?**
No. Recovery is *implemented* but not *measured as a trajectory property*. The agent loop retries on empty responses up to `empty_response_retry_limit=3` (`studies/agent-harness-study/sources/letta/letta/agent.py:306-428`), retries summarization (`letta_agent.py:1426-1480`), and marks failed steps with `update_step_error_async` → `status=FAILED`, `error_type`, `error_data: {message, traceback, details}` (`studies/agent-harness-study/sources/letta/letta/services/step_manager.py:368-414`) plus partial metric capture on failure (`studies/agent-harness-study/sources/letta/letta/agents/letta_agent_v2.py:715-722`). Cancellation is tracked as `StepStatus.CANCELLED` (`studies/agent-harness-study/sources/letta/letta/schemas/enums.py:273`). There are no tests or metrics for recovery rate, time-to-recovery, whether the post-failure path was minimal or meandering, or whether the agent learned from the error within the same trajectory. The error taxonomy is a string (`type(e).__name__`), not a scored recovery event.

## Architectural Decisions

- **Persistent step as primary trajectory primitive.** Every agent turn is reified as a `Step` ORM row (`studies/agent-harness-study/sources/letta/letta/orm/step.py` via `studies/agent-harness-study/sources/letta/letta/services/step_manager.py:96-173`) with foreign keys to `agent_id`, `run_id`, and token usage. This makes trajectories *reconstructable* from DB alone, but the decision stops at storage/observability — no evaluation layer is layered above it.
- **Latency-centric StepMetrics.** `StepMetrics` (`studies/agent-harness-study/sources/letta/letta/schemas/step_metrics.py:13-26`) was introduced to capture `llm_request_ns / tool_execution_ns / step_ns` for performance analysis and is dual-written via `record_step_metrics_async` (`studies/agent-harness-study/sources/letta/letta/services/step_manager.py:562-652`). The choice to model only nanosecond durations (plus cloud-only `template_id/base_template_id/project_id`) explicitly avoids quality scoring; extending it to hold reward signals would require a schema change.
- **OTEL for trajectory observability, not evaluation.** `trace_method` (`studies/agent-harness-study/sources/letta/letta/otel/tracing.py:228-435`) and `TelemetryManager` with multi-backend dual-write (`studies/agent-harness-study/sources/letta/letta/services/telemetry_manager.py:16-68`) give a complete provider-request lifecycle with `step_id` correlation, but the design delegates any judgment to external systems (e.g., Grafana/ClickHouse). The `_excluded_v1_endpoints_regex` and `_included_v1_endpoints_regex` filters show deliberate sampling, not exhaustive trajectory capture for eval.
- **Human feedback as the quality escape hatch.** `feedback: positive|negative` on `Step` plus `tags` (`studies/agent-harness-study/sources/letta/letta/schemas/step.py:57-58`) and query filters `feedback/has_feedback` (`studies/agent-harness-study/sources/letta/letta/server/rest_api/routers/v1/steps.py:35-36`) push trajectory judgment to humans. This keeps the core framework unopinionated but leaves automated trajectory evaluation entirely to consumers.
- **Context window as execution concern.** `ContextWindowCalculator` was factored into a dedicated service (`studies/agent-harness-study/sources/letta/letta/services/context_window_calculator/context_window_calculator.py:19-384`) with pluggable `TokenCounter` backends (tiktoken/Anthropic/Gemini) and exhaustive `extract_system_components` parsing, precisely because Letta's long-horizon memory is realized as context compaction. The decision to expose it as an operational API (`GET /context`) rather than an evaluation signal is consistent with the framework's role as a memory provider, not a judge.

## Notable Patterns

- **Checkpointed step progression.** `letta_agent_v2.py:941-1034` implements `_step_checkpoint_start / _step_checkpoint_llm_request_start / _step_checkpoint_llm_request_finish / _step_checkpoint_finish`, threading `StepMetrics` and `Span` through each phase and persisting partial metrics even on exception (`studies/agent-harness-study/sources/letta/letta/agents/letta_agent_v2.py:715-722`). This pattern would be the natural insertion point for per-step evaluators, but none are inserted.
- **No-op manager pattern for test/migration isolation.** Both `NoopStepManager` (`studies/agent-harness-study/sources/letta/letta/services/step_manager.py:718-818`) and `NoopTelemetryManager` (`studies/agent-harness-study/sources/letta/letta/services/telemetry_manager.py:105-131`) allow tests to run without DB/telemetry — evidence that trajectory tracking is considered infrastructure to be disabled, not an evaluation invariant.
- **Webhook step completion as trajectory handoff.** `update_step_error_async/success_async/cancelled_async` each call `WebhookService.notify_step_complete` outside the DB session (`studies/agent-harness-study/sources/letta/letta/services/step_manager.py:411-414, 473-476, 552-554`), enabling external trajectory consumers. No canonical webhook consumer that scores trajectories is shipped.

## Tradeoffs

- **Fidelity vs. judgment.** Letta invests heavily in lossless trajectory capture (full `request_json/response_json` in `ProviderTrace`, per-section token breakdown, per-step timing) at the cost of shipping no opinion about path quality. Consumers get perfect replayability but must build their own evaluators; the framework will not tell you whether the agent took a good path when the final answer was wrong.
- **Performance telemetry vs. semantic telemetry.** `MetricRegistry`'s 20+ instruments all measure latency, throughput, saturation, or error counts; none normalize by task difficulty or goal relevance. This yields actionable SRE signals (TTFT, endpoint e2e, DB pool saturation) but provides zero signal for "tool choice was parsimonious" or "context usage was efficient."
- **Binary human feedback vs. graded trajectory scores.** The `positive|negative` feedback field is simple to store and query (`has_feedback` filter), but discards nuance needed for trajectory-level questions ("was step 3 useful even though step 7 failed?"). No aggregation (e.g., trajectory nDCG, step-level F1) is computed from it.
- **Proliferation of agent loop variants without shared eval.** `letta_agent.py`, `letta_agent_v2.py`, `letta_agent_v3.py`, and `voice_agent.py` each implement distinct streaming/retry/summarization logic, but share the same `StepManager`/`TelemetryManager` primitives. Without a canonical trajectory scorer, each variant's path quality cannot be compared apples-to-apples.

## Failure Modes / Edge Cases

- **Silent non-evaluation of failed trajectories.** A step that ends `status=FAILED` with `error_type/error_data` (`studies/agent-harness-study/sources/letta/letta/services/step_manager.py:402-404`) is still a trajectory element, but no evaluator flags that the *preceding* steps may have caused the failure (e.g., poor tool choice leading to context overflow). Root-cause attribution across steps is absent.
- **`allow_partial` / `NoResultFound` swallow missing trajectory data.** `record_step_metrics_async` and `log_step_async` accept `allow_partial=True` and return early without persisting timing (`studies/agent-harness-study/sources/letta/letta/services/step_manager.py:232-237, 604-607`), and `_safe_create_async` in `TelemetryManager` logs and swallows backend errors (`studies/agent-harness-study/sources/letta/letta/services/telemetry_manager.py:69-80`). Incomplete trajectories can therefore appear successful with no warning to an evaluator.
- **Context overflow recovery masks trajectory inefficiency.** The summarization retry loop (`studies/agent-harness-study/sources/letta/letta/agent.py:957-989`, `studies/agent-harness-study/sources/letta/letta/agents/letta_agent.py:1426-1480`) can recover from `context_window_overflow` by compacting and retrying, producing a successful final step despite an earlier wasteful path. Without context-efficiency evaluation, this recovery is indistinguishable from an efficient path.
- **OTEL sampling and truncation discard trajectory signal.** `trace_method` excludes `messages`, `memory`, `system`, `content` from span attributes (`studies/agent-harness-study/sources/letta/letta/otel/tracing.py:252-269`) and truncates at 2 MB per param / 4 MB total, while metrics middleware only tracks opt-in endpoints (`studies/agent-harness-study/sources/letta/letta/otel/metrics.py:24-28`). An evaluator relying on traces would see a lossy view of tool arguments and context.
- **Feedback is optional and unauthenticated for quality.** `add_feedback_async` overwrites `feedback/tags` unconditionally (`studies/agent-harness-study/sources/letta/letta/services/step_manager.py:272-280`) with no rate limiting, audit, or inter-rater agreement. A trajectory dataset built from it would mix unlabeled, sparsely labeled, and inconsistently labeled steps.

## Future Considerations

- Add a first-party `letta/evals/` package with a `TrajectoryEvaluator` interface (`evaluate_step(step, trace, context_overview) -> StepScore` and `evaluate_trajectory(List[Step]) -> TrajectoryScore`) that consumes existing `Step`/`ProviderTrace`/`ContextWindowOverview` without new storage, and ship two reference evaluators: tool-choice parsimony (tool F1 vs. minimal tool set) and context-efficiency (tokens per goal progress).
- Extend `StepMetrics` or introduce `StepEvaluation` sidecar table keyed by `step_id` to hold scored fields (`reasoning_quality`, `tool_correctness`, `context_efficiency`, `recovery_quality`) so evaluation is not forced into latency columns.
- Instrument recovery explicitly: emit `recovery_attempt` span events with `recovery.cause`, `recovery.strategy`, `recovery.latency_ms`, and aggregate `recovery_rate`/`mean_recovery_steps` histograms in `MetricRegistry`, then test them via fault-injection cases (forced empty LLM response, forced context overflow) asserting recovery within N steps.
- Provide trajectory-level aggregation beyond per-step feedback: `TrajectoryScore` with `path_efficiency`, `tool_precision@k`, and `context_overview_delta` computed from `StepModel.list_async` with `run_id` filter, and expose `GET /v1/runs/{run_id}/trajectory/score`.
- Add eval-focused tests parallel to `test_context_window_calculator.py` and `test_managers.py:9880-9939` that run mini-trajectories through `letta_agent_v2` with a stub LLM client asserting step-level scores, not just persistence round-trips.
