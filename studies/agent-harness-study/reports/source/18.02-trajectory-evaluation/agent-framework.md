## Summary

`agent-framework` provides a provider-agnostic evaluation layer that *partially* enables trajectory evaluation but is primarily optimized for final-output quality and tool-correctness checks. The core abstraction `EvalItem` (`python/packages/core/agent_framework/_evaluation.py:182`) stores the full `conversation: list[Message]` as single source of truth; `query`/`response` are derived via a pluggable `ConversationSplitter` (`python/packages/core/agent_framework/_evaluation.py:76`). Built-in splits `LAST_TURN` and `FULL` (`python/packages/core/agent_framework/_evaluation.py:110-178`) plus `EvalItem.per_turn_items()` (`python/packages/core/agent_framework/_evaluation.py:254`) allow scoring at last-turn, whole-trajectory, or per-turn granularity, and custom callables are explicitly supported (`docs/decisions/0023-foundry-evals-integration.md:29`, `python/packages/core/agent_framework/_evaluation.py:95-104`). Tool selection is a first-class evaluation axis via both local checks (`tool_called_check` `python/packages/core/agent_framework/_evaluation.py:1090`, `tool_calls_present` `python/packages/core/agent_framework/_evaluation.py:1173`, `tool_call_args_match` `python/packages/core/agent_framework/_evaluation.py:1215` + `ExpectedToolCall` `python/packages/core/agent_framework/_evaluation.py:139`) and Foundry cloud evaluators (`tool_call_accuracy`, `tool_selection`, `tool_input_accuracy`, `tool_output_utilization`, `tool_call_success` `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:107-126`). Context/groundedness is modeled via `EvalItem.context` (`python/packages/core/agent_framework/_evaluation.py:205`) mapped to `builtin.groundedness` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:297-298`), but no dedicated context-window utilization or retrieval-precision metric exists. Recovery from failure has no evaluator: checkpoint/resume is a runtime feature (`docs/features/durable-agents/README.md:10`) not a measured eval dimension. Scores are tracked per-item with rich structures (`EvalResults` `python/packages/core/agent_framework/_evaluation.py:373`, `EvalItemResult` `python/packages/core/agent_framework/_evaluation.py:326`, `EvalScoreResult` `python/packages/core/agent_framework/_evaluation.py:306` + `RubricScore` `python/packages/core/agent_framework/_evaluation.py:650`), including per-evaluator aggregates, token usage, error categorization, and workflow `sub_results` (`python/packages/core/agent_framework/_evaluation.py:390`), enabling trajectory-level inspection when `FULL` or `per_turn` factoring is used.

## Rating

**Score: 6 / 10** — Present but inconsistent.

Rationale: Intermediate-step and tool-choice evaluation are explicitly modeled, tested, and extensible (split strategies, per-turn items, 5 dedicated tool evaluators, local unordered/arg-matching checks). Context usage is only indirectly covered via `groundedness` and custom `@evaluator` access to `context`/`conversation` — no systematic context-utilization or window-management metric. Recovery behavior is absent as an eval concern (no retry/error-recovery scorers, no trajectory-repair datasets). Trajectory scores are tracked per-item/per-evaluator with portal links and rubric dimensions, but there is no first-class step-by-step scorer that emits a ordered sequence of intermediate judgments inside a single `EvalItem`; per-step signal requires synthesizing `per_turn_items()` or a custom splitter. Documented, protocol-driven, and proven in local + Foundry paths, but not yet durable/observable for full trajectory diagnostics.

## Answers to Dimension Questions

**1. Are intermediate steps evaluated? — Partially yes, via factoring not per-step scoring.**
Implemented behavior: `ConversationSplit.LAST_TURN` (`python/packages/core/agent_framework/_evaluation.py:130`) scores only the final turn; `ConversationSplit.FULL` (`python/packages/core/agent_framework/_evaluation.py:131`, `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:186`) scores the entire trajectory (first user → end) as a single response; `EvalItem.per_turn_items()` (`python/packages/core/agent_framework/_evaluation.py:254`) materializes one item per turn with cumulative history. Custom splitters (`python/packages/core/agent_framework/_evaluation.py:94-104`, `docs/decisions/0023-foundry-evals-integration.md:29`) enable arbitrary cut points (e.g., before a `retrieve_memory` call). This distinguishes trajectory quality from final-answer quality, but there is no built-in ordered step scorer that emits a score per tool-call or reasoning step *within* a single `EvalItem`; such granularity requires synthesizing `per_turn_items()` or a custom splitter and loses tool-result interleaving nuance. Workflow eval partially compensates by extracting per-agent items (`python/packages/core/agent_framework/_evaluation.py:941`). Gaps: no step index, no intermediate reasoning trace field, no built-in "step correctness" evaluator.

**2. Is tool selection quality measured? — Yes, extensively.**
Two layers: (a) Local fast path — `tool_called_check` (`python/packages/core/agent_framework/_evaluation.py:1090`), `tool_calls_present` (`python/packages/core/agent_framework/_evaluation.py:1173`), `tool_call_args_match` (`python/packages/core/agent_framework/_evaluation.py:1215`) with tests `python/packages/core/tests/core/test_local_eval.py:543` — covers presence, unordered extras-OK, and subset arg matching. (b) Foundry cloud — 5 built-in evaluators requiring `tool_definitions`: `tool_call_accuracy`, `tool_selection`, `tool_input_accuracy`, `tool_output_utilization`, `tool_call_success` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:107-126`, constants `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:811-816`). `_build_testing_criteria` wires `tool_definitions` into the data mapping only when items carry tools (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:275-303`), and `_filter_tool_evaluators` drops tool evaluators when no tools present (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:352-380`). Ground truth flows via `ExpectedToolCall` + `evaluate_agent(expected_tool_calls=...)` (`python/packages/core/agent_framework/_evaluation.py:1634`). Limitation: tool trajectory quality (e.g., ordering, redundant calls) is not scored as a sequence — `tool_calls_present` is explicitly unordered and `tool_selection` is delegated to the LLM judge without local deterministic sequencing.

**3. Is context usage evaluated? — Weakly / indirectly.**
Mechanism exists: `EvalItem.context` (`python/packages/core/agent_framework/_evaluation.py:205`) and `@evaluator` injection supports `context`, `conversation`, `tools` (`python/packages/core/agent_framework/_evaluation.py:1296-1332`). Foundry `groundedness` evaluator consumes `context` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:297-298`, `_BUILTIN_EVALUATORS` `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:158`). Workflow `evaluate_agent(context=...)` plumbing confirms grounding intent (`python/packages/core/agent_framework/_evaluation.py:1676`). However, no evaluator measures *context usage* as an operational dimension (e.g., context window utilization, compaction strategy effectiveness, retrieval precision/recall, selective tool-call compaction `python/packages/core/agent_framework/__init__.py:52-53`). Grep for `context.*usage` returned no eval code; `groundedness` is the sole context-related metric and is itself an LLM judge, not a deterministic measurement. Custom `context`-aware `@evaluator`s are possible (`python/packages/core/tests/core/test_local_eval.py:197-205`) but not provided out-of-box.

**4. Is recovery behavior measured? — No.**
No evidence of recovery/fault-tolerance evaluation. Search for `recovery`/`retry.*eval`/`fail.*recover` across the source (`python/packages/core` and `docs`) returned only runtime checkpoint/resume features (`docs/features/durable-agents/README.md:10`, `python/packages/core/agent_framework/_workflows/_workflow.py:809`, `python/packages/core/tests/workflow/test_functional_workflow.py:592`) and a sample demonstrating tool failure continuation (`python/samples/02-agents/tools/function_tool_recover_from_failures.py:16`), none wired into `Evaluator`. No evaluator scores whether an agent retries correctly after a tool error, recovers from `FunctionResult` errors, or degrades gracefully; `LocalEvaluator` treats any check failure as item `fail` but does not model multi-step repair trajectories. Workflow checkpoint recovery (`WorkflowCheckpoint` `python/packages/core/agent_framework/__init__.py:265`) is durability infrastructure, not an eval dimension. Missing: error-injection eval datasets, recovery success-rate scorers, or trajectory-replay after failure.

## Architectural Decisions

- **Conversation-as-source-of-truth with pluggable splitting.** Storing `conversation` on `EvalItem` (`python/packages/core/agent_framework/_evaluation.py:182`) and deriving `query`/`response` via `ConversationSplitter` (`python/packages/core/agent_framework/_evaluation.py:76`) keeps one canonical record while allowing multiple evaluation lenses (last-turn vs full vs per-turn vs custom) without duplicating data. Decision rationale documented in `docs/decisions/0023-foundry-evals-integration.md:29-33` (factoring measures different things). Tradeoff: flexibility pushes complexity to callers who must pick the right split; no guidance enforces consistency across evaluators.

- **Provider-agnostic `Evaluator` protocol with orchestration helpers.** `Evaluator` (`python/packages/core/agent_framework/_evaluation.py:683`) has only `name` + `evaluate(items)→EvalResults`; orchestration (`evaluate_agent` `python/packages/core/agent_framework/_evaluation.py:1629`, `evaluate_workflow` `python/packages/core/agent_framework/_evaluation.py:1833`, `_run_evaluators` `python/packages/core/agent_framework/_evaluation.py:2088`) extracts `FunctionTool` schemas via `AgentEvalConverter` (`python/packages/core/agent_framework/_evaluation.py:733`) and handles `num_repetitions` consistency measurement. This isolates tool extraction and conversation factoring from evaluator logic, enabling `LocalEvaluator` and `FoundryEvals` to interoperate (`docs/decisions/0023-foundry-evals-integration.md:45-53`). Tradeoff: `experimental` feature flag (`python/packages/core/agent_framework/_evaluation.py:68`) signals instability.

- **Two-tier evaluation: local deterministic checks + cloud LLM judges.** Local path (`LocalEvaluator` `python/packages/core/agent_framework/_evaluation.py:1519`, `tool_calls_present`/`tool_call_args_match`) is API-free and CI-friendly; cloud path (`FoundryEvals` `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:728`) delegates to Foundry's 18 built-in evaluators (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:142-166`) including agent-behavior (`task_adherence`, `intent_resolution`), quality, safety, and tool suites. Auto-defaults (`_resolve_default_evaluators` `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:332`) and filtering (`_filter_tool_evaluators` `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:352`) keep zero-config friction low.

- **Explicit tool-definition propagation.** `AgentEvalConverter.extract_tools` (`python/packages/core/agent_framework/_evaluation.py:848`) and `to_eval_item` (`python/packages/core/agent_framework/_evaluation.py:884`) pull `FunctionTool` and MCP tools into `EvalItem.tools`, then serialized as `tool_definitions` for Foundry (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:915-918`). Known limitation: multi-modal reasoning is acknowledged as incomplete — `query`/`response` string projections are text-only; full `conversation` must be used for multi-modal evaluators (`docs/decisions/0023-foundry-evals-integration.md:555-557`).

## Notable Patterns

- **Parameter-name injection for function evaluators.** `@evaluator` (`python/packages/core/agent_framework/_evaluation.py:1415`) inspects `inspect.signature` to inject `query`, `response`, `expected_output`, `conversation`, `tools`, `context` into plain functions, supporting sync/async and flexible return coercion (`bool`/`float`/`dict`/`CheckResult` via `_coerce_result` `python/packages/core/agent_framework/_evaluation.py:1354`). Documented as three tiers (simple → ground-truth → full context) in `docs/decisions/0023-foundry-evals-integration.md:482-514`.

- **Rich result hierarchy with portal observability.** `EvalResults` (`python/packages/core/agent_framework/_evaluation.py:373`) aggregates `result_counts`, `per_evaluator`, `items: list[EvalItemResult]`, `sub_results` (per-agent for workflows), `report_url`, and offers CI helpers `raise_for_status()` (`python/packages/core/agent_framework/_evaluation.py:470`), `assert_score_at_least()` (`python/packages/core/agent_framework/_evaluation.py:502`), `assert_dimension_score_at_least()` (`python/packages/core/agent_framework/_evaluation.py:545`), `assert_no_failed_items()` (`python/packages/core/agent_framework/_evaluation.py:616`). Foundry's `_fetch_output_items` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:560`) preserves `token_usage` and `error_code`.

- **Workflow per-agent vs overall decomposition.** `evaluate_workflow` (`python/packages/core/agent_framework/_evaluation.py:1833`) walks `WorkflowRunResult` events, groups by `executor_id`, builds shared `agent_items_by_id`, and nests results in `overall_result.sub_results` (`python/packages/core/agent_framework/_evaluation.py:1986-2021`). Sample usage at `python/samples/05-end-to-end/workflow_evaluation/run_evaluation.py` (glob match, not read in detail due to bandwidth cap).

- **Defensive compatibility for evolving rubric payloads.** `_extract_rubric_scores` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:512`) and `_parse_dimension_entries` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:461`) accept both `dimension_scores` and legacy `rubric_scores` keys and tolerate dict/object shapes — forward/backward compatible parsing (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:450-459`).

## Tradeoffs

- **Whole-trajectory vs per-step precision.** `FULL` split (`python/packages/core/agent_framework/_evaluation.py:167`) scores the entire trajectory as a single item — simple and LLM-judge-friendly but conflates multiple steps into one score, masking where failure occurred. `per_turn_items()` (`python/packages/core/agent_framework/_evaluation.py:254`) restores localization at turn boundaries but not at individual tool-call boundaries; truly step-wise tool sequencing errors require custom splitters, increasing authoring cost.

- **Local determinism vs cloud fidelity.** Local checks (`keyword_check` `python/packages/core/agent_framework/_evaluation.py:1062`) are fast, reproducible, and offline but shallow (keyword presence, tool name presence). Cloud evaluators (`builtin.task_adherence`, `tool_selection` `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:107`) are richer but LLM-judged, non-deterministic, billable, and require `model`/`project_client` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:842`). No hybrid scorer bridges the gap (e.g., deterministic tool-sequence diff + LLM rationale).

- **Expressiveness vs ergonomics of `ExpectedToolCall`.** `ExpectedToolCall.arguments` subset matching (`python/packages/core/agent_framework/_evaluation.py:1256`) tolerates extra args (e.g., `units` field) — robust against model verbosity but may hide over-specification bugs where the agent hallucinates unrelated arguments.

- **Experimental stability.** All eval types are gated by `@experimental(feature_id=ExperimentalFeature.EVALS)` (`python/packages/core/agent_framework/_evaluation.py:68`, `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:60`). This permits rapid iteration per `python/PACKAGE_STATUS.md` lifecycle but signals breaking-change risk for trajectory-eval consumers.

## Failure Modes / Edge Cases

- **Split mismatch silently changes what's scored.** Passing `conversation_split=FULL` (`python/packages/core/agent_framework/_evaluation.py:1639`) versus default `LAST_TURN` yields materially different `query`/`response` pairs from the same `EvalItem`; no warning is emitted if callers inconsistently mix splits across evaluators. Workflow's stamping (`python/packages/core/agent_framework/_evaluation.py:1978-1983`) overwrites per-item `split_strategy`, so per-item custom strategies are lost when `evaluate_workflow(conversation_split=...)` is used.

- **Tool-evaluator prerequisite not surfaced until runtime.** Requesting `tool_call_accuracy`/`tool_selection` without `tools` raises `ValueError` only inside `_filter_tool_evaluators` after data collection (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:371-376`), and doc warns `evaluate_agent(responses=...)` must provide `queries` + agent tool definitions (`docs/decisions/0023-foundry-evals-integration.md:549-550`). Pre-flight validation does not catch missing tool schemas earlier.

- **Multi-modal gap.** `AgentEvalConverter.convert_message` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:743`, `python/packages/core/agent_framework/_evaluation.py:742`) correctly handles `input_image` content, but `EvalItem.query`/`response` string properties (`python/packages/core/agent_framework/_evaluation.py:218-229`) are text-only and `FunctionEvaluator` string overloads are text-only (`docs/decisions/0023-foundry-evals-integration.md:557`). Trajectory evaluations relying on string projections silently drop image context.

- **No trajectory-repair or retry tracking.** `LocalEvaluator` aggregates per-item `failed` via `counts["failed"] += 1` (`python/packages/core/agent_framework/_evaluation.py:1584`) but does not model temporal dependencies (e.g., tool error → agent retry → success). A trajectory that recovers after one failed tool call is scored identically to one that never failed at the tool level if final tool set matches `tool_calls_present`. Score for `tool_call_success` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:115`) is delegated to the LLM judge with no deterministic trace of intermediate `tool_result` error payloads.

- **Rubric dimension ambiguity.** `_parse_dimension_entries` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:461`) silently skips malformed entries (`continue` on missing `id`/`weight`/`applicable` `python/packages/foundry/agent_framework_foundry/_foundry_evals.py:496-497`) and `_extract_rubric_scores` returns `None` when no dimensions present (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:557`). Consumers calling `assert_dimension_score_at_least` with `require_applicable=False` (default) may silently pass when dimensions were never produced.

- **Polling timeout obscures trajectory results.** `_poll_eval_run` (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:383`) returns a synthetic `EvalResults(status="timeout")` with no `items` or `per_evaluator`; callers checking `all_passed` (`python/packages/core/agent_framework/_evaluation.py:456`) will get `False` but lose per-item trajectory scores for diagnostics. `timeout` defaults to 180s (`python/packages/foundry/agent_framework_foundry/_foundry_evals.py:840`) and is not adaptive to item count.

## Future Considerations

- Add a first-class stepwise trajectory scorer that emits an ordered `list[StepScore]` (step index, `tool_call_id`, `passed`, `reason`) per `EvalItem` instead of requiring synthetic `per_turn_items()` expansion; this would answer "good path even if final answer wrong" without custom splitters.
- Introduce explicit recovery evaluators: `retry_after_error_check`, `tool_error_recovery_check`, or Foundry-side `task_recovery_efficiency` leveraging error-injected `EvalItem` fixtures that assert the agent retries correctly after `function_result` error payloads.
