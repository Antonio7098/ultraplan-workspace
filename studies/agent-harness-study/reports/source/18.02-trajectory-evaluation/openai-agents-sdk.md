## Summary

`openai-agents-sdk` is a production agent-harness, not an evaluation harness. It provides no built-in trajectory evaluation: no step scorer, no tool-choice quality metric, no context-grounding evaluator, no recovery benchmark, and no aggregated trajectory score. What it *does* provide is best-in-class observability primitives that make external trajectory evaluation possible — `trace()`/`agent_span()`/`generation_span()`/`function_span()`/`guardrail_span()`/`handoff_span()` (`src/agents/tracing/create.py:89-350`), `TurnSpanData`/`TaskSpanData` with per-turn and per-run usage (`src/agents/tracing/span_data.py:64-132`, `src/agents/usage.py:434-485`), `RunResult.raw_responses`/`new_items`/`input_guardrail_results`/`output_guardrail_results` (`src/agents/result.py:309-337`), and lifecycle hooks (`src/agents/lifecycle.py:13-103`). Final-output artifact validators exist only as tutorial demos (`examples/sandbox/tutorials/dataroom_metric_extract/evals.py:240`, `examples/sandbox/tutorials/repo_code_review/evals.py:21`) and the `llm_as_a_judge` pattern is a user-side loop (`examples/agent_patterns/llm_as_a_judge.py:25-71`), not an SDK evaluator. Official docs explicitly defer evaluation to the external OpenAI Evals platform (`docs/index.md:9`, `docs/multi_agent.md:39`). Recovery is implemented operationally (`src/agents/run_internal/model_retry.py:389`, `src/agents/retry.py:239`) but never scored.

## Rating

**2 / 10 — Absent / Ad-hoc**

Rationale: All five dimension questions score negative on implemented behavior. Intermediate-step quality, tool-selection quality, context-use relevance, and recovery adaptability have no evaluator, metric, or test in `src/`. The only “scores” are token counts and a demo `Literal["pass","needs_improvement","fail"]` in an example. Tracing and hooks provide observation, not judgment; even the two checked-in `evals.py` files assert exact final-artifact equality, not trajectory path quality. External platform evals are referenced but not integrated, instrumented, or tested inside this repo.

## Answers to Dimension Questions

**1. Are intermediate steps evaluated?**
No. The SDK emits fine-grained spans (`generation_span`, `function_span`, `guardrail_span`, `handoff_span`, per-turn `turn_span` and per-run `task_span` in `src/agents/tracing/create.py:124-350` and `src/agents/tracing/span_data.py:28-315`) and exposes `RunResult.new_items` / `raw_responses` / guardrail results (`src/agents/result.py:315-336`) plus lifecycle hooks (`src/agents/lifecycle.py:18-103`). None of these is scored. The only step-aware checks are demo final-artifact validators that ignore the path (`examples/sandbox/tutorials/dataroom_metric_extract/evals.py:240`). The `llm_as_a_judge` loop (`examples/agent_patterns/llm_as_a_judge.py:31-39`) is a recommended user pattern, not a built-in intermediate-step evaluator. So: observable, not evaluated.

**2. Is tool selection quality measured?**
No. Tool-choice machinery validates configuration (`src/agents/tool.py:1612` `ensure_tool_choice_supports_backend`, `src/agents/tool.py:1703` `tool_choice` wiring, reset logic in `tests/test_tool_choice_reset.py:19-41`) and tracing records which tools were available (`AgentSpanData.tools` at `src/agents/tracing/span_data.py:36`) and which were called (`FunctionSpanData.name` at `src/agents/tracing/span_data.py:135-166`). No metric checks whether the agent chose the right tool, the right arguments, the minimal tool set, or avoided redundant calls. No test in `tests/` asserts tool-choice correctness as a score.

**3. Is context usage evaluated?**
No — only counted. `Usage` and its helpers (`src/agents/usage.py:195`, `src/agents/usage.py:434-485`) and span helpers (`src/agents/tracing/span_data.py:64-97` `TaskSpanData`, `98-132` `TurnSpanData`) aggregate token volumes and cache hits. `GenerationSpanData` can optionally capture full `input`/`output` (`src/agents/tracing/span_data.py:172-209`) when `trace_include_sensitive_data` is true (`docs/tracing.md:132-140`). There is no evaluator for retrieval relevance, citation faithfulness, context-window efficiency, or “did the agent use the provided file-search result.” Session compaction and server-managed conversation tracking (`src/agents/run_internal/oai_conversation.py:131`, `src/agents/run_state.py:200`) manage context mechanically without scoring its use.

**4. Is recovery behavior measured?**
No — implemented, not measured. Retry/ backoff (`src/agents/run_internal/model_retry.py:389` `_evaluate_retry`, `src/agents/run_internal/run_loop.py:2237` `stream_response_with_retry`) and queue/sandbox cleanup on streamed runs (`src/agents/result.py:752-787`) provide operational recovery. Spans can record an error (`src/agents/tracing/spans.py:373` `set_error`, `src/agents/tracing/spans.py:396` `export` with `error`) and `RunErrorDetails` captures `new_items`/`raw_responses`/`last_agent` (`src/agents/exceptions.py:418-425`). No evaluator grades “time-to-recovery,” “self-correction rate,” or “degraded vs. failed trajectory”; HITL resume tests (`tests/test_agent_tracing.py:272-393`) only assert trace reuse and usage deltas, not recovery quality. The tutorial `evals.py` files treat a wrong row set as a hard fail with no partial credit or retry-path analysis.

## Architectural Decisions

*   **Observability over evaluation** (`src/agents/tracing/__init__.py:1-42`, `docs/tracing.md:14-46`): The SDK chose a tracing-first architecture — `Trace`/`Span` with `TraceProvider` + `BatchTraceProcessor` + `BackendSpanExporter` (`src/agents/tracing/processors.py:44-762`). This cleanly separates “record what happened” from “judge whether it was good,” leaving judgment to the external Evals API or user code (`docs/multi_agent.md:39`). Tradeoff: durable, low-overhead observability now; no in-repo trajectory rubric.
*   **Final-artifact validators as tutorials, not a framework** (`examples/sandbox/tutorials/dataroom_metric_extract/evals.py:1-315`, `examples/sandbox/tutorials/repo_code_review/evals.py:1-79`): Evals live beside example output directories and are invoked manually (`uv run python .../evals.py --artifact-path ...`). They assert exact set equality, not trajectory. This avoids coupling the core harness to benchmark datasets but means trajectory regression needs external tooling.
*   **Hooks + `RunResult` as the extensibility seam** (`src/agents/lifecycle.py:13`, `src/agents/result.py:309`, `src/agents/run_context.py:1356`): Instead of shipping scorers, the SDK exposes `RunHooks`/`AgentHooks` and a rich `RunResult`/`RunState` for users or platform services to consume. This is intentionally unopinionated but leaves the trajectory-evaluation gap unfilled.
*   **Retry as transport concern, not as evaluated behavior** (`src/agents/run_internal/model_retry.py:505-554`, `src/agents/models/interface.py` via `ModelRetryAdvice`): Retries are gated by `retry_settings.max_retries` and provider advice, with usage folding (`apply_retry_attempt_usage` at `src/agents/run_internal/model_retry.py:338`), not by trajectory quality signals.
*   **Sensitive-data controls gate evaluation data** (`docs/tracing.md:132-140`, `src/agents/tracing/create.py:188-233` `GenerationSpanData`): Full inputs/outputs are optional and redacted by exporter (`src/agents/tracing/processors.py:261-319` truncation + sanitization), which is correct for privacy but forces any deep trajectory scorer to explicitly opt into `trace_include_sensitive_data`.

## Notable Patterns

*   **Span hierarchy mirrors the run loop:** `trace()` → `task_span` (one `Runner.run`) → `agent_span` (one agent segment) → `turn_span` (one LLM→tools→output loop) → `generation_span`/`function_span`/`guardrail_span`/`handoff_span` (`src/agents/tracing/create.py:124-350`, `tests/test_agent_tracing.py:99-185` asserts parent_id chain `task→agent→turn→generation`). This is an excellent skeleton for a trajectory scorer, but no scorer is attached.
*   **Usage folding for retried calls:** `apply_retry_attempt_usage()` and `turn_usage_to_span_data()`/`task_usage_to_span_data()` ensure retried model calls do not double-count in spans (`src/agents/run_internal/run_loop.py:2291-2303`, `src/agents/usage.py:434-485`). Again, operational accounting without qualitative scoring.
*   **Deterministic scripted model for tests:** `ScriptedModel`/`ModelStep` in `src/agents/testing/model.py:249-538` records every `ModelCall` (system_instructions, input, model_settings, tools, tracing) and replays fixed `output`/`usage`/`error`/`stream_events` — ideal for trajectory unit tests, yet the test suite uses it to assert span counts and guardrail tripwires rather than trajectory grades.
*   **Platform hand-off for evals:** The repo’s only stable eval guidance is hyperlinks to `https://platform.openai.com/docs/guides/evals` (`docs/index.md:9`, `docs/multi_agent.md:39`), matching the SDK’s role as a harness that exports traces to that platform.

## Tradeoffs

*   **Pro: Minimal core, maximal integrability.** By not bundling a domain-specific rubric (e.g., finance QA, code review), the SDK avoids opinionated scoring that would rot. The tracing processor abstraction (`TracingProcessor` in `src/agents/tracing/processor_interface.py`) lets third-party observability vendors (W&B, LangSmith, Phoenix, etc., listed in `docs/tracing.md:194-226`) attach their own trajectory analytics without forking the core.
*   **Pro: Privacy-safe by default.** Truncation (100 KB field cap), sanitization, and retry-bounded export (`src/agents/tracing/processors.py:45-431`) keep trace volume bounded even under failure loops — important if a future trajectory scorer were to replay full payloads.
*   **Con: No guardrail against trajectory regresssion.** Without an in-repo `TrajectoryScorer` interface or fixture, PRs cannot prevent “final answer still passes but took 4 redundant tool calls” regressions. The demo `evals.py` would not catch it.
*   **Con: Duplication for every team.** Every adopter must reinvent intermediate-step rubrics (tool-choice correctness, context relevance, recovery self-correction) on top of the same `RunResult`/`Trace` data. The `llm_as_a_judge` demo (`examples/agent_patterns/llm_as_a_judge.py:1-89`) shows the pattern once but provides no reusable `Evaluator` abstraction or trajectory-assertion library.
*   **Con: Recovery tested for correctness, not graded.** HITL resume and retry paths are well exercised (`tests/test_run_state.py`, `tests/test_hitl_error_scenarios.py`, `tests/test_agent_tracing.py:272`+), but as functional tests (“does resume work?”), not as graded recoverability benchmarks.

## Failure Modes / Edge Cases

*   **Silent trajectory degradation:** An agent that adds an unnecessary web-search call before answering still yields a valid final artifact; `evals.py` exact-set checks (`examples/sandbox/tutorials/dataroom_metric_extract/evals.py:268-300`) would still pass because they ignore the span sequence. No in-repo detector would flag tool-choice bloat.
*   **Cache-aware usage misinterpreted as context-use quality:** `Usage.input_tokens_details.cached_tokens`/`cache_write_tokens` (`src/agents/usage.py:71-82`) are exported to spans, but a scorer that naively rewards low `input_tokens` could reward truncation rather than efficient context use; no guidance distinguishes the two.
*   **Sensitive-data gating blinds deep evaluation:** With `trace_include_sensitive_data=False` (common under ZDR, `docs/tracing.md:13`), `generation_span`/`function_span` inputs/outputs are withheld from traces, so a post-hoc trajectory evaluator loses prompt/context fidelity (`src/agents/tracing/create.py:188-209`, `src/agents/tracing/processors.py:261-279`).
*   **Queue-full trace loss:** `BatchTraceProcessor` drops spans when the queue is full (`src/agents/tracing/processors.py:602-621` “Queue is full, dropping trace/span”) — a long looping trajectory under failure could lose the very spans needed to diagnose recovery, with only a warning log.
*   **Retry masking:** Because retries are folded into usage and then hidden behind a single successful `response_span`, a trajectory that succeeded after 3 retries looks token-similar to one that succeeded first-try unless the scorer inspects `failed_retry_attempts` (`src/agents/run_internal/run_loop.py:2235`, `src/agents/run_internal/model_retry.py:338`) — which tracing does not surface as a distinct span type.
*   **External eval drift:** Delegating all judgment to `platform.openai.com/docs/guides/evals` means in-repo changes to span shapes or `RunResult` fields can silently break external trajectory evals that parse exported traces; there is no contract test tying `GenerationSpanData.export()` (`src/agents/tracing/span_data.py:202-209`) to an external eval schema.

## Future Considerations

*   Add a minimal `TrajectoryScorer` interface in `src/agents/testing/` or `src/agents/evaluation/` that consumes `RunResult` + `list[Span]` + `Usage` and returns step scores, avoiding platform lock-in while reusing existing `ModelStep`/`ScriptedModel` infrastructure (`src/agents/testing/model.py:249`). Implement reference scorers: `ToolChoiceAccuracy`, `ContextCitationCoverage`, `RecoverySelfCorrection`.
*   Ship trajectory-assertion helpers for `pytest`: e.g., `assertTrajectory(result).hadToolOrder([...]).usedContext(key).recoveredWithin(turns=2)` built on `fetch_ordered_spans()` / `fetch_normalized_spans()` patterns (`tests/test_agent_tracing.py:99-185`, `tests/testing_processor.py`). This would turn the existing `ScriptedModel` determinism into graded trajectory tests without inventing a full benchmark harness.
*   Export `failed_retry_attempts` and `tool_guardrail_results` as first-class span fields (today `failed_retry_attempts` is internal to `run_loop.py`, and `tool_input/output_guardrail_results` live on `RunResult` only (`src/agents/result.py:333-336`)), so a scorer does not need to infer recovery from indirect usage deltas.
*   Provide an optional OpenTelemetry-compatible or OTLP exporter alongside `BatchTraceProcessor` so trajectory evaluators can join agent spans with application spans outside the OpenAI ingest endpoint; the processor abstraction already supports this (`src/agents/tracing/processor_interface.py`).
*   Document a contract test between `SpanData.export()` payloads (`src/agents/tracing/span_data.py:54-451`) and the recommended external Evals schema so trace-field renames are caught before they break trajectory dashboards.

## Questions / Gaps

*   No evidence found that intermediate reasoning is scored even when the final answer is wrong — there is no “good path, wrong answer” metric. Searched `src/agents/tracing/*.py`, `src/agents/result.py`, `src/agents/lifecycle.py`, `src/agents/usage.py`, and `tests/test_agent_tracing.py`; only span emission and token accounting exist.
*   No evidence found of context-grounding evaluation (e.g., “did the agent cite the retrieved 10-K note?”). The sandbox `10-k-*` fixtures and `FinancialMetric` schemas exist under `examples/sandbox/tutorials/dataroom_metric_extract/` but are only final-value checked; no retrieval-attribution test found.
*   No evidence found of recovery adaptability benchmarks (e.g., inject a tool error, measure self-correction). `tests/test_hitl_error_scenarios.py` and `tests/test_run_internal_error_handlers.py` test error propagation, not graded recovery.
*   No trajectory-score persistence or history — `TraceState` (`src/agents/tracing/traces.py:195`) and `RunState` (`src/agents/run_state.py:763`) store trace/usage/context but no `trajectory_score` or `step_scores` field.
*   Open question for SDK owners: Is trajectory evaluation intentionally out-of-scope (to be owned solely by the Evals platform), or is an in-repo `evaluation/` scaffolding planned that would reuse the tracing/ hooks surface? Current `README.md` and `AGENTS.md` give no signal.
