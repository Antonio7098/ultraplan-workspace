## Summary

Langfuse is not an agent harness but an LLM observability/evaluation platform that **provides the infrastructure** for prompt evaluation and experiments to its users. It does not self-evaluate its own internal prompts. The platform ships a mature evaluation stack: versioned Datasets with `input`/`expectedOutput`/`metadata` and JSON-schema validation, versioned Prompts with labels, LLM-as-judge and code-based evaluators (EvalTemplates + JobConfigurations + JobExecutions), and batch prompt experiments (dataset runs) tracked via `ExperimentCreate` queue and ClickHouse `dataset_run_items_rmt`/`events` tables. Experiment results and scores are aggregated for comparison (`getExperimentsFromEvents`, `getExperimentItemsFromEvents`). LLM-as-judge execution compiles a template prompt with extracted trace/dataset/observation variables and calls an LLM with structured-output scoring (`runLLMAsJudgeEvaluation`). The gap is operational: prompt changes are versioned and can be A/B-tested via experiments, but there is no automatic regression harness or CI gate that blocks a degrading prompt change — evaluation is opt-in (manual `testRunCodeEval`, pre-flight model validation, and `timeScope: EXISTING/NEW` backfills) not enforced before deployment.

## Rating

**Score: 6 / 10 — Present but inconsistent / fragile**

**Rationale:** Datasets, LLM-as-judge, code evals, and experiment tracking are explicit, well-typed, and production-wired (queues, ClickHouse, sharded dispatchers, sampling/delay). However prompt-change testing and regression gating are ad-hoc: `PromptRouter.create`/`duplicatePrompt` only checks dependencies and protected labels, not output quality; `EvalRouter.testRunCodeEval` and evaluator pre-flight validate *configuration*, not prompt quality; CI (`pipeline.yml`) runs unit/integration/e2e tests but has no prompt-eval dataset or LLM-judge gate. A user *can* build a regression suite with datasets + experiments, but the platform does not guarantee it is run before a prompt version with `latest` label ships.

## Answers to Dimension Questions

**1. Are prompt changes tested?**

Partially, and only when users opt in. The platform versions prompts (`prompts` table, `version`, `labels` including `latest`, `promptRouter.allVersions` / `resolvePromptGraph` at `web/src/features/prompts/server/routers/promptRouter.ts:1326`) and provides the machinery to test a prompt change: create a Dataset of representative `input`/`expectedOutput` pairs (`dataset-router.ts:1193`), run a prompt experiment against a specific prompt version (`experimentServiceClickhouse.ts:292` replaces variables, calls LLM, records `dataset_run_items_rmt`), and score outputs via LLM-as-judge or code eval evaluators. However `promptRouter.create` (`promptRouter.ts:297`) never triggers an evaluation; it only checks `checkHasProtectedLabels`, dependency graph, and audit logs. The `testRunCodeEval` harness (`router.ts:1070` -> `codeEvalTestRun.ts:82`) tests evaluator *code*, not prompt quality. Existing prompt tests (`web/src/__tests__/server/prompts.v2.servertest.ts`) assert CRUD/listing, not output correctness. Own prompts (e.g., `in-app-agent-system-prompt.txt:1`) have zero automated tests. So: capability exists, enforcement does not.

**2. Are experiments tracked?**

Yes — explicitly and durably. Experiments are first-class: `ExperimentCreate` queue (`queues.ts:131`) with `projectId/datasetId/runId`, processor `experimentCreateQueueProcessor` (`experimentQueue.ts:16`) that calls `createExperimentJobClickhouse`, which for each dataset item creates a `DATASET_RUN_ITEM_CREATE` ingestion event + LLM completion trace (`experimentServiceClickhouse.ts:73-156`). Runs and items are persisted in `dataset_runs` (Postgres) and `dataset_run_items_rmt` (ClickHouse) plus `events` for observability. Retrieval is via `getExperimentsFromEvents` / `getExperimentItemsFromEvents` / `getExperimentItemsBatchIO` (`experiments.ts:138/1029/1173`) supporting filtered comparison, baseline-vs-comparisons, score aggregations (`obs_scores_avg`, `trace_scores_avg`), cost/latency metrics, and version-aware dataset resolution (`getDatasetVersionForRun`). Metadata includes `experiment_name`, `experiment_run_name`, `structured_output_schema`. No MLflow/W&B integration — tracking is internal and tied to dataset semantics.

**3. Is LLM-as-judge used for evaluation?**

Yes — as the primary automated judge alongside code-based evals. Template type `LLM_AS_JUDGE` stores `prompt` (eval instruction), `vars` (variable names), `provider/model/modelParams`, and `outputDefinition` (typed score schema: NUMERIC/BOOLEAN/CATEGORICAL at `evalService.ts:802-814`). At runtime `runLLMAsJudgeEvaluation` (`evalService.ts:736`) extracts variables from trace/observation/dataset_item via `extractVariablesFromTracingData` (`evalService.ts:1153`), compiles the judge prompt (`evalRuntime.ts:14 compileEvalPrompt`), builds a single user message (`evalRuntime.ts:46`), fetches model config (`deps.fetchModelConfig`), calls `deps.callLLM` with `structuredOutputSchema`, validates with `validateEvalOutputResult`, and normalizes to `CodeEvalScoreWithName` (`evalService.ts:964 toNormalizedScores`). A parallel path handles observation-level judges via `LLMAsJudgeExecution` queue (`queues.ts:348`). Managed prebuilt judges live in `worker/src/constants/managed-evaluators.json:1`. Failure modes (invalid model config, LLM completion error) auto-block the evaluator (`blockEvaluatorConfigs`).

**4. Are regressions caught before deployment?**

No. There is no pre-deployment regression gate for prompts. CI in `.github/workflows/pipeline.yml:398` runs lint/typecheck/build and server/client/e2e tests, including `prompts.v2.servertest.ts` CRUD checks, but no step evaluates prompts against an eval dataset or fails on score degradation. Runtime guards are limited to configuration validation: `getEvaluatorDefinitionPreflightError` (model/provider/outputDefinition) and `assertCodeEvalJobConfigCanRun` / `testRunCodeEval` (mapping + live observation fetch) gating `evalRouter.createJob`/`updateEvalJob` (`router.ts:941/1381`). `createEvalJobs` sampling/delay and block-on-invalid-model-config (`evalService.ts:832-846`) prevent bad judges from spamming but do not catch prompt quality drift. A prompt version can be labeled `latest` and served immediately (`promptRouter.setLabels` at `promptRouter.ts:801`) without any score threshold.

## Tradeoffs

- **Flexibility vs determinism**: LLM-as-judge handles open-ended outputs (NUMERIC/BOOLEAN/CATEGORICAL with reasoning) but is non-deterministic and expensive; no temperature/seed control exposed for judges, no retry-aggregation. `worker/src/features/evaluation/evalService.ts:736`
- **Internal ingestion reuse vs schema divergence**: Experiments reuse `processEventBatch` ingestion (cheap to build, consistent traces) but write path nuance: error runs create ClickHouse traces in ClickHouse path while Postgres path only updates metadata (`experimentServiceClickhouse.ts:372` comment). Migration dual-path (`executeWithDatasetServiceStrategy` versioned vs stateful) adds complexity. `packages/shared/src/server/repositories/dataset-items.ts:355`
- **Powerful filtering vs learning curve**: `FilterState` + `FilterList` + `CTEQueryBuilder` enables post-aggregation score filtering (`obs_scores_avg`/`trace_score_categories`) and per-experiment intersection logic, but requires deep understanding of `experimentItemsTableNativeUiColumnDefinitions` and score CTEs. `packages/shared/src/server/repositories/experiments.ts:875`
- **Sharded queues vs operational overhead**: Separate `EvaluationExecutionSecondaryQueue`, `IngestionSecondaryQueue`, per-shard `EvalExecutionQueue.getInstance({shardingKey})` and `CodeEvalExecutionQueue` isolate high-throughput projects but increase worker registration complexity (`worker/src/app.ts:279`). `packages/shared/src/server/queues.ts:347`
- **Immediate prompt availability vs safety**: Label mutation (`setLabels`) takes effect after cache invalidation (`PromptService.invalidateCache`) with no canary/score gate — fast iteration at cost of regression risk. `web/src/features/prompts/server/routers/promptRouter.ts:801`

## Failure Modes / Edge Cases

- **No pre-deploy prompt regression**: A new prompt version can be promoted to `latest` via `setLabels` without running an experiment; CI has no LLM-judge gate, so semantic regressions ship silently. `web/src/features/prompts/server/routers/promptRouter.ts:801`, `.github/workflows/pipeline.yml:539`
- **Judge model unavailable / misconfigured**: `fetchModelConfig` returning `!valid` blocks the evaluator (`blockEvaluatorConfigs`, `EvaluatorBlockReason.EVAL_MODEL_CONFIG_INVALID`) and throws `UnrecoverableError`; jobs become `CANCELLED` and historical traces remain unscored until unblocked. `worker/src/features/evaluation/evalService.ts:832`
- **LLM completion retry asymmetry**: `experimentQueue.ts:25` retries rate-limit errors via `retryLLMRateLimitError` (re-queues with delay), swallows `isLLMCompletionError`/`UnrecoverableError`, but generic errors rethrow — transient provider errors can still drop items (caught per-item in `experimentServiceClickhouse.ts:356` with `return {success:false}` and no retry). `worker/src/queues/experimentQueue.ts:16`
- **Stale dataset item version**: `jobInputDatasetItemValidFrom` is optional; if omitted `getDatasetItemById` with `validFrom` absent resolves to latest (`validTo IS NULL`), so an experiment run may score against a newer `expectedOutput` than intended. `worker/src/features/evaluation/evalService.ts:501`, `packages/shared/src/server/repositories/dataset-items.ts:1367`
- **Deduplication window is traceId-only**: `createEvalJobs` dedup checks `jobExecution` by `(jobConfigurationId, traceId, datasetItemId, observationId)` but not time — re-ingested traces with same traceId are silently skipped as "already exists" (`evalService.ts:613`), which can mask re-evaluation needs.
- **Prompt variable substitution failure**: `replaceVariablesInPrompt`/`compileTemplateString` logs and returns `{success:false}` per item but does not surface which variable mismatched beyond debug logs; batch continues. `worker/src/features/experiments/experimentServiceClickhouse.ts:167`, `worker/src/features/evaluation/evalRuntime.ts:14`
- **Evaluation loop guard is prefix-only**: Only `environment startsWith "langfuse"` is suppressed for `trace-upsert`; a user trace with same prefix would be incorrectly suppressed, and an internal trace with different env would still create jobs. `worker/src/features/evaluation/evalService.ts:243`
- **Score schema mismatch**: `PersistedEvalOutputDefinitionSchema` / `PersistedEvalOutputDefinitionSchema` validation fails -> `UnrecoverableError("Output definition not found or invalid")`, evaluator halts without partial scoring. `worker/src/features/evaluation/evalService.ts:801`

## Future Considerations

- **Gate prompt promotion on experiment scores**: Add a pre-condition in `promptRouter.setLabels` / `createPrompt` that requires a recent experiment run (filtered to `datasetId` + `promptName@version`) to exceed score thresholds before `latest`/`production` labels can be set; store required `datasetId -> threshold` in `PromptProtectedLabels` or new `promptEvalGates` table.
- **CI prompt-eval job**: Add `.github/workflows/pipeline.yml` job that seeds a minimal dataset + managed prompt, runs `createExperimentJobClickhouse` via seeded worker, asserts LLM-judge scores or required evaluators via shell test (e.g., `worker/src/__tests__/experimentsService.test.ts:1` pattern), and fails PR if scores degrade beyond delta.
- **Golden dataset version pinning**: Always persist `datasetVersion` (validFrom) on `dataset_runs` and require `jobExecution.jobInputDatasetItemValidFrom` to be set; fail experiment creation if version has drifted since run creation (`getDatasetVersionForRun` already exists at `dataset-items.ts:1737`).
- **Deterministic judge harness**: Expose judge `temperature=0`, `seed`, and retry aggregation (majority vote) in `EvalTemplate.modelParams`; record judge prompt hash in `executionTraceId` metadata so prompt changes are diffable alongside score deltas.
- **Disqualified-run visibility**: Surface `createAllDatasetRunItemsWithConfigError` traces (currently just error-level generations) as first-class run failures with structured `error` column aggregation in `getExperimentsFromEventsGeneric` so experiments with bad prompts are not silently treated as zero-item successes.
