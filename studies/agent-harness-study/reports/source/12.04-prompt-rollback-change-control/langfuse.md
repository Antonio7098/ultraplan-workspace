## Summary

Langfuse implements prompt management as **immutable versioned records with movable label pointers** rather than mutable in-place edits. Creating a prompt always appends a new row with `version = max+1` (`web/src/features/prompts/server/actions/createPrompt.ts:87-90`, `141-156`). Deployment/production routing is via labels (`production`, `latest`, custom) stored as `String[] labels` on each version (`packages/shared/prisma/schema.prisma:847`). Moving a label is an atomic transaction that strips the label from old versions and sets it on the target (`web/src/features/prompts/server/utils/updatePromptLabels.ts:17-41`, `web/src/features/prompts/server/actions/updatePrompts.ts:108-132`, `web/src/features/prompts/server/routers/promptRouter.ts:801-995`). Cache coherence is via a Redis epoch token rotated on every mutation (`packages/shared/src/server/services/PromptService/index.ts:177-190`), so label moves become visible to SDK fetches within seconds. Audit logging, RBAC, and protected-label entitlements provide governance, and every observation is stamped with `prompt_id/name/version` enabling post-hoc correlation. There is **no formal multi-reviewer approval workflow, no dedicated `rollback` endpoint, and no automated drift detection**; rollback is a manual label move and drift must be inferred from metrics queries.

## Rating

**6 / 10** — Present but inconsistent / weakly documented / fragile.

Immutability, atomic label transactions (`FOR UPDATE` in `web/src/features/prompts/server/actions/updatePrompts.ts:26-44`), epoch-based cache invalidation (`packages/shared/src/server/services/PromptService/index.ts:177-190`), RBAC-gated protected labels (`web/src/features/prompts/server/routers/promptRouter.ts:1395-1491`), audit logs (`web/src/features/audit-logs/auditLog.ts:27-28`), and full observation→prompt linkage (`packages/shared/src/server/repositories/observations.ts:186-189`) are explicit, tested, and operationally safeguarded. However, review is only a permission check (no approval/4-eyes), rollback has no first-class API/UI action (caller must know the target version and issue `setLabels`/`PATCH`), and prompt drift monitoring is absent — gaps that make the answer to "can a bad prompt be rolled back in under a minute?" technically yes (label move + epoch rotation is <1s) but organizationally fragile.

## Answers to Dimension Questions

**1. Can prompts be rolled back?**
Yes — indirectly, in seconds, but with no dedicated rollback primitive. Prompts are immutable versions (`web/src/features/prompts/server/actions/createPrompt.ts:141-156`); rollback is moving the `production` (or any custom) label back to a prior version via `setLabels` (`web/src/features/prompts/server/routers/promptRouter.ts:801-995`) or `PATCH /api/public/v2/prompts/{name}/{version}` with `newLabels` (`web/src/features/prompts/server/handlers/promptVersionHandler.ts:6-34` → `web/src/features/prompts/server/prompt-api-service.ts:81-130` → `web/src/features/prompts/server/actions/updatePrompts.ts:16-166`). The operation is a single Postgres transaction (`FOR UPDATE` lock at `web/src/features/prompts/server/actions/updatePrompts.ts:26-44`) that strips the label from other versions (`web/src/features/prompts/server/utils/updatePromptLabels.ts:17-41`) and `invalidateCache` rotates the Redis epoch (`packages/shared/src/server/services/PromptService/index.ts:177-190`), so SDK fetches (`PromptService.getPrompt` at `packages/shared/src/server/services/PromptService/index.ts:47-79`) see the rolled-back version after at most one cache miss (<1s if Redis is healthy, otherwise TTL `LANGFUSE_CACHE_PROMPT_TTL_SECONDS`). Deleting a version that held `latest` automatically reattaches `latest` to the highest survivor (`web/src/features/prompts/server/actions/deletePrompt.ts:94-119`), but content rollback still requires an explicit label move. No `rollback` endpoint or one-click UI button exists; the caller must know the target `version` number.

**2. Are prompt changes reviewed?**
Partially — permission-gated, not workflow-reviewed. There is no approval queue, draft state, or required reviewer list. `commitMessage` (`packages/shared/src/features/prompts/constants.ts:3`, `packages/shared/src/features/prompts/types.ts:40`) is optional free text, not a review gate. The only review-like control is **protected labels** (EE feature): admins can mark labels (e.g., `production`) as protected via `promptRouter.addProtectedLabel` (`web/src/features/prompts/server/routers/promptRouter.ts:1395-1447`); any `create`/`delete`/`setLabels` touching a protected label checks `checkHasProtectedLabels` (`web/src/features/prompts/server/utils/checkHasProtectedLabels.ts:3-25`) and requires `scope: 'promptProtectedLabels:CUD'` (`web/src/features/rbac/constants/projectAccessRights.ts:38`) plus `entitlement: 'prompt-protected-labels'`. Regular creates/updates also require `scope: 'prompts:CUD'` (`web/src/features/prompts/server/routers/promptRouter.ts:297-349,801-995`). Every mutation is `auditLog`'d (`web/src/features/audit-logs/auditLog.ts:27-28`, `web/src/features/prompts/server/routers/promptRouter.ts:337-347`) with `before/after`, but audit is retrospective, not a blocking review.

**3. Can production issues be linked to prompt changes?**
Yes — strongly, via persisted prompt linkage on every observation plus queryable metrics. `observations` rows store `prompt_id`, `prompt_name`, `prompt_version` at ingestion (`packages/shared/src/server/repositories/observations.ts:186-189`, `packages/shared/prisma/schema.prisma:462-475`, `packages/shared/src/server/repositories/definitions.ts:585-587`). The public ingestion path links generations to prompts (`web/src/__tests__/server/prompts.v2.servertest.ts:414-484`) and ClickHouse repositories can filter/group by those columns (`packages/shared/src/server/repositories/observations.ts:1436-1565`). `promptRouter.metrics` (`web/src/features/prompts/server/routers/promptRouter.ts:251-276`) and `versionMetrics` (`web/src/features/prompts/server/routers/promptRouter.ts:1275-1325`) call `getObservationsWithPromptName` / `getObservationMetricsForPrompts` / `getAggregatedScoresForPrompts` to return per-version `observationCount`, `firstUsed`/`lastUsed`, `medianOutput/inputTokens`, `medianTotalCost`, `medianLatency`, and aggregated `observationScores`/`traceScores` over a caller-supplied time window. `PromptService` also persists the `resolutionGraph` (`packages/shared/src/server/services/PromptService/types.ts:28-31`) documenting transitive prompt dependencies at fetch time. Combined with `audit_logs` (who moved which label when, `web/src/features/audit-logs/auditLog.ts:84-121`), an incident can be correlated to the exact prompt version/label that was live for any time range.

**4. Is prompt drift monitored?**
No evidence found. A repository-wide `grep` for `drift` returns only search/parser comments, feature-flag rollback notes, and doc-referencing inserts — zero prompt-specific drift logic. There is no scheduled job, monitor, or alert that compares live prompt output, embedding distance, or score distribution against a baseline. The building blocks for manual drift analysis exist — `getObservationMetricsForPrompts` / `versionMetrics` and the dashboard/monitor `scheduler` types (`packages/shared/src/features/monitors/scheduler/types.test.ts`) — but they require the operator to poll or build custom monitors; no out-of-the-box "prompt drift" rule ships. ## Architectural Decisions

- **Immutable version + mutable label pointer** (`packages/shared/prisma/schema.prisma:841-847`, `web/src/features/prompts/server/actions/createPrompt.ts:141-156`): Version rows are never updated in place for content/config; `version` auto-increments (`latest.version+1` or `1`). Deployment is a label row-update, not a content mutation — simplifies rollback and audit but means every edit is a new version.
- **Labels are unique per prompt name** enforced transactionally: before creating or moving a label, all other versions holding that label are stripped in the same `$transaction` (`web/src/features/prompts/server/utils/updatePromptLabels.ts:17-41`, `web/src/features/prompts/server/actions/createPrompt.ts:171-184`, `web/src/features/prompts/server/actions/updatePrompts.ts:108-132`). Prevents split-brain `production` pointers.
- **Epoch-based cache invalidation** (`packages/shared/src/server/services/PromptService/index.ts:177-190`, `192-232`): Instead of `DEL` per key, rotation of `prompt_cache_epoch:{projectId}` (7-day TTL) moves all reads to a fresh Redis namespace; old keys expire via `LANGFUSE_CACHE_PROMPT_TTL_SECONDS`. Project-scoped because resolved prompts may include transitive dependencies (`packages/shared/src/server/services/PromptService/index.ts:208-212` comment).
- **Dependency graph with validation on create/fetch** (`web/src/features/prompts/server/actions/createPrompt.ts:117-139`, `packages/shared/src/server/services/PromptService/index.ts:234-379`): `@@@langfusePrompt:name=X|version=Y@@@` / `|label=Z` tags are parsed (`parsePromptDependencyTags`), validated for circularity and max depth 5, and eagerly resolved (stringified regex replace). Failure blocks creation — prevents broken deployments.
- **Protected labels as entitlement-gated RBAC** (`web/src/features/prompts/server/routers/promptRouter.ts:1395-1491`, `web/src/features/prompts/server/utils/checkHasProtectedLabels.ts:3-25`): The `production`-like labels can be locked to `promptProtectedLabels:CUD` holders; `LATEST_PROMPT_LABEL='latest'` is explicitly unprotectable (`web/src/features/prompts/server/routers/promptRouter.ts:1414-1419`).
- **Event-sourced webhook notifications** (`web/src/features/prompts/server/promptChangeEventSourcing.ts:14-56`, `packages/shared/src/server/queues.ts:274-291`): Every create/update/delete enqueues an `EntityChangeJob` (`entityType: 'prompt-version'`) for the worker's `promptVersionProcessor` / automation webhooks — decouples observability from the write path.

## Notable Patterns

- **Audit-log everything with before/after snapshots** (`web/src/features/audit-logs/auditLog.ts:84-121`, `web/src/features/prompts/server/routers/promptRouter.ts:337-347,909-921`, `web/src/features/prompts/server/prompt-api-service.ts:68-77,115-125`): Both `USER` and `API_KEY` actors are recorded with `resourceType: 'prompt'|'promptProtectedLabel'` for forensics.
- **Idempotent label dedup** (`web/src/features/prompts/server/actions/createPrompt.ts:110`, `146`): `[...new Set(finalLabels)]` on create prevents duplicate-label races.
- **Tags as cross-version convergent state** (`web/src/features/prompts/server/actions/createPrompt.ts:112-113,186-200`): Tags are intentionally spread to all versions (`updatePromptTagsOnAllVersions`) — unlike labels, they are not per-version pointers.
- **Validation-first, transaction-second**: Dependency graph is resolved outside the transaction (`web/src/features/prompts/server/actions/createPrompt.ts:122-139`) to fail fast before acquiring locks; the final `$transaction` is limited to the minimal write set.
- **Cache-miss fallback with error tolerance** (`packages/shared/src/server/services/PromptService/index.ts:147-175`, `web/src/__tests__/server/promptCache.servertest.ts:186-226`): Redis errors are caught and degraded to DB fetch; `getOrCreateEpoch` uses `NX` to handle concurrent initializers (`packages/shared/src/server/services/PromptService/index.ts:228-231`).

## Tradeoffs

- **Label move vs. explicit rollback**: Label indirection makes rollback instant and non-destructive, but the absence of a `rollback` verb means callers must track "which version was production before" themselves (audit_logs is the only source). No UI "Revert to vN" button; `SetPromptVersionLabels` (`web/src/features/prompts/components/SetPromptVersionLabels/index.tsx:92`) is generic.
- **Project-scoped epoch**: Rotating the epoch invalidates *all* prompts in a project, even one label move (`packages/shared/src/server/services/PromptService/index.ts:208-212`). Cheap (one Redis SET) and correct for cross-prompt dependencies, but causes a thundering-herd of cache misses for unrelated prompts after any mutation.
- **Protected labels are deny-list, not allow-list/approval**: Cheaper to implement than a multi-step approval workflow, but a single authorized user can still push a bad prompt to `production` without peer review — the control is authorization, not verification.
- **Tags converge, labels diverge**: Converging tags across all versions simplifies filtering but destroys per-version tag history; labels preserve history but require careful `hasSome` queries.
- **No drift monitoring keeps the platform unopinionated** (avoids LLM-judge cost and false positives) but leaves the detection burden on the consumer; the metrics needed for drift (`versionMetrics`) already exist but are not wired to alerts.

## Failure Modes / Edge Cases

- **Concurrent creates for same name race on version**: `createPromptForApi` catches Prisma `P2002` (unique `[projectId,name,version]`) and surfaces `InvalidRequestError` asking the caller to add a delay (`web/src/features/prompts/server/prompt-api-service.ts:51-66`). No retry loop — high-concurrency SDK callers must serialize or back off.
- **Label move with dependents**: Both tRPC `setLabels` (`web/src/features/prompts/server/routers/promptRouter.ts:868-905`) and `deleteVersion` (`web/src/features/prompts/server/routers/promptRouter.ts:668-729`) query `prompt_dependencies` before removing a label/version and throw `CONFLICT` if the label/version is depended on — prevents broken dependency graphs, but blocks legitimate clean-up until dependents are deleted/rewired.
- **Cache not invalidated if Redis is down / `LANGFUSE_CACHE_PROMPT_ENABLED=false`**: `invalidateCache` returns early when `!cacheEnabled` (`packages/shared/src/server/services/PromptService/index.ts:180`), and Redis SET errors are logged but only `invalidateCache` rethrows (`web/src/__tests__/server/promptCache.servertest.ts:228-238`); a failed invalidation leaves stale cached prompts serving until `LANGFUSE_CACHE_PROMPT_TTL_SECONDS` expires.
- **Immutability violation via `updateTags`**: `promptRouter.updateTags` uses `updateMany` to reset tags on *all* versions of a prompt name (`web/src/features/prompts/server/routers/promptRouter.ts:1107-1118`) — a rare mutable cross-version write that, if raced with a concurrent `createPrompt`, could leave tag sets divergent; no explicit test for this race was found.
- **`latest` label cannot be protected** (`web/src/features/prompts/server/routers/promptRouter.ts:1414-1419`) by design — prevents lockout of new version creation, but means the `latest` pointer is always movable by any `prompts:CUD` holder.
- **Deleting the `production`-labelled version without reassigning**: `deletePrompt` and `deleteVersion` handle `latest` reattachment (`web/src/features/prompts/server/actions/deletePrompt.ts:94-119`, `web/src/features/prompts/server/routers/promptRouter.ts:751-777`) but production link is *not* automatically reattached — production will point at nothing until manually moved, causing `getPromptForApi` to 404 (`web/src/features/prompts/server/handlers/promptNameHandler.ts:43-53` defaults to `label='production'`).

## Future Considerations

- Add a first-class `rollback` operation (tRPC + `POST /api/public/v2/prompts/{name}/rollback` or `POST .../{name}/labels/production/rollback`) that atomically moves `production` to `version-1` (or caller-specified target) and returns the new production version — reduces human error vs. raw `setLabels` and enables an auditable one-click UI action with "rollback window <60s" SLO.
- Introduce an optional **4-eyes / approval flow** for protected labels (e.g., `PromptLabelApproval` table, pending→approved state) reusing the existing `PromptProtectedLabels` gate but adding a required second approver when moving `production`; aligns with enterprise change-control expectations.
- Implement **opt-in drift monitoring** atop `getObservationMetricsForPrompts` / `getAggregatedScoresForPrompts`: a scheduled evaluator that compares score/latency/token distributions per `prompt_version` (e.g., KS-test or score threshold) and emits a `monitor-alert` / webhook — no existing monitor covers prompt drift (`grep drift` empty).
- Consider **per-prompt-name epoch** (or per-label epoch) instead of project-wide epoch to avoid invalidating the entire project's prompt cache on unrelated label moves; measure miss-rate before/after (`PromptServiceMetrics.PromptCacheHit/Miss` at `packages/shared/src/server/services/PromptService/index.ts:16-19` already emitted).
- Expose **prompt lineage in observation queries** more directly: surface `prompt_id/version` in trace/observation list filters and dataset export so downstream monitors can slice without custom ClickHouse queries.
