## Summary

Pydantic AI defines its agent runtime as a small set of **centralized ABCs** — `Model`, `StreamedResponse`, `AbstractToolset`, `EmbeddingModel`, `AbstractCapability`, `OutputSchema`, `AbstractAgent`, `Provider`, `AbstractConcurrencyLimiter` — backed by **typed `Protocol`s** for every hook signature (`capabilities/hooks.py:98-228`, `mcp.py:1927 CallToolFunc`, `ext/langchain.py:11 LangChainTool`, `toolsets/abstract.py:26 SchemaValidatorProt`). The contracts are organized around **consumer ownership**: each ABC declares only the methods needed by the framework's call site (`Model.request`/`request_stream`/`prepare_request` are called by the agent graph at `models/__init__.py:265-409`, `AbstractToolset.get_tools`/`call_tool` are called by `ToolManager` at `tool_manager.py:120-145`), and concrete implementations supply the behavior. A `WrapperX` base class (`WrapperModel`, `WrapperToolset`, `WrapperCapability`, `WrapperEmbeddingModel`, `WrapperAgent`) plus `apply`/`visit_and_replace` visitor methods on toolsets and capabilities (`toolsets/abstract.py:182-190`, `capabilities/abstract.py:232-239`) form a **decorator-stack substitution pattern** that lets a single `Wrapper` subclass satisfy every hook without inheriting from the base ABC.

Contract validation is layered. At compile time, **discriminated `pydantic.Annotated` unions** carry `Discriminator(...)` callbacks that route `(part_kind, tool_kind)` pairs to typed part subclasses via registry lookup (`messages.py:2009-2088`, `_TYPED_PART_TAGS` at `messages.py:1971-1984`, populated by `_tool_search.py:410-418` and `_deferred_capabilities.py:134-135`). At construction time, `_utils.install_deprecated_kwarg_alias` (`_utils.py:770`) and `ModelProfile.__new__` lazy-install MRO-wide deprecated-name aliasing (`profiles/__init__.py:52-64`) so old and new public surfaces both work. At call time, `Model.prepare_request` (`models/__init__.py:338-408`) is the **single funnel** for `ModelRequestParameters` mutation, raising `UserError` for unsupported output modes and unsupported native tools (`models/__init__.py:397-487`), and `function_schema.function_schema` (`_function_schema.py:103-281`) builds a runtime `pydantic_core.SchemaValidator` from the Python signature for every tool. At wire time, `ToolsetTool.args_validator` (`toolsets/abstract.py:59`) is the validator passed to the framework, and a `SchemaValidatorProt` Protocol is used in the type slot to accept either `SchemaValidator` or its private-API-compatible `PluggableSchemaValidator` (`toolsets/abstract.py:26-39`).

Semantic guarantees are encoded as **dataclass field docstrings** plus concrete dispatch logic. The `ToolDefinition.kind` literal (`tools.py:682`) encodes the four invocation semantics — `'function'` / `'output'` / `'external'` / `'unapproved'` — with a `defer` property that derives `'external' | 'unapproved'` from `kind in (...)` (`tools.py:880-881`), and the `ToolDefinition.tool_kind` discriminator (`tools.py:809-825`) separates "this is the `tool-search` call shape" from "this is a regular function call". The `ToolDefinition.unless_native`/`with_native` symmetric pair (`tools.py:770-799`) encodes the local-fallback/corpus-member relationship between function tools and native tools, and `Model._resolve_native_tool_swap` (`models/__init__.py:437-521`) executes a four-rule filter that drops, keeps, or routes each tool based on `profile.supported_native_tools`. The `StreamedResponse` contract encodes cancellation as a state machine with three documented states — `'complete'` / `'incomplete'` / `'interrupted'` — and a `get_stream_cancel_errors` extension point (`models/__init__.py:846-868`) so different transports can declare which `httpx` exceptions to suppress when `cancel()` tears down the connection.

Substitutability is the project's main architectural lever. A custom provider only needs to subclass `Provider[Client]` and override `name`/`base_url`/`client` (`providers/__init__.py:25-110`), a custom model only needs `Model[Client]` and the three abstract methods `request`/`model_name`/`system` (`models/__init__.py:265-527`), a custom toolset only needs `AbstractToolset.get_tools` + `call_tool` + `id` (`toolsets/abstract.py:74-180`), and a custom embedding model only needs `EmbeddingModel.embed` + `model_name` + `system` (`embeddings/base.py:8-72`). The MCP surface extends the toolset interface: `MCPServer(AbstractToolset[Any], ABC)` (`mcp.py:684`) requires only a single `client_streams` async context manager to be implemented by transports, and the recommended `MCPToolset(AbstractToolset[AgentDepsT])` (`mcp.py:1983`) wraps any FastMCP `Client`. The test suite exercises substitutability end-to-end: `MockToolsetWithInstructions(AbstractToolset[Any])` in `tests/test_toolsets.py:72-92` is the conformance example, `LegacyCustomProvider(Provider[None])` in `tests/models/test_model.py:375-399` proves backward compatibility with the old instance-method `model_profile`, and `MCPToolset` is driven against an in-process FastMCP server (`tests/test_mcp_toolset.py:259-945`) to exercise lifecycle, resource methods, prompt caching, and SEP-1686 task-augmented execution.

The contracts are mature, well-tested, and consistent with the project's stated philosophy of "strong primitives, powerful abstractions, general solutions". The main seams show clear fragility: the `AbstractCapability` hook surface (28 hooks × 4 forms × multiple lifecycle stages = `capabilities/abstract.py:146-958`) is huge and the typed `Protocol`s for hook functions (`capabilities/hooks.py:98-228`) are only used by the `Hooks` decorator-namespace class — users who subclass `AbstractCapability` directly rely on the docstring signature rather than a checked protocol; the `OutputSchema` ABC (`_output.py:441-693`) is private and not part of the public extension surface even though `OutputMode` is exported; and `Provider.model_profile` is `@staticmethod` (`providers/__init__.py:74`) but tests show legacy instance-method providers still work (`tests/models/test_model.py:365-399`) — i.e., the contract is enforced by convention rather than by type system. The model-side `WrapperModel.__getattr__` (`models/wrapper.py:160`) falls through to the wrapped model, which means a future addition to the base class can silently change wrapper behavior; the same `__getattr__` pattern is on `WrapperEmbeddingModel` (`embeddings/wrapper.py:71-72`) — both are explicit tech debt with no `__init_subclass__` guard.

## Rating

**9 / 10** — Mature, durable, observable, extensible, and proven under failure/scale. Earned by (a) **small, named, consumer-owned ABCs** for every cross-boundary extension point (`Model`, `StreamedResponse`, `AbstractToolset`, `EmbeddingModel`, `AbstractCapability`, `OutputSchema`, `Provider`, `AbstractConcurrencyLimiter`); (b) **typed Protocol hooks** with documented signatures for every lifecycle event in `capabilities/hooks.py:98-228` plus `WrapperX` decorator-stack patterns (`models/wrapper.py`, `toolsets/wrapper.py:14-74`, `capabilities/wrapper.py:46-429`, `embeddings/wrapper.py:15-72`); (c) **discriminated union serialization** with a registry pattern (`messages.py:1971-1984`, `_TYPED_PART_TAGS`/`_TYPED_PART_TAGS_BY_TYPE`) so typed subclasses can register without touching the base module; (d) **semantic guarantees in dataclass fields and dispatcher logic** rather than in side-channel comments (`ToolDefinition.kind`/`tool_kind`/`unless_native`/`with_native` at `tools.py:682-825`, `Model._resolve_native_tool_swap` at `models/__init__.py:437-521`, `StreamedResponse.cancel()` state machine at `models/__init__.py:806-868`); (e) **runtime validation** via `Model.prepare_request` (single funnel for capability checks, `models/__init__.py:338-408`), `function_schema` (per-tool `SchemaValidator`, `_function_schema.py:223-231`), and `_model_request_part_discriminator` (dict deserialization routing, `messages.py:2009-2033`); (f) **deprecation aliasing** with a single utility (`_utils.install_deprecated_kwarg_alias`) and a `__init_subclass__`-based promotion pattern (`models/__init__.py:584-627`, `capabilities/abstract.py:199-230`) so old public names continue to work after rename; and (g) **conformance-style tests** for substitutability (`tests/test_toolsets.py:72-102` for the toolset interface, `tests/test_function_schema.py:9-100` for the function-schema Protocol, `tests/models/test_model.py:365-399` for the `Provider.model_profile` backward-compat, `tests/models/test_model_request_parameters.py:21-200` for round-trip JSON serialization of `ModelRequestParameters`, `tests/test_mcp_toolset.py:331-945` for the full MCP toolset lifecycle).

Falls short of 10 because: (i) the `AbstractCapability` surface is 28 hooks × 4 forms (`before/after/wrap/on_error`) — a custom capability implementer has to copy a lot of `pass` bodies from `capabilities/abstract.py:407-919` to override just one; (ii) `OutputSchema` is a private ABC (`_output.py:441-693`) — users cannot add a new output mode by subclassing, and the public `OutputMode` Literal (`output.py:42`) is the only stable surface; (iii) `WrapperModel.__getattr__` and `WrapperEmbeddingModel.__getattr__` (`models/wrapper.py:160`, `embeddings/wrapper.py:71-72`) pass through to the wrapped instance, which means adding a new method to the base class silently changes every wrapper; (iv) the `ToolDefinition.defer_loading` field has dual semantics (user-input intent vs current visibility state) with explicit acknowledgement as "tech debt" (`tools.py:747-768`) — a future `RunContext.loaded_tools` view would resolve it but doesn't yet exist; (v) there is no central **conformance test harness** that drives the same lifecycle assertions across every registered provider/toolset/capability — the test suite has per-component mocks (`MockToolsetWithInstructions`, `LegacyCustomProvider`, `MockChatClient`-style fixtures) but not a single parameterized cross-implementation conformance suite.

## Answers to Dimension Questions

1. **Are interfaces small, coherent, and owned by the consumer side?**
   Yes. Each ABC declares only what the framework's call site uses — `Model.request` / `request_stream` / `prepare_request` are called by the agent graph at `models/__init__.py:265-409`; `AbstractToolset.get_tools` / `call_tool` are called by `ToolManager` at `tool_manager.py:120-145`; `AbstractCapability.get_instructions` / `get_native_tools` / `get_toolset` / `get_model_settings` are called by the capability-collecting pass before a run starts (`capabilities/abstract.py:288-337`). Provider ownership is explicit: `Provider` lives in `pydantic_ai/providers/__init__.py` and providers live alongside their SDK imports (`pydantic_ai/providers/openai.py:22`). Toolset ownership is similar: `AbstractToolset` lives next to the tool manager and `ToolManager.for_run_step` is the single consumer (`tool_manager.py:120`). Embedding models are owned by `Embedder` (`pydantic_ai/embeddings/__init__.py:139`) with `Embedder._get_model` calling `infer_embedding_model` and `instrument_embedding_model` (`pydantic_ai/embeddings/__init__.py:372-388`).

2. **Do contracts specify behavior, not just method signatures?**
   Yes for the core lifecycle methods, partial for hooks. `ToolDefinition.kind` encodes four invocation semantics (`'function'`/`'output'`/`'external'`/`'unapproved'`) with derived `defer` property (`tools.py:880-881`); `ToolDefinition.tool_kind` separates "typed call/return shape" from invocation semantics (`tools.py:809-825`); `Model.profile` documents that `default_structured_output_mode` is the canonical mode selection (`profiles/__init__.py:95-96`); `ModelRequestParameters.native_tools` documents the soft requirement via `optional: bool` (`native_tools/__init__.py:58-67`); `StreamedResponse.cancel` documents the state-machine contract with explicit ordering of `_cancelled=True` before `close_stream()` (`models/__init__.py:833-844`); `get_stream_cancel_errors()` documents which transport errors are suppressed (`models/__init__.py:846-855`). Capability hooks have **typed `Protocol`s** for the user-facing `Hooks` decorator (`capabilities/hooks.py:98-228`) but users who subclass `AbstractCapability` directly rely on the docstring signature, not a checked protocol. `OutputSchema` documents `mode` and `allows_text` semantics (`_output.py:441-456`) but its `build(...)` factory and `mode` property are typed as plain `Any` in several internal call sites (`_output.py:486-628`), so the semantics are encoded as runtime branches rather than compile-time types.

3. **Can providers, tools, stores, and runtimes be replaced safely?**
   Yes — this is the central architectural lever. Custom Provider needs three abstract properties (`name`/`base_url`/`client`) plus optional `model_profile` static method (`providers/__init__.py:50-78`); legacy instance-method `model_profile` still works (`tests/models/test_model.py:365-399`). Custom Model needs three abstract methods (`request`/`model_name`/`system`) and may override the streaming/messaging pipeline (`models/__init__.py:265-527`); `TestModel`, `FunctionModel`, `OutlinesModel`, `WrapperModel`, `InstrumentedModel`, `FallbackModel`, `ConcurrencyLimitedModel`, `MCPSamplingModel` all implement the contract. Custom Toolset needs three abstract methods (`id`/`get_tools`/`call_tool`) and the lifecycle is opt-in (`toolsets/abstract.py:74-180`); `MockToolsetWithInstructions` in the test suite proves this (`tests/test_toolsets.py:72-102`). Custom EmbeddingModel needs three abstract methods (`embed`/`model_name`/`system`) (`embeddings/base.py:8-72`); OpenAI/Cohere/Google/Bedrock/VoyageAI/SentenceTransformers/Instrumented/Wrapper all implement it. Custom Capability subclassing is the largest surface (28 hooks) but the `WrapperCapability` base (`capabilities/wrapper.py:46-429`) makes it cheap to compose; `Hooks` (`capabilities/hooks.py:713-1128+`) and `Capability` (`capabilities/capability.py:29-325`) provide zero-subclass alternatives. Custom MCP transport needs only one async context manager (`mcp.py:684`); `MCPToolset` already accepts any FastMCP transport shape.

4. **Are compatibility failures caught early by tests or validation?**
   Partial — strong on the model/toolset/embedding side, weaker on the capability/output side. `tests/models/test_model.py` parametrizes provider inference across OpenAI/Anthropic/Google/Bedrock/Cohere/Grok/Mistral/OpenRouter/`gateway/*` (lines 40-289) and asserts `infer_model_profile` matches the provider's `model_profile` (lines 305-362). `tests/models/test_model_request_parameters.py:21-200` round-trips `ModelRequestParameters` through `pydantic.TypeAdapter` to catch schema drift. `tests/test_toolsets.py` has 2,665 lines covering `AbstractToolset` conformance, lifecycle (`for_run`/`for_run_step`/`__aexit__`), `CombinedToolset` instruction aggregation and cancellation-on-sibling-failure (`tests/test_toolsets.py:1486-1832`), `DynamicToolset`, `FilteredToolset`/`PreparedToolset`/`PrefixedToolset`/`RenamedToolset` (`tests/test_toolsets.py:2086-2380`). `tests/test_function_schema.py` covers `_takes_ctx` across partials, callable classes, and ctx-not-first (`tests/test_function_schema.py:9-100`). `tests/test_mcp_toolset.py:331-945` covers `MCPToolset` against an in-process FastMCP server (lifecycle, resource/prompt methods, cache invalidation, task-augmented execution per SEP-1686). `tests/test_capabilities.py` (21,003 lines) covers ordering, serialization, hook dispatch, and `CombinedCapability` semantics. The gap: there is **no central parameterized "conformance" harness** that runs every registered provider through the same `request`/`request_stream`/`cancel` lifecycle — instead, every provider has its own `tests/models/test_<provider>.py` that VCR-plays cassettes against the real provider. This is consistent with the project's stated testing philosophy ("provider APIs are the ultimate judge", `tests/AGENTS.md`) but means substitutability regressions are caught at the per-provider-VCR layer rather than at the contract layer.

## Architectural Decisions

- **Small consumer-owned ABCs per cross-boundary.** `Model`/`EmbeddingModel`/`AbstractToolset`/`AbstractCapability`/`OutputSchema`/`AbstractAgent`/`Provider`/`AbstractConcurrencyLimiter` each declare the minimum surface their consumer (`agent graph`/`ToolManager`/`Embedder`/`capability collector`/`output pipeline`/`run loop`) needs. New integration types (MCP, FastMCP, LangChain, ACI) extend the same `AbstractToolset` ABC rather than defining a parallel surface.
- **Wrapper-with-delegation substitution.** `WrapperModel` (`models/wrapper.py:69-161`), `WrapperToolset` (`toolsets/wrapper.py:14-74`), `WrapperCapability` (`capabilities/wrapper.py:46-429`), `WrapperEmbeddingModel` (`embeddings/wrapper.py:15-72`), `WrapperAgent` (`agent/wrapper.py:35-92`) all override every method by calling `super()` or the wrapped instance, plus a default `__getattr__` pass-through for ad-hoc attributes. This makes "wrap a model to add OTel/middleware/concurrency" a one-line subclass.
- **Decorator methods on AbstractToolset.** `filtered`/`prefixed`/`prepared`/`renamed`/`approval_required`/`defer_loading`/`include_return_schemas`/`with_metadata` (`toolsets/abstract.py:192-279`) return new wrapper instances without subclassing. Same idea on `AbstractCapability.prefix_tools` (`capabilities/abstract.py:951-958`).
- **Visitor methods for tree replacement.** `AbstractToolset.apply`/`visit_and_replace` (`toolsets/abstract.py:182-190`) and `AbstractCapability.apply` (`capabilities/abstract.py:232-239`) walk the wrapper tree so the framework can rewrite leaf nodes at `for_run_step` time.
- **Discriminated unions + registry, not hard-coded if/elif.** `ModelRequestPart` and `ModelResponsePart` are `Annotated[Union[...], Discriminator(_model_*_part_discriminator)]` with discriminators that look up `(part_kind, tool_kind)` in `_TYPED_PART_TAGS`/`_TYPED_PART_TAGS_BY_TYPE` (`messages.py:2009-2088`, registries at `messages.py:1971-1984`). New typed subclasses (e.g., `_tool_search.py:120 ToolSearchCallPart`) register themselves by writing to the registry at module-import time, with no edit to `messages.py` itself.
- **Schema-derived runtime validation.** `function_schema.function_schema` (`_function_schema.py:103-281`) builds a `pydantic_core.SchemaValidator` from a Python signature via `_generate_schema.GenerateSchema` + `create_schema_validator`. `ToolsetTool.args_validator` (`toolsets/abstract.py:59`) carries the validator; a `SchemaValidatorProt` Protocol (`toolsets/abstract.py:26-39`) accepts the public `SchemaValidator` or the private `PluggableSchemaValidator` interchangeably.
- **Capability-driven lifecycle hooks with parallel `before/after/wrap/on_error` for every stage.** `AbstractCapability` exposes 4×(run + node_run + model_request + tool_validate + tool_execute + output_validate + output_process) + 1 (`handle_deferred_tool_calls`) = 28 hooks. Each hook has a typed `Protocol` (`capabilities/hooks.py:98-228`) so users writing `Hooks()` get compile-time signatures.
- **Profile as the source of truth for capability facts.** `ModelProfile` exposes `supports_thinking`, `supports_json_schema_output`, `supports_image_output`, `supports_inline_system_prompts`, `default_structured_output_mode`, `supported_native_tools` as explicit fields (`profiles/__init__.py:66-142`) instead of `isinstance`/`provider == 'x'` scattered through adapters. `Model.profile` intersects `Model.supported_native_tools()` with `profile.supported_native_tools` (`models/__init__.py:629-652`) so the intersection is computed once.
- **Deprecation aliasing built into the metaclass.** `_utils.install_deprecated_kwarg_alias` (`_utils.py:770-820`) patches `__init__` to accept the old kwarg and warn. `ModelProfile.__new__` walks the MRO and lazily installs every subclass's `_deprecated_kwarg_aliases` (`profiles/__init__.py:52-64`). `Model.__init_subclass__` (`models/__init__.py:584-627`) and `AbstractCapability.__init_subclass__` (`capabilities/abstract.py:199-230`) promote legacy `supported_builtin_tools`/`get_builtin_tools` overrides to the new `supported_native_tools`/`get_native_tools` names — a mixed-generation MRO still works.
- **Cancellation as documented state machine.** `StreamedResponse.cancel()` sets `_cancelled=True` before delegating to `close_stream()` (`models/__init__.py:833-844`); `iterator_with_cancel_guard` (`models/__init__.py:806-826`) suppresses configured transport errors; `get()` returns `'complete'` / `'incomplete'` / `'interrupted'` based on `_finished` and `_cancelled` (`models/__init__.py:884-903`). Subclasses must implement `close_stream()` or `cancel()` will raise a clear error (`models/__init__.py:857-868`).

## Notable Patterns

- **Toolset wrapper hierarchy with single-purpose subclasses.** `FilteredToolset` (32 LOC) wraps `get_tools`; `PreparedToolset` (41 LOC) wraps `get_tools` with a hook; `RenamedToolset` wraps `get_tools` for name translation; `PrefixedToolset` wraps `get_tools` for namespace. Each is a small `WrapperToolset` subclass, demonstrating how the wrapper-with-delegation pattern makes new cross-cutting behaviors cheap to add.
- **Symmetric pair `unless_native` / `with_native` on `ToolDefinition`.** Encodes the two ways a function tool can interact with a native tool: drop the local fallback when native is supported (`unless_native='web_search'`), or keep the local fallback as a corpus member managed by the native tool (`with_native='tool-search'`). `Model._resolve_native_tool_swap` (`models/__init__.py:437-521`) executes the four-rule filter.
- **Provider-agnostic model with typed `InterfaceClient` parameter.** `Model[InterfaceClient]` and `Provider[InterfaceClient]` (`models/__init__.py:217`, `providers/__init__.py:25`) parameterize over the SDK client type so `Model[AsyncOpenAI]`/`Provider[AsyncOpenAI]`, `Model[Mistral]`/`Provider[Mistral]`, `Model[httpx.AsyncClient]`/`Provider[httpx.AsyncClient]` etc. coexist. `InterfaceClient = TypeVar('InterfaceClient', default=Any)` (`providers/__init__.py:22`) lets generic inference work.
- **`for_run` / `for_run_step` lifecycle hooks.** Every wrapper has these two async hooks so per-run state isolation is opt-in. `WrapperToolset.for_run` (`toolsets/wrapper.py:31-35`) creates a new instance if the wrapped toolset returns a new one; `CombinedToolset.for_run_step` (`toolsets/combined.py:48-52`) aggregates and returns `self` when nothing changed.
- **Capability ordering via topological sort.** `CapabilityOrdering` (`capabilities/abstract.py:100-143`) declares `position`/`wraps`/`wrapped_by`/`requires`. `CombinedCapability` topologically sorts children so user-provided order is a tiebreaker, not the only constraint.
- **Dual semantics on `ToolDefinition.defer_loading`.** Documented as tech debt (`tools.py:747-768`): user-input intent vs current visibility state. The framework mutates per-step instances via `replace(...)` so user-persisted `ToolDefinition`s are untouched.
- **`SchemaValidatorProt` as a Protocol bridge.** `pydantic_core.SchemaValidator` is the public validator; `pydantic_core.PluggableSchemaValidator` is private but API-compatible. `SchemaValidatorProt` (`toolsets/abstract.py:26-39`) is a `Protocol` accepting either, so user code holding either type can be stored in `ToolsetTool.args_validator`.
- **`callables` and `Awaitable` returned from hooks.** Every hook protocol documents both sync and async returns (`capabilities/hooks.py:98-228`). `_call_func` (`capabilities/hooks.py:251-256`) auto-wraps sync results, removing the boilerplate of "do I need `async def`?" from the user's mind.

## Tradeoffs

- **`AbstractCapability` hook surface is large.** 28 hook methods × multiple lifecycle stages is a lot for a custom capability implementer to override. The `WrapperCapability` base (`capabilities/wrapper.py:46-429`) mitigates by passing through, but anyone wanting to override one hook still has to read all 28 docstrings to understand the contract.
- **`OutputSchema` is private.** `_output.py:441-693` is a clean ABC but lives in a private module — users cannot add a new output mode by subclassing; they have to use one of the four marker classes (`ToolOutput`/`NativeOutput`/`PromptedOutput`/`TextOutput`). The public `OutputMode` Literal (`output.py:42`) is the only extension point.
- **`WrapperModel.__getattr__` and `WrapperEmbeddingModel.__getattr__`** pass through to the wrapped instance (`models/wrapper.py:160`, `embeddings/wrapper.py:71-72`). Adding a new public method to the base class will silently change every wrapper's behavior. No `__init_subclass__` guard warns when a new method is shadowed.
- **No central conformance test harness.** Substitutability regressions are caught at the per-provider-VCR layer, not by a generic cross-implementation suite. Per-component mocks (`MockToolsetWithInstructions`, `LegacyCustomProvider`, `FunctionModel`, `TestModel`, in-process FastMCP server) exist but no `conftest.py` runs every mock through the same lifecycle assertion.
- **`ToolDefinition.defer_loading` dual semantics.** Acknowledged tech debt (`tools.py:761-766`); the dual use works because the framework mutates per-step instances via `replace(...)`, but a future contributor reading user-persisted definitions could be confused.
- **Provider `model_profile` is `@staticmethod` but legacy instance methods still work.** `providers/__init__.py:74` declares the static method; `tests/models/test_model.py:365-399` proves the instance-method pattern still satisfies `Provider[None]` — i.e., the contract is enforced by convention not by type system. A future `pyright` strictness bump could surface this gap.
- **Capability hooks are typed Protocols only in `Hooks`.** `capabilities/hooks.py:98-228` defines `BeforeRunHookFunc`, `AfterRunHookFunc`, etc., but `AbstractCapability` (`capabilities/abstract.py:146-958`) declares the same methods as plain async methods. Users who subclass `AbstractCapability` directly don't get type-checked hook signatures.

## Failure Modes / Edge Cases

- **`Model.count_tokens` raises `NotImplementedError` with a per-class name.** `models/__init__.py:286` says `f'Token counting ahead of the request is not supported by {self.__class__.__name__}'` — the framework surfaces a clear error rather than failing silently.
- **Native tool unsupported on a model.** `Model._resolve_native_tool_swap` (`models/__init__.py:474-487`) raises `UserError` listing unsupported tools and the supported set, with guidance to install optional dependency groups (`models/__init__.py:478-487`).
- **`output_mode='native'` on a model that doesn't support JSON schema.** `Model.prepare_request` (`models/__init__.py:397-398`) raises `UserError('Native structured output is not supported by this model.')` — fail loud at request time rather than silently degrading.
- **`prepared` function adds or renames tools.** `PreparedToolset` raises `UserError` with migration guidance (`toolsets/prepared.py:33-36`) — `FunctionToolset.add_function()` or `RenamedToolset` instead.
- **`PreparedToolset` returns `None` from the prepare function.** `warn_on_prepare_callback_returned_none` is emitted so silent tool removal doesn't pass unnoticed (`toolsets/prepared.py:29-30`).
- **Tool call with no matching tool.** `ExternalToolset.call_tool` raises `NotImplementedError('External tools cannot be called directly')` (`toolsets/external.py:44-47`) — fail loud, the tool was supposed to be externally executed.
- **`ApprovalRequired` raised but `tool_call_approved=False`.** `ApprovalRequiredToolset.call_tool` (`toolsets/approval_required.py:26-30`) raises `ApprovalRequired` so the framework can route to `handle_deferred_tool_calls`.
- **Tool name conflict across toolsets.** `CombinedToolset.get_tools` raises `UserError` with the conflicting toolset label and a hint to wrap with `PrefixedToolset` (`toolsets/combined.py:73-77`).
- **Stream cancelled mid-flight.** `StreamedResponse.get()` reports `'interrupted'` (`models/__init__.py:886-887`) and the cancellation guard suppresses configured transport errors (`models/__init__.py:806-826`).
- **`MCPToolset` HTTP-only kwargs with a non-HTTP input.** Raises `ValueError('only apply to HTTP transports built from a URL')` at construction (`tests/test_mcp_toolset.py:115-122`).
- **Pre-built FastMCP client with `init_timeout`/`read_timeout`.** Raises `ValueError` (`tests/test_mcp_toolset.py:137-145`) — the timeouts are MCP-protocol kwargs that only apply when the toolset constructs a default client.
- **`__aexit__` called more times than `__aenter__`.** `MCPToolset.__aexit__` raises `ValueError('called more times than __aenter__')` (`tests/test_mcp_toolset.py:347-356`) rather than silently closing resources.
- **Legacy `BuiltinTool`/`AbstractBuiltinTool` rename.** `capabilities/__init__.py:154-169` and `builtin_tools/__init__.py:79-100` route old imports through `__getattr__` with a `PydanticAIDeprecationWarning`. `Model.__init_subclass__` (`models/__init__.py:584-627`) and `AbstractCapability.__init_subclass__` (`capabilities/abstract.py:199-230`) promote legacy `supported_builtin_tools`/`get_builtin_tools` overrides at class creation time.

## Future Considerations

- **Conformance test harness.** A parameterized suite that drives every `Provider`/`Model`/`AbstractToolset`/`EmbeddingModel`/`AbstractCapability` through the same lifecycle (initialize, request, cancel, error path, lifecycle exit) would catch substitutability regressions that per-provider-VCR tests miss. The existing per-component mocks (`MockToolsetWithInstructions`, `LegacyCustomProvider`, `FunctionModel`, `TestModel`) are the right building blocks.
- **Drop `__getattr__` from `WrapperModel` and `WrapperEmbeddingModel`.** Explicit delegation catches shadowed methods at type-check time. A `__init_subclass__` warning when a new base-class method isn't overridden in the wrapper would also help.
- **Promote `OutputSchema` to public.** The clean ABC at `_output.py:441-693` is a natural extension point; users with a custom output mode currently have to add a Literal entry to `OutputMode` and a corresponding `OutputSchema` subclass in the private module. A public base would let third-party plugins ship custom output parsers.
- **Resolve `ToolDefinition.defer_loading` dual semantics.** A `RunContext.loaded_tools` view that derives "is this tool visible right now?" from user input + `loaded_capability_ids` + `discovered_tool_names` would let `defer_loading` cleanly stay a user-input flag (`tools.py:747-768`).
- **Type the `OutputSchema` discriminated branches.** Currently `_output.py:486-628` uses `# pyright: ignore` on several lines because `isinstance` over a union of `OutputDataT`-parameterized types isn't statically narrowable. A `TypeAdapter`-based dispatch or a tagged union (`Literal['native', 'prompted', 'tool', 'text', 'image']` discriminator) would let pyright narrow.
- **Promote `Provider.model_profile` to `@abstractmethod @staticmethod`.** The legacy instance-method pattern (`tests/models/test_model.py:375-399`) is documented as backward compat; once `v2` lands, tightening the contract would surface gaps earlier.
- **Conformance test for `WrapperCapability` semantics.** The `WrapperCapability` base adopts the wrapped capability's `id` and `defer_loading` when not explicitly set (`capabilities/wrapper.py:62-66`); `apply` recursively visits when wrapping a container (`capabilities/wrapper.py:67-76`). A unit test pinning these semantics would catch future refactors.
- **`callables` and `Awaitable` are documented in protocols but not enforced.** The `Hooks` class dispatches via `_call_func` (`capabilities/hooks.py:251-256`) which auto-wraps sync results; `AbstractCapability` direct subclasses don't get this. Centralizing the dispatch helper would let any subclass benefit.

## Questions / Gaps

- The `OutputSchema` ABC at `_output.py:441-693` is private. Is there a deliberate decision to keep output modes internal-only (so users always go through marker classes), or is this an artifact of the v1→v2 rename (`builtin_tools`→`native_tools`)? `pydantic_ai/output.py:1-32` re-exports `OutputObjectDefinition` but not `OutputSchema`.
- The `Model.supported_native_tools()` classmethod (`models/__init__.py:566-572`) defaults to `frozenset()` and is overridden per-class (e.g., `TestModel.supported_native_tools` excludes `ToolSearchTool`, `models/test.py:168-176`). The intersection with `profile.supported_native_tools` happens in `Model.profile` (`models/__init__.py:629-652`). Is the **intersection** of `Model`-declared and `Profile`-declared tools documented as the canonical mechanism, or is the override pattern scattered across models an emergent convention?
- `WrapperModel.__getattr__` and `WrapperEmbeddingModel.__getattr__` (`models/wrapper.py:160`, `embeddings/wrapper.py:71-72`) pass through to the wrapped instance. The AGENTS.md guidance in `pydantic_ai_slim/pydantic_ai/AGENTS.md` ("API Design") says to "centralize provider-specific metadata in structured `provider_details`/`provider_metadata` fields, not in `id`/`content`/`args`" — does the same pattern apply to wrapper delegation, or is shadowing acceptable when the wrapper explicitly overrides the base method?
- `StreamedResponse.get_stream_cancel_errors()` defaults to `(httpx.StreamError, httpx.TransportError)` (`models/__init__.py:854-855`) but the docstring lists gRPC and botocore transports as needing overrides. No current code overrides it (`models/openai.py:934`, `models/anthropic.py:555`, `models/bedrock.py:607`, `models/google.py:632` all use the default). Is this intentional — i.e., the project accepts that non-`httpx` transports will leak cancellation errors — or is it a TODO?
- The capability ordering rules (`CapabilityOrdering.wraps`/`wrapped_by`, `capabilities/abstract.py:117-139`) use instance-identity matching by default but warn about `for_run` returning a new instance breaking the match. Is there a planned API to make per-run ordering robust, or is it intentional that users keep `id` stable across `for_run`?
- `ToolDefinition.unless_native` / `with_native` symmetric pair (`tools.py:770-799`) is documented as a generalization of the older `prefer_builtin` flag. Is the **dual semantic** of `unless_native` (drop when supported vs use as local fallback) carried through `Model._resolve_native_tool_swap` correctly for all providers, or do some providers still have `unless_native`-specific branches in their wire formatting?
- `MCPServer` (legacy) vs `MCPToolset` (FastMCP-based) is documented as a v1→v2 transition (`mcp.py:684-694`, `toolsets/fastmcp.py:62-69`). Is `MCPServer` scheduled for removal in v2, or is it kept as a parallel interface for users who can't migrate?
- `Agent.iter()` accepts a `spec: dict[str, Any] | AgentSpec | None` parameter (`agent/wrapper.py:132-155`) — the spec deserialization path (`_spec.py`, `agent/spec.py`) is mentioned but the contract between `AgentSpec` and `CAPABILITY_TYPES` (`capabilities/__init__.py:70-91`) isn't fully traced here. Are there `get_serialization_name` return-`None` capabilities that aren't serializable today but should be?
- `Tool.from_schema(...)` (`tools.py:582-636`) constructs a `Tool` with a user-provided JSON schema and `core_schema.any_schema()` validator (`tools.py:621`). The comment says "Schema validation of the arguments is skipped, but a custom `args_validator` will still run if provided." Is there a way to get schema validation back without losing the user-provided schema, or is this an explicit decision to trust the user-provided schema?
