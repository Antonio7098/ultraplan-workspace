## Summary

Letta defines contracts across at least seven distinct extension axes: LLM clients (`LLMClientBase`), agent loops (`BaseAgent`/`BaseAgentV2`), tool executors (`ToolExecutor`), tool sandboxes (`AsyncToolSandboxBase`), MCP clients (`AsyncBaseMCPClient`), MCP server configs (`BaseServerConfig`/`HTTPBasedServerConfig`), provider trace backends (`ProviderTraceBackendClient`), embedders (`BaseEmbedder`), file parsers (`FileParser`), token counters (`TokenCounter`), storage backends (`StorageBackend`), and the summarizer plugin (`SummarizerProtocol`). Every ABC uses `abc.ABC` + `@abstractmethod`, and every concrete implementation is selected through a factory/registry (`LLMClient.create` at `letta/llm_api/llm_client.py:13`, `ToolExecutorFactory._executor_map` at `letta/services/tool_executor/tool_execution_manager.py:35`, `AgentLoop.load` at `letta/agents/agent_loop.py:19`, `_create_backend` at `letta/services/provider_trace_backends/factory.py:8`).

The shape of the contracts is mixed: most ABCs encode both behavior and structure (e.g., `AsyncToolSandboxBase.run` returns `ToolExecutionResult` and the base class generates execution scripts centrally, `letta/services/tool_sandbox/base.py:107-176`), but several — most notably the LLM client hierarchy — leave the actual HTTP/wire logic entirely to subclasses and only pin the response shape (`ChatCompletionResponse`). Errors are mapped into a structured `LettaError` taxonomy with an `ErrorCode` enum (`letta/errors.py:11-25`); each LLM client implements its own `handle_llm_error` to translate provider-specific exceptions (`letta/llm_api/anthropic_client.py:965-1064`, `letta/llm_api/openai_client.py:1216-1252`, `letta/llm_api/baseten_client.py:120-150`). Pydantic schemas are the canonical type system, with `LettaBase` enforcing `extra="forbid"` plus snake/camel aliasing (`letta/schemas/letta_base.py:15-27`) and ID regex/prefix enforcement (`letta/validators.py:15-44`).

Substitutability is the system's strongest axis. There are 13+ LLM client implementations behind one base; 8+ `ToolExecutor` subclasses; 4 sandbox backends; 3 MCP client transports; 4 trace backends; multiple embedders and storage backends. Substitution is mediated by factories and a runtime `provider_type`/`tool_type` discriminator rather than by composition, and most swap paths are exercised by `tests/` (e.g., `test_llm_clients.py`, `tests/mcp_tests/test_mcp_schema_validation.py`, `tests/test_provider_trace_backends.py`). The system explicitly encodes deprecated fields and migration paths (`deprecated=True` in Pydantic Fields, ~50 occurrences across `letta/schemas/`), and the legacy vs new LLMConfig split is handled via `Model._from_llm_config` (`letta/schemas/model.py:97`) and `LLMConfig._to_model_settings` (`letta/schemas/llm_config.py:355`). Validation is layered: Pydantic schema-time + a custom JSON Schema strict-mode validator (`letta/functions/schema_validator.py`) + AST-level function introspection (`letta/functions/functions.py`, `letta/functions/ast_parsers.py`) + URL/ID validation (`letta/validators.py`, `letta/helpers/url_validation.py`).

The weak points are (a) absence of a conformance harness — behavior is validated by per-implementation tests rather than a shared spec runner; (b) schema drift — `LLMConfig` is deprecated but still consumed widely, with two parallel config systems (`LLMConfig`, `ModelSettings`) that must round-trip; (c) hidden assumptions in the LLM client interface — `extract_usage_statistics` is a non-abstract hook with no-op default (`letta/llm_api/llm_client_base.py:83-85`), and `send_llm_batch_request_async` is documented as raising `NotImplementedError` without a fallback; (d) the BaseAgentV2 abstract methods include both blocking and streaming entry points, so implementations must satisfy all three (`build_request`, `step`, `stream`, `letta/agents/base_agent_v2.py:35-104`) even if a deployment only ever uses one; (e) some ABCs (e.g., `AgentInterface` in legacy `letta/interface.py:21`) have commented-out abstract methods, signalling the contract is under active churn.

## Rating

**7 / 10** — Clear model with tests, explicit interfaces, and operational safeguards.

Rationale:
- **+** Every extension axis uses a formal ABC with `@abstractmethod`, factories exist for each family, and the schema layer is a single source of truth (`LettaBase`).
- **+** Errors are mapped across provider boundaries into a typed taxonomy, and the structured JSON-schema validator (`schema_validator.py`) catches a real class of integration bugs (OpenAI strict-mode compatibility).
- **+** Real substitutability is demonstrated by the breadth of in-tree implementations (13+ LLM clients, 4 sandboxes, 3 MCP transports, 4 trace backends) without fork-incompatible code paths.
- **+** Deprecation is encoded in the type system (`deprecated=True`), and `Model._from_llm_config` / `LLMConfig._to_model_settings` provide bidirectional migration helpers (`letta/schemas/model.py:97`, `letta/schemas/llm_config.py:355`).
- **−** No conformance suite — every implementation's contract is exercised by per-implementation tests, so a new LLM client can silently miss an edge case the others all handle.
- **−** `BaseAgentV2` requires three abstract methods (`build_request`, `step`, `stream`) even if a deployment only ever calls one; the `BaseAgent` legacy base duplicates the same shape (`letta/agents/base_agent.py:55-75`).
- **−** `LLMConfig` is "deprecated" but remains the wire format the entire codebase consumes; two parallel type systems double the surface to maintain.
- **−** Several ABCs include unimplemented methods that simply raise `NotImplementedError` (e.g., `send_llm_batch_request_async`, `letta/llm_api/llm_client_base.py:280-290`); these are documented but not enforced.
- **−** Agent-facing streaming interfaces (`OpenAIStreamingInterface`, `AnthropicStreamingInterface`) and the LLM client streaming methods are not behind a single ABC — they're duck-typed, so adding a new streaming protocol requires matching an undocumented shape.

The interface contract design is mature for a server of this scope but not as rigorously tested as, e.g., LangGraph's `checkpoint-conformance` package. It earns 7/10 for explicit interfaces, strong substitutability, and layered validation; it does not reach 8 because behavior verification rests on per-impl integration tests rather than a shared spec runner.

## Answers to Dimension Questions

### 1. Are interfaces small, coherent, and owned by the consumer side?

**Mixed.** The most disciplined contracts are the *small* ones:

- `FileParser.extract_text(content: bytes, mime_type: str)` — single abstract method (`letta/services/file_processor/parser/base_parser.py:4-8`).
- `BaseEmbedder.generate_embedded_passages(file_id, source_id, chunks, actor)` — single method (`letta/services/file_processor/embedder/base_embedder.py:19-21`).
- `StorageBackend` — focused on a coherent object-store API (`upload_bytes`/`download_bytes`/`exists`/`delete`/`list_files`/`delete_prefix`); helper methods like `upload_text` are derived from primitives (`letta/services/memory_repo/storage/base.py:7-127`).
- `SummarizerProtocol` — a two-method `typing.Protocol` (`letta/plugins/plugins.py:7-12`).
- `MCPBaseServerConfig` — `server_name` + abstract `resolve_environment_variables` plus optional templated-variable helpers (`letta/functions/mcp_client/types.py:42-157`).

The *larger* contracts show clear consumer ownership but sprawl:

- `LLMClientBase` has 8 abstract methods + several concrete helpers (`extract_usage_statistics`, `request_async_with_telemetry`, `_fix_truncated_json_response`). Ownership is consumer-side (the agent loop holds the client), but the method count is high and several of the abstract methods (`send_llm_batch_request_async`) are deliberately unimplemented across most providers — they exist as "if you can support this, here's the shape."
- `BaseAgentV2` requires `build_request`, `step`, and `stream` (`letta/agents/base_agent_v2.py:35-104`). The legacy `BaseAgent` requires `step` + `step_stream` (`letta/agents/base_agent.py:55-75`). Subclasses must implement all of them even though most call sites use one — this is interface bloat.
- `Provider` requires a non-trivial surface: `check_api_key`, `list_llm_models_async`, `list_embedding_models_async`, `get_model_context_window`, `get_default_max_output_tokens`, plus a `cast_to_subtype()` factory that depends on `provider_type` enum (`letta/schemas/providers/base.py:19-258`). The legacy `list_llm_models` (sync) raises a deprecation warning rather than being removed, increasing the surface.

### 2. Do contracts specify behavior, not just method signatures?

**Partially.** The most behavior-rich contracts:

- `LettaLLMAdapter` documents that the `invoke_llm` async generator must populate `chat_completions_response`, `reasoning_content`, `tool_calls`, `usage`, `tool_call`, `logprobs`, and `finish_reason` on the instance (`letta/adapters/letta_llm_adapter.py:23-104`). The base class enforces the side-effect contract but does not verify the abstract implementation obeys it.
- `AsyncToolSandboxBase` specifies that `run()` must produce a `ToolExecutionResult` and that `_render_sandbox_code` must produce executable Python (with `asyncio.run`) or TypeScript (`letta/services/tool_sandbox/base.py:107-176, 177-388`). The base class *generates* the script centrally so behavior is consistent across backends.
- `LLMConfig.apply_reasoning_setting_to_config` (`letta/schemas/llm_config.py:573-733`) is a behavioral specification: for `letta_v1_agent`, OpenAI native reasoning is forced on, Anthropic/Gemini are toggle-honored, ZAI/OpenRouter/Baseten are toggle-honored, others disabled. This is policy-as-code.
- `validate_complete_json_schema` (`letta/functions/schema_validator.py:20-201`) is a behavioral spec for "what makes a tool schema OpenAI strict-mode compliant." It returns `SchemaHealth` + reasons list rather than just passing/failing.
- `AsyncBaseMCPClient.execute_tool` returns `(text: str, success: bool)` and treats `EXPECTED_MCP_TOOL_ERRORS` as recoverable vs everything else as worth re-raising (`letta/services/mcp/base_client.py:14-37, 104-129`). Behavior is documented in code.

The most signature-only contracts:

- `ToolExecutor.execute` (signature only — return type is a `ToolExecutionResult`, no documented invariants on which fields are populated).
- `LLMClientBase.request_embeddings` (signature only — no documented contract on ordering, batch size, or normalization).
- `BaseStore` does not exist as an ABC; storage backends rely on duck-typing for non-`StorageBackend` consumers (e.g., `MemfsClient` exposes its own methods rather than implementing `StorageBackend`).

### 3. Can providers, tools, stores, and runtimes be replaced safely?

**Yes, demonstrated by the codebase, but with friction.**

Substitutability is demonstrated by parallel implementations across all major axes:

- **LLM providers:** 13+ clients behind `LLMClient.create(provider_type)` (`letta/llm_api/llm_client.py:13-145`), with `OpenAIClient` as the default fallback. New providers are added by adding a `case ProviderType.foo:` clause.
- **Tool types:** 5 `ToolType` entries mapped to 6 executors in `ToolExecutorFactory._executor_map` (`letta/services/tool_executor/tool_execution_manager.py:35-43`), with `SandboxToolExecutor` as the default.
- **Sandbox backends:** 4 implementations of `AsyncToolSandboxBase` (`letta/services/tool_sandbox/`), with `Local` as the safe default.
- **MCP transports:** 3 implementations of `AsyncBaseMCPClient` (`letta/services/mcp/`), driven by `MCPServerType` discriminator.
- **Embedders:** 3 implementations of `BaseEmbedder`, with `vector_db_type` class field controlling which vector store they target.
- **Trace backends:** 3 implementations of `ProviderTraceBackendClient`, with multi-backend support for dual-write migrations (`letta/services/provider_trace_backends/factory.py:31-42`).
- **Token counters:** 4 implementations of `TokenCounter`, with caching decorator uniform across all (`letta/services/context_window_calculator/token_counter.py`).
- **File parsers:** 2 implementations of `FileParser` (Markitdown + Mistral OCR).
- **Storage backends:** `StorageBackend` ABC with `LocalStorageBackend` in-tree; cloud impl is loaded conditionally at import (`letta/services/memory_repo/__init__.py:7-10`).

Friction points:

- The agent hierarchy has *four* live `BaseAgent` implementations (`BaseAgent` legacy, `BaseAgentV2`, `BaseAgentV3`, plus `VoiceAgent`/`VoiceSleeptimeAgent`) — substitution is by `AgentLoop.load` which routes by `agent_type` (`letta/agents/agent_loop.py:19-62`). `LLMConfig` vs `ModelSettings` is a parallel schema with bidirectional converters (`letta/schemas/llm_config.py:355-494`, `letta/schemas/model.py:97-100`); replacing one means touching both.
- `SGLangNativeClient` is *not* behind `LLMClientBase` (`letta/llm_api/sglang_native_client.py:17`); it bypasses the contract for RL training. There's a separate `SGLangNativeAdapter` (`letta/adapters/sglang_native_adapter.py`). This is documented but means a new "non-chat-completions" provider is a copy-paste rather than an extension.

### 4. Are compatibility failures caught early by tests or validation?

**Mostly yes, with structural validation, schema-time validation, and runtime validation; but no shared conformance suite.**

- **Compile/import-time:** The legacy `providers.py` module coexists with the split `letta/schemas/providers/` package — both define `Provider`, `OpenAIProvider`, etc. (`letta/schemas/providers.py:21-1618`, `letta/schemas/providers/base.py:19-300`). The split module's `__init__.py` re-exports the new package (`letta/schemas/providers/__init__.py:1-56`), so importing the old path silently routes to the new. There's no deprecation warning at the module level; only field-level deprecations are signaled.
- **Schema-time:** Every persisted entity inherits from `LettaBase` with `extra="forbid"`, which prevents silent schema drift (`letta/schemas/letta_base.py:24`). `Update`/`Create` variants relax to `extra="ignore"` for backward compat (`letta/schemas/tool.py:209`, `letta/schemas/block.py:49`).
- **Field-level validators:** `redirect_deprecated_google_models`, `validate_codex_reasoning_effort`, `validate_typescript_requires_schema`, `validate_file_blocks_no_duplicates`, `validate_server_url` (all referenced in the evidence table).
- **Tool schema validation:** `validate_complete_json_schema` is called when MCP tools are listed (`tests/mcp_tests/test_mcp_schema_validation.py:11-67`); non-compliant schemas are marked `NON_STRICT_ONLY` and stored as metadata rather than rejected — graceful degradation.
- **ID prefix validation:** `PATH_VALIDATORS` enforces `^prefix-[a-fA-F0-9]{8}-...$` regex at FastAPI boundary (`letta/validators.py:15-44, 80-121`); `@raise_on_invalid_id` decorator enforces the same for service code (`letta/validators.py:124-162`).
- **URL validation:** `validate_mcp_server_url` rejects non-http(s) URLs (`letta/schemas/mcp.py:54-60`).
- **Provider name conflict:** `LettaToolNameConflictError` raised on duplicate names within an organization (`letta/errors.py:135-143`).
- **Tool name/schema mismatch:** `LettaToolNameSchemaMismatchError` raises when declared name doesn't match source code or schema (`letta/errors.py:146-152`).

What's missing: there is no `conformance` test package comparable to LangGraph's `libs/checkpoint-conformance`. Validation lives in three places: per-implementation integration tests (`tests/test_llm_clients.py`, `tests/test_providers.py`, `tests/test_provider_trace_backends.py`, `tests/integration_test_*`); ad-hoc assertions in the test file; and runtime fallback paths (e.g., `SandboxToolExecutor` falls back from Modal to E2B/LOCAL on failure, `letta/services/tool_sandbox/base.py:90-100`). A new LLM client subclass can pass its own integration test suite while silently missing an edge case the others handle (e.g., `handle_llm_error` returning the wrong exception class for a context-window overflow).

## Architectural Decisions

1. **Pydantic as the universal schema layer.** Every contract that crosses a persistence boundary uses a Pydantic `BaseModel`. `LettaBase` (`letta/schemas/letta_base.py:15-103`) is the common ancestor enforcing `extra="forbid"`, populated-by-name aliasing, ORM attribute mapping, and prefix-aware ID generation. This single decision propagates to ~80 schema modules and gives the system uniform validation, serialization, and OpenAPI generation.
2. **ABC + factory for every extension axis.** Each family of implementations uses `@abstractmethod` in a base class and a factory that dispatches by an enum discriminator (`LLMClient.create` by `provider_type`, `ToolExecutorFactory._executor_map` by `tool_type`, `_create_backend` by `ProviderTraceBackend`, `AgentLoop.load` by `agent_type`). This makes substitution explicit at construction time and avoids runtime `isinstance` branching in business logic.
3. **Error mapping at provider boundaries.** Every `LLMClientBase` subclass implements `handle_llm_error` to translate provider-specific exceptions (`anthropic.RateLimitError`, `httpx.RemoteProtocolError`, etc.) into a common `LLMError` taxonomy with `ErrorCode` (`letta/errors.py:11-25`). The base class provides a default that handles `httpx.RemoteProtocolError` and a generic `LLMError` (`letta/llm_api/llm_client_base.py:368-397`). `BasetenClient.handle_llm_error` (`letta/llm_api/baseten_client.py:120-150`) composes: it logs a searchable tag then `super().handle_llm_error()` — demonstrating the extension pattern.
4. **Centralized tool execution script generation.** `AsyncToolSandboxBase.generate_execution_script` (`letta/services/tool_sandbox/base.py:126-388`) produces the same Python/TypeScript source shape across all sandbox backends. Subclasses only override `run()` (the actual transport) and optionally `use_top_level_await()` (for running-event-loop environments). This centralizes coercion, agent_state pickling, letta_client injection, and result serialization in one place.
5. **Streaming interface duck-typing rather than ABC.** `OpenAIStreamingInterface` (`letta/interfaces/openai_streaming_interface.py:78`) and `AnthropicStreamingInterface` (`letta/interfaces/anthropic_streaming_interface.py:63`) are concrete classes, not ABCs. The `LettaLLMStreamAdapter` instantiates the right one based on `llm_config.model_endpoint_type` (`letta/adapters/letta_llm_stream_adapter.py:97-100`). This is a *less rigorous* contract than the rest of the codebase but matches the practical reality that streaming protocols are provider-specific and difficult to abstract.
6. **Deprecation in the type system.** Pydantic `Field(deprecated=True)` is used on ~50+ fields (`letta/schemas/llm_config.py:107-115`, `letta/schemas/agent.py:88-149`, `letta/schemas/model.py:27-89`, `letta/schemas/letta_message.py:236-347`) to surface deprecated fields in OpenAPI docs and client SDKs. Migration paths: `Model.from_llm_config(llm_config)` and `LLMConfig._to_model_settings()` (`letta/schemas/model.py:97`, `letta/schemas/llm_config.py:355`) provide bidirectional conversion.
7. **Plugin protocol via `typing.Protocol`.** `SummarizerProtocol` is `@runtime_checkable` (`letta/plugins/plugins.py:7-12`), and the registry validates `isinstance(plugin, type(protocol))` at lookup time (`letta/plugins/plugins.py:39-40`). This is the only place using structural typing.
8. **Schema validation as a first-class concern.** `SchemaHealth` (`letta/functions/schema_validator.py:12-18`) is a three-state enum used to communicate "compliant / usable-but-not-strict / broken" rather than binary pass/fail. `MCPTool.health` carries this into the wire model (`letta/functions/mcp_client/types.py:21-33`) so callers can decide policy at the point of use rather than at import time.

## Notable Patterns

- **Template-method + abstract-method mix.** `StorageBackend.upload_text`/`download_text`/`copy` are concrete defaults over `upload_bytes`/`download_bytes` (`letta/services/memory_repo/storage/base.py:93-127`); `LLMClientBase` mixes abstract (`request_async`) with concrete helpers (`request_async_with_telemetry`, `_fix_truncated_json_response`) (`letta/llm_api/llm_client_base.py:83-464`). The base provides cross-cutting concerns (telemetry, JSON repair) while subclasses focus on wire details.
- **Inheritance for OpenAI-compatible providers.** `BasetenClient(OpenAIClient)`, `GroqClient(OpenAIClient)`, `XAI(OpenAIClient)`, `TogetherClient(OpenAIClient)`, `FireworksClient(OpenAIClient)`, `DeepseekClient(OpenAIClient)`, `LMStudioOpenAIProvider(OpenAIProvider)`, `CohereProvider(OpenAIProvider)` all reuse the OpenAI request-building pipeline and only override `build_request_data` for provider-specific quirks (`letta/llm_api/baseten_client.py:30-103`, `letta/llm_api/xai_client.py:18-55`). Similarly, `BedrockClient(AnthropicClient)`, `MiniMaxClient(AnthropicClient)`, `GoogleAIClient(GoogleVertexClient)` (`letta/llm_api/bedrock_client.py:18`, `letta/llm_api/minimax_client.py:19`, `letta/llm_api/google_ai_client.py:17`).
- **Per-implementation telemetry context object.** `LettaLLMAdapter.__init__` accepts `agent_id`/`agent_tags`/`run_id`/`org_id`/`user_id`/`billing_context`; subclasses populate instance fields and write telemetry at end-of-call (`letta/adapters/letta_llm_adapter.py:25-61`, `letta/adapters/letta_llm_request_adapter.py:100-147`). The pattern is verified by `test_request_and_stream_adapters_have_consistent_interface` (`tests/test_provider_trace_agents.py:277-292`).
- **Multi-version support with bidirectional converters.** `LLMConfig` (legacy, deprecated) ↔ `ModelSettingsUnion` (new, discriminated by `provider_type`). The two classes co-exist; `LLMConfig._to_model_settings` (`letta/schemas/llm_config.py:355`) and `Model.from_llm_config` (`letta/schemas/model.py:97`) provide round-trip conversion.
- **Discriminated unions with Pydantic `Field(discriminator=...)`.** Used in `ResponseFormatUnion`, `ModelSettingsUnion`, `ToolRule` types, `LettaMessageReturnUnion`, `MCPServerConfig`, `Group` types, `LettaImage`/`ImageSourceUnion`, `AgentFile` types (`letta/schemas/response_format.py:74-77`, `letta/schemas/model.py:550-569`, `letta/schemas/tool_rule.py:372`, `letta/schemas/letta_message.py:51,477,595,699`, `letta/schemas/mcp_server.py:271,281`, `letta/schemas/letta_message_content.py:91,106,147,189,351`). This makes polymorphic deserialization first-class.
- **`Secret` value object for encrypted credentials.** `Secret.from_plaintext` / `get_plaintext` / `get_plaintext_async` provide a uniform envelope; fall back to plaintext storage when no encryption key is configured (`letta/schemas/secret.py:13-100`). Replaces direct `api_key: str` fields and is paired with `__setattr__`/`__getattribute__` warnings on the legacy fields (`letta/schemas/providers/base.py:42-56`).
- **URL allowlist + scheme validation.** `validate_mcp_server_url` restricts MCP servers to http/https (`letta/schemas/mcp.py:54-60`); `validate_server_url` exists in both `mcp.py` and `mcp_server.py` (`letta/schemas/mcp.py:54-60`, `letta/schemas/mcp_server.py:40-42`), suggesting the two modules were split but the validator was duplicated rather than shared.
- **Multi-instance config + default factory.** `EmbeddingConfig.default_config(model_name, provider)` returns known-good configs (`letta/schemas/embedding_config.py:44-82`); `LLMConfig.default_config` does the same for GPT-4/4o/4.1/5/5.1/5.2/letta (`letta/schemas/llm_config.py:263-347`); `TokenCounter.create_token_counter(provider_type, ...)` selects the right counter (`letta/services/context_window_calculator/token_counter.py:268-316`).

## Tradeoffs

- **Two parallel LLM config systems.** `LLMConfig` is the wire-format schema used throughout the codebase; `ModelSettingsUnion` (with discriminated union of 16 settings classes) is the new one. Both must be kept in sync; `LLMConfig._to_model_settings` (`letta/schemas/llm_config.py:355-494`) is a 140-line converter that must be updated for every new provider and every new model. The tradeoff: backward compatibility for clients consuming `LLMConfig` against type safety for new code paths.
- **Streaming interfaces are not ABCs.** `OpenAIStreamingInterface` and `AnthropicStreamingInterface` are concrete classes with concrete method signatures (`letta/interfaces/openai_streaming_interface.py:78`, `letta/interfaces/anthropic_streaming_interface.py:63`). The `LettaLLMStreamAdapter` (`letta/adapters/letta_llm_stream_adapter.py:97-100`) decides which to instantiate based on `model_endpoint_type`. This makes adding a new streaming protocol an exercise in matching an undocumented shape rather than implementing an ABC.
- **Abstract methods that just raise `NotImplementedError`.** `LLMClientBase.send_llm_batch_request_async` is abstract and raises `NotImplementedError` (`letta/llm_api/llm_client_base.py:280-290`); only Anthropic implements it. This is documented but means a non-Anthropic provider will fail at runtime, not at import time. A more rigorous design would mark the method as non-abstract with a clearer failure mode or remove it from the base entirely.
- **`BaseAgentV2` requires three abstract methods.** A new agent implementation must provide `build_request`, `step`, *and* `stream` even if it never serves one of those call paths (`letta/agents/base_agent_v2.py:35-104`). This forces every implementation to duplicate code paths it might not need.
- **No conformance suite.** Each implementation has its own integration test file. `test_llm_clients.py` exercises Anthropic batch requests (`tests/test_llm_clients.py:71-259`); `test_providers.py` exercises provider model listing (`tests/test_providers.py`); `test_provider_trace_backends.py` covers all three trace backends (`tests/test_provider_trace_backends.py`). There is no `test_conformance.py` that asserts every `LLMClientBase` subclass behaves the same way for a given input. This makes drift silent.
- **Legacy `providers.py` module alongside `schemas/providers/` package.** `letta/schemas/providers.py` (1618 lines) coexists with `letta/schemas/providers/` directory containing per-provider modules (`openai.py`, `anthropic.py`, etc.). The new package's `__init__.py` re-exports the new classes (`letta/schemas/providers/__init__.py:1-56`), but `providers.py` still defines its own `OpenAIProvider`, `AnthropicProvider`, etc. This creates a maintenance burden — changes must be made in both files or risk divergence.
- **Plugin protocol via duck-typing + registry.** `SummarizerProtocol` is `typing.Protocol` with `@runtime_checkable`, but enforcement is at lookup time (`letta/plugins/plugins.py:39-40`), not at construction. A plugin that doesn't implement the protocol will fail at `get_plugin` time, not at instantiation.

## Failure Modes / Edge Cases

- **Provider base-URL normalization.** `Provider.default_base_url` sets `base_url = model_settings.openai_api_base` when `provider_type == openai` and `base_url is None` (`letta/schemas/providers/base.py:74-80`). Other provider types rely on `field_validator` defaults like `AnthropicProvider.base_url = "https://api.anthropic.com/v1"` (`letta/schemas/providers/anthropic.py:128`). A custom base URL set via `ProviderUpdate` could be lost if normalization runs after the user-provided value. `cast_to_subtype()` defends by setting `self.base_url = None` for empty strings (`letta/schemas/providers/base.py:207-208`).
- **Streaming connection drops.** All `LLMClientBase.handle_llm_error` implementations recognize `httpx.RemoteProtocolError` and map it to `LLMConnectionError` (`letta/llm_api/llm_client_base.py:386-395`, `letta/llm_api/anthropic_client.py:1006-1015`, `letta/llm_api/openai_client.py:1253-1262`, `letta/llm_api/google_vertex_client.py:1040-1044`). The Anthropic sync path explicitly rejects streaming-required long-running ops with a `LLMBadRequestError` (`letta/llm_api/anthropic_client.py:119-134`).
- **OpenAI strict-mode schema failures.** `validate_complete_json_schema` flags empty-object schemas under `required`, missing `additionalProperties: false`, missing top-level `type`, free-form unions (`letta/functions/schema_validator.py:107-200`). The validator is *informational* — non-compliant MCP tools are accepted but marked `NON_STRICT_ONLY` (`tests/mcp_tests/test_mcp_schema_validation.py:97-160`). A strict-mode deployment would need a pre-flight check.
- **Tool name collision across organizations.** `LettaToolNameConflictError` is raised on collision *within* an organization (`letta/errors.py:135-143`). Cross-organization name reuse is permitted by design; if a custom tool is migrated between organizations, the name carries through.
- **Tool function signature drift.** `parse_function_arguments` AST-parses the source code at execution time (`letta/services/helpers/tool_parser_helper.py`). Source code that fails to parse (e.g., TypeScript or malformed Python) falls back to "no argument annotations detected" (`letta/services/tool_sandbox/base.py:80-95`). TypeScript tools are explicitly excluded from `agent_state`/`agent_id` injection (`letta/services/tool_sandbox/base.py:76-79`).
- **Sandbox fallback.** `SandboxToolExecutor` tries Modal first if configured, falls back to E2B or LOCAL on failure (`letta/services/tool_executor/sandbox_tool_executor.py:77-100`). A silent fallback can mask provider outages.
- **LLMConfig / ModelSettings drift.** A change to either schema must be matched in `_to_model_settings` / `from_llm_config` / `_to_legacy_config_params` (`letta/schemas/llm_config.py:355-494`, `letta/schemas/model.py:97-547`). The bidirectional converters are 140+ lines each.

## Future Considerations

- **Introduce a conformance harness.** A `tests/conformance/` package with shared scenarios ("context-window overflow returns `ContextWindowExceededError`", "BYOK provider key takes precedence over base", "tool executor returns `ToolExecutionResult(status='error')` on tool exception") would catch silent contract drift as new providers are added.
- **Promote streaming interfaces to ABCs.** Define a `StreamingResponseParser` ABC with `process_chunk`, `finalize` methods; make `OpenAIStreamingInterface` and `AnthropicStreamingInterface` implementations. - **Consolidate `LLMConfig` and `ModelSettings`.** Pick one as the canonical wire format; remove the other or convert it to a deprecated alias. The 140-line `_to_model_settings` and matching `_to_legacy_config_params` are maintenance debt.
- **De-duplicate `letta/schemas/providers.py` vs `letta/schemas/providers/`.** Two parallel definitions of `OpenAIProvider`, `AnthropicProvider`, etc. — one in each file. Either delete the legacy module or have it re-export from the new package exclusively.
- **Tighten `BaseAgentV2` abstract surface.** Split into `BlockingAgent` (just `step`) and `StreamingAgent` (just `stream`) so subclasses don't have to implement methods they don't need.
- **Make non-functional abstract methods non-abstract.** `send_llm_batch_request_async` is abstract but raises `NotImplementedError`. Mark it as a default-`NotImplementedError` method or remove it from the base.
- **Promote `StorageBackend` to a documented wire shape.** Only `LocalStorageBackend` is in-tree; cloud impl relies on conditional import. Add a clear "what does a StorageBackend implementation need to do" docstring or test fixture.
- **Strengthen `BaseStore`-style abstractions for MemfsClient.** `MemfsClient` (`letta/services/memory_repo/memfs_client_base.py:36`) does not implement `StorageBackend` directly — it uses `LocalStorageBackend` and `GitOperations` as collaborators.
