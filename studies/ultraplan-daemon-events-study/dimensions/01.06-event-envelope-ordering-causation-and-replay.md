# Dimension 01.06: Event Envelope, Ordering, Causation, and Replay

## Purpose

Study durable event contracts: typed facts, schema evolution, per-subject ordering, causation/correlation, replay cursors, and reconnectable observation.

## Steps

1. Catalog event envelope fields and type/version naming.
2. Separate event identity from operation/step/attempt identity.
3. Inspect sequence assignment and ordering guarantees.
4. Trace replay/subscription APIs and resume cursors.
5. Check causation, correlation, timestamps, and schema compatibility.

## Evidence to Capture

- Event models and schemas
- Sequence/cursor code
- Subscription APIs
- Replay/read-after-sequence handlers
- Schema versioning conventions
- Correlation/causation metadata

## Questions

1. What ordering is actually guaranteed?
2. Can a reconnecting client resume without gaps or duplicates?
3. Are events named as immutable past-tense facts?
4. Can the consumer tell why an event happened?
5. How does a schema evolve without breaking old clients?

| Score | Meaning |
