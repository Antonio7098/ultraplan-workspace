# Dimension 01.01: Daemon RPC and Execution Ownership

## Purpose

Study how long-lived execution ownership is separated from CLI, web, and TUI clients, including detach semantics, local RPC, authentication, versioning, and explicit workspace context.

## Steps

1. Identify which process owns accepted work after the submitting client disconnects.
2. Trace the client-to-daemon protocol and the smallest stable wire/API surface.
3. Inspect local transport choices such as Unix sockets, named pipes, or loopback RPC.
4. Check peer authentication, authorization, protocol/version negotiation, and workspace scoping.
5. Find shutdown and reconnect behavior for CLI/web observers.

## Evidence to Capture

- Daemon/server entrypoints
- RPC/service definitions
- Socket or transport setup
- Client attach/detach code
- Authentication and protocol handshake code
- Workspace or working-directory propagation

## Questions

1. Does a client exit affect execution?
2. What exactly crosses the daemon boundary?
3. Can a client reconnect and recover the same operation?
4. How is the local caller authenticated?
5. Does daemon code ever depend on its own current working directory?
