# Dimension 01.03: Durable Submission and Idempotent Acceptance

## Purpose

Study how work is durably accepted before acknowledgement and how duplicate client submissions are detected and resolved.

## Steps

1. Trace submission from request receipt to durable acknowledgement.
2. Find idempotency keys, request fingerprints, deduplication stores, or equivalent logic.
3. Check behavior when the caller times out after acceptance but before receiving the response.
4. Inspect validation/revalidation around prepare and start boundaries.
5. Identify retention and conflict rules for idempotency records.

## Evidence to Capture

- Submit/start handlers
- Idempotency tables or maps
- Canonical request fingerprinting
- Transactions around acceptance
- Duplicate/conflict tests
- Client retry behavior

## Questions

1. Can acknowledgement happen before durable acceptance?
2. What happens if the same key is retried with identical input?
3. What happens if the same key is reused with different input?
4. How long is deduplication state retained?
5. Can a network/client failure accidentally start duplicate work?

## Rating
