## Executive Summary

Only one of four systems survives the dimension's canonical failure — crash after commit but before the response reaches the client with a retry that returns the original operation. Temporal (8/10) does: a conditional write to the current-execution table durably records `RequestIds` (`service/history/workflow/mutable_state_impl.go:2591`, `common/persistence/data_interfaces.go:45` `CreateWorkflowModeBrandNew`) before any ack, and a retry with the same opaque `RequestId` (`service/frontend/workflow_handler.go:6947`) returns the original `RunId` with `Started:false` via `respondToRetriedRequest` (`service/history/api/startworkflow/api.go:340`). The other three conflate deduplication with resource identity and offer no replay.

Containerd (5/10) and Dagster (5/10) both enforce durable-before-ack but diverge on what that guarantees. Containerd's bbolt `DB.Update` (`core/metadata/db.go:272`, `core/metadata/containers.go:149`) commits `CreateBucket` → `ErrAlreadyExists` before reply, so retry with the same resource name/idempotently reports `AlreadyExists` (`core/metadata/containers.go:149`, `core/metadata/images.go:145`). Dagster's `SqlRunStorage._core_add_run` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:145` `RunsTable.insert` with `run_id String(255) unique=True` at `python_modules/dagster/dagster/_core/storage/runs/schema.py:17`) commits the `DagsterRun` row before GraphQL `do_launch` acks (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/launch_execution.py:51`), and the daemon's tick reservation (`python_modules/dagster/dagster/_daemon/sensor.py:210` `set_run_requests` before `create_run`) gives at-most-once-as-expected within sensors — but neither returns the cached response, and external callers that mint a fresh UUID on retry double-create.

BuildKit (2/10) is the negative control: acceptance is `Solver.NewJob` (`solver/jobs.go:687` `jl.jobs[id]` map insert under `jl.mu.Lock`) with no durable write; the BoltDB `history.Queue.Update(STARTED)` (`solver/llbsolver/history.go:49`, `solver/llbsolver/history/buildhistory.go:531`) follows in a separate, non-atomic transaction. There is no idempotency table, no fingerprint, and duplicate `Ref` is rejected or silently re-executed depending on whether the 10 s `Discard` grace (`solver/jobs.go:890`) has elapsed. Vertex-level `flightcontrol`/`sharedOp` dedup (`solver/jobs.go:995`) masks the absence at the job boundary but does not fix it.

The universal gap is canonical fingerprinting: every source dedupes on an opaque key (`Ref`, `ContainerID/digest`, `run_id/run_key`, `RequestId`) without hashing the payload. Reusing the same key with different inputs is rejected as `AlreadyExists` (containerd, dagster `run_id`), silently swallowed as "already done" (dagster `run_key` → `SkippedSensorRun` at `python_modules/dagster/dagster/_daemon/sensor.py:1358`, temporal `StartDeduped` at `service/history/api/startworkflow/api.go:340`), or accepted as new work after a short window (buildkit). No source except Dagster's narrow `register_managed_run` (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:621` `_check_run_equality` → `DagsterRunConflict` at `python_modules/dagster/dagster/_core/errors.py:562`) compares payloads on collision.

## Core Thesis

**Durable acceptance and idempotent acceptance are two independent axes, and only Temporal nails both; the other three split.**

- **Durable-before-ack** is necessary but not sufficient for idempotency. Containerd and Dagster prove you can commit before reply without being able to *replay* the reply. BuildKit proves the converse failure: without durability, any retry window is bounded by RAM.
- **Identity-as-key** works when the caller is disciplined about stable IDs, but it couples API ergonomics to caller-generated uniqueness. Temporal's opaque `RequestId` (auto-filled via `uuid.NewString()` at `service/frontend/workflow_handler.go:6947`) plus per-execution `RequestIds` map (`api/persistence/v1/executions.pb.go:1452`) decouples the dedup key from the resource name and enables true idempotent *return* rather than just idempotent *reject*.
- **Retention is the hidden contract.** All four tie dedup lifetime to object lifetime except Temporal's CHASM path and containerd's 24 h ingest `expireAt` (`core/metadata/content.go:458`). Indefinite retention (Dagster runs forever, containerd containers until `Delete`, Temporal classic `RequestIds` with `AttachTime==nil` at `service/history/workflow/mutable_state_impl.go:2691`) prevents accidental reuse but grows state and precludes key recycling. Bounded retention (BuildKit 10 s, Temporal `MaximumRequestIDsPerExecution=25` at `common/dynamicconfig/constants.go:2646` + `RequestIDMaxAge=7d` at `common/dynamicconfig/constants.go:2652`, containerd ingest 24 h) reopens the duplicate-work window if misconfigured.

In short: if you need at-most-once submission that survives client timeout, you need (1) a conditional or transactional commit *before* ack, (2) a dedicated dedup store separate from the resource table or indexed by opaque `RequestId`, and (3) replay of the stored response on `AlreadyExists` — the combination only Temporal demonstrates end-to-end. If you only need at-least-once with caller-side `AlreadyExists`-as-success handling, containerd/Dagster's identity-as-key plus bbolt/UNIQUE commit is sufficient and simpler.

## Approach Models

Sources cluster into four durability/idempotency models ordered by strength of the retry-after-commit guarantee.

### A. No Durable Submission — Ephemeral Map + Best-Effort History (buildkit — 2/10)

Submission is `Control.Solve` (`control/control.go:409`) unary → `Solver.NewJob(id)` (`solver/jobs.go:687`) `jobs map[string]*Job` existence check → `llbsolver.recordBuildHistory` (`solver/llbsolver/history.go:49`) BoltDB `Update(STARTED)` in a *separate* transaction (`solver/llbsolver/history/buildhistory.go:418`). No `idempotency_key` field on `SolveRequest` (`api/services/control/control.proto:14`); `Ref` is random per `Client.solve` (`client/solve.go:107`). Dedup window is `Job.Discard` 10 s delayed delete (`solver/jobs.go:890`); history retention `MaxAge 48h / MaxEntries 50` (`solver/llbsolver/history/buildhistory.go:81`) is observability-only and never consulted on admission. Vertex-level `actives map[digest]*state` (`solver/jobs.go:41`) + `sharedOp.gCacheRes/gDigest/gExecRes` (`solver/jobs.go:995`) dedupes *inside* a build, not across submissions.

Why it fits BuildKit: builds stream client-local files over a `Session` (`client/solve.go:141`) and the daemon is single-node; synchronous `Solve` is simplest and cache sharing already amortizes duplicate work.

### B. Resource-Identity-as-Idempotency — bbolt Existence Check (containerd — 5/10)

Idempotency key equals resource identity: `container.ID`/`image.Name`/`snapshot key`/`digest`/`lease ID` (`core/metadata/buckets.go:146`). Each `Create` does `bkt.CreateBucket(key)` inside `DB.Update`/`update` (`core/metadata/db.go:272`, `core/metadata/bolt.go:47`) and maps `ErrBucketExists` → `errdefs.ErrAlreadyExists` (`core/metadata/containers.go:149`, `core/metadata/images.go:145`, `core/metadata/snapshot.go:344`, `core/metadata/content.go:698`, `plugins/content/local/store.go:542`) before reply. Content ingest adds resumable file state under `root/ingest/<hash>` (`plugins/content/local/store.go:546`) plus `ingests/<ref>` bucket (`core/metadata/buckets.go:289`) with 24 h `expireAt` when unleased (`core/metadata/content.go:458`). Tasks are the exception: `plugins/services/tasks/local.go:171` checks `rtime.Get` not bbolt. No fingerprint, no `Idempotency-Key` header; dedup lives as long as the object (or until GC via `core/metadata/gc.go:495`).

Why it fits containerd: embedded node runtime with single-writer bbolt; content-addressed digests already serve as natural keys; callers (CRI, unpacker) already handle `AlreadyExists` as success (`client/pull.go:309`, `core/unpack/unpacker.go:419`).

### C. DB-Row Intent with Tick-Reserved WAL — Dual-Key Tag Scan (dagster — 5/10)

Two dedup keys at different layers. System layer: `run_id` UNIQUE (`python_modules/dagster/dagster/_core/storage/runs/schema.py:17`) enforced by `_core_add_run` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:142`) raising `DagsterRunAlreadyExists` (`python_modules/dagster/dagster/_core/errors.py:562`) before `instance.submit_run` (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/launch_execution.py:53`). Application layer: `dagster/run_key` tag (`python_modules/dagster/dagster/_core/storage/tags.py:54`) checked via serial `fetch_existing_runs` → `RunsFilter(tags={RUN_KEY_TAG: k})` (`python_modules/dagster/dagster/_daemon/sensor.py:1292`) → `_get_or_create_sensor_run` returning `SkippedSensorRun` (`python_modules/dagster/dagster/_daemon/sensor.py:1358`). Durability envelope is DB commit before ack plus sensor WAL: `SensorLaunchContext.set_run_requests` (`python_modules/dagster/dagster/_daemon/sensor.py:210`) persists `reserved_run_ids` in the tick, resumed within `MAX_TIME_TO_RESUME_TICK_SECONDS=86400` (`python_modules/dagster/dagster/_daemon/sensor.py:77`) via `_get_evaluation_tick` (`python_modules/dagster/dagster/_daemon/sensor.py:530`). Only `register_managed_run` (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:576`) does field-diff `_check_run_equality` → `DagsterRunConflict` (`python_modules/dagster/dagster/_core/errors.py:562`).

Why it fits Dagster: Python orchestration where DB is source of truth and daemon is a polling controller; tick reuse was already needed for cursor durability, so reservation piggybacks cheaply.

### D. Opaque RequestId Ledger with Conditional Current-Table Write (temporal — 8/10)

Submission is `WorkflowHandler.StartWorkflowExecution` (`service/frontend/workflow_handler.go:550`) → `prepareStartWorkflowRequest` validating/defaulting `RequestId` (`service/frontend/workflow_handler.go:615`, `service/frontend/workflow_handler.go:6939` `uuid.NewString()` if empty) → `Starter.prepare` (`service/history/api/startworkflow/api.go:119`) → `lockCurrentWorkflowExecution` (`service/history/api/startworkflow/api.go:235`) → `CreateWorkflowExecution(CreateWorkflowModeBrandNew)` (`service/history/api/startworkflow/api.go:307`) conditional on `(namespace, workflowId)` uniqueness (`common/persistence/data_interfaces.go:45`). On conflict, persistence returns `CurrentWorkflowConditionFailedError{RequestIDs}` (`common/persistence/data_interfaces.go:114`) and `handleConflict` checks `currentWorkflowRequestIDs[requestId]` (`service/history/api/startworkflow/api.go:340`) → `StartWorkflowRequestDeduped` metric (`service/history/api/startworkflow/api.go:341`) → `respondToRetriedRequest` (`service/history/api/startworkflow/api.go:344`) rehydrating history (`service/history/api/startworkflow/api.go:571` `getMutableStateInfo`/`getWorkflowHistory`). Dedup store is `WorkflowExecutionState.RequestIds map[string]*RequestIDInfo` (`api/persistence/v1/executions.pb.go:1452`, `service/history/workflow/mutable_state_impl.go:410`) written via `AttachRequestID` (`service/history/workflow/mutable_state_impl.go:2591`) / `AttachChasmRequestID` (`service/history/workflow/mutable_state_impl.go:2615`). Signal (`service/history/api/signalworkflow/api.go:45` `IsSignalRequested`/`AddSignalRequested`) and Update (`service/history/workflow/update/update.go:324` `stateCreated` guard) reuse the same pattern.

Why it fits Temporal: multi-tenant workflow service where any frontend may die and any other must idempotently recover; conditional current-table is the linearizable arbiter without an external lock service.

## Pattern Catalog

### Pattern 1: Bucket/TABLE Existence as Idempotency Gate

**Problem:** Detect duplicate submission without a separate dedup table.

**Sources:** containerd (`core/metadata/containers.go:149` `bkt.CreateBucket` → `ErrAlreadyExists`, plus `core/metadata/images.go:145`, `core/metadata/snapshot.go:344`, `core/metadata/content.go:698`, `plugins/content/local/store.go:542`), dagster (`python_modules/dagster/dagster/_core/storage/runs/schema.py:17` `unique=True` + `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:148` `IntegrityError` → `DagsterRunAlreadyExists`), temporal conditional `CreateWorkflowModeBrandNew` (`common/persistence/data_interfaces.go:45` + `service/history/api/startworkflow/api.go:307`).

**Why it works:** The storage engine's uniqueness constraint *is* the dedup check — no extra lookup, atomic with commit, crash-safe via `bbolt.Tx.Commit`/`SQL INSERT`/`conditional write`. Tests assert deterministically (`plugins/content/local/store_test.go:218`, `python_modules/dagster/dagster_tests/storage_tests/utils/run_storage.py:1084`).

**When to copy:** Single-writer embedded stores (bbolt, SQLite) or conditional-write capable DBs where the dedup key is the resource primary key.

**When overkill/risky:** When the natural key is user-controlled free text — collisions are indistinguishable from retries, and no payload diff is possible. Add an opaque `RequestId` ledger (Temporal model) instead of overloading the resource name.

**Evidence:** `core/metadata/containers.go:149`, `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:148`, `service/history/api/startworkflow/api.go:307`.

### Pattern 2: Durable-Before-Ack via Transaction or Conditional Write

**Problem:** Avoid acking before the accept is crash-safe.

**Sources:** containerd `DB.Update` (`core/metadata/db.go:272`) before gRPC reply (`plugins/services/containers/local.go:122`), dagster `with self.connect() as conn` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:145`) before `do_launch` returns, temporal `CreateWorkflowExecution` (`service/history/api/startworkflow/api.go:307`) before `generateResponse` (`service/history/api/startworkflow/api.go:226`). BuildKit is the counter-example — `NewJob` (`solver/jobs.go:687`) then detached `history.Update` (`solver/llbsolver/history.go:49`).

**Why it works:** Client timeout after commit still sees `AlreadyExists` and can `Get` the object (`core/metadata/containers.go:55`, `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:427`); no WAL replay needed for the happy path.

**When to copy:** Always for operations that must survive daemon crash. Keep the transaction minimal (containerd's split-phase snapshot at `core/metadata/snapshot.go:367` shows why I/O should stay outside the lock).

**When overkill/risky:** Holding a global bbolt lock (`core/metadata/db.go:272` `wlock.RLock`) across slow snapshot driver or network call stalls all writers — split as containerd does, but accept the orphan-GC cost.

**Evidence:** `core/metadata/db.go:272`, `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:145`, `service/history/api/startworkflow/api.go:307`.

### Pattern 3: Opaque RequestId Separate from Resource Identity

**Problem:** Let retries be idempotent even when the resource name is not known or is content-addressed.

**Sources:** temporal `validateRequestId` (`service/frontend/workflow_handler.go:6939`) + `WorkflowExecutionState.RequestIds` (`api/persistence/v1/executions.pb.go:1452`) and `CurrentWorkflowConditionFailedError.RequestIDs` (`common/persistence/data_interfaces.go:119`); dagster's partial analogue is `run_key` tag (`python_modules/dagster/dagster/_core/storage/tags.py:54`) plus `reserved_run_ids` in tick (`python_modules/dagster/dagster/_daemon/sensor.py:1105`).

**Why it works:** The `RequestId` is the dedup key, the `(namespace, WorkflowId, RunId)` is the resource identity — they vary independently. Replaying the same `RequestId` after a lost response returns the original operation without requiring the caller to know the `RunId` (`service/history/api/startworkflow/api.go:356` `RequestIdRef` link).

**When to copy:** Any gRPC/HTTP API where clients may retry on `DeadlineExceeded`/`Unavailable`. Auto-generate when empty (`service/frontend/workflow_handler.go:6944`) but require SDKs to echo it on retry; expose it in `AlreadyExists` error details so direct API callers can recover.

**When overkill/risky:** Pure content-addressed stores where `digest` already is the opaque key (containerd blobs). Adding a second key duplicates indexing.

**Evidence:** `service/frontend/workflow_handler.go:6947`, `api/persistence/v1/executions.pb.go:1452`, `python_modules/dagster/dagster/_core/storage/tags.py:54`.

### Pattern 4: Tick Reservation / WAL Before Side Effects

**Problem:** Make a polling controller's "prepare then create" crash-resumable without a distributed transaction.

**Sources:** dagster `SensorLaunchContext.set_run_requests` (`python_modules/dagster/dagster/_daemon/sensor.py:210`) persisting `run_requests + reserved_run_ids + cursor` before `instance.create_run` (`python_modules/dagster/dagster/_daemon/sensor.py:1419`), resumed via `_get_evaluation_tick` (`python_modules/dagster/dagster/_daemon/sensor.py:530`); containerd's two-phase `createSnapshot` first-tx lease reserve (`core/metadata/snapshot.go:334` + `core/metadata/leases.go:337`) before backend `Prepare`.

**Why it works:** The reservation is the minimal durable intent; crash after reserve but before create replays the same IDs without forking new work. Keeps the hot-path transaction short.

**When to copy:** Any daemon that does polling evaluation → batch creation (sensors, schedulers, snapshot prepares). Use the existing durable row (tick, lease) as WAL rather than inventing a new journal.

**When risky:** The 24 h cliff (`python_modules/dagster/dagster/_daemon/sensor.py:77`) and lack of fencing on concurrent daemon writers (`python_modules/dagster/dagster/_daemon/sensor.py:182` log-only duplicate detection) can silently drop or double-create.

**Evidence:** `python_modules/dagster/dagster/_daemon/sensor.py:210`, `core/metadata/snapshot.go:334`.

### Pattern 5: Resumable Writer with Hash Replay

**Problem:** Let a client resume content upload after a timeout without re-uploading bytes or creating a second ingest.

**Sources:** containerd `store.resumeStatus` (`plugins/content/local/store.go:501` re-hash via `io.CopyBuffer` over `data`) + `store.writer` `tryLock` per `ref` (`plugins/content/local/store.go:475`), and `contentStore.Writer` early `exists=true` check (`core/metadata/content.go:373`) skipping backend allocation when `expected` digest already shared (`core/metadata/content.go:414`).

**Why it works:** `Ref` (`plugins/content/local/store.go:484`) is the ingest session key; file offset + hash validation (`plugins/content/local/store.go:571`) lets the same `ref` continue from `Status.Offset` rather than erroring with `AlreadyExists`.

**When to copy:** Large blob uploads over unreliable networks. Keep ingest path hashed (`plugins/content/local/store.go:654` `digest.FromString(ref)`) and `expireAt` bounded (24 h at `plugins/content/local/store.go:593`).

**When overkill:** Small, fast metadata creates where re-`Create` with `AlreadyExists` handling is cheaper than resumable protocol.

**Evidence:** `plugins/content/local/store.go:501`, `core/metadata/content.go:373`.

### Pattern 6: Retention as Object Lifetime vs Bounded Sweep

**Problem:** Decide how long a dedup key blocks reuse.

**Sources:** Indefinite: containerd containers/images/snapshots/blobs until `Delete` (`core/metadata/containers.go:287`, `core/metadata/gc.go:495`), dagster `run_id`/`run_key` until `delete_run`/`wipe` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:602`), temporal classic `RequestIds` with `AttachTime==nil` never swept (`service/history/workflow/mutable_state_impl.go:2691`) until execution retention scanner (`common/dynamicconfig/constants.go:3511`). Bounded: buildkit 10 s jobs (`solver/jobs.go:890`), containerd ingest 24 h (`core/metadata/content.go:458`), temporal CHASM `MaximumRequestIDsPerExecution=25`/`RequestIDMaxAge=7d` (`common/dynamicconfig/constants.go:2646`, `common/dynamicconfig/constants.go:2652`) via `closeTransactionSweepChasmRequestIDs` (`service/history/workflow/mutable_state_impl.go:2664`).

**Why it works:** Indefinite retention makes `AlreadyExists` forever and prevents accidental re-trigger (desired for pipelines); bounded sweep caps storage and allows key recycling but reopens the duplicate window after eviction.

**When to copy:** Keep the dedup store separate from GC roots if you need bounded recycling — add an `idempotency` bucket with TTL (containerd `expireAt` model) rather than overloading object lifetime. Dagster would benefit from a `run_key_expiry` side table.

**When risky:** Classic Temporal signals never swept → `RequestIds` map grows linearly with signals (`service/history/workflow/mutable_state_impl.go:2574` `approximateSize`, `common/persistence/data_interfaces.go:745` `SignalRequestIDSize`) with no backpressure except `MaximumSignalsPerExecution=10000` (`common/dynamicconfig/constants.go:2641`).

**Evidence:** `solver/jobs.go:890`, `core/metadata/content.go:458`, `service/history/workflow/mutable_state_impl.go:2691`.

### Pattern 7: Idempotent Replay of the Original Response (Not Just Reject)

**Problem:** After crash-before-response, the client needs the *same* success to avoid branching logic.

**Sources:** temporal `respondToRetriedRequest` (`service/history/api/startworkflow/api.go:571` loading `mutableStateInfo` + `getWorkflowHistory` at `service/history/api/startworkflow/api.go:671`, eager-start rehydration) returning `RunId`/`FirstExecutionRunId` with `Started:false` (`service/history/api/startworkflow/api.go:340`). Containerd/dagster counter-examples return `AlreadyExists` and expect caller to `Get` (`client/pull.go:309` treating `AlreadyExists` as success, `python_modules/dagster-graphql/dagster_graphql/client/client.py:290` mapping `RunConflict` to error requiring manual `get_run_by_id`).

**Why it works:** The dedup path reconstructs the response from durable state, so retry is transparent to the caller — SDKs already preserve `RequestId` on retry, and `StartWorkflowRequestDeduped` (`service/history/api/startworkflow/api.go:341`) proves it is hit in production.

**When to copy:** Any API where the response contains server-assigned IDs (RunId, operation handle, lease). Persist `requestId → (response, expiry)` or derive replay from the execution row.

**When risky:** Replaying must not reuse a mutating side effect (registry push). Temporal avoids this by only replaying *start/signal* — the execution still runs once.

**Evidence:** `service/history/api/startworkflow/api.go:340`, `client/pull.go:309`.

## Key Differences

**Convergence — what holds despite different implementations:**

- **Commit-before-reply is table stakes except BuildKit.** Containerd (`core/metadata/db.go:272`), Dagster (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:145`), Temporal (`service/history/api/startworkflow/api.go:307`) all commit before gRPC reply; BuildKit's `NewJob` → `history.Update` split (`solver/jobs.go:687`, `solver/llbsolver/history.go:49`) is the outlier.
- **No fingerprint, only key equality.** All four dedupe on the key string alone — `Ref` (`solver/jobs.go:692`), `ContainerID/digest/key` (`core/metadata/containers.go:149`), `run_id` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:148`) / `run_key` (`python_modules/dagster/dagster/_daemon/sensor.py:1351`), `RequestId` (`service/history/api/startworkflow/api.go:340`). Payload diff only exists in Dagster's `register_managed_run` island (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:621`).
- **Retention defaults to forever unless explicitly bounded.** Containerd/dagster/temporal-classic keep dedup state until object deletion; bounded windows only appear for ingest or CHASM updates.

## Decision Guide

Use this as a flowchart. Start from the dimension's prompt: **crash after commit but before the response — can retry return the original operation?**

1. **Do you need retry to return the *same* operation without client-side `Get`?**
   - **Yes** (user-facing API, SDK retry on `DeadlineExceeded` must be transparent): implement **Temporal model**. Mint opaque `RequestId` at edge (`service/frontend/workflow_handler.go:6939`), conditional write to a current/primary table (`common/persistence/data_interfaces.go:45` `CreateWorkflowModeBrandNew`), store `RequestId → (RunId, response)` in the execution row (`executions.pb.go:1452`), and on `CurrentWorkflowConditionFailedError` (`common/persistence/data_interfaces.go:119`) check `RequestIDs[requestId]` (`service/history/api/startworkflow/api.go:340`) → `respondToRetriedRequest` (`service/history/api/startworkflow/api.go:571`). For non-workflow resources, add a dedicated `idempotency` bucket with `requestId + fingerprint → response + expiry` (containerd ingest `expireAt` at `core/metadata/content.go:458` is the TTL template).
   - **No, `AlreadyExists` + `Get` is acceptable**: containerd/Dagster model suffices. Commit via `DB.Update`/`UNIQUE INSERT` before reply (`core/metadata/db.go:272`, `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:145`) and document that callers must treat `AlreadyExists` as success and `Get` the object. Ensure clients *preserve* the key on retry (`client/pull.go:309`).

2. **Does the operation stream client-local inputs that cannot be pre-materialized?**
   - If yes (BuildKit session files): split `Control.Solve` (`control/control.go:409`) into `CreateJob(Ref, descriptor)` durable + `Start(Ref)` with lease (`solver/llbsolver/history/buildhistory.go:104`). Persist descriptor and `CreateRequestId` (`service/history/workflow/mutable_state_impl.go:2591` analogue) in Bolt before ack so retry can poll `Status(Ref)` (`solver/llbsolver/solver.go:465`) or `ListenBuildHistory` (`solver/llbsolver/history/buildhistory.go:770`) for `COMPLETE`. Copy containerd's hashed `ingestRoot(ref)` (`plugins/content/local/store.go:654`) to avoid path traversal.

3. **Is the natural dedup key user-visible (container name, image tag, daily partition)?**
   - If yes, keep it but add a second opaque layer: resource name for *creation* dedup, `RequestId`/`run_key` for *submission* dedup. Dagster's dual `run_id` + `run_key` (`python_modules/dagster/dagster/_core/storage/tags.py:54`) shows the split — fix its silent-skip by adding `_check_run_equality` (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:624`) on `run_key` collision.

4. **Do you need to dedupe high-frequency signals/updates without unbounded growth?**
   - Use bounded retention with lazy sweep at transaction close (`service/history/workflow/mutable_state_impl.go:2664` `closeTransactionSweepChasmRequestIDs`) gated by `MaximumRequestIDsPerExecution`/`RequestIDMaxAge` (`common/dynamicconfig/constants.go:2646`). For long-lived dedup (workflow start), keep classic IDs immortal and delete only with the execution. Emit `CHASMRequestIDEvicted` (`service/history/workflow/mutable_state_impl.go:2714`) / `SignalRequestIDSize` metrics and alarm at 80% cap.

5. **Are you a polling controller (sensor, scheduler) not an RPC handler?**
   - Reserve IDs in the tick/WAL *before* creating runs (`python_modules/dagster/dagster/_daemon/sensor.py:210` `set_run_requests`), resume within a bounded window (`python_modules/dagster/dagster/_daemon/sensor.py:538` 24 h), and cache `existing_runs_by_key` for same-tick dedup (`python_modules/dagster/dagster/_daemon/sensor.py:1373`). Add fencing (`SELECT FOR UPDATE` or advisory lock) if multiple daemons can run.

## Practical Tips

### Patterns to copy

- **Conditional write as commit point.** Use `CreateWorkflowModeBrandNew` / `bkt.CreateBucket` / `UNIQUE INSERT` and return `AlreadyExists` on conflict before any publish or side effect (`core/metadata/containers.go:149`, `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:148`, `service/history/api/startworkflow/api.go:307`). This single invariant eliminates half of duplicate-work bugs.
- **Opaque `RequestId` auto-generated at the edge.** Default `RequestId` when empty (`service/frontend/workflow_handler.go:6947` `uuid.NewString()`) but require SDKs/clients to echo it on retry. Return it in error details so direct gRPC callers can retry correctly (temporal `GenerateRequestIdRefLink` at `service/history/api/link_util.go:30`).
- **Replay, don't just reject.** On dedup hit, reconstruct the success response from durable state (`service/history/api/startworkflow/api.go:571` `respondToRetriedRequest` + eager `getWorkflowHistory` at `service/history/api/startworkflow/api.go:671`). For containerd/dagster, at minimum provide a `Get/Create` helper that maps `AlreadyExists` → `Get` (`client/pull.go:309` pattern) — document it in the proto.
- **WAL via existing durable row.** Reuse tick/lease as prepare ledger (`python_modules/dagster/dagster/_daemon/sensor.py:210` `reserved_run_ids`, `core/metadata/snapshot.go:334` lease) rather than a new journal. Keep the reservation minimal (IDs + cursor) and replay on restart.
- **Hashed ingest paths + resumable offset.** `digest.FromString(ref)` (`plugins/content/local/store.go:654`) keeps paths bounded; `resumeStatus` (`plugins/content/local/store.go:501`) lets `Writer` continue at `Offset` (`plugins/content/local/store.go:571`). Add 24 h `expireAt` (`plugins/content/local/store.go:593`).
- **Count + age sweep, lazy on write.** `closeTransactionSweepChasmRequestIDs` (`service/history/workflow/mutable_state_impl.go:2664`) evicts by age then oldest-first count in one pass, only when `chasmRequestIDsAdded` — minimal write amplification.
- **Distinguish `AlreadyExists` (retry) from `Conflict` (payload mismatch) where possible.** Dagster's `DagsterRunConflict` with `_format_field_diff` (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:621`) is the only example — generalize it.

### Patterns to avoid or delay until needed

- **Synchronous unary RPC holding the handler for the whole operation** (`control/control.go:409` `Solve` blocks until export). Fails the kill-test and forces `10 s` grace hacks. Split into `Create`/`Start` + poll unless inputs truly require streaming and you add a durable descriptor.
- **`Chmod 0666` / `insecure channel` on retry paths.** Client retry over insecure transport amplifies duplicate-work risk if an attacker can trigger replays. Require `RequestId` + fingerprint check before dedup-replay.
- **Silent `SkippedSensorRun` on `run_key` collision** (`python_modules/dagster/dagster/_daemon/sensor.py:1358`) without diff. It hides legitimate divergence (new `run_config` with same key). Return `409 Conflict` with diff (as `register_managed_run` does) or log with `existing_run` payload.
- **Publishing after commit without idempotent consumer.** `publisher.Publish` after `DB.Update` (`plugins/services/containers/local.go:139`) that returns error on publish failure turns a durable success into a client-visible failure — retries then see `AlreadyExists` but may not know to treat it as success. Either outbox or mark publish as best-effort with metric.
- **Content-addressed reuse without attempt isolation for side-effecting work.** `flightcontrol.Group` coalescing (`solver/jobs.go:1219`) is correct for cache but wrong for registry pushes or materializations — key singleflight by `(digest, attemptId)` or `(run_id, step_key)` if retries must be side-effect-quarantined.

### Decision rules

- **If the operation creates a server-assigned handle** (`RunId`, `Ref`): the retry must accept the same client-supplied `RequestId` and return the same handle with `Started:false`/`AlreadyExists` + `Get`. Pin a test: commit, kill gRPC stream before flush, retry with same `RequestId`, assert same handle (temporal `service/history/api/startworkflow/api.go:340` path, dagster `test_write_conflicting_run_id` at `python_modules/dagster/dagster_tests/storage_tests/utils/run_storage.py:1084` extended to retry-after-commit).
- **If the dedup key is the resource name**: generation must be `make_new_run_id()` / `identity.NewID()` *only* when caller omits it (`python_modules/dagster/dagster/_core/storage/dagster_run.py:326`, `client/solve.go:107`); when caller supplies it, treat it as the idempotency key and implement `hash(input)` mismatch detection.
- **If you bound retention**: document the window and monitor near-cap eviction (`service/history/workflow/mutable_state_impl.go:2714` `CHASMRequestIDEvicted`). Never bound workflow-start dedup without an operator-facing alarm — re-execution after expiry creates duplicate materializations.

### Caution signs (the dimension is becoming brittle)

- **No `AlreadyExists` → `Get` path tested end-to-end.** Grep for retry harness covering `timeout after commit` — containerd and dagster both lack one (`core/metadata/containers_test.go` only tests immediate duplicate, `python_modules/dagster/dagster_tests/storage_tests/utils/run_storage.py:1084` only tests same-payload duplicate).
- **Split commit without compensating visibility.** `RunsTable.insert` + `RunTagsTable.insert` on Postgres `AUTOCOMMIT` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:225`) or bbolt `ingest/<hash>/data` + `ingests/<ref>` bucket (`plugins/content/local/store.go:608` vs `core/metadata/content.go:427`) diverging — next reader sees half-state and double-creates.
- **`RequestIds` / `SignalRequestedIDs` growth without cap.** Each distinct `RequestId` adds `len(requestID)` to `approximateSize` (`service/history/workflow/mutable_state_impl.go:2574`); `MaximumSignalsPerExecution=10000` does not bound `SignalRequestIDSize` (`common/dynamicconfig/constants.go:2641`).
- **Tick/WAL retention mismatch** where tick purge (`python_modules/dagster/dagster/_daemon/sensor.py:334`) is shorter than run retention — resumed tick is `SKIPPED` (`python_modules/dagster/dagster/_daemon/sensor.py:553`) and ingestion silently lost.
- **Client generates new UUID on every retry** (BuildKit `identity.NewID()` per `Client.solve` at `client/solve.go:107` unless `opt.Ref`稳定, Dagster `make_new_run_id()` when `executionMetadata.runId` absent at `python_modules/dagster-graphql/dagster_graphql/implementation/execution/run_lifecycle.py:87`). Any `DeadlineExceeded` retry then double-creates by construction — the fix is caller-preserved `RequestId`/`runId`.
- **Two-phase snapshot metadata divergence** (`core/metadata/snapshot.go:508`) with no WAL entry — backend snapshot exists, metadata doesn't, `Prepare` retry only leases, never mounts.
- **History GC while `Listen` holds refs** (`solver/llbsolver/history/buildhistory.go:241` `refs` refcount vs `solver/llbsolver/solver.go:465` `Status` fallback) — status tail can race with GC and return `os.ErrNotExist` despite live job.

## Anti-Patterns / Caution Signs

- **Ack before durable commit.** BuildKit `solver/jobs.go:687` before `solver/llbsolver/history.go:49`; containerd task `plugins/services/tasks/local.go:171` without bbolt. Any `Create` that replies before `DB.Update`/`conditional write` fails the crash-after-commit test.
- **Identity collision without payload diff.** Containerd `core/metadata/containers.go:149` and dagster `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:148` return same `AlreadyExists` for identical retry and semantic conflict. Callers cannot diagnose misuse without `Get` + manual diff. Add `_check_run_equality` (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:624`) or `hash(canonicalRequest)` on collision.
- **Random key per retry as default path.** BuildKit `client/solve.go:107` and dagster GraphQL `python_modules/dagster-graphql/dagster_graphql/implementation/execution/launch_execution.py:37` mint new IDs when caller omits them — guarantees duplicate work on timeout retry. Make `RequestId`/`runId` an explicit `Idempotency-Key` header/mutation field with docs.
- **Silent swallow on business-key dedup.** Dagster `python_modules/dagster/dagster/_daemon/sensor.py:1358` `SkippedSensorRun` and temporal signal `service/history/api/signalworkflow/api.go:45` `Noop` both discard the second intent without diff. Log at `info` with `existing_run` correlation or surface `409 Conflict`.
- **Post-commit publish that can fail the RPC.** `plugins/services/containers/local.go:139` returning publish error after commit, `core/metadata/snapshot.go:280` same. The client sees "failed" but the object is durable — the fix is best-effort publish with internal retry, not RPC error.
- **Orphan-prone two-phase without WAL.** `core/metadata/snapshot.go:367` backend `Prepare` between two `update` txs; `plugins/content/local/store.go:608` file before `core/metadata/content.go:427` ingest bucket. Crash leaves filesystem/database halves GC must asynchronously repair (`core/metadata/snapshot.go:862`, `core/metadata/content.go:844`).
- **10 s grace as de-facto idempotency window** (`solver/jobs.go:890`). Undocumented, unconfigured, RAM-only, lost on restart — any client retry after network blip either collides or forks a new expensive build with `b.Put` overwrite of prior `COMPLETE` (`solver/llbsolver/history/buildhistory.go:485`).
- **Shared-namespace O(n) check racing GC** (`core/metadata/content.go:758` `isSharedContent` scanning all namespaces `labels.LabelSharedNamespace=="true"` between check and `Writer` commit). Concurrent GC can delete the shared blob between `exists=true` shortcut and commit.

## Notable Absences

- **Canonical request fingerprinting.** No source hashes `Definition`/`FrontendAttrs`/`Image`/`Digest`/`run_config`/`Input` into a compare key on duplicate. Temporal explicitly has no `fingerprint`/`hash.*request` implementation (`grep` negative at `common/`, `service/history/api/`). The only diff path is dagster `register_managed_run._check_run_equality` (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:624`), scoped to Airflow ingestion.
- **Generic idempotency/TTL table.** No source has a cross-cutting `request_id → (fingerprint, response, expiry)` bucket independent of the resource table. Containerd has no `idempotency`/`requestID` bucket (`core/metadata/buckets.go:146` search negative), dagster has no `idempotency` table (`python_modules/dagster/dagster/_core/storage/runs/schema.py:1`), temporal's `RequestIds` is per-execution, not per-namespace global. Bounded dedup windows exist only as ingest `expireAt` (24 h) and CHASM caps.
- **Structured conflict error with diff on `Create`.** Only temporal could return `RunId` of existing execution; containerd `AlreadyExists` and dagster `DagsterRunAlreadyExists` carry no `existing` payload. `GrapheneRunConflict` (`python_modules/dagster-graphql/dagster_graphql/schema/errors.py:346`) is defined but never raised from `launch_execution.py:37` normal launch — the GraphQL `RunConflict` surface is dead code for external retries.
- **Retry-with-same-key harness.** No integration test simulates "commit then kill gRPC context before response, retry with same key". Containerd `core/metadata/containers_test.go` and `plugins/content/local/store_test.go:218` only test immediate duplicate; dagster `python_modules/dagster/dagster_tests/storage_tests/utils/run_storage.py:1084` only tests same-UUID duplicate without timeout; buildkit `solver/jobs_test.go` uses distinct `job0`/`job1`.
- **Client retry with preserved key.** BuildKit `client/solve.go:337` single `Solve` RPC with no retry loop; dagster `DagsterGraphQLClient` (`python_modules/dagster-graphql/dagster_graphql/client/client.py:290`) maps `RunConflict` to error without retry; containerd has no gRPC retry policy with `idempotency_level`. Temporal frontend auto-generates `RequestId` (`service/frontend/workflow_handler.go:6947`) which naive HTTP retries without preserving it defeats.
- **Revalidation at prepare/start boundary.** BuildKit has no prepare/start split; containerd snapshot `Commit` inside same `update` tx (`core/metadata/snapshot.go:520`) is the closest but task `Start` (`plugins/services/tasks/local.go:295`) does no revalidation of container spec; dagster's validation at `run_lifecycle.py:61` and sensor `_resolve_run_requests` (`python_modules/dagster/dagster/_daemon/sensor.py:1039`) is not re-run after durable tick write.

## Per-Source Notes

### buildkit — 2/10 — No Durable Submission

`Control.Solve` (`control/control.go:409`) is the narrow waist but acceptance is `solver/jobs.go:687` RAM insert. Notable that the *only* durable artifact (`solver/llbsolver/history/buildhistory.go:531` `Queue.Update`) is best-effort and not transactional with admission. The standout is what *does* exist: per-vertex content-addressed sharing (`solver/jobs.go:41` `actives` + `solver/jobs.go:995` flightcontrol) and lease-protected history blobs (`solver/llbsolver/history/buildhistory.go:418`), both excellent for cache reuse and observability but disconnected from submission idempotency. ### containerd — 5/10 — Resource-Identity Deduplication, Durable, No Replay

The most consistent `Bucket-existence-as-conflict` pattern across 8 locations (`core/metadata/containers.go:149`, `core/metadata/images.go:145`, `core/metadata/snapshot.go:344`, etc.). Strength is ordering: bbolt commit before publish/ack, `AlreadyExists` treated as benign by higher layers (`client/pull.go:309`). Weakness is conflation: same key ≠ same intent is invisible, task path bypasses bbolt, and hybrid filesystem+bbolt for content (`plugins/content/local/store.go:546` + `core/metadata/content.go:427`) plus two-phase snapshot (`core/metadata/snapshot.go:274`) create split-brain orphans requiring GC walk-and-diff (`core/metadata/snapshot.go:862`, `core/metadata/content.go:844`). Client retry safety depends on caller behavior (preserve `ID`/`ref`) not on daemon guarantee — `HandleResponse` (`core/metadata/containers.go:171`) could surface richer `409` details.

### dagster — 5/10 — DB-Row Intent with Daemon-Only At-Most-Once
