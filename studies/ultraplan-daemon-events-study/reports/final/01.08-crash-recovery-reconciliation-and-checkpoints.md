## Executive Summary

No source resumes arbitrary in-memory execution. All four recover only checkpointed work, but they checkpoint at radically different granularities and reconcile on radically different schedules.

- **buildkit (6/10)** has no job-level recovery at all: interrupted builds vanish, and recovery means the client re-issues `Solve` and skips completed vertices via content-addressed cache hits. Its strength is crash-window hardening of the cache itself (torn-commit repair, deleted-first prune, temp-lease sweep, corrupt-DB fallback).
- **containerd (7/10)** keeps execution in out-of-process shims and re-attaches on startup (`LoadExistingShims`), corrects CRI status checkpoints against live shim truth, and enforces restart policies via a 10s poll monitor. It is the only source with true process survival across daemon crash (when the host stays up).
- **dagster (7/10)** treats the event log as the checkpoint and recovery as launching a new worker for the same `run_id` that replays events (`KnownExecutionState`). Reconciliation is lazy polling by the run-monitoring daemon (start/cancel timeouts, dead-worker resume with bounded attempts). The OSS default launcher degrades to fail-only.
- **temporal (8/10)** is the most mature: event history + mutable-state snapshot + conditional write (`NextEventID`/`DBRecordVersion`) committed atomically, with timeout tasks planted at dispatch as crash detectors and fencing (RangeID, stamp/attempt, version) instead of a boot-time scan. Recovery is lazy per-workflow, at-least-once, and pushes exactly-once burden to activity authors.

The convergent lesson: durable intent + completion-derived resume + timeout-driven redelivery + sweep-or-fence orphan handling. The divergent lesson is *what* is durable (completed cache entries vs. shim bundles + meta.db vs. run rows + event log vs. history branch + snapshot) and *when* reconciliation runs (startup sweep vs. lazy poll vs. timer expiry).

SIGKILL during an external side effect is unsafe everywhere at the system layer. Every source delegates safety to sink idempotency (content addressing, digest-keyed pulls, idempotent activities/ops) or to the caller/orchestrator (client re-`Solve`, kubelet recreate, manual re-execution). None maintains a side-effect journal or exactly-once commit marker.

## Core Thesis

Crash recovery in long-lived executors is not process resume — it is **re-derivation from durable completion records plus timeout-driven redelivery of uncompleted intent, with orphans fenced or swept**.

Sources converge on four invariants: (1) only terminal/completed units survive (cache results, shim tasks with live processes, step success events, committed history batches); (2) interrupted work is re-executed from the last completion boundary, never continued mid-instruction (except explicit CRIU snapshots in containerd); (3) a timer or poll, not a restart scan, is the crash detector in the mature systems (temporal timer tasks, dagster monitoring iteration, containerd restart monitor); (4) orphans are discovered by list-and-diff sweeps or by fencing stale dispatches, not by transactional cleanup.

They diverge on durability scope and reconciliation eagerness because their products diverge: buildkit can afford rebuild-from-cache because builds are pure functions of content; containerd must reattach because containers are running OS processes; dagster must replay because steps are arbitrary user code with an observable event log; temporal must fence because many history owners contend over shared workflow state.

## Approach Models

**Model A — Rebuild-from-cache (buildkit).** The content-addressed result cache *is* the checkpoint. Solver jobs, actives, edges, and `STARTED` history entries live only in memory (`sources/buildkit/solver/jobs.go:43-44`, `sources/buildkit/solver/llbsolver/history/buildhistory.go:531-551`). Durable state is completed vertices in `cache.db` (`sources/buildkit/solver/bboltcachestorage/storage.go:144-172`) plus per-ref metadata (`snapshot.committed`/`cache.deleted`/`cache.equalMutable` in `sources/buildkit/cache/metadata.go:15-40`) and `COMPLETE`-only history records. On restart there is no reconciler for interrupted work; the client starts a new `Solve` and cache hits skip finished steps. Crash safety reduces to making each cache commit atomic-ish and healing torn commits on load (`sources/buildkit/cache/manager.go:440-506`).

**Model B — Reattach-to-survivor (containerd).** Execution outlives the daemon in per-container shims. Startup reconciliation has three layers: `LoadExistingShims` walks the state dir, re-dials via `bootstrap.json`, and reaps empty/leaked shims (`sources/containerd/core/runtime/v2/shim_load.go:39-64`, `sources/containerd/core/runtime/v2/shim_load.go:189-226`); the CRI plugin `recover()` rebuilds stores from `meta.db` + status JSON and corrects against live task status (`sources/containerd/internal/cri/server/restart.go:54-249`, `sources/containerd/internal/cri/server/restart.go:342-413`); the restart monitor polls desired-vs-actual every 10s and enforces `no/always/on-failure/unless-stopped` (`sources/containerd/plugins/restart/monitor.go:37-64`). Interrupted creates/execs/pulls are never continued — only re-attachable tasks resume; the rest map to `UNKNOWN`/255/`NOTREADY` for the orchestrator.

**Model C — Replay-from-event-log with new worker (dagster).** All recovery state is in instance DBs (run rows, plan snapshots, append-only event log, tick/backfill records). There is no boot sweep; the monitoring daemon each iteration collects `STARTING`/`STARTED`/`CANCELING`/`NOT_STARTED` runs and applies start/cancel timeouts plus dead-worker `resume_run` within a bounded budget (`python_modules/dagster/dagster/_daemon/monitoring/run_monitoring.py:174-223`, `python_modules/dagster/dagster/_daemon/monitoring/run_monitoring.py:113-171`). Same-`run_id` resume launches a fresh worker that replays events via `KnownExecutionState` (`python_modules/dagster/dagster/_core/execution/plan/state.py:169-380`); cross-run recovery creates a child run linked by `parent_run_id`/`root_run_id`. Ticks and backfills checkpoint iteration cursors (`MAX_TIME_TO_RESUME_TICK_SECONDS`, `submitting_run_requests`, `last_submitted_partition_name`).

**Model D — Event-sourced state + timeout resurrection + fencing (temporal).** The checkpoint is the history branch plus mutable-state snapshot (`ExecutionInfo`/`ExecutionState`/`NextEventID`/`DBRecordVersion` in `studies/ultraplan-daemon-events-study/sources/temporal/common/persistence/data_interfaces.go:348-402`), written atomically with new events and durable tasks via conditional `UpdateWorkflowExecution`. No startup scan exists; shard takeover via RangeID (`studies/ultraplan-daemon-events-study/sources/temporal/service/history/shard/context_impl.go:2030-2149`), lazy reload into LRU cache, timer-task expiry (`studies/ultraplan-daemon-events-study/sources/temporal/service/history/timer_queue_active_task_executor.go:440-478`), and stamp/attempt/version fencing (`studies/ultraplan-daemon-events-study/sources/temporal/service/history/api/recordworkflowtaskstarted/api.go:98-149`) jointly provide recovery. Speculative tasks and page buffers are explicitly ephemeral.

## Pattern Catalog

**1. Completed-unit cache as the only checkpoint.**
- Problem: avoid journaling running work while still surviving crashes cheaply.
- Sources: buildkit (cache.db results + metadata), containerd (content chunks reusable by digest), dagster (step SUCCESS events skip re-execution), temporal (committed history batches replay).
- Why it works: completion is already content-addressed or event-recorded, so re-derivation is idempotent and needs no WAL.
- Copy when: units are deterministic/pure or completion is cheap to test (digests, step events, history IDs).
- Overkill/risky when: single units are long (whole-vertex redo in buildkit; long RUN pays full cost) or side effects are non-idempotent.
- Evidence: `sources/buildkit/solver/bboltcachestorage/storage.go:144-172`; `sources/buildkit/cache/manager.go:440-506`; `python_modules/dagster/dagster/_core/execution/plan/state.py:169-380`; `studies/ultraplan-daemon-events-study/sources/temporal/common/persistence/execution_manager.go:147-235`.

**2. Plant-your-own-resurrection-timer at dispatch.**
- Problem: detect dead owners without a global watchdog.
- Sources: temporal (durable `WorkflowTaskTimeoutTask` + activity retry timers generated in `task_generator.go:441-544`, fired in `timer_queue_active_task_executor.go:440-478`); dagster (monitoring timeouts `START_TIMEOUT`/cancel timeout in `run_monitoring.py:28-105`); containerd (10s restart-monitor poll in `plugins/restart/monitor.go:90-129`).
- Why it works: every dispatch carries its own crash detector; loss of the owner is indistinguishable from slowness, and both trigger the same redelivery path.
- Copy when: redelivery is idempotent or fenced; timers are durable (temporal) or polling is acceptable (dagster default 120s, containerd 10s).
- Overkill/risky when: sub-second detection needed (poll latency) or timer writes dominate (temporal mitigates with in-memory speculative timeouts — see pattern 6).
- Evidence: `studies/ultraplan-daemon-events-study/sources/temporal/service/history/workflow/task_generator.go:441-463`; `python_modules/dagster/dagster/_daemon/monitoring/run_monitoring.py:28-105`; `sources/containerd/plugins/restart/monitor.go:37-64`.

**3. Fence stale dispatches instead of scanning for orphans.**
- Problem: prevent a revived old owner from corrupting post-crash state without a boot-time global scan.
- Sources: temporal (RangeID/`ShardOwnershipLostError`, stamp/attempt/schedID checks, `TaskAlreadyStarted`/`ObsoleteMatchingTask` drops in `matching_engine.go:820-864`); containerd (fail-fast `AnonReconnectDialer` vs retry `AnonDialer`, `shouldCleanupShim` takeover rule); dagster (status-reload-before-act in `monitor_started_run`, dequeue recheck `still QUEUED`).
- Why it works: concurrent/old writers fail fast at the linearization point; no coordination with the dead owner needed.
- Copy when: multiple writers can contend (shard moves, slow workers, daemon restarts during `NewTask+Start`).
- Overkill/risky when: single-owner embedded use — fencing keys add schema/complexity for little gain.
- Evidence: `studies/ultraplan-daemon-events-study/sources/temporal/service/history/shard/context_impl.go:2030-2149`; `studies/ultraplan-daemon-events-study/sources/temporal/service/history/api/recordworkflowtaskstarted/api.go:69-79`; `sources/containerd/core/runtime/v2/shim.go:336-338`; `python_modules/dagster/dagster/_daemon/run_coordinator/queued_run_coordinator_daemon.py:363-491`.

**4. Startup sweep: list everything, delete what looks dead.**
- Problem: reclaim resources whose owner died without a durable death record.
- Sources: buildkit (`cacheManager.init` purge in `cache/manager.go:326-341`, temp-lease sweep in `worker/base/worker.go:222-228`, `clearOrphans` in `buildhistory.go:200-239`); containerd (empty-bundle delete, undialable-shim delete, `cleanupWorkDirs` in `shim_load.go:96-125` + `shim_load.go:264-296`, `cleanupOrphanedIDDirs` in `restart.go:449-476`).
- Why it works: leases, bundle dirs, and ID dirs are enumerable; liveness (dial, PIDs, container list) is checkable at boot.
- Copy when: resource set is enumerable and liveness probe is cheap (socket dial, PID check, lease membership).
- Overkill/risky when: enumeration is huge (global scan delays startup — temporal and dagster deliberately avoid it) or liveness is ambiguous (slow-starting shim reaped as leaked; `init` purge logged at debug only).
- Evidence: `sources/buildkit/cache/manager.go:326-341`; `sources/buildkit/worker/base/worker.go:222-228`; `sources/containerd/core/runtime/v2/shim_load.go:264-296`; `sources/containerd/internal/cri/server/restart.go:449-476`.

**5. Torn-commit repair via ordered marks (deleted-first, commit-then-clear).**
- Problem: survive SIGKILL between a data commit and its metadata commit without a WAL.
- Sources: buildkit (`finalize` lease → snapshot commit → clear `equalMutable` → commit metadata in `cache/refs.go:1498-1544`, healed by `getRecord` in `cache/manager.go:440-506`; prune marks `deleted` before removing data in `cache/manager.go:1216-1233`); containerd/temporal analogues are atomic file writes (`continuity.AtomicWriteFile` in `internal/cri/store/container/status.go:164-195`) and conditional DB writes (`DBRecordVersion`/`NextEventID`).
- Why it works: the reader can distinguish half-finished states from the mark combination and finish or roll back deterministically; covered by `TestLoadHalfFinalizedRef` (`sources/buildkit/cache/manager_test.go:2309-2389`).
- Copy when: two-phase commit spans two stores (snapshotter + metadata) and a full WAL is too heavy.
- Overkill/risky when: states multiply — ad-hoc per-record repair becomes its own bug surface; prefer atomic write or conditional-write transaction once available.
- Evidence: `sources/buildkit/cache/refs.go:1498-1544`; `sources/buildkit/cache/manager.go:440-506`; `sources/buildkit/cache/manager_test.go:2309-2389`.

**6. Explicit ephemeral tier: mark what must NOT survive.**
- Problem: avoid persisting hot-path state that is cheap to re-derive but expensive to write.
- Sources: temporal (speculative WT + `CategoryMemoryTimer` queue in `speculative_workflow_task_timeout_queue.go:15-99`, transient WTs, page buffers dropped by `reconcileTaskCompletionBuffer` in `workflow/context.go:219-231`); dagster (`Update` memory-only vs `UpdateSync` durable split analogous in containerd CRI status `store/container/status.go:270-299`; dagster in-memory `ActiveExecution`/gRPC handles); buildkit (`STARTED` in memory-only `active` map); containerd (transfer progress in memory in `core/transfer/local/progress.go:83-166`).
- Why it works: crash semantics stay simple ("loss is by design, re-created on next dispatch") and write amplification drops.
- Copy when: re-derivation path already exists (next workflow task, next monitoring poll, next `Solve`).
- Overkill/risky when: operators mistake loss for a bug — must be documented and observable (temporal documents it; buildkit's silent `active` loss is the negative example).
- Evidence: `studies/ultraplan-daemon-events-study/sources/temporal/service/history/workflow/mutable_state_impl.go:7456-7485`; `sources/containerd/internal/cri/store/container/status.go:270-299`; `sources/buildkit/solver/llbsolver/history/buildhistory.go:531-551`.

**7. Synthesize a terminal state for the unknown.**
- Problem: unblock orchestrators waiting on a dead owner without claiming success.
- Sources: containerd (`UNKNOWN`/exit 255 sentinel in `internal/cri/server/helpers.go:249-266`, dead-shim `TaskExit+TaskDelete` synthesis in `core/runtime/v2/shim.go:144-187`); dagster (`_force_mark_as_failed` with explicit leak caveat in `run_monitoring.py:226-289`); temporal (`failWorkflowTask` + schedule-new-task in `workflow_task_state_machine.go:1050-1104`, `Unknown` mapping in CRI-equivalent paths).
- Why it works: downstream (kubelet, UI, matching) converges on a terminal/retriable state without special crash handling.
- Copy when: an orchestrator or queue consumes your state and must make progress after owner death.
- Overkill/risky when: synthesis masks data loss (containerd corrupt-status fallback, buildkit `.bak`-and-reset, dagster force-fail leak) — always log loudly and count with metrics.
- Evidence: `sources/containerd/core/runtime/v2/shim.go:144-187`; `sources/containerd/internal/cri/server/helpers.go:249-266`; `python_modules/dagster/dagster/_daemon/monitoring/run_monitoring.py:226-289`.

**8. Bound every retry with a durable budget.**
- Problem: prevent crash loops from retrying forever while surviving daemon restarts.
- Sources: dagster (resume attempts counted from event log `RESUME_RUN_LOG_MESSAGE` in `run_monitoring.py:25-110`, `max_resume_run_attempts` default 0, tick horizon 24h, failure resubmission cap 1); temporal (`RetryActivity` policy/backoff/exhaustion in `mutable_state_impl.go:6880-6959`); containerd (`restart.count` label + `max-retries` in `core/runtime/restart/restart.go:117-143`).
- Why it works: budget lives in durable state (event log, labels, mutable state), so a crash does not reset it.
- Copy when: automatic retry exists at all.
- Overkill/risky when: budget storage is itself lossy (dagster event compaction would corrupt counts; containerd `NoSync` can lose label bumps).
- Evidence: `python_modules/dagster/dagster/_daemon/monitoring/run_monitoring.py:25-110`; `studies/ultraplan-daemon-events-study/sources/temporal/service/history/workflow/mutable_state_impl.go:6880-6959`; `sources/containerd/plugins/restart/change.go:39-103`.

## Key Differences

- **Checkpoint granularity.** buildkit: whole completed vertex (coarsest). containerd: container/process (OS-level) plus explicit CRIU whole-memory snapshots only on demand. dagster: step (start/success/failure/output events). temporal: single history event batch + state transition (finest, transactional).
- **Reconciliation timing.** buildkit and containerd-shim do a startup sweep (eager, boot-time). dagster, containerd-restart-monitor, and temporal are lazy: next monitoring poll (120s/10s) or next timer fire / shard acquire / task access. Consequence: buildkit/containerd startup pays enumeration cost but converges before serving; temporal/dagster restart fast but leave stale `STARTED`/`RUNNING` rows until timers fire.
- **Resume unit.** buildkit: nothing resumes — new `Solve` skips hits. containerd: live shim re-attached (same PID); dead shim → new task via restart policy or kubelet recreate. dagster: same `run_id` with new worker (replay) or child run (re-execution). temporal: same run with next workflow/activity task redelivered from history (replay + new attempt number/stamp).
- **Automatic new attempt.** buildkit: never (always manual). containerd: only under restart policy (`always`/`on-failure`/`unless-stopped`) or via orchestrator reacting to synthetic exits; CRI itself converges to `NOTREADY`/`UNKNOWN` and waits. dagster: dead-worker `resume_run` while under budget, auto-retry daemon for terminal failures matching policy, queue re-enqueue for unreachable code, tick resubmission. temporal: timeout/failure/heartbeat/failover paths auto-schedule the next task while retry policy says `IN_PROGRESS`.
- **Orphan discovery.** buildkit: four heuristic sweeps (init walk, lazy repair, temp-lease delete, history clearOrphans) — no running-container handling. containerd: four complementary sweeps across shim/CRI/storage layers plus synthetic events. dagster: polling health checks (`check_run_worker_health`/`check_step_health`) gated on launcher capability. temporal: no sweeps — distributed fencing (shard/task/version) plus `BestEffortDeleteTasks` and rescheduler park-and-resubmit.
- **Durability vs throughput knob.** buildkit `NoSync: true` on `cache.db`; containerd `no_sync` option (`NoSync+NoGrowSync`) with explicit crash-loss warning; dagster defers to SQL backend (SQLite vs Postgres differences unexamined); temporal relies on remote DB conditional writes (no local fsync story in-tree).
- **Corruption philosophy.** buildkit: quarantine to `.bak` and start empty (availability over durability). containerd: `NoFreelistSync` mitigation plus fail-fast budget timeouts (skip wedged shim, keep serving). dagster: force-fail with leak warning (convergence over hygiene). temporal: conditional-write failure + ownership loss (consistency over availability — old owner stops).
- **Why divergence is valid, not just quality.** buildkit's rebuild-only model fits pure content-addressed builds where recompute is safe; a journal would add little. containerd must reattach because killing and recreating containers on every daemon restart would violate runtime semantics. dagster's fail-only OSS default fits library-vs-application constraints (health/resume live in K8s/Docker launchers outside core). temporal's fencing complexity fits multi-owner server topology where boot scans would not scale.

## Tradeoffs

- **Rebuild-from-cache (buildkit) vs replay-from-log (dagster/temporal).** Cache wins on simplicity (no WAL, no fencing, one crash test covers the window); cost is whole-unit redo and no interrupted-state visibility. Log/event-sourcing wins on fine-grained resume (step, event batch) and auditability; cost is log scanning, retention interplay (dagster compaction vs budget counting; temporal history growth vs transient-task dedup), and at-least-once redelivery complexity.
- **Startup sweep vs lazy poll/timer.** Sweep (buildkit init, containerd shim load) converges before serving but delays boot linearly with resource count and risks misclassifying slow starters as dead (5s load budget, 10s dial). Lazy (temporal, dagster) restarts fast and scales, but detection latency equals timer/poll interval (seconds to minutes) and stale rows linger — operators need separate "time since crash to first successful task" signals that none of the sources fully provide.
- **Out-of-process survival (containerd shims) vs in-process loss (everyone else).** Shims let running containers survive daemon SIGKILL — unique strength; cost is bundle/state-dir lifecycle, socket/dial management, and a whole reattach protocol with timeouts. Others accept process death and re-execute, which is simpler but unacceptable for long-running containers.
- **Poll restart enforcement (containerd 10s, dagster 120s) vs timer-per-dispatch (temporal).** Poll is crash-immune (no subscription to lose) and simple; cost is latency and races (deleted-task/`on-failure` race; status-moved-after-reload checks). Per-dispatch durable timers give precise per-operation timeouts; cost is a timer write per dispatch (temporal pays it, mitigated by memory-tier speculative tasks).
- **Synthetic terminal states.** Benefit: downstream converges without crash-aware logic. Cost: true outcome lost (exit 255, `Unknown`, force-failed, `WorkflowTaskTimedOut` all conflate crash/slowness/side-effect-unknown). Every source chooses convergence and documents (or should document) that retry safety is the caller's job.
- **Ephemeral tiers.** Benefit: order-of-magnitude write reduction on hot paths. Cost: guaranteed loss on crash that must be re-derivable and clearly documented — temporal does this best (explicit memory queue + materialization path); buildkit's silent `active`-map loss is the cautionary tale.

## Decision Guide

- **If operations are pure functions of content (builds, artifact assembly):** copy buildkit. Checkpoint completed units by digest, heal torn commits on load with ordered marks, sweep temp leases at startup, and require client re-submission. Do not build a job journal until whole-unit redo cost hurts.
- **If you own running OS processes that must survive daemon restart:** copy containerd. Move execution out-of-process, persist dial identity (`bootstrap.json` equivalent), reattach with fail-fast dial + bounded budgets, synthesize exits for dead shims, and correct desired-state checkpoints against live truth (task wins). Accept that pulls/execs/creates still retry by digest.
- **If operations are arbitrary user code with an observable event log:** copy dagster. Derive resume state from immutable step events (`KnownExecutionState` pattern: started-but-no-terminal = interrupted), gate resume on launcher health-check capability, count budgets durably, and make every daemon write idempotent (recheck-before-act, existing-child-run check). Default to fail-with-timeout unless a resume-capable launcher is configured.
- **If many owners contend over shared durable state with strict ordering:** copy temporal. Commit history + snapshot + tasks atomically with optimistic-concurrency keys, plant a durable timeout at every dispatch, and fence (RangeID/stamp/attempt/version) rather than scanning. Accept at-least-once redelivery and push idempotency keys to operation authors.
- **Choosing eagerness:** need convergence before serving (bounded resource set, operators list orphans at boot)? Startup sweep. Need fast restart at scale (thousands of workflows/runs)? Lazy poll + timers, plus metrics for time-to-first-successful-task after shard acquire/daemon boot.
- **SIGKILL-during-side-effect rule (all models):** never claim the system decides safety. Gate side effects behind durably recorded intents (activity/step event, digest-keyed operation), make sinks idempotent, and on crash map to unknown/timeout + bounded retry. If the sink is non-idempotent, require human/orchestrator judgment — do not auto-retry.

## Practical Tips

- Persist intent before dispatch and completion after effect, never the reverse. Temporal's `UpdateWorkflowExecution` bundle, dagster's plan snapshot + step events, containerd's `UpdateSync` checkpoint, and buildkit's commit-then-clear ordering are four syntaxes for the same rule.
- Give every dispatch its own timeout at dispatch time. A global sweeper is not enough; per-operation ScheduleToStart/StartToClose (temporal), start/cancel timeouts (dagster), and restart-policy reconciliation (containerd) each caught crashes the others would miss.
- Separate memory-only from durable updates in the API (`Update` vs `UpdateSync`; durable vs speculative WT; `active` map vs `_records` bucket). Tests should assert non-sync updates do not persist (containerd `status_test.go:152-205` is the template).
- Count retry budgets in durable state, not in memory. Event-log markers (dagster), labels (containerd `restart.count`), or state-machine fields (temporal attempt/stamp) survive the crash that the budget is meant to bound.
- Recheck status immediately before acting after any load-then-act window (dagster `monitor_started_run` reload; temporal stamp checks; containerd `shouldCleanupShim` PID probe). The crash window between "read checkpoint" and "start new attempt" is where duplicates are born.
- Make orphan sweeps per-item isolated with budgets (5s load, 10s dial, per-container 10s timeout + errgroup). One wedged item must log-and-skip, never block startup (containerd) or serving (buildkit fire-and-forget is the negative extreme — surface errors with counts instead).
- Log crash-attributed fallbacks loudly with counts (`.bak` quarantine, `clearOrphans` deletes, `Unknown` mappings, force-fails). buildkit's debug-only purge log and containerd's log-only recovery signals are both reaudit targets — add metrics for re-attached vs reaped, unknown/notready counts, orphan dirs removed.
- Test the crash window, not just the steady state: half-finalized ref reopen (buildkit `TestLoadHalfFinalizedRef`), resume-attempt counting 1..3-then-fail with mock launchers (dagster `test_monitoring_daemon.py`), stamp-mismatch drops and activity-retry suites (temporal), restart-policy table tests (containerd `restart_test.go`). Add a kill-9-daemon-mid-operation restart assertion wherever it is missing (all four reports flag this gap at some layer).

## Anti-Patterns / Caution Signs

- **Memory-only status masquerading as durability.** `STARTED` in an `active` map (buildkit), transfer progress in memory (containerd), `ActiveExecution`/gRPC handles (dagster), speculative/page-buffer state (temporal) — all vanish. Caution sign: post-restart "interrupted" view is empty or `NOT_STARTED` rows reappear with no lineage. Fix: persist `STARTED` or explicitly document loss + re-derivation.
- **Silent amputation on corruption.** `.bak`-and-empty (buildkit), `clearOrphans` whole-record delete on missing blobs, corrupt-status fallback to unknown (containerd), force-fail with leak warning (dagster). Caution sign: post-crash evidence disappears from default logs. Fix: warn-level logs with counts + quarantined artifact paths + metrics.
- **Fire-and-forget startup cleanup.** buildkit `clearOrphans`/GC goroutine swallowing errors and racing early reads. Caution sign: flaky early reads after restart, unreproducible missing records. Fix: synchronous-before-serve or error-surfaced with metrics.
- **`NoSync` without a documented contract.** buildkit `cache.db`, containerd `no_sync` option. Caution sign: recently committed results vanish after host crash with no detection (safe recompute, wasteful and confusing). Fix: document the window; consider durable writes for low-volume high-value stores (buildkit `history.db`).
- **Auto-retry without fencing or budget.** `NewTask+Start` double-bump on successive ticks, daemon-die-between-create-and-submit duplicates, activity double-execution after side effect. Caution sign: duplicate lineage, inflated attempt counts, non-idempotent effects firing twice. Fix: idempotency keys/request IDs + recheck-before-act + durable budget.
- **Strict preconditions assumed, never enforced.** containerd CRI "do not touch while down", dagster monitoring-disabled default, temporal sticky-affinity best-effort. Caution sign: upgrade/operator workflows violate the assumption and containers are skipped/deleted. Fix: fail loudly at startup when preconditions are violated; surface disabled-recovery defaults as warnings.
- **Poll latency mistaken for hang.** 120s dagster interval + 180s start/cancel timeouts, 10s containerd interval. Caution sign: stale `STARTED`/`RUNNING` rows linger minutes after a crash and operators force-kill. Fix: startup verification pass on boot + documented detection SLO.

## Notable Absences

- **No source guarantees exactly-once external side effects.** All four explicitly or implicitly delegate to sink idempotency or orchestrator judgment. No write-ahead side-effect journal, no "was the HTTP call sent?" probe, no idempotency-key framework at the executor layer (temporal request-ID/stamp dedup is dispatch-level, not effect-level).
- **No shared crash/restart integration test pattern.** Each source has unit/table tests for windows (half-finalized ref, mock-launcher resume counts, stamp drops, policy tables) but per-source reports flag missing kill-9-daemon + restart + assert-reattach/no-leak end-to-end tests at some layer (buildkit beyond one unit test; containerd daemon-level; dagster real-worker SIGKILL; temporal host-reboot runbook).
- **No central recovery planner in the two most mature systems.** Temporal recovery is distributed across shard acquire, queue reload, timer executors, matching drops, and rescheduler; dagster recovery is spread across monitoring/auto-retry/queue/sensor/backfill daemons. Operators get logs and counters, not one observable reconciliation pass.
- **No cross-backend durability analysis for dagster** (SQLite vs Postgres/MySQL checkpoint semantics) and no transfer/pull resume story for containerd (progress in memory; digest reuse only).
- **No BuildKit-side orphan-container reaper** after daemon SIGKILL (delegated to containerd/runc, unverified) and no client-side (buildctl) resume semantics traced.
- **No recovery-health metrics in any source** (time from acquire/boot to first successful task, re-attached vs reaped counts, unknown/notready gauges, orphan-removal counters) — consistently recommended as future work.

## Per-Source Notes

- **buildkit (6/10):** Completed-work durability only; interrupted builds vanish silently with no reconciler and always-manual retry. Copy the torn-commit repair idiom, deleted-first prune, single-temp-lease-spanning-export, and temp-lease sweep. Do not copy memory-only `active` history or debug-only purge logging.
- **containerd (7/10):** Three-layer reconciliation (shim reattach, CRI correction, restart-policy poll) with bounded budgets and synthetic terminal events. Copy the reconnect/fail-fast dialer split, label-as-desired-state, versioned status with atomic writes, and per-item isolation. Watch the `on-failure`/deleted-task race, no-touch-while-down contract, and slow-shim-as-leaked risk.
- **dagster (7/10):** Lazy polling reconciler over DB truth with event-log-derived resume and idempotent daemon writes. Copy interrupted-step inference, dangling-tick promotion to `SKIPPED`, and budget-as-events. Do not ship the fail-only OSS default without documenting it; add a boot verification pass.
- **temporal (8/10):** Atomic history+snapshot+task commit with timeout-driven redelivery and multi-layer fencing; speculative/ephemeral tiers explicitly non-durable. Copy conditional-write linearization, timer-as-watchdog, transient-task dedup, and rescheduler park-and-resubmit. Budget for lazy-detection latency and activity-author idempotency guidance.
