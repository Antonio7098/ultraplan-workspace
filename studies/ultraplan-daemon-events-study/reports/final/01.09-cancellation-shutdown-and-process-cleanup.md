## Executive Summary

Cancellation splits this cohort into two families. BuildKit and containerd treat cancellation as a **volatile signal**: a gRPC `ctx` cancellation or a one-shot `Kill` RPC with no persisted intent. If no worker/shim is attached, the intent is lost. Dagster and Temporal treat cancellation as a **durable control request**: a persisted `CANCELING` / `CancelRequested` state written before any kill is attempted, which survives disconnect and is later acknowledged cooperatively by the worker.

No source implements preemptive, guaranteed process-tree termination. The strongest kill path is BuildKit's SIGKILL-only cancel; the weakest is Dagster's single cooperative SIGINT with no escalation. Containerd pushes escalation to the highest layer (CRI `StopContainer` TERM→KILL only), and Temporal has no OS kill at all — correct for its goroutine model, but a gap against this dimension's expectations.

What converges: all four detach cleanup from the canceled parent context (`context.WithoutCancel` / detached contexts + fixed timeouts) so finalization is not starved by the cancel it serves. All four prefer drain-or-detach on daemon shutdown over cancel-in-flight; none cancels active work on SIGTERM by default. All four arbitrate cancel-vs-complete races explicitly rather than with a central fencing token.

Prompt-scenario answer (cancel races completion; child ignores first signal): in every source the terminal outcome is **whichever side commits first**. Late cancel to a finished unit is a benign noop / not-cached / `NotFound` / `is_finished→False`. Cleanup for an ignoring child diverges: BuildKit still kills it (SIGKILL is unblockable) but may then wait unboundedly for reaping; containerd raw API leaves it running until a second explicit SIGKILL (`All=true`), only CRI auto-escalates; Dagster sends exactly one SIGINT and then waits until the 180s monitoring timeout force-marks `CANCELED` with a "may not have been fully cleaned up" warning; Temporal delivers one transfer-queue cancel / one worker-command and otherwise relies on heartbeat polling, dropping the cancel if the child already closed.

## Core Thesis

**Durability of cancel intent is the load-bearing design choice; everything else (kill strength, shutdown policy, race arbitration) follows from it.**

- Volatile-cancel systems (buildkit, containerd) are simple and fast — no cancel journal to reconcile — but cannot "cancel by ref" after disconnect, cannot replay intent after shim/daemon restart, and force orchestrators to hold the caller's context open or kill the whole daemon.
- Durable-intent systems (dagster, temporal) survive disconnect, queuing, pause, and worker absence — `QueuedRunCoordinator.cancel_run` handles `QUEUED` with no worker; `requestcancelworkflow.Invoke` schedules a workflow task for a future poller — but pay a write + poll round-trip per cancel and must solve cooperative acknowledgement (SIGINT polling, SDK cancel command), which introduces the "CANCELING lingers while compute ignores it" failure mode and requires a daemon timeout backstop.
- Shutdown policy is orthogonal but correlated: volatile systems still drain (buildkit) or detach (containerd) rather than interrupt, because interrupting volatile work has no durable record to reconcile. Durable systems also drain, because cancelling is safe to defer — the persisted `CANCELING` intent will be honored whenever the worker next polls.
- The universal invariant across all maturity levels is **cleanup must outlive cancellation**: detached contexts with explicit budgets. The universal weakness is **OS process-tree containment**: only isolated paths (BuildKit git fetcher, containerd verifier, containerd `runc kill --all`, Dagster/Temporal container launchers) contain descendants; the local-process hot paths do not.

## Approach Models

Two intent families × two shutdown postures cover all four sources.

**Family A — Volatile signal (buildkit, containerd).** No cancel object, journal, tombstone, or poll loop. Cancel is `ctx.Done()` / `Receiver.Cancel()` (buildkit: `studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler.go:229-235`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/internal/pipe/pipe.go:182-187`) or a stateless `Kill(signal, All)` RPC (containerd: `sources/containerd/plugins/services/tasks/local.go:473`, `sources/containerd/cmd/containerd-shim-runc-v2/task/service.go:493`). Cancel with no attached `Solve` ctx / live shim is a noop. Strength: small API, no reconciliation. Cost: orchestrator must hold the request open.

**Family B — Durable intent + cooperative ack (dagster, temporal).** Intent is persisted before any runtime effect: Dagster `report_run_canceling` → `PIPELINE_CANCELING` event → `CANCELING` status (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:374-390`); Temporal `AddWorkflowExecutionCancelRequestedEvent` + `CancelRequested=true` (`service/history/workflow/mutable_state_impl.go:5091-5118`, `service/history/workflow/mutable_state_impl.go:5120-5125`). Delivery is decoupled: Dagster pushes a `multiprocessing.Event` over `CancelExecution` RPC or polls the DB every 10s; Temporal schedules a new workflow task plus heartbeat-pollable `ai.CancelRequested` plus eager `WorkerCommand_CancelActivity`. The worker acknowledges with `job_canceled` / `COMMAND_TYPE_CANCEL_WORKFLOW_EXECUTION`. Strength: survives disconnect, queue, pause, crash. Cost: extra write + task churn, plus lingering `CANCELING`/`CancelRequested` when workers stall.

**Shutdown posture 1 — Drain (buildkit, dagster, temporal).** First SIGTERM cancels a root context and calls `GracefulStop()` / `server.stop(grace)` while in-flight work continues: BuildKit `server.GracefulStop()` with history-finalizer drain (`studies/ultraplan-daemon-events-study/sources/buildkit/cmd/buildkitd/main.go:452-483`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:139-147`); Dagster `ShutdownServer → shutdown_once_executions_finish → grace → stop` (`python_modules/dagster/dagster/_grpc/server.py:1266-1287`, `python_modules/dagster/dagster/_grpc/server.py:1477-1489`); Temporal reverse-`initOrder` drain-then-`GracefulStop` bounded by `serviceStopTimeout=5m` (`temporal/server_impl.go:47-53`, `temporal/server_impl.go:109-146`). Escalation is operator-driven (BuildKit 1-2-3 signal ladder; Temporal 2s `AfterFunc(→Stop)` fallback) or absent (Dagster detached code servers by default).

**Shutdown posture 2 — Detach (containerd).** SIGTERM stops plugins LIFO, not workloads (`sources/containerd/cmd/containerd/command/main_unix.go:30`, `sources/containerd/cmd/containerd/server/server.go:282`); shims are separate `Setpgid` processes that survive (`sources/containerd/cmd/containerd-shim-runc-v2/manager/manager_linux.go:110`) and are reloaded on restart. Strength: fast non-disruptive daemon upgrades. Cost: no quiescence guarantee — orchestrators must stop containers first.

## Pattern Catalog

**1. Cancel-before-RPC (durable intent first).**
What problem: kill RPC can fail or arrive with no worker attached; intent must survive.
Sources: dagster (`python_modules/dagster/dagster/_core/launcher/default_run_launcher.py:153-184`, `python_modules/dagster/dagster/_core/run_coordinator/queued_run_coordinator.py:327-341`, K8s `python_modules/libraries/dagster-k8s/dagster_k8s/launcher.py:352-378`), temporal (`service/history/api/requestcancelworkflow/api.go:14-96`).
Why it works: the persisted `CANCELING`/`CancelRequested` write is the source of truth; the runtime signal is a best-effort notification. Queued/paused runs cancel with no worker at all.
Copy when: any orchestrator with queues, re-attach, or cross-restart cancel requirements.
Overkill/risky when: low-level executor with no store (BuildKit solver, containerd shim) — adds a journal with nothing to anchor it to.
Evidence: Dagster `QUEUED→report_run_canceling→report_run_canceled` synchronously; Temporal cancel-while-paused writes `CANCEL_REQUESTED` with no task dispatched until `Unpause` (`tests/pause_workflow_execution_test.go:1959-2030`).

**2. Detached cleanup contexts (`WithoutCancel` + fixed timeout).**
Problem: parent cancel starves the finalization that the cancel itself requires (leases, mounts, history, delete RPCs).
Sources: all four. BuildKit pervasive `WithoutCancel` for releases/history/exporter (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/solver.go:290-292`, `studies/ultraplan-daemon-events-study/sources/buildkit/cache/manager.go:165-180`); containerd generic `cleanup.Do` 10s (`sources/containerd/internal/cleanup/context.go:27`) + shim 5s/3s (`sources/containerd/core/runtime/v2/shim.go:62-77`) + 30s shutdown fan-out (`sources/containerd/pkg/shutdown/shutdown.go:51`); Temporal `newDetachedContext: CopyContextValues + WithTimeout` (`service/history/shard/context_impl.go:2408-2433`).
Why it works: firewall between request lifetime and resource lifetime; caller always returns.
Copy always. Pair every detached context with an explicit timeout — BuildKit's unbounded post-SIGKILL `p.ended` wait and containerd's untimed `Server.Stop` plugin loop are the two violations that prove the rule.
Risk: too-short budgets leak-by-log (containerd 3s shim shutdown explicitly logs "shim might be leaked" at `sources/containerd/core/runtime/v2/shim.go:582`).

**3. Kill escalation ladder (TERM→KILL with deadline).**
Problem: cooperative targets ignore the first signal.
Sources: containerd CRI `stopContainer` (signal once CAS-guarded, wait `timeout`, SIGKILL, bounded wait — `sources/containerd/internal/cri/server/container_stop.go:165`); BuildKit git fetcher (pgid SIGTERM, escalate SIGKILL after 10s — `studies/ultraplan-daemon-events-study/sources/buildkit/source/git/source_linux.go:37-63`); BuildKit daemon 1-2-3 signal ladder (`studies/ultraplan-daemon-events-study/sources/buildkit/util/appcontext/appcontext.go:33-65`); Temporal `GracefulStop → AfterFunc(2s→Stop)` (`service/history/service.go:117-176`).
Why it works: bounds graceful behavior, then guarantees termination.
Copy when: any host/container process supervision. Note the anti-pattern distribution: BuildKit container cancel is SIGKILL-only (no graceful hook, but un-ignorable); Dagster hot path is SIGINT-only with no escalation (`python_modules/libraries/dagster-shared/dagster_shared/ipc.py:64-71`) and an unused `interrupt_then_kill_ipc_subprocess` helper (`python_modules/libraries/dagster-shared/dagster_shared/ipc.py:42-53`); containerd raw API is one-signal-per-RPC with escalation only in CRI.
Overkill when: kernel-delivered SIGKILL to a container init is already unblockable — a second signal adds nothing except reaping pressure.

**4. Don't-cache-the-cancel / reload-before-decide / first-writer-wins arbitration.**
Problem: cancel landing exactly as work completes must not poison shared state or produce duplicate terminal events.
Sources: BuildKit `complete=false + releaseError` on canceled shared ops (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:1248-1260`) + `finishIncoming` synthesis (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/edge.go:178-186`); Dagster `finally`-reloads-run (`python_modules/dagster/dagster/_core/execution/api.py:766-799`) + `is_finished` entry gates; Temporal `IsWorkflowExecutionRunning`/`IsCancelRequested`/`checkMutability` triad + same-WFT first-wins (`service/history/api/respondworkflowtaskcompleted/workflow_task_completed_handler.go:855-979`); containerd `checkKillError` ESRCH→`NotFound` (`sources/containerd/cmd/containerd-shim-runc-v2/process/utils.go:115`) + documented duplicate `TaskExit` tolerance (`sources/containerd/core/runtime/v2/shim.go:596`).
Why it works: losers resolve to benign noops instead of errors; winners never store cancel as a cacheable result.
Copy when: any shared/fan-out execution graph or at-least-once event delivery. Containerd's "tolerate duplicates, consumer dedupes" is the weakest variant — acceptable for container exits, insufficient for billed workflow runs.

**5. Dual-channel propagation (push event + poll flag).**
Problem: no persistent connection to the worker at cancel time.
Sources: Temporal heartbeat `CancelRequested` + eager `WorkerCommand_CancelActivity` (`service/history/api/recordactivitytaskheartbeat/api.go:77-101`, `service/history/api/respondworkflowtaskcompleted/workflow_task_completed_handler.go:680-779`); Dagster in-memory `multiprocessing.Event` push + 10s DB poll thread (`python_modules/dagster/dagster/_grpc/server.py:1289-1336`, `python_modules/dagster/dagster/_core/execution/run_cancellation_thread.py:9-44`).
Why it works: fast path when attached, poll fallback when detached.
Copy when: cancellation must cross process/host boundaries without holding a stream open. Cost is poll latency vs store load (Dagster 10s run poll, 120s monitor poll).

**6. Drain-then-force shutdown with fallback timer.**
Problem: graceful drain can stall on wedged work.
Sources: Temporal frontend/history/matching drain-sleep + `GracefulStop` + `AfterFunc(→Stop)` (`service/frontend/service.go:548-595`, `service/history/service.go:117-176`); BuildKit `GracefulStop` + history finalizer drain (no timer — the gap); Dagster `server.stop(grace)` + `wait(grace+5)` (`python_modules/dagster/dagster/_grpc/server.py:1477-1489`); containerd 30s `errgroup` shutdown fan-out (`sources/containerd/pkg/shutdown/shutdown.go:51`).
Copy the fallback timer always. BuildKit (no build-level deadline ties shutdown to a bound), containerd `Server.Stop` (no timeout at `sources/containerd/cmd/containerd/server/server.go:282`), Dagster daemon `join(timeout=30)` log-and-continue, and Temporal worker `Stop()` (no fallback unlike history/matching) are all instances of missing or partial bounds.

**7. Detach-on-shutdown (supervisees survive the supervisor).**
Problem: daemon upgrades should not kill workloads.
Sources: containerd shims as `Setpgid` processes (`sources/containerd/cmd/containerd-shim-runc-v2/manager/manager_linux.go:110`, `sources/containerd/pkg/shim/util_unix.go:53`); Dagster code servers detached by default (`python_modules/dagster/dagster/_core/remote_representation/grpc_server_registry.py:264-295`).
Why it works: fast restarts, crash isolation. Cost: shutdown provides no workload quiescence; orphan detection (`_check_for_orphaned_runs`, dead-shim synthetic `TaskExit(255)`) becomes mandatory.

**8. Idempotent kill via error normalization.**
Problem: kill-after-exit and double-stop must be benign.
Sources: containerd `checkKillError` mapping finished/not-running/ESRCH → `NotFound`; BuildKit `IsCanceled` classifier (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/errdefs/context.go:12-27`); Temporal cancel-success-noop on closed runs vs strict terminate-error (`service/history/api/requestcancelworkflow/api.go:46-53` vs `service/history/api/terminateworkflow/api.go:47-49`); Dagster `CanCancelExecution = in _executions and not terminated` (`python_modules/dagster/dagster/_grpc/server.py:1289-1336`).
Copy always: every destructive op needs a stated after-close semantic (noop vs error), or callers cannot safely retry.

**9. Daemon timeout backstop that force-marks terminal state.**
Problem: cooperative workers can ignore cancellation forever.
Sources: Dagster `monitor_canceling_run` (180s default → force `CANCELED`), `monitor_starting_run` (180s → `FAILED`), `check_run_timeout` max-runtime path (`python_modules/dagster/dagster/_daemon/monitoring/run_monitoring.py:70-105`, `python_modules/dagster/dagster/_daemon/monitoring/run_monitoring.py:28-67`, `python_modules/dagster/dagster/_daemon/monitoring/run_monitoring.py:226-289`); containerd dead-shim synthesizer (`sources/containerd/core/runtime/v2/shim.go:144`).
Why it works: trades correctness (compute may still run; warning "may not have been fully cleaned up") for liveness (no stuck `CANCELING` row). Temporal notably lacks a server-side cancel-to-close watchdog — `CancelRequested` can linger if the SDK never acks.

**10. Process-group / cgroup containment for descendant trees.**
Problem: children that fork grandchildren escape single-PID signals.
Sources (all partial): containerd verifier negative-PID group kill (`sources/containerd/pkg/imageverifier/bindir/processes_unix.go:35`) and `runc kill --all` gated on `All=true` (`sources/containerd/cmd/containerd-shim-runc-v2/process/init.go:375`); BuildKit git negative-pgid kill + runc `Setpgid`/`PdeathSignal` (with "can still leak" comment at `studies/ultraplan-daemon-events-study/sources/buildkit/executor/runcexecutor/executor_linux.go:24-27`); Dagster/Temporal container launchers (K8s `delete_job`, Docker `container.stop`) as the only containing paths.
Copy the containment primitive (process group on Unix, job objects on Windows, `runc kill --all` / cgroup freezer for containers) for every local executor — its absence in Dagster multiprocess and containerd raw-`Kill(All=false)` is the most replicated escape hatch in the cohort.

## Key Differences

- **Durability:** Dagster and Temporal persist intent (`RUN_CANCELING` event; `CancelRequested` history event + new workflow task) and cancel queued/paused/detached work. BuildKit and containerd have no cancel store — cancel with no attached ctx/shim is a noop (BuildKit `Solver.Get` only looks up live jobs; containerd `Kill` requires resolving a live task).
- **Disconnect vs explicit cancel:** Dagster (disconnect no-op; only `terminate` cancels) and Temporal (disconnect returns long-polls gracefully; only `RequestCancel` writes history) and BuildKit (dropping `Status`/session streams does not stop the `Solve`) all distinguish the two. Containerd does not — both surface as transport `ctx.Done()` with no workflow effect beyond aborting the in-flight leg.
- **Daemon shutdown:** BuildKit/Dagster/Temporal drain (with varying bounds); containerd detaches (workloads survive; plugins close LIFO with no timeout). Only containerd treats daemon SIGTERM as workload-neutral by design.
- **Kill strength:** BuildKit container cancel is SIGKILL-only (strongest, denies graceful hooks); containerd CRI is TERM→KILL with caller grace period, raw API single-signal; Dagster is single SIGINT, no retry; Temporal has no signal (SDK cooperation + heartbeat).
- **Race arbitration strictness:** BuildKit (scheduler + cache guards + executor `select` preferring observed exit) and Temporal (first-writer-wins + mutability guards) and Dagster (reload-before-decide + `is_finished` gates) all arbitrate centrally per unit. Containerd resolves by tolerance: single-flight CAS against double-TERM plus documented duplicate `TaskExit` delivery the consumer must dedupe.
- **Cleanup bounds:** containerd bounds nearly everything (10s/5s/3s/30s) except `Server.Stop`; Temporal bounds daemon stops (5m) but not workflow cleanup; Dagster bounds by default (180s) but `cancel_timeout_seconds=0` disables enforcement; BuildKit detaches cleanup pervasively but leaves the post-SIGKILL reap unbounded.

## Tradeoffs

- **Durable intent vs API simplicity.** Benefit of durability: cancel-by-ref, re-attach, queue/pause coverage (dagster, temporal). Cost: history write + task churn per cancel, plus cooperative-ack complexity. Volatile cancel (buildkit, containerd) has no journal to reconcile but forces the orchestrator to hold the call open; cf. BuildKit "must keep the `Solve` ctx open or kill the whole daemon" vs Temporal "extra workflow-task churn per cancel."
- **SIGKILL immediacy vs graceful cooperation.** BuildKit SIGKILL guarantees un-ignorable termination and simple race logic but denies flush/checkpoint hooks. Dagster single-SIGINT preserves event-log integrity and `finally` flushing but provides no guarantee against swallowed interrupts or blocked native code. Containerd splits the difference by layer (raw surgical, CRI escalating).
- **Drain vs detach vs interrupt on shutdown.** Drain (buildkit, temporal, dagster gRPC) favors in-flight correctness but a wedged unit stalls shutdown without a fallback timer. Detach (containerd, dagster code servers) favors restart speed but requires orphan detection and provides no quiescence. None of the four interrupts in-flight work on SIGTERM — interrupt-on-shutdown is the absent third option.
- **`All=true` power vs blast radius.** Cgroup-wide kill closes the grandchild escape hatch but can kill execs the caller did not intend; default surgical (`All=false`, single PID, single SIGINT) is precise but escapable. Every source defaults to surgical.
- **Bounded cleanup vs completeness.** 3–10s budgets (containerd) and 180s monitors (dagster) and 5m service stops (temporal) guarantee the caller returns but produce leaks-by-log / orphaned-compute-by-warning when budgets expire. Unbounded waits (BuildKit post-kill reap, containerd plugin close, Dagster `cancel_timeout=0` path, Temporal cooperative ack) guarantee completeness-or-hang.
- **Pragmatic string/duplicate tolerance vs typed exactly-once.** BuildKit substring `IsCanceled` detection and containerd duplicate-tolerant exits interoperate with untyped runtime errors at the cost of fragility and consumer-side dedupe burden; Temporal `RequestId`/`CancelRequestId` end-to-end idempotency is the typed counter-model.

## Decision Guide

- **Choose durable intent + cooperative ack** (Temporal/Dagster shape) when: work outlives connections, queues/pauses exist, clients re-attach by ID, or cancel must survive restarts. Accept the cost: you must also build acknowledgement polling, `is_finished`/mutability guards, and a daemon timeout backstop.
- **Choose volatile signal** (BuildKit/containerd shape) when: the executor is a low-level, high-throughput, share-nothing worker with no store, and the orchestrator above you already owns durability. Accept the cost: document that cancel-requires-attachment and provide a `Cancel(ref)` or escalating-stop helper at the higher layer.
- **SIGKILL-only** when termination latency dominates and targets are container inits that cannot meaningfully flush. **TERM→KILL with caller-supplied grace** when targets hold user state worth flushing (CRI model). **SIGINT-only cooperative** only when an event log / compensation protocol must run before death — and then always pair it with a SIGKILL deadline.
- **Drain on shutdown** for build/orchestration daemons where killing in-flight work corrupts shared caches. **Detach on shutdown** for container supervisors where workloads must survive daemon upgrade. Either way, add a fallback timer (`GracefulStop → AfterFunc(→Stop)`; `join(timeout)` → force) — an unbounded drain is a hang.
- **Default surgical kill, offer tree kill explicitly:** single-PID/signal default with an opt-in `All=true` / `killpg` / job-delete path whose blast radius is documented, mirroring containerd's flag and Dagster/Temporal container launchers.

## Practical Tips

Patterns to copy:
- Write `CANCELING`/`CancelRequested` before touching compute; make late-cancel-after-close a documented noop or error, never an exception.
- Wrap every cleanup path in detached-context-plus-timeout (`WithoutCancel` / `CopyContextValues + WithTimeout` / `cleanup.Do`); never let finalization inherit the canceled context.
- Gate every destructive op on live state (`is_finished`, `IsWorkflowExecutionRunning`, per-state `Kill`/`Delete`) and normalize post-exit kills to benign outcomes.
- Never cache or commit a canceled error as a shared result (`complete=false + releaseError` idiom).
- Pair every push notification (event, RPC, worker command) with a pollable flag (DB status, heartbeat `CancelRequested`) so detached workers still observe cancel.
- Give every drain a deadline and a force fallback; log-and-continue on expiry rather than hanging, but count the leak.

Patterns to avoid or delay:
- Substring cancel classification (`"EOF"`/`"context canceled"`) — use typed cancel/exit errors as soon as the runtime permits.
- Duplicate-tolerant exit delivery without sequence/idempotency keys — acceptable inside one shim, not across billing boundaries.
- `cancel_timeout=0`-means-disabled backstops and `0s`-default drains — make "no bound" explicit and lint production overlays for non-zero values.
- Single-shot cooperative interrupt with no escalation on the hot path — wire the existing helpers (`interrupt_then_kill`, CRI grace loop) in before scaling local executors.

Caution signs the design is becoming brittle:
- `CANCELING`/`CancelRequested` rows older than the configured timeout with still-running compute.
- Shutdown times tracking the slowest in-flight unit (missing fallback timer).
- Rising `NotFound`-on-kill or duplicate-exit rates (cancel arriving after completion — normal in isolation, a leak signal in aggregate).
- Grandchild PIDs surviving parent cancel (missing group/cgroup containment).
- Status-column/body skew warnings or cancel-clock resets on repeated `terminate` (Dagster `RUN_CANCELING`-timestamp overwrite question).

## Anti-Patterns / Caution Signs

- **Fire-and-forget signal with no intent record** (containerd raw `Kill`, BuildKit transport-only cancel): intent lost on detach; caller cannot distinguish "delivered" from "dropped."
- **Cleanup inheriting the canceled context:** finalization starved by its own cancel — fixed everywhere here by `WithoutCancel`, absent anywhere it is not.
- **Unbounded post-kill wait:** BuildKit `<-p.ended` after SIGKILL (`studies/ultraplan-daemon-events-study/sources/buildkit/executor/runcexecutor/executor.go:810-821`); containerd `Server.Stop` plugin loop; Dagster `cancel_timeout_seconds=0` skip; Temporal cooperative ack with no watchdog.
- **One-signal-fits-all:** raw `All=false` / single SIGINT as the only primitive — grandchildren and SIGTERM-ignorers escape by construction.
- **Silent success-noop ambiguity:** Temporal late-cancel success vs terminate error, containerd `NotFound` on kill-after-exit — callers that need "did I cancel it?" must read history/state, not the RPC status.
- **Detach-by-default without orphan accounting:** fast shutdown that leaves zombies unless synthetic-exit + heartbeat-expiry + GC paths exist.

## Notable Absences

- **No source cancels in-flight work on daemon shutdown.** All drain or detach; a bounded drain→cancel→`Stop()` transition (BuildKit future consideration) exists nowhere.
- **No durable cancel replay after full restart in volatile systems** (BuildKit in-memory job table; containerd no pending-kill record). Only Dagster/Temporal intent survives restart.
- **No cgroup freezer/kill fallback in container hot paths** beyond `runc kill --all` gated on a flag; OOM/cgroup code is read-only accounting (BuildKit) or absent (Dagster OSS, Temporal server).
- **No server-side cancel-to-close deadline for cooperative cleanup** in Temporal; Dagster's is the only enforced one and is disableable.
- **No bounded teardown budget inside user code** after interrupt (Dagster `finally` unbounded; Temporal compensation SDK-side with no server timeout primitive).
- **No central fencing token** for cancel-vs-complete; arbitration is per-layer guards plus idempotence, not epoch/sequence fencing.
