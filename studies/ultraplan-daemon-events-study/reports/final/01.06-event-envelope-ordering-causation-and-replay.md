## Executive Summary

The four sources split cleanly along an axis that this study makes explicit: **durable log vs ephemeral broadcast**. Temporal and Dagster treat events as a per-subject (per-workflow / per-run) append-only journal that doubles as the source of truth for replay; they ship monotonic sequence numbers, opaque cursor-based resume, transactional append, and explicit forward-compatibility shims. BuildKit and Containerd treat events as a best-effort in-memory notification stream with a separate optional history layer; neither ships sequence numbers, cursors, or a reconnection contract — disconnecting an observer mid-stream demonstrably loses data on the live path.

All four sources agree on the low-level fact that names should be past-tense verbs at the payload level, that wall-clock timestamps are insufficient for ordering (Temporal, BuildKit and Containerd rely on them; Dagster uses autoincrement IDs instead), and that schema evolution must be additive. Where they diverge is in the depth of the contract: only Temporal and Dagster commit to a resume-without-gaps-or-duplicates semantic, and only Temporal surfaces a meaningful continuity guarantee to public subscribers (via `WaitNewEvent` long-poll that re-validates mutable state).

The single biggest lesson: **durability and ordering have to be designed in from the start**. Bolt-on persistence on top of an in-memory broadcaster (BuildKit's `ListenBuildHistory`, Containerd's `eventq`) cannot fix the resume contract, because the producer side never assigns a sequence number that survives the publisher's lifetime.

## Core Thesis

**Event envelopes need an explicit identity model that separates event identity (`id` / `EventId`) from operation/transition identity (`VersionedTransition`, `run_id`) from attempt identity (retry counter, attempt field). Ordering must be assigned by the producer under transactional control, not inferred from wall-clock timestamps on the consumer side. Resume cursors must be opaque, monotonic per subject, and paired with an explicit gap/duplicate contract — not retrofitted to an in-memory broadcaster.**

Temporal is the clearest reference implementation for a durable, replicated event log; Dagster is the clearest reference for cursor-based pagination over a SQL journal with explicit back-compat metadata; BuildKit and Containerd demonstrate what happens when these decisions are deferred.

## Approach Models

The sources cluster into four distinct approach models for the "event envelope, ordering, causation, and replay" problem. Each is a coherent response to a different product shape, and none is strictly wrong for its context — but they are not interchangeable.

### A. Durable Append-Only Per-Subject Journal (Temporal)

Temporal models the event log as the canonical state: the workflow's `mutable state` is reconstructed from history. Producer-side sequence (`EventId`) is assigned in-memory by `EventStore.AllocateEventID` (`service/history/historybuilder/event_store.go:58-66`), buffered in `reorderBuffer` to undo storage-layer reordering (`service/history/historybuilder/event_store.go:161-200, 461-491`), then flushed transactionally with a `PrevTransactionID` chain and "larger wins" concurrency control (`common/persistence/data_interfaces.go:776-792`). Two-tier identity — `EventId` for intra-shard order and `VersionedTransition{NFV, TC}` for cross-cluster staleness — gives failover safety that a single counter cannot. Resume is cursor + long-poll: `WaitNewEvent=true` re-validates mutable state before returning (`service/history/api/get_workflow_util.go:128-260`), so correctness does not depend on the in-memory notifier.

### B. SQL Journal with Opaque Cursor (Dagster)

Dagster uses an `event_logs` SQL table where `id` autoincrement PK acts as the per-run sequence (`python_modules/dagster/dagster/_core/storage/event_log/schema.py:8-24`). Cursor is opaque base64 JSON: `EventLogCursor(cursor_type=OFFSET|STORAGE_ID, value=int)` (`python_modules/dagster/dagster/_core/event_api.py:20-64`). Two watcher strategies — `SqlPollingEventWatcher` (adaptive 0.25–16s backoff) and `SqliteEventLogStorageWatchdog` (filesystem-notify on `<run_id>.db`) — cover remote SQL and local SQLite respectively. Evolution is codified at the type level via `@whitelist_for_serdes` with `old_storage_names`, `old_fields`, `storage_field_names`, and a centralized `DagsterEventSerializer.before_unpack` that rewrites legacy event types (`STEP_MATERIALIZATION -> ASSET_MATERIALIZATION`, `PIPELINE_* -> RUN_*`) before construction (`python_modules/dagster/dagster/_core/events/__init__.py:413-447`). Degradation is graceful: `handle_unpack_error` wraps the row into an `ENGINE_EVENT` rather than failing the reader.

### C. Two-Stream Hybrid: Ephemeral Progress + Durable History (BuildKit)

BuildKit exposes two disjoint APIs rather than one log. Live build progress is `Control.Status(Ref)`, a server-streaming gRPC RPC whose payload is `StatusResponse{Vertex[],VertexStatus[],VertexLog[],VertexWarning[]}` (`api/services/control/control.proto:116-164`); it collapses by `dirty[ID]` per read (`util/progress/progress.go:241-246`), losing intermediate states. Durable history is `Control.ListenBuildHistory` backed by `history.Queue` (bbolt + content blobs): on every new subscription it emits the in-memory active snapshot (Go map iteration — non-deterministic order) then scans persisted `COMPLETE` blobs, then attaches to a `pubsub` for live updates (`solver/llbsolver/history/buildhistory.go:770-868`). There is no cursor — every new subscriber sees the full replay, guaranteeing duplicates — and no sequence number on either path. Schema evolution is proto3 additive + imperative `translateLegacySolveRequest` (`control/control.go:370-407`), not envelope versioning.

### D. Pure Ephemeral Pub/Sub (Containerd)

Containerd's event system is `docker/go-events` `Broadcaster` + per-subscriber `Queue` + optional `Filter` + `Channel`, with no persistence at the core (`core/events/exchange/exchange.go:37-199`). The envelope is `Envelope{Timestamp, Namespace, Topic, Any event}` (`api/types/event.proto:27-33`) — minimal, cross-language via protobuf, but no `id`/`sequence`/`correlation`. The gRPC surface (`api/services/events/v1/events.proto:60-62`) and TTRPC mirror carry only `repeated string filters`. CRI uses a separate `internal/eventq.EventQueue[T]` with a `discardAfter` TTL (`internal/eventq/eventq.go:56-140`) which is **not** wired into the core exchange — so the only short-term buffering lives outside the production event path. Schema evolution is `google.protobuf.Any` + `typeurl.Register` (`core/runtime/typeurl.go:31-35`); missing registration on the consumer side causes `UnmarshalAny` errors that get downgraded to `log.Warn`, silently losing facts.

## Pattern Catalog

Each pattern below solves a problem visible across multiple sources or unusually clearly in one.

### P1. Opaque Base64/Protobuf Cursor for Resume

- **What it solves**: Hides internal storage cursor representation; lets the server change pagination strategy without breaking clients; enforces stable wire format across schema bumps.
- **Where demonstrated**:
  - Dagster `EventLogCursor(cursor_type=OFFSET|STORAGE_ID, value=int).to_string() == base64(json({type,value}))` (`python_modules/dagster/dagster/_core/event_api.py:20-64`).
  - Temporal `HistoryContinuation{FirstEventId, NextEventId, PersistenceToken, BranchToken, VersionHistoryItem, VersionedTransition}` (`api/token/v1/message.pb.go:30-42`).
- **Why it works**: The consumer treats the cursor as an opaque blob and round-trips it; the server can swap `OFFSET` → `STORAGE_ID` (Dagster's migration warning at `python_modules/dagster/dagster/_core/storage/event_log/base.py:232-238`) or rotate storage pagination without protocol change.
- **When to copy**: Any time the consumer-side pagination state must survive server upgrades or storage changes.
- **When it's overkill**: A single-consumer local log where the storage layout is stable and the cursor is the same as the offset.
- **Risk**: Temporal's token mixes event cursor and storage cursor in one blob, so a server-side storage change invalidates old tokens unless a migration path is added (`service/history/api/getworkflowexecutionhistory/api.go:232-239` `ErrInvalidNextPageToken`).

### P2. Two-Tier Identity: EventId vs Operation Transition

- **What it solves**: Distinguishes "intra-subject order" (which event came first) from "cluster-wide logical clock" (which version of the operation is current).
- **Where demonstrated**:
  - Temporal `EventId` (monotonic per shard) + `VersionedTransition{NFV, TC}` on `WorkflowExecutionInfo` and every persisted task (`api/persistence/v1/executions.pb.go:275, 2844`, `api/persistence/v1/hsm.pb.go:457-465`).
  - Dagster `storage_id` (autoincrement, global on consolidated stores) + `run_id` + `step_key` (`python_modules/dagster/dagster/_core/events/log.py:31-44`).
  - BuildKit `Vertex.Digest` (LLB node identity) + `Ref` (build identity) (`api/services/control/control.proto:127-136`).
- **Why it works**: Without separation, you cannot answer both "what order" and "is this still the current operation" — the same monotonic counter gets overloaded and breaks under failover.
- **When to copy**: Any multi-subject log that must survive replication, failover, or shard migration.
- **Risk**: Adds envelope surface area that must be evolved; BuildKit gets away with one tier because it has no replication story.

### P3. Producer-Assigned Sequence Under Transactional Control

- **What it solves**: Removes the "did the clock skew?" question entirely; guarantees monotonic per-subject ordering even with concurrent producers.
- **Where demonstrated**:
  - Temporal `EventStore.AllocateEventID` increments `nextEventID` in shard-owned mutable state (`service/history/historybuilder/event_store.go:58-66`); persistence uses `PrevTransactionID` chain with "larger wins" (`common/persistence/data_interfaces.go:788-791`).
  - Dagster `SqlEventLogStorageTable.id BigInteger autoincrement PK` (`python_modules/dagster/dagster/_core/storage/event_log/schema.py:11-16`); `result.inserted_primary_key[0]` returned at INSERT time (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:388-419`).
- **Why it works**: The producer is the only point that can guarantee no gaps; consumers can never reconstruct a total order from timestamps alone.
- **When to copy**: Any system that needs replay-without-gaps, resumable cursors, or causal reasoning.
- **When it's overkill**: Notification-only systems where loss is acceptable (BuildKit live `Status`, Containerd live `Subscribe`).
- **Risk**: Requires a linearization point (shard lock, DB autoincrement) that becomes a write bottleneck; Dagster's sharded SQLite explicitly gives this up for cross-run queries.

### P4. Centralized Type-Whitelisted Serdes with Backcompat Shims

- **What it solves**: Lets the producer evolve the schema (rename fields, repurpose event types, deprecate enums) while consumers keep reading old data; codifies the contract instead of relying on protobuf additive rules.
- **Where demonstrated**:
  - Dagster `@whitelist_for_serdes(old_storage_names, old_fields, storage_field_names, field_serializers, skip_when_none_fields)` on every persisted type (`python_modules/dagster/dagster/_core/events/log.py:21-29`); `DagsterEventSerializer.before_unpack -> _handle_back_compat` rewrites four legacy rewrites in one place (`python_modules/dagster/dagster/_core/events/__init__.py:413-447, 2221-2278`).
  - Temporal `FixFollowEvents` rewrites last event to `ContinuedAsNew` for older SDKs that don't understand `NewExecutionRunId` (`service/history/api/get_history_util.go:554-638`).
- **Why it works**: Centralizes the rewrite logic; survives multiple legacy versions; degrades gracefully (`RunFailureReasonSerializer.unpack` swallows unknown enum values to `UNKNOWN` at `python_modules/dagster/dagster/_core/events/__init__.py:297-304`).
- **When to copy**: Any persistence layer that must survive upgrades over years without forced migrations.
- **When it's overkill**: Short-lived ephemeral streams where the schema is owned by one team and migrations are easy.
- **Risk**: Each rewrite rule becomes an undocumented contract; Dagster's degradation to `ENGINE_EVENT` for unknown event types silently changes semantics for forward-compat readers (`python_modules/dagster/dagster/_core/events/__init__.py:423-447`).

### P5. Pull+Push Hybrid for Live Observation

- **What it solves**: Gives consumers sub-second latency for active workflows while preserving correctness via re-validation after long-poll.
- **Where demonstrated**:
  - Temporal `GetWorkflowExecutionHistory(WaitNewEvent=true)` returns the page, then long-polls via `events.Notifier.WatchHistoryEvent` (`service/history/api/get_workflow_util.go:128-260`) gated by per-workflow channels; on wake-up re-reads mutable state (`service/history/api/getworkflowexecutionhistory/api.go:456-480`).
  - Dagster `SqlPollingEventWatcher` (poll) + `SqliteEventLogStorageWatchdog` (filesystem notify) (`python_modules/dagster/dagster/_core/storage/event_log/polling_event_watcher.py:29-86`, `python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:528-568`).
- **Why it works**: Correctness rides on the pull path (DB read with cursor); push is an optimization that can drop without breaking the resume contract.
- **When to copy**: Any system where active observation latency matters and resume correctness is non-negotiable.
- **When it's overkill**: High-throughput notification-only systems (BuildKit `Status`, Containerd `Subscribe`) where cursor resume is not a goal.
- **Risk**: Two code paths can drift — Dagster's polling vs fs-notify watchers handle teardown differently (`storage_id > cursor` vs filesystem `on_modified`), and a producer that flushes via SQLite WAL may not raise `on_modified` until fsync.

### P6. Producer-Stamped Causation via Typed Pointer Fields

- **What it solves**: Records the causal chain (which activity caused this completion, which signal initiated this update) without a generic envelope field that would be wrong for some event shapes.
- **Where demonstrated**:
  - Temporal `EventStore.wireEventIDs` patches `StartedEventId`/`scheduledEventId`/`initiatedEventId`/`lastCompletedEventId` into completion events (`service/history/historybuilder/event_store.go:381-454`); request-id causation on `WorkflowExecutionOptionsUpdated.AttachedRequestId`, `WorkflowExecutionSignaled.RequestId` (`service/history/historybuilder/event_store.go:441-452`).
  - BuildKit `Vertex.Inputs: []digest.Digest` for parent links + `ProgressGroup{id,name,weak}` for grouping (`api/services/control/control.proto:127-136`, `solver/pb/ops.proto:220-234`).
  - Dagster `LoadedInputData(upstream_step_key, upstream_output_name)` + `JobFailureData.first_step_failure_event` + run-level `dagster/parent_run_id` tags (`python_modules/dagster/dagster/_core/events/__init__.py:2128-2131, 2030`, `python_modules/dagster/dagster/_core/storage/tags.py:42-44`).
- **Why it works**: Causality varies per event shape; a single generic field cannot express "this completion was caused by that schedule" without a separate ontology.
- **When to copy**: Any event taxonomy where the causal relation depends on event type (activity vs timer vs child workflow vs materialization).
- **When to push back**: When you want a single OpenTelemetry-style `trace_id` to cross system boundaries — see P7.
- **Risk**: Causation lives in attribute-specific fields; consumers must peruse each event type to construct a causal graph.

### P7. Cross-System Causation as an Explicit Envelope Field (Missing Pattern)

- **What it solves**: Carries an OTel-compatible trace identifier so events emitted by different daemons (buildkit, containerd) can be joined with external observability without per-type knowledge.
- **Where demonstrated**: **Nowhere.** Grepped all four sources for `causationId`, `correlationId`, `traceparent`, `trace_id` in envelope — no source has it.
  - Containerd has `pkg/tracing/log.go:81` injecting `trace_id` into logs but not events (`containerd.md:62` negative evidence).
  - Dagster has `logging_tags` opaque map but no standardized trace propagation.
  - Temporal has `Links` on Nexus callbacks (`api/historyservice/v1/request_response.pb.go:8764`) but not a generic envelope field.
- **Why it matters**: This is the highest-leverage absent feature across the study. Without it, no source can answer "which user request caused this vertex to start?" without joining against external systems by payload fields.
- **When to copy**: Any new event system that participates in a multi-system control plane (CI runners, orchestration, K8s operators).

### P8. Graceful Subscriber Teardown on Terminal Status

- **What it solves**: Prevents observer leaks on completed runs.
- **Where demonstrated**:
  - Dagster `SqliteEventLogStorageWatchdog.on_modified` auto-calls `end_watch` when callback returns `SUCCESS|FAILURE|CANCELED` (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:559-564`).
  - Containerd `Exchange.Subscribe` defers `closeAll` (removes sink + closes errq) and propagates `ctx.Err()` except `context.Canceled` (`core/events/exchange/exchange.go:137-142, 189-195`).
  - Temporal `Notifier` removes subscriber on context cancel via `events.Notifier.unwatchHistoryEvent` (`service/history/events/notifier.go:120, 180-200`).
- **When to copy**: Any system with per-subject subscribers; terminal-state autodetection prevents zombie observers.
- **Risk**: Auto-detecting "terminal" requires the watcher to know the domain (Dagster knows `SUCCESS`/`FAILURE`/`CANCELED`); pure transports like Containerd have to fall back on context cancellation.

### P9. Per-Subject Channel-Based Notification with Bounded Buffer

- **What it solves**: Decouples notification fan-out from the database write path while bounding per-subscriber resource use.
- **Where demonstrated**:
  - Temporal `Notifier` per-workflow channel of size 1 with drop-on-overflow (`service/history/events/notifier.go:120, 191-197`).
  - BuildKit `pubsub[T]` channel size 32 with `go c.send(v)` + `select {case ch<-v; case <-done}` (`solver/llbsolver/history/pubsub.go:10-54`).
  - Containerd `Queue{list.List unbounded}` + `Channel(0)` (`vendor/github.com/docker/go-events/queue.go:13-111`).
- **Why it works**: Bounded buffers prevent OOM; drop-on-overflow forces the consumer to fall back to pull.
- **Risk**: Temporal's size 1 + silent drop is the sharpest — the long-poll re-read masks it; if a consumer uses the notifier without re-read, they will silently miss events. BuildKit's `go c.send` spawns one goroutine per subscriber per event, risking goroutine explosion under slow consumers.

### P10. Content-Addressable Status Blob Replay (BuildKit-Specific)

- **What it solves**: Stores the same wire-format `StatusResponse` chunks in content-addressable storage so consumers can replay post-build status without re-running the build.
- **Where demonstrated**: `history.Queue.ImportStatus` writes length-prefixed `StatusResponse` frames into a `application/vnd.buildkit.status.v0` blob (`solver/llbsolver/history/buildhistory.go:679-768`); replay is `ReadAtLeast` loop (`385-413`).
- **Why it works**: Reuses the wire format; immutable; cache-friendly.
- **When to copy**: When you need post-completion replay of a stream that was originally ephemeral and you control the wire format.
- **When it's overkill**: When the original stream was already durable.

## Key Differences

The four sources diverge on five axes that map cleanly to their product constraints.

### Ordering Model

- **Temporal**: Per-workflow monotonic `EventId` assigned in-memory under shard lock; persisted transactionally with `PrevTransactionID` chain. Cross-cluster via `VersionedTransition{NFV, TC}`.
- **Dagster**: Per-run `id` autoincrement from SQL `INSERT`; per-run monotonic by construction; cross-run global order requires consolidated storage (Postgres/MySQL/ConsolidatedSqliteEventLogStorage) or falls back to timestamp + fan-out on sharded SQLite.
- **BuildKit**: Timestamp-sorted within a `Read` batch (`slices.SortFunc(a.Timestamp.Compare(b.Timestamp))`); collapsed by ID per read; no per-vertex or per-build sequence number.
- **Containerd**: Synchronous in-memory FIFO per broadcaster instance via `Broadcaster.events chan` + `Queue.list.List`; no sequence number; no cross-instance order.

The driver here is whether the producer must commit durably: Temporal and Dagster must, so they need a sequence that survives the producer. BuildKit and Containerd don't, so they skip it.

### Resume Contract

- **Temporal**: Public API `GetWorkflowExecutionHistory(WaitNewEvent=true)` returns continuation token; long-poll re-reads mutable state to fill gaps; branch token + `VersionedTransition` rejected if stale.
- **Dagster**: `EventLogCursor(STORAGE_ID|value)` opaque; cursor migration path from legacy `OFFSET`; per-run idempotent.
- **BuildKit**: No cursor. New `ListenBuildHistory` subscriber gets full active + persisted replay (duplicates guaranteed); new `Status(Ref)` subscriber gets only future events.
- **Containerd**: No cursor. New subscriber gets only future events.

Temporal and Dagster treat resume as a first-class contract; BuildKit and Containerd treat it as "rebuild state from scratch."

### Causation Representation

- **Temporal**: Typed pointer fields (`scheduledEventId`, `initiatedEventId`, `startedEventId`, `lastCompletedEventId`) wired by `EventStore.wireEventIDs`; request-id fields on Options Updated/Signaled.
- **Dagster**: Run lineage tags (`dagster/parent_run_id`, `dagster/root_run_id`) + step lineage via `LoadedInputData.upstream_step_key` + `JobFailureData.first_step_failure_event`.
- **BuildKit**: Structural DAG via `Vertex.Inputs` (LLB digests) + `ProgressGroup` for grouping; causation is the LLB graph itself, not a per-event field.
- **Containerd**: None. `namespace` + `topic` + payload `id` only.

All four lack a generic envelope-level `causationId`/`correlationId`. None would benefit from OpenTelemetry trace propagation without one.

### Schema Evolution Strategy

- **Temporal**: Protobuf `reserved` field numbers (`proto/internal/temporal/server/api/history/v1/message.proto:11-12`); deprecated field paths via doc comments; `StrippedHistoryEvent` skips field numbers (`api/history/v1/message.pb.go:338-339`); `FixFollowEvents` runtime rewrite for old SDKs.
- **Dagster**: `whitelist_for_serdes` per-type with explicit `old_storage_names`/`storage_field_names`/`field_serializers`; `before_unpack` remapping; graceful `ENGINE_EVENT` degradation; Alembic migrations for schema columns.
- **BuildKit**: Proto3 additive + imperative `translateLegacySolveRequest`; deprecated fields with `[deprecated=true]`; `CompatibilityVersion` for image output (not events).
- **Containerd**: Protobuf3 additive + `google.protobuf.Any` + `typeurl.Register`; no formal versioning; type-URL mismatch downgrades to `log.Warn` (silent loss).

Dagster has the most codified contract; BuildKit and Containerd rely on protobuf additive rules plus runtime fallbacks.

### Storage Integration

- **Temporal**: Shard-owned mutable state in Cassandra/MySQL/Postgres/SQLite; branch tokens encode cluster generation.
- **Dagster**: Default per-run `<run_id>.db` SQLite + mirrored `index` shard for assets/checks; pluggable SQL backends.
- **BuildKit**: bbolt `recordsBucket` for history records + content store blobs for status frames; leases for GC.
- **Containerd**: No storage.

The deeper the storage integration, the stronger the resume contract. BuildKit's bbolt is the only non-stream source with explicit replay, but it is layered on top of the live path, not replacing it.

## Tradeoffs

| Tradeoff | Temporal | Dagster | BuildKit | Containerd |
|----------|----------|---------|----------|------------|
| Durable ordering vs write contention | Shard lock serializes; per-workflow hot shard becomes bottleneck | Sharded SQLite maximizes single-run write throughput; cross-run loses global order | None — live path ephemeral; history serializes per bbolt bucket | None — pure in-memory |
| Opaque cursor vs wire visibility | Hides storage cursor; mixes event + storage | Single type-stable base64 JSON | N/A — no cursor | N/A — no cursor |
| Causation via typed pointers vs generic envelope | No generic `causationId`; must know each event shape | Run/step lineage via tags + payload; no generic field | DAG-as-event; perfect for build graph but not for cross-system | None |
| Pull+push hybrid vs pure push | Long-poll re-validates; notifier drops OK | Polling watcher (DB-agnostic) + fs-notify (local SQLite) | Live `Status` is push; `ListenBuildHistory` is push+durable-snapshot | Pure push; `eventq` TTL is the only buffering |
| Type-whitelisted serdes vs protobuf additive rules | Proto additive + `reserved` + runtime rewrite | Centralized serdes + graceful `ENGINE_EVENT` degradation | Proto additive + imperative shim | Proto additive + `Any`/typeurl |
| Best-effort notifier vs guaranteed delivery | Size 1 drop + long-poll re-read | Poll/notify + idempotent watcher teardown | `pubsub` buffer 32 + `go c.send` fanout | Unbounded `list.List` + `Channel(0)` |
| Cross-cluster ordering via transition history | `VersionedTransition{NFV, TC}` is the headline feature | Single-process; not applicable | Single-process | Single-process |

The recurring trade is **stronger guarantees cost more complexity at the producer side**. Temporal pays for two-tier identity, branch tokens, and buffered-reorder logic. Dagster pays for sharded storage and `RunShardedEventsCursor` fan-out. BuildKit and Containerd avoid all of this by being ephemeral.

## Decision Guide

Choose your approach model based on the consumer's needs:

- **Need exactly-once / at-least-once resume with no gaps?** Use Temporal's pattern: producer-assigned `EventId` + opaque cursor + post-page mutable-state re-read. Do not rely on a push notifier for correctness.
- **Need cursor-stable replay over SQL with optional cross-run global order?** Use Dagster's pattern: autoincrement PK + `STORAGE_ID` cursor + polling/notify watcher pair. Accept that cross-run order on sharded storage is best-effort.
- **Need post-hoc replay of an originally-ephemeral stream?** Use BuildKit's pattern: serialize the wire format into content-addressable blobs after the live stream completes. Accept that mid-stream disconnects are still lost.
- **Need a live notification bus with no durability requirement?** Use Containerd's pattern: `Broadcaster + Queue + Filter + Channel`. Pair with a separate TTL queue (`eventq`) only if a transient buffer is genuinely needed.

Do not mix patterns casually: a `STORAGE_ID` cursor over an in-memory broadcaster is a contradiction, because the broadcaster's `id` does not survive process restart.

## Practical Tips

Patterns worth copying, in priority order:

1. **Assign sequence at the producer under a transaction.** Don't ask the consumer to reconstruct order from timestamps.
2. **Ship an opaque cursor.** Base64 JSON (`Dagster`) or protobuf (`Temporal`). Treat it as a black box; never inspect it on the client.
3. **Separate event identity from operation identity.** A `run_id` + `storage_id` is not enough — also carry `parent_run_id` or equivalent so consumers can answer "what caused this run?"
4. **Make the durable path the source of truth and the live path an optimization.** Temporal's `WaitNewEvent` re-reads mutable state before returning; Dagster's watchers always re-fetch by `storage_id`. The push path can drop.
5. **Centralize schema evolution in one type-whitelist module.** Dagster's `before_unpack` is the clearest example — every legacy rewrite in one place, with graceful degradation.
6. **Encode causation via typed pointers, not generic envelope fields.** Temporal's `wireEventIDs` walks the buffered events and patches `StartedEventId` into completions; BuildKit's `Vertex.Inputs` carries the parent DAG. A single generic `causationId` cannot express these shapes.
8. **Test disconnect/reconnect at the storage layer.** Temporal's `TestGetWorkflowExecutionHistory_LongPollDiscardsRequestBranchToken` and Dagster's `seen_storage_ids` plumbing both assume the test would have surfaced a real bug. Containerd's `TestDiscardedAfterTime` (`internal/eventq/eventq_test.go:85-103`) is the cleanest demonstration that disconnect loses data.
9. **Auto-teardown watchers on terminal status.** Dagster's `on_modified` callback returning `SUCCESS|FAILURE|CANCELED` ends the watch.
10. **Document the cursor type and migration path.** Dagster's `OFFSET -> STORAGE_ID` migration warning is the right shape.

Patterns worth avoiding or delaying:

- **Bolt-on persistence on an in-memory broadcaster.** BuildKit's `ListenBuildHistory` cannot guarantee gap-free resume because the live `Status` path never assigned sequence numbers.
- **`time.Now().UTC()` as the only ordering field.** All four sources that try this (BuildKit `Timestamp`, Containerd `time.Now().UTC()`) inherit clock skew.
- **Generic `causationId`/`correlationId` envelope field before you know your event shapes.** Temporal and Dagster deliberately don't have one for good reason.
- **Silent log-and-continue on type-URL mismatch** (Containerd's `log.Warn` downgrade at `core/events/exchange/exchange.go:189-195`). This makes evolution cost invisible until the consumer asks "where are my events?"
- **Goroutine-per-subscriber-per-event fan-out** (BuildKit's `pubsub.Send go c.send(v)` at `solver/llbsolver/history/pubsub.go:22-28`). Bounded buffers or ring buffers prevent goroutine explosion.
- **Map-iteration replay** (BuildKit's `for _, e := range h.active` at `solver/llbsolver/history/buildhistory.go:800-811`). Replay order must be deterministic.

## Anti-Patterns / Caution Signs

These are the specific signals that an event envelope design is becoming brittle:

- **Two disjoint APIs for "live" and "history"** (BuildKit). Users will conflate them; resume semantics will diverge.
- **No `id`/`sequence` field on the envelope** (Containerd, BuildKit live). Cannot reconstruct order, cannot deduplicate, cannot resume.
- **Timestamp-only ordering**. Watch for: `ORDER BY timestamp` without a tie-breaker; `slices.SortFunc(a.Timestamp.Compare(b.Timestamp))`; `time.Now()` at write time.
- **Last-writer-wins collapsing by ID** (BuildKit's `progressReader.dirty[ID]`). Fine for gauges, fatal for events.
- **Map-iteration replay**. If you see `for _, x := range someMap` in a replay path, you've already lost determinism.
- **Goroutine-per-subscriber-per-event fan-out without bounded buffers**. Slow consumers will exhaust memory.
- **Silent log-and-continue on schema mismatch**. Watch for `log.Warn(...)` followed by `continue` in event receive paths.
- **Cursor stored in the consumer without migration support**. Dagster's `OFFSET -> STORAGE_ID` migration warning is the right pattern; BuildKit and Containerd have no migration support because they have no cursor.
- **Cross-run ordering that depends on filesystem `mtime` or `update_timestamp`**. Dagster's `SqliteEventLogStorage` sharded cross-run can miss events whose `update_timestamp` did not advance.
- **Causation represented only by payload fields with no indexable key**. Dagster's `LoadedInputData.upstream_step_key` is fine; Containerd's bare `ContainerCreate.id` with no parent linkage is not.
- **Single-message-channel-of-size-1 notifier** (Temporal's `Notifier` at `service/history/events/notifier.go:120`). Acceptable only because the long-poll re-reads; if anyone uses the notifier without that re-read, they will silently miss events.
- **Re-driving an event producer without idempotency keys**. Dagster's `store_event` always allocates a new autoincrement id; consumers must dedupe via `seen_storage_ids`.

## Notable Absences

What no source does — and what each absence costs:

| Absent Feature | Sources Missing | What It Costs |
|----------------|-----------------|---------------|
| Generic `causationId` / `correlationId` envelope field | All four | Cross-system event correlation requires external join by payload fields; no OTel-style distributed tracing |
| Per-subject monotonic sequence on ephemeral streams | BuildKit, Containerd | Reconnect mid-stream loses events with no detection; resume = rebuild state from scratch |
| Schema registry / compatibility contract | BuildKit, Containerd | Evolution cost invisible to producers until consumers fail to parse |
| Per-subject backpressure with explicit overflow signal | All four | Containerd `Queue.list.List` is unbounded; Temporal `Notifier` drops silently; BuildKit goroutine-spams |
| Retention / TTL policy on the event log | Dagster (no policy found), BuildKit (lease-based GC), Temporal (configurable) | Long-lived daemons can grow event tables unbounded; Dagster `event_logs` has `delete_events`/`wipe` but no auto-prune |
| Bounded replay buffer for ephemeral streams | BuildKit, Containerd | No way to resume a recently-disconnected observer without full state replay |
| Producer-side idempotency keys | Dagster, BuildKit, Containerd | Re-drive creates duplicate rows/events; consumer must dedupe |
| Auto-migration of opaque cursors across server versions | Containerd (N/A — no cursor), BuildKit (N/A — no cursor) | Resuming with an old cursor after server upgrade is undefined |

The highest-leverage absence is the generic causation/correlation field. All four sources spend code on per-type causation, but none would benefit from a one-line `traceparent` field that works with external observability.

## Per-Source Notes

### buildkit (4/10)

- **Approach**: Two-stream hybrid — ephemeral `Status(Ref)` for live progress + durable `ListenBuildHistory` over bbolt/content blobs.
- **Strongest evidence of the chosen model**: `llbsolver.Solver.Status` first tries `history.Queue.Status` (replays persisted log blobs), else falls back to `solver.Solver.Get(id) → Job.Status` (live progress pipe) (`solver/llbsolver/solver.go:465-481`).
- **Where the design fails**: `progressReader.dirty[ID]` collapses by `ID` per read (`util/progress/progress.go:241-246`); `ListenBuildHistory` re-emits the full active + persisted snapshot on every subscription (`solver/llbsolver/history/buildhistory.go:770-868`).
- **Where to look for the pattern**: `Vertex.Inputs: []digest.Digest` + `ProgressGroup{id,name,weak}` (`api/services/control/control.proto:127-136`, `solver/pb/ops.proto:220-234`) — the LLB DAG itself is the causation model.
- **Where to look for the antipattern**: `pubsub.Send` with `go c.send(v)` + `select {case ch <- v; case <-done}` (`solver/llbsolver/history/pubsub.go:22-54`) — goroutine-per-subscriber-per-event fan-out.
- **Why the rating**: Envelope fields exist but are split across two APIs with different durability/ordering semantics; no sequence/cursor; reconnect cannot guarantee exactly-once reconstruction.

### containerd (4/10)

- **Approach**: Pure in-memory pub/sub over `docker/go-events` `Broadcaster` + per-subscriber `Queue`/`Filter`/`Channel`.
- **Strongest evidence of the chosen model**: `Exchange.Subscribe(ctx, filters...) (<-chan *Envelope, <-chan error)` (`core/events/events.go:78-80`) with no cursor/sequence parameters; gRPC `SubscribeRequest { repeated string filters }` only (`api/services/events/v1/events.proto:60-62`).
- **Where the design fails**: `TestDiscardedAfterTime` (`internal/eventq/eventq_test.go:85-103`) explicitly demonstrates that even with the optional `eventq` TTL buffer, late subscribers miss events. The core exchange does not even use `eventq`.
- **Where to look for the pattern**: Minimal `Envelope{ts,ns,topic,Any}` (`api/types/event.proto:27-33`) with protobuf `Any` for payload evolution.
- **Where to look for the antipattern**: `log.Warn(...); continue` on `UnmarshalAny` failure (`cri/server/events/events.go:92-94`, `events.go:48-50`) — silent event loss on type-URL mismatch.
- **Why the rating**: Typed envelope and topic validation exist with tests, but no sequence/cursor, no durable ordering, no gap-free resume, no causation, and no schema-version contract.

### dagster (7/10)

- **Approach**: Per-run SQL journal `event_logs(id autoincrement)` + serialized `DagsterEvent` payload; opaque `EventLogCursor(STORAGE_ID|OFFSET)`; pluggable watchers.
- **Strongest evidence of the chosen model**: `get_records_for_run(run_id, cursor, of_type, limit, ascending)` with `WHERE id > cursor.storage_id ORDER BY id ASC` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:469-473`) and `EventLogCursor.from_storage_id(id)` (`python_modules/dagster/dagster/_core/event_api.py:62-63`).
- **Where the design fails**: Cross-run global order on sharded SQLite (`SqliteEventLogStorage`) degrades to timestamp + fan-out via `RunShardedEventsCursor` (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:332-413`); non-asset events are not mirrored to the index shard.
- **Where to look for the pattern**: `@whitelist_for_serdes(old_storage_names, old_fields, storage_field_names, field_serializers, skip_when_none_fields)` (`python_modules/dagster/dagster/_core/events/log.py:21-29`) and `DagsterEventSerializer.before_unpack -> _handle_back_compat` (`python_modules/dagster/dagster/_core/events/__init__.py:413-447, 2221-2278`) — the codified serdes contract.
- **Where to look for the antipattern**: `handle_unpack_error -> ENGINE_EVENT` degradation (`python_modules/dagster/dagster/_core/events/__init__.py:423-447`) — graceful but loses semantic information silently.
- **Why the rating**: Typed envelope, per-run ordering, cursor-stable resume, and explicit backcompat shims; deducted for conditional global ordering, no first-class causation, no producer-side idempotency.

### temporal (8/10)

- **Approach**: Per-workflow append-only `HistoryEvent` journal on shard-owned mutable state; `EventId` + `Version` + `VersionedTransition`; opaque `HistoryContinuation` token; pull+push (`WaitNewEvent` long-poll).
- **Strongest evidence of the chosen model**: `EventStore.AllocateEventID` increments `nextEventID` in shard-owned mutable state (`service/history/historybuilder/event_store.go:58-66`); `AppendHistoryNodesRequest{PrevTransactionID, TransactionID}` with "larger wins" tie-break (`common/persistence/data_interfaces.go:776-792`); public `GetWorkflowExecutionHistory(WaitNewEvent=true)` re-reads mutable state before returning (`service/history/api/get_workflow_util.go:128-260`).
- **Where the design fails**: `Notifier` channel size 1 with silent drop-on-overflow (`service/history/events/notifier.go:120, 191-197`) — the long-poll re-read masks it but pure notification consumers are exposed.
- **Where to look for the pattern**: `EventStore.wireEventIDs` (`service/history/historybuilder/event_store.go:381-454`) — typed-pointer causation wired at flush time. `FixFollowEvents` (`service/history/api/get_history_util.go:554-638`) — read-time rewrite for old SDKs.
- **Where to look for the antipattern**: `HistoryContinuation` mixes event cursor and storage cursor in one opaque blob (`api/token/v1/message.pb.go:30-42`) — couples client to server-versioned payload; `ErrInvalidNextPageToken` (`service/history/api/getworkflowexecutionhistory/api.go:232-239`) is the migration hazard.
- **Why the rating**: Two-tier identity, transactional append, branch tokens, gap-fill on pagination, read-time backcompat — the strongest envelope in the study. Deducted for the notifier sharp edge and missing generic causation field.

## Open Questions

These questions persist after reading all four per-source reports. Some have negative-evidence answers (we searched and did not find); others genuinely require input from the source maintainers.

1. **Should the event envelope carry a generic `causationId`/`correlationId`?** All four sources deliberately avoid it. Is this universally correct, or does it only hold for single-system control planes?
2. **What is the right retention policy for a durable event log?** Dagster has `delete_events`/`wipe` but no TTL. Temporal is configurable. BuildKit uses lease-based GC. Containerd has no log. Without a documented policy, long-lived daemons grow unbounded.
3. **Can `OFFSET`-style cursors ever be safe?** Dagster's `STORAGE_ID` cursor is the safer pattern, but the `OFFSET` cursor exists for backward compatibility. Is there a class of consumer that genuinely needs `OFFSET` (e.g., pagination UIs) where `STORAGE_ID` is overkill?
4. **What is the right answer when the consumer is too slow to keep up?** Containerd's unbounded `list.List` is unsafe; BuildKit's goroutine spam is unsafe; Temporal's silent drop is unsafe without re-read. Is there a bounded-buffer-with-overflow-signal pattern that works?
5. **Should schema evolution be codified at the type level (Dagster) or at the wire level (protobuf additive)?** Both sources succeed with their choice. What is the threshold where one becomes more maintainable than the other?
6. **Is cross-cluster event ordering a fundamental requirement?** Temporal's `VersionedTransition` is built for it; the other three are single-process. Does a multi-cluster failover story justify the complexity?
7. **Can `HistoryContinuation`-style opaque tokens survive server upgrades?** Temporal returns `ErrInvalidNextPageToken` on bad tokens. Is there a documented migration path for old cursors after a storage layout change?
8. **What is the right semantics for "delete" on a durable event log?** BuildKit's `Queue.delete` defers `DELETED` emission until the listener unsubscribes (`solver/llbsolver/history/buildhistory.go:241-266`). Dagster has `delete_events` but no equivalent notification. Temporal tombstone semantics on history are unclear from the analyzed code.
9. **Should producer-side idempotency be a hard requirement?** Dagster's `store_event` always allocates a new autoincrement id; BuildKit and Containerd have no producer-side dedupe. Is the consumer-side `seen_storage_ids` pattern (Dagster's executor) sufficient, or should producers carry idempotency keys?
10. **Are batched events (Dagster's `DagsterEventBatchMetadata`) ordered within a batch?** Dagster's analysis notes that `is_end` does not participate in ordering queries. Is intra-batch ordering a real requirement for batched materializations?
