## Executive Summary

All four systems split events into at least two durability tiers, but only one does it well. Temporal (8/10) makes the split explicit — durable history nodes and task queues committed inside the shard transaction before any fan-out, plus lossy notification tiers that drop/coalesce with counters and force waiters to re-read authoritative state. BuildKit (5/10) has a real two-tier design (lossy in-memory progress + durable bbolt/content-store history) but leaks on both ends: unbounded replay buffers in memory and post-hoc rather than transactional durability. Dagster (5/10) inverts the tradeoff: every event is synchronously written to SQL (durable by default) but the write blocks the execution hot path, subscriber fan-out is synchronous with no isolation, and retention is manual-only. containerd (4/10) has no durable event tier at all — the core `Exchange` bus is ephemeral broadcast with unbounded per-subscriber queues, while durability lives in BoltDB rows and shim state, not in envelopes.

The convergent lesson: never let a slow UI stall execution — all four achieve that for the primary path — but they pay for it differently (memory growth in three systems, explicit drop counters only in Temporal and one containerd corner). The divergent lesson: what counts as "must never drop" and where the bound lives (byte caps, count caps, TTLs, or nothing) is a direct function of product shape: build reproducibility (BuildKit), container lifecycle broadcast (containerd), data-pipeline auditability (Dagster), workflow determinism under scale (Temporal).

Stress probe answer (never-reading subscriber under flood): in BuildKit daemon RSS and goroutine count grow while the build completes and history still commits via a separate drain; in containerd the dead subscriber's `Queue` list grows until OOM while Bolt facts survive but envelopes are unrecoverable; in Dagster the GraphQL `asyncio.Queue` grows without bound while DB writes continue; in Temporal the 1000-slot ingress fills, drops are counted, the parked subscriber holds one stale wakeup, and durable history, queue tasks, and retention timers remain intact. Only Temporal degrades to a counter.

## Core Thesis

Durable lifecycle facts must be committed before notification, and notifications must be allowed to drop with accounting — Temporal proves the model; the other three each violate one half (BuildKit commits after, Dagster blocks on commit, containerd never commits events at all). The practical corollary: bound every buffer explicitly (bytes, count, or time), make the drop policy visible (counter + log + resync signal), and give slow consumers a replay path (cursor, backlog window, or authoritative re-read) instead of unbounded memory.

## Approach Models

Three approach clusters emerge:

**1. Durable-first with lossy notification (temporal — mature).**
Hot-path writes happen inside the mutable-state transaction through shard-gated `AppendHistoryNodes` before any fan-out. Subscribers never block persistence. Pressure is shed by dropping/coalescing notifications (1000-slot ingress drop, size-1 per-subscriber coalesce, buffered-1 drop-newest), `TrySubmit`-only scheduling, and reject/terminate circuit breakers (`BufferSizeAcceptable`, history size/count forced termination). Retention is a first-class staged protocol: per-namespace retention timers with jitter, 4-stage ordered delete, ref-counted branch pruning, archival-then-delete, with lag/depth gauges throughout.

**2. Split-tier with weak coupling (buildkit, dagster — partial).**
Both separate a hot delivery path from a durable store, but couple them badly in opposite directions. BuildKit's live tier never blocks the producer (lock + dirty-map-set + broadcast) and sheds via ID-collapse, log clip, gRPC chunking, and display throttling — but durability is post-hoc (re-read the live stream at completion into bbolt/content-store), so a crash mid-build loses in-flight truth, and the "non-blocking" guarantee is paid for with unbounded replay RAM. Dagster's durable tier is synchronous (every `handle_new_event` does a blocking SQL INSERT then inline status update then synchronous subscriber loop) — never-lose by default — but log floods exert DB pressure directly on the executing process, one stuck subscriber stalls all later events, and retention is operator-manual (`delete_events`/`wipe`/`purge_ticks`).

**3. Broadcast-only with facts elsewhere (containerd — absent).**
The core `Exchange` bus is fire-and-forget fan-out (synchronous broadcaster → per-subscriber unbounded `Queue` → rendezvous `Channel(0)` → blocking `srv.Send`). No WAL, no replay, no retention, no batching, no drop policy. Durability lives outside the bus (BoltDB rows, shim task state) with commit-then-notify ordering, but publish errors can still fail the RPC (half-coupling). Only peripheral paths have bounds: shim forwarder (2048 slots, 5-retry eviction), CRI `eventq` (5-minute hold, cap-100 chan, drop counter), Windows log writer (explicit discard). The CRI backoff queue is unbounded per ID.

## Pattern Catalog

- **Durable-commit-before-notify.** Problem: notification loss must never imply data loss. Temporal demonstrates it clearly: `transaction_impl.go` notifies only after commit; BuildKit partially (history commit after build, but not transactional); containerd partially (Bolt commit before publish, but publish error still fails RPC); Dagster synchronously (store then fan out inline, which preserves order at the cost of coupling). Copy when lifecycle facts drive other subsystems. Overkill for pure progress deltas. Evidence: temporal `service/history/workflow/transaction_impl.go:678,718`; containerd `core/metadata/images.go:164-175`; dagster `instance/methods/event_methods.py:189-280`; buildkit `solver/llbsolver/history/buildhistory.go:531-551`.
- **ID-keyed coalescing / old-wins wakeup.** Problem: high-frequency status updates overwhelm consumers. BuildKit collapses same-ID writes in a `dirty` map (`util/progress/progress.go:110-174`); Temporal keeps the stale wakeup in a buffered-1 channel and drops the newer one, forcing a full state re-read (`service/history/notification/notifier.go:131-148`). Both work because any single signal triggers a full reload. Copy for status/progress where the latest full state subsumes deltas. Risky for logs where every byte matters — BuildKit correctly mints unique IDs per log chunk so logs do not collapse. Evidence: buildkit `util/progress/progress.go:241-247`, `util/progress/logs/logs.go:137-144`; temporal `service/history/notification/notifier.go:15-25`.
- **Clip-and-tail / chunk-at-bound for byte floods.** Problem: unbounded stdout/stderr explodes messages and storage. BuildKit clips at 2 MiB / 200 KiB/s into a 256 KiB circbuf with an explicit marker and splits gRPC at ~1 MiB; Dagster tiers compute logs to files with 1 MB chunked reads; containerd Windows drops log bytes with no reader rather than blocking the shim. Copy whenever human-facing logs share a channel with control events. Overkill if logs already bypass the event table (Dagster's file tier). Evidence: buildkit `util/progress/logs/logs.go:22-23,62-164`, `client/status.go:66-129`; dagster `storage/compute_log_manager.py:17-18`; containerd `pkg/shim/shim_windows.go:244-271`.
- **Cursor-paginated replay + time-boxed hold.** Problem: slow or late consumers must catch up without loss. Dagster threads a `storage_id` cursor through storage, watchers, executor tailer, and GraphQL (`event_api.py:20-63`) with 1000-row chunks and backoff; containerd's CRI `eventq` holds 5 minutes for late subscribers then discards with a counter; BuildKit replays full `items`/`sent` prefix on join; Temporal requires re-read on wake/timeout. Copy the cursor/window form; avoid BuildKit's unbounded full-prefix replay (O(events) RAM per job). Evidence: dagster `storage/event_log/polling_event_watcher.py:55-101`; containerd `internal/eventq/eventq.go:53-63,90-130`; buildkit `util/progress/multiwriter.go:34-96`, `util/progress/multireader.go:29-137`.
- **Non-blocking fan-out with drop counter.** Problem: publishers must not stall on subscribers, but drops must be observable. Temporal does `select ch<-v default: metric++` at both ingress and per-subscriber stages; containerd's CRI `eventq` increments `container_events_dropped`; BuildKit and Dagster and containerd-core lack the counter. Copy everywhere a drop is possible — a drop without a counter is indistinguishable from a bug. Evidence: temporal `service/history/events/notifier.go:25,120,180-229`; containerd `internal/cri/server/service.go:236-244`, `internal/cri/server/metrics.go:39`.
- **Per-key admission control + TrySubmit-only scheduling.** Problem: waiter/scheduler fan-out under flood. Temporal caps `maxSubscribersPerKey` (excess gets `ResourceExhausted`), caps time-skipping waiters at 5, and never blocks a scheduler (`TrySubmit` contract, overflow to rescheduler). No other source has an equivalent. Copy for any multi-tenant daemon event router. Evidence: temporal `service/history/notification/notifier.go:83-108,131-148`, `service/history/notification/timeskipping_notifier.go:28-34`, `service/history/queues/scheduler.go:46`, `service/history/queues/reader.go:384-403`.
- **Staged, versioned, jittered retention with ref-counted pruning.** Problem: deleting durable facts without orphaning or resurrecting. Temporal's 4-stage delete (visibility → current pointer → mutable state → history branch, branch last), close-version checks, resurrection guards, full-jitter retention timers, and ref-counted branch delete sparing fork-shared ancestors are the only complete retention story studied. BuildKit has conjunctive count+age GC with lease pinning (good but weaker); Dagster has manual wipe/delete plus tombstone `wipe_timestamp`; containerd has no event retention at all. Copy the ordering and version-check ideas even for simple stores. Evidence: temporal `service/history/shard/context_impl.go:910-935`, `service/history/workflow/task_generator.go:341-367`, `common/persistence/history_manager.go:131-224`; buildkit `solver/llbsolver/history/buildhistory.go:152-198,553-565`; dagster `storage/event_log/sql_event_log.py:644-719,1800-1839`.
- **Sensor→alert→mitigator queue control.** Problem: queue buildup needs closed-loop action, not just metrics. Only Temporal has it: pending/slice/watermark sensors → deduped alerts → shrink/split-and-clear + pause + checkpoint + notify. Copy for any durable task queue; overkill for a pure notification bus where drop-with-counter suffices. Evidence: temporal `service/history/queues/monitor.go:133-153,167-219`, `service/history/queues/mitigator.go:58-93`.
- **Presentation-side throttling.** Problem: UI paint rate need not match event rate. BuildKit rate-limits TUI painting (~100 ms limiter + 150 ms ticker while consuming every message); Dagster backs off polling 0.25 s → 16 s when idle. Copy to keep slow UIs from amplifying floods. Evidence: buildkit `util/progress/progressui/display.go:81-118`; dagster `storage/event_log/polling_event_watcher.py:168-198`.

## Key Differences

- **Where durability lives.** Temporal: inside the event transaction (history nodes + task queues). Dagster: inside the event table (synchronous SQL per event). BuildKit: beside the event stream (post-hoc bbolt + blobs materialized from the live stream). containerd: outside the event bus (Bolt rows + shim state; envelopes never persisted). Consequence: only Temporal and Dagster survive a crash mid-stream without extra work — and Dagster pays per-event latency for it.
- **Whether the hot path blocks.** BuildKit producer never blocks (memory absorbs pressure); Temporal durable append blocks on persistence but never on subscribers (drops absorb pressure); Dagster blocks on both persistence and inline subscribers (neither absorbs — the emitter stalls); containerd core publisher appends fast but metadata RPCs run publish inline (latency coupling) and shim publish blocks up to 5 s per forward.
- **Drop policy explicitness.** Temporal: explicit everywhere (ingress drop, per-subscriber coalesce, drop-newest, waiter caps) with counters/gauges. containerd CRI/shim: explicit in two corners (5-minute discard + counter; 2048/5-retry eviction). BuildKit: explicit for logs (clip-and-tail) and message size (1 MiB split) but implicit elsewhere (ID-collapse is the only policy; replay buffers never drop). Dagster: exactly one filter (`should_store_event` for asset-failure events); no sampling/coalescing/throttling.
- **Replay story.** Dagster: full cursor replay from SQL (strongest for late joiners, costs threads + SELECTs). containerd CRI: 5-minute window replay (bounded, counted). BuildKit: full in-memory prefix replay (works but unbounded). Temporal: no notification replay — re-read authoritative state instead (cheapest, requires version discipline). containerd core: no replay at all.
- **Retention trigger.** Temporal: automatic (retention timer + archival chain + branch GC). BuildKit: automatic but conjunctive (count AND age, every 120 s, pinned exempt). Dagster: manual only (`delete_events`/`wipe`/`purge_ticks`; asset wipe is a tombstone). containerd events: none (only shim/CRI buffer bounds).
- **Why the divergence is valid.** BuildKit optimizes build liveness and late-attach UX over crash-durability (a build is reproducible; losing in-flight progress is tolerable, losing the history record is not). containerd optimizes broadcast fan-out latency for low-volume lifecycle transitions (no high-volume log tier on the bus at all). Dagster optimizes auditability (every pipeline event queryable in SQL) over write throughput. Temporal optimizes workflow determinism at scale (history is the state machine; everything else is a hint). Judged against their own constraints, each choice is coherent; judged as a reusable daemon-events design, only Temporal generalizes.

## Tradeoffs

- **Producer-never-blocks vs. memory safety.** BuildKit, containerd-core, and Dagster-live all isolate execution from slow consumers with unbounded buffers — a stall becomes an OOM. Temporal inverts it with bounded buffers + drop + counter. Benefit of unbounded: zero slow-path logic, trivial late-join replay. Cost: the exact failure in the dimension probe. Best fit: unbounded only when event volume × retention window is provably small; otherwise bound + count.
- **Synchronous durability vs. hot-path latency.** Dagster (per-event SQL) and Temporal (per-transaction append) never lose lifecycle; BuildKit (post-hoc materialization) and containerd (best-effort notify) can. Benefit of sync: crash safety and simple reasoning. Cost: DB/persistence pressure on chatty steps; Dagster's SQLite WAL contention and per-event Postgres round-trips are the clearest example. Alternative: Temporal's buffered-vs-immediate event classes (command/state-change bypass the buffer; markers buffer to WFT boundary) — durability without paying for every byte synchronously.
- **Post-hoc materialization vs. WAL.** BuildKit avoids write amplification by re-reading the live stream at completion; cost is the crash-before-commit window and a 300 s drain timeout. Temporal pays the WAL cost on every append; benefit is no window at all.
- **Drop-newest (old-wins) vs. drop-oldest.** Temporal keeps the stale wakeup (one re-read covers all missed versions — cheap when wakeups are hints). BuildKit/Dagster-live effectively keep everything (no drop). Drop-oldest would give a stalled subscriber the freshest hint but costs a sequence number to be useful — none of the sources have notification sequence numbers.
- **Reject/terminate vs. shed.** Temporal's buffered-event caps and history size/count limits protect storage by failing transactions or killing workflows — safe but user-visible. BuildKit's log clip and containerd-Windows log drop shed silently with only a marker/log line — invisible but non-fatal. Choose reject for correctness-critical tiers, shed for byte-volume tiers, and never confuse the two.
- **Commit-then-notify coupling.** containerd returns publish errors from mutating RPCs even though the Bolt row is already committed — callers cannot distinguish committed-without-notified from failed. Dagster re-raises system-event write failures to fail the step (fail-closed) but swallows user-log failures with a compensating engine event (fail-open) — the better-articulated version of the same tradeoff.
- **Batching reduces round-trips, not coupling.** Dagster's opt-in batching and BuildKit's 1 MiB gRPC split both reduce per-event overhead while keeping the emitter blocked at flush/send time. Temporal's `TrySubmit` + rescheduler is the only mechanism that actually decouples.

## Decision Guide

- **If lifecycle facts drive other subsystems (schedulers, stats, run status, workflow state): commit them transactionally before fan-out, then notify lossily.** Follow Temporal: durable append inside the transaction, post-commit non-blocking fan-out, waiter re-reads on wake. Do not follow containerd-core (no durability) or BuildKit (post-hoc) for this class.
- **If the volume is human-facing progress/logs/output deltas: coalesce by ID, clip bytes with a tail marker, chunk messages at a byte bound, throttle presentation.** Follow BuildKit's four-part combination. Tier bulk bytes out of the event table entirely (Dagster compute-log files).
- **If slow consumers must not lose data: give them a cursor or time window, not unbounded memory.** Follow Dagster's storage-id cursor (full replay) or containerd CRI's 5-minute hold (bounded replay) depending on scale. Never follow unbounded prefix replay (BuildKit `sent`/`items`, containerd `Queue` list, Dagster `asyncio.Queue`) without a cap.
- **If you must drop: drop with a counter, a log, and a resync signal.** Follow Temporal (`FailDeliveryCount` + gauges) and CRI (`container_events_dropped`). A drop without observability is a bug report waiting to happen.
- **If retention matters: make it automatic, ordered, version-checked, and jittered.** Follow Temporal's timer + 4-stage delete + version guard; at minimum BuildKit's count+age GC with pinning. Do not ship manual-only retention (Dagster, containerd) unless an operator-owned sweeper is part of the deliverable.
- **If subscribers are in-process callbacks: put them behind a bounded queue with per-subscriber lag accounting.** None of the sources except Temporal's notifiers do this; Dagster's inline `for sub: sub(event)` and BuildKit's synchronous fan-out under one mutex are the cautionary examples.

## Practical Tips

- Copy: `select ch<-v default: counter++` at every fan-out stage; storage-id or version cursors threaded through every consumer; byte caps on log paths with explicit truncation markers; message-size chunking on RPC bridges; presentation throttling separate from ingestion; per-namespace retention with jitter; delete ordering that removes the history branch last; tombstones over row deletion for asset-like entities only if readers filter on them.
- Delay: full sensor→alert→mitigator queue control until you run a durable task queue at scale; ref-counted branch pruning until you have fork/shared history; batching until per-event round-trips are measured (Dagster's default-off batching is the right posture).
- Watch for: `dirty`/`sent`/`items`-style append-only replay logs with no prune on `Close`; goroutine-per-send or thread-per-watched-run with no pool cap; `put_nowait` into unbounded queues; commit-then-return-publish-error RPC signatures; `delete_run`-without-`delete_events`/`delete_logs` partial-cleanup APIs; read caps (1000/10000 rows, 1 MB chunks) mistaken for write bounds.

## Anti-Patterns / Caution Signs

- **Unbounded per-subscriber queue as backpressure policy.** containerd core `Queue` list, BuildKit `MultiWriter.items` + `MultiReader.sent`, Dagster GraphQL `asyncio.Queue`, containerd CRI backoff `events []any` — all convert a slow consumer into daemon memory growth with no counter. Brittle signal: RSS climbs while throughput is flat.
- **Goroutine/thread-per-event-per-subscriber.** BuildKit `pubsub.Send` parking a goroutine per event on a full 32-slot channel; Dagster one polling thread per watched run; containerd shim `queue()` spawning sleeping goroutines on a full 2048 requeue. Brittle signal: goroutine/thread count linear in events.
- **Synchronous in-process fan-out.** Dagster `for sub in ...: sub(event)` with no try/except/timeout/queue; BuildKit `MultiWriter` fan-out under one mutex with O(n) sorted replay; containerd `Broadcaster.run` inline `sink.Write`. One bad subscriber delays all later ones. Brittle signal: p99 store/emit latency tracks the slowest listener.
- **Post-commit publish error failing the RPC.** containerd image/content/snapshot paths. Callers retry a mutation that already committed. Fix: async publish or success-with-warning + document reconcile-via-List.
- **Manual-only retention presented as a retention story.** Dagster `delete_events`/`wipe`/`delete_logs`, containerd nothing. Brittle signal: storage grows with build/run rate × blob size until an operator intervenes; row counts diverge from `wipe_timestamp`-filtered reads.
- **Read bounds mistaken for growth bounds.** Dagster 1000-row watcher chunks, 10000-row read cap, 1 MB log chunks; BuildKit 1 MiB gRPC split and display throttle — none bound total stored or buffered bytes.
- **No lag/depth/drop telemetry on the hottest bus.** BuildKit progress, containerd core `Exchange`, Dagster event log — the dimension's required signals (lag, queue depth, WAL/log growth) exist only in Temporal and the CRI corner. If you cannot graph drops, you cannot operate drops.

## Notable Absences

- **No spill-to-disk or persistent overflow anywhere.** Temporal's 1000-slot notifier drops to a counter; BuildKit's replay buffers grow in RAM; Dagster's batch buffer is crash-volatile; containerd's queues are memory-only. No source demonstrates bounded-memory + durable-overflow.
- **No notification sequence numbers.** Temporal has stale-version ignore but no dropped-count-between-wakeups; BuildKit log clip and 1 MiB split have no offsets; Dagster cursors cover storage but not live-queue drops. Consumers cannot quantify gaps.
- **No compaction for event history.** Only ref-counted branch delete / selective trim (Temporal), conjunctive GC (BuildKit), manual purge (Dagster). No log-compaction-by-key in any source.
- **No sampling policy.** No source samples high-volume non-lifecycle records; the only volume reducers are ID-collapse, byte-clip, filter-at-sink, and presentation throttle.
- **No lag/queue-depth dashboards outside Temporal.** Three of four sources have zero gauges for the signals this dimension names; the sole cross-source counter pattern is CRI's `container_events_dropped`.

## Per-Source Notes

- **buildkit (5/10) — lossy live + post-hoc durable, producer-never-blocks.** Strengths: ID-collapse coalescing, non-blocking hot path, clip-and-tail logs, 1 MiB gRPC chunking, display rate-limiting, lease-pinned bbolt history with conjunctive GC, EOF + synthesized-completion flush. Concerns: unbounded `items`/`sent`/`dirty-for-unique-log-IDs`, goroutine-per-send 32-slot pubsub, no lag/drop metrics, crash-before-`ImportStatus` window. Best idea to steal: the four-layer byte defense (clip + chunk + throttle + tail marker) as a unit.
- **containerd (4/10) — ephemeral broadcast, facts committed elsewhere.** Strengths: CRI `eventq` (5 m hold + cap-100 + drop counter + replay test), shim bounded retry/drop bridging restarts, Windows never-block-logs discard, filter-at-sink. Concerns: core bus unbounded/unobservable/unreplayable; terminal `TaskExit`/`TaskOOM` losable past the retry window; backoff queues unbounded; metadata RPCs fail on publish-after-commit. Best idea to steal: the `eventq` discard-hook-plus-counter shape applied to the core bus.
- **dagster (5/10) — synchronous durable SQL + cursor replay, manual retention.** Strengths: explicit lifecycle taxonomy (`DagsterEventType` + stats-critical subsets), storage-id cursor protocol across all consumers, file-tiered compute logs, batch-fallback-to-single, fail-open user logs / fail-closed system events. Concerns: hot-path blocking writes, inline subscriber fan-out, unbounded GraphQL queue, thread-per-run, no auto retention/TTL, orphaned files on partial delete. Best idea to steal: the cursor protocol + executor tailer self-healing (jump on all-duplicate full page).
- **temporal (8/10) — durable-first with lossy wakeups and closed-loop queue control.** Strengths: transactional durable append, buffered-vs-immediate event classes, non-blocking fan-out with counters at two stages, old-wins coalescing + waiter caps + `TrySubmit`-only scheduling, decay-scaled reader quotas, jittered versioned 4-stage retention, ref-counted branch pruning, full lag/depth gauge set. Concerns: counter-only drops with no replay sequence, eventual retention consistency across clusters, reject/terminate failure mode is user-visible, unbuffered internal handoff mitigated by goroutine-spawned retry. Best idea to steal: the whole durable-first/notify-after-commit + drop-with-counter + re-read contract as a unit.
