## Executive Summary

No source achieves a single-transaction `state + durable event` commit. All four keep authoritative current-state and operational journal separate and commit them sequentially, deliberately avoiding full event sourcing. Injecting a crash between the two durable writes yields an observable inconsistency in every system — just via different window and recovery story. BuildKit (3/10) is absent by design: authoritative solver state is RAM-only (`sources/buildkit/solver/jobs.go:42-44`), history is a post-facto sidecar. Containerd (5/10) has the strongest single-store transaction discipline (short `bolt.Tx` via `sources/containerd/core/metadata/bolt.go:30`, dirty/GC fencing) but explicitly forbids publishing inside it (`sources/containerd/core/metadata/db.go:288` returns `nil` Publisher) and publishes best-effort after commit. Dagster (4/10) splits further — default SQLite runs `runs.db` and per-run `history/runs/<run_id>.db` are distinct files/engines (`python_modules/dagster/dagster/_core/storage/sqlite_storage.py:60-64`), so a two-DB `store_event` then `handle_run_event` saga (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:248-257`) can commit one without the other. Temporal (7/10) is closest: it durably appends both `executions` and `history_node` and guards every workflow write with optimistic `DBRecordVersion` + shard `RangeID` fencing (`sources/temporal/common/persistence/sql/execution_util.go:628-665`), yet history is appended **before** the shard transaction (`sources/temporal/common/persistence/sql/execution.go:64-77`), leaving an orphan branch on crash that requires `trimHistoryNode` (`sources/temporal/common/persistence/execution_manager.go:262-273`). Short bounded transactions and explicit migrations exist everywhere (bbolt `Transactor`, SQLAlchemy `with conn.begin()`, `txExecuteShardLocked`); shared-transaction journaling and revision CAS exist only in Temporal.

## Core Thesis

Atomic `state + event` is not a by-product of "good transactions" — it requires **co-ownership of one transaction/connection by the state mutation and the event append, plus an optimistic revision that rejects stale writers**. Short `bolt.Tx`/`conn.begin()` alone gives intra-object atomicity (BuildKit `b.Put + AddResource` in one `DB.Update` at `sources/buildkit/solver/llbsolver/history/buildhistory.go:418-487`, containerd `Create + AddResource` at `sources/containerd/core/metadata/images.go:140`, Dagster `run_tags`+`runs` at `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:224-248`) but says nothing about cross-boundary atomicity. Without that co-ownership every system chooses the same window — state commit then event publish (or event then state in Temporal/Dagster) — and compensates differently: BuildKit with `clearOrphans` scan and 5-min temporary leases (`sources/buildkit/solver/llbsolver/history/buildhistory.go:200-239`, `sources/buildkit/util/leaseutil/manager.go:83-88`), containerd with lossy `goevents.Broadcaster` (`sources/containerd/core/events/exchange/exchange.go:36`) and async GC publish (`sources/containerd/core/metadata/db.go:441`), Dagster with nothing (stale `run_body` fixup at `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:264-266`), Temporal with versioned trim (`sources/temporal/common/persistence/history_manager.go:213-309`). The reason for divergence is product shape: single-daemon/single-node systems (BuildKit `flock` at `sources/buildkit/cmd/buildkitd/main.go:386-397`, containerd `meta.db` at `sources/containerd/plugins/metadata/plugin.go:169-184`) optimize for bounded write latency and cache reuse, accepting audit-only events; Temporal is a multi-host orchestrator that must linearize workflows across shards, so it pays LWT/CAS cost and adds compensating deletion.

## Approach Models

Three archetypes emerged; they are not a quality ladder but responses to different durability, scale, and recovery constraints.

**Model A — Ephemeral fan-out after commit (buildkit, containerd).**
Both treat the bolt/bbolt file as sole source of truth (`sources/buildkit/util/db/transactor.go:7-11`, `sources/containerd/core/metadata/db.go:42`), keep the event system as in-memory pubsub (`sources/buildkit/solver/llbsolver/history/pubsub.go:5-28` buffered 32, `sources/containerd/core/events/exchange/exchange.go:36` `goevents.Broadcaster`), and **intentionally forbid** publishing inside the transaction. Containerd enforces the guard (`sources/containerd/core/metadata/db.go:289` comment "Do not publish events within a transaction"); BuildKit enforces it by structure — STARTED does `h.active[id]=record; ps.Send(e)` with no DB write at `sources/buildkit/solver/llbsolver/history/buildhistory.go:538-541`, COMPLETE does `ps.Send` after `h.update()` commits at `sources/buildkit/solver/llbsolver/history/buildhistory.go:544-548`. Writer contention is bounded by single-writer `flock`/`wlock` (`sources/buildkit/cmd/buildkitd/main.go:386-397`, `sources/containerd/core/metadata/db.go:89`). Suitable when late subscribers can replay by rescanning current state (`Listen` DB scan at `sources/buildkit/solver/llbsolver/history/buildhistory.go:770-887`, Exchange has no replay) and exactly-once delivery is not required.

**Model B — Sharded relational saga (dagster).**
Authoritative current-state (`RunsTable` at `python_modules/dagster/dagster/_core/storage/runs/schema.py:8-48`) and journal (`SqlEventLogStorageTable` at `python_modules/dagster/dagster/_core/storage/event_log/schema.py:8-24`) are separate SQLAlchemy `MetaData`/Alembic trees and, on default SQLite, separate engines/files (`python_modules/dagster/dagster/_core/storage/sqlite_storage.py:28-66` three storages). Event append writes to `run_connection(run_id)` then mirrors into `index` shard via `index_transaction()` (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:260-303`) — 2-3 transactions per call — before the orchestrator updates run status in a *different* DB (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:230-257`). Asset keys are a derived secondary index rebuildable by `reindex_events` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:621-632`). Transactions are short/bounded (`with conn.begin()` everywhere) and WAL+tuning helps, but co-atomic commit is structurally impossible without 2PC. Suitable when per-run write isolation and simple tailing/watch (`history/runs/*.db` watchdog at `python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:492-508`) matter more than cross-run linearizability.

**Model C — Sequential durable dual-write with compensating trim (temporal).**
Both history (`history_node`/`history_tree` via `sources/temporal/common/persistence/sql/history_store.go:23-109`) and mutable state (`executions` + maps at `sources/temporal/common/persistence/sql/execution.go:211-332`) are durable and external, routed through `ExecutionManager` → `ExecutionStore` (`sources/temporal/common/persistence/data_interfaces.go:1126-1138`, `sources/temporal/common/persistence/persistence_interface.go:116-167`). Every transition builds `WorkflowSnapshot`/`WorkflowMutation` + `WorkflowEvents` into `InternalAppendHistoryNodesRequest` (`sources/temporal/common/persistence/execution_manager.go:114-154`, `sources/temporal/service/history/workflow/transaction_impl.go:53-94`), but persists them sequentially: `AppendHistoryNodes` outside any shard tx, then `txExecuteShardLocked` for state (`sources/temporal/common/persistence/sql/execution.go:60-78`, `sources/temporal/common/persistence/cassandra/execution_store.go:97-108`). Stale writers are rejected inside the shard tx by `DBRecordVersion`/`NextEventID` CAS (`sources/temporal/common/persistence/sql/execution_util.go:628-665`) and `RangeID` fencing (`sources/temporal/common/persistence/sql/shard.go:152-174`). Crash between steps leaves an orphan branch, cleaned by `trimHistoryNode` → `TrimHistoryBranch` (`sources/temporal/common/persistence/history_manager.go:213-309`). Suitable when you need workflow linearizability across shards/hosts and can tolerate a best-effort compensating delete instead of a single co-atomic commit.

## Pattern Catalog

### 1. Single-bucket atomic bundle (co-commit lease + record + links)

*Problem:* Prevent torn state where a record exists without its GC lease/content references.
*Sources:* buildkit `history.Queue.update` single `DB.Update` that does `Create/leaseID` → `AddResource(Logs,Trace,…)` → `b.Put` (`sources/buildkit/solver/llbsolver/history/buildhistory.go:418-487`); `bboltcachestorage.AddResult` writes `_links+_result+_byresult` at `sources/buildkit/solver/bboltcachestorage/storage.go:144-172`; containerd `addImageLease` inside same `Update` as image create (`sources/containerd/core/metadata/images.go:140` + lease linkage `sources/containerd/core/metadata/leases.go:38`); dagster `handle_run_event` `RunTagsTable` before `RunsTable` inside one `connect()` for Postgres AUTOCOMMIT safety (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:224-248`).
*Why it works:* Bolt/DB transaction is the fence; lease GC will not collect referenced blobs while `dirty`/`dirtyCS` flags are set.
*When to copy:* Always — this is the minimum atomicity that exists in all four and is worth preserving even if you never add cross-boundary atomicity.
*When overkill:* Never; cost is just batching calls before commit.
*Evidence:* BuildKit success + Containerd `core/metadata/gc.go:495-1034` four-phase GC that assumes lease links are co-committed.

### 2. Transaction reuse via context-bound `Tx` (composable writes)

*Problem:* Batch lease + object + tag writes without nested-transaction support from bbolt/SQLAlchemy.
*Sources:* containerd `boltutil.WithTransaction`/`Transaction` context key reused by `view`/`update` (`sources/containerd/core/metadata/boltutil/context.go:25-31`, `sources/containerd/core/metadata/bolt.go:30-51`) called from `containers.go:63`, `images.go:58`, `content.go:79`, `snapshot.go:88`; dagster `run_connection()`/`index_connection()`/`index_transaction()` helper that yields ongoing `conn` if `conn.in_transaction()` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:156-177`).
*Why it works:* Lets `withStore`/`withStoreUpdate` at `sources/containerd/plugins/services/containers/local.go:207` call `Store.Create` inside caller's tx.
*When to copy:* When your storage layer is a single DB engine and you need multi-repo operations in one atomic batch.
*When risky:* If you carry the pattern to multi-engine deployments (Dagster SQLite shards) — the context reuse crosses engine boundaries and silently becomes non-atomic; prefer explicit outbox there.
*Evidence:* Pattern absent in BuildKit/Temporal where callers hold the `bolt.Tx` or shard tx directly.

### 3. Content-then-record split with temporary lease (hold-free I/O)

*Problem:* Avoid holding the global bbolt write lock during slow blob ingest.
*Sources:* BuildKit `OpenBlobWriter` creates 5-min temporary lease then `content.OpenWriter` at `sources/buildkit/solver/llbsolver/history/buildhistory.go:567-635`; `Writer.Commit` commits blob before `update()` re-parents it to persistent `ref_<Ref>` lease (`sources/buildkit/solver/llbsolver/history/buildhistory.go:679-768`). Containerd `namespacedWriter.Commit` does `fp.Sync()` outside `l.RLock` + `update` at `sources/containerd/core/metadata/content.go:582-592`. Temporal's `AppendHistoryNodes` before shard tx is the same motivation.
*Why it works:* Keeps the hot-path tx short; GC expiry (5 min, `sources/buildkit/util/leaseutil/manager.go:83-88`; 24h ingest `sources/containerd/core/metadata/content.go:458`) is the compensating lease.
*When to copy:* When payload is large or sink is external (content store, history blobs).
*Cost:* Two-phase window requires compensating `clearOrphans` (`sources/buildkit/solver/llbsolver/history/buildhistory.go:200-239`) or `trimHistoryNode`.

### 4. Compensating orphan trim / reaper

*Problem:* Reconcile the two-phase window after crash.
*Sources:* BuildKit `clearOrphans` startup scan deleting `_records` with empty `ListResources(leaseID)` (`sources/buildkit/solver/llbsolver/history/buildhistory.go:200-239`); Temporal `trimHistoryNode` catching `ConditionFailedError` and `TrimHistoryBranch` validating `node_id`/`txn_id` chain (`sources/temporal/common/persistence/execution_manager.go:262-273`, `sources/temporal/common/persistence/history_manager.go:213-309`, `sources/temporal/common/persistence/history_manager.go:286-305`).
*Why it works:* Durable state is correct; orphan history is detectable via CAS failure or lease emptiness.
*When to copy:* If you keep sequential durable writes — a reaper is mandatory, not optional.
*When overkill/risky:* Periodic O(n) scans (`buildhistory.go:214` per-record `ListResources`, `history_manager.go:296-306` sequential deletes) tail-latency cost; best-effort logging (`sources/temporal/common/persistence/execution_manager.go:1103-1138` swallows error) can leave orphans until next conflict.
*Evidence:* Containerd/Dagster lack a reaper for the state↔event window — they just accept loss.

### 5. Bounded short transactions + explicit migrations + WAL tuning

*Problem:* Keep writer latency predictable without a daemon-local WAL.
*Sources:* All four. Bbolt `NoFreelistSync`/`NoSync`/`NoStatistics` flags (`sources/containerd/plugins/metadata/plugin.go:132-161`, `sources/buildkit/solver/bboltcachestorage/storage.go:28-31`); Dagster `PRAGMA journal_mode=WAL` + 30s `busy_timeout` + `NullPool` (`python_modules/dagster/dagster/_core/storage/sqlite.py:8-15`); Temporal `txExecute` single `BEGIN/COMMIT` per transition (`sources/temporal/common/persistence/sql/common.go:52-81`), `transactionSizeLimit` (`sources/temporal/common/persistence/history_manager.go:367-374`); migrations (`sources/containerd/core/metadata/migrations.go:42`, `sources/temporal/schema/mysql/v8/version.go:1-30`, `python_modules/dagster/dagster/_core/storage/sql.py:30-68`).
*Why it works:* Short tx avoids holding locks over I/O; WAL/tuning reduces contention without changing consistency model.
*When to copy:* Default posture; choose durability flag per DB (`cache.db` `NoSync:true` vs `history.db` synchronous at `sources/buildkit/solver/bboltcachestorage/storage.go:28`).
*Tradeoff:* `NoSync` widens crash window for both state and already-published events.

### 6. Optimistic revision / CAS (only mature in Temporal)

*Problem:* Reject stale writes without distributed lock.
*Sources:* Temporal `DBRecordVersion` (`IF db_record_version = ?` at `sources/temporal/common/persistence/cassandra/mutable_state_store.go:90-123`) + fallback `Condition/NextEventID` (`sources/temporal/common/persistence/sql/execution_util.go:628-665`), shard `RangeID` (`sources/temporal/common/persistence/sql/shard.go:124-149`, `sources/temporal/common/persistence/cassandra/mutable_state_store.go:453-463`), `current_executions` CAS (`sources/temporal/common/persistence/sql/execution_util.go:604-627`). BuildKit/Containerd/Dagster have no check: `Generation++` at `sources/buildkit/solver/llbsolver/history/buildhistory.go:335` with unconditional `b.Put`, `UpdatedAt=Now()` at `sources/containerd/core/metadata/containers.go:174-270`, `WHERE run_id==...` without `AND version` at `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:250-259`.
*Why it works:* Check is inside the same tx/batch as the mutation; failure surfaces `WorkflowConditionFailedError`/`ShardOwnershipLostError`.
*When to copy:* Any concurrent writer beyond single-daemon `flock`.
*When overkill:* Single-daemon `flock` (`sources/buildkit/cmd/buildkitd/main.go:386-397`) — adds version plumbing for no benefit, but mark the field as decorative if you keep it.

### 7. Status column over serialized body / field-mask guard (weaker revision analogues)

*Problem:* Tolerate lost-update without rejecting it.
*Sources:* Dagster `_row_to_run` trusts `status` column over `run_body.status` after clobber (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:261-267`); containerd field-mask whitelists (`sources/containerd/core/metadata/containers.go:230`, `sources/containerd/core/metadata/images.go:209`).
*Why semi-works:* Preserves at least one authoritative column; partial update reduces blast radius.
*When to copy:* As defense-in-depth alongside CAS, not as replacement — it still last-write-wins.
*Evidence:* Temporal discarded this half-measure and kept full CAS; its `historySizeRollback` (`sources/temporal/common/persistence/execution_manager.go:70-102`) shows even metrics mutation is fenced.

## Key Differences

**What converges despite different stacks (Go bbolt, Go Cassandra/SQL, Python SQLAlchemy):**
* Transactions are short/bounded by convention — no tx spans RPC streams or blob I/O. BuildKit bounds each `DB.Update` to small JSON (`sources/buildkit/solver/bboltcachestorage/storage.go:144`), containerd caps to one bucket + lease link (`sources/buildkit/solver/bboltcachestorage/storage.go:37-43` analogue), Dagster uses `with conn.begin()` per method, Temporal enforces `transactionSizeLimit` (`sources/temporal/common/persistence/history_manager.go:367-374`).
* Event journal is audit/observation — never sole source of truth for liveness. Solver graph at `sources/buildkit/solver/jobs.go:42`, containerd `meta.db` at `sources/containerd/core/metadata/db.go:42`, Dagster `RunsTable` at `python_modules/dagster/dagster/_core/storage/runs/schema.py:8-48`, Temporal `executions` at `sources/temporal/common/persistence/sql/execution.go:211-332` — all read via `view`/`Get`, not replay.
* No co-ownership of `Tx`/connection across state+event. Every system publishes outside the mutation (containerd guard at `sources/containerd/core/metadata/db.go:289`, BuildKit `ps.Send` after commit at `sources/buildkit/solver/llbsolver/history/buildhistory.go:544-548`, Dagster `store_event` then `handle_run_event`, Temporal history before shard tx).

**Why sources diverge:**
* **Deployment constraint → durability delegation.** BuildKit/containerd are single-host daemons (`flock` at `sources/buildkit/cmd/buildkitd/main.go:386-397`, `bolt.Open` with `Timeout=0` at `sources/containerd/plugins/metadata/plugin.go:132-184`). Daemon-local bbolt with `NoSync` is acceptable; external WAL is not needed. Temporal/Dagster delegate to external Postgres/MySQL/Cassandra or SQLite WAL (`python_modules/dagster/dagster/_core/storage/sqlite.py:8-15`, `sources/temporal/common/persistence/sql/sqlplugin/sqlite/plugin.go:92-116`). Hence BuildKit can afford `NoSync:true` on `cache.db` (`sources/buildkit/solver/bboltcachestorage/storage.go:28`) with `fallbackOpen` reset (`sources/buildkit/util/db/boltutil/safe_open.go:17-48`) — history loss is tolerable — while Temporal must keep `NoSync:false` for `history_node`.
* **Scale constraint → sharding.** Dagster shards per-run (`SqliteEventLogStorage` `history/runs/*.db` + `index.db` at `python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:174-179`) to avoid cross-run contention; Temporal shards workflows (`RangeID` at `sources/temporal/common/persistence/data_interfaces.go:148-195`). Both pay with sequential cross-shard commits. BuildKit/containerd avoid sharding via single bolt file and accept single-writer serialization (`wlock` at `sources/containerd/core/metadata/db.go:89`, `Metastore.dbL` at `sources/containerd/core/snapshots/storage/metastore.go:69-72`).
* **Consistency requirement → CAS investment.** Temporal is the only multi-host orchestrator that must linearize concurrent workflow tasks, so it implements two-generation CAS (`DBRecordVersion` + `NextEventID`) plus shard fencing. Containerd's single-writer already linearizes via bbolt's writer + `wlock`, so last-write-wins hides the gap. Dagster's comment about `run_body` clobber (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:264-266`) and BuildKit's `Generation++` (`sources/buildkit/solver/llbsolver/history/buildhistory.go:335`) are acknowledgments without enforcement — valid for single-daemon throughput but not for contested writes.
* **Recovery philosophy.** BuildKit prefers `fallbackOpen` corrupt-and-reset (availability over retention); Containerd prefers ephemeral loss (best-effort requeue `sources/containerd/pkg/shim/publisher.go:80-102` max 5×`1s*count`, Exchange unbounded `NewChannel(0)` at `sources/containerd/core/events/exchange/exchange.go:132`); Dagster relies on daemon heartbeat reconciliation that never retries the missed transition; Temporal invests in versioned trim that is observable only at DEBUG.

## Tradeoffs

**Post-commit publish (all) vs transactional outbox (none).**
*Benefit of current:* Keeps mutation tx short (containerd comment "Do not publish within transaction" at `sources/containerd/core/metadata/db.go:289`, BuildKit `go c.send` to isolate at `sources/buildkit/solver/llbsolver/history/pubsub.go:23-26`, Temporal avoids holding shard lock over blob I/O). Measured outcome: gc `wg.Go(m.publishEvents)` keeps sweep `Update` short (`sources/containerd/core/metadata/db.go:395-441`).
*Cost:* Crash-between-commit-and-publish window with no replay. BuildKit COMPLETE gap (`sources/buildkit/solver/llbsolver/history/buildhistory.go:544-548`), containerd image/content gap (`sources/containerd/core/metadata/images.go:124-172`), Dagster event→status gap (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:231`→`255`), Temporal orphan branch (`sources/temporal/common/persistence/sql/common.go:77-78` vs `sources/temporal/common/persistence/sql/history_store.go:52`).
*Alternative seen:* No source implements outbox `v1/<ns>/outbox/<seq>` append then forwarder; strongest advocate is Temporal's `IsNewBranch` grouping of `history_tree`+`history_node` in one `txExecute` (`sources/temporal/common/persistence/sql/history_store.go:77-108`) — limited to tree creation.

**Pre-commit history append (Temporal) vs state-first (others).**
*Benefit of Temporal ordering:* Blob I/O isolated; state tx never holds lock over large payload; `TransactionSizeLimitError` caught before state mutation (`sources/temporal/common/persistence/history_manager.go:369-373`). *Cost:* Event without state on failure; `trimHistoryNode` reads `GetWorkflowExecution` then `DeleteHistoryNodes` (`sources/temporal/common/persistence/execution_manager.go:1081-1140`), best-effort. *Benefit of state-first (Containerd/Dagster):* No orphan durable event, but observer may see state never — still a gap (`sources/containerd/core/metadata/db.go:348-441` async GC events).

**Throughput over durability toggles.**
*BuildKit* `cache.db` `NoSync:true` vs `history.db` sync; *containerd* `NoSync` configurable (`sources/containerd/plugins/metadata/plugin.go:49-67` crash-loss warning); *Dagster* WAL+NORMAL vs `SQLITE_BUSY_TIMEOUT_SECONDS=30` (`python_modules/dagster/dagster/_core/storage/sqlite.py:15`). All trade torn pages/lost events for 10× write throughput. Temporal avoids the knob by delegating to external store's WAL.

**Last-write-wins vs optimistic CAS.**
*Benefit of LWW:* No `If-Match` plumbing, no `412`/`FailedPrecondition` to surface (`sources/containerd/core/containers/containers.go:93` small API). *Cost:* Silent lost-update on concurrent `UpdateRef` (`sources/buildkit/solver/llbsolver/history/buildhistory.go:335` — Pin vs trace race), `Update` labels (`sources/containerd/core/metadata/containers.go:218-270`), `add_run_tags` vs `handle_run_event` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:264-266`). Temporal shows the CAS path requires error taxonomy (`WorkflowConditionFailedError`/`CurrentWorkflowConditionFailedError` at `sources/temporal/common/persistence/data_interfaces.go:131-148`) and client retry.

**Single-writer lock vs sharded engines.**
*Single bolt* (BuildKit/Containerd) gives one ordered journal and atomic lease linking (`sources/containerd/core/metadata/gc.go:35`) at cost of `wlock` GC pause (`sources/containerd/core/metadata/db.go:383-489` mark+sweep holds `Lock`) and `block forever` `bolt.Open` (`sources/containerd/plugins/metadata/plugin.go:44` `Timeout=0` with 10s warning at `sources/containerd/plugins/metadata/plugin.go:172`). *Sharded SQL* (Dagster per-run DB, Temporal `shards` table) gives per-shard concurrency (`txExecuteShardLocked` `ReadLockShard`) but creates the two-DB impossibility (`runs.db` vs `event_logs`).

## Decision Guide

Use this as a flowchart for a new daemon/service.

*Need single-host, cache-reuse/scheduling throughput, and can call history "UI-only"?*
Choose **Model A** (BuildKit/containerd shape). Keep one authoritative bolt/SQL file, make per-object `Update` atomic (`_links+_result+_byresult` pattern), do post-commit `Publish` via fan-out, document that subscribers re-scan state on reconnect, and accept `NoSync` on cache. If you fork this, copy BuildKit's `b.Put + AddResource` bundle and containerd's context-bound `WithTransaction` reuse — not the ephemeral gap.

*Need per-run isolation and cheap tailing, deployed default on SQLite?*
Choose **Model B** (Dagster shape). Use per-run shards + WAL + 30s timeout and short `with conn.begin()` transactions. **Do not** claim atomicity across DB files. Either (a) co-locate `runs`+`event_logs` on same engine when durable (Postgres/MySQL) and route `handle_new_event` through one `Connection`/`Transaction` (flag `handles_run_events_in_store_event` at `python_modules/dagster/dagster/_core/storage/event_log/base.py:745-748`), or (b) add an outbox bucket in `runs.db` and forwarder that `View`-scans and publishes after commit. Add a `revision`/`update_timestamp` CAS column (`WHERE run_id=:id AND update_timestamp=:expected` at `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:250`) with retry if any concurrent writer exists.

*Need multi-host/multi-shard workflow linearizability?*
Choose **Model C** (Temporal shape). Make every authoritative mutation `txExecuteShardLocked` (SQL) or `LOGGED BATCH` with `IF range_id` + `IF db_record_version` (Cassandra). Serialize history sizing before the tx (`transactionSizeLimit`). Keep history append inside the same tx/batch if payload fits (Temporal's `IsNewBranch` path proves it); if you must split (large blobs), implement `trimHistoryNode` as first-class observable metric, not DEBUG log. Add detached context and `historySizeRollback` guards (`sources/temporal/common/persistence/execution_manager.go:70-102`) to avoid double-count on retry. Surface `WorkflowConditionFailedError` with both `NextEventID` and `DBRecordVersion` so caller refreshes correctly.

*Rule of thumb:* If you can answer "what happens if I kill -9 between the two commits?" with a **concrete inconsistency** (e.g., `instance.logs_after(run_id)` has `PIPELINE_SUCCESS` but `get_run_by_id(status)` still `STARTED`; `history.Status(ref)` `ErrNotExist` while `content.Info` exists; `history_node` orphan beyond `LastFirstEventId`), you have the dimension gap. Fix by either merging the two commits into one `Tx`/`Batch` or by persisting the second commit's intent as an outbox row inside the first tx.

## Practical Tips

**Patterns to copy now:**
- Bundle all bucket/lease/content refs for one logical object in a single `Tx` — wait until blob temp lease exists, then `b.Put` + `AddResource` together (`sources/buildkit/solver/llbsolver/history/buildhistory.go:418-487`, `sources/containerd/core/metadata/images.go:140`).
- Keep mutations short: `with conn.begin(): yield conn` per call, pre-sync outside lock for large content (`sources/containerd/core/metadata/content.go:582-592`).
- Use composeable tx reuse on single engine (`boltutil.Transaction(ctx)` at `sources/containerd/core/metadata/boltutil/context.go:25`) to keep claim-check fluent.
- Enforce size limits before commit (`serializeAppendHistoryNodesRequest` `transactionSizeLimit()` at `sources/temporal/common/persistence/history_manager.go:367-374`) and revert caller-mutated stats on failure (`historySizeRollback` at `sources/temporal/common/persistence/execution_manager.go:70-102`).
- Own migrations explicitly with version rows (`migrations = []migration` at `sources/containerd/core/metadata/migrations.go:42`, `bucketKeyDBVersion` varint at `sources/containerd/core/metadata/db.go:156`, Alembic per storage at `python_modules/dagster/dagster/_core/storage/sql.py:30-68`).

**Patterns to avoid or delay until you need multi-writer:**
- Do not use a transactional outbox as ceremony if you are single-daemon and subscribers can replay via `DB.View` scan — `Listen` DB replay (`sources/buildkit/solver/llbsolver/history/buildhistory.go:823-843`) is an adequate compensating read, but document the gap.
- Do not add `expectedGeneration`/`revision` plumbing unless you will increment, check `WHERE version=?`, and surface `Conflict` to callers — decorative `Generation++` at `sources/buildkit/solver/llbsolver/history/buildhistory.go:335` is worse than none because it suggests safety.
- Do not hold the shard/bolt lock over `AppendHistoryNodes`/blob I/O; split-phase is correct if you implement reaping — just make reaping observable and incremental, not O(n) full scan.

**Caution signs the design is becoming brittle:**
- A `generation`/`revision`/`update_timestamp` column is incremented but never appears in a `WHERE` predicate — exactly `python_modules/dagster/dagster/_core/storage/dagster_run.py:234-352` + `sql_run_storage.py:250-267`.
- `Publisher == nil` inside tx (`sources/containerd/core/metadata/db.go:289`) with no outbox alternative and callers returning publish error despite committed state (`sources/containerd/core/metadata/images.go:172`).
- `clearOrphans` scanning every record with `ListResources` per entry (`sources/buildkit/solver/llbsolver/history/buildhistory.go:214`) or GC `publishEvents` in goroutine with `context.Background()` (`sources/containerd/core/metadata/db.go:348-441`) — reaper that papers over two-phase cost.
- SQLite shards where `run_connection == index_connection` only in `ConsolidatedSqliteEventLogStorage` test-only variant (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/consolidated_sqlite_event_log.py:38-39`, `119-123`) while prod shards diverge.
- `WAL`/`journal_mode` only warned (`sources/temporal/common/persistence/sql/sqlplugin/sqlite/plugin.go:94-109` `Warning` if not WAL) rather than enforced, with `MaxConns=1` collapsing throughput.

## Anti-Patterns / Caution Signs

- **Publish-after-commit with no durable alternative.** Containerd `Exchange` (`sources/containerd/core/events/exchange/exchange.go:36` `broadcaster.Write`) and BuildKit `pubsub[T]` (`sources/buildkit/solver/llbsolver/history/pubsub.go:22` buffered 32, `go c.send` never blocks tx, dropped on `close`) are lossy by design. Crash between `db.Update` return and `Publish` (`sources/containerd/core/metadata/images.go:164` → `Publish`) yields committed-but-unobserved state with no replay except full `View`/`List` rescan.
- **Two DBs, one saga, no 2PC.** Dagster `handle_new_event` holds two independent `connect()` contexts (often two files). The tag-before-status ordering workaround for Postgres AUTOCOMMIT (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:224-248`) only ensures readers see tag if they see status — still torn across DB files. Batch path loops individual `store_event` on generic `Exception` without idempotency (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:183-246`).
- **Corrupt-and-reset as durability policy.** `SafeOpen` → `fallbackOpen` renames corrupted `history.db`/`cache.db` to `*.bak` and opens empty DB (`sources/buildkit/util/db/boltutil/safe_open.go:17-48`). Daemon stays up but audit log is silently wiped — content blobs remain but lose `ref_<Ref>` lease, becoming GC-eligible.
- **Late attach on `context.TODO()`.** BuildKit trace blobs attached via `UpdateRef(ctx context.TODO(), …)` up to 3 s after `COMPLETE` (`sources/buildkit/solver/llbsolver/history.go:285-332`) can silently overwrite `Pinned` at `sources/buildkit/solver/llbsolver/history/buildhistory.go:335-485`; if it fails, temp lease leaks until GC.
- **Backend commit inside metadata tx (hidden coupling).** Containerd `Snapshotter.Commit` inside `db.Update` (`sources/containerd/core/metadata/snapshot.go:639-660` "transaction failed after commit… should be removed") and Temporal `AppendHistoryNodes` outside shard tx are duals — both admit two-resource, one-transaction hazard documented in a comment rather than fixed.
- **Backpressure drop with no retry.** `pubsub.Send` launches goroutine per subscriber and non-blockingly tries `ch <- v` (`sources/buildkit/solver/llbsolver/history/pubsub.go:49-54`); `pkg/shim/publisher.go:59-104` caps requeue at 2048 and evicts after 5 retries — OOM storm can evict task events silently.

## Notable Absences

- **Transactional outbox / durable event bucket.** Zero sources append an outbox row inside the state `Tx` and relay it after commit. Greps for `eventstore`/`Journal`/`outbox`/`WAL` per report found only bolt internal hits, vendor constants, or ephemeral `internal/eventq` with `discardAfter` (`sources/containerd/internal/eventq/eventq.go:56`).
- **Optimistic revision in three sources.** No `revision`/`version`/`ETag` column guarded by `WHERE version = expected` (BuildKit `Generation`, containerd `UpdatedAt`, Dagster `update_timestamp`). Only Temporal has it.
- **Shared-Transaction journaling.** Even where Postgres could co-locate `runs` + `event_logs`, code keeps separate engines/connections (`python_modules/dagster/dagster/_core/storage/sql.py:30-68` per-storage Alembic). Flag `handles_run_events_in_store_event` exists (`python_modules/dagster/dagster/_core/storage/event_log/base.py:745-748`) but is `False` for SQL storages.
- **Bounded journal retention / cursor replay.** Containerd's `Exchange` keeps zero history (`Subscribe` builds fresh `goevents.NewChannel(0)` at `sources/containerd/core/events/exchange/exchange.go:132`); BuildKit `active` map is non-durable mirror (`sources/buildkit/solver/llbsolver/history/buildhistory.go:57`); Dagster cross-run queries require `RunShardedEventsCursor` or exception (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:344-354`); Temporal pages ancestry (`sources/temporal/common/persistence/history_manager.go:619-665`) but not post-crash subscriber backlog.
- **Operational runbook for WAL/checkpoint.** None expose `PRAGMA wal_checkpoint(TRUNCATE)` or `journal_size_limit`; Dagster's `SQLITE_BUSY_TIMEOUT_SECONDS=30` is constant import (`python_modules/dagster/dagster/_core/storage/sqlite.py:15`), not config. Temporal SQLite `MaxConns` warning is test-only.
