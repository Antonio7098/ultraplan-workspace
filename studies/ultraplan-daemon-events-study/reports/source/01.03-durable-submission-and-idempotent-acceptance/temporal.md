## Summary

Temporal durably accepts work through a frontend-validated `RequestId` that is forwarded to history and only acknowledged after a conditional persistence write succeeds. Workflow start (`StartWorkflowExecution`), `SignalWorkflowExecution`, `SignalWithStart`, and `UpdateWorkflowExecution` each follow the pattern `frontend.validateRequestId -> history conditional Create/Update -> durable RequestId recorded -> response`. Duplicate detection is via `WorkflowExecutionState.RequestIds map[string]*RequestIDInfo` (`service/history/workflow/mutable_state_impl.go:410`) and the `CurrentWorkflowConditionFailedError.RequestIDs` map bubbled from persistence (`common/persistence/data_interfaces.go:119`). The conditional write (`CreateWorkflowModeBrandNew` / `CreateWorkflowModeUpdateCurrent`, `common/persistence/data_interfaces.go:45`) guarantees no acknowledgement before commit. Retrying the same `RequestId` after a crash-before-response returns the original `RunId`/`FirstExecutionRunId` with `Started:false` (`service/history/api/startworkflow/api.go:340`). Temporal does **not** fingerprint request payloads; the opaque `RequestId` (auto-generated if empty via `uuid.NewString()` at `service/frontend/workflow_handler.go:6947`) is the sole deduplication key, and reusing it with different arguments silently returns the first result. Retention is split: event-backed request IDs (`AttachTime==nil`) are never swept and live as long as the execution (deleted by retention scanner); CHASM-attached IDs are bounded by `MaximumRequestIDsPerExecution=25` (`common/dynamicconfig/constants.go:2646`) and `RequestIDMaxAge=7d` (`common/dynamicconfig/constants.go:2652`) and lazily swept at `closeTransactionSweepChasmRequestIDs` (`service/history/workflow/mutable_state_impl.go:2664`).

## Rating

**8 / 10 — Clear model with tests, explicit interfaces, and operational safeguards; minor gaps prevent 9.**

Rationale: Durable-before-ack is enforced by DB conditional writes and `AttachRequestID` only after the started event is durable (`service/history/workflow/mutable_state_impl.go:3102`). Idempotency is first-class (`WorkflowExecutionState.RequestIds`, `IsSignalRequested`, `Update.Amit` dedup) with metrics (`StartWorkflowRequestDeduped` at `service/history/api/startworkflow/api.go:341`) and dedicated conflict-resolution code (`service/history/api/workflow_id_dedup.go:26`). Eager-start retry path re-hydrates history (`service/history/api/startworkflow/api.go:571`). Deducted two points because (a) no canonical payload fingerprint means mismatched retry silently succeeds (no `RequestId` collision error), and (b) retention policy is bifurcated and barely documented — classic IDs are unbounded per execution, CHASM IDs are swept — with no operational alerting on near-cap eviction beyond `CHASMRequestIDEvicted` metric (`service/history/workflow/mutable_state_impl.go:2714`).

## Answers to Dimension Questions

### 1. Can acknowledgement happen before durable acceptance?

**No.** Frontend does not acknowledge until `historyClient.StartWorkflowExecution` returns successfully (`service/frontend/workflow_handler.go:572`). On the history side, `Starter.Invoke` builds the mutable-state snapshot (`service/history/api/startworkflow/api.go:254`) and calls `CreateWorkflowExecution(CreateWorkflowModeBrandNew)` (`service/history/api/startworkflow/api.go:307`) which is a conditional DB write. `AttachRequestID` (`service/history/workflow/mutable_state_impl.go:2591`) is invoked inside `ApplyWorkflowExecutionStartedEvent` (`service/history/workflow/mutable_state_impl.go:3102`) *before* the snapshot is persisted. Only after the persistence succeeds does `generateResponse` run (`service/history/api/startworkflow/api.go:226`). Signal (`service/history/api/signalworkflow/api.go:42`) and SignalWithStart (`service/history/api/signalwithstartworkflow/signal_with_start_workflow.go:333`) follow the same `GetAndUpdateWorkflowWithNew` → `AddSignalRequested` → conditional `UpdateWorkflowExecution` pattern. Update admission writes an `UpdateAdmitted` event as part of the same `CloseTransactionAsSnapshot` transaction; acknowledgement (`WaitLifecycleStage` → `statusAdmitted`) is only returned after that commit.

### 2. What happens if the same key is retried with identical input?

Retry is **idempotent and returns the original operation** (`StartDeduped`). In `handleConflict` (`service/history/api/startworkflow/api.go:340`), history loads `CurrentWorkflowConditionFailedError.RequestIDs` (populated by `SqlExecutionStore`/`Cassandra` at `common/persistence/sql/sqlplugin/tests/history_current_execution.go:329` and `common/persistence/cassandra/errors.go:226`). If `request.GetRequestId()` exists in that map, it increments `StartWorkflowRequestDeduped` (`service/history/api/startworkflow/api.go:341`) and calls `respondToRetriedRequest` (`service/history/api/startworkflow/api.go:344`) which returns the same `RunId`, `FirstExecutionRunId`, `Status`, and a `RequestIdRef` link (`service/history/api/startworkflow/api.go:356`). `Started` is `true` for the original caller but callers should treat deduped `Started:false` as "already started". Signal dedup returns a no-op `UpdateWorkflowAction{Noop:true}` (`service/history/api/signalworkflow/api.go:46`). Update dedup: `Admit` no-ops when `u.state != stateCreated` (`service/history/workflow/update/update.go:324`), so the second `UpdateWorkflowExecution` with same `updateID` returns the same future without creating a second event.

### 3. What happens if the same key is reused with different input?

**No payload comparison; the second call is still treated as a retry and the original result is returned (payload difference is silently ignored).** The dedup check at `service/history/api/startworkflow/api.go:340` compares only the `RequestId` string, never `WorkflowType`, `Input`, `TaskQueue`, or `SearchAttributes`. Same for signals (`service/history/api/signalworkflow/api.go:45` compares only `RequestId`). For updates, dedup is by `updateId` (`service/history/workflow/update/update.go:324`), not by input hash. Reusing a `RequestId`/`updateId` with different arguments does **not** yield `AlreadyExists`/`InvalidArgument` — it returns `RunId` of the first execution. This is intentional (opaque key model) but means clients that accidentally reuse keys across distinct logical operations get wrong workflows. No evidence of canonical request fingerprinting or `GenerateRequestIDRefLink`-side validation was found; `grep` for `fingerprint|hash.*request` returned no results.

### 4. How long is deduplication state retained?

**Two-tier model:**

- **Event-backed IDs (workflow start, signal):** Retained as long as the execution lives. `AttachRequestID` entries have `AttachTime==nil` (`service/history/workflow/mutable_state_impl.go:2591`) and `closeTransactionSweepChasmRequestIDs` explicitly skips them (`service/history/workflow/mutable_state_impl.go:2691`). They are stored in `WorkflowExecutionState.RequestIds` and serialized with the execution (`common/persistence/serialization/serializer.go:462`). They disappear only when the execution is deleted — either explicitly or by the retention/scanner subsystem (`worker.historyScannerDataMinAge` default `60*24h` at `common/dynamicconfig/constants.go:3511`, `ExecutionDataDurationBuffer 90d` at `common/dynamicconfig/constants.go:3475`). No TTL or count cap applies.

- **CHASM-attached IDs (UpdateComponent, workflow-update callbacks):** Bounded. `MaximumRequestIDsPerExecution` defaults to `25` (`common/dynamicconfig/constants.go:2646`) and `RequestIDMaxAge` to `7d` (`common/dynamicconfig/constants.go:2652`), both `dynamicconfig.IntPropertyFnWithNamespaceFilter` / `DurationPropertyFnWithNamespaceFilter` evaluated per namespace. Eviction is lazy on `TransactionPolicyActive` close (`service/history/workflow/mutable_state_impl.go:2665`), age-first then oldest-first count cap, with `CHASMRequestIDEvicted` metric (`service/history/workflow/mutable_state_impl.go:2714`). Tests prove eviction (`service/history/workflow/mutable_state_impl_test.go:6733`, `service/history/chasm_engine_test.go:1133`).

Gap: No documentation that `RequestIDMaxAge=0` disables age sweep or that classic IDs are immortal until retention; operators could mis-expect garbage collection of old Workflow start dedup keys.

### 5. Can a network/client failure accidentally start duplicate work?

**No, if the client correctly retries with the same `RequestId` (SDK behavior).** The critical invariant is stated in the prompt: *Crash or disconnect after commit but before the start response reaches the client. Can retry return the original operation?* — **Yes.** The conditional write already committed the `RequestIds` map. A retried `StartWorkflowExecutionRequest` with identical `RequestId` hits `handleConflict` → `StartDeduped` (`service/history/api/startworkflow/api.go:340`) and `respondToRetriedRequest` re-hydrates the workflow task/history even for eager start (`service/history/api/startworkflow/api.go:594`). Signal path similarly returns `IsSignalRequested` noop without double-signaling (`service/history/api/signalworkflow/api.go:45`). Update path: `WaitLifecycleStage` will surface `registryClearedErr` → `AbortedByServerErr` (`service/history/workflow/update/update.go:238`), which the history handler re-creates on retry, and `PollWorkflowExecutionUpdate` (`service/frontend/workflow_handler.go:5583`) allows polling the original update by `updateId`.

**However, duplicate work *can* occur if:** the client generates a **new** `RequestId` on retry (e.g., direct API without SDK, or `validateRequestId` auto-generates `uuid.NewString()` at `service/frontend/workflow_handler.go:6947` when field is empty). Because frontend defaults empty IDs, naive HTTP retries without preserving the header create new executions. Also, CHASM dedup can expire: after `7d`/`25`-cap eviction, a late retry with the same key creates new work — mitigated by the small default cap only for CHASM updates, not for workflow starts.

## Notable Patterns

- **Conditional-write-as-consensus:** No external lock service; the `current_executions` table's unique key `(namespace, workflowId)` plus `CreateWorkflowMode` acts as linearizable arbiter (`common/persistence/sql/sqlplugin/tests/history_current_execution.go:329` pattern).
- **Request-ID-as-link:** Deduped responses return `GenerateRequestIDRefLink` (`service/history/api/link_util.go:30`) rather than concrete `EventId`, allowing the client to resolve the event later even if it was buffered (not yet assigned `EventId`).
- **State-machine dedup for updates:** `Update` registry dedup by `updateId` (`service/history/workflow/update/update.go:324`) plus `HasRequestID` check for callbacks (`service/history/workflow/update/update.go:484`) — two-layer dedup (update identity + callback request identity).
- **Lazy sweep at transaction close:** CHASM request IDs are not GC'd by background scanner; eviction happens piggy-backed on the next write (`closeTransactionSweepChasmRequestIDs` gated by `chasmRequestIDsAdded`, `service/history/workflow/mutable_state_impl.go:2665`), minimizing write amplification.
- **Defensive re-defaulting on retry:** `prepareStartWorkflowRequest` clones the request before mutating `SearchAttributes` (`service/frontend/workflow_handler.go:684`) with comment `Since unaliasedSearchAttributesFrom is not idempotent, we need to clone` — ensures idempotent handling of internal retries that reuse the same proto.

## Tradeoffs

- **Durability vs latency:** Every start must `CloseTransactionAsSnapshot` (`service/history/api/startworkflow/api.go:281`) + `CreateWorkflowExecution` before ack. This adds a persistence RTT (DB write + history branch append) but is required for exactly-once start. Eager start amortizes cost by returning the first workflow task inline (`generateResponse` at `service/history/api/startworkflow/api.go:799`).
- **Unbounded vs bounded dedup state:** Not bounding event-backed `RequestIds` simplifies correctness (no premature eviction of start dedup) but payload size grows with every `Signal`/`Update`/`Start` that hits the execution — problematic for workflows that receive thousands of signals with distinct `RequestIds` (each adds `len(requestID)` to `approximateSize` at `service/history/workflow/mutable_state_impl.go:2574`). The alternative (hard cap) would risk late retries creating duplicates.
- **Opaque key vs fingerprint:** Skipping payload hashing keeps dedup logic trivial and avoids false negatives due to nondeterministic serialization, but forfeits detection of buggy caller reusing a key with different inputs. Adding fingerprint comparison and returning `InvalidArgument` on mismatch would be safer but is a breaking change.
- **Per-execution dedup vs per-namespace table:** Storing `RequestIds` inside the execution row avoids cross-shard lookup and scales with execution history, but replication (`service/history/replication/sync_state_retriever.go:404`) and visibility archiving must copy the map. A global idempotency table would allow shorter retention but requires extra storage and GC.

## Future Considerations

- **Add payload fingerprint on `RequestId` reuse:** Store `hash(TaskQueue, WorkflowType, Input, SearchAttributes)` alongside `RequestIDInfo` and return `InvalidArgument (requestId already used with different payload)` on mismatch. Requires new field in `persistencespb.RequestIDInfo` (currently `EventType`/`EventId`/`AttachTime` only) and a feature flag for rollout.
- **Unify retention policy:** Make event-backed IDs also subject to `RequestIDMaxAge` but with a much longer default (e.g., retention period + buffer) and emit `MutableStateStatistics.SignalRequestIDCount` metric alarm at 80% of `MaximumRequestIDsPerExecution` equivalent threshold for signals. Alternatively, expose `MaximumSignalRequestIDsPerExecution` setting analog to CHASM path.
- **Expose dedup observability:** `StartWorkflowRequestDeduped` (`service/history/api/startworkflow/api.go:341`) exists but `Signal`/`Update` dedup has no counter; add `SignalRequestDeduped` / `UpdateRequestDeduped` metrics and include `deduplicated:true` in `DescribeWorkflowExecution` response (`service/history/api/describeworkflow/api.go:173` already surfaces `RequestIdInfos` but not dedup counts).
- **Client-side `RequestId` preservation guidance:** SDKs already preserve `RequestId` on retry, but direct gRPC users rely on frontend auto-generation; consider rejecting empty `RequestId` when `ClientSupported` indicates SDK version supports it, or return `RequestId` in error details so callers can retry correctly.
- **Eager-start dedup optimization:** `getWorkflowHistory` (`service/history/api/startworkflow/api.go:671`) re-reads full history branch on deduped eager start; cache the first page or generate the poll response from mutable state (TODO at `service/history/api/startworkflow/api.go:672`) to avoid extra DB read under retry storm.
