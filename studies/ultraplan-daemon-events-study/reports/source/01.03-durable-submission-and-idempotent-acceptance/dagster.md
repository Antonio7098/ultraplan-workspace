## Summary

Dagster durably accepts work as a `DagsterRun` row before any acknowledgement. `RunDomain.create_run` (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:257`) constructs the run + snapshots and persists via `SqlRunStorage._core_add_run` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:142-149`) which does a single `RunsTable.insert` with a `UNIQUE` constraint on `run_id` (`python_modules/dagster/dagster/_core/storage/runs/schema.py:17`) inside a `with self.connect() as conn` block. IntegrityViolation → `DagsterRunAlreadyExists` (`python_modules/dagster/dagster/_core/errors.py:562`). GraphQL `launchPipelineExecution` (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/launch_execution.py:53`) first calls `create_valid_pipeline_run` (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/run_lifecycle.py:81`) then `instance.submit_run`. The sensor/daemon path reserves `run_id`s in `TickData.reserved_run_ids` (`python_modules/dagster/dagster/_daemon/sensor.py:1105`) and writes them to `InstigatorTick` via `SensorLaunchContext.set_run_requests` (`python_modules/dagster/dagster/_daemon/sensor.py:210-221`) *before* creating runs, giving a durable prepare/verify boundary that survives crashes via 24-h tick resume (`python_modules/dagster/dagster/_daemon/sensor.py:77`, `538-569`).

There is no generic `idempotency_key` table or request-fingerprint. Two deduplication mechanisms exist: (1) `run_id` equality as the canonical idempotency key at the storage layer, and (2) `run_key` (`dagster/run_key` tag at `python_modules/dagster/dagster/_core/storage/tags.py:54`) as an application-level sensor idempotency key checked via `fetch_existing_runs` (`python_modules/dagster/dagster/_daemon/sensor.py:1292`) which queries `RunsFilter(tags={RUN_KEY_TAG: run_key})` (`python_modules/dagster/dagster/_daemon/sensor.py:1310`). Identical-key retries are deduped (return `SkippedSensorRun` at `python_modules/dagster/dagster/_daemon/sensor.py:1358` or raise `DagsterRunAlreadyExists` at `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:149`); different-payload under same key is **not** fingerprinted — for `run_id` the second insert is rejected blindly, for `run_key` the existing run is silently returned without input comparison (silent conflict suppression). Only the airlift/airflow `register_managed_run` path does field-diff validation and raises `DagsterRunConflict` (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:621-631`, `638`). Retention is indefinite until explicit `delete_run`/`wipe` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:602`), not a TTL window. The GraphQL layer does not map `AlreadyExists` to the `RunConflict` GraphQL error (`python_modules/dagster-graphql/dagster_graphql/schema/errors.py:353-358`) on the main launch path, so a client that times out after commit cannot safely retry with the same `run_id` to retrieve the original operation without out-of-band `get_run_by_id` polling. Sensor retries are safe within the same tick благодаря reserved IDs + resume; external client retries with fresh UUIDs double-create work.

## Rating

**5 / 10 — Present but inconsistent, weakly documented, or fragile**

**Rationale:** Durable-before-acknowledgement is correctly implemented for `DagsterRun` persistence (UNIQUE `run_id`, transactional insert, `DagsterRunAlreadyExists` guard). Tick-level prepare (reserve → create) is durable and crash-resumable. However there is no cross-cutting request fingerprint, no `Idempotency-Key` header, no dedup window management, and inconsistent conflict-vs-duplicate handling: `run_id` collision is always an error even if payloads match (no idempotent replay of response), `run_key` collision silently skips even if payloads differ (no `409 Conflict` with diff), and only one code path (`register_managed_run`) validates equality before raising `DagsterRunConflict`. Client retry guidance is absent and GraphQL does not provide retry-to-retrieve semantics after a dropped response. Tests cover `run_id` collision (`python_modules/dagster/dagster_tests/storage_tests/utils/run_storage.py:1084`) but not end-to-end timeout-after-commit retry.

## Answers to Dimension Questions

### 1. Can acknowledgement happen before durable acceptance?

No for the core `DagsterRun` path, yes for peripheral state updates.

- **Run durability is correct:** `instance.create_run` → `RunDomain.create_run` → `run_storage.add_run` executes `conn.execute(RunsTable.insert...)` inside `with self.connect() as conn` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:145-147`). The method returns only after the context manager commits. `GraphQL do_launch` (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/launch_execution.py:51-56`) creates the run *before* calling `submit_run`, so the DB commit precedes any GraphQL acknowledgement. This satisfies durable-before-ack for the run row.

- **Tags insert is second statement in same connection** (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:151-155`). For SQLite this is one transaction; for Postgres with `AUTOCOMMIT` engine noted in `handle_run_event` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:226-228`) each execute can auto-commit, creating a window where `runs` is committed but `run_tags` (including `dagster/run_key`) is not yet fully visible. The explanatory comment at line 225 explicitly calls out needing to order `run_tags` before `runs` update for visibility, proving the team is aware of non-atomic multi-statement commits on Postgres.

- **Tick durability precedes run creation:** Sensor path does `context.set_run_requests` → `instance.update_tick` (`python_modules/dagster/dagster/_daemon/sensor.py:1109`) *before* looping over `instance.create_run` (`python_modules/dagster/dagster/_daemon/sensor.py:1339-1375` path via `_create_sensor_run` at `python_modules/dagster/dagster/_daemon/sensor.py:1419`). If daemon crashes between tick reserve and run creates, resume logic at `python_modules/dagster/dagster/_daemon/sensor.py:538-548` replays the reserved IDs. Thus the prepare step is durably recorded.

- **Non-durable tail:** `RunTagsTable` insert failure after `RunsTable` success leaves a run visible without its `run_key` tag, breaking future `fetch_existing_runs` dedup (run will not be found by tag filter). No compensating transaction rolls back the `RunsTable` row. Similarly, `handle_run_event` + `add_tags` on `instance.submit_run` path may be called after the acknowledgement response.

### 2. What happens if the same key is retried with identical input?

Depends on which key:

- **`run_id` retries (storage layer):** Second `add_run` with same UUID raises `DagsterRunAlreadyExists` regardless of payload identity (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:148-149`). The caller does **not** get the original success response replayed. For the canonical `DagsterRun` path (`DagsterRunAlreadyExists` not caught in `python_modules/dagster-graphql/dagster_graphql/implementation/execution/run_lifecycle.py:81`), the GraphQL layer surfaces this as a `PythonError` (or at best an unmapped `PipelineRunConflict` interface) rather than a successful idempotent `LaunchRunSuccess(runId)`. The caller must separately call `instance.get_run_by_id(run_id)` to retrieve the original run — the retry itself is not idempotently resolved by the server. The one exception is `register_managed_run` (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:633-639`) where `has_run` + `_check_run_equality` returns the existing run on equality, effectively idempotent for that call site only (Airflow ingestion).

- **`run_key` retries (sensor layer):** `fetch_existing_runs` at `python_modules/dagster/dagster/_daemon/sensor.py:1292` pre-fetches all runs with that `run_key` tag. `_get_or_create_sensor_run` at `python_modules/dagster/dagster/_daemon/sensor.py:1351-1364` treats an existing run (any status except `NOT_STARTED`) as a hit and returns `SkippedSensorRun(run_key, existing_run)` (`python_modules/dagster/dagster/_daemon/sensor.py:1358`). The daemon logs "Skipping {n} runs … already completed with run keys" (`python_modules/dagster/dagster/_daemon/sensor.py:1229`) and marks tick success without creating a duplicate `DagsterRun`. This is idempotent within the same sensor's namespace (sensor name + repository selector filter at `python_modules/dagster/dagster/_daemon/sensor.py:1317-1325`). The same key retried within the same tick also hits the in-memory `existing_runs_by_key` cache (`python_modules/dagster/dagster/_daemon/sensor.py:1373`) preventing intra-tick duplicates.

- **Intra-tick same-key idempotency is also test-adjacent:** `fetch_existing_runs` dedup at the tag query level avoids double-creating when two `RunRequest`s in one sensor evaluation share a `run_key`.

### 3. What happens if the same key is reused with different input?

No fingerprint is computed; behavior diverges silently by layer:

- **`run_id` with different input:** Storage treats dedup key as sole identity. `RunsTable.run_id` uniqueness violation raises `DagsterRunAlreadyExists` without comparing `run_config`, `job_name`, `tags`, or `asset_selection` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:142-149`). The conflicting second submission is rejected as indistinguishable from a retry, losing the fact that the intent diverged. GraphQL has no `400 Conflict` payload carrying the existing run's fingerprint to let the caller diagnose mismatch. Only `register_managed_run` at `python_modules/dagster/dagster/_core/instance/runs/run_domain.py:621-631` performs `_check_run_equality` and raises `DagsterRunConflict` (distinct from `AlreadyExists`) with a field diff (`_format_field_diff`) — but this path is not used for normal `launchPipelineExecution` or sensor `create_run`.

- **`run_key` with different input:** Application-level dedup at `python_modules/dagster/dagster/_daemon/sensor.py:1351-1358` does not compare `run_config`/`tags`/`asset_selection`. If a sensor emits `RunRequest(run_key="k", run_config={"a":1})` and later (after polling interval) emits `RunRequest(run_key="k", run_config={"a":2})`, `fetch_existing_runs` returns the first run and `_get_or_create_sensor_run` returns `SkippedSensorRun` for the second, silently suppressing the new intent. The sensor author is expected to make `run_key` a deterministic fingerprint of intent (e.g., `cursor` or ingestion id), but the framework does not enforce or hash it. No error is surfaced; `sensor.py:1229` logs counts only. The same failure mode exists for schedules where `run_key` dedup shares the pattern (scheduler dedup via `add_run_info` at `python_modules/dagster/dagster/_scheduler/scheduler.py:130`).

- **Result:** Retry-vs-conflict is ambiguous. Identical retries are safe (no dupe) but misusing the same key with new data either hard-fails (run_id) or is silently swallowed (run_key), neither giving a structured `409 Conflict` with existing-vs-requested diff.

### 4. How long is deduplication state retained?

Indefinitely — deduplication state is the object itself, with no TTL.

- **`run_id` dedup lifetime:** `RunsTable.run_id` UNIQUE persists until `RunStorage.delete_run` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:602`) or `wipe` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:880`). No expiry column. Every `run_id` ever created blocks reuse forever, which is correct for content-addressed UUIDs but means there is no bounded idempotency window table that could be garbage-collected independently of run retention.

- **`run_key` dedup lifetime:** `fetch_existing_runs` scans live `RunTagsTable` (`python_modules/dagster/dagster/_daemon/sensor.py:1310`) for `RUN_KEY_TAG`. Since runs are never TTL-expired, a `run_key` emitted once will dedup forever — desired for sensors that must not re-trigger ingestion for the same entity, but problematic if the sensor author reuses a key for a logically distinct re-trigger (e.g., daily `run_key="2026-09-02"` will never re-fire for that date). The only pruning is run/tick retention: old ticks are purged after N days per `tick_retention_settings` (`python_modules/dagster/dagster/_daemon/sensor.py:334-342`), but `RunsTable`/`RunTagsTable` are not purged with them. Instance-level run retention is manual (UI "wipe" or admin `delete_run`).

- **No idempotency TTL bucket:** Searched `python_modules/dagster/dagster/_core/storage/runs/schema.py:1-209` — no `idempotency` or `deduplication` table, no `expireAt` column like containerd's content ingest `expireAt` at `core/metadata/content.go:458`. Retention is thus governed by run lifecycle, not by a bounded dedup window, which precludes safe key reuse after a configured interval.

### 5. Can a network/client failure accidentally start duplicate work?

Yes for external GraphQL clients, no (mostly) for the daemon internal loop.

- **External `launchPipelineExecution` (vulnerable):** Client obtains `run_id` via `make_new_run_id()` (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/run_lifecycle.py:87-89`). If the client times out after the server has committed `RunsTable.insert` but before the HTTP response arrives, retrying will generate a **new** `run_id` (fresh UUID) unless the client explicitly preserves and resends the same `executionMetadata.runId`. Most webserver/UI and `DagsterGraphQLClient` callers do not set `runId` (it is optional in `ExecutionParams`), so the second attempt creates a second `DagsterRun` with identical `run_config` but distinct identity — duplicate work is started. Even if the client does preserve `run_id`, the server raises `DagsterRunAlreadyExists` rather than returning `LaunchRunSuccess` with the original run, so a naive retry still surfaces as an error and the client must implement `get_run_by_id` polling to discover the already-accepted run. There is no outbox + `Idempotency-Key` → `200 OK + cached response` pattern.

- **Sensor/daemon internal submissions (protected):** `SensorLaunchContext` writes `reserved_run_ids` to the tick before `create_run` (`python_modules/dagster/dagster/_daemon/sensor.py:210-221`, `1109`). Combined with `_get_evaluation_tick` resumption of `STARTED` ticks within 24 h (`python_modules/dagster/dagster/_daemon/sensor.py:538-548`) and same-tick `existing_runs_by_key` caching (`python_modules/dagster/dagster/_daemon/sensor.py:1373`), a daemon crash or transient DB failure after tick reserve but before `submit_run` (`python_modules/dagster/dagster/_daemon/sensor.py:755`) does not duplicate work — the next daemon iteration replays `tick.unsubmitted_run_ids_with_requests`. The `already_exist: SkippedSensorRun` path at `python_modules/dagster/dagster/_daemon/sensor.py:1358` also prevents double-create when a previous tick partially completed. This is the only path that achieves at-most-once-as-expected semantics.

- **Queued coordinator split:** `instance.submit_run` enqueues to `QueuedRunCoordinator` (`python_modules/dagster/dagster/_daemon/sensor.py:755` annotation, `reports/source/01.01-daemon-rpc-and-execution-ownership/dagster.md:43`), so duplicate `submit_run` calls for the same `run_id` after crash are idempotent at the queue layer (status transition `NOT_STARTED → QUEUED` is guard-checked), mitigating double-launch. But duplicate *creation* with fresh `run_id`s is not mitigated.

## Architectural Decisions

- **Run row as the durability boundary, not a WAL/outbox.** `RunDomain.create_run` (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:86`) chooses to make the `DagsterRun` DB row the sole atomic commit before acknowledgement. Keeps implementation simple (single table insert + tags, no 2PC with an event queue) and leverages existing SQL UNIQUE constraint rather than a separate idempotency ledger. Tradeoff: `run_tags` insert fragility on Postgres autocommit and lack of post-commit event delivery guarantee.

- **Dual dedup keys at different layers.** `run_id` (storage UNIQUE) is the system-generated nonce; `run_key` (tag) is the user-defined business dedup key for sensors. This splits concerns cleanly — UUID prevents accidental collision, tag encodes domain idempotency — but creates two non-overlapping dedup regimes with different failure semantics (hard-error vs silent-skip).

- **Tick as a durable prepare ledger.** Sensors write `TickData` with `reserved_run_ids` + `run_requests` + `cursor` via `context.set_run_requests` (`python_modules/dagster/dagster/_daemon/sensor.py:1109`) before side-effecting on runs. Treats the tick as the write-ahead log, enabling crash resume without an external queue. Chosen over ad-hoc journaling because ticks are already retained and replicated in `schedule_storage`; alternative of transactional run-plus-tick atomic commit is avoided (tick update is separate SQL statement from run insert).

- **No fingerprint hashing of request intent.** Run creation does not compute `hash(job_name + run_config + tags + asset_selection)` to compare against existing run under same key. Declined presumably to keep API surface minimal and avoid large payload hashing, but leaves conflict detection to `register_managed_run`'s field-wise equality (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:624`) which is only invoked for airflow-style managed runs, not general launches.

- **Indefinite retention of dedup keys via live runs.** Keeping `run_id`/`run_key` until explicit deletion avoids needing a GC/TTL subsystem and matches dagster's audit requirement (run history is permanent). Cost is unbounded growth of dedup state and inability to recycle keys after a retention window without admin wipe.

## Notable Patterns

- **Transactional run insert with IntegrityError mapping** (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:142-149`, `python_modules/dagster/dagster/_core/errors.py:562`). Canonical pattern: DB UNIQUE → `IntegrityError` → `DagsterRunAlreadyExists`. Proven with fixed duplicate-run test (`python_modules/dagster/dagster_tests/storage_tests/utils/run_storage.py:1084`), but not extended to idempotent response replay.

- **Equality-guarded managed run registration** (`python_modules/dagster/dagster/_core/instance/runs/run_domain.py:576-639`). Uses `_check_run_equality` + `_format_field_diff` to surface `DagsterRunConflict` on differing payload under the same `run_id`, enabling exactly-once Airflow dag retry with race detection (`DagsterRunAlreadyExists` → re-read + compare comment at `python_modules/dagster/dagster/_core/instance/runs/run_domain.py:598-601`). This pattern is *not* generalized to GraphQL launch or sensor create.

- **Prepare-then-execute via tick reservation** (`python_modules/dagster/dagster/_daemon/sensor.py:1099-1115` reserves IDs, `python_modules/dagster/dagster/_daemon/sensor.py:538-569` resumes). Gives daemon executions property: crash after reserve but before execute is recoverable within 24 h (configurable via `MAX_TIME_TO_RESUME_TICK_SECONDS` at `python_modules/dagster/dagster/_daemon/sensor.py:77`). Non-tick callers (CLI `dagster run launch`) do not get this safety.

- **Application-level dedup via tag scan** (`python_modules/dagster/dagster/_daemon/sensor.py:1292-1336`). Scans `RunsFilter(tags={RUN_KEY_TAG: k})` per key (serially for better query-planning per comment at `python_modules/dagster/dagster/_daemon/sensor.py:1307`) then filters by `SENSOR_NAME_TAG` + repository selector. Effective for low-cardinality sensor keys but O(n) queries per tick, not a hash-bucketed dedup index.

## Tradeoffs

- **Durability-first vs. visibility-atomicity.** Persisting run before any queue avoids lost intents but splitting `runs` + `run_tags` into two SQL statements (without explicit transaction on Postgres `AUTOCOMMIT` engines) risks tag-visibility lag. Callers that poll by `run_key` tag could miss the run transiently. Wrapping both inserts in one explicit transaction would eliminate the split but would require engine-specific handling noted in `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:225-228`.

- **UUID dedup vs. content-addressed dedup.** Random `run_id` makes collisions cryptographically improbable and histories permanent, simplifying retry safety. But it eliminates natural idempotency (same intent → different UUID → dedup never fires) unless the caller opts into stable `run_id` or `run_key`. Fingerprinting the `Definition`/`run_config` would give stable-key dedup but would require centralizing fingerprint computation and defining conflict resolution policy (as BuildKit's `Digest()` does).

- **Silent run_key skip vs. explicit conflict error.** Returning `SkippedSensorRun` and logging at `python_modules/dagster/dagster/_daemon/sensor.py:1229` makes sensors resilient (no operator-visible error on second evaluation of same file) but hides legitimate divergence where sensor incorrectly reuses a key with new data. Raising `DagsterRunConflict` with diff (as `register_managed_run` does) would make divergence observable but would require sensor authors to handle errors.

- **Indefinite dedup retention vs. operational boundedness.** Permanent retention gives perfect audit and prevents accidental re-trigger of historical ingests, at cost of ever-growing `RunTagsTable` and inability to recycle daily partition `run_key`s after N days without manual cleanup. Adding TTL would reduce storage but would reintroduce at-most-once windows.

- **Daemon-internal idempotency vs. external client exposure.** Daemon's tick reservation + resume is mature for scheduled polling; external API consumers (REST `python_modules/libraries/dagster-rest-resources/dagster_rest_resources/api/run.py:154` handling `RunConflict`, `DagsterGraphQLClient` at `python_modules/dagster-graphql/dagster_graphql/client/client.py:290`) get a weaker contract (error not replay), forcing clients to add post-retry `get_run_by_id` verification. Uniform idempotency ledger would cover both.

## Failure Modes / Edge Cases

- **Lost response after commit (the dimension's crash-after-commit):** Client issues `launchPipelineExecution` without explicit `runId`, server commits `RunsTable.insert`, HTTP response dropped. Client retry creates a new UUID → second `DagsterRun` launched → duplicate pipeline execution and duplicate asset materializations. No server-side `request_id → response` cache exists to replay original `LaunchRunSuccess`. Mitigation requires caller-preserved `run_id` + manual `get_run_by_id` after `RunConflict`/`AlreadyExists`, not documented in `python_modules/dagster-graphql/dagster_graphql/implementation/execution/run_lifecycle.py:81`.

- **Tag-split commit failure (Postgres AUTOCOMMIT):** `RunsTable.insert` succeeds, `RunTagsTable.insert` fails (DB restart, network partition). Run is visible by `run_id` but invisible to `fetch_existing_runs` tag scan (`python_modules/dagster/dagster/_daemon/sensor.py:1310`). Next sensor tick with same `run_key` creates a second `DagsterRun` with same business key → duplicate work. Inverse is not possible (tag without run) due to FK (`python_modules/dagster/dagster/_core/storage/runs/schema.py:75` `ondelete=CASCADE`), but forward split is.

- **Concurrent tick writers double-create.** Two `dagster-daemon` processes with same `InstanceRef` (split-brain, last-write-wins heartbeat at `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:852-873` with no fence) both execute `fetch_existing_runs` seeing empty, both `create_run` with different `run_id`s but same `run_key` → two runs committed with same `run_key` tag. Subsequent ticks will dedup arbitrarily to whichever run is last in `existing_runs` dict (`python_modules/dagster/dagster/_daemon/sensor.py:1333`). Sensor run_key guarantees are thus conditional on single-daemon invariant.

- **24 h resume cliff.** `_get_evaluation_tick` (`python_modules/dagster/dagster/_daemon/sensor.py:538-555`) only resumes `STARTED` ticks within `MAX_TIME_TO_RESUME_TICK_SECONDS=86400`. A daemon outage >24 h leaves a `STARTED` tick with `unsubmitted_run_ids_with_requests` permanently abandoned — moved to `SKIPPED` with `moving dangling STARTED tick … into SKIPPED` log at `python_modules/dagster/dagster/_daemon/sensor.py:553`, losing reserved but uncreated runs. No run was persisted for those reservations, so the ingestion is silently skipped.

- **Reuse of run_key with mutated intent silently swallowed.** As captured in Q3, second `RunRequest(run_key="k", run_config=v2)` after `v1` is already materialized is treated as duplicate. Downstream asset may be stale without operator alert. Sensor author must encode version/hash into `run_key`; framework does not validate.

- **`register_managed_run` race on field equality relies on serialized `run_body`.** `_check_run_equality` compares deserialized fields (checked at `python_modules/dagster/dagster/_core/instance/runs/run_domain.py:624`) but does not account for server-added tags (`CODE_LOCATION_TAG` at `python_modules/dagster/dagster/_core/instance/runs/run_domain.py:230-234`) inserted after construction; such tags would register as conflict even though caller did not provide them, causing spurious `DagsterRunConflict`.

## Future Considerations

- **Add `Idempotency-Key` / `request_id` to `ExecutionParams`.** Accept optional `executionMetadata.runId` as the idempotency key for all creation paths (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/run_lifecycle.py:86-89` already threads it through), persist `(request_id, fingerprint, response)` in a dedicated idempotency bucket with TTL (e.g., 24 h) separate from `RunsTable`. On collision with same fingerprint, replay `LaunchRunSuccess(runId)`; on differing fingerprint, return `RunConflict` with structured diff via `_format_field_diff`. Generalize `register_managed_run`'s equality check to the general `create_run` path or at least to `create_valid_pipeline_run`.

- **Retry-to-retrieve RPC.** Expose `getRunById` as authoritative post-retry path and document safe retry predicate: clients should retry `launchPipelineExecution` with same `runId` on `DeadlineExceeded`/`Unavailable`; on `RunConflict`/`DagsterRunAlreadyExists` fetch via `instance.get_run_by_id` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:427`). Add integration test that kills gRPC context between `_core_add_run` and response send, retries, and asserts original `run_id` returned.

- **Transactional run+tags insert.** Wrap `RunsTable` + `RunTagsTable` inserts in an explicit `conn.begin()` transaction on all engines (not relying on autocommit) to prevent tag-visibility split. Align with existing guidance in `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:225-228`.

- **Bounded dedup window for `run_key`.** Add `run_key_expiry` tag or separate `sensor_dedup` table with `expire_at` (mirroring containerd `contentStore` 24 h `expireAt` at `core/metadata/content.go:458`), GC'd by a daemon sweep. Keep history indefinite but allow key reuse after window; sensor config could opt into `run_key_ttl_days`.

- **Single-daemon fencing.** Persist `daemon_type` reservation via `SELECT FOR UPDATE` / advisory lock instead of log-only duplicate detection (`python_modules/dagster/dagster/_daemon/sensor.py:182` analogue noted in final 01.01 report) so concurrent `fetch_existing_runs` + `create_run` cannot race to double-create same `run_key`.
