## Summary

Dagster's durable event contract is `EventLogEntry + EventLogRecord` persisted in a SQL table (`event_logs`) with an autoincrement `id` acting as the per-run sequence number. The typed inner payload is `DagsterEvent` (49 `DagsterEventType` values) with a discriminated `event_specific_data` union. Ordering is strictly monotonic per `run_id` via `id ASC`; cross-run global ordering is only well-defined on non-sharded stores (consolidated SQLite/Postgres/MySQL) where a single autoincrement namespace exists, while the default `SqliteEventLogStorage` shards per-run into `<run_id>.db` and falls back to timestamp-ordered fan-out with a `RunShardedEventsCursor`. Replay is cursor-based: `EventLogCursor = base64({type,value})` with `STORAGE_ID` (and legacy `OFFSET`) cursors, surfaced in `get_records_for_run(cursor, limit)` and `fetch_*` helpers returning `EventLogConnection(cursor, has_more)` / `EventRecordsResult`. Live observation uses pluggable watchers (`SqlPollingEventWatcher`, filesystem `Watchdog`, in-memory callbacks) that deliver `(EventLogEntry, storage_id_cursor)` after `storage_id > cursor`. Schema evolution relies on `whitelist_for_serdes` with `old_storage_names`, `old_fields`, `storage_field_names`, `field_serializers`, and Dagster-specific backcompat shims (`DagsterEventSerializer.before_unpack`, `_handle_back_compat`, `handle_unpack_error -> ENGINE_EVENT`). Explicit causation/correlation IDs are absent; "why" is inferred from `run_id`/`step_key`/`logging_tags` plus run-level system tags (`dagster/parent_run_id`, `dagster/root_run_id`, `dagster/partition`, etc.) and typed payloads like `JobFailureData.first_step_failure_event`. The model is durable and test-covered but not extensible as a generic stream: no producer-side sequence, no per-subject monotonic version per asset/step, and no idempotent producer deduplication on the write path.

## Rating

**7 / 10 — Clear model with tests, explicit interfaces, and operational safeguards**

Justification: envelope is typed, versioned, and backcompat-tested; per-run ordering and cursor resume are formally specified with storage isolation handling (sharded vs consolidated), pagination, and multiple watcher implementations. Schema compat is explicitly codified via serdes metadata and migration tables (`secondary_indexes`). Deducted because (a) global ordering is conditional on storage choice, (b) no first-class causation/correlation envelope field (inferred from tags/step hierarchy), (c) no gap-free exactly-once guarantee on the read side — reconnect requires the consumer to correctly manage the opaque cursor and de-duplicate `storage_id`, and storage backends differ in cursor semantics, and (d) producer cannot safely re-drive without duplicate suppression.

## Answers to Dimension Questions

### 1. What ordering is actually guaranteed?

**Per-run total order by `id`. Cross-run partial, storage-dependent.**

- Per-run: `SqlEventLogStorageTable.id` is an autoincrement PK assigned at `INSERT` time (`python_modules/dagster/dagster/_core/storage/event_log/schema.py:11-16`). `get_records_for_run` enforces `run_id == ?` then `id > cursor.storage_id` (ascending) and `ORDER BY id ASC` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:469-473, 451-455`). This is linearizable against concurrent writers serialized by SQLite/Postgres row insertion; reconnect by replaying `get_records_for_run(cursor)` is monotonic.
- Per-asset global: `SqliteEventLogStorage` *mirrors* `ASSET_EVENTS` and `ASSET_CHECK_EVENTS` and `PIPELINE_*` status events into a central `index` DB (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:274-303`) so `get_event_records` for asset/event-type filters can be globally ordered by `id` in the index shard. For non-asset cross-run queries on sharded storage, global order degenerates to timestamp order with fan-out: `_get_run_sharded_event_records` opens each run DB in `run.update_timestamp` order and merges `ORDER BY timestamp` per-run, capped via `RunShardedEventsCursor` (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:332-413`). `ConsolidatedSqliteEventLogStorage` (single DB) restores global `id` order and is "intended for test cases only" (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/consolidated_sqlite_event_log.py:36-37`). No per-subject monotonic version (e.g., per-`step_key` sequence) is assigned; filtering by `step_key`/`dagster_event_type` is post-hoc and not sequentially numbered.

### 2. Can a reconnecting client resume without gaps or duplicates?

**Yes if the client correctly manages an opaque `STORAGE_ID` cursor on the same run; duplicates are possible but detectable; global cross-run resume has gaps risk on sharded storage.**

- Cursor contract: `EventLogCursor.from_storage_id(id).to_string()` (`python_modules/dagster/dagster/_core/event_api.py:62-63`) is returned as `EventLogConnection.cursor` equal to last `record_id` fetched, or the incoming cursor if no new records (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:498-505`). The contract for the next call is `WHERE id > cursor.storage_id`, so re-issuing with previous cursor does not skip.
- Polling watcher semantics: `SqlPollingRunIdEventWatcherThread.run` persists `cursor = conn.cursor` each poll and delivers only when `callback.cursor.storage_id < event_record.storage_id` (`python_modules/dagster/dagster/_core/storage/event_log/polling_event_watcher.py:180-197`). `SqliteEventLogStorageWatchdog._process_log` advances `self._cursor = connection.cursor` after each emission (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:546-549`). Disconnect → reconnect from last `cursor` replays any writes that occurred while disconnected; no tombstone gap because storage is append-only.
- Duplicates: writer-side `store_event` is not idempotent — re-emitting the same `DagsterEvent` allocates a new `id`. Consumer-side idempotence must use `storage_id`. The executor explicitly tracks `seen_storage_ids` to de-dupe when `offset` handling forces overlap (`python_modules/dagster/dagster/_core/executor/step_delegating/step_delegating_executor.py:101-140`). A naïve consumer that ignores `storage_id` or uses the deprecated `OFFSET` cursor (`python_modules/dagster/dagster/_core/storage/event_log/base.py:232-238`) can see ordering anomalies if events were inserted between offset calculation and fetch.
- Global cross-run: on `SqliteEventLogStorage` a reconnect using `RunShardedEventsCursor` must supply `run_updated_after`; missed runs whose `update_timestamp` did not advance beyond the cursor's window will not be scanned (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:371-380`). This is a best-effort fan-out, not a linearizable global log.

### 3. Are events named as immutable past-tense facts?

**Mostly yes for user-visible domain events; lifecycle/marker events include present/active verbs.**

- Past/achieved: `STEP_SUCCESS`, `STEP_FAILURE`, `STEP_SKIPPED`, `ASSET_MATERIALIZATION`, `ASSET_OBSERVATION`, `ASSET_FAILED_TO_MATERIALIZE`, `LOGS_CAPTURED`, `HANDLED_OUTPUT`, `LOADED_INPUT`, `HOOK_COMPLETED/ERRORED/SKIPPED`, `PIPELINE_SUCCESS/FAILURE/CANCELED` (`python_modules/dagster/dagster/_core/events/__init__.py:112-191`). Values are `UPPER_SNAKE` stable strings persisted as `dagster_event_type` (`python_modules/dagster/dagster/_core/storage/event_log/schema.py:19`), renamed only via displayed map (`python_modules/dagster/dagster/_core/events/__init__.py:194-203`) not storage rewrite.
- Non-past/marker: `STEP_START`, `RESOURCE_INIT_STARTED`, `STEP_WORKER_STARTING/STARTED`, `STEP_UP_FOR_RETRY`, `STEP_RESTARTED`, `RESOURCE_INIT_STARTED/SUCCESS/FAILURE` are marker start/end events (`python_modules/dagster/dagster/_core/events/__init__.py:252-259`) with `EngineEventData.marker_start/marker_end` (`python_modules/dagster/dagster/_core/events/__init__.py:1952-1955`) — they describe a transition in progress, not an achieved fact. `RUN_ENQUEUED/DEQUEUED/STARTING/START/CANCELING` similarly include queue transitions. Evolution preserved via `_handle_back_compat` mapping old `STEP_MATERIALIZATION` → `ASSET_MATERIALIZATION` and keeping legacy `PIPELINE_*` storage values while aliasing to `RUN_*` (`python_modules/dagster/dagster/_core/events/__init__.py:162-169,2264-2266`).

### 4. Can the consumer tell why an event happened?

**Structural why is inferable (run/step lineage), causal why is not carried as a first-class envelope field.**

- What is present: `run_id`, `job_name`, `step_handle`/`step_key`/`node_handle`/`step_kind_value`, `logging_tags`, `pid`, `timestamp` in `DagsterEvent`/`EventLogEntry` (`python_modules/dagster/dagster/_core/events/__init__.py:462-478`, `python_modules/dagster/dagster/_core/events/log.py:36-44`). Typed payloads add richer causality: `JobFailureData.first_step_failure_event` retains the triggering `STEP_FAILURE` (`python_modules/dagster/dagster/_core/events/__init__.py:2030`), `LoadedInputData.upstream_step_key/upstream_output_name` records data provenance (`python_modules/dagster/dagster/_core/events/__init__.py:2128-2131`), `EngineEventData` can carry `metadata {"pool":...}` for concurrency blocks (`python_modules/dagster/dagster/_core/events/__init__.py:1198-1200`) and `marker_start/marker_end` for resource init. Run-level tags give `dagster/parent_run_id`, `dagster/root_run_id`, `dagster/partition`, `dagster/backfill`, `dagster/retry_number`, `dagster/is_resume_retry` (`python_modules/dagster/dagster/_core/storage/tags.py:34-44`).
- What is missing: no `causationId`, `correlationId`, `triggeredBy`, `actor`, or OpenTelemetry `traceId` in the envelope. The `logging_tags` mapping is opaque and not standardized. Consumers must join `run_id -> parent_run_id -> root_run_id` via the run storage, and `step_key -> upstream_step_key` via `LoadedInputData`, rather than following a single envelope chain.

### 5. How does a schema evolve without breaking old clients?

**Serdes whitelisting + storage-field remapping + backcompat unpack + graceful degradation.**

- Whitelist discipline: every persisted type is `@whitelist_for_serdes` with explicit `storage_field_names`, `old_storage_names`, `old_fields`, `field_serializers`, `skip_when_none_fields` (`python_modules/dagster/dagster/_core/events/log.py:21-29`, `python_modules/dagster/dagster/_core/events/__init__.py:455-461`, `python_modules/dagster/dagster/_core/events/__init__.py:1727-1728`). This allows additive renames like `node_handle<->solid_handle`, `job_name<->pipeline_name`, `metadata<->metadata_entries`, `file_key<->log_key` without breaking deserialization.
- Code-level migration: `DagsterEventSerializer.before_unpack` rewrites old `event_type_value`/`event_specific_data` payloads before construction (`python_modules/dagster/dagster/_core/events/__init__.py:413-421`), and `_handle_back_compat` handles four legacy rewrites in one place (`python_modules/dagster/dagster/_core/events/__init__.py:2221-2278`). `RunFailureReasonSerializer.unpack` maps unknown enum values to `UNKNOWN` rather than throwing (`python_modules/dagster/dagster/_core/events/__init__.py:297-304`).
- Storage degradation: `handle_unpack_error` wraps any deserialization failure into an `ENGINE_EVENT` with `SerializableErrorInfo` and preserves original `message` (`python_modules/dagster/dagster/_core/events/__init__.py:423-447`). `get_records_for_run` raises `DagsterEventLogInvalidForRun` only for the poll path (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:494-496`), while `_get_event_records` for cross-run silently skips unparsable rows with a warning (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:948-963`). Schema upgrades use Alembic revisions (`stamp_alembic_rev`, `run_alembic_upgrade` at `python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:181-204`) and secondary-index migrations gated by `SecondaryIndexMigrationTable` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:621-642`) — no event-log format version field exists; versioning is per-type via whitelist evolution.

## Architectural Decisions

- **Per-run sharded SQLite as default.** `SqliteEventLogStorage` stores each run in `<run_id>.db` plus a mirrored `index` shard (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:174-258`, `python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:260-273`). Chosen to isolate write contention and keep per-run log size bounded on single-node deployments; tradeoff is no global autoincrement and requiring `RunShardedEventsCursor` fan-out for cross-run queries.
- **Append-only SQL table as event journal, not an explicit event store with aggregate versions.** No `expectedVersion`/optimistic-concurrency column; writes are `INSERT` with DB-assigned `id` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:388-401`). Simpler than versioned event sourcing; relies on run-level execution exclusion for ordering rather than CAS on the log.
- **Dual envelope (`EventLogEntry` outer, `DagsterEvent` inner) over single flattened envelope.** Outer holds framework logging concerns (`level`, `user_message`, `timestamp`, `run_id`); inner holds domain typing and lineage (`step_handle`, `event_type`, `event_specific_data`) (`python_modules/dagster/dagster/_core/events/log.py:31-44`, `python_modules/dagster/dagster/_core/events/__init__.py:462-478`). Enables reuse of Python logging pipeline (`StructuredLoggerHandler`, `construct_event_record` at `python_modules/dagster/dagster/_core/events/log.py:183-209`) but forces consumers to handle `is_dagster_event` branching.
- **Serdes whitelist as schema contract instead of protobuf/Avro.** Every persisted struct enumerates its stable name and field maps, enabling rename-tolerant evolution without explicit `schema_version` per event. Degradation to `ENGINE_EVENT` keeps readers forward-compatible.
- **Poll + filesystem-notify watchers over server-push stream.** `SqlPollingEventWatcher` uses an adaptive 0.25–16s backoff (`python_modules/dagster/dagster/_core/storage/event_log/polling_event_watcher.py:13-14,168-198`); sharded SQLite uses `watchdog.Observer` on `*.db` files (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:492-568`). Simple, portable across storage backends, but latency-sensitive vs brokered pub/sub.
- **Mirroring strategy for cross-run indexes.** Only asset/check/status events are proactively mirrored to the index DB; generic step/engine events remain sharded (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:274-303`). Optimizes the hot path (asset catalog) at the cost of making generic cross-run fan-out expensive.

## Notable Patterns

- **Validated discriminated union for payloads.** `_validate_event_specific_data(event_type, data)` checks `inst_param` per `DagsterEventType` at construction (`python_modules/dagster/dagster/_core/events/__init__.py:333-372`), so an `ASSET_MATERIALIZATION` cannot be constructed with `EngineEventData` — a lightweight form of envelope schema enforcement.
- **Opaque cursor as base64 JSON.** `EventLogCursor` hides whether it is offset vs id-based, making pagination resilient to internal representation changes while exposing `from_storage_id` ergonomic helper (`python_modules/dagster/dagster/_core/event_api.py:45-63`). Used uniformly in `EventLogConnection.cursor`/`EventRecordsResult.cursor` and in `watch` callback second argument.
- **Batch metadata without sequence.** `DagsterEventBatchMetadata(id=uuid4(), is_end)` (`python_modules/dagster/dagster/_core/events/__init__.py:450-452`) groups batched asset observations/materializations emitted within one step — enables receiver to buffer until `is_end` without introducing a total order.
- **Idempotent watcher teardown on terminal status.** Watchdog `on_modified` auto-calls `end_watch` when callback returns `SUCCESS|FAILURE|CANCELED` (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:559-564`, `python_modules/dagster/dagster/_core/storage/event_log/sqlite/consolidated_sqlite_event_log.py:193-198`) — prevents leaked observers.
- **Offset-to-id cursor migration.** `get_logs_for_run` accepts legacy `int` offset cursors but warns and converts to `EventLogCursor.from_offset(offset+1)` (`python_modules/dagster/dagster/_core/storage/event_log/base.py:232-238`), providing a migration path while deprecating non-id cursors.
- **Asset lineage inside materialization, not as separate link event.** `StepMaterializationData(asset_lineage: Sequence[AssetLineageInfo])` (`python_modules/dagster/dagster/_core/events/__init__.py:1781-1804`) embeds upstream asset links directly in the materialization fact, unlike temporal-style separate `Link` records.

## Tradeoffs

- **Write-availability vs global ordering.** Sharded SQLite maximizes single-run write throughput (no cross-run lock) but sacrifices global sequence and forces timestamp ordering + run-list scan for cross-run queries (`_get_run_sharded_event_records` iterates `get_run_records(updated_after=...)` per run, `python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:369-406`). Consolidated/Postgres restores global id but reintroduces contention on a single table.
- **Durability vs latency of observation.** FS-notify watchers react within milliseconds to DB file `on_modified`; polling watcher worst-case 16s idle delay (`python_modules/dagster/dagster/_core/storage/event_log/polling_event_watcher.py:198`). Polling works on remote SQL (no fs) but is slower; fs-notify only works for local SQLite. No push broker like Kafka — tradeoff is zero extra infrastructure.
- **Flexibility of JSON serdes vs queryability.** Persisting `event` as `LongText` JSON (`python_modules/dagster/dagster/_core/storage/event_log/schema.py:18`) keeps schema evolution trivial but pushes filtering to extracted columns (`dagster_event_type`, `asset_key`, `partition`, `step_key`, `timestamp`). Querying `metadata` tags requires a secondary `asset_event_tags` join (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:875-901`), which is sparse.
- **Strict validation vs forward compatibility.** `before_unpack` remaps known old types, but unknown future types are not mapped — they surface as degraded `ENGINE_EVENT`s (`python_modules/dagster/dagster/_core/events/__init__.py:423-447`). This preserves availability but silently changes event semantics for forward-compat readers.
- **Storage-level deduplication vs consumer dedupe.** No producer-side idempotency key (e.g., dedup by `request_id`) — retries produce duplicate facts with new ids. Consumer must de-dupe via `storage_id` or domain keys (`asset_key + partition + timestamp`). Minimal write path complexity, higher read path burden.

## Failure Modes / Edge Cases

- **Duplicate on re-drive.** Because `store_event` is `INSERT`-only with new autoincrement (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:388-401`), a step that yields the same `ASSET_MATERIALIZATION` twice (retry/replay) creates two rows with different ids but identical payload — a consumer that keys on `(asset_key, partition)` without considering `storage_id` will double-count. Mitigation is `seen_storage_ids` tracking (`python_modules/dagster/dagster/_core/executor/step_delegating/step_delegating_executor.py:101-140`) or asset-level dedup via `last_materialization` index.
- **Gap on sharded cross-run resume.** If a run's `update_timestamp` is not bumped after its event was written, a `RunShardedEventsCursor` positioned after `run_updated_after` will never scan that run again (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:371-380`). The index-mirrored asset path avoids this for assets; generic cross-run tail does not.
- **Offset cursor skew.** Legacy `OFFSET` cursors (`from_offset`) count rows after filters; inserting events before the offset shifts which row offset `N` points to, causing missed or repeated events. The `STORAGE_ID` cursor is id-stable; the migration warning at `python_modules/dagster/dagster/_core/storage/event_log/base.py:233-237` nudges off offset usage but does not prevent it.
- **Unbounded fetch without limit enforcement.** `enforce_max_records_limit(limit)` caps `fetch_*` at 10000 or `MAX_LIMIT_GET_EVENT_RECORDS` env (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:125-140`), but `get_records_for_run` allows unlimited `limit=None` — a caller replaying a large run from cursor `-1` can OOM the instance.
- **Deserialization failure modes differ by API.** `get_records_for_run` raises `DagsterEventLogInvalidForRun` on any corrupted row (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:495-496`) — a single poison event blocks run tailing. `get_event_records` skips the row and logs a warning (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:961-963`), so cross-run consumers see silent gaps.
- **Polling watcher duplicate emission on cursor overlap.** If `DAGSTER_EXECUTOR_POP_EVENTS_OFFSET>0`, `_pop_events` deliberately backtracks `cursor - offset` to survive late writes (`python_modules/dagster/dagster/_core/executor/step_delegating/step_delegating_executor.py:126-138`); overlap window events are re-delivered and must be filtered via `seen_storage_ids`. Without that set a consumer would process the same `STEP_SUCCESS` twice.
- **FS-notify missed modification on SQLite WAL coalesce.** `SqliteEventLogStorageWatchdog` triggers on `event.src_path == <run_id>.db` `on_modified` (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:566-568`); WAL-mode SQLite may batch commits into `-wal` file modifications that do not raise `on_modified` for the `.db` file for short windows, delaying observer notification until next poll or next fsync.
- **Timestamp ordering tie-breaking.** Sharded cross-run ordering sorts by `timestamp` then by scan order of `get_run_records` (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:364-367`); two events with equal `timestamp` (common at millisecond granularity for bulk materializations) have nondeterministic global order — `BATCH_WRITABLE_EVENTS` using `DagsterEventBatchMetadata.id` does not provide an intra-batch sequence.

## Future Considerations

- Introduce a per-`run_id` monotonic `sequence` field distinct from global `id` so `id` can remain global on consolidated stores while per-run streaming stays deterministic even after storage migration; today `id` is conflated with per-run cursor on sharded stores.
- Add `correlation_id`/`causation_id` (UUID, `traceparent`) to `DagsterEvent`/`EventLogEntry` populated from OpenTelemetry context, and thread it through `logging_tags` → `DagsterLogManager` → `EventLogEntry` so `JobFailureData.first_step_failure_event` is not the only retained cause; enables cross-system join without synthesizing from tags.
- Enforce idempotent write: accept an optional client-supplied `idempotency_key` (e.g., deterministic from `run_id + step_key + attempt + output_name`) and add a unique constraint `UNIQUE(run_id, idempotency_key)` to make re-drive safe without row duplication.
- Standardize cross-run cursor: deprecate `OFFSET` cursors entirely and require `RunShardedEventsCursor` with `run_updated_after` for sharded stores, or adopt consolidated storage by default so a single `STORAGE_ID` namespace is authoritative; document the gap risk of fan-out scans in the public docstring of `EventLogStorage.get_event_records`.
- Version the envelope explicitly (`event_schema_version: int`, or per-type `DagsterEvent.schema_version`) instead of relying solely on serdes field evolution, to support breaking payload changes beyond additive renames.
- Add `has_more` + limit enforcement to `get_records_for_run` mirroring `fetch_*`, and make poison-event handling consistent (skip+warn or fail-fast, not both) so reconnect logic can reason about partial streams.
