## Summary

BuildKit exposes two disjoint event systems rather than a single durable event log. The live build progress path is `Control.Status` — a per-build (`Ref`) server-streaming RPC that fan-outs in-memory `progress.Progress` items through `solver.Job.Status` into `StatusResponse` chunks (`Vertex`/`VertexStatus`/`VertexLog`/`VertexWarning`). The post-build durability path is `Control.ListenBuildHistory` backed by `history.Queue` (bbolt + content-store blobs) emitting `BuildHistoryEvent{STARTED,COMPLETE,DELETED}`. Neither path provides a typed event envelope with version/sequence/correlation/causation fields, monotonic per-subject sequence numbers, or cursor-based replay. Status history is best-effort, collapses by ID, and relies on timestamps for ordering; History provides full-state replay on subscribe (active map + DB scan) plus live pubsub, but no resume token, no gap/duplicate guarantees, and deletes are best-effort. Schema evolution is handled via proto3 additive fields and imperative legacy translation, not formal event versioning.

## Rating

**4 / 10 — Present but inconsistent, weakly documented, fragile.**

Rationale: Envelope fields exist (Vertex digest, Ref as correlation, timestamps, ProgressGroup, SourceInfo) but are split across two APIs with different durability/ordering semantics; no sequence/cursor, no idempotent replay, naming mixes state snapshots and past-tense lifecycle events; schema evolution relies on deprecated-field shims and a separate `CompatibilityVersion` for image output rather than event contract versioning; reconnect cannot guarantee exactly-once reconstruction — matches the 4-6 rubric ("present but inconsistent, weakly documented, or fragile").

## Answers to Dimension Questions

### 1. What ordering is actually guaranteed?

No explicit total order is guaranteed. Live status ordering is best-effort: `progressReader` collapses writes per `ID` (`dirty[ID] = p`) and sorts each `Read` batch by `Timestamp` (`slices.SortFunc` by `a.Timestamp.Compare(b.Timestamp)`) (`studies/ultraplan-daemon-events-study/sources/buildkit/util/progress/progress.go:164-170,241-246`); `solver/progress.go:81-94` re-sorts `Vertexes` by `Started` and `Statuses`/`Logs` by `Timestamp` per emitted `SolveStatus`. There is no per-vertex or per-build sequence number, so cross-batch ordering depends on clock monotonicity and gRPC stream order. History `Listen` ordering is weaker: active snapshot iterates a Go map (`for _, e := range h.active`) with random iteration order (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:800-811`), persisted scan emits in bbolt iteration order (lexicographic by Ref), only `filterHistoryEvents` with `Limit != 0` sorts by `CreatedAt` descending (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/filter.go:56-68`). Therefore ordering is at best timestamp-sorted within a chunk, not a durable per-subject (per-Ref/per-vertex) total order.

### 2. Can a reconnecting client resume without gaps or duplicates?

No. Neither `StatusRequest` nor `BuildHistoryRequest` carries a cursor/sequence/offset (`studies/ultraplan-daemon-events-study/sources/buildkit/api/services/control/control.proto:116-118,184-190`). `Status` is ephemeral: `Job.Status` reads from `progress.MultiReader`/`progressReader` which collapses by `dirty[ID]` — missed batches are lost, and there is no replay buffer (`studies/ultraplan-daemon-events-study/sources/buildkit/util/progress/progress.go:241-244`). The solver keeps jobs only 10s after `Discard` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:890-897`), then `Solver.Get` times out after 6s (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:717-743`). `llbsolver.Solver.Status` does offer a post-completion replay via `history.Queue.Status` reading the persisted status blob sequentially (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:351-416`), but only after the build completes and `recordBuildHistory` has called `ImportStatus` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history.go:185-206`). `ListenBuildHistory` replays the full `active` set plus all persisted records on every new subscription (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:770-868`), guaranteeing duplicates if the client re-subscribes, and `pubsub.Send` fans out via `go c.send` with buffered channel size 32 but no backpressure beyond dropping on `done` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/pubsub.go:22-54`), so gaps are possible under slow consumers. Disconnect mid-stream and reconnect from "last cursor" is not an API — the client must re-`Status(Ref)` from scratch (`studies/ultraplan-daemon-events-study/sources/buildkit/client/solve.go:369-397`) and accept either missed live updates or full replay duplicates.

### 3. Are events named as immutable past-tense facts?

Partially. `BuildHistoryEventType` uses past-tense lifecycle names `STARTED`, `COMPLETE`, `DELETED` (`studies/ultraplan-daemon-events-study/sources/buildkit/api/services/control/control.proto:192-196`) applied to `BuildHistoryEvent`. However the high-frequency live stream is not fact-typed: `StatusResponse` carries `Vertex` state snapshots (`Started`/`Completed`/`Error`/`Cached`) and `VertexStatus`/`VertexLog` deltas (`studies/ultraplan-daemon-events-study/sources/buildkit/api/services/control/control.proto:120-164`, `studies/ultraplan-daemon-events-study/sources/buildkit/client/graph.go:10-55`), which are mutable state observations, not immutable facts. `Vertex` transitions are modeled as `Started` → `Completed` on the same digest-identified object (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/progress.go:35-80`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:1368-1388`), so the consumer must infer "completed" from field presence rather than receiving a `VertexCompleted` fact. Naming therefore mixes past-tense build-lifecycle facts with stateful progress updates, violating a uniform "immutable past-tense fact" envelope.

### 4. Can the consumer tell why an event happened?

At build granularity, yes partially; at vertex granularity, weakly. `BuildHistoryRecord` captures `Frontend`, `FrontendAttrs`, `Exporters`, `Error` (`google.rpc.Status`), `CreatedAt`/`CompletedAt`, and result descriptors (`studies/ultraplan-daemon-events-study/sources/buildkit/api/services/control/control.proto:203-225`), and `recordBuildHistory` records provenance attestations and error details (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history.go:35-60,251-261`). Warnings carry `SourceInfo` + `Range` pointing to Dockerfile source (`studies/ultraplan-daemon-events-study/sources/buildkit/api/services/control/control.proto:156-164`). Vertex-level causation is available structurally via `Vertex.Inputs: []digest.Digest` and `Vertex.ProgressGroup` (`studies/ultraplan-daemon-events-study/sources/buildkit/client/graph.go:10-19`), and the solver maintains a full DAG in `state.parents`/`childVtx` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:53-55`). `Vertex.Error` carries the failure string and `Vary` errors wrap vertex digest (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:1339-1352`), but there is no explicit `correlationId`/`causationId`/`triggeredBy` envelope field; the consumer must reconstruct "why" by joining `Ref` (build correlation) + input digest DAG + error/source metadata, not from a first-class causation header.

### 5. How does a schema evolve without breaking old clients?

Via proto3 additive evolution plus imperative compatibility shims, not via event versioning. New fields are added with reserved/deprecated markers (e.g., `ExporterDeprecated`, `CacheOptionsEntry` evolution, `UsageRecord.Parent [deprecated=true]`) (`studies/ultraplan-daemon-events-study/sources/buildkit/api/services/control/control.proto:61-80,88-97`). `control/control.go:370-407` translates legacy `ExportRefDeprecated`/`ImportRefsDeprecated`/`ExporterDeprecated` into the new `Exporters`/`Exports`/`Imports` at request handling time, preserving wire compatibility at the cost of hidden server-side mutation. The one explicit version signal is `SolveRequest.CompatibilityVersion` (`studies/ultraplan-daemon-events-study/sources/buildkit/api/services/control/control.proto:80`), which gates image/OCI output serialization, not event envelope versioning. History records carry `Generation` increments (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:335`) and bbolt `versionBucket` migration (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:107-129`), but status events have no `typeVersion` or `schemaVersion`. Old clients can ignore unknown fields per protobuf, but there is no contract for consumer-driven schema negotiation or event upcasting.

## Architectural Decisions

- **Split live vs durable streams**: Live `Status(Ref)` serves in-memory progress (`solver.Job.pr`) while `ListenBuildHistory` serves durable history (`bbolt` + content blobs) (`studies/ultraplan-daemon-events-study/sources/buildkit/control/control.go:594-625` vs `336-345`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/solver.go:465-481`). Trade: low latency for active builds but no unified event log; clients need two APIs.
- **Ref as sole correlation key**: All Solve/Status/History operations key on `Ref = identity.NewID()` or caller-supplied `SolveOpt.Ref` (`studies/ultraplan-daemon-events-study/sources/buildkit/client/solve.go:107-110`). No global sequence; isolation is per-build, enabling concurrent builds but preventing cross-build causal joins.
- **Digest-addressed vertices as identity**: `Vertex.Digest` is the LLB op digest, `Vertex.Inputs` are input digests; solver `actives` map is keyed by `digest.Digest` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:520-594`). Reuses active vertices via `dgstWithoutCache` fallback, enabling cache-aware merging.
- **Collapsed progress pipe**: `progressReader.dirty[ID]` keeps only the latest `Progress` per ID per `Read` cycle (`studies/ultraplan-daemon-events-study/sources/buildkit/util/progress/progress.go:241-246`). Reduces chatter but loses per-update history.
- **Length-prefixed blob replay**: `history.Queue.ImportStatus` serializes each `StatusResponse` as `uint32 LE len + MarshalVT(bytes)` into a `application/vnd.buildkit.status.v0` blob (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:679-745`); replay is sequential `ReadAtLeast` loop (`385-413`). Simple and content-addressable, but not indexed for cursor seek.
- **Pubsub with decoupled send**: `pubsub.Send` iterates channels and `go c.send(v)` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/pubsub.go:22-28`) — prevents head-of-line blocking but introduces goroutine-per-subscriber-per-event overhead and no ordering across subscribers.
- **Backward-compat via translation not versioning**: `translateLegacySolveRequest` and `ProtoReflect` additive fields handle schema evolution without a formal envelope `version` (`studies/ultraplan-daemon-events-study/sources/buildkit/control/control.go:370-407`).

## Notable Patterns

- **Per-build MultiWriter fan-out**: `state.mpw = progress.NewMultiWriter(WithMetadata("vertex", dgst))` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:576-584`) and `connectProgressFromState` propagates `mpw.Add(pw)` to ancestors (`665-685`), so a single vertex write fans out to all jobs sharing that vertex.
- **Vertex-state coalescing**: `vertexStream.append` marks transitive cached inputs and deletes them from cache to avoid duplicate completion events (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/progress.go:110-143`), plus `encore()` synthesizes `Completed` for dangling vertices on EOF (`145-158`).
- **Finalizer gate for traces**: `Queue.AcquireFinalizer` / `Finalize` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:489-529`) defers history `COMPLETE` observability until async provenance/trace writers finish, with a 3s grace window before `stopTrace()` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history.go:283-332`).
- **Dual status retrieval**: `llbsolver.Solver.Status` tries history first (persisted), falls back to live solver (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/solver.go:465-481`) — allows post-completion re-query but requires the caller to know the `Ref` still exists.
- **Progress via context**: `progress.WithProgress(ctx, pw)` / `progress.FromContext` / `progress.NewFromContext` threads writers through `context.Context` (`studies/ultraplan-daemon-events-study/sources/buildkit/util/progress/progress.go:60-68,28-54`, `studies/ultraplan-daemon-events-study/sources/buildkit/util/progress/controller/controller.go:30-76`), a Go-idiomatic alternative to explicit event buses.

## Tradeoffs

- **Latency vs durability**: In-memory `progressReader` delivers sub-millisecond streaming but is ephemeral; durable history only materializes after build completion via `ImportStatus` blob commit (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:679-768`). Mid-build disconnects cannot be durably reconstructed.
- **State snapshots vs event facts**: Sending full `Vertex{Started,Completed,Error,Cached}` snapshots simplifies UI rendering (idempotent overwrite by `digest`) but doubles payload and requires sorting/dedup logic client-side (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/progress.go:81-94`, `studies/ultraplan-daemon-events-study/sources/buildkit/client/status.go:66-129` splitting on 1 MiB log threshold).
- **Map-iteration replay**: Full `active` + DB scan on each `Listen` subscription ensures new observers see history, but at O(N) cost and without pagination except `Limit` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:797-868`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/filter.go:52-73`).
- **No backpressure, bounded buffer**: `pubsub` channel size 32 with `go c.send` avoids blocking publishers but risks slow-consumer goroutine explosion and unobserved drops on `done` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/pubsub.go:10-54`).
- **Imperative migration**: Legacy field translation keeps wire compat without version negotiation, but obscures schema — clients cannot tell which fields were synthesized vs sent.

## Failure Modes / Edge Cases

- **Resume gap**: `Client.solve`'s status stream has a 5s inactivity timer that cancels `statusContext` (`studies/ultraplan-daemon-events-study/sources/buildkit/client/solve.go:255-282,369-397`); a transient network partition that exceeds the timer causes the session and status goroutines to cancel, and no cursor allows resumption — the consumer sees EOF and must restart polling.
- **Slow consumer / goroutine leak**: `pubsub.Send` spawns one goroutine per subscriber per event (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/pubsub.go:22-28`); with many subscribers or slow `ListenBuildHistory` consumers, goroutine count can grow unbounded; the `select {case ch <- v; case <-done}` prevents blocking but not accumulation before `done` fires.
- **Dirty collapse loss**: If two `VertexStatus` updates for the same `ID` occur between `Read` calls, only the last is returned (`studies/ultraplan-daemon-events-study/sources/buildkit/util/progress/progress.go:241-246`) — fine for gauges but would violate exactly-once event semantics.
- **Clock skew ordering**: Ordering relies on `time.Now()` at `Write` (`studies/ultraplan-daemon-events-study/sources/buildkit/util/progress/progress.go:231-232`) and `Started` timestamps synthesized in `solver/jobs.go:1371,1379-1381`; NTP adjustments or scheduler delays can reorder `Timestamp`-sorted batches.
- **Job expiry race**: `Job.Discard` sleeps 10s before `delete(jl.jobs, id)` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:890-897`) and `Solver.Get` waits 6s (`717-743`); a `Status(Ref)` request arriving 7-10s after `Discard` races between "found but progress already closed (EOF)" vs `UnknownJobError`.
- **Blob size / split**: `SolveStatus.Marshal` splits on 1 MiB log threshold (`studies/ultraplan-daemon-events-study/sources/buildkit/client/status.go:102-110`) but `ImportStatus` buffers up to 32 KiB and reallocates per frame (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:690-739`); a single huge log line >32 KiB triggers reallocation, and a build producing >1 MiB logs yields many `StatusResponse` frames, increasing content-store writes.
- **History delete while subscribed**: `Queue.delete` checks `refs[ref]` reference count and defers `DELETED` emission until `Listen` unsubscribes (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:241-266,777-795`), so a subscriber holding a `Ref` filter will not see `DELETED` until it unsubscribes — a minor liveness hazard.
- **Content-store GC interaction**: History blobs are tied to leases (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/history/buildhistory.go:418-485,567-635`); lease expiration (5 min temporary) or `GarbageCollect` after `delete` could remove blobs before the consumer fetches them via `ReaderAt`.

## Future Considerations

- Introduce a per-Ref monotonic sequence (e.g., `uint64 sequence` or ULID) on `StatusResponse`/`BuildHistoryEvent` and expose `StatusRequest{Ref, AfterSequence}` / `ListenBuildHistory{AfterGeneration}` to enable idempotent resume without gaps/duplicates — requires persisting sequence in the `ImportStatus` blob index.
- Unify envelope: wrap `Vertex`/`VertexStatus`/`VertexLog`/`VertexWarning` in a `oneof Event { VertexEvent, StatusEvent, LogEvent, WarningEvent }` with `eventId`, `eventType`, `eventVersion`, `timestamp`, `correlationId (Ref)`, `causationId (parent vertex digest)` — enables schema evolution via `typeVersion`.
