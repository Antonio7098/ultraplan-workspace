## Summary

Temporal recovers by event sourcing, not process resume. The durable checkpoint is the persisted workflow history branch plus a mutable-state snapshot (execution info/state, activity/timer/child maps, `NextEventID`/`DBRecordVersion`), written atomically with new history events and durable transfer/timer tasks via conditional `UpdateWorkflowExecution`. There is no startup reconciliation loop that scans non-terminal workflows; recovery is lazy and fencing-based: shard ownership is acquired via RangeID (`service/history/shard/context_impl.go`), workflow state is reloaded from DB into an LRU cache on next access, outstanding workflow/activity tasks time out via durable timer tasks and are rescheduled, and stale/orphaned dispatches are dropped by stamp/attempt/version checks. Speculative workflow tasks and in-memory buffers are explicitly non-durable and lost on crash. SIGKILL during an external side effect is safe to retry only if the side effect was gated by a durably recorded event; otherwise the timeout/retry machinery re-dispatches the logical operation, and idempotency depends on the activity/workflow implementation plus server-side deduplication (request ID, stamp, `TaskAlreadyStarted`/`ObsoleteMatchingTask`).

## Rating

**8 / 10** — Clear, tested durability model (event history + snapshot + conditional write + RangeID fencing + timeout-driven rescheduling + stamp fencing), with explicit in-memory vs durable distinction. Deducted because there is no single crash-recovery planner/controller or documented host-reboot runbook in-repo; orphan cleanup is distributed across timeout executors, cache eviction, and matching drop-reasons rather than one observable reconciliation pass, and exactly-once side effects are explicitly not guaranteed by the server.

## Answers to Dimension Questions

**1. What survives a client crash, daemon crash, and host reboot?**
- *Client (SDK worker) crash:* nothing on the worker needs to survive. All progress is the server-side history branch + mutable-state snapshot + pending durable tasks (`common/persistence/data_interfaces.go:348-402`, `common/persistence/history_manager.go:481-535`). A crashed worker's leased workflow/activity task simply times out (ScheduleToStart if never started, StartToClose if started) and the timer executor appends a timed-out event and schedules a fresh task (`service/history/timer_queue_active_task_executor.go:440-478`). Sticky-queue affinity is best-effort: first failure clears stickiness (`service/history/workflow/workflow_task_state_machine.go:1059-1062`) and matching falls back to the normal queue on `StickyWorkerUnavailable` (`service/matching/matching_engine.go:605`, `service/history/api/recordworkflowtaskstarted/api.go:114-136`).
- *Daemon (history/matching) crash:* everything committed via `UpdateWorkflowExecution` survives in the configured store (Cassandra/SQL): history nodes, snapshot/mutation, durable transfer + timer tasks. Shard RangeID fencing prevents a revived owner from writing (`common/persistence/data_interfaces.go:148`, `service/history/shard/context_impl.go:2030-2149`). On reassignment the new owner reloads shard metadata, renews the range, starts the engine, and reloads queues (`service/history/shard/context_impl.go:2084-2115`, `service/history/queues/queue_base.go:235-249`). Queue `checkpoint()` state (reader scopes, deletion watermark) is recomputed from persisted tasks on load (`service/history/queues/queue_base.go:295-339`).
- *Host reboot:* identical to daemon crash provided the DB is remote/durable (the only supported topology in this tree; no local-disk checkpoint format was found). What does NOT survive any of the three: speculative workflow tasks and their timeout tasks (`CategoryMemoryTimer`, `service/history/queues/speculative_workflow_task_timeout_queue.go:73-99`), transient-WT in-memory state, workflow-cache contents, and intermediate task-completion page buffers (`service/history/workflow/context.go:219-289`). Those are safely re-derivable: speculative work is re-created on the next update/dispatch, transient WTs are re-materialized as normal scheduled events when buffered events exist (`service/history/workflow/workflow_task_state_machine.go:326-334`).
- Search boundary: no host-local snapshot/WAL directory, no `fsync`/disk-checkpoint config, and no boot-time "scan all open workflows" reconciler were found; recovery is lazy per-workflow on next task execution or poll.

**2. Can arbitrary in-memory execution resume, or only checkpointed work?**
- Only checkpointed work. The unit of durability is a committed history event batch + state transition. Anything not yet committed (SDK-side workflow code progress, in-flight `RespondWorkflowTaskCompleted` pages, speculative dispatch, cached mutable state) is discarded and re-driven by replay: the next workflow task redelivers history from `PreviousStartedEventId+1` (sticky) or from the start (normal) (`service/history/api/recordworkflowtaskstarted/api.go:270-372`). `reconcileTaskCompletionBuffer` explicitly drops a page buffer whose task identity is no longer current (`service/history/workflow/context.go:219-231`). Update delivery similarly resends unsent messages on the next started task (`service/history/api/recordworkflowtaskstarted/api.go:460-465`).

**3. When is a new attempt started automatically?**
- Workflow task ScheduleToStart or StartToClose timeout fires a durable timer task; the executor appends `WorkflowTaskTimedOut` and immediately schedules a new workflow task in the same transaction (`service/history/timer_queue_active_task_executor.go:440-478`, `service/history/workflow/workflow_task_state_machine.go:267-302`). Failure via `RespondWorkflowTaskFailed` follows the same `failWorkflowTask(true)` path (`service/history/workflow/workflow_task_state_machine.go:256-258`). Sticky timeouts do not inflate `Attempt` so the retry is not mistaken for a transient failure (`service/history/workflow/workflow_task_state_machine.go:260-265`).
- Activity attempts retry automatically while `RetryActivity` returns `IN_PROGRESS`: backoff computed from retry policy / application delay, persisted as an `ActivityRetryTimerTask` (`service/history/workflow/mutable_state_impl.go:6937-6959`, `service/history/timer_queue_active_task_executor.go:540-559`). Cron/retry/backoff timers also auto-schedule the next workflow task (`service/history/timer_queue_active_task_executor.go:480-538`).
- Failover/version conflict auto-fails the started task and schedules a normal one (`service/history/ndc/workflow.go:221-235`).

**4. When is human/manual retry required?**
- When the retry policy is exhausted or absent (`RETRY_POLICY_NOT_SET`, `RETRY_STATE_TIMEOUT`, `NON_RETRYABLE_FAILURE` in `service/history/workflow/mutable_state_impl.go:6880-6910`) the activity closes with a failure event and the workflow author must handle it in code (or an operator must reset/terminate/retry via admin APIs — no auto-resurrection path was found in the studied tree). Workflow-level close (completed/failed/terminated/cancelled) is terminal; a new run requires explicit start/reset. Buffered-update loss (`WorkflowTaskCompletionBufferLost`) requires the SDK to resend from page 0 (`service/history/workflow/context.go:282-289`). `BestEffortDeleteTasks` omissions are safe to ignore by design (`common/persistence/data_interfaces.go:372-373`).

**5. How are orphaned resources discovered?**
- No central orphan scanner. Orphans are fenced lazily at four layers: (a) shard fencing — old owner writes fail with `ShardOwnershipLostError` after RangeID moves (`service/history/shard/context_impl.go:2120-2149`); (b) task fencing — late `RecordWorkflowTaskStarted` calls fail stamp/attempt/schedID checks and matching drops them as `NotFound`/`TaskAlreadyStarted`/`ObsoleteMatchingTask` (`service/history/api/recordworkflowtaskstarted/api.go:69-112`, `service/matching/matching_engine.go:820-864`); (c) timeout-task cancellation — `recordTimeoutTasksForDeletion`/`BestEffortDeleteTasks` plus `RemoveSpeculativeWorkflowTaskTimeoutTask` cancel superseded timers (`service/history/workflow/workflow_task_state_machine.go:1042-1047`, `service/history/workflow/mutable_state_impl.go:7479-7485`); (d) queue rescheduler — failed executables are parked and resubmitted per namespace rather than leaked (`service/history/queues/rescheduler.go:31-40`, `service/history/queues/rescheduler.go:139-169`). Matching-side leases (`service/matching/db.go:150`) and poll-expiry jitter prevent thundering-herd resurrection of stale polls (`service/matching/matching_engine_test.go:377-397`).

> SIGKILL the execution owner during an external side effect. On restart, how does the system decide whether retry is safe?
>
> It does not — the server cannot know whether the side effect committed. Safety comes from the operation type: workflow-code side effects must be expressed as activities (or Nexus operations) whose timeout + retry policy re-drives the logical operation (`service/history/workflow/mutable_state_impl.go:6908-6959`, `service/history/hsm/nexusoperations/executors.go:233`, `service/history/hsm/nexusoperations/executors.go:623`); activities that already started are retried only if the failure is retryable, otherwise the failure event closes the activity and workflow code decides. At-least-once dispatch is the contract: a killed owner leaves a started task that either completes (if `Respond*` raced the kill and committed) or times out and is rescheduled, with duplicates suppressed by stamp/request-ID/`TaskAlreadyStarted` checks — but non-idempotent external effects require activity-level idempotency keys or manual reconciliation. There is no server-side "was the HTTP call sent?" probe in the studied code.

## Architectural Decisions

- **Event history is the checkpoint.** Mutable state is a cached projection; every state change commits history events + snapshot + tasks atomically with `NextEventID`/`DBRecordVersion` optimistic concurrency (`common/persistence/data_interfaces.go:348-402`, `common/persistence/execution_manager.go:147-235`, `common/persistence/sql/execution_util.go:649-659`).
- **Timeouts, not heartbeats from the orchestrator, drive recovery.** ScheduleToStart and StartToClose timer tasks are the crash detectors for both workflow and activity tasks (`service/history/workflow/task_generator.go:441-544`, `service/history/timer_queue_active_task_executor.go:440-478`).
- **Sticky is a performance hint, cleared on first failure.** First WFT failure on a sticky queue clears stickiness and retries on the normal queue without inflating attempt counters (`service/history/workflow/workflow_task_state_machine.go:1057-1062`, `service/history/api/recordworkflowtaskstarted/api.go:114-136`).
- **Speculative execution is explicitly ephemeral.** Speculative WTs never create transfer tasks and their timeouts live in a memory queue; loss is by design and recovered by materializing a normal WT (`service/history/workflow/task_generator.go:468-517`, `service/history/queues/speculative_workflow_task_timeout_queue.go:15-99`).
- **Fencing over reconciliation.** Rather than a boot-time scan, concurrent/old owners are fenced by RangeID (shard), stamp/attempt (task), and version/failover-version (replication) (`service/history/shard/context_impl.go:2030-2149`, `service/history/api/recordworkflowtaskstarted/api.go:69-79`, `service/history/ndc/workflow.go:210-264`).

## Notable Patterns

- Conditional-write transaction (`UpdateWorkflowExecution` with `Condition`/`DBRecordVersion`/`NextEventID`) as the single linearization point for workflow state.
- Timer-task-as-watchdog: every dispatch plants its own resurrection timer at dispatch time.
- `BestEffortDeleteTasks` for idempotent cancellation of superseded timers — deletion failure is non-fatal.
- Rescheduler park-and-resubmit for poisoned queue executables instead of blocking the queue.
- `Transient` workflow tasks: consecutive failures reuse the same scheduled event ID until new history forces materialization — avoids history bloat during crash loops.

## Tradeoffs

- Lazy reload keeps restart fast (no global scan) but delays detection of stuck workflows until their timers fire or they are polled; there is no "list all non-terminal and verify" pass.
- At-least-once task redelivery simplifies crash handling but pushes exactly-once burden to activity authors (idempotency keys, request IDs).
- Sticky queues cut history transfer cost but add a failure mode (stale sticky dispatch) handled by extra round trips (clear-sticky + reschedule + `StickyWorkerUnavailable` fallback).
- Memory-queue speculative tasks reduce persistence write amplification at the cost of guaranteed loss on history-process crash — acceptable only because speculative work is retryable by construction.

## Failure Modes / Edge Cases

- Kill during `UpdateWorkflowExecution` commit: conditional write either commits fully (new owner sees new `NextEventID`) or fails (old state intact); no torn workflow state, but the client may need to retry the API.
- Kill between transfer-task enqueue and matching dispatch: timer (ScheduleToStart) eventually reschedules; matching may also hold a duplicate persisted task, suppressed by stamp checks on start.
- Kill after external side effect, before `RespondActivityTaskCompleted`: activity times out (heartbeat/StartToClose) and retries — non-idempotent side effect executes twice unless the activity is idempotent.
- Shard move during in-flight write: `ShardOwnershipLostError` → shard stops; in-flight workflow leases release without committing; new owner reloads pre-crash snapshot.
- Clock skew: timeout visibility timestamps derive from workflow virtual time converted via `ToRealTime` at the shard boundary (`service/history/workflow/mutable_state_impl.go:7464-7468`); large skew delays resurrection timers.
- Buffer-overflow during paginated completion (`ErrTaskCompletionBufferSizeExceeded` / `BufferLost`): partial progress dropped, SDK must resend from page 0.
