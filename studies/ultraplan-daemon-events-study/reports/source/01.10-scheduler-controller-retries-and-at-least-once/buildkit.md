## Summary

BuildKit's scheduler is a reconciliation-style, in-memory DAG controller (`solver/scheduler.go`, `solver/edge.go`, `solver/jobs.go`), not a durable queue with retry budgets. A single `scheduler.loop` goroutine dispatches edges FIFO off a deduped `waitq`; each `edge.unpark` reconciles `desiredState` (what requesters want: `initial → cache-fast → cache-slow → complete`) against observed `edgeState` + dependency states, then issues async work through `pipe` channels (`solver/internal/pipe/pipe.go`). Deduplication is strong: `edgeIndex.LoadOrStore` + `mergeTo` coalesces identical cache keys, and `flightcontrol.Group` single-flights `CacheMap`/`Exec`/`CalcSlowCache` per shared op. Concurrency is unbounded in the solver; bounding happens one layer down in op `Acquire()` via a shared `semaphore.Weighted` sized from `max-parallelism` config. There is no transient/permanent/throttle taxonomy, no retry budget/backoff for failed steps (only canceled work is retried; real errors are sticky), and no crash recovery — all scheduler, cache-key, and result state is process memory. The net semantic is at-most-once execution per daemon lifetime with content-cache idempotency on the read path, not at-least-once with safe retries.

## Rating

**5/10 — Present but inconsistent, weakly documented, fragile (for this dimension).**

Rationale: desired-vs-observed reconciliation, FIFO dispatch, dedup/merge, cancel-aware singleflight, semaphore capacity, and duplicate-execution tests are real and explicit. But stacked against the dimension rubric: no retry policy object, no failure taxonomy beyond canceled/not-canceled, no backoff/jitter for step failures (the only backoff lives inside `flightcontrol` coalescing), no priority/fairness, no durability/capacity recovery, and external side effects (exec, push) have no idempotency token — so a crash between work and acknowledgement is a retry-by-rebuild with no safety guarantee.

## Answers to Dimension Questions

1. **Can the same logical step execute more than once?**
   Yes, across time but not concurrently within one daemon lifetime. Concurrent identical vertices are coalesced: `edgeIndex.LoadOrStore` + `mergeTo` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler.go:153-178`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/index.go:81-121`) plus `flightcontrol` single-flight on `exec`/`cachemap-<n>`/`slow-compute-<n>` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:995-997`) guarantee one execution — proven by `execCallCount==1` parallel tests (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler_test.go:206-207`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler_test.go:375-378`). But memoization is RAM-only (`execDone/cacheDone` in `studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:1005-1010`); after `Discard`/GC or daemon restart the same digest re-executes. Retry after a real (non-cancel) failure does not happen automatically — the error is cached (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:1261-1274`) — so "more than once" requires a new build/job, not scheduler retry.

2. **Is retry policy centralized or stacked across layers?**
   There is no step-retry policy object at any layer — no max-attempts, no per-error budget. What exists is stacked *coalescing/cancel* handling, not failure retry: (a) `edge.respondToIncoming`/`createOutgoingRequest` cancel-and-replace dep pipes (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/edge.go:880-899`); (b) `flightcontrol.Group.Do` retries internally only on `errRetry` with jittered backoff capped at 15s (`studies/ultraplan-daemon-events-study/sources/buildkit/util/flightcontrol/flightcontrol.go:34-55`); (c) `sharedOp` suppresses memoization on cancel so the next waiter re-runs (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:1105-1111`). Non-cancel errors propagate immediately with `WithOp/WrapVertex` attribution and stick. Net: decentralized cancel-recovery, absent failure-retry.

3. **How does the scheduler recover capacity after crashes?**
   It does not need to and does not try: capacity is a process-local `semaphore.Weighted` acquired in `Acquire()` and released by `defer release()` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/llbsolver/ops/exec.go:592-603`). No lease table, no fencing, no WAL. A crash drops the semaphore, `waitq`, `actives`, and `edgeIndex` together; restart recreates the semaphore from `max-parallelism` config (`studies/ultraplan-daemon-events-study/sources/buildkit/cmd/buildkitd/main_oci_worker.go:327-330`) with zero in-flight state. In-flight external work (e.g., a started container) is orphaned to the executor/worker layer, not reaped by the solver.

4. **Are scheduled and started events semantically distinct?**
   Yes. "Scheduled" is an `edgeRequest{desiredState}` injected into the pipe graph (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler.go:220`, escalated per-dep in `studies/ultraplan-daemon-events-study/sources/buildkit/solver/edge.go:841-878`); "started" is the moment a `NewFuncRequest` closure actually invokes `CacheMap/Exec/CalcSlowCache`, which separately emits progress `Started` → `Completed/Error` via `notifyStarted` (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:1368-1388`). Many scheduled escalations (e.g., `cache-fast` probes) never start an exec; `respondToIncoming` can `Update` (state push), `Finalize` (complete), or leave open for a future dispatch (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/edge.go:792-803`).

5. **Can priority/fairness decisions be tested deterministically?**
   No — because there are none to test. Dispatch is strict FIFO with `waitq` dedup (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler.go:81-96`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler.go:192-207`); no priority field exists on `edge`, `edgeRequest`, or `dispatcher`. Deterministic tests that do exist control *overlap* (paired `blockingFuncion(2)` barriers in `TestParallelInputs`, `TestSingleLevelCacheParallel`) to assert dedup/parallelism, not ordering fairness. A fairness regression test would have nothing to latch onto short of adding a priority lane.

6. **Crash after the external work succeeds but before acknowledgement. Is retry expected, and is the side effect safe?**
   Retry is expected only in the weak sense: nothing was memoized (`execDone` set only inside the `complete` branch after `op.Exec` returns, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:1261-1274`; cache `Save` happens in `execOp` after `Exec`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/edge.go:997-1015`), so a rebuild re-executes the vertex. Safety is not guaranteed: `Exec` has no idempotency token and `Acquire` is just a semaphore, so a non-hermetic op (network fetch, push, container side effect) can run twice with visible duplication. The read path is safe (content-addressed `Cache().Query/Records/Load`), but the write path is at-most-once-per-process with no exactly-once mechanism. No evidence found of a commit/ack split, WAL, or dedup key for external effects; searched `solver/edge.go` exec/save path, `solver/jobs.go` memoization, `worker/`, and `errdefs/`.

## Architectural Decisions

- **Single-threaded reconcile + async work**: one `loop()` goroutine owns all graph mutation; expensive work (`CacheMap`, `Exec`, slow-cache digest) runs in `pipe.NewWithFunction` goroutines. Keeps the DAG consistent without fine-grained locking at the cost of scheduler throughput being single-threaded.
- **Desired-state escalation over explicit task queue**: no task rows; pressure propagates as `desiredState` upgrades and `currentKeys`/`currentState` deltas. Enables fine-grained cache-vs-exec staging (`cache-fast` → `cache-slow` → `complete`) and lazy dep fetching.
- **Content-key dedup as the concurrency control**: `edgeIndex` + `mergeTo` + `flightcontrol` replace locks/queues for the thundering-herd case; duplicate builds share pipes and results.
- **Cancel is first-class, failure is terminal**: `Canceled` propagates through pipes, cancels func contexts, and bypasses memoization; all other errors are attributed (`WithOp`/`WrapVertex`/`SlowCacheError`) and stuck to the edge/vertex.
- **Capacity pushed to ops**: solver never counts slots; each op type self-throttles on a shared weighted semaphore, with `BuildOp` deliberately exempt. Simple and worker-scoped, but invisible to the scheduler (no backpressure signal, no queue-depth metric).

## Notable Patterns

- **Reconciliation with self-checking invariants**: `dispatch()` asserts no dispatch leaves `incoming` open without `outgoing` and vice versa, converting algorithm bugs into edge failures with a "please report with BUILDKIT_SCHEDULER_DEBUG=1" message (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler.go:180-189`).
- **Two-phase slow-cache with skip heuristics**: `skipPhase2SlowCache`/`skipPhase2FastCache` prioritize unmatched deps to avoid loading unneeded inputs (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/edge.go:293-321`); covered by `TestOptimizedCacheAccess{,2}`.
- **Late-joiner key backfill**: completed edge appends committed keys to `e.keys` so shared waiters arriving post-completion still get cache-probe data (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/edge.go:638-647`).
- **Progress-coupled lifecycle**: every `CacheMap`/`Exec`/`LoadCache` wraps execution in tracing span + `notifyStarted` vertex progress write, coupling observability to the attempt itself (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:1160-1167`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/jobs.go:1240-1246`).

## Tradeoffs

- **At-most-once + content cache vs. durable at-least-once**: cheap, fast, and correct for hermetic builds; wrong for side-effecting steps. No WAL/journal means zero recovery cost but total loss on crash.
- **FIFO simplicity vs. starvation/priority**: no head-of-line blocking logic beyond `waitq` dedup; a flood of cheap vertices can delay an interactive one. No quota per job/session — one job's subgraph can saturate the shared semaphore.
- **Semaphore-at-op vs. scheduler-aware admission**: ops block inside `Acquire` holding a func-pipe goroutine; the scheduler sees them as `hasActiveOutgoing` and keeps dependents parked. Works, but scheduler cannot shed load, reorder, or report queue depth.
- **Sticky errors vs. flaky-infra resilience**: caching non-cancel errors avoids retry storms and duplicate billing, but a transient registry/network blip fails the build with no backoff — caller (client/CI) must retry the whole solve.
- **Single dispatch thread vs. scale**: eliminates graph races; at 1000-node graphs (`TestHugeGraph`) dispatch overhead is still fine, but dispatch is a hard serial bottleneck under very wide graphs.

## Failure Modes / Edge Cases

- **Daemon crash mid-`Exec`**: external effect may have happened; solver state (including any `Save`) is gone; rebuild re-executes with no dedup. No evidence of orphan reaping in solver scope.
- **Transient fetch failure**: no classification — treated identically to a deterministic build error, memoized per `sharedOp`, surfaced with vertex digest. Whole-build retry required.
- **Cancel race**: two jobs sharing a vertex where one cancels: `flightcontrol.wait` distinguishes last-canceller (waits for fn shutdown, returns real result) from early leavers (return `context.Cause`); `TestSingleCancelParallel` covers the second-job-continues case (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler_test.go:557-630`).
- **Semaphore leak on `Acquire` ctx-cancel**: `semaphore.Acquire(ctx,1)` returns ctx error without holding the slot — safe; but a canceled waiter still leaves its edge parked until the next `signal`, adding latency, not deadlock.
- **Merge across dependency boundary refused**: `mergeTo` skipped when `isDep` in either direction or owner-chain conflict (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler.go:159-174`) — prevents cycles at the cost of duplicate execution for near-identical subgraphs.
- **`IgnoreCache` poisoning**: `LoadOrStore`/`mergeTo` guards (`studies/ultraplan-daemon-events-study/sources/buildkit/solver/scheduler.go:290-292`, `studies/ultraplan-daemon-events-study/sources/buildkit/solver/index.go:100-103`) keep forced-rerun vertices from merging into cached ones; misconfiguring `IgnoreCache` on a parent forces full subtree re-execution (see `TestRepeatBuildWithIgnoreCache`).

## Future Considerations

- Add an explicit `RetryPolicy` type (max attempts, retryable-error predicate, backoff/jitter) at the `SolverOpt` or per-vertex `Options` level, and thread attempt counts through `notifyStarted`/progress so retries are observable.
- Introduce a minimal failure taxonomy (`transient`/`throttle`/`conflict`/`permanent`) in `solver/errdefs`, mapping gRPC/containerd/registry errors, so only safe errors retry.
- Give `Exec` an idempotency/commit key (e.g., cache-key-gated `Save` or executor-side dedup) to make crash-between-work-and-ack safe; alternatively document non-idempotent ops as at-most-once.
- Expose scheduler queue depth, `waitq` size, semaphore utilization, and `flightcontrol` coalescing hits as metrics; add a deterministic FIFO-order unit test (scripted `signal` sequence asserting dispatch order) and a fairness/priority lane if head-of-line blocking matters.
- For crash recovery, persist at minimum the committed `ExportableCacheKey` set (already content-addressed) so restarts can skip re-execution even when `actives` are lost.
