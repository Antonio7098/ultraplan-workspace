## Summary

Dagster splits events into two durability tiers: (1) a durable, synchronously-written SQL event log for run/step/asset lifecycle facts, and (2) ephemeral fan-out (in-process subscribers, per-run watcher threads, GraphQL `asyncio.Queue`, compute-log file tails) with no backpressure isolation. Every `handle_new_event` does a blocking `store_event` DB write on the execution hot path, then synchronously fans out to in-process subscribers. Opt-in batching (`DAGSTER_EVENT_BATCH_SIZE`, default 0 = off) only reduces round-trips, it does not decouple the write path. UI/delivery uses cursor-paginated polling (`storage_id` cursors, 1000-row chunks, 0.25s→16s backoff) so a slow consumer can always replay, but the live bridge is an unbounded `asyncio.Queue` and one polling thread per watched run. There is no drop/coalesce/sample policy for high-volume events and no automatic retention/TTL/compaction job: storage grows until explicit `delete_run` / `delete_events` / `wipe` / `wipe_asset` / `purge_ticks` calls. Compute logs (stdout/stderr) are a separate file-based tier with 1 MB chunked reads and no size cap or pruning.

## Rating

**5/10 — Present but inconsistent, weakly documented, fragile under flood.**

Rationale: the durable core is explicit (typed `DagsterEventType` lifecycle set, synchronous SQL writes, cursor replay, batch-write fallback to single writes, asset index mirroring). But: (a) durable writes block the runtime hot path with no async WAL/queue; (b) subscriber fan-out is synchronous with no slow-consumer protection (one bad subscriber delays all later ones and the emitter); (c) live UI delivery uses an unbounded queue with no lag/queue-depth metric; (d) no retention, compaction, or storage-bound policy — only manual wipe/delete/purge APIs. This matches rubric band 4–6.

## Answers to Dimension Questions

1. **Which events must never be dropped?**
   Lifecycle facts that other subsystems derive state from: `PIPELINE_EVENTS` (`RUN_ENQUEUED/DEQUEUED/STARTING/START/SUCCESS/FAILURE/CANCELING/CANCELED`) which drive `handle_run_event` run-status transitions (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:173-259`); step terminal events and materializations in `RUN_STATS_EVENT_TYPES`/`STEP_STATS_EVENT_TYPES` used by stats builders (`python_modules/dagster/dagster/_core/execution/stats.py:19-38`); asset materialization/observation/planned events mirrored into the `AssetKeyTable` index (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:244-344`); and system-generated log events, whose write failure re-raises and fails the step/run (`python_modules/dagster/dagster/_core/instance/types.py:53-58`). No code path intentionally drops these — the only filter is `should_store_event` for asset-failure events on storages that cannot store them (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:163-171`).

2. **Which events are ephemeral or short-lived?**
   Nothing in the event log is marked TTL/ephemeral. Ephemerality exists only in delivery, not storage: in-process `_subscribers[run_id]` callbacks (`python_modules/dagster/dagster/_core/instance/instance.py:227`), per-run polling threads and watchdog callbacks (`python_modules/dagster/dagster/_core/storage/event_log/polling_event_watcher.py:55-101`; `python_modules/dagster/dagster/_core/storage/event_log/sqlite/consolidated_sqlite_event_log.py:153-207`), the GraphQL `asyncio.Queue` live tail (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/__init__.py:286-309`), and compute-log `CapturedLogSubscription` tails (`python_modules/dagster/dagster/_core/storage/compute_log_manager.py:131-181`). User-level log records that fail to persist are deliberately swallowed (with a compensating engine event) rather than failing the run (`python_modules/dagster/dagster/_core/instance/types.py:53-68`) — the closest thing to an ephemeral concession.

3. **Can a slow UI stall execution?**
   No — but it can leak memory. Execution writes go straight to the DB synchronously and never wait for UI delivery (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:216-257`). The UI path is poll-then-push: polling/watchdog threads read from storage by cursor, and the GraphQL bridge uses `queue.put_nowait` on an unbounded `asyncio.Queue` (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/__init__.py:286-297`). A never-reading subscriber therefore grows the queue (and keeps its polling thread + DB reads alive) without applying backpressure to the run. The in-process exception is `InMemoryEventLogStorage` (tests/ephemeral): there `store_event` invokes handlers inline, so a slow test subscriber does stall the writer (`python_modules/dagster/dagster/_core/storage/event_log/in_memory.py:86-95`). Likewise any server-side `add_event_listener` callback runs inline in `handle_new_event` (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:279-280`).

4. **How are lifecycle and terminal facts flushed under pressure?**
   Synchronously and individually by default: `DAGSTER_EVENT_BATCH_SIZE` defaults to `0`, so each event is its own blocking `store_event` transaction (`python_modules/dagster/dagster/_core/instance/utils.py:26-43`). When batching is enabled, events accumulate in a per-`batch_id` in-memory list and flush on size or `is_end`, with fallback to single writes on batch failure (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:216-246`). Terminal run-status effects are applied inline via `handle_run_event` right after the store (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:248-257`). There is no flush-on-shutdown, no WAL buffer, and no priority lane for terminal events — a terminal event behind a flood of log events waits its turn in the same synchronous path. The executor-side reader compensates with bounded 1000-row tail polls and cursor self-healing (`python_modules/dagster/dagster/_core/executor/step_delegating/step_delegating_executor.py:90-142`).

5. **What bounds storage and in-memory growth?**
   Almost nothing automatic. Reads are bounded (`1000`-row watcher/executor chunks, `10000` max event-record limit: `python_modules/dagster/dagster/_core/storage/event_log/polling_event_watcher.py:178`, `python_modules/dagster/dagster/_core/executor/step_delegating/step_delegating_executor.py:75`, `python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:122-132`), and compute-log reads are 1 MB / 1000-line chunked (`python_modules/dagster/dagster/_core/storage/compute_log_manager.py:17-18`, `python_modules/dagster/dagster/_core/storage/compute_log_manager.py:368-377`). But writes and retention are unbounded: no sampling, coalescing, truncation, TTL, compaction, or size-triggered pruning was found. Growth is only bounded by explicit operator action: `delete_events`/`wipe` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:644-719`), `delete_run` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:602-606`), asset tombstones via `wipe_timestamp` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:1800-1839`), `delete_logs` for compute logs (`python_modules/dagster/dagster/_core/storage/compute_log_manager.py:256-266`), and time-based `purge_ticks`/`purge_asset_evaluations` (`python_modules/dagster/dagster/_core/storage/schedules/sql_schedule_storage.py:438-566`). In-memory growth is bounded only by the batch-size flush and by `end_watch`/thread exit when callbacks drain (`python_modules/dagster/dagster/_core/storage/event_log/polling_event_watcher.py:145-162`).

## Architectural Decisions

- **Synchronous durable write as the source of truth.** `handle_new_event → store_event → handle_run_event` is one blocking chain (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:189-280`). Decision favors never-lose-lifecycle over throughput; cost is that log floods exert DB pressure (SQLite WAL + busy timeouts, Postgres round-trips) directly on the executing process.
- **Opt-in batching, not a queue.** Batching is a caller-annotated (`batch_metadata.id`/`is_end`) in-memory accumulator keyed by batch id with a size flush (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:216-246`), documented as primarily for cloud deployments where `store_event_batch` is a single remote call (`python_modules/dagster/dagster/_core/instance/utils.py:26-34`). OSS default stays at one-transaction-per-event, preserving ordering at the cost of write amplification.
- **Polling + cursor replay instead of push.** All durable consumers (polling watcher, executor tailer, GraphQL catch-up) re-read `get_records_for_run` by `storage_id` cursor with `has_more` pagination. This makes delivery at-least-once and replayable, and lets slow consumers catch up without loss — at the cost of one thread per watched run and repeated SELECTs with exponential backoff to 16s (`python_modules/dagster/dagster/_core/storage/event_log/polling_event_watcher.py:168-198`).
- **Run-sharded SQLite + mirrored index.** Default SQLite shards events per run and mirrors only asset/check/run-status events into a central index (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:260-303`). This bounds per-run write contention but complicates cross-run queries (requires `RunShardedEventsCursor`: `python_modules/dagster/dagster/_core/event_api.py:66-75`).
- **Compute logs as files, not events.** High-volume stdout/stderr bypasses the event table entirely into per-step files with byte-offset cursors (`python_modules/dagster/dagster/_core/storage/local_compute_log_manager.py:84-100`, `python_modules/dagster/dagster/_core/storage/compute_log_manager.py:293-332`). Sensible tiering (keeps the SQL log from exploding) but inherits file-system retention problems.
- **Fail-open for user logs, fail-closed for system events.** `_EventListenerLogHandler.emit` swallows user-log persistence failures but re-raises system-event failures (`python_modules/dagster/dagster/_core/instance/types.py:48-68`). Pragmatic: a logging backend blip does not kill user compute, but control-plane truth is still enforced.

## Notable Patterns

- **Storage-id cursor protocol.** `EventLogCursor.from_storage_id(...).to_string()` / `parse(...)` threaded through storage, watchers, executor tailer, and GraphQL — the single mechanism for exactly-once-advancing, replayable delivery (`python_modules/dagster/dagster/_core/event_api.py:25-63`).
- **Batch-fallback-to-single.** `handle_new_event` catches generic `Exception` on `store_event_batch` and retries event-by-event (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:230-246`) — robust against partial cloud failures, but masks the original error to stderr text only.
- **Backoff polling.** Watcher sleeps `0.25s` on activity, doubles to `16s` cap when idle (`python_modules/dagster/dagster/_core/storage/event_log/polling_event_watcher.py:175-198`) — cheap when idle, bursty under flood.
- **Stale-page self-healing tailer.** Executor detects a full page of already-seen storage ids and jumps the cursor halfway forward with a warning (`python_modules/dagster/dagster/_core/executor/step_delegating/step_delegating_executor.py:110-124`).
- **Tombstone wipe.** Asset deletion is a `wipe_timestamp` marker with read-time filtering, not row deletion (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:1800-1839`) — preserves history, confuses naive row-count-based retention.
- **Launch-time backpressure only.** `max_concurrent_runs` / tag concurrency limits throttle run starts in the queue daemon (`python_modules/dagster/dagster/_daemon/run_coordinator/queued_run_coordinator_daemon.py:192-307`) — no equivalent for in-run event rates.

## Tradeoffs

- **Durability vs. hot-path latency.** Every log line costs a synchronous SQL transaction by default. No sampling means fidelity; cost is DB contention under chatty steps (notably SQLite, mitigated only by WAL + busy timeout: `python_modules/dagster/dagster/_core/storage/event_log/sqlite/consolidated_sqlite_event_log.py:108-117`).
- **Replayability vs. thread/connection fan-out.** One polling thread + repeated SELECTs per watched run gives lossless catch-up but scales poorly with many concurrent UI watchers; no multiplexed/shared poller was found.
- **Unbounded live queue vs. execution isolation.** `put_nowait` into an unbounded `asyncio.Queue` protects execution from slow UI at the price of unbounded webserver memory (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/__init__.py:286-297`).
- **Batching reduces round-trips, not coupling.** Enabling `DAGSTER_EVENT_BATCH_SIZE` still blocks the emitter at flush time and holds unflushed events in an in-memory dict (`python_modules/dagster/dagster/_core/instance/instance.py:232`) — a crash before `is_end` loses the whole buffered batch with no spill to disk.
- **File-tier compute logs vs. retention.** Offloading bytes to files keeps the event DB lean but leaves unbounded disk growth with only manual `delete_logs`.

## Failure Modes / Edge Cases

- **Slow in-process subscriber blocks the emitter.** `for sub in self._subscribers_impl[run_id]: sub(event)` has no try/except, timeout, or queue (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:279-280`); one stuck callback stalls persistence of all later events including terminal ones, and stalls `handle_run_event` status updates behind it. Same for `InMemoryEventLogStorage` test/ephemeral path (`python_modules/dagster/dagster/_core/storage/event_log/in_memory.py:86-95`).
- **Buffered-batch loss on crash.** Unflushed `_event_buffer[batch_id]` lives only in process memory; a worker crash before `is_end`/size-flush silently drops the batch (no flush-on-exit found).
- **Unbounded GraphQL queue OOM.** A subscribed-but-never-reading UI grows `asyncio.Queue` without limit while the polling thread keeps feeding it; recovery is reconnect + cursor replay, but the leaked queue persists until `end_watch` (`python_modules/dagster-graphql/dagster_graphql/implementation/execution/__init__.py:286-309`).
- **Thread-per-run exhaustion.** Each watched run spawns a daemon thread that lives until callbacks drain (`python_modules/dagster/dagster/_core/storage/event_log/polling_event_watcher.py:66-86`); many concurrent runs × watchers = thread and DB-connection pressure with no pool cap found.
- **SQLite write contention under flood.** Synchronous per-event transactions across run shards + index mirroring contend on WAL; busy-timeout retries are the only cushion found. Postgres path inherits per-event round-trip latency.
- **Concurrent status/tag overwrite.** Code comment acknowledges `handle_run_event` vs `add_tags` can clobber run-body status; mitigation is a separate `status` column read as truth (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:261-267`).
- **Orphaned compute-log files.** `delete_run` removes the run row but event/compute-log cleanup requires separate `delete_events`/`delete_logs` calls — partial cleanup leaves orphaned files/rows consuming disk indefinitely.
- **Silent run-event no-op.** `handle_run_event` returns silently for unknown run ids (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:184-187`); lifecycle events for deleted/pruned runs vanish without error.

## Future Considerations

- Put subscriber fan-out behind a bounded queue with drop-or-log policy and per-subscriber lag accounting, so a slow listener can be shed without stalling `store_event`/`handle_run_event`.
- Make `DAGSTER_EVENT_BATCH_SIZE` async with a background flusher + flush-on-shutdown + disk spill, or document that buffered batches are crash-volatile.
- Bound the GraphQL live queue (e.g., `maxsize` + `put_nowait` drop-oldest with `hasMorePastEvents`-style resync signal) and expose queue-depth/lag metrics; no lag, queue-depth, or WAL-growth metrics were found.
- Add a first-class retention story: run/event TTL, compute-log size/age caps, and a daemon-owned `purge_ticks`-style sweeper for events — currently only manual `delete_events`/`wipe`/`delete_logs` exist.
- Add coalescing/sampling for high-volume non-lifecycle records (e.g., `ENGINE_EVENT` log spam, `LOGS_CAPTURED`) while keeping `PIPELINE_EVENTS`/terminal step/asset events on the never-drop path.
- Reconcile `delete_run` vs `delete_events` vs `delete_logs` into a single cascading retention API to prevent orphans.
