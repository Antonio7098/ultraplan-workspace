## Summary

Dagster separates authoritative current-state (RunsTable via `RunStorage`) from its durable operational journal (EventLogEntry via `EventLogStorage`). State mutation (`handle_run_event` updating `RunsTable.status`/`run_body`) and event append (`store_event` inserting into `event_logs`) are **not co-transactional**: `DagsterInstance.handle_new_event` persists the event first in the event-log DB, then in a second independent transaction updates the run status in the run DB (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:248-257`). For the default SQLite deployment the two stores are physically distinct databases (`runs.db` vs per-run `*.db` + `index.db`), making a single atomic commit impossible. Even within the event-log store, asset/index updates use a separate `index_transaction()` from the `run_connection` insertion. Transactions themselves are short/bounded (`with conn.begin(): yield conn`), WAL + 30 s busy-timeout mitigates writer contention, and Alembic-owns migrations per-storage, but there is **no optimistic revision / expected-state CAS** for run status — updates are last-write-wins with a documented race on `run_body` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:264-266`). The event log is an audit/observation journal for runs but doubles as source-of-truth for assets (with `asset_keys` as a derived secondary index). A crash between the two writes leaves a durable event without its status transition or a status without its ordering guarantee.

## Rating

**4 / 10 — Present but inconsistent, weakly documented, or fragile**

Rationale: stores, journals, transactions, migrations, and WAL are implemented and bounded, but the core invariant — atomic `state + event` — is missing. No shared connection/transaction owner, no revision field, no compensating saga. The comment about concurrent `handle_run_event`/`add_tags` clobbering `run_body` is acknowledged but not prevented. SQLite sharding doubles the gap (run shard vs index shard). Postgres could co-locate tables yet the code still uses two independent `connect()` contexts. Operational safeguards exist for locking (WAL, busy timeout, foreign-key pragmas) but not for partial-commit visibility.

## Answers to Dimension Questions

### 1. Can state commit without its corresponding durable event?

**Yes — both directions are possible because commits are in separate transactions/DBs.**

The canonical path is `handle_new_event` (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:248-257`): line 231 stores the `EventLogEntry` in `event_logs`, then lines 255-256 call `run_storage.handle_run_event` to update `RunsTable`. Those are two `with connect() as conn: with conn.begin():` blocks, often on **different engines/files** (SQLite: `runs.db` vs `history/runs/<run_id>.db`). A crash, process kill, or `database is locked` exception between them leaves the event durable but the run status stale (e.g., a `PIPELINE_START` event visible via `get_records_for_run` while `get_run_by_id` still returns `NOT_STARTED/STARTING`). The inverse (status without an event log entry) is possible if code calls `add_run_tags`/`handle_run_event` directly outside `handle_new_event`, or if the event insertion fails but the run update succeeds when invoked independently. For SQLite-sharded asset events, the run-shard insert can commit while the mirror into the `index` shard (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:274-288`) fails, leaving per-run logs complete but cross-run `asset_keys`/`get_event_records` queries empty.

Concrete crash injection: kill between `python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:400` (`run_connection` insert) and `python_modules/dagster/dagster/_core/instance/methods/event_methods.py:255` (`handle_run_event`). Observable: `instance.logs_after(run_id)` contains `PIPELINE_SUCCESS` but `instance.get_run_by_id(run_id).status` is still `STARTED`; UI run list vs run detail disagree. Daemon heartbeat reconciliation may eventually reconcile, but no transactional guarantee.

### 2. Can an event commit for a state transition that later rolls back?

**Yes.** Because the event log transaction commits independently, a later rollback of the state transaction does not retract the event.

Sequence in `handle_new_event`: the `store_event` transaction commits at the exit of `with conn.begin():` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:400-401`). The subsequent `handle_run_event` transaction (second DB) may raise (`IntegrityError`, `OperationalError: database is locked` after 30 s busy timeout, or any exception in `get_daemon_heartbeats`/`add_run_tags`). The code has **no compensating delete** of the just-inserted `event_logs` row and no two-phase commit. The batch path (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:233-246`) even catches batch-insert exceptions and falls back to individual `store_event` loops, but does not retract previously-inserted batch members. For asset check executions the insert-then-update in `store_asset_event` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:283-286`) catches `IntegrityError` and issues an update within the *index* transaction, but if the outer run-shard event already committed, the index row may be stale or duplicated.

### 3. Is the event log an audit/observation journal or the sole source of truth?

**Both — split by domain.**

*Runs*: `RunsTable` is the **authoritative current-state store**. History APIs read `RunsTable.status` and `run_body` directly (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:427-434`, `python_modules/dagster/dagster/_core/storage/runs/schema.py:8-48`). The event log is an **audit/observation journal** that *drives* state transitions via `EVENT_TYPE_TO_PIPELINE_RUN_STATUS` mapping (only events of those types mutate runs; `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:181-183` returns early otherwise). Run stats can be derived either from indexed `start_time`/`end_time` columns (fast path) or by aggregating events (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:513-576` vs `python_modules/dagster/dagster/_core/storage/event_log/base.py:262-266`), confirming the log is not the sole source of truth for run liveness.

*Assets & partitions*: `event_logs` is the **source of truth**; `asset_keys.last_materialization`, `asset_keys.last_materialization_timestamp`, `asset_event_tags`, `dynamic_partitions`, `concurrency_slots` are **secondary indexes / materialized views** rebuilt by `reindex_events`/`reindex_assets` and guarded by `secondary_indexes` checkpoint table (`python_modules/dagster/dagster/_core/storage/event_log/schema.py:26-38`, `python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:634-643`). `SqlEventLogStorage._store_asset_event` and `_store_asset_event_tags` only fire for `ASSET_EVENTS`/`ASSET_CHECK_EVENTS`, and existence checks short-circuit when the table is missing (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:373`). Thus losing `event_logs` would lose asset history; losing `asset_keys` could be rebuilt.

*Legacy vs consolidated*: `ConsolidatedSqliteEventLogStorage` makes the journal co-located (`run_connection` == `index_connection` both `return self._connect()` at `python_modules/dagster/dagster/_core/storage/event_log/sqlite/consolidated_sqlite_event_log.py:119-123`), but still uses separate transactions; `SqliteEventLogStorage` shards per-run, explicitly not global source-of-truth for cross-run queries without the index mirror.

### 4. Are transactions short and bounded?

**Yes — all transactions are short, scoped to a single `connect()` context, with no long-held locks across calls.**

Pattern is uniform:

```python
with self.connect() as conn:   # or run_connection/index_connection
    with conn.begin():
        yield conn
```

Seen in `SqliteRunStorage.connect()` (`python_modules/dagster/dagster/_core/storage/runs/sqlite/sqlite_run_storage.py:129-134`), `SqliteEventLogStorage._connect()` (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:233-252`), `ConsolidatedSqliteEventLogStorage._connect()` (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/consolidated_sqlite_event_log.py:108-118`), and `InMemoryRunStorage.connect()` (`python_modules/dagster/dagster/_core/storage/runs/in_memory.py:59-65`). Even `fetchall`/`fetchone` open a fresh bounded TX per query (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:103-112`).

However, `handle_new_event` spans **two** short TX sequentially (event store + run store) and for SQLite-sharded events up to **three** (run shard + index shard asset mirror + index shard status mirror). Batch handles (`store_event_batch`) may buffer up to `DAGSTER_EVENT_BATCH_SIZE` events in memory before a single `store_event_batch` TX; fallback on exception replays as N individual short TX (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:233-246`). Overall, no TX holds across I/O or across the scheduler tick, meeting the "short and bounded" criterion, but the multi-TX saga extends the vulnerability window for partial commits.

### 5. How are stale state revisions rejected?

**They are not — there is no optimistic revision / expected-state check.**

`DagsterRun` is a `record` with `status: DagsterRunStatus` but no `version`, `revision`, `etag`, or `updated_timestamp` CAS column (`python_modules/dagster/dagster/_core/storage/dagster_run.py:234-283`). `SqlRunStorage.handle_run_event` does `RunsTable.update().where(RunsTable.c.run_id == run_id).values(status=new_status, run_body=serialize_value(updated_run))` without `AND status = expected_old_status` or `AND update_timestamp = expected` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:250-259`). `add_run_tags` similarly blind-merges tags and overwrites `run_body` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:524-553`).

The only documented mitigation is a **comment at** `python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:264-266`: the `status` column is more trustworthy than the serialized `run_body` because concurrent writes can clobber `run_body.status` with an old value. The fix is to always re-hydrate with `run.with_status(status_column)` in `_row_to_run`, not to reject the stale write. Unique constraints exist for `RunsTable.run_id`, `SnapshotsTable.snapshot_id`, `RunTagsTable`, `BulkActionsTable.key`, `DynamicPartitionsTable` composite, and `PendingStepsTable` composite, but not for run state versioning. Concurrency slots (`concurrency_slots`, `pending_steps`) use unique `concurrency_key+run_id+step_key` but also rely on last-write-wins plus `initialize_concurrency_limit_to_default` CAS via `IntegrityError` catch, not on run status versioning.

Effectively **last-write-wins**; out-of-order `PIPELINE_START` vs `PIPELINE_SUCCESS` handling depends on arrival order, not on a monotonic revision.

## Notable Patterns

* **Bounded connection-per-operation with `conn.begin()`**: every storage method opens a fresh engine and commits on context exit — consistent across run/event/schedule storages, including in-memory variants that execute `PRAGMA foreign_keys=ON` per TX (`python_modules/dagster/dagster/_core/storage/runs/in_memory.py:61-65`).
* **Insert-then-on-`IntegrityError`-update upsert** for idempotent writes: `SnapshotsTable` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:654-664`), `AssetKeyTable` (`python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:283-286`), `DaemonHeartbeatsTable` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:852-873`), `KeyValueStoreTable` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:1138-1144`).
* **Secondary index as materialized view**: `asset_keys`, `asset_event_tags`, `concurrency_slots` are maintained transactionally in `index_transaction()` but rebuildable via `reindex_*` migrations.
* **Environment-gated batching**: `DAGSTER_EVENT_BATCH_SIZE` toggles between single-write and batched `store_event_batch` with generic fallback (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:179-246`), documented as cloud-expected.
* **Explicit run-status whitelist**: `handle_run_event` only reacts to `EVENT_TYPE_TO_PIPELINE_RUN_STATUS` (`python_modules/dagster/dagster/_core/storage/runs/sql_run_storage.py:181-183`), making the journal the driver but the run table the filter.

## Tradeoffs

* **Isolation vs atomicity**: Separate DBs/engines give deployment flexibility (SQLite for local, Postgres for prod can co-locate or not) and fault isolation, but the product accepts a visibility window where journal and state disagree. No outbox or transactional inbox pattern is used.
* **Per-run sharding vs cross-run consistency**: Sharding gives excellent write isolation and simple per-run log tailing (`watch`/`end_watch` via watchdog on `*.db` files at `python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:492-508`), but cross-run asset/concurrency queries need the mirrored index and inherit its lag.
* **Last-write-wins vs optimistic locking**: Avoids version-column migration and CAS retry complexity, but enables lost updates when two callers concurrently `handle_run_event` or `add_run_tags` for the same run. The chosen mitigation (trust `status` column, merge dicts) is cheap but not linearizable.
* **WAL performance vs checkpoint stalls**: WAL improves concurrent reads, but long-running readers or large event batches can stall checkpoints; the 30 s busy timeout (`python_modules/dagster/dagster/_core/storage/sqlite.py:15`) hides transient lock contention yet increases tail latency for scheduling loops.
* **Batch throughput vs durability granularity**: Batching reduces round trips for high-volume step events, but a single batch failure replays as individual writes without deduplication or idempotency keys, risking partial duplication.

## Failure Modes / Edge Cases

* **Crash between event and state** (injected between `python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py:400` and `python_modules/dagster/dagster/_core/instance/methods/event_methods.py:255`): durable orphan event exists but run status is stale. Recovery requires a reconciliation sweep (daemon heartbeat / tick re-evaluation) not a transactional rollback. For assets, orphan run-shard event without index mirror yields "materialization not found" via `get_event_records` until next `store_asset_event` or reindex.
* **Stale `run_body` clobber**: Two threads call `handle_run_event` (e.g., `PIPELINE_START` + concurrent `add_run_tags` via `WILL_RETRY_TAG` at `python_modules/dagster/dagster/_core/instance/methods/event_methods.py:271-278`) — both read same `run_body`, second write overwrites first's `run_body.status` while `status` column is correct, forcing the `_row_to_run` fixup but losing the first body's tag merge.
* **`database is locked` on SQLite**: concurrent `SqliteEventLogStorage.store_event` writers on same `run_id.db` contend on WAL write lock; after 30 s the operation raises `OperationalError` and `handle_new_event` still notifies subscribers (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:279-280`) with the event that may not have persisted the subsequent run transition.
* **Alembic stamp race**: simultaneous first-connect `_initdb` in two processes hits `table already exists` / `UNIQUE constraint failed: alembic_version`; handled by 10-retry loop (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:207-231`), but a third process that starts mid-stamp can see mismatched `db_revision`/`head_revision` and stamp to wrong rev (`LAST_KNOWN_STAMPED_SQLITE_ALEMBIC_REVISION`).
* **Non-unique cursor ids across shards**: `get_event_records` without `RunShardedEventsCursor` raises exception for cross-run queries (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:344-354`); callers that page by storage_id can skip or duplicate events after a run-shard rollover.
* **WAL file unbounded growth**: `*.db-wal` / `*.db-shm` are only checkpointed on `engine.dispose()` or explicit `checkpoint`; long-lived webserver with `NullPool` may hold WAL without checkpoint, risking disk fill before `wipe` helper deletes `*.db-wal` files (`python_modules/dagster/dagster/_core/storage/event_log/sqlite/sqlite_event_log.py:459-472`).
* **Split `delete_run` without event delete**: `SqliteRunStorage.delete_run` manually deletes `RunTagsTable` then `RunsTable` (`python_modules/dagster/dagster/_core/storage/runs/sqlite/sqlite_run_storage.py:167-176`); events for that run remain in per-run DB until `delete_events` is explicitly called, leaving dangling journal history.

## Future Considerations

* Introduce an **outbox / transactional inbox** or single-DB atomic option: when `run_storage` and `event_log_storage` share the same Postgres/MySQL engine (as in cloud deployments that use `ConsolidatedSqliteEventLogStorage` pattern / `PostgresEventLogStorage`), route `handle_new_event` through a shared `Connection`/`Transaction` or use `store_event_batch` that `handles_run_events_in_store_event = True` to keep status+event co-atomic; the `handles_run_events_in_store_event` flag already exists (`python_modules/dagster/dagster/_core/storage/event_log/base.py:745-748`) but is `False` for SQL storages.
* Add an **optimistic `version`/`update_timestamp` CAS column** to `RunsTable` and make `handle_run_event` do `WHERE run_id=:id AND update_timestamp=:expected` with retry, mirroring patterns already used for concurrency slots. Would reject stale state and make scheduler ticks idempotent.
* Make **batch writes idempotent** with an idempotency key on `event_logs.id` or dedup on `(run_id, dagster_event_type, timestamp)` to safely replay after mid-batch failures; currently the fallback loops without dedup (`python_modules/dagster/dagster/_core/instance/methods/event_methods.py:240-246`).
* For SQLite, **separate WAL checkpoint policy** (periodic `PRAGMA wal_checkpoint(TRUNCATE)` or `journal_size_limit`) and expose `SQLITE_BUSY_TIMEOUT_SECONDS` as tunable config rather than constant import; document operational runbook for WAL/shm cleanup.
* Add a **reconciliation tick** that scans `event_logs` max `id` vs `RunsTable.update_timestamp` to detect and backfill missed status transitions (the existing `migrate`/`reindex` infrastructure already tracks `secondary_indexes` — extend it to a `run_event_consistency` check).
* Consider unifying **run-shard + index writes** for `SqliteEventLogStorage` via a two-phase mirror with a durable queue file or by adopting `ConsolidatedSqliteEventLogStorage` for new installations to avoid split-brain asset queries.
