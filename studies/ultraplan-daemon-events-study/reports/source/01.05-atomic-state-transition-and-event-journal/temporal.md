## Summary

Temporal treats **mutable state** (`executions` table + per-shard `shards.RangeID`) as the authoritative current-state store and the **history branch** (`history_node` + `history_tree`) as the durable operational journal. Every meaningful transition (create / update / conflict-resolve / reset) is funneled through `ExecutionManager` → `ExecutionStore` via three persistence verbs `CreateWorkflowExecution` / `UpdateWorkflowExecution` / `ConflictResolveWorkflowExecution`. Payloads carry both a `WorkflowSnapshot`/`WorkflowMutation` (current state) and an ordered list of `WorkflowEvents` (history batches) serialized into `InternalAppendHistoryNodesRequest` objects before the call (`common/persistence/execution_manager.go:114-154`, `service/history/workflow/transaction_impl.go:53-94`).

On **SQL** the two durable writes are sequential but not co-transactional: `AppendHistoryNodes` is executed first (outside any shard transaction) and the shard-locked `txExecuteShardLocked` that mutates `executions`/`current_executions` follows (`common/persistence/sql/execution.go:60-78`, `common/persistence/sql/execution.go:339-357`). On **Cassandra** the same ordering holds: `ExecutionStore` (`common/persistence/cassandra/execution_store.go:97-108`) calls `HistoryStore.AppendHistoryNodes` before delegating to `MutableStateStore`'s `LOGGED BATCH` with `IF range_id` / `IF db_record_version` CAS. A crash between the two steps can leave orphan history nodes (event without state). The mitigation is best-effort: `ExecutionManager` catches `WorkflowConditionFailedError`/`ConditionFailedError`/`CurrentWorkflowConditionFailedError` and calls `trimHistoryNode` (`common/persistence/execution_manager.go:262-273`, `common/persistence/execution_manager.go:1081-1140`) which validates the node chain via `TrimHistoryBranch` (`common/persistence/history_manager.go:213-309`) and deletes stray nodes. The journal is therefore an **audit/replay source**, not the sole source of truth — `MutableStateRebuilder` rebuilds from history, but the live path always reads `executions`.

Transactions are intentionally short and bounded: single `BEGIN/COMMIT` per workflow transition (`common/persistence/sql/common.go:52-81`), single shard locked (`common/persistence/sql/shard.go:152-174`), payload size checked in `serializeAppendHistoryNodesRequest` (`common/persistence/history_manager.go:367-374` → `TransactionSizeLimitError`), and metrics emitted post-commit (`service/history/workflow/transaction_impl.go:393-413`). Stale revisions are rejected by **optimistic CAS**: `DBRecordVersion` (primary) plus legacy `Condition`/`NextEventID`, enforced in `lockAndCheckExecution` (`common/persistence/sql/execution_util.go:628-665`) for SQL and in CQL `IF db_record_version = ?` (`common/persistence/cassandra/mutable_state_store.go:107-123`) for Cassandra, alongside shard fencing via `RangeID` (`common/persistence/sql/shard.go:124-149`, `common/persistence/cassandra/mutable_state_store.go:453-463`).

There is no daemon-local DB ownership/WAL to tune: Temporal delegates durability to the external store. SQLite WAL is explicitly surfaced only for test/dev (`common/persistence/sql/sqlplugin/sqlite/plugin.go:94-109`). Writer contention is resolved per shard (exactly one history service owns a shard) and via contention-retry policies (`common/persistence/persistence-tests/history_v2_persistence.go:801`).

## Rating

**7 / 10 — Clear model with tests, explicit interfaces, and operational safeguards, but not fully atomic under crash.**

Rationale: Interfaces (`ExecutionManager` `common/persistence/data_interfaces.go:1126-1138`, `ExecutionStore` `common/persistence/persistence_interface.go:116-167`, `Transaction` `service/history/workflow/transaction.go:11-57`) are explicit, shard-scoped transactions are short/bounded/serialized, and optimistic `DBRecordVersion` fencing with shard `RangeID` is uniformly enforced and tested (`common/persistence/sql/sqlplugin/tests/history_execution.go:271-304`). The deduction from 9 is the deliberate **split-phase durability**: history nodes are appended outside the shard transaction, so a crash between `AppendHistoryNodes` and `UpdateWorkflowExecution` yields an observable orphan branch until `trimHistoryNode` (best-effort, post-failure reads `GetWorkflowExecution`) removes it. That is proven operationally but not atomic, and logging is at most `Warn`/`Debug`. True single-transaction co-commit (as the prompt's "without full event sourcing" ideal suggests) would require `AppendHistoryNodes` inside the same `Tx`/`LOGGED BATCH` — currently not the case.

## Answers to Dimension Questions

### 1. Can state commit without its corresponding durable event?

**Yes, transiently — but not durably after the transaction commits, with a split-phase caveat.** The critical window is **append-before-state**. In both stores history is appended **before** the shard transaction (`common/persistence/sql/execution.go:64-66`, `common/persistence/sql/execution.go:340-342`). If `AppendHistoryNodes` succeeds and the subsequent `txExecuteShardLocked` fails (conflict, timeout, crash), the **event persists without state** (orphan branch). Conversely, if `AppendHistoryNodes` fails (size limit `common/persistence/history_manager.go:369-373`, `AppendHistoryTimeoutError` `common/persistence/sql/history_store.go:56-59`) the state transaction is never attempted, so the inverse **state without event cannot happen on the write path**. However, an in-memory state advancement that later calls `UpdateWorkflowExecution` with `eventBatches` empty is explicitly allowed (`common/persistence/execution_manager.go:537`, `service/history/workflow/transaction_impl.go:258`) — that is a state transition without new history, which is intentional for task-only refreshes and `SetWorkflowExecution` (`common/persistence/sql/execution.go:719-743`).

Inject a crash **after** `updateWorkflowExecution` mutates `executions` row but **before** the engine's in-memory notify (`service/history/workflow/transaction_impl.go:523-534`) — the DB state is durable, tasks/history observers recover on reload, so no observable divergence. Inject it **between** `AppendHistoryNodes` and the `Tx.Commit` (`common/persistence/sql/common.go:77-78`) — you get dangling `history_node` rows whose `node_id`/`txn_id` chain fails `validateNodeChainAndTrim` and will be lazily deleted by the next conflicting write's `trimHistoryNode`.

### 2. Can an event commit for a state transition that later rolls back?

**Yes — orphan history node scenario described above.** Because history append and state mutation do not share one `Tx`/`LOGGED BATCH` connection ownership, a rolled-back state transition does not roll back the already-inserted `history_node` rows. Evidence: `AppendHistoryNodes` for non-new branch does a standalone `m.DB.InsertIntoHistoryNode` (`common/persistence/sql/history_store.go:52-55`) without any `Tx`, while `updateWorkflowExecutionTx` holds `WriteLockExecutions` (`common/persistence/sql/execution_util.go:45-53`). The reconciling code explicitly exists because maintainers know this: `execution_manager.go:262-273` ("trimHistoryNode on `ConditionFailedError`"), `sql/history_store.go:111-148` `DeleteHistoryNodes`, and `history_manager.go:286-305` `validateNodeChainAndTrim` deciding to `DeleteHistoryNodes` for each orphan. Cassandra path is slightly stronger: `LOGGED BATCH` gives atomicity among **mutable state + tasks + current record + shard lease**, but history nodes are still inserted **outside** that batch (`common/persistence/cassandra/execution_store.go:101-104`), so the same orphan is possible.

### 3. Is the event log an audit/observation journal or the sole source of truth?

**Audit/observation + replay journal, NOT the sole source of truth.** The authoritative current-state store is the normalized `executions` row plus its map tables (`activity_info_maps`, `timer_info_maps`, etc.) and `current_executions` pointer (`common/persistence/sql/execution.go:211-332`, `common/persistence/cassandra/mutable_state_store.go:384-493`). History is durably appended to `history_node`/`history_tree` and read back via `ReadHistoryBranch`/`ReadHistoryBranchByBatch` (`common/persistence/history_manager.go:517-541`), but the live execution path never replays from history — it loads `GetWorkflowExecution` from `executions`. History's roles are: (a) audit trail for SDK `GetWorkflowHistory`, (b) replay source for `MutableStateRebuilder` / NDC replication / reset continuation, and (c) version lineage via `HistoryBranch` ancestors (`common/persistence/history_manager.go:36-85`). The `TransitionHistory`/`VersionHistory` dual tracking (`service/history/workflow/mutable_state_impl.go:1148-1170`) further shows history as an observer journal layered over the versioned state.

### 4. Are transactions short and bounded?

**Yes.** Every workflow transition maps to exactly one short shard-locked transaction:

* `txExecute` (`common/persistence/sql/common.go:52-81`) does `BeginTx` → function → `Rollback` on error or `Commit`; `Commit` failure is surfaced as `Unavailable`.
* `txExecuteShardLocked` (`common/persistence/sql/execution.go:39-58`) adds a single `SELECT ... FOR SHARE` / `FOR UPDATE` on `shards` (`common/persistence/sql/shard.go:152-174`) to fence writers; the entire mutation (current record + executions row + child maps + tasks) commits together (`common/persistence/sql/execution_util.go:23-191`, `common/persistence/sql/execution.go:360-444`).
* Cassandra equivalent is one `LOGGED BATCH` with shard `IF range_id` plus one or two `IF db_record_version` CAS conditions (`common/persistence/cassandra/mutable_state_store.go:702-738`).
* Size is bounded before entry: `serializeAppendHistoryNodesRequest` enforces `transactionSizeLimit()` (`common/persistence/history_manager.go:367-374`) throwing `TransactionSizeLimitError` (`common/persistence/data_interfaces.go:160-163`); `historySizeRollback` (`common/persistence/execution_manager.go:70-102`) prevents retry-double-count of `HistorySize`.
* Operationally, transactions hold no network calls: notifications (`NotifyNewHistoryMutationEvent` `service/history/workflow/transaction_impl.go:696-734`, task queues) run after commit, with `OperationPossiblySucceeded` guards (`service/history/workflow/transaction_impl.go:201-214`) so re-delivery is safe.

### 5. How are stale state revisions rejected?

**Optimistic concurrency with two-generation protocol plus shard fencing:**

* **Preferred:** `DBRecordVersion` — monotonic integer persisted in `executions.db_record_version` (`common/persistence/sql/sqlplugin/history_execution.go:21`, `common/persistence/cassandra/mutable_state_store.go:57-58`, `common/persistence/sql/execution_util.go:52-70`). On write, `lockAndCheckExecution` loads `dbRecordVersion` via `WriteLockExecutions` and checks `version == dbRecordVersion - 1` (`common/persistence/sql/execution_util.go:653-661`), CQL uses `IF db_record_version = ?` (`common/persistence/cassandra/mutable_state_store.go:107-123`). Failure returns `WorkflowConditionFailedError` (with `DBRecordVersion` + `NextEventID` for diagnostics `common/persistence/data_interfaces.go:131-137`) bubbled to `serviceerror`.
* **Legacy:** `Condition`/`NextEventID` (`common/persistence/data_interfaces.go:375-377`) — when `DBRecordVersion==0` (pre-migration rows) the check falls back to `nextEventID != condition` (`common/persistence/sql/execution_util.go:645-651`).
* **Shard fencing:** `RangeID` on `shards` (`common/persistence/sql/shard.go:124-149`, `common/persistence/data_interfaces.go:148-153`) version-gates every batch; mismatch yields `ShardOwnershipLostError` which `txExecute` surfaces without swallowing (`common/persistence/sql/common.go:65-70`).
* **Current-run fencing:** `current_executions` row CAS (`templateUpdateCurrentWorkflowExecutionQuery` `common/persistence/cassandra/mutable_state_store.go:33-42`, `sql/execution_util.go:604-627`, `sql/execution_util.go:966-1009`) ensures at most one run is current; `UpdateWorkflowModeUpdateCurrent` vs `BypassCurrent` (`common/persistence/data_interfaces.go:54-71`) explicitly encodes the stale-current decision.
* Load path propagates `DBRecordVersion` (`common/persistence/sql/execution.go:228-330`) into `NewMutableStateFromDB` (`service/history/workflow/mutable_state_impl.go:446-572` with `dbRecordVersion` field) so the next transaction carries the correct `Condition`.

## Architectural Decisions

| Decision | Rationale & Evidence | Consequence |
|----------|---------------------|-------------|
| **Split-phase: history before state** | Keeps `history_node` insert simple and isolates large blob I/O from row-lock critical section. Visible in `sql/execution.go:60-78` and `cassandra/execution_store.go:97-108`. | Requires compensating `trimHistoryNode` and makes the window between `AppendHistoryNodes` and `Tx.Commit` observable. Single-transaction atomicity is not achieved. |
| **Shard-scoped serialized transactions** | All workflow mutations go through `txExecuteShardLocked` (`sql/execution.go:39-58`) with `ReadLockShards` (`sql/shard.go:152-174`) and `RangeID` CAS. | At most one writer per shard; eliminates cross-workflow contention but serializes unrelated workflows on the same shard. |
| **Normalized mutable-state schema (SQL) vs map-collection (Cassandra)** | SQL decomposes state into `executions` + `activity_info_maps`/`timer_info_maps`/`chasm_node_maps` (`sql/execution.go:211-332`, `sql/execution_util.go:23-191`); Cassandra packs maps into single `executions` row (`cassandra/mutable_state_store.go:60-71`). | SQL enables fine-grained updates and WAL-per-table durability; Cassandra relies on `LOGGED BATCH` atomicity. Behavioral parity hidden behind `ExecutionStore` interface adds test surface. |
| **ExecutionManager as serialization boundary** | `SerializeWorkflowMutation/Snapshot` and `serializeWorkflowEventBatches` sit above `ExecutionStore` (`common/persistence/execution_manager.go:629-845`, `common/persistence/history_manager.go:325-411`). | Centralizes blob encoding, size limit, XDC cache population; keeps storage adapters thin. |
| **Best-effort post-transaction effects** | `DeleteHistoryTasks` with `BestEffort=true` (`common/persistence/execution_manager.go:281-310`) and `NotifyNewHistory*` after commit (`service/history/workflow/transaction_impl.go:89-214`) run outside transaction with `OperationPossiblySucceeded` guards. | Failure does not roll back state; observability lag is tolerated for operational simplicity. |
| **External durability delegation (no daemon-local WAL)** | No local RocksDB/WAL; all persistence goes to external DB via `SqlStore`/`CassandraSession` (`sql/common.go:20-32`, `cassandra/execution_store.go:89-95`). Migrations live in `schema/` (`schema/mysql/...`, `schema/postgresql/...`, `schema/sqlite/...`). SQLite WAL exposed only for `MaxConns` test config (`sql/sqlplugin/sqlite/plugin.go:94-109`). | Deployment must provision and tune external DB's WAL/checkpoint; Temporal daemon itself is stateless for crash-recovery. Single-node SQLite deployment would need explicit `journal_mode=wal`. |
| **Dual optimistic concurrency (NextEventID → DBRecordVersion)** | Both fields coexist (`data_interfaces.go:348-402`) with deprecation TODOs; `lockAndCheckExecution` branches on `dbRecordVersion==0` (`sql/execution_util.go:644-662`). | Migration-transparent correctness; clients must handle `WorkflowConditionFailedError` containing both `NextEventID` and `DBRecordVersion` to refresh correctly. |

## Notable Patterns

* **Optimistic CAS with row-level lock** — `WriteLockExecutions` + `IF db_record_version` pattern appears in both stores: `sql/execution_util.go:667-695` and `cassandra/mutable_state_store.go:107-123`. Used uniformly for executions, current executions, and shards.
* **Append-then-transaction with compensating trim** — General pattern across `CreateWorkflowExecution` / `UpdateWorkflowExecution` / `ConflictResolveWorkflowExecution`. Evidence: `execution_manager.go:247-278` classifies `ConditionFailedError` vs generic `Unavailable`.
* **Version-lineage junctions** — `HistoryBranch` with `Ancestors` (`history_manager.go:54-85`), `GetCurrentBranchToken` (`common/persistence/execution_manager.go:1247-1259`), and `ForkHistoryBranch` (`history_manager.go:38-128`) create a git-like branch graph for history continuity on reset/fork.
* **Shard-as-lease (RangeID fencing)** — Shard `RangeID` incremented on every `UpdateShard` (`sql/shard.go:83-113`) and validated on every workflow write (`sql/execution.go:40-50`, `cassandra/mutable_state_store.go:453-463`). Acts as inter-history-node writer lease.
* **History-size revert guard** — `historySizeRollback` (`execution_manager.go:70-102`) defers against the named return error to undo `ExecutionStats.HistorySize` mutation — prevents workflow-ID-reuse double count, a subtle atomicity complement.
* **Token-based paginated history reads** — `historyPagingToken` + `ReadHistoryBranch` merging across `Ancestors` ranges (`history_manager.go:619-665`, `sql/history_store.go:155-246`) gives bounded reads without loading entire branch.

## Tradeoffs

* **Availability vs single-copy atomicity.** Sequential `AppendHistoryNodes` → `UpdateWorkflowExecution` minimizes lock time for large event blobs but sacrifices physical co-atomicity; compensating `TrimHistoryBranch` is cheaper than holding a row lock over a large payload insertion. The cost is eventual orphan history and an extra `GetWorkflowExecution` read on conflict.
* **External-store WAL vs daemon-local WAL.** Delegating durability to Postgres/MySQL WAL or Cassandra commit log lets Temporal scale horizontally without daemon-local write-ahead files, but operators must size that WAL; there is no daemon-side `checkpoint` interval to tune beyond `queue_base.go` task ack persistence.
* **Normalized SQL schema vs wide Cassandra row.** The SQL schema gives per-map durability and indexability (`activity_info_maps` etc.) at the price of many statements per transaction (`execution_util.go:84-188` executes up to seven map mutations). Cassandra's single wide row is fewer round trips but requires `LOGGED BATCH` (coordinator overhead).
* **Two generations of condition fields.** Keeping `NextEventID`/`Condition` alongside `DBRecordVersion` (`data_interfaces.go:375-378` TODO comments) allows rolling upgrade but doubles mental model and diff surface in `applyWorkflowMutationTx` vs `applyWorkflowSnapshotTxAsReset`.
* **Logged batch atomicity limited.** Cassandra `LOGGED BATCH` guarantees atomicity among mutations in the batch, but TimeoutErrors (`AppendHistoryTimeoutError` `data_interfaces.go:108-112`) signal coordinator uncertainty — Temporal maps `DeadlineExceeded` to that type (`sql/history_store.go:56-59`) and relies on retry-or-trim heuristics rather than a two-phase transaction log.
