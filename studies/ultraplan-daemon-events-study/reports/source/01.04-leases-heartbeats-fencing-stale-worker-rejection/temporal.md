## Summary

Temporal history shards are owned via a **RangeID** fencing token, not a time-based lease with heartbeats. Each shard row in `executions` table carries `range_id` (`common/persistence/data_interfaces.go:187-193`, `common/persistence/cassandra/shard_store.go:29-37`, `common/persistence/sql/shard.go:86-113`). Ownership is claimed by incrementing `RangeID` with a conditional write `IF range_id = ?` (`common/persistence/cassandra/shard_store.go:119-152`, `common/persistence/sql/shard.go:86-113`, `service/history/shard/context_impl.go:1164-1208`). All authoritative workflow mutations (`CreateWorkflowExecution`, `UpdateWorkflowExecution`, `ConflictResolveWorkflowExecution`, `SetWorkflowExecution`, `AddHistoryTasks`) bundle a `RangeID` lease check (`templateUpdateLeaseQuery`) in the same logged batch/CAS as the workflow row CAS (`common/persistence/cassandra/mutable_state_store.go:453-463`, `701-712`, `833-844`, `1008-1019`, `common/persistence/sql/execution.go:73`, `354`, `470`, `724`). Failure surfaces as `ShardOwnershipLostError` (`common/persistence/data_interfaces.go:148-152`, `common/persistence/cassandra/errors.go:163-188`) which transitions the shard to `Stopping/Stopped` (`service/history/shard/context_impl.go:1491-1549`). Membership (`service/history/shard/ownership.go:132-147`, `service/history/shard/controller_impl.go:402-413`) decides *who should* own a shard; persistence RangeID decides *who does* own it for writes. There is no periodic lease heartbeat; renewal is on-demand (exhaustion of task-ID range, `service/history/shard/context_impl.go:1164-1208` and `service/history/shard/task_key_manager.go:20-75`) and on acquisition. Stale workers are rejected at two layers: (1) shard-level `ShardOwnershipLost` and (2) workflow-level CAS on `DBRecordVersion`/`NextEventID` and activity/workflow-task token validation (`common/persistence/cassandra/errors.go:238-284`, `service/history/api/activity_util.go:58-80`, `service/history/consts/const.go:31-40`). Process identity incorporates a UUID to distinguish restarts (`service/history/shard/context_impl.go:2201`). Takeover uses `acquireShard` with exponential backoff and a linger path that delays unloading the old owner (`service/history/shard/controller_impl.go:300-373`, `service/history/shard/context_impl.go:2030-2151`).

## Rating

**7 / 10 — Clear model with tests, explicit interfaces, and operational safeguards, but with documented gaps in heartbeat-based revocation and no-op AssertOwnership.**

**Rationale:** Shard fencing via monotonic `RangeID` CAS is explicit, consistently applied to all primary write paths, and backed by error-priority handling (`common/persistence/cassandra/errors.go:18-24`) and tests. Workflow-level fencing via `DBRecordVersion` provides per-execution linearizability. Membership-driven assignment + linger provides graceful handover. Gaps prevent a 9: no time-bounded lease expiry or heartbeat keepalive (revocation is lazy, only on next write/membership event); `AssertShardOwnership` is a no-op on both Cassandra and SQL implementations (`common/persistence/cassandra/shard_store.go:158-164`, `common/persistence/sql/shard.go:115-121`); `ShardInfo.Owner` string is informational only and never participates in the CAS; delete-path stages lack RangeID checks; clock assumptions are implicit.

## Answers to Dimension Questions

**1. Can two workers believe they own the same work?**
Yes — transiently. Membership ring (`service/history/shard/ownership.go:132-147`) may assign shard N to a new host before the old host observes `ChangedEvent`. Both hosts' `ContextImpl` can be in `Acquired` state (`service/history/shard/context_impl.go:64-72`) and report `IsValid() == true` until the next persistence CAS. The window is bounded: the old owner continues to serve reads and may accept API calls, but every authoritative write includes `RangeID` (`service/history/shard/context_impl.go:584-585`, `648`, `726`, `781`, `863`) and the batch contains `IF range_id = ?` (`common/persistence/cassandra/mutable_state_store.go:453-463`, `701-712`). Exactly one host's `RangeID` will match the persisted value; the other's batch fails with `ShardOwnershipLostError` (`common/persistence/cassandra/shard_store.go:148-153`, `common/persistence/sql/shard.go:138-141`) and forces `transition(Stop{OwnershipLost})` (`service/history/shard/context_impl.go:1534-1538`). Linger (`service/history/shard/controller_impl.go:300-373`) intentionally keeps the old shard alive for up to `ShardLingerTimeLimit` (capped at `1m`, `service/history/shard/controller_impl.go:30`) while polling `AssertOwnership`, so dual-ownership is tolerated for availability but fenced at the storage layer.

**2. Does lease expiry alone prevent stale writes?**
No. There is no time-based lease expiry or heartbeat timeout that automatically revokes a shard (`service/history/shard/ownership.go:79-101` shows only `AcquireShardInterval` ticker and membership events, not a RangeID TTL). Prevention is strictly via **conditional-update fencing**: `RangeID` equality is checked on every write (`templateUpdateLeaseQuery ... IF range_id = ?`, `common/persistence/cassandra/mutable_state_store.go:22-31`). `AssertShardOwnership` is a no-op for both Cassandra (`common/persistence/cassandra/shard_store.go:158-164`) and SQL (`common/persistence/sql/shard.go:115-121`), so even `doLinger`'s periodic `shard.AssertOwnership` (`service/history/shard/controller_impl.go:369`) cannot expire a lease without a write. The only "expiry" is when a new owner successfully executes `UpdateShard ... IF range_id = PreviousRangeID` with `RangeId++` (`service/history/shard/context_impl.go:1174-1185`), which invalidates the old owner's enqueued `RangeID`.

**3. Is fencing checked by product-state and artifact mutations, not only event writes?**
Yes for the primary product-state path, with caveats. All history-service authoritative mutations are shard-gated: `CreateWorkflowExecution` (`service/history/shard/context_impl.go:538-595`), `UpdateWorkflowExecution` (`service/history/shard/context_impl.go:597-657`), `ConflictResolveWorkflowExecution` (`service/history/shard/context_impl.go:675-735`), `SetWorkflowExecution` (`service/history/shard/context_impl.go:737-790`), and `AddHistoryTasks` (`service/history/shard/context_impl.go:487-505`, `824-869`) acquire `ioSemaphore`, hold `rwLock`, set `request.RangeID = getRangeIDLocked()`, then call the persistence layer where the batch atomically checks `RangeID` **and** workflow `DBRecordVersion`/`NextEventID`. Task-queue mutations are similarly fenced by `RangeID` (`common/persistence/data_interfaces.go:498-513`, `common/persistence/cassandra/matching_task_store_v1.go:93-129`). History branch appends (`AppendHistoryNodes`) are **not** RangeID-fenced (`service/history/shard/context_impl.go:871-908` directly calls `executionManager.AppendHistoryNodes` without `RangeID`). The `DeleteWorkflowExecution` path's stages 2 (delete current) and 3 (delete mutable state) call `executionManager.DeleteCurrentWorkflowExecution`/`DeleteWorkflowExecution` without a `RangeID` (`service/history/shard/context_impl.go:1040-1085`); stage 1's task adds are fenced via `addTasksSemaphoreAcquired`. This means visibility/replication artifact cleanup is fenced, but raw history-branch deletion is not shard-fenced (by design, since branch is immutable after workflow completion).

**4. How is process identity distinguished from reusable PIDs?**
Via an ephemeral owner string that embeds host identity **plus** a per-process monotonic sequence and a UUID: `owner = fmt.Sprintf("%s-%v-%v", hostIdentity, sequenceID, uuid.NewString())` (`service/history/shard/context_impl.go:2201`, `service/history/shard/context_impl.go:81-82`). `sequenceID` is `atomic.AddInt64(&shardContextSequenceID, 1)` per `ContextImpl` creation (`service/history/shard/context_impl.go:2184`). The `Owner` is persisted in `ShardInfo.Owner` on first load (`service/history/shard/context_impl.go:1914-1916`) but is **not** used in the CAS predicate — only `RangeID` is checked (`common/persistence/cassandra/shard_store.go:29-37`, `common/persistence/sql/shard.go:86-105`). Membership identity is `HostInfo.Identity()` (`service/history/shard/ownership.go:141-143`). Thus restart of the same binary on the same host with same PID yields a distinct `owner` (new UUID), but fencing still relies solely on `RangeID` monotonicity, not owner string comparison. The distinction is primarily for observability (`tag.Address(hostIdentity)`, `tag.ShardID`) and `StolenSinceRenew` accounting (`service/history/shard/context_impl.go:1176`), not for fencing correctness.

**5. What happens to a late completion from a superseded attempt?**
It is rejected as `NotFound` and never mutates state. Activity completions carry a `TaskToken` (`tokenspb.Task`, `common/tasktoken/token.go:33-61`) containing `ScheduledEventId`, `Attempt`, `ActivityId`, `Version`, `StartVersion`, `ActivityAttemptStamp`, and `Clock`. On arrival, handlers deserialize the token (`service/history/api/respondactivitytaskcompleted/api.go:30`, `service/history/api/respondactivitytaskfailed/api.go:31`, `service/history/api/respondactivitytaskcanceled/api.go:30`, `service/history/api/recordactivitytaskheartbeat/api.go:25`) and call `IsActivityTaskNotFoundForToken` (`service/history/api/activity_util.go:58-80`): if `ai.Attempt != token.Attempt` when `ScheduledEventId != Empty`, or `token.StartVersion != ai.StartVersion`, the request returns `ErrActivityTaskNotFound` (`service/history/consts/const.go:44-45`, `service/history/api/respondactivitytaskcompleted/api.go:85-86`). For workflow tasks, analogous `Attempt`/`StartedEventId` checks via `taskToken.NewWorkflowTaskToken` (`common/tasktoken/token.go:9-31`) produce `ErrWorkflowTaskNotFound` (`service/history/consts/const.go:94-95`). Late heartbeat (`service/history/api/recordactivitytaskheartbeat/api.go:73-74`) follows the same check. Even if the token passed, the subsequent `GetAndUpdateWorkflowWithNew` CAS would fail on stale `DBRecordVersion`/`NextEventID` (`common/persistence/cassandra/errors.go:238-284`) yielding `WorkflowConditionFailedError`, which is not retried as a stale-worker success. The client receives `NotFound` (non-retryable), and metrics `StaleMutableStateCounter` (`service/history/api/recordactivitytaskheartbeat/api.go:66-70`, `service/history/statemachine_environment.go:216`) records the event.

## Architectural Decisions

| Decision | Rationale & Location | Consequence |
|----------|---------------------|-------------|
| **RangeID as monotonic fencing token, not TTL lease** — shard table `range_id` incremented via `UpdateShard IF range_id = PreviousRangeID` (`common/persistence/cassandra/shard_store.go:119-153`, `common/persistence/sql/shard.go:82-113`, `service/history/shard/context_impl.go:1164-1208`) | Avoids clock dependence; leverages Cassandra/SQL LWT serializability for linearizable ownership. Matches design where membership already provides failure detection. | No spontaneous revocation; stale owner can serve stale reads until next write. Requires careful handling of `OperationPossiblySucceeded` errors (`service/history/shard/context_impl.go:502-503`, `1541-1549`). |
| **Batch CAS bundling workflow + RangeID** — every workflow mutation batch includes shard lease check as extra CAS query (`common/persistence/cassandra/mutable_state_store.go:453-463`, `701-712`, `833-844`) | Ensures workflow write and shard ownership check are atomic without distributed transaction. | Single round-trip to persistence; error priority sorting ensures `ShardOwnershipLost` surfaces over workflow condition failures (`common/persistence/cassandra/errors.go:18-24`). |
| **Priority semaphore for LWT path** — `ioSemaphore` (`service/history/shard/context_impl.go:129-130`, `1642-1666`) serializes LWT-eligible persistence calls per shard | Prevents thundering herd of CAS failures; Cassandra LWT throughput is limited. | Write latency includes semaphore wait; preemptable callers get low priority (`service/history/shard/context_impl.go:1647`). |
| **Drain-then-bump for RangeID renewal** — `renewRangeLocked` calls `taskKeyManager.drainTaskRequests()` before `UpdateShard` (`service/history/shard/context_impl.go:1165-1171`) | Guarantees no in-flight request is conditioned on a stale `RangeID` when the increment commits. | Renewal is blocking; new task IDs stall until renewal completes. |
| **Linger-then-close** — old shard lingers up to `min(ShardLingerTimeLimit, 1m)` polling `AssertOwnership` (`service/history/shard/controller_impl.go:300-373`) | Allows old owner to continue serving until new owner proves it has the range lock, reducing availability gap during rebalancing. | Lingering shard still consumes resources; `AssertOwnership` no-op means linger effectively waits for `IsValid()` to become false via write failure, so timeout (metrics `ShardLingerTimeouts`, `service/history/shard/controller_impl.go:363`) is the fallback. |
| **Per-workflow `DBRecordVersion` + `NextEventID` as workflow-level fencing** (`common/persistence/data_interfaces.go:131-136`, `common/persistence/cassandra/mutable_state_store.go:107-123`) | Provides execution linearizability even within a single shard owner (optimistic concurrency), independent of shard lease. Supports `UpdateWorkflowModeBypassCurrent/IgnoreCurrent` semantics. | Clients must retry on `WorkflowConditionFailedError`; transition-history staleness adds another layer (`service/history/statemachine_environment.go:244-254`). |
| **Token-borne attempt/version fencing for activities** (`common/tasktoken/token.go:33-61`, `service/history/api/activity_util.go:58-80`) | Stateless workers; token is the only proof of ownership for an activity attempt. | Late completions from superseded attempts are rejected without DB write (`ErrActivityTaskNotFound`). Requires `ActivityAttemptStamp` to distinguish retries with same `Attempt`. |

## Notable Patterns

- **CAS-based fencing everywhere** — Shard `RangeID`, workflow `DBRecordVersion`/`NextEventID`, task-queue `RangeID`, and namespace `NotificationVersion` all use conditional updates, giving a uniform mental model (`common/persistence/cassandra/errors.go:18-24` priority map is evidence of intentional hierarchy).
- **Membership as oracle, persistence as arbiter** — `ownership.verifyOwnership` via `ServiceResolver.Lookup` (`service/history/shard/ownership.go:135-144`) decides *should-own*; `RangeID` CAS decides *can-write*. The two are deliberately decoupled.
- **Detached context for persistence** — `newDetachedContext` copies values and deadline but decouples cancellation (`service/history/shard/context_impl.go:2408-2433`) so caller cancellation cannot leave persistence outcome ambiguous; `handleWriteErrorLocked` then forces `transition(Lost)` to reacquire with new `RangeID` for reliable read-after-write (`service/history/shard/context_impl.go:1541-1548`).
- **Activity token as capability** — token encodes `(ScheduledEventId, Attempt, StartVersion, ActivityAttemptStamp)` and is validated without extra DB round-trip before entering the workflow update path (`service/history/api/recordactivitytaskheartbeat/api.go:62-75`, `service/history/api/respondactivitytaskcompleted/api.go:73-86`).
- **State-machine transition registry** — `contextState{Initialized, Acquiring, Acquired, Stopping, Stopped}` with explicit `contextRequest*` messages (`service/history/shard/context_impl.go:64-83`, `1668-1826`) makes ownership lifecycle testable.

## Tradeoffs

- **Availability over strong single-owner guarantee**: Shard can be served by stale owner for reads and even speculative writes until CAS fails. This maximizes availability during membership churn but means two hosts can temporarily believe they own the same shard (Q1). The alternative (TTL lease with proactive revocation) would reduce the window at cost of clock dependence and forced unavailability on heartbeat loss.
- **No clock dependence vs. no bounded staleness**: Using `RangeID` avoids hybrid-logical-clock complexity and cross-DC clock skew, but provides no time-bounded guarantee on when stale owner is fenced without a write. A workload that stops writing could remain "owned" indefinitely.
- **LWT cost vs. correctness**: Every workflow write pays a lightweight-transaction (Paxos) cost for the `IF range_id = ?` check on Cassandra. The `ioSemaphore` throttles concurrency to protect the DB but limits per-shard write throughput. SQL path uses `WriteLockShards` (SELECT FOR UPDATE) which is heavier on contention.
- **Owner string vs. fencing effectiveness**: Embedding UUID in `ShardInfo.Owner` aids debugging (`service/history/shard/context_impl.go:2201` comment) but since it never participates in CAS (`common/persistence/cassandra/shard_store.go:126-134` only checks `range_id`), a storage-layer bug that allowed `RangeID` reuse would not be caught by owner comparison.
- **Linger improves graceful handover but masks ownership loss**: Waiting for `!IsValid()` via `AssertOwnership` no-op means linger's success metric (`ShardLingerSuccess`, `service/history/shard/controller_impl.go:354`) may indicate the shard naturally became invalid via write failure, not that linger fencing was effective.

## Failure Modes / Edge Cases

- **Stolen lease without immediate write**: Old owner continues to serve reads; `GetWorkflowExecution` has no `RangeID` check (`service/history/shard/context_impl.go:808-822`), so it can return stale mutable state that is later detected as `ErrStaleState`/`ErrStaleReference` on next task execution (`service/history/statemachine_environment.go:184-216`). Late `DescribeWorkflow` may observe stale pending activities.
- **Unknown write outcome (timeout before CAS response)**: `handleWriteErrorLocked` default case treats any error not in the known-safe list as possibly succeeded, calls `transition(Lost)` to reacquire shard with new `RangeID` (`service/history/shard/context_impl.go:1541-1549`). Callers must read-after-write to determine outcome; without this, concurrent workflows could double-create.
- **`AssertShardOwnership` no-op**: Both store implementations return `nil` (`common/persistence/cassandra/shard_store.go:158-164`, `common/persistence/sql/shard.go:115-121`). The linger loop's `shard.AssertOwnership(ctx)` (`service/history/shard/controller_impl.go:369`) therefore never marks the shard invalid on its own; only a real write error does. If the new owner never increments `RangeID` (e.g., crashes during `acquireShard` backoff), the old owner could linger until timeout and then be unloaded anyway, leaving the shard briefly unowned.
- **Delete path without fencing**: `DeleteWorkflowExecution` does `DELETE FROM executions WHERE ...` without `IF range_id = ?` (`common/persistence/cassandra/mutable_state_store.go:921-937`). If called from a stale shard concurrently with a new run's creation, the delete could remove state that the new owner just created (though the delete's preceding `DeleteCurrentWorkflowExecution` has `IF current_run_id = ?`, `common/persistence/cassandra/mutable_state_store.go:939-956`, which mitigates current-pointer corruption).
- **Task-key exhaustion race**: `taskKeyManager.drainTaskRequests` is required before `renewRangeLocked` (`service/history/shard/context_impl.go:1171`); if omitted, in-flight `AddHistoryTasks` conditioned on old `RangeID` would fail spuriously, causing unnecessary `ShardOwnershipLostError` surfacing to clients.
- **Clock skew on activity timeout vs. fencing**: Activity `HeartbeatTimeout` and `ScheduleToClose` are wall-clock driven, but fencing is version-driven. A late heartbeat that races with timeout re-drive could be both rejected (token mismatch) and still have its timeout timer fire, requiring idempotent timer handling (`service/history/consts/const.go:37-40` `ErrStaleReference` is safe to drop).
- **Split-brain on membership partition with no DB partition**: If membership partitions but DB remains reachable, both sides may `verifyOwnership` successfully (each side's resolver thinks it owns the shard). Only `RangeID` CAS breaks the tie; until then, both can create tasks that will be deduplicated only after one side's write fails.
