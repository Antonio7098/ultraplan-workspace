## Purpose

Establish who owns lifecycle truth, which facts become authoritative together, and what concurrent callers may observe. These conclusions constrain both sprints without selecting exact Go types, packages, synchronization primitives, or API signatures. The governing product is one supervised in-process work invocation, not a durable execution engine or universal executor. [IN-03 §§4–10, 14–19; IN-04]

The principal conclusion is that **one private, per-run authority must serialize validation, terminal interpretation, and commitment of the complete lifecycle fact set**. Work supplies completion facts; callers supply cancellation requests; neither publishes lifecycle truth. Retained history, current state, timing, cancellation metadata, and outcome are representations maintained by that same authority, not independently reconciled stores. [IN-03 §§5–17; IN-05 §11.1; IN-09, Phase 1 decision map]

## Atomicity model

### Authority and ownership

| Fact or operation | Authority | Boundary |
| --- | --- | --- |
| Run identity | Aren, before creation recording | Immutable for the run lifetime |
| Current state, event sequence, history, and lifecycle timing | One private per-run authority | Mutated only through the lifecycle publication protocol |
| Accepted cancellation reason and acceptance occurrence | Same per-run authority | Explicit and parent requests cannot write separate records |
| Work result, returned error, or panic occurrence | Supplied by work and captured by Aren | Inputs to resolution, not a terminal state |
| Terminal classification and outcome container | Aren's central resolution and commitment path | Never selected by an observer or independent cancellation writer |
| Waiter completion readiness | Same publication owner | Cannot precede the complete terminal fact set |
| Observer cursor and delivery progress | Observation-local state | Cannot change canonical history or decide whether execution proceeds |
| Arbitrary objects reachable from a work result | User code's ownership contract | Outside Aren's deep-immutability and transactional guarantees |

This division is a lifecycle API boundary, not protection from malicious code in the same process. It also does not imply that a work closure cannot possess cancellation authority deliberately supplied by its host. Such a closure may request cancellation through the ordinary controller, but still cannot commit a state. [IN-03 §§9–10, 17, 19; IN-16 P1, P8]

### Minimum coherent fact set

A supported observation must correspond to one complete committed prefix of a run's lifecycle. “Prefix” here is a reasoning model, not a requirement to expose a version number or implement event-sourced reconstruction. [IN-03 §§14–17; IN-14 Pattern 1]

| Transition kind | Preconditions | Facts produced | Observers released | Forbidden partial views |
| --- | --- | --- | --- | --- |
| Creation | Identity generated; run not externally published | Identity, `created`, `run.created` at sequence `0`, creation occurrence time, absent terminal outcome and finish time | No terminal waiter; later history readers can retrieve creation | Event without identity; externally reachable uninitialized history; fabricated start or finish time |
| Start | Current state is `created`; creation already recorded | `running`, start time, `run.started` with `created -> running`, next sequence and occurrence time | History readers may observe start; work may be invoked after start commitment | Running without start event/time; work invoked before start recording; outcome while running |
| Cancellation acceptance | Running, no terminal commitment, no previously accepted request | First reason and provenance required by the cancellation contract, one `run.cancellation_requested`, next sequence and occurrence time; state remains running | Observation may notice acceptance; work receives the cancellation signal only after acceptance is committed; no terminal waiter is released | Signal bypassing acceptance; reason without request event; duplicate request event; terminal cancellation while work remains active |
| Terminal | Running; work has returned or unwound through the supervised panic boundary; applicable accepted cancellation facts are stable for resolution | One terminal state, finish time, resolved outcome, matching terminal event and sequence, preserved prior history and cancellation facts, terminal readiness | All completion waiters become eligible; live observers can drain through the terminal event and then complete | Terminal state without event/outcome/timing; event ahead of commitment; early waiter return; contradictory terminal records; later lifecycle append |

Repeated cancellation and post-terminal cancellation do not append history or allocate a sequence. They return the appropriate disposition from the same authority. An internal attempt to finalize twice is rejected without changing the committed outcome or adding a second event; it must not be silently normalized into successful internal execution. [IN-03 §§12–15; IN-05 §7]

Given the fixed vocabulary and acceptance rules, an ordinary completed Phase 1 run has three lifecycle records without accepted cancellation and four with it. This is a derived event-count bound, not a memory-byte bound: arbitrary result objects and diagnostic data may be much larger. It does not justify high-volume retention or new diagnostic event types. [IN-03 §§7, 12, 15–17; IN-05 §11.7]

### Linearization and terminal interpretation

Each mutating operation has one conceptual point at which its decision and complete fact set become authoritative relative to other operations. The operation must not report acceptance or successful commitment before this point. Private intermediate calculations are permitted; supported readers must never acquire them as committed facts. [IN-03 §§5, 12–14]

Terminal handling has two distinct responsibilities:

1. **Interpretation:** Resolve captured work facts against the cancellation facts committed before terminal commitment, using the PRD truth table.
2. **Exclusion:** Refuse any attempt to alter the run once a terminal commitment exists.

These responsibilities may share one implementation function or use private helpers, but they cannot have a stale-state window between them. Classifying a cancellation-related error outside authority and later publishing that classification without revalidation could use an obsolete acceptance fact set. Scheduler order may change which cancellation request is accepted before commitment; it must not change the interpretation of an identical committed fact set. [IN-03 §13; IN-19 P1–P2; IN-09, Phase 1 decision map]

Cancellation signaling is a consequence of accepted lifecycle facts, not an alternative authority. The cancellation area must close the interval between acceptance and signal propagation, including a work return during that interval, without reintroducing an early terminal-cancellation path. This area fixes the ordering obligation but does not select the Go parent-context bridging or signaling mechanism. [IN-03 §§12–14; IN-05 §7; IN-02, Reasoning Areas]

### Supported reads

Every supported read must return data from a valid committed point during that operation. A multi-field inspection promising a coherent snapshot must capture all its fields together; assembling it from separate state, history, and outcome reads is insufficient. A history snapshot may show an earlier valid prefix, but its contents must not change after return through an Aren-owned alias. [IN-03 §§14–17; IN-05 §11.2; IN-14 Pattern 1]

Separate reads are not one transaction. For example, a caller may read `running`, completion may commit, and a later history read may include the terminal event. That sequence is valid. By contrast, reading a terminal state and then starting a fresh full-history or outcome inspection must not reveal missing terminal facts, because terminal commitment is final and those later operations cannot linearize before it. [IN-03 §§7, 14, 17]

Historical event state is also historical: replaying `run.started` after completion does not assert that the current run is still running. Event transition data must agree with the committed transition it describes, not equal the latest state at delivery time. [IN-03 §§15–16]

The exact coherent inspection surface belongs to Sprint 1. It must make publication testable without exposing mutation authority. Sprint 2 must preserve the same read semantics when adding subscriptions and cursors rather than introducing an eventually consistent observation mirror. [IN-04, both implementation waves; IN-17 P3]

### Timing and notification

Event occurrence time belongs in the committed event, not in a delivery wrapper. For this local lifecycle, the event describes the Aren-owned creation, start, acceptance, or terminal commitment; it does not claim to timestamp the caller's earlier intent, the exact user-function return instruction, or an observer's receipt. Start and terminal timing must be captured once at their corresponding lifecycle boundaries and used consistently by event and outcome representations. This is a project interpretation of the PRD's lifecycle-event and timing requirements, not a timing mechanism demonstrated by the Go study. [IN-03 §§5, 15, 18; IN-19, Notable Absences]

Sequence establishes order even when timestamps are equal or wall-clock values are unsuitable for ordering. No elapsed-time threshold, public clock interface, or separate raw-return timestamp is introduced here. Sprint 1 must prove start/finish coherence with its chosen time representation; the outcome area owns any additional duration semantics. [IN-03 §18; IN-02, Source Document Assignments]

Terminal readiness must be integrated with complete publication so there is no supported state in which a terminal run lacks its outcome or completed waiting path. Internal signaling may occur while ownership is still held after all facts are installed, or through another proven protocol; consumer execution must remain outside mutation ownership. This distinction does not require every waiter to run simultaneously or every observer to receive the event before a waiter returns. It requires that the canonical terminal event already be available. [IN-03 §§10, 14, 16–17; IN-05 §§3, 11.1]

A goroutine join, user callback, blocking delivery, error-formatting callback, or user-defined cause-matching method must not become an unexamined operation under lifecycle ownership. Sprint reasoning must audit indirect calls as well as explicit work invocation. This is a lock-scope risk derived from the no-blocking/reentrancy obligations; exact cause matching remains the outcome area's responsibility. [IN-05 §7; IN-19 P5–P7; IN-02, Reasoning Areas]

For contained invariant faults, an Aren-origin failed outcome is appropriate only when a truthful `running -> failed` commitment remains possible and the supervised work is no longer active. Detection before start, after terminal commitment, or after loss of trustworthy bookkeeping cannot authorize an invented transition or replacement outcome. Such defects require explicit invariant-failure signaling rather than silent continuation or a fabricated successful recovery. The outcome area and Sprint 1 must specify and test the concrete containment boundary. [IN-03 §§7, 11–14; IN-05 §7; IN-09, Phase 1 decision map]

## Trade-Offs

**Inspectability versus serialized indirection.** Direct mutation under one private ownership boundary is likely easier to inspect for a five-state run with at most one accepted cancellation. An ownership loop can make writer identity more explicit and simplify command-order instrumentation, but adds queue, reply, and lifetime obligations. The current evidence supports both as mechanisms, not a claim that either is universally safer. Sprint 1 should prefer the smallest correct realization. [IN-03 §§7, 12; IN-05 §§11.1, 11.3, 11.10; IN-19, Approach Models]

**Fail-fast invariants versus returned failures.** A panic exposes defects close to the violation but is unsafe as an accidental host-process policy. A classified Aren failure supports inspection but can hide corruption if it requires recursively repairing invalid state. The semantic choice is immediate rejection and preserved classification; containment is allowed only where truth can still be published coherently. Logging and proceeding with the illegal write is not an acceptable compromise. [IN-03 §11; IN-05 §7; IN-15, Soft-assert pattern; IN-19 P5, P7]

**Direct state access versus snapshots.** A value-returning state accessor can be cheap and coherent without returning every field. It cannot offer a transaction with separate later accessors. A combined snapshot costs copying or immutable retention but supplies a precise multi-field inspection contract. The sprint should expose only the read shapes actually needed, with each consistency boundary documented. [IN-03 §§14, 17; IN-14 Pattern 1; IN-05 §11.2]

**Immediate canonical truth versus delivery latency.** Waiters need a complete outcome, not proof that every observer has processed the event. Requiring acknowledgements would couple execution to abandoned observers. Allowing delivery lag is safe only because canonical retention and terminal readiness do not depend on delivery. [IN-03 §§15–17; IN-19 P6]

**Exact successful results versus stronger object isolation.** Copying arbitrary user values could alter identity, invoke unsafe behavior, or falsely imply universal freezing. Not copying them leaves users responsible for their own mutable objects. The correct boundary is strict protection of Aren lifecycle data and an explicit exception for arbitrary result graphs, rather than weakening every payload's ownership contract. [IN-03 §§11, 17; IN-05 §11.2]

**Narrow current truth versus future generality.** A later durable runtime may need a log-first reconstruction model or executor-specific stop conditions. Phase 1 needs neither. Clear private ownership preserves refactoring options without promising that today's work function or in-memory representation is universal. [IN-03 §§4, 25; IN-06 §§3.2, 5.6; IN-18, Executive Summary]

## Self-critique

**What is the strongest credible argument for a different authority model?** A dedicated ownership loop can make unauthorized writes harder to introduce and can expose a clean command-order trace. That may be worth its additional lifetime and request/reply protocol if direct ownership becomes scattered. This document does not rule it out. Its preference is for minimum demonstrated complexity, not for a predetermined mutex implementation. [IN-05 §§11.1, 11.10; IN-12, Approach Models]

**Which atomicity claim is currently prose rather than executable proof?** All Aren-specific publication claims are presently semantic obligations. No current implementation, source revision, controlled schedule, or memory-order proof was inspected. The strongest concrete Go evidence shows fragments of the discipline and relevant failures, not a complete Aren implementation including timing, active inspection, immutable lifecycle payloads, and multiple waiters. [IN-19, Notable Absences; IN-09, Evidence quality assessment]

**Could these conclusions permit an observer to see a combination the PRD forbids?** They would if “one writer” were implemented without a shared read-publication discipline, if a combined snapshot were assembled through separate accessors, or if readiness were handled as unrelated post-processing. The atomicity model explicitly excludes those interpretations. It allows different valid versions across separate calls and historical event delivery, neither of which is a torn single observation. Sprint tests must make that distinction precise. [IN-03 §§14–17]

**Does invariant handling remain too open?** The allowed semantics are bounded: reject illegal mutation, preserve recognizable Aren-origin failure, do not fabricate transitions, do not overwrite terminal truth, and do not recursively finalize. The unresolved choice is how the concrete runtime exposes and contains faults when its bookkeeping cannot be trusted. That choice belongs to the outcome area and Sprint 1; it must be resolved before claiming their acceptance, not hidden behind a generic recovery helper. [IN-03 §§7, 11, 13; IN-05 §7; IN-02]

**Did future durability concerns distort the in-memory model?** The evidence repeatedly encourages log-first state and transactional machinery, but neither is selected. A committed prefix is used to define observable consistency and an independent verifier, not to prescribe a reconstruction engine. Current facts and retained history remain under one local owner, with no crash-survival claim. [IN-03 §§4, 16, 19; IN-13, Approach Model C; IN-14, Core Thesis]

**Where is confidence weakest?** The acceptance-to-signal interval, arbitrary error/panic object ownership, callback-free cause matching, and completion-versus-resource-release boundary need downstream analysis and concrete tests. The reasoning README also remains unverified. These limitations do not reopen the PRD, but they prevent treating this area output as implementation evidence or a passing project review. [IN-02, Reasoning Areas; IN-05 §§7, 11.2–11.3; IN-08; IN-09, Self-critique]
