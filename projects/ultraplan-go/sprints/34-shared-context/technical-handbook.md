## Relevant Patterns

- **Product-owned composition behind a one-way boundary:** `01-project-structure` finds thin boundary code delegating to protected application logic, including the command/action split at `helm/pkg/cmd/install.go:347` and `helm/pkg/action/install.go:73-140` and the one-way imports at `yq/cmd/root.go:9` and `yq/cmd/evaluate_sequence_command.go:7`. For this sprint, that evidence creates pressure to keep shared sprint semantics in the sprint domain while leaving generic execution infrastructure unaware of those semantics; reasoning must determine the narrowest API that preserves that direction.
- **Explicit stage delegation rather than implicit middleware:** `02-command-architecture` shows factory-based construction at `gh-cli/pkg/cmdutil/factory.go:16-43` and thin delegation at `helm/pkg/cmd/install.go:132-145`; it also reports no formal middleware chain across the cohort. This may favor visible integration at each agent-backed stage boundary over a hidden lifecycle hook, while leaving the exact composition shape for reasoning.
- **Manual wiring for a single canonical behavior:** `03-dependency-injection` reports explicit composition roots at `gh-cli/internal/ghcmd/cmd.go:52-132` and `opencode/internal/app/app.go:42-81`, with no Wire/Fx/Dig-style framework in the studied repositories. A concrete renderer or assembler may therefore be easier to trace than a registry, service locator, or configurable provider, but reasoning must test whether existing UltraPlan seams already justify an injected collaborator.
- **A complete I/O seam for source resolution and byte capture:** `06-io-abstraction` demonstrates filesystem interfaces at `chezmoi/internal/chezmoi/system.go:25` and `restic/internal/fs/interface.go:10-31`, in-memory streams at `gh-cli/pkg/iostreams/iostreams.go:551-568`, and the cost of bypassing an abstraction at `rclone/cmd/ls/ls.go:42`. Sprint reasoning should account for every repository read and prompt write path, because a partial seam would weaken containment and exact-byte tests.
- **Cancellation propagated through all long work:** `07-state-context` ties operational maturity to root-context propagation, with signal wiring at `helm/pkg/cmd/install.go:333-347` and sibling cancellation at `go-task/task.go:89,321`. Source reads, prompt preparation, and every downstream runtime request may need one coherent cancellation lineage; detached cleanup, if any, requires a separately bounded rationale such as `restic/internal/restic/lock.go:290-305`.
- **Functional output separated from diagnostics:** `05-error-handling` distinguishes user and operational errors at `age/cmd/age/tui.go:37-54` and `k9s/internal/model/flash.go:100-103`; `10-logging-observability` independently finds stdout/stderr separation and stable structured keys at `k9s/internal/slogs/keys.go:6-231`. This matters because timestamps, run IDs, attempts, and diagnostic details must not accidentally alter a stable common prefix.
- **Observable bytes tested at more than one level:** `11-testing-strategy` shows golden comparison at `go-task/task_test.go:166-169`, shared golden helpers at `helm/internal/test/test.go:43`, and command-pipeline coverage at `chezmoi/internal/cmd/main_test.go:64-174`. The evidence supports combining focused serializer checks with representative stage-level request capture; reasoning must define which complete byte boundary is contractual and which fields are intentionally outside it.
- **Bounded, selected source handling before speculative indexing:** `14-performance` demonstrates fixed-size streaming at `age/internal/stream/stream.go:20,195-219`, incremental processing at `yq/pkg/yqlib/stream_evaluator.go:78-113`, and bounded workers at `gdu/pkg/analyze/parallel.go:13`. Together with `15-philosophy`'s simplicity-first evidence (`age/age.go:18`, `restic/doc.go:5-10`), this supports evaluating a bounded reference-driven approach before introducing retrieval or indexing machinery, without predetermining the exact budget policy.
- **Trust boundaries made explicit and enforced centrally:** `13-security` associates stronger tools with explicit untrusted-input handling, schema validation at `k9s/internal/config/json/validator.go:146`, and permission checks at `opencode/internal/permission/permission.go:44-108`. Repository-relative references and resolved excerpts should therefore be treated as trust-boundary inputs, while the canonicalization, symlink, file-kind, and race policies remain sprint-reasoning decisions.

## Trade-Offs

| Trade-Off | Benefit | Cost | When It Matters |
| --- | --- | --- | --- |
| Central sprint-owned composition vs stage-local composition | One visible owner can prevent drift across planning, execute, review, and smoke, consistent with the one-way domain boundaries in `01-project-structure` (`helm/pkg/cmd/install.go:347`, `helm/pkg/action/install.go:73-140`). | A central object or helper can become a god abstraction, a risk reflected by centralized-state cautions in `07-state-context` and `helm/pkg/action/action.go:119-146`. | When reasoning chooses what belongs to the byte-stable common prefix and what remains stage-specific. |
| Direct concrete calls vs injected renderer interface | Direct calls align with the manual-construction norm in `03-dependency-injection` and make a single implementation easy to trace. | Injection can isolate tests and substitutions, but an interface for one stable implementation may add configuration paths that permit divergence. | When deciding whether existing service construction needs a test seam or a pure concrete function is sufficient. |
| Full buffering vs streaming assembly | Full buffering makes exact byte comparison, separator handling, and atomic request construction straightforward. | Memory grows with context size; streaming evidence such as `age/internal/stream/stream.go:195-219` is safer for unbounded inputs but complicates line boundaries, truncation, and error handling. | When source excerpts approach the prompt budget; a hard aggregate bound may make buffering acceptable. |
| Sequential reads vs bounded concurrent reads | Sequential processing gives simple deterministic order and cancellation behavior. | It may increase latency; bounded workers like `gdu/pkg/analyze/parallel.go:13` improve throughput but require ordered collection independent of completion order. | When measured source-resolution time is material for large context packs. |
| Fail fast vs aggregate reference findings | Failing fast limits unsafe work after cancellation or containment failure. | Aggregation can provide a more actionable repair list, as multi-error examples at `helm/pkg/action/uninstall.go:232-254` and `restic/internal/checker/checker.go:70-91` show. | When distinguishing security-critical failures from ordinary missing or out-of-range references. |
| Golden fixtures vs focused assertions | Goldens catch whitespace, order, delimiter, and full-output regressions (`go-task/task_test.go:166-169`; `helm/internal/test/test.go:43`). | Fixtures can become stale, and broad update commands can bless unintended changes; substring or regex assertions are easier to maintain but weaker for exact-byte contracts. | When defining stable prefix compatibility and review controls for intentional updates. |
| Stable structured diagnostics vs free-form messages | Shared keys such as `k9s/internal/slogs/keys.go:6-231` improve cross-stage correlation while keeping dynamic facts outside functional bytes. | A schema requires maintenance and can become overbuilt for a narrow feature. | When stage, path, range, runtime, and cancellation facts must be diagnosable without contaminating the common prefix. |
| Lazy context preparation vs eager preflight | Lazy construction avoids work for commands that do not need source context, as shown by `gh-cli/pkg/cmdutil/factory.go:27-42`. | First-use latency and deferred failures may make behavior harder to predict. | When deciding whether preparation occurs once per flow/run or independently at each downstream invocation. |

## Anti-Patterns And Warnings

- **Duplicated stage-specific prefix assembly:** Repeating composition in planning, execute, review, or smoke risks drift and violates the thin-delegate pressure in `02-command-architecture`; large handlers such as `opencode/cmd/root.go:49-183` and `restic/cmd/restic/cmd_backup.go:84-115` show how orchestration can absorb domain behavior.
- **Generic runtime knowledge of sprint semantics:** The one-way dependency evidence in `01-project-structure`, especially `yq/cmd/root.go:9` and `yq/cmd/evaluate_sequence_command.go:7`, cautions against reversing product-to-platform dependency direction merely to make prefix injection convenient.
- **Global mutable or context-hidden dependencies:** `03-dependency-injection` identifies global configuration at `rclone/fs/config.go:793` and global parser/logger state at `yq/pkg/yqlib/lib.go:13-21` as hidden-coupling risks; `07-state-context` similarly warns about service-locator context keys at `k9s/internal/keys.go:10-38`. These patterns would make exact-byte behavior and parallel tests harder to isolate.
- **Partial I/O abstraction:** An abstract core is not sufficient if one stage bypasses it, as shown by `rclone/fs/operations/operations.go:864` versus `rclone/cmd/ls/ls.go:42`. Direct `os.ReadFile`, global stdout, or alternate repository access in one downstream path could evade containment, budgets, or captured request tests.
- **Stringly typed or broken error chains:** The error report warns against message parsing and lost causes; mature examples preserve chains at `opencode/internal/llm/agent/agent.go:238` and classify sentinels at `helm/pkg/storage/driver/driver.go:29` and `helm/pkg/action/upgrade.go:235`. Trimming errors into plain text too early would obscure cancellation and reference-failure handling.
- **Detached contexts in cancellable work:** `07-state-context` flags `chezmoi/internal/cmd/templatefuncs.go:215` and `dive/image/analysis.go:20` as propagation breaks. Source inspection or downstream calls started with `context.Background()` could outlive the governed operation and report misleading state.
- **Diagnostics mixed into canonical prompt bytes:** `10-logging-observability` identifies stdout contamination at `fzf/src/core.go:325` and abstraction bypass in `urfave-cli/cli.go:32-59`. Debug mode, timestamps, run IDs, output paths, and session fields must remain observability data rather than accidental prefix content.
- **Regex or substring-only tests for an exact-byte contract:** `11-testing-strategy` calls regex output checks such as `gh-cli/pkg/cmd/issue/list/list_test.go:88-91` more fragile than golden comparison. Presence checks can pass while order, whitespace, duplicate insertion, or boundary placement is wrong.
- **Path validation by lexical matching alone:** `13-security` identifies raw-path handling at `gdu/internal/common/ignore.go:16-37` as a canonicalization weakness and notes broader gaps around paths passed to file reads. Prefix string checks alone do not settle absolute paths, `..`, symlinks, special files, or replacement races.
- **Unbounded queues, reads, or final prompts:** `14-performance` cautions that bounded workers do not help if queued work remains unbounded. Streaming source files also does not bound the assembled prompt; per-reference and aggregate limits need explicit semantics.
- **Premature framework, plugin, index, or persistence machinery:** `15-philosophy` emphasizes explicit non-goals and intentional complexity (`age/age.go:18`; `lazygit/VISION.md:97`). A generic prompt framework, provider registry, RAG/index, or database would require evidence beyond the selected sprint problem.
- **Overstated dogfood evidence:** `11-testing-strategy` distinguishes library-only tests from actual CLI/pipeline integration, while `13-security` shows explicit permission gates at `opencode/internal/permission/permission.go:44-108`. A blocked, simulated, constructed-only, or unsent runtime request must not be reported as completed real-runtime dogfood.

## Design Pressures

- One common prefix must remain byte-identical while later stage instructions, output contracts, run metadata, and diagnostics vary.
- Stored `requirements.md` and `code-context.md` bytes must remain distinct from transient resolved source evidence; the reports support deterministic seams but do not define this serialization boundary.
- Every agent-backed route must participate, including independently issued review requests and conditional smoke authoring, without moving sprint policy into generic runtime infrastructure.
- Source references originate in generated Markdown and point into an implementation repository, creating validation, containment, symlink, file-kind, line-range, and time-of-check/time-of-use pressures.
- Bounded evidence must still be truthful: omitted or truncated material cannot appear complete, and overflow behavior must be deterministic.
- Cancellation, runtime failure, invalid references, and failed reruns must preserve actionable error identity and the prior valid governed artifacts.
- Deterministic fake-runtime coverage must prove exact bytes and call order, while gated real-runtime evidence must distinguish unavailable prerequisites from passed behavior.
- Stable prompt bytes and useful observability pull in opposite directions unless functional content and dynamic diagnostics have separate channels.
- The same product capability reaches CLI, TUI, browser, manual skill, flow orchestration, and direct stage calls; shared behavior must not become duplicated surface logic.
- Performance pressure should be answered with measured bounds and targeted reads before introducing indexing, retrieval, caches, or persistence that the selected evidence does not justify.
- The evidence favors simple explicit construction, but existing UltraPlan service seams may impose integration constraints that the external studies did not examine.

## Open Questions For Reasoning

- What exact byte range defines the common prefix, including heading text, separators, trailing newlines, encoding, and the stage-specific boundary?
- Does the renderer return a complete immutable byte slice, write to an injected stream, or expose a narrower composition operation, and how is accidental mutation prevented?
- Is the shared context prepared once per governed operation or rebuilt for each downstream request; what source-change behavior is truthful between those choices?
- Which values belong inside the stable prefix, which belong after the stage boundary, and which belong only in runtime metadata or structured logs?
- How are reference order, duplicate references, overlapping ranges, path spelling, line endings, and final newline behavior canonicalized without rewriting the stored context pack?
- What containment algorithm handles absolute paths, `..`, symlinks, hard links, special files, repository-root replacement, and files changed between validation and read?
- What per-reference, per-file, aggregate byte, estimated-token, line-count, and elapsed-time limits apply, and is the budget measured before or after prompt formatting?
- On budget overflow, are references rejected, truncated with explicit markers, prioritized deterministically, or handled by another bounded policy?
- Should reference failures aggregate for repair, fail fast for safety, or use different behavior by error class?
- If source reads are concurrent, how are deterministic ordering, cancellation, error aggregation, and bounded queued work preserved?
- Which representative downstream operations must share one exact fixture, and should tests compare full runtime request bytes or an explicitly extracted prefix boundary?
- How are golden updates reviewed so an update command cannot silently bless changed prefix ordering or whitespace?
- How does the manual code-context skill delegate to the canonical operation without reproducing stage order, target resolution, validation, or prompt behavior?
- Which observable facts prove that `code-context` ran exactly once in cumulative flow and that each downstream agent request received exactly one prefix?
- What evidence distinguishes fake-runtime coverage, a constructed but unsent request, a permission-blocked request, provider acceptance, valid artifact generation, and successful end-to-end dogfood?
- Are any existing stage call paths intentionally agent-free, and how should tests prove that conditional runtime paths receive context whenever they do invoke an agent?
- Does existing application composition provide the right shared seam, or would reusing it create a central object broader than the behavior warrants?

## Handoff To Reasoning

- Use this handbook as evidence input.
- Validate whether the observed patterns fit this project's constraints.
- Resolve exact-byte, containment, budget, cancellation, and dogfood semantics explicitly rather than inferring them from analogous tools.
- Treat report findings as comparative evidence, not final implementation choices.
- Do not copy external patterns without sprint-specific reasoning.
