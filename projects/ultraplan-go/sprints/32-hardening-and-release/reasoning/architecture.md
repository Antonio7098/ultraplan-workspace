# Architecture: Local Web Hardening and Release

Scope: harden the Sprint 30-31 local browser surface while preserving the module-driven architecture, shared CLI/TUI/web product capabilities, filesystem-backed durable authority, bounded server-owned operations, and single-binary distribution. The current architecture fits partially: its dependency direction is correct, but any remaining workflow interpretation, shutdown reconciliation, or stage-specific behavior in `internal/web` must be moved behind typed `internal/app` capabilities before release hardening is complete.

Key conclusion: perform a small boundary refactor first, then harden in place. Keep `internal/web` as a transport and presentation adapter, extend `internal/app` only with narrow use-case-oriented capabilities required by all local surfaces, and leave workflow rules, mutation exclusion, durable terminal state, and recovery in their owning product modules. Do not introduce a web workflow engine, generic plugin system, alternate persistence layer, or broad service container.

## Area Decisions

### Ownership and dependency direction

- Preserve the required direction: `cmd/ultraplan -> internal/app + internal/tui + internal/web`, `internal/web -> internal/app`, and `internal/app -> product/platform modules`. `internal/web` may use the Go standard library but must not import `internal/study`, `internal/project`, `internal/sprint`, runtime adapters, process adapters, or CLI handlers.
- Keep the composition root at the executable edge. `cmd/ultraplan` constructs side-effectful interface runners, effective configuration, logger, clocks/IDs where required, app services, and the web server explicitly. No package-global runner, mutable registry, context service locator, or reflection-based DI container is added.
- Keep HTTP handlers thin: validate transport input, call one typed app use case, and map typed results into JSON DTOs or explicit page view models. Handlers do not parse CLI output, read workflow files directly, invoke `ultraplan` as a subprocess, compute verdicts, construct prompts, select runtimes, or interpret product state strings.
- Keep templates presentation-only and downward-composed as `page -> layout -> component -> primitive`. Templates receive explicit typed view models and perform no filesystem access, app call, HTTP validation, state mutation, or workflow-state interpretation. Duplicate or invalid namespaced definitions fail startup.

### Shared application capability

- Define the web-facing app boundary around the smallest stable capability vocabulary already required by all local surfaces: status/readiness, findings, artifacts, available commands, normalized operation preparation, execution, progress, cancellation, terminal result, and durable recovery/next action.
- Capabilities describe what a product operation supports, not how a stage is orchestrated. Product modules retain stage order, validation, mutation locks, runtime/harness invocation, durable state transitions, verdicts, and recovery rules. The app layer composes those product operations and maps their typed results into surface-neutral values.
- Prove extensibility with a fake future-stage capability in tests. Adding that fixture must expose status, artifacts, commands, progress, cancellation, and recovery without a new web route branch or production plugin registry. This is a contract test, not authorization to implement a new stage.
- Prefer concrete app result types and small consumer-oriented interfaces. Add an interface only at a volatile boundary or where at least CLI/TUI/web and deterministic fakes need substitution. Reject a single `WebService`, `Manager`, or all-product god interface and reject one-method interfaces that merely mirror concrete methods without isolating volatility.

### State authority and mutation

- Workspace artifacts and product-owned run/flow state remain the only durable authority. Product modules own atomic writes, mutation exclusion, terminal reconciliation, stale-lock policy, and restart recovery.
- The web operation hub owns only bounded ephemeral transport state: operation IDs, normalized safe request summaries, confirmation records, canonical cancellation functions, recent redacted events, subscribers, and short-lived safe terminal projections. It is neither a scheduler nor a durable run store.
- Queries and commands remain explicit. HTTP `GET` reads app projections; `POST` prepares or starts commands; `DELETE` requests canonical cancellation; SSE observes progress only. Polling, event buffers, browser state, and subscriber presence never become product state.
- The server owns every operation it starts. Refresh, navigation, tab close, and SSE loss end only the subscription. Detached product work after server exit is unsupported; a durable worker or operation queue requires a future architecture decision.
- Product-owned mutation locks arbitrate conflicts across CLI, TUI, and web. HTTP middleware may reject draining or malformed requests but must not become the owner of study/sprint mutation exclusion.

### Operation and shutdown lifecycle

- Create one operation work context from server ownership and explicit operation cancellation. Propagate it through app, product, runtime, and process boundaries. Do not create fresh background contexts inside normal work.
- Centralize terminal arbitration so completion, failure, timeout, user cancellation, and server shutdown produce exactly one terminal result and invoke canonical cancellation at most once. A late cancellation cannot overwrite an already-authoritative completion or failure.
- On graceful shutdown, transition the server to draining, reject new mutations and starts, snapshot active operation cancellation functions without waiting under hub locks, request cancellation with reason `server_shutdown`, and wait for bounded product cleanup/reconciliation.
- Use a distinct bounded cleanup context only for process-tree cleanup, durable terminal reconciliation, and lock ownership resolution after the work context is cancelled. If cleanup cannot be proven before the deadline, the owning product module persists owner-specific `cleanup_uncertain` or equivalent truthful uncertainty before HTTP/SSE closes.
- Startup recovery asks product modules to reconcile stale active state and locks conservatively. Process absence and artifact presence are evidence inputs, never proof of success.
- Use explicit lock ordering and never call app/product code, perform filesystem writes, send to subscribers, or wait for goroutines while holding hub locks. Slow subscribers are disconnected or given a replay gap; they cannot block product execution or shutdown.

### Configuration, security, and observability boundaries

- Resolve configuration through built-in defaults, workspace config, environment, then command flags; validate the merged immutable server configuration before listening. Unsafe bind addresses, invalid templates, duplicate definitions, impossible limits, and incoherent timeout/retention combinations fail startup.
- Keep browser security in `internal/web`: numeric-loopback bind enforcement, Host/Origin/CSRF/session policy, request limits, headers/CSP, HTTP path/reference validation, safe Markdown rendering, and final JSON/HTML/SSE redaction. Keep executable construction, product path containment, runtime permissions, and product object authorization in their existing app/product/platform owners.
- Redact at both type and projection boundaries. Secret-safe app/runtime values reduce accidental formatting; web mapping independently allowlists fields. Raw prompts, provider payloads, stderr, cookies, CSRF/session values, tokens, unsafe paths, and executable arguments never enter retained events or terminal projections.
- Emit structured request, operation, cancellation, cleanup, replay-gap, and recovery diagnostics through the injected logging path. Product output and diagnostics remain separate, and direct writes that bypass capture/redaction are prohibited.

### Presentation and packaging

- Keep server-rendered HTML complete without JavaScript. Dependency-free JavaScript enhances guarded operations, cancellation, SSE reconnect, and durable refresh but owns no router, persistent store, workflow state, or terminal truth.
- Parse and validate embedded namespaced templates before serving. Embed templates, layered CSS, and narrow JavaScript in the Go binary; runtime must not depend on the source tree, Node.js, Vite, a package manager, a database, or a separate frontend process.
- Keep CSS and template layering as architectural dependency rules because they prevent presentation cycles and state interpretation from leaking downward. They do not justify a new frontend component framework.

### Verification architecture

- Test app capabilities independently with fake product/runtime/harness dependencies. Test HTTP/SSE as adapters with `httptest`, temporary workspaces, deterministic clocks/IDs/barriers, and injected app fakes. Keep live provider and external harness checks gated.
- Add an import-boundary test or equivalent inspection proving `internal/web` imports only `internal/app` and standard-library packages. Add a capability fixture proving a new stage needs no route-specific orchestration.
- Separate deterministic layers: typed app capability tests; API compatibility fixtures; template/view-model and accessibility tests; security/path/redaction tests; operation/SSE race, leak, and lifecycle tests; representative real-app integration over temporary workspaces; packaging outside the source tree; gated runtime/harness evidence.
- Run race and leak coverage against operation start/cancel/terminal races, slow subscribers, shutdown deadlines, and restart reconciliation. Runtime success, HTTP success, and artifact existence alone never establish product success.

Final architecture decision: refactor boundary violations first, then harden the existing shape. Complexity introduced is medium in lifecycle arbitration and deterministic verification; complexity removed is high where route-specific logic, hidden dependencies, or web-owned interpretation are eliminated.

## Trade-Offs

| Decision | Benefit | Cost | Rejected Alternative |
| --- | --- | --- | --- |
| Small boundary refactor before hardening | Makes security, compatibility, shutdown, and cross-surface behavior testable against one product core | Requires moving existing logic before adding release checks | Harden route-specific workflow code in place; rejected because it would preserve duplicate ownership |
| Narrow app capabilities over product modules | Reuses behavior across CLI, TUI, and web and proves future-stage extensibility | Requires careful result vocabulary and mapping | Web importing product modules or calling CLI handlers; rejected because both bypass the shared application boundary |
| Explicit manual composition | Keeps dependencies and lifecycle visible and permits deterministic fakes | Constructors may be verbose | DI framework, globals, or context service locator; rejected as hidden complexity without a concrete need |
| Product-owned durable state plus ephemeral web hub | Preserves one source of truth and supports truthful restart recovery | Old operation handles expire and clients must refresh | Web database, operation queue, or durable scheduler; rejected as a second authority outside sprint scope |
| One work context plus bounded cleanup context | Delivers prompt cancellation while allowing truthful reconciliation | More lifecycle states and timeout handling | Reuse cancelled context for cleanup or detach cleanup indefinitely; rejected because one loses reconciliation and the other loses ownership |
| Central terminal arbiter and exact-once cancellation | Makes cancellation, failure, completion, and shutdown races deterministic | Requires synchronization and exhaustive race tests | Let each transport callback write terminal state independently; rejected because outcomes could conflict |
| Consumer-oriented capability interfaces | Supports fakes and multiple local surfaces without exposing internals | Interface evolution requires coordination | One broad web service or interface-per-method; rejected because both obscure cohesion |
| Fail-closed startup validation | Prevents unsafe serving with malformed limits, templates, or security policy | A bad configuration prevents startup rather than degrading | Warning and fallback; rejected because silent correction undermines security and operability |
| Bounded lossy transport with durable refresh | Protects memory and product progress from slow browsers | SSE continuity is not guaranteed | Unlimited replay or blocking fan-out; rejected because browser fidelity cannot outrank product execution |
| Embedded server-rendered presentation | Single binary, no runtime frontend dependency, complete no-JavaScript path | Rich client interaction remains deliberately limited | Client framework/router/store; rejected because current complexity does not earn another application layer |

## Evidence

- **Report finding:** `studies/go-cli-study/reports/final/01-project-structure.md` identifies thin entrypoints and unidirectional imports as the dominant stable structure, with Helm's `pkg/cmd -> pkg/action` and Restic's inward-defined repository interface as examples. **Sprint inference:** `internal/web -> internal/app` remains the enforceable boundary; reverse imports and direct product imports are architectural failures.
- **Report finding:** `studies/go-cli-study/reports/final/02-command-architecture.md` finds thin delegates reusable while monolithic handlers accumulate untestable orchestration. **Sprint inference:** HTTP handlers should map protocol concerns only, and workflow logic must be extracted before hardening rather than tested indirectly through routes.
- **Report finding:** `studies/go-cli-study/reports/final/03-dependency-injection.md` favors explicit composition roots, constructor injection, narrow service interfaces, and manual wiring, while identifying global state and context service locators as major testability risks. **Sprint inference:** construct web/app dependencies at `cmd/ultraplan`, inject clocks/IDs/logging/fakes, and avoid a global runner or service container.
- **Report finding:** `studies/go-cli-study/reports/final/04-configuration-management.md` supports explicit precedence followed by validation of the merged result and warns against silent configuration failure. **Sprint inference:** server security and resource invariants are validated once before the listener accepts requests.
- **Report finding:** `studies/go-cli-study/reports/final/05-error-handling.md` supports typed/sentinel classification and separate user/operational rendering. **Sprint inference:** app/product errors remain typed and transport-neutral; web maps them to stable safe HTML/JSON/SSE projections without string parsing.
- **Report finding:** `studies/go-cli-study/reports/final/06-io-abstraction.md` shows that injected streams and boundary interfaces enable deterministic testing and that direct output bypasses defeat capture. **Sprint inference:** web/app/runtime diagnostics and external boundaries must be injected or typed so tests can prove redaction and lifecycle behavior without real infrastructure.
- **Report finding:** `studies/go-cli-study/reports/final/07-state-context.md` establishes propagated cancellation as an operational maturity marker and highlights Restic's bounded cleanup context. **Sprint inference:** work cancellation and shutdown reconciliation require related but distinct context ownership; browser subscription contexts cannot own product work.
- **Report finding:** `studies/go-cli-study/reports/final/08-concurrency.md` supports localized launch sites, bounded fan-out, explicit timed waits, and one-time cleanup while warning against fire-and-forget goroutines. **Sprint inference:** the operation hub must make launches auditable, track every goroutine, isolate slow subscribers, and centralize terminal/cancellation arbitration.
- **Report finding:** `studies/go-cli-study/reports/final/10-logging-observability.md` finds structured fields and output/diagnostic separation essential and warns against direct-output bypasses. **Sprint inference:** request/operation correlation belongs in injected diagnostics, while public projections remain allowlisted and redacted.
- **Report finding:** `studies/go-cli-study/reports/final/11-testing-strategy.md` favors layered behavior tests, centralized fakes, integration pipelines, and deliberate golden fixtures over implementation-detail assertions. **Sprint inference:** architecture boundaries need direct tests, while API, lifecycle, packaging, and cross-surface behavior need separate evidence layers.
- **Report finding:** `studies/go-cli-study/reports/final/12-extensibility.md` shows optional capability detection and adapters can support controlled growth, while global registries risk collisions and hidden side effects. **Sprint inference:** a fixed app capability vocabulary is sufficient for the future-stage proof; a plugin/route registry is unnecessary and unsafe here.
- **Report finding:** `studies/go-cli-study/reports/final/13-security.md` ties strong security to explicit trust boundaries, structured validation, safe argument construction, permission control, and layered redaction. **Sprint inference:** `internal/web` owns browser trust checks, but product/process authority stays inward; local-only deployment does not justify implicit trust.
- **Report finding:** `studies/go-cli-study/reports/final/14-performance.md` supports lazy initialization, streaming, bounded queues, and explicit caps while warning against speculative pooling. **Sprint inference:** initialize runtime/harness dependencies lazily, validate cheap security/template invariants eagerly, bound SSE/hub resources, and defer pooling until profiling demonstrates need.
- **Project constraint:** `projects/ultraplan-go/docs/ARCHITECTURE.md` explicitly assigns `internal/web` transport/presentation only, `internal/app` shared use-case composition, and product modules their workflows and durable state. `projects/ultraplan-go/docs/TRD.md` section 18A fixes the ephemeral hub, server-owned shutdown, command/SSE split, mutation-lock ownership, and presentation hierarchy. `projects/ultraplan-go/docs/PRD.md` requires one product core across local surfaces and durable recovery after refresh, reconnect, and shutdown.
- **Sprint requirement:** `projects/ultraplan-go/sprints/32-hardening-and-release/requirements.md` requires `internal/web` to depend only on app/stdlib, future-stage exposure without route-specific workflow logic, exact-once shutdown cancellation, truthful `cleanup_uncertain`, bounded operation/SSE behavior, layered presentation, embedded packaging, and deterministic plus gated verification. These requirements make the boundary refactor mandatory rather than stylistic.

## Risks

- **Boundary leakage:** Existing Sprint 30-31 handlers may already read files, branch on stage names, interpret state, or call concrete product services. Each violation must move to the owning app/product boundary; wrapping it in another web helper would not repair ownership.
- **God-capability risk:** Combining all status, artifact, command, progress, cancellation, and recovery behavior into one broad interface could recreate the coupling being removed. Interfaces must follow consumer cohorts and cohesive lifecycle responsibilities.
- **Duplicate abstraction risk:** CLI, TUI, and web DTOs differ for valid presentation reasons. Only product knowledge and typed app results should be shared; transport DTOs and view models should not be generalized merely because fields look similar.
- **Shutdown deadlock risk:** Hub locks, product locks, terminal persistence, subscriber closure, and process cleanup can form a cycle. Lock ordering, snapshot-before-callback behavior, and no-I/O-under-lock rules require explicit tests.
- **False terminal state risk:** Artifact presence, process absence, HTTP completion, or SSE terminal delivery can be mistaken for durable success. Only the owning product module may establish terminal truth after validation/reconciliation.
- **Cleanup ownership risk:** A detached cleanup context without a hard deadline can outlive the server, while reusing the cancelled work context can release locks before durable uncertainty is recorded. The cleanup context must be bounded and purpose-specific.
- **Subscriber coupling risk:** Blocking fan-out or terminal flush can make browser behavior control product progress. Per-subscriber bounds, eviction, replay gaps, and durable refresh are mandatory.
- **Global-state risk:** Package-global clocks, IDs, registries, loggers, runners, or cancellation maps can leak across tests and concurrent server instances. Construction and ownership must remain explicit.
- **Capability-version risk:** Making capability registration dynamic would create duplicate-name, ordering, and compatibility concerns not needed for one in-process product. Keep production capability assembly explicit and compile-time visible.
- **Security-boundary drift:** Browser checks in middleware can create false confidence if app/product references still accept raw paths or executable input. Both transport and product boundaries need tests for their own authority.
- **Packaging risk:** Templates or assets that parse only from the source tree can pass development tests and fail in the release binary. Build-and-run-outside-tree evidence is required.
- **Verification cost:** Exhaustive race, leak, shutdown, compatibility, accessibility, and integration testing is substantial. It cannot be collapsed into one end-to-end suite because failures would be slow and difficult to localize.
- **Assumption:** Phase 4 remains a single local process with numeric-loopback, same-origin, single-user operation and no detached workers. Hosted access, tenancy, durable queues, or multiple cooperating servers would require new authentication, authority, persistence, idempotency, and coordination architecture.
- **Open verification question:** The exact current locations of any route-specific workflow and shutdown-reconciliation logic must be established during implementation. The decision is final: such logic moves inward; discovery affects task sizing, not architecture direction.
