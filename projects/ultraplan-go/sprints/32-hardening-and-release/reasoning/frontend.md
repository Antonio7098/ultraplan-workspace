# Frontend: Local Web Hardening and Release

Scope: harden the existing server-rendered browser dashboard, project/study/sprint detail pages, artifact and finding views, guarded-operation flow, progress and recovery views, responsive layout, and embedded presentation assets. The frontend remains a same-origin interface inside the single local Go binary, not an independent client application.

Key conclusion: proceed with a server-first presentation refactor and accessibility hardening, not a frontend rewrite. Every route must render a complete, operable page from an explicit typed view model; namespaced templates and layered CSS provide the reusable presentation system; dependency-free JavaScript may enhance guarded operations and SSE observation but cannot own navigation, workflow state, terminal truth, or recovery.

## Area Decisions

### Ownership and composition

- Keep browser presentation in `internal/web`: handlers map typed `internal/app` results into page-specific view models, pages select layouts, layouts compose components, and components compose primitives. Enforce the single downward dependency order `page -> layout -> component -> primitive`; templates never read files, call app use cases, validate HTTP requests, mutate durable state, or interpret workflow status.
- Parse one embedded template set at server startup and require stable namespaced definitions such as `page/sprint`, `layout/detail`, `component/operation-status`, and `primitive/button`. Missing, duplicate, or invalid definitions fail startup rather than becoming load-order-dependent behavior. Route handlers invoke only page names, and lower layers receive narrow presentation data rather than whole app/domain values.
- Introduce presentation abstractions only where reuse is demonstrated. Primitives cover controls and content atoms; components cover repeated navigation, status, findings, progress, artifacts, confirmation, empty, and error compositions; layouts cover shared shells and arrangements; route-specific composition remains in pages. Reject a generic component registry, template-driven state machine, or broad map-based view model.
- Keep CSS in the required order: `tokens.css`, `base.css`, `primitives.css`, `components.css`, `layouts.css`, and narrowly scoped `utilities.css`. Tokens define color, type, spacing, borders, focus, and motion; utilities may express presentation only and must not encode product states such as success, failure, readiness, or cancellation.
- Keep JavaScript dependency-free and capability-focused in `app.js`, `operations.js`, and `sse.js`. There is no package manager, bundler, client router, service worker, virtual DOM, persistent store, or frontend framework. Templates, CSS, and JavaScript are embedded in the Go binary and must resolve when the binary runs outside the source tree.

### Page and workflow behavior

- Render dashboard, detail, finding, artifact, confirmation, progress, terminal, recovery, empty, and error states as complete HTML before JavaScript runs. Links and ordinary forms provide the baseline navigation and read behavior. Runtime-backed or mutating work remains guarded by a server-prepared confirmation page that displays safe operation scope, mutation class, affected references, and runtime/model metadata before start.
- Use ordinary HTTP requests for preparation, start, cancellation, and durable refresh. SSE is observation only. Enhanced operation flow is: prepare through HTTP, render and focus confirmation, start through HTTP, attach SSE with the returned operation ID, project bounded progress, allow explicit cancellation, then refresh the operation and durable page state after terminal events, gaps, expiry, reconnect failure, or page restoration.
- Treat browser-local state as disposable. Permitted local state is limited to enhancement mechanics such as the active request, current operation ID for the rendered page, last received event ID, connection indicator, pending/disabled controls, and focus-return target. Workspace artifacts and product-owned state are server state; URL path/query is navigation state; no global or persistent client state is introduced.
- A refresh, navigation, tab close, page restoration, SSE loss, slow-subscriber eviction, or stream lifetime expiry ends only the browser subscription. It never cancels or determines product work. On reconnect, replay retained events when possible; on an explicit replay gap or expired operation, show a non-terminal notice and refresh durable state. Never infer success from a terminal-looking progress message, process absence, or artifact presence.
- Display loading and pending state without erasing the last truthful server-rendered state. Empty states explain what is absent and provide a valid next action. Typed errors render a safe summary, actionable recovery or retry path, and correlation identifier when available, while raw causes remain in redacted diagnostics. Success, failure, cancellation, blocked, stale, draining, and `cleanup_uncertain` are separate text-labelled states and are never distinguished by color or icon alone.
- Apply `no-store` behavior to state-bearing pages and operation responses. Static assets use revalidation unless URLs are proven content-addressed. Any fallback polling is visibility-aware, has a documented minimum interval and lifetime, stops at terminal/unmounted state, and only requests server truth; it cannot become an independent scheduler.

### Accessibility and responsive behavior

- Use semantic landmarks (`header`, `nav`, `main`, and contextual `aside`/`footer`), one descriptive page heading, real links for navigation, real buttons for actions, explicit form labels, associated help and error text, table captions/headers where tabular relationships matter, and lists for findings or events where tables do not add semantics.
- Preserve a complete keyboard path through navigation, artifact inspection, confirmation, cancellation, retry, and recovery. Source order follows visual order. There are no positive `tabindex` values or pointer-only controls. Focus is always visible with a tokenized high-contrast outline that is not removed by component styles.
- On validation failure, focus the error summary and link each summary item to its field. On confirmation display, focus the confirmation heading without trapping focus. After enhanced start, move focus to the operation status heading; after cancellation or terminal refresh, place focus on the resulting status heading; after an inline retry failure, return focus to the actionable error. Destructive or guarded action buttons keep stable accessible names while pending.
- Use restrained live regions: connection/progress summaries use a single `aria-live="polite"` status region with coalesced updates; immediate start/cancel failures use an alert; verbose event logs are not live. Terminal state is announced once. Reconnect attempts and heartbeats do not flood assistive technology.
- Pair every state color with visible text and, where useful, a non-color cue. Meet contrast requirements for text, controls, focus, and state indicators. Respect `prefers-reduced-motion`; no essential information depends on animation, and progress changes avoid continuous motion. Native controls and semantic HTML are preferred over custom ARIA widgets.
- Use mobile-first layouts that reflow without horizontal page scrolling at narrow widths and remain usable at 200% zoom and text enlargement. Navigation wraps or collapses through semantic disclosure, metadata and action groups stack, long paths/code wrap or scroll within labelled regions, tables receive a deliberate narrow presentation, and touch targets remain adequately sized. No viewport-width assumption may hide a recovery or cancellation action.

### Security and safe rendering

- Render all untrusted values through `html/template` escaping. Markdown is converted by the approved safe renderer with embedded HTML and script execution disabled, then projected through an allowlisted representation. Artifact previews are bounded and reference-based; templates and JavaScript never receive raw filesystem paths or executable command strings.
- Apply the same final allowlist/redaction policy to HTML attributes, text, data attributes, client-visible JSON, retained events, and terminal results. Tokens, cookies, CSRF/session values, prompts, raw provider payloads, stderr, unsafe paths, secrets, and internal command arguments must never be inserted into the DOM or browser console.
- Keep strict same-origin behavior. Mutation enhancement sends the server-issued CSRF value through the documented mechanism and does not persist it. No third-party script, remote font, inline executable data, permissive CORS, unsafe HTML escape hatch, or CSP exception is introduced.
- Keep diagnostic output separate from user presentation. The browser receives safe error classifications and recovery guidance, while structured server diagnostics carry request/operation correlation fields. JavaScript must not log response bodies, confirmations, event payloads, or security values to the console.

### Verification expectations

- `templates_test.go` must parse the embedded tree, reject missing/duplicate definitions, verify downward-only namespaced composition, render every representative page from typed view models, prove complete no-JavaScript content and actions, and assert escaping of hostile text, Markdown, URLs, paths, and attributes.
- Accessibility tests must assert landmarks, heading order, labels, descriptions, error associations, button/link semantics, status/alert regions, non-color state labels, and stable focus targets. Manual release evidence must cover keyboard-only operation, focus order/visibility, screen-reader announcements, 200% zoom, text enlargement, narrow reflow, color independence, and reduced motion because those properties are not fully established by static HTML assertions.
- JavaScript tests or browser integration fixtures must cover prepare/confirm/start, duplicate submission suppression, pending control behavior, explicit cancellation, SSE ordering/replay/gaps, reconnect bounds, terminal refresh, operation expiry, disconnect isolation, stale confirmation, typed error projection, and no-JavaScript fallback. Fake clocks, IDs, barriers, app capabilities, runtimes, and harnesses keep normal tests deterministic.
- CSS/render review must exercise long project/sprint names, long paths and code, empty and dense finding sets, large progress histories, all terminal states, narrow viewports, zoom, high contrast, and reduced motion. Static assertions alone are insufficient for reflow and focus visibility.
- Packaging verification must build the binary, run it outside the source checkout, request every page and static asset, and prove there is no Node.js, source-tree asset, network CDN, or separate frontend-process dependency. Representative study and sprint browser integration tests must compare the rendered state and next actions with shared app, CLI, and TUI projections.

Decision: proceed with the server-first layered frontend hardening described above. The main trade-off is accepting full-page durable refreshes and bounded, occasionally lossy enhancement in exchange for one authoritative product state, complete no-JavaScript operation, a small attack surface, and single-binary distribution.

## Trade-Offs

| Decision | Benefit | Cost | Rejected Alternative |
| --- | --- | --- | --- |
| Complete server-rendered pages with narrow enhancement | Pages remain operable, testable, recoverable, and truthful without JavaScript | Some interactions use navigation or full refresh instead of instant client transitions | Client-rendered SPA; rejected because it adds a second application/state layer and runtime toolchain without an earned need |
| Strict namespaced `page -> layout -> component -> primitive` composition | Prevents collisions, cycles, and workflow interpretation in lower template layers | More explicit template names and view-model mapping | Flat template collection or dynamic registry; rejected because load order and dependencies would be implicit |
| Explicit typed view models | Keeps templates presentation-only and makes escaping/state cases reviewable | Handlers need route-specific mapping structs | Passing domain objects or `map[string]any`; rejected because both expose internals and move interpretation into templates |
| Layered CSS with semantic state classes | Produces consistent responsive/accessibility behavior without a build system | Requires discipline to avoid utility and specificity drift | Utility-only CSS or component framework; rejected because product-state semantics and build/runtime complexity would leak into presentation |
| Disposable browser state and durable refresh | Maintains one source of truth across browser, CLI, and TUI and recovers after restart | Progress continuity can be lost after retention gaps or operation expiry | Persistent client store, IndexedDB, or web-owned database; rejected as an alternate authority |
| Bounded SSE with polling fallback | Gives responsive progress while isolating product work from slow or disconnected browsers | Gaps require a visible refresh and progress history is not lossless | WebSockets or unlimited replay; rejected because bidirectional transport is unnecessary and unlimited retention is unsafe |
| Restrained live announcements | Keeps progress understandable to assistive technology without flooding it | Not every event is announced in real time | Mark the event stream itself live; rejected because frequent tool/progress events would make the interface unusable |
| Semantic HTML over custom widgets | Provides keyboard and assistive behavior with less code | Visual customization remains constrained by native semantics | Div-based controls and bespoke ARIA widgets; rejected because they increase interaction and test risk without product value |
| Embedded local assets only | Preserves one binary, offline operation, CSP simplicity, and release reproducibility | No CDN packages or frontend ecosystem conveniences | Remote dependencies or a bundled framework pipeline; rejected because they expand supply-chain and runtime complexity |
| Golden render fixtures plus semantic assertions and manual review | Detects exact presentation regressions while checking behavior that snapshots miss | Fixture updates and manual accessibility evidence require deliberate review | Snapshot-only or automation-only verification; rejected because either can bless inaccessible behavior or miss visual/focus defects |

Accepted technical debt is intentionally narrow: progressive enhancement uses imperative DOM code rather than a component runtime, some durable transitions cause full-page refreshes, and manual accessibility review remains part of release evidence. These costs are preferable to introducing a client application layer before measured interaction complexity justifies it. A future framework decision would require evidence that the current scripts cannot safely express required interactions; it must not be introduced merely to reduce template verbosity.

## Evidence

- **Report finding:** `studies/go-cli-study/reports/final/05-error-handling.md` finds that typed error classification and separate user/operational rendering produce actionable interfaces without exposing internal causes, citing Restic's fatal classification and gh-cli's outer guidance renderer. **Frontend inference:** page and inline error components consume a safe typed projection with recovery guidance; templates and JavaScript never parse error strings or expose raw causes.
- **Report finding:** `studies/go-cli-study/reports/final/06-io-abstraction.md` shows that injectable boundaries and `httptest` permit deterministic interface testing, while direct output and template-function bypasses escape capture. **Frontend inference:** handlers and renderers need injectable app dependencies and response capture, and templates must have no direct filesystem, app, logging, or process side effects.
- **Report finding:** `studies/go-cli-study/reports/final/07-state-context.md` establishes propagated cancellation for long work and warns against detached contexts, while Restic's `delayedCancelContext` distinguishes bounded cleanup. **Frontend inference:** request/SSE context may own only the HTTP exchange or subscription; tab loss cannot own product cancellation, and explicit cancel/recovery must return to server-owned operation state.
- **Report finding:** `studies/go-cli-study/reports/final/08-concurrency.md` favors localized goroutine ownership, explicit waits and timeouts, bounded fan-out, and one-time cleanup, and identifies fire-and-forget and unbounded waits as failures. **Frontend inference:** enhancement reconnect and polling loops need one visible owner, hard bounds, and cleanup on navigation/terminal state; slow subscribers and missed terminal delivery cannot block product work.
- **Report finding:** `studies/go-cli-study/reports/final/10-logging-observability.md` identifies structured fields and strict user-output/diagnostic separation as the clearest operational pattern and warns that direct output bypasses defeat control. **Frontend inference:** users receive concise safe status and correlation values, while detailed redacted diagnostics remain server-side; console logging of payloads is prohibited.
- **Report finding:** `studies/go-cli-study/reports/final/11-testing-strategy.md` supports layered behavior tests, centralized fakes, command/integration pipelines, and deliberate golden fixtures, while warning against brittle UI-internal assertions such as K9s hint counts. **Frontend inference:** test rendered semantics and user journeys, not template call counts or CSS implementation details; combine fixtures, semantic assertions, browser interactions, and manual accessibility evidence.
- **Report finding:** `studies/go-cli-study/reports/final/13-security.md` finds that explicit trust boundaries, structured validation, type-level redaction, credential scrubbing, and guarded permission flows outperform implicit local trust. **Frontend inference:** loopback content remains untrusted; HTML/Markdown/data attributes require escaping and allowlisting, guarded operations require server-bound confirmation, and sensitive values never reach DOM, events, logs, or console.
- **Report finding:** `studies/go-cli-study/reports/final/14-performance.md` favors streaming, bounded structures, and explicit resource caps, notes pragmatic slow-consumer event loss, and cautions against speculative pooling. **Frontend inference:** SSE and previews remain bounded, gaps trigger durable refresh, polling is capped, and no client cache/pool/framework optimization is added without measurement.
- **Handbook synthesis:** `projects/ultraplan-go/sprints/32-hardening-and-release/technical-handbook.md` identifies no-JavaScript completeness, progressive enhancement, explicit replay gaps, bounded resources, fail-closed template startup, and durable server/product truth as the frontend design pressures. This document resolves them through complete HTML, typed view models, startup validation, bounded enhancement, and refresh-based recovery.
- **Project contract:** `projects/ultraplan-go/docs/ARCHITECTURE.md` assigns HTML, templates, static assets, JSON/SSE mapping, and browser security to `internal/web`, fixes namespaced downward composition, and prohibits product workflow ownership. `projects/ultraplan-go/docs/TRD.md` sections 7.5 and 18A require embedded Go presentation, no-JavaScript completeness, guarded commands, SSE observation, responsive accessibility, and same-origin security. `projects/ultraplan-go/docs/PRD.md` requires one product core across browser, CLI, and TUI.
- **Sprint requirement:** `projects/ultraplan-go/sprints/32-hardening-and-release/requirements.md` acceptance criteria require typed view models, layered templates/CSS/JavaScript, keyboard/focus/label/live-region/color/reduced-motion/zoom/narrow-layout coverage, hostile content and redaction tests, disconnect isolation, embedded packaging, and representative browser integration. These are binding release decisions rather than optional frontend polish.

## Risks

- **Existing-markup migration risk:** splitting Sprint 30-31 templates into namespaced layers can accidentally change forms, routes, field names, or no-JavaScript behavior. Preserve behavior first, add semantic assertions before extraction, and review fixture changes rather than regenerating them wholesale.
- **Template-boundary drift:** convenience functions or broad view models could reintroduce app calls, filesystem reads, status interpretation, or unsafe HTML. Keep the template function map presentation-only, use narrow typed fields, and fail startup on an invalid embedded tree.
- **Accessibility false confidence:** static checks cannot prove visual focus, useful announcement timing, zoom, reflow, color independence, or keyboard ergonomics. Manual evidence for representative pages is a release requirement, not an optional follow-up.
- **Live-region overload:** mapping each SSE event to an announcement would obscure terminal state. Coalesce progress, announce connection changes only when actionable, and announce one terminal summary.
- **Focus race:** asynchronous replacement can move or lose focus when cancellation, terminal events, reconnect, and user navigation overlap. Use stable focus targets, abort stale DOM updates, and test race ordering with deterministic events.
- **Stale-state ambiguity:** an SSE gap or expired operation can leave a convincing but outdated progress panel. Display a clear non-terminal stale/gap state and require durable HTTP refresh before showing completion, failure, cancellation, or recovery advice.
- **Double-submit risk:** network delay and reconnection can cause repeated start actions. Disable only the submitted control while pending, preserve an accessible pending label, and rely on server confirmation deduplication rather than client state for correctness.
- **Security regression risk:** safe server data can become unsafe when inserted into `innerHTML`, URLs, CSS selectors, data attributes, or console output. Prefer text/DOM APIs, allowlist URL/reference shapes, avoid inline script data, and test hostile payloads at every projection.
- **Responsive overflow risk:** long workspace references, code, tables, and diagnostics can force page-wide horizontal scrolling or hide actions. Include pathological-length fixtures and verify narrow layouts and 200% zoom before release.
- **CSS architecture debt:** utilities or high-specificity selectors may bypass component states and focus tokens. Keep utilities presentation-only, constrain selector depth, and include all semantic state/focus combinations in render review.
- **Polling/reconnect leak risk:** overlapping timers or event sources can continue after navigation or terminal state. Give each enhancement one abort owner, enforce retry/lifetime limits, and verify cleanup and no duplicate requests.
- **Packaging risk:** development can mask a missing embedded asset through source-relative paths or browser cache. Run packaging checks from outside the checkout with an empty cache and request every referenced asset.
- **Assumption:** Sprint 32 remains numeric-loopback-only, same-origin, single-process, and single-user, with server-rendered routes and existing documented `/api/v1` behavior. Hosted access, remote users, client-side routing, offline mutation, or durable workers would invalidate these frontend authority and security decisions.
- **Open verification question:** the current pages and assets must be inventoried during implementation to determine which static URLs are content-addressed and which existing forms already provide complete no-JavaScript operation. Until proven otherwise, static assets use revalidation and every enhanced action requires a server-rendered fallback.
