# API Design: Local Web Hardening

Scope: stabilize the existing same-origin, loopback-only `/api/v1` HTTP and SSE surface for dashboard state, artifact previews, validation, guarded operations, cancellation, and recovery. This is an internal browser-facing API in the single local `ultraplan` process, not a public, partner, hosted, tenant-aware, or SDK API.

Key conclusion: proceed with compatibility hardening, not route redesign. Preserve every documented Sprint 30-31 method, route, success field, error field, status mapping, and stable error code; make the operation protocol retry-safe and bounded; and keep workspace artifacts and product-owned run state authoritative whenever ephemeral operation data and durable state differ.

## Area Decisions

### Contract and ownership

- Keep the API under `/api/v1` with the route capabilities already selected by the sprint: `GET /api/v1/dashboard`, `GET /api/v1/artifacts/{ref}`, `POST /api/v1/validations`, `POST /api/v1/operations/prepare`, `POST /api/v1/operations`, `GET /api/v1/operations/{id}`, `GET /api/v1/operations/{id}/events`, and `DELETE /api/v1/operations/{id}`. Existing documented detail routes remain valid and are included in compatibility fixtures.
- Treat methods, success envelopes, error envelopes, field names, nullability, status mappings, and machine-readable error codes already documented through Sprint 31 as frozen. Sprint 32 may add a field only when it is optional, has an explicit compatibility test, and does not alter existing field meaning. Renaming, removing, changing type, changing nullability, or reinterpreting an existing field is breaking and is rejected for this sprint.
- Keep request/response DTOs in `internal/web`. Handlers decode and validate transport input, call a typed `internal/app` capability, and map the typed result. They must not call CLI handlers, parse CLI text, import product/runtime/process packages, or infer workflow state from strings, files, subscriber state, process absence, or artifact presence.
- Use a shared capability vocabulary for status, artifacts, available commands, preparation, execution, progress, cancellation, terminal result, and recovery. A new stage supplies those capabilities through `internal/app`; it does not receive a stage-specific HTTP route or handler branch. This satisfies the sprint's extensibility proof without creating a plugin API or generic workflow engine.

### Request contract

- Accept JSON only on JSON command endpoints, reject malformed or duplicate-significant input, reject unknown operation kinds and caller-supplied internal fields, and apply the configured body limit before decoding. All operation references, artifact references, project/sprint/study references, and paths are normalized and resolved through allowlisted app capabilities; raw caller paths and executable command strings are never accepted.
- Validate the fully merged server configuration once before serving. Numeric loopback bind, body size, active-operation count, preparation count and lifetime, event and result payload size, retained-event count and lifetime, per-operation subscriber count, total stream count, heartbeat interval, stream lifetime, polling floor, and cleanup timeout must all be positive, mutually coherent, documented, and fail startup when invalid. Configuration precedence remains built-in defaults, workspace config, environment, then explicit command flags.
- `POST /api/v1/operations/prepare` receives a normalized operation request and returns a short-lived, server-issued confirmation bound to the normalized request, operation scope, mutation class, current governed-input fingerprint, and browser session. A stale, expired, mismatched, replayed-for-another-request, or cross-session confirmation is rejected.
- `POST /api/v1/operations` consumes a valid confirmation and starts through the shared app operation capability. Confirmation consumption and operation creation are one logical critical section. The server retains the resulting operation ID with the consumed confirmation for the bounded operation-retention window so a duplicate submission returns the same accepted operation rather than starting duplicate work.
- `DELETE /api/v1/operations/{id}` requests canonical cancellation and is idempotent. Repeated requests return the current operation projection while exact-once cancellation arbitration ensures only one cancellation reaches product work. A terminal operation is never rewritten as cancelled merely because a late cancellation arrived.
- `GET /api/v1/operations/{id}/events` accepts the standard `Last-Event-ID` replay cursor only. Query parameters cannot mutate work. Browser disconnect, stream expiry, and slow-client eviction cancel only the subscription.

### Response and error contract

- Preserve the existing documented success and typed error envelope shapes exactly; do not expose internal domain structs directly. Compatibility fixtures, rather than internal Go type layout, are the release authority for wire shape.
- Every error response contains the existing stable machine-readable code and safe user-facing message fields. Existing recovery or next-action fields retain their documented meaning. Internal causes, error chains, stack traces, raw stderr, provider payloads, prompts, cookies, CSRF values, tokens, unsafe paths, and executable arguments are excluded.
- Map typed errors with `errors.Is`/`errors.As`, never display-string matching. The fixed mapping must distinguish at least malformed input, failed validation, forbidden Host/Origin/CSRF/session, not found, unsupported method, stale or invalid confirmation, mutation conflict, draining server, request too large, resource limit, cancellation, unavailable dependency, and internal failure. Unknown `/api/` paths and unsupported methods always use the JSON error envelope and never fall through to HTML.
- Preserve the current documented HTTP status for each stable code. New mappings, if needed for the Sprint 31 shutdown gap, follow HTTP semantics: client syntax/validation errors are `4xx`; stale confirmation or mutation conflict is `409`; body overflow is `413`; configured capacity exhaustion is `429` or the already documented equivalent; draining/unavailable service is `503`; accepted asynchronous start or cancellation remains the already documented accepted status. A fixture change requires an explicit compatibility decision, never a mechanical golden update.
- Operation status is an ephemeral transport projection. It may include safe progress and a retained terminal result while present, but durable workflow status, artifacts, verdicts, and next actions come from app capabilities backed by product-owned state. After operation expiry or server restart, clients refresh dashboard/detail state instead of treating `404` on an old operation ID as product failure.

### SSE protocol and recovery

- SSE is one-way observation. Each progress record has a monotonically increasing per-operation event ID, a stable safe event type, and a compatibility-controlled JSON data envelope. Heartbeats are transport comments and carry no product state.
- Retain a configured bounded replay window. A reconnect with an available `Last-Event-ID` receives later retained events in order without duplication. If the cursor predates retention or event loss occurred, emit the stable replay-gap signal, then require a normal HTTP refresh of operation and durable state; a gap is not operation failure.
- Slow subscribers never apply backpressure to product execution. When a subscriber cannot keep pace within its bounded queue/write deadline, close that subscription. Reconnect either replays retained events or reports a gap.
- Publish one terminal event only after terminal arbitration and safe result projection. Attempt bounded delivery to current subscribers, but do not block terminal persistence, cleanup, or shutdown on a browser. The HTTP operation projection while retained and the product-owned durable state after refresh are authoritative if terminal SSE delivery is missed.
- Server shutdown first enters draining and rejects new preparation/start mutations, then requests canonical cancellation exactly once for each server-owned active operation. Cleanup and durable reconciliation use a separate bounded cleanup context. HTTP/SSE closes only after a durable terminal outcome or truthful `cleanup_uncertain` equivalent has been recorded.

### Security and authority

- There is no hosted user authentication or role authorization in Phase 4. Access is gated by numeric-loopback binding, strict Host validation, exact same-origin checks, a per-process browser session, and CSRF protection for mutation requests. This session is a browser-security boundary, not an account or durable identity.
- Authorization is capability and object based: a request may operate only on objects resolved by typed app capabilities within the active workspace and only through an advertised command. Artifact references are opaque or allowlisted references, not filesystem paths. Forged references, escaped paths, unsupported operation kinds, and caller-selected executable/runtime internals are rejected.
- Apply CSP and documented security headers to pages and API responses, no permissive CORS, strict content types, safe cookie attributes appropriate to the actual loopback HTTP mode, and final projection-level redaction across JSON and SSE in addition to type-level redaction inside the app/runtime boundary.
- Confirmation tokens and session secrets are never logged, returned in diagnostics, copied into SSE, or retained in terminal results. Comparisons use constant-time operations where the value functions as a bearer secret.

### Idempotency, cache, and compatibility behavior

- `GET` routes are naturally retryable. Validation is read-only but bounded and may be retried only after the previous request has completed. Preparation may return a fresh confirmation and must not mutate product state. Start is retry-safe through confirmation-to-operation deduplication. Cancellation is idempotent. SSE reconnect is safe through event IDs and gap handling.
- API state, operation status, confirmation responses, errors, and SSE use `Cache-Control: no-store`. Server-rendered pages containing local state also use `no-store`. Embedded static assets use revalidation unless their URL is content-addressed; only content-addressed assets may receive immutable long-lived caching. This prevents stale browser state from becoming an apparent source of truth.
- Freeze a route matrix fixture for every documented path and method, including wrong methods, unknown `/api/` paths, content types, status codes, cache headers, success fields, error fields, stable codes, optionality, and representative null/empty cases. Existing fixtures are reviewed as contracts, not regenerated wholesale.

### Observability and testing

- Emit structured diagnostics for request ID, operation ID, safe operation kind, route template, method, status, duration, error code, event sequence, replay/gap outcome, cancellation reason, and cleanup outcome. Correlation identifiers are propagated through app operations. Never log raw request bodies or forbidden sensitive fields.
- Test the contract in layers: table-driven route/method/schema tests; golden compatibility fixtures; Host/Origin/CSRF/session/body/path/redaction tests; deterministic operation/SSE tests with fake clocks, IDs, and barriers; race/leak/slow-subscriber/shutdown tests; `httptest` integration over temporary workspaces and fake runtime/harness dependencies; and cross-surface agreement checks against typed app, CLI, and TUI projections.
- Compatibility tests must fail on accidental field addition as well as omission, type, nullability, method, status, code, content-type, and cache-policy changes. Golden updates require a reviewed contract rationale. Gated real-runtime and real-harness browser checks supplement but never replace deterministic API tests; missing prerequisites are blocked, not passed.

Decision: proceed with compatibility-preserving hardening of the existing API. The main trade-off is accepting explicit bounds, replay gaps, and durable refresh instead of promising lossless streams or durable web-owned operations.

## Trade-Offs

| Decision | Benefit | Cost | Rejected Alternative |
| --- | --- | --- | --- |
| Preserve the existing `/api/v1` wire shape | Avoids breaking the Sprint 30-31 browser and documentation while making release changes reviewable | Existing awkward fields or routes remain until a separately versioned change | Redesign envelopes or rename routes during hardening; rejected because this sprint explicitly requires compatibility control |
| Thin HTTP mapping over shared app capabilities | Keeps CLI, TUI, HTML, JSON, and SSE semantically aligned and lets future stages appear without route orchestration | Requires disciplined typed mapping and capability tests | Route-specific stage handlers or invoking CLI commands; rejected because they duplicate workflow ownership |
| One-time confirmation with retained deduplication | Prevents double starts when browsers retry after a lost response | Requires bounded confirmation-to-operation retention and careful locking | Treat `POST /operations` as non-retryable; rejected because network ambiguity would expose duplicate mutation risk |
| Typed fixed error vocabulary | Stable automation and consistent HTML/JSON/SSE projection | Each new public code becomes a compatibility obligation | Expose raw errors or parse strings; rejected because causes are unsafe and strings are unstable |
| Bounded SSE replay with explicit gaps | Bounds memory and isolates slow clients while preserving reconnect behavior | Clients sometimes need a full durable refresh | Unlimited replay or blocking subscribers; rejected because either creates unbounded memory or lets browsers block product work |
| Separate work and cleanup contexts | Prompt cancellation plus a bounded chance to persist truthful reconciliation | More lifecycle states, including cleanup uncertainty | Reuse the cancelled work context for cleanup or detach cleanup without a bound; rejected because one prevents reconciliation and the other can outlive ownership |
| `no-store` for state-bearing responses | Prevents stale local workflow and security-sensitive data from being reused by browser caches | More local requests and less browser caching | Cache API/status responses for responsiveness; rejected because cached state must not masquerade as durable truth |
| Golden fixtures plus semantic assertions | Detects exact wire regressions while retaining behavioral intent | Fixtures require deliberate review and can be noisy | Snapshot-only testing or loose substring assertions; rejected because one encourages blind updates and the other misses shape regressions |
| Fixed resource limits validated at startup | Makes overload behavior deterministic and testable | Misconfigured limits fail startup and conservative defaults may reject bursts | Silent fallback, unbounded queues, or runtime correction; rejected because security and shutdown behavior must fail closed |

## Evidence

- **Report finding:** `studies/go-cli-study/reports/final/02-command-architecture.md` finds that high-scoring tools keep transport/command wrappers thin and delegate to reusable actions, especially its "Thin-Delegate Pattern" and Helm evidence at `helm/pkg/cmd/install.go:132-145`. **Sprint inference:** HTTP routes should perform protocol mapping only and use the same app capabilities as CLI/TUI.
- **Report finding:** `studies/go-cli-study/reports/final/04-configuration-management.md` finds that precedence must be explicit and merged configuration validated once, with centralized validation evidence at `k9s/internal/config/k9s.go:423-451`. **Sprint inference:** API and SSE safety limits are startup invariants; invalid combinations cannot silently fall back while serving.
- **Report finding:** `studies/go-cli-study/reports/final/05-error-handling.md` documents typed/sentinel classification, preserved error chains, and separate outer rendering, including Helm's storage errors and gh-cli's user renderer. **Sprint inference:** stable API codes and statuses derive from typed app errors, while JSON/SSE receive a safe projection rather than raw internal causes.
- **Report finding:** `studies/go-cli-study/reports/final/07-state-context.md` shows one propagated cancellation lineage for work and identifies Restic's deliberately delayed cleanup context at `restic/internal/restic/lock.go:290-305`. **Sprint inference:** browser cancellation, server shutdown, and bounded durable reconciliation need explicit distinct ownership; subscriber disconnect cannot own the operation context.
- **Report finding:** `studies/go-cli-study/reports/final/08-concurrency.md` favors localized launch sites, bounded coordination, timed waits, and `sync.Once` cleanup, and warns against fire-and-forget goroutines and unbounded `WaitGroup.Wait`. **Sprint inference:** operation start/cancel/terminal arbitration must be exact-once, all stream/subscriber paths bounded, and shutdown waits timed without holding hub locks.
- **Report finding:** `studies/go-cli-study/reports/final/10-logging-observability.md` finds structured fields and strict product-output/diagnostic separation most operable, while direct output bypasses defeat capture. **Sprint inference:** request and operation correlation fields are useful, but wire output and diagnostics need separate safe projections with no raw body/payload logging.
- **Report finding:** `studies/go-cli-study/reports/final/11-testing-strategy.md` supports layered acceptance tests, centralized fakes, and golden output checks while warning against brittle internal assertions and loose regexes. **Sprint inference:** exact API fixtures, semantic lifecycle tests, fake dependency integration, and gated real checks are complementary release gates.
- **Report finding:** `studies/go-cli-study/reports/final/12-extensibility.md` shows optional-interface capability detection at `rclone/fs/features.go:294-370` and adapters as stable boundaries, while warning that registries may silently overwrite names. **Sprint inference:** expose future stages through a fixed app capability vocabulary and fail on duplicate capability/route registration; do not add a generic route registry or plugin protocol.
- **Report finding:** `studies/go-cli-study/reports/final/13-security.md` supports explicit trust boundaries, structured validation, type-level redaction, safe argument construction, and confirmation flows; Restic's `SecretString` and Helm's credential scrubbing show defense at more than one layer. **Sprint inference:** loopback does not remove browser, path, bearer-token, hostile-content, or diagnostic leakage threats, so validation and redaction must be repeated at the HTTP/SSE projection boundary.
- **Report finding:** `studies/go-cli-study/reports/final/14-performance.md` favors streaming, bounded queues, explicit caps, and profiling before pooling; it notes pragmatic slow-consumer drops in event streaming. **Sprint inference:** bounded event retention and explicit replay gaps are preferable to lossless unbounded SSE, and speculative pooling is unnecessary until profiles justify it.
- **Project constraint:** `projects/ultraplan-go/docs/TRD.md` section 18A fixes the initial route capabilities, command/SSE separation, ephemeral hub, shutdown ownership, and durable recovery model. `projects/ultraplan-go/docs/ARCHITECTURE.md` assigns JSON/SSE mapping to `internal/web` and product rules to app/product modules. `projects/ultraplan-go/docs/PRD.md` requires confirmation, explicit cancellation, refresh/reconnect recovery, and cross-surface state agreement.
- **Sprint requirement:** `projects/ultraplan-go/sprints/32-hardening-and-release/requirements.md` requires exhaustive compatibility fixtures, structured unknown-route/method errors, documented cache policies, security/redaction regression coverage, bounded operations/SSE, disconnect isolation, truthful shutdown uncertainty, and shared-capability extensibility. These are binding decisions here rather than optional report recommendations.

## Risks

- **Baseline inventory risk:** The governed inputs state that existing documented Sprint 30-31 fields and mappings must be preserved but do not enumerate every field. Implementation must inventory the current documentation and compatibility surface before changing DTOs. Any unexplained mismatch between implementation, docs, and fixtures is a release blocker; this document does not authorize guessing a replacement schema.
- **Confirmation race:** Concurrent duplicate starts, expiry, input-fingerprint changes, and shutdown can race. Confirmation consumption, deduplication record creation, capacity reservation, and operation publication need one explicit ordering and deterministic race tests.
- **Terminal race:** Completion, app failure, user cancellation, timeout, and server shutdown may arrive together. A single terminal arbiter must preserve an already-authoritative result and invoke canonical cancellation exactly once.
- **Lock-order risk:** Hub state, product mutation locks, subscriber queues, and durable reconciliation can deadlock if code waits or performs I/O under hub locks. The implementation must document lock order and copy work out of locks before cancellation, writes, or waits.
- **Replay ambiguity:** A generic disconnect without a stable gap signal can leave the browser showing stale progress. The event schema and client behavior must distinguish clean replay, gap, operation expiry, and durable recovery without interpreting any as success or failure by itself.
- **Compatibility-fixture complacency:** Golden files can be blindly regenerated. Review must require a per-change rationale and semantic assertions for statuses, idempotency, redaction, recovery, and cache behavior.
- **Error-code proliferation:** Exposing every internal error category would freeze implementation details. Only caller-actionable stable classes belong in the wire vocabulary; unknown internal causes map to the existing generic internal code and remain available only in redacted diagnostics.
- **Local-boundary overconfidence:** DNS rebinding, forged Host/Origin, CSRF, hostile Markdown, path traversal, leaked confirmation/session values, and browser cache reuse remain credible on loopback. Security tests must cover both IPv4 and IPv6 loopback and fail closed on ambiguous headers.
- **Resource-limit tuning:** Limits that are too high undermine memory and shutdown guarantees; limits that are too low impair substantial workflows. Defaults and configuration documentation must be tested against the representative study and sprint operations, with capacity rejection remaining explicit and safe.
- **Open verification question:** Whether every current static asset URL is content-addressed must be established before assigning immutable caching. Until proven, revalidation is the final safe policy.
- **Assumption:** The API remains same-process, same-origin, single-user, and loopback-only for Sprint 32. Any hosted, LAN, remote, account, role, tenant, durable-worker, or multi-server requirement invalidates the session, authorization, idempotency-retention, and recovery decisions and requires a new versioned design.
