## Relevant Patterns

- **Shared capability behind thin surfaces:** The structure and command reports consistently place business capability behind CLI/UI adapters, with imports flowing inward only. gdu exposes interchangeable TUI/stdout/report implementations through one UI interface (`gdu/cmd/gdu/app/app.go:30-49`), while helm commands delegate to action objects (`helm/pkg/cmd/install.go:132-145`). For this sprint, the pattern pressures run acceptance, inspection, replay, and cancellation toward a shared capability that CLI, TUI, and web adapters can invoke without any one surface becoming the authority.
- **Explicit composition root and narrow injected services:** Gh-cli constructs lazy dependencies through a factory (`gh-cli/pkg/cmdutil/factory.go:16-43`; `gh-cli/pkg/cmd/factory/default.go:26-46`), and opencode assembles services in `app.New` (`opencode/internal/app/app.go:42-81`). This pattern makes repository, clock, process identity, event sink, cancellation coordinator, and diagnostics dependencies visible and replaceable, while warning against a single mega-config or hidden singleton.
- **Lifecycle context plus durable identity:** Signal-to-context wiring appears in helm and restic (`helm/pkg/cmd/install.go:333-347`; `restic/cmd/restic/cleanup.go:24-38`), while opencode models explicit parent-child sessions (`opencode/internal/session/session.go:12-23`) and restic refreshes persistent locks (`restic/internal/restic/lock.go:105`). The combined evidence separates ephemeral cancellation propagation from durable operation identity: both are needed, but one cannot substitute for the other.
- **Localized structured concurrency and bounded work:** Go-task and restic use `errgroup.WithContext` for sibling cancellation (`go-task/task.go:87`; `restic/internal/repository/repository.go:567`), while k9s and gdu bound fan-out with semaphores (`k9s/internal/pool.go:26-48`; `gdu/pkg/analyze/parallel.go:13`). Run reconciliation, heartbeat, fan-out, and subscriber delivery therefore need explicit ownership, finite queues, and auditable shutdown rather than scattered goroutines.
- **Append or persist before presentation:** The reports do not provide a complete run journal implementation, but opencode demonstrates disk-backed long-session state (`opencode/internal/message/message.go:37-42`; `opencode/internal/db/connect.go:39-54`) and progressive pub/sub delivery (`opencode/internal/pubsub/broker.go:10-16`). Combined with streaming examples in lazygit (`lazygit/pkg/tasks/tasks.go:189-217`), this supports reasoning about durable state as the replay source and live delivery as a bounded projection, while leaving the concrete store undecided.
- **Bounded retention with visible loss:** Rclone caps memory through weighted semaphores (`rclone/lib/pool/pool.go:17-24,52-53`), restic excludes oversized pooled buffers (`restic/internal/archiver/buffer.go:24-46`), and opencode accepts slow-consumer event drops as a resource trade-off. The sprint must preserve the boundedness pattern but strengthen it with explicit gap, compaction, drop, and current-snapshot semantics rather than silent loss.
- **Typed failures and dual-channel diagnostics:** Rclone's behavioral error interfaces (`rclone/fs/fserrors/error.go:22-192`), restic's fatal classification (`restic/internal/errors/fatal.go:10-53`), and k9s's combined UI/log reporting (`k9s/internal/model/flash.go:100-103`) show that failures need machine-inspectable identity plus safe human guidance. Storage unavailable, replay gap, stale owner, cancelled, terminal conflict, and cleanup uncertainty should remain distinguishable in reasoning even if their eventual type hierarchy differs.
- **Correlation through structured fields:** K9s centralizes more than 50 log keys (`k9s/internal/slogs/keys.go:6-231`), dive creates component-tagged child loggers (`dive/cmd/dive/cli/internal/ui/v1/view/status.go:38`), and rclone exposes local metrics (`rclone/fs/accounting/prometheus.go:78-108`). These patterns create pressure for one correlation vocabulary spanning run, attempt, stage, task, owner, runtime, and sequence across logs, diagnostics, metrics, and optional traces.
- **Redaction at the trust boundary:** Restic's `SecretString` prevents accidental formatting (`restic/internal/options/secret_string.go:15-20`), helm scrubs authorization headers before logging (`helm/pkg/registry/transport.go:37-41`), and chezmoi bounds diagnostic byte exposure (`chezmoi/internal/chezmoilog/chezmoilog.go:238-244`). Durable event recording raises the cost of late redaction, so reasoning must identify the earliest safe normalization boundary and make unsafe payload omission inspectable without retaining the payload.
- **Layered deterministic verification:** Chezmoi and gh-cli execute real command paths through testscript (`chezmoi/internal/cmd/main_test.go:64-174`; `gh-cli/acceptance/acceptance_test.go:26-29`), while restic supplies functional backend mocks (`restic/internal/backend/mock/backend.go:14-26`) and lazygit uses PTY integration (`lazygit/pkg/integration/clients/go_test.go:81`). The sprint's race and fault matrix will need all three levels: repository/lifecycle unit tests, process-level integration, and browser/TUI behavior checks.

## Trade-Offs

| Trade-Off | Benefit | Cost | When It Matters |
| --- | --- | --- | --- |
| Centralized composition vs hidden globals | One traceable place to wire storage, ownership, clocks, process control, and observability; easy deterministic substitution (`opencode/internal/app/app.go:42-81`) | A central object can become a god object, as seen in chezmoi's large config (`chezmoi/internal/cmd/config.go:193-291`) | When introducing a cross-surface capability without moving product logic into adapters |
| Constructor injection vs context-carried services | Constructor injection is type-safe and explicit; context values reduce parameter plumbing in deep trees | Constructor chains grow; context service locators hide dependencies and can panic (`k9s/internal/keys.go:10-38`; `k9s/internal/dao/ds.go:72`) | When propagating run identity and ownership through CLI, TUI, product, and runtime layers |
| Structured `errgroup` vs independent `WaitGroup` work | `errgroup` propagates first error and cancellation; `WaitGroup` permits independent completion | Fail-fast can suppress useful sibling results; manual groups need separate error and timeout handling (`go-task/task.go:87`; `helm/pkg/kube/client.go:996`) | For heartbeat, journal append, reconciliation, fan-out, and shutdown work with different failure coupling |
| Streaming delivery vs buffered snapshots | Streaming gives immediate feedback and bounded memory (`lazygit/pkg/tasks/tasks.go:189-217`) | Ordering, reconnect, slow subscribers, and cleanup become more complex; buffered snapshots delay visibility but simplify consistency | When defining journal replay, current snapshots, SSE resume, and subscriber backpressure |
| Disk-backed state vs in-memory speed | Bounded memory and restart recovery (`opencode/internal/message/message.go:37-42`) | Write latency, locking, migration, corruption, and storage-failure policy | When selecting the run repository and event journal representation |
| Typed errors vs a small sentinel set | Typed errors carry structured recovery data; sentinels keep branching simple (`go-task/errors/errors_task.go:13-32`; `helm/pkg/storage/driver/driver.go:27-48`) | Larger type taxonomies cost API and compatibility maintenance | When exposing replay gaps, stale leases, retention, cancellation uncertainty, and terminal races to JSON and humans |
| Detailed telemetry vs data minimization | Rich correlation shortens incident diagnosis (`k9s/internal/slogs/keys.go:6-231`) | More fields increase leakage, disk, cardinality, and retention risk | When choosing default persisted event fields, support bundles, local metrics, and trace export |
| Lazy initialization vs fail-early health checks | Fast unaffected commands and surfaces (`gh-cli/pkg/cmdutil/factory.go:27-42`; `helm/pkg/action/lazyclient.go:35-53`) | First-use latency and delayed storage/config errors | When deciding whether repository health blocks all commands or only runtime-backed acceptance |
| Golden/fixture tests vs focused assertions | Golden artifacts catch contract drift and make diffs visible (`helm/internal/test/test.go:43`) | Dynamic timestamps, IDs, and concurrency can make fixtures brittle | When freezing JSON/SSE compatibility while allowing nondeterministic runtime facts |
| Explicit settings vs a minimal fixed policy | Configurable retention, limits, and intervals support varied workspaces | Precedence, migration, validation, and unsafe combinations expand (`rclone/fs/config/configmap/configmap.go:14-22`) | When deciding which operational limits are user-configurable in this sprint |

## Anti-Patterns And Warnings

- **Surface-owned lifecycle authority:** Thin-boundary evidence (`helm/pkg/cmd/install.go:132-145`; `gdu/cmd/gdu/app/app.go:30-49`) warns against letting a browser hub, TUI model, or CLI process-local map define durable run truth.
- **Global mutable registries or config:** Rclone's fallback globals and singleton cache obscure per-operation state (`rclone/fs/config.go:793`; `rclone/fs/cache/cache.go:16-21`), while global coordination limits can make unrelated work interfere (`gdu/pkg/analyze/parallel.go:13`). Avoid hidden process-local authority for runs, leases, cancellation, cursors, or limits.
- **Context as an identity store:** Context is effective for cancellation but context-carried services are implicit and runtime-typed (`k9s/internal/keys.go:10-38`). A cancelled or expired context cannot be the durable run record, owner identity, event cursor, or terminal arbiter.
- **Fire-and-forget background work:** Dive's unjoined notification goroutine (`dive/cmd/dive/cli/internal/command/adapter/resolver.go:70`) and unbounded gh-cli fan-out (`gh-cli/pkg/cmd/extension/manager.go:196-206`) demonstrate lifecycle and capacity hazards. Every heartbeat, notifier, subscriber, and reconciler needs ownership, cancellation, waiting, and limits.
- **Wait without timeout:** The concurrency report identifies indefinite `WaitGroup.Wait` as a shutdown hazard (`gh-cli/pkg/cmd/extension/manager.go:205`); cleanup and cancellation coordination must fail visibly rather than hang forever.
- **Silent loss or discard-by-default:** Dive's no-op logger can erase diagnostics if initialization is missed (`dive/internal/log/log.go:9`), and slow-consumer dropping without a durable replay contract leaves observers unable to distinguish lag from missing history. Storage failures, compaction, and subscriber drops must be explicit.
- **String-only or flattened failures:** Missing `%w` breaks cause inspection (`mitchellh-cli/cli.go:205-206`), while plain strings cannot carry cursor ranges, owner facts, or recovery actions. Avoid making all missing, expired, unauthorized, corrupt, and unavailable states look alike.
- **Mixed IO abstraction:** Direct `os.Stdout`, `os.Stderr`, filesystem, time, or network access bypasses deterministic seams (`rclone/cmd/ls/ls.go:42`; `chezmoi/internal/cmd/templatefuncs.go:296`). Fault injection will be incomplete if journal writes, clocks, process probes, or diagnostics bypass injected boundaries.
- **Late or partial redaction:** Debug output is still durable exposure. Secret scrubbing needs to precede logging, persistence, and fan-out, following the helm and restic patterns (`helm/pkg/registry/transport.go:37-41`; `restic/internal/options/secret_string.go:15-20`).
- **Unbounded journals, queues, caches, or goroutines:** The performance evidence repeatedly treats bounds as correctness, not tuning (`rclone/lib/pool/pool.go:17-24,52-53`; `k9s/internal/pool.go:26-48`). Retention and backpressure cannot be deferred as operational polish.
- **Overgeneralized plugin or workflow machinery:** The extensibility report shows formal plugin systems carry versioning, security, and lifecycle costs (`helm/internal/plugin/plugin.go:27-50`; `helm/internal/plugin/metadata.go:114-130`). A run control capability should not become a generic scheduler, plugin framework, or remote worker protocol without evidence that the sprint topology requires it.
- **Implementation-detail tests:** K9s's fixed hint-count assertion (`k9s/internal/view/pod_test.go:23`) illustrates brittle testing. Prefer lifecycle invariants and observable outcomes over exact goroutine counts, internal map shape, or incidental timing.

## Design Pressures

- The run capability must be interior to all presentation surfaces, but remain narrower than a general workflow engine. The structure, command, and DI reports favor a small domain boundary with explicit composition over a surface-owned hub or global service locator.
- Durable identity and repository state must coexist with ephemeral context cancellation. The state report shows both concerns, but none of the studied systems proves cross-process terminal arbitration or stale-writer fencing; sprint reasoning must supply that analysis.
- Owner liveness needs more than process presence. Restic's refreshable lock is relevant evidence, but the reports do not cover PID reuse, process birth identity, fencing tokens, or multi-host clocks.
- Durable event ordering must survive observer replacement while keeping live delivery bounded. Streaming and pub/sub evidence covers responsiveness and slow consumers, but not complete replay-gap or cursor-retention semantics.
- Acceptance, event append, and terminal transition failures need explicit degraded-mode behavior. Error evidence supports typed recovery and wrapped causes; it does not answer whether work stops after mid-run persistence loss.
- Read visibility and mutation authority must be separate. Security evidence supports explicit permission boundaries and session-scoped approval, but the sprint must determine which run facts are workspace-readable and what fresh authority cancellation requires.
- Retention is simultaneously a correctness, performance, and privacy boundary. Bounded-memory evidence favors finite storage, while security evidence requires redaction and log scrubbing before retention.
- Operational telemetry must remain local-first and useful across short CLI invocations and long-lived servers. The evidence strongly supports structured logs and debug controls, gives limited metrics precedent, and provides no implemented OpenTelemetry example.
- Compatibility work needs explicit schema and migration treatment. Configuration and plugin evidence shows version fields and conversion functions reduce upgrade ambiguity (`helm/internal/plugin/metadata_v1.go:24-48`; `lazygit/pkg/config/app_config.go:256-330`).
- Verification must control time, process identity, storage errors, subscriber speed, and terminal races. IO and testing reports show the seams needed; concurrency evidence shows why timing-only tests are insufficient.
- Fast workspace projections compete with durability and multi-process freshness. Lazy initialization and disk-backed state reduce startup and memory costs, but active-run reads and periodic reconciliation need bounded latency without hidden in-memory authority.
- Support diagnostics need enough correlation to explain stale ownership, replay gaps, and cancellation uncertainty without retaining prompts, provider-native payloads, credentials, or unrestricted paths.

## Open Questions For Reasoning

- Which package boundary can own run acceptance, lifecycle transitions, event append, projection, cancellation routing, and reconciliation while keeping product workflow decisions in their existing modules and interface state in adapters?
- Does the sprint require one-host multi-process semantics only, or must the repository and lease protocol tolerate hosts with independent clocks and process namespaces?
- Which durable representation best supplies atomic acceptance, monotonic per-run sequence allocation, cross-process terminal compare-and-set, bounded compaction, and repair diagnostics without unnecessary operational dependencies?
- Is direct repository access, a coordinator, or a hybrid the smallest model that supports multiple CLI/TUI/web owners and observers? What authority remains if the coordinator dies?
- What identity hierarchy distinguishes user operation, durable run, attempt, stage/task execution, owner generation, process birth, runtime run, provider session, and external smoke run?
- Which lease, heartbeat, process-birth, and fencing facts are required to classify live, stalled, interrupted, and cleanup-uncertain work conservatively? Which clocks are trusted?
- Can any active stage be adopted after owner death, or must all orphaned work be reconciled as interrupted while product-owned resume semantics remain separate?
- What is the terminal transition primitive, and how does it arbitrate success, failure, cancellation, timeout, interruption, cleanup uncertainty, storage failure, and reconciliation races across processes?
- What delivery guarantee applies between journal append and subscriber delivery? How are duplicate producer events normalized, and which cursor denotes the authoritative committed sequence?
- What snapshot, compaction, tombstone, event retention, disk quota, and cursor-expiry rules make gaps explicit while keeping run detail useful?
- What happens if persistence fails before child start, after runtime work has begun, during heartbeat, during cancellation request, or at terminal commit? Which modes fail closed, stop work, retry, or become cleanup-uncertain?
- How does authorized cancellation find and fence the current owner without relying on PID alone? What does idempotent cancellation return when the owner is stale, unreachable, or terminal already won?
- Which historical fields and sanitized events are readable across browser sessions, and which mutations require fresh session, CSRF, or command-line authority?
- How do legacy operation URLs, current JSON shapes, locks, product run state, flow state, checkpoints, and cleanup markers correlate without inventing history or transferring authority to the new repository?
- Which limits are fixed product invariants and which are configurable? If configurable, what precedence, validation, migration, and unsafe-minimum rules apply?
- Which log fields, local metrics, diagnostic commands, and support-bundle contents are mandatory? Is optional trace export worth implementing despite the selected reports containing no OpenTelemetry implementation evidence?
- Where does redaction happen, what safe omission metadata survives, and how can operators understand why data is absent without revealing the original sensitive content?
- Which deterministic fakes and process harnesses can reproduce torn writes, disk full, stale lease, PID reuse, abrupt death, subscriber lag, duplicate cancel, and terminal races under `go test -race`?
