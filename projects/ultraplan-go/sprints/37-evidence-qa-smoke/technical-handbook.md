## Relevant Patterns

- **Thin adapters over shared behavior:** The project-structure report shows command entrypoints that parse and delegate, and a `UI` interface with TUI, stdout, and report implementations. This may help reasoning keep QA and smoke behavior independent of any one presentation path. See `studies/go-cli-study/reports/final/01-project-structure.md`, "Pattern Catalog", with `helm/pkg/cmd/install.go:347`, `helm/pkg/action/install.go:73-140`, and `gdu/cmd/gdu/app/app.go:30-49`.
- **One execution wrapper for shared policy:** Rclone's `cmd.Run()` centralizes retry, statistics, and error counting for many commands. A shared wrapper can reduce policy drift, though the report does not address QA evidence semantics. See `studies/go-cli-study/reports/final/02-command-architecture.md`, "Pattern 5: cmd.Run() Wrapper for Cross-Cutting Concerns", citing `rclone/cmd/cmd.go:240-340`.
- **Visible composition root with narrow seams:** Gh-cli assembles dependencies in a central command root and exposes expensive operations as factory functions. Restic and gdu use interfaces for storage and UI boundaries. This gives isolated tests a place to substitute process, filesystem, and output behavior. See `studies/go-cli-study/reports/final/03-dependency-injection.md`, "Centralized Composition Root" and "Interface Abstraction for Core Services", citing `gh-cli/internal/ghcmd/cmd.go:52-132`, `gh-cli/pkg/cmdutil/factory.go:16-43`, `restic/internal/backend/backend.go:19-90`, and `gdu/cmd/gdu/app/app.go:31-49`.
- **Effective configuration validated once:** The configuration report finds broad agreement on explicit source precedence and post-merge validation. Most one-shot CLIs then leave configuration unchanged for the invocation. That is a useful analogue for a frozen, inspectable execution input, not evidence that it is sufficient as a QA plan. See `studies/go-cli-study/reports/final/04-configuration-management.md`, "Pattern 1", "PostLoad Validation Hook", and "Immutability After Startup", citing `chezmoi/internal/cmd/config.go:2253-2287`, `opencode/internal/config/config.go:609-641`, and `k9s/internal/ui/config.go:134-190`.
- **Typed outcomes with retained partial failures:** Typed errors and exit-code mapping let callers distinguish cancellation and operational failures. Multi-error aggregation retains failures when independent work partly succeeds. These mechanics may support truthful attempt status, but adjudication remains a separate product concern. See `studies/go-cli-study/reports/final/05-error-handling.md`, "Pattern 9" and "Pattern 10", citing `gh-cli/pkg/cmdutil/errors.go:35-41`, `gh-cli/internal/ghcmd/cmd.go:44-49`, and `restic/internal/checker/checker.go:70-91`.
- **Injectable side-effect boundaries:** Test constructors for I/O streams, filesystem interfaces, in-memory backends, and fake command runners make outputs and failures controllable. This matters for attempts that must prove where they read, write, and execute. See `studies/go-cli-study/reports/final/06-io-abstraction.md`, "IOStreams with Test Constructor" and "Backend Interface for Network/Storage", citing `gh-cli/pkg/iostreams/iostreams.go:551-568`, `restic/internal/fs/interface.go:10-31`, and `restic/internal/backend/mem/mem_backend.go:52-255`.
- **Root cancellation with bounded cleanup:** Signal-derived root contexts and `errgroup.WithContext` propagate cancellation across active work. Restic shows cleanup with a lifetime separate from the cancelled operation. Reasoning must still define the bound and the truth recorded when cleanup cannot be proven. See `studies/go-cli-study/reports/final/07-state-context.md`, "Signal-Context Wiring", "errgroup for Structured Concurrency", and practical tip 6, citing `helm/pkg/cmd/install.go:333-347`, `restic/cmd/restic/cmd_backup.go:627`, and `restic/internal/restic/lock.go:290-305`.
- **Bounded fan-out and explicit shutdown:** Semaphores and worker pools cap active work. Explicit shutdown combines cancellation, waiting, and timeout, while `sync.Once` prevents duplicate cleanup calls. This supports finite attempts without proving that concurrent writable attempts are isolated. See `studies/go-cli-study/reports/final/08-concurrency.md`, "Semaphore via Buffered Channel", "Deferred Cancel + Explicit Wait with Timeout", and "sync.Once for One-time Cleanup", citing `gdu/pkg/analyze/parallel.go:13,36`, `opencode/root.go:261-279`, and `lazygit/tasks.go:122`.
- **TTY-aware human output with automation fallback:** Mature terminal tools detect terminal capabilities and retain a line-based or non-TTY path. Long work can stream progress, but redirected output needs an independent, durable result rather than relying on an animation. See `studies/go-cli-study/reports/final/09-terminal-ux.md`, "Non-TTY Fallback" and "Progressive Streaming with Interruptibility", citing `internal/cmd/prompt.go:124-137`, `iostreams/iostreams.go:514-516`, and `lazygit/pkg/tasks/tasks.go:31-435`.
- **Separate user output, diagnostics, and retained records:** Structured logging and output interfaces keep machine diagnostics separate from stable stdout. File-backed logs aid post-mortem inspection, but they are operational records rather than adjudicated QA evidence. See `studies/go-cli-study/reports/final/10-logging-observability.md`, "Standard Library slog", "Output Interface Abstraction", and "Component-Tagged Loggers", citing `internal/logging/logging.go:31-71`, `internal/output/output.go:12-14`, and `internal/logging/logger.go:25-62`.
- **Layered deterministic verification:** Golden outputs protect stable presentation, temporary or virtual filesystems isolate fixtures, functional mocks inject failures, and true command tests cover behavior omitted by library tests. The layers answer different questions and should not be collapsed into one test style. See `studies/go-cli-study/reports/final/11-testing-strategy.md`, "Golden File Regression Prevention", "Virtual Filesystem Isolation", and "CLI Integration Depth", citing `dive/cmd/dive/cli/testdata/snapshots/cli_build_test.snap:1`, `chezmoi/internal/chezmoitest/chezmoitest.go:86-92`, and `gh-cli/acceptance/acceptance_test.go:26-29`.
- **Narrow extension contracts:** Configuration-defined extension points and formal interfaces constrain what an extension can do. Subprocesses isolate crashes and ABI concerns, but they still need explicit permissions, timeouts, environment, and path controls. See `studies/go-cli-study/reports/final/12-extensibility.md`, "Configuration-Driven Extension Without Code" and "Subprocess Plugin Isolation", citing `k9s/internal/config/plugin.go:53-67` and `helm/internal/plugin/runtime_subprocess.go:65-79`.
- **Explicit process and secret boundaries:** Argument arrays avoid shell interpretation, executable resolution checks reduce PATH attacks, and secret-aware types or scrubbers prevent accidental formatting. These are useful mechanics for evidence commands and persisted diagnostics. See `studies/go-cli-study/reports/final/13-security.md`, "Shell-Safe Argument Construction", "Secret Redaction Type", and "Credential Scrubbing in Logs", citing `lazygit/cmd_obj_builder.go:38`, `gh-cli/pkg/surveyext/editor_manual.go:23`, `restic/internal/options/secret_string.go:15-20`, and `helm/pkg/registry/transport.go:37-41`.
- **Streaming with finite resource ownership:** Line, event, chunk, and document streaming avoid full-result accumulation. Bounded channels and buffer pools cap active resource use. This is relevant to generated output and progress, but slow-consumer loss and chunk-boundary errors must remain visible. See `studies/go-cli-study/reports/final/14-performance.md`, "Streaming via Channels and bufio" and "Concurrency Bounding via Semaphore Channels", citing `lazygit/pkg/tasks/tasks.go:189-217`, `opencode/internal/llm/provider/provider.go:56`, `restic/internal/archiver/file_saver.go:56-58`, and `rclone/lib/pool/pool.go:17-24,52-53`.

## Anti-Patterns And Warnings

- **Do not treat subprocess separation as containment:** The extensibility and security reports show that subprocesses can inherit the user's environment and permissions. A child process boundary alone does not prove target immutability, path containment, resource bounds, or descendant cleanup. See `studies/go-cli-study/reports/final/12-extensibility.md`, "Subprocess Plugin Isolation", and `studies/go-cli-study/reports/final/13-security.md`, "Trust Boundary Visibility".
- **Do not construct evidence commands with shell-interpreted strings:** String concatenation turns arguments into syntax and expands the injection boundary. Use explicit executable and argument representations at the process seam. See `studies/go-cli-study/reports/final/13-security.md`, "Shell-Safe Argument Construction", citing `lazygit/cmd_obj_builder.go:38` and `restic/internal/backend/shell_split.go:45-76`.
- **Do not infer path safety from a textual prefix:** The security report flags raw path comparison without canonicalization and provides no symlink-complete isolation pattern. Sprint reasoning must not claim that the selected reports solve path and symlink escape. See `studies/go-cli-study/reports/final/13-security.md`, "Anti-Patterns / Caution Signs", citing `gdu/internal/common/ignore.go:16-37`.
- **Do not let global mutable state cross attempt boundaries:** Global config, caches, hooks, and semaphores can retain stale values or let one workload starve another. See `studies/go-cli-study/reports/final/01-project-structure.md`, "Global Configuration Registry"; `studies/go-cli-study/reports/final/03-dependency-injection.md`, "Singleton Cache Pollution"; and `studies/go-cli-study/reports/final/08-concurrency.md`, "WaitGroup + Semaphore".
- **Do not assume cancellation implies cleanup:** Context cancellation only reaches code that observes the context. `sync.Once` guarantees one cleanup call, not successful cleanup, and an unbounded `Wait()` can hang. See `studies/go-cli-study/reports/final/07-state-context.md`, "Context Background in Long-Running Operations", and `studies/go-cli-study/reports/final/08-concurrency.md`, "Cleanup Models", citing `gh-cli/manager.go:205`.
- **Do not hide operational detail inside stable stdout:** Debug text on stdout breaks scripts, while TTY-only progress disappears under redirection. Stable machine results, live diagnostics, and retained evidence need distinct channels. See `studies/go-cli-study/reports/final/09-terminal-ux.md`, "Non-TTY Fallback", and `studies/go-cli-study/reports/final/10-logging-observability.md`, "Output Separation Strategies".
- **Do not equate a log with adjudicated evidence:** File-backed and structured logs improve diagnosis, but the observability report does not supply evidence identity, sufficiency, freshness, or promotion rules. Those remain product decisions. See `studies/go-cli-study/reports/final/10-logging-observability.md`, "File-Based Debug Logging" and "Notable Absences".
- **Do not allow an investigator, command exit, or generated test to promote its own claim:** The error and testing reports explain classification and behavioral checks, not product-owned adjudication. Their patterns cannot establish evidence sufficiency by themselves. See `studies/go-cli-study/reports/final/05-error-handling.md`, "Error Taxonomy", and `studies/go-cli-study/reports/final/11-testing-strategy.md`, "Behavior vs Implementation Testing".
- **Do not add unbounded fan-out or accumulation:** `errgroup` without a limit, goroutine-per-item patterns, unbounded queues, and all-at-once output can exhaust resources. See `studies/go-cli-study/reports/final/08-concurrency.md`, "Unbounded errgroup", and `studies/go-cli-study/reports/final/14-performance.md`, "Anti-Patterns / Caution Signs".
- **Do not split meaningful command behavior between unrelated CLI and TUI systems:** The command-architecture report identifies this as a parity gap. A second smoke or QA path would make equivalent operation difficult to prove. See `studies/go-cli-study/reports/final/02-command-architecture.md`, "Bifurcated CLI/TUI Pattern", citing `k9s/cmd/root.go:76` and `k9s/internal/view/cmd/interpreter.go:62-86`.
- **Do not regenerate goldens casually:** Golden files are useful only when reviewers can explain each change. Dynamic IDs, timestamps, and reordered records can turn them into noise or let defects pass during bulk updates. See `studies/go-cli-study/reports/final/11-testing-strategy.md`, "Golden files vs inline assertions".
- **Do not add speculative pooling or plugin systems:** Buffer pools add contention and lifecycle complexity, while plugin systems add discovery and trust problems. Neither report provides a need for a new general framework in this sprint. See `studies/go-cli-study/reports/final/12-extensibility.md`, "Patterns to Avoid or Delay", and `studies/go-cli-study/reports/final/14-performance.md`, "Buffer Pooling with sync.Pool".

## Design Pressures

- Sprint reasoning must separate generic isolation and process mechanics from QA evidence, adjudication, issue, and assessment semantics. The selected reports favor thin boundaries and narrow interfaces, but they do not identify the ownership split for this product.
- A writable attempt needs reproducible inputs and finite limits. Configuration immutability is a useful analogue, but a frozen evidence plan needs sprint-specific identity, expectation, and approval rules that the reports do not define.
- Cancellation has two outcomes to represent: work stopped, and cleanup proven. The context and concurrency reports show why one does not imply the other.
- Cross-surface agreement needs one typed product result and separate renderers. Terminal progress, JSON, logs, HTML, Markdown, and durable state have different retention and formatting needs.
- Generated evidence may be large or hostile. Streaming and output caps control resources, while secret-safe and escaped presentation paths control exposure. Truncation must remain explicit.
- Smoke compatibility puts pressure on the design to reuse one discovery and execution authority. The command-architecture report's CLI/TUI split is a concrete warning against parallel behavior paths.
- Deterministic offline tests need controllable filesystem, process, runtime, clock-like, and output seams. Real process and harness checks answer different questions and should remain gated.
- Writable concurrency cannot be justified by worker-pool evidence alone. Reasoning needs direct proof of workspace independence, process containment, cleanup, and target identity before raising concurrency.
- Durable evidence needs stable identity, atomic publication, freshness, and recovery semantics. The selected reports cover logs, fixtures, and persistence examples but not this artifact graph.
- Adjudication must remain stronger than error classification. Typed failures and test outcomes are inputs; the reports contain no basis for letting them set canonical QA assessment directly.
- Security claims need explicit negative evidence. The reports offer argv, permission, and redaction patterns, but no complete symlink-safe local workspace isolation design.
- The sprint must remain bounded. The extensibility report warns that new plugin or registry frameworks bring collision and trust costs, while the performance report warns against speculative resource machinery without measured need.

## Open Questions For Reasoning

- What exact immutable data forms an evidence plan, and at what point does an attempt freeze it?
- Which component proves target identity, workspace containment, writable-path policy, descendant cleanup, and post-run target immutability?
- How should the product distinguish `cancelled`, `timed_out`, `blocked`, `failed`, and `cleanup_uncertain` across typed app results, exit codes, JSON, durable state, and human reports?
- Which attempt results survive fail-fast cancellation, and how are incomplete sibling results represented without overstating their evidentiary value?
- What finite defaults and hard maxima apply to attempts, commands, output, retained patches, storage, duration, retries, follow-up, progress, and issue records?
- What evidence proves writable attempts can run concurrently? Until that proof exists, where is sequential execution enforced?
- How does one shared smoke execution path preserve the existing `smoke` command while also serving `qa --suite smoke` without a second discovery, invocation, or verdict path?
- Which typed use-case result is authoritative for CLI text and JSON, TUI, browser HTML and JSON, durable run inspection, `qa.md`, and verification-state projections?
- What is the publication order for generated patches, evidence records, adjudication, issues, state pointers, and `qa.md`, and how does recovery preserve the last complete current report?
- How are logs and progress correlated to an attempt while remaining distinct from evidence accepted by adjudication?
