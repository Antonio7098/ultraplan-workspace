## Sprint Technical Handbook Summary

- **Relevant Patterns:** Keep policy and orchestration with the owning product module; put thin commands over shared operations; inject volatile dependencies; separate governed values from operational settings; validate complete inputs before freezing identity; represent verdicts as typed facts; run external work through explicit bounded requests; propagate one cancellation lineage with a separate bounded cleanup context; bound execution and retained data; profile one proven miss before optimizing; project one bounded fact model to every interface; test isolation, recovery, fencing, and promotion rather than arithmetic alone.
- **Important Trade-Offs:** Serial measurement costs time but avoids self-inflicted noise. Rich immutable private evidence improves audit and recovery but requires digest-bound summary publication. Closed descriptors delay extension but prevent runtime-authored execution authority. Lazy runtime construction keeps disabled status and dry-run cheap but requires complete admission before acceptance. Shared fencing mechanics reduce duplicated ownership logic while separate QA and performance stores preserve product meaning.
- **Warnings / Anti-Patterns:** No shell strings, runtime-selected commands, package-global current-run state, context service locators, eager runtime work in status or dry-run, unbounded goroutines or output, direct presenter filesystem reads, panic or prose-only failures, warning-only duplicate registration, speculative pooling or parallelism, benchmark/test weakening, or UI verdicts inferred from events.
- **Evidence Confidence:** High for package, process, cancellation, configuration, persistence, interface, and testing patterns because the selected reports cite concrete mature Go CLI implementations. Medium for UI and extension details. The reports do not define a complete statistical policy, so the measurement constants below are a Sprint 39 product decision constrained by AC-5 and Aren's baseline-first performance guidance.

## Decisions

### Decision 1: Activation and target authority are strict and separate

- **Decision:** `internal/project` will parse only an optional real `## Performance Policy` section containing exactly one `- **Mode:** disabled|enabled` field. Missing means `disabled`. Duplicate sections, duplicate `Mode`, unknown keys, invalid values, and any target-like field fail project validation. `internal/sprint` will parse targets only from a real level-two `## Performance Targets` heading and its immediately associated table. A Markdown-aware scanner will exclude fenced code, inline-code pseudo-headings, HTML comments, blockquotes, and other sections. The header must be the exact ordered nine-column V1 header. Enabled policy requires one to 100 usable rows; disabled policy plus a target table is a mismatch error. `ID` accepts only uppercase ASCII letters, digits, and hyphens after the exact `PERF-` prefix. Scenario is trimmed valid UTF-8 of 1 to 256 bytes; Metric is trimmed valid UTF-8 of 1 to 128 bytes. Cell keywords and units are exact and case-sensitive. Decimal targets use a finite base-10 grammar without exponent notation, normalize `+0`, `-0`, leading zeros, and trailing fractional zeros to canonical text, and retain exact rational form for threshold comparison. Rows sort by bytewise target ID. The packet binds the exact requirements digest, project-policy digest, parser version, normalized rows, and packet digest. No other source can alter membership or values.
- **Rationale:** Activation and target values have different owners and different change cadence. Joining typed policy and parsed requirements at the sprint service boundary reports policy disagreement without turning project configuration into a target source. Strict Markdown context is necessary because a fenced example that looks like a target is not an executable commitment. Canonical decimal text and exact rational thresholds make packet digests and equality comparisons stable.
- **Study / Source Grounding:** `technical-handbook.md` sections "Separate governed values from operational settings" and "Validate after complete parsing, then freeze identity" draw on chezmoi precedence restoration and k9s schema validation. `04-configuration-management`, `12-extensibility`, and `13-security` support post-merge validation, versioned closed schemas, and fail-closed boundary parsing. The exact table semantics come from `requirements.md`, not from a study repository.
- **Trade-Offs Accepted:** The parser is intentionally less forgiving than general Markdown. Cosmetic edits to governed bytes change freshness even when normalized rows do not. That cost is acceptable because the packet records both source identity and normalized meaning.
- **Technical Debt / Future Impact:** The product owns fixed text and row bounds and a V1 decimal normalizer. A later schema may add units or fields only through an explicit parser version and migration decision. Project policy remains unable to gain target fields through ordinary config evolution.
- **Alternatives Rejected:** A full-document regular expression was rejected because it can accept examples, comments, and quoted content. A permissive table parser was rejected because unknown or reordered columns can silently change meaning. Float-only target normalization was rejected because binary representation makes canonical digests and boundary equality harder to audit. Target values in project config, environment, flags, runtime output, benchmark files, or prior baselines were rejected by AC-2.
- **Contracts Satisfied:** Architecture, Configuration, Security, Errors, Testing, Documentation; AC-1, AC-2, AC-7, AC-9.
- **Evidence Required:** Table-driven project policy tests; hostile Markdown fixtures for fences, comments, blockquotes, inline code, duplicate headings, table association, exact headers, row bounds, UTF-8/text bounds, all cell combinations, non-finite/exponent values, duplicates, and stable ordering; golden packet and digest fixtures; disabled-policy mismatch guidance; tests proving every alternate target source is ignored or rejected.

### Decision 2: Performance is an optional verification phase with runtime-free admission

- **Technical Debt / Future Impact:** The optional flow-state performance projection adds migration and status branches. Old schema versions must decode with no user migration and semantic disabled behavior. No compatibility alias is added to the planning-stage enum.
- **Alternatives Rejected:** A planning stage was rejected because performance is conditional verification and may mutate implementation after execute. Always creating disabled state was rejected because AC-1 requires byte-preserving compatibility. - **Study / Source Grounding:** `12-extensibility` uses helm's versioned metadata as a positive example and rclone's overwrite-prone registry as a warning. `13-security` supports explicit argv and strict schema validation. ### Decision 4: Qualification uses one complete median sample set and exact product comparisons

- **Decision:** Each target receives two product-owned warmups by default, then exactly its requirements-owned measured sample count. The fixed target sample range is 5 through 100. Warmups and samples execute serially, one command at a time, and retain bounded raw numeric and output facts before aggregation. V1 aggregation is the median; for an even count it is the exact arithmetic midpoint of the two central exact decimal values. Qualification also records arithmetic mean, sample standard deviation with `n-1`, and coefficient of variation `100 * sample_standard_deviation / abs(mean)`. A set qualifies when every expected sample parses exactly once with matching target, scenario, metric, unit, command, benchmark, target-packet, and compatible stable environment identities, cleanup is proven, and CV is at or below the effective threshold. If all values and the mean are zero, CV is zero. A zero mean with any nonzero sample is inconclusive. No sample is deleted as an outlier and no second set is selected because it passes. Missing, duplicate, ambiguous, non-finite, overflowed, wrong-identity, wrong-unit, truncated, drifted, or noisy data is `inconclusive` unless a broken frozen authority or unsafe cleanup makes it `blocked`. Dynamic thermal or resource detectors are product-owned and versioned; an available detector reporting instability makes the set inconclusive, while an unavailable optional detector is recorded as unavailable and does not itself create a pass or failure.
- **Rationale:** Median resists a single extreme value, while CV records whether the full sample set is stable enough to compare. Keeping every sample avoids data-dependent curation. Exact decimal medians and threshold rationals make inclusive boundaries auditable. The policy screens noise; it does not claim statistical significance.
- **Study / Source Grounding:** `08-concurrency` and `14-performance` support bounded work and warn that throughput-oriented concurrency can contaminate measurement. Aren's performance guidance requires repeatable baselines and variance qualification. `technical-handbook.md` explicitly says the studies do not provide a complete statistical model, so the formula and constants are product decisions constrained by AC-5.
- **Trade-Offs Accepted:** A single noisy set can block a run and requires a new attempt after the environment is fixed. Median can hide the magnitude of tails, so raw bounded samples and dispersion remain inspectable. Serial sampling increases wall time.
- **Technical Debt / Future Impact:** Qualification records `aggregation_version: median-v1` and `qualification_version: cv-v1`. A later estimator must use a new version and cannot reinterpret old results. V1 makes no confidence-interval, percentile, normality, or significance claim.
- **Alternatives Rejected:** Arithmetic mean as the sole aggregate was rejected because one extreme sample can dominate. Automatic outlier removal and repeated sampling until one set qualifies were rejected because they can manufacture a pass. Parallel target samples were rejected because product-created contention weakens comparability. Treating parser or environment uncertainty as a miss or pass was rejected because the numeric claim is unproven.
- **Contracts Satisfied:** Performance, Security, Errors, Observability, Testing, Workflows; AC-4, AC-5, AC-8, AC-11.
- **Evidence Required:** Pure fixtures for odd/even median, exact decimals, equality, negative values, all-zero and mixed zero mean, sample deviation and CV boundary; every malformed and identity mismatch case; noisy and dynamic-instability fixtures; process output truncation and cleanup tests; serial-execution assertion; independent recalculation during sprint review.

The V1 comparison and outcome rules are fixed as follows:

| Target form | Numeric fact | Target outcome |
| --- | --- | --- |
| `<=` or `>=`, `Basis=absolute`, `Gate=required` | Compare qualified final median directly with exact `Value`; equality passes. | `met` or `missed`; failed qualification is `inconclusive` or `blocked`. |
| `<=` or `>=`, `Basis=baseline`, `Gate=required` | Compute exact `100 * (final_median - baseline_median) / baseline_median`; equality passes; raw units must match. | `met` or `missed`; zero/non-finite baseline or failed qualification is `inconclusive` or `blocked`. |
| Threshold comparator with `Gate=report` | Compute the same met/missed comparison fact, but do not turn it into a blocking target verdict. | `report_only`; failed qualification remains `inconclusive` or `blocked` and is non-blocking at target-gate level. |
| `Comparator=baseline`, `Basis=current`, `Gate=report` | Record the qualified final current median. Preserve the initial baseline separately if implementation changed. | `baseline_recorded`; failed qualification is `inconclusive` or `blocked` and is non-blocking at target-gate level. |

Baseline measures every target against the frozen manifest. Final measurement measures every target again against the final canonical implementation, including a no-change run. This avoids presenting the initial baseline as an independently confirmed final value. Product code derives all facts; runtime prose and prior artifacts cannot set an outcome.

Run outcome precedence is also fixed:

| Precedence | Condition | Run outcome |
| ---: | --- | --- |
| 1 | Owned descendants or disposable-copy cleanup cannot be proven after terminal or cancellation handling. | `cleanup_uncertain` |
| 2 | Durable cancellation wins terminal arbitration and cleanup is proven. | `cancelled` |
| 3 | Current authority, persistence, correctness, required qualification, isolation, or recovery is blocked or inconsistent. | `blocked` |
| 4 | Optimization cannot reach its next proven boundary because no-progress or proposal/runtime limits are exhausted before the planned final convergence path. | `stalled` |
| 5 | Final qualified current evidence contains at least one required miss after allowed work ends or optimization is not authorized. | `target_missed` |
| 6 | Every required target is current, qualified, and met; final correctness and cleanup pass; at least one report or baseline target is retained. | `passed_with_reports` |
| 7 | Every target is required and met, with current identities, final correctness, and proven cleanup. | `passed` |

### Decision 5: Optimization is one-miss-at-a-time, isolated, and correctness-first

- **Decision:** Optimization begins only after a qualified baseline shows a required miss. V1 does not expose report-target optimization; report comparison facts remain visible for a later governed selector. Required misses are considered in stable target-ID order. Each cycle selects one miss, captures one bounded product-selected profile, records one target-linked hypothesis, and asks for one structured proposal in a fresh disposable copy based on the current accepted implementation identity. V1 selects a memory profile for `B/op`, `allocs/op`, and `MiB`; it selects a CPU profile for `ns/op`, `ms`, `ops/s`, `tasks/run`, and `%`, using product-built Go test flags and bounded profile files. Optimization patches may change only contained production source under the execute target. They cannot touch requirements, policy, planning artifacts, benchmark/test files, test helpers, fixtures, expected outputs, generated snapshots, parser or performance code that owns authority, correctness policy, configuration, evidence, review/QA/smoke/repair artifacts, repository-control files, Git metadata, symlinks, hard links, or unapproved generated files. Before a candidate can be considered, product code verifies source identity, patch syntax, actual diff, path/file/byte limits, no unrelated overlap, cleanup, and the full frozen correctness command set. The selected target must have a qualified strict improvement in its comparator's passing direction under the frozen benchmark. Equality is not improvement. Every already-met required target is remeasured and must remain qualified and met. Product code writes and syncs an apply journal, rechecks canonical identity immediately before apply, applies through the existing mutation boundary, verifies the resulting identity, and invalidates downstream verification. A rejected candidate never changes canonical bytes.
- **Rationale:** Performance proposals are hostile until containment, correctness, and measured effect are proven. One symptom, profile, hypothesis, and proposal keeps attribution reviewable. Correctness runs first because faster incorrect behavior is failure, and already-met targets protect against trading one commitment for another.
- **Study / Source Grounding:** `14-performance` points to fzf slab reuse and restic bounded pools as profile-backed changes rather than generic tuning. `07-state-context`, `08-concurrency`, and `13-security` support owned cancellation, bounded work, explicit argv, and contained temporary state. Aren's performance guidance requires profile-led optimization and correctness after each change.
- **Trade-Offs Accepted:** Full correctness and required-target remeasurement make each candidate expensive. Strict aggregate improvement can accept a small qualified gain without a significance claim, but the CV gate and final full measurement prevent unqualified promotion. Broad refactors and report-only tuning are intentionally excluded.
- **Technical Debt / Future Impact:** Profile selection is a simple unit-to-profile map. Sprint 40 may show a need for trace or block profiles, but any addition remains product-owned. Report-target optimization needs a separate explicit selector and cost policy.
- **Alternatives Rejected:** Runtime writes to the canonical worktree, direct patch apply, test or fixture edits, correctness command changes, benchmark edits after baseline, acceptance on runtime prose, target relaxation, multi-target redesign, and automatic snapshot regeneration were rejected. Measuring before correctness was rejected because it spends benchmark work on an invalid candidate and risks promoting false gains.
- **Contracts Satisfied:** Security, Workflows, Performance, LLM Runtime, LLM Evaluation / Cost / Safety, Persistence And Migrations, Testing; AC-4, AC-6, AC-7, AC-8, AC-9.
- **Evidence Required:** Fresh-copy-per-cycle tests; deterministic profile selection and bounds; protected-path and diff adversaries; overlapping user-change preservation; full correctness-before-measure ordering; a faster functional regression rejection; strict improvement and already-met regression fixtures; apply-journal crash injection before and after mutation; stale downstream fingerprint checks; cycle convergence and exhaustion outcomes.

A lower requirements sample ceiling blocks admission with both values rather than reducing `Samples`. Effective values, source, frozen deadline, and consumed counters persist in the attempt and never reset on resume. All byte limits count captured or proposed bytes before truncation; truncation remains explicit and cannot qualify a sample.
- **Rationale:** Finite budgets make cancellation, recovery, cost, and retention testable. Separating the ordinary default from the hard maximum allows conservative operation now while protecting internal paths from oversized state. Lower-only resolution cannot become target relaxation.
- **Study / Source Grounding:** `04-configuration-management` shows why source precedence must preserve explicit intent. `08-concurrency`, `12-extensibility`, `13-security`, and `14-performance` support finite workers, timeouts, outputs, private data, and retained evidence. - **Trade-Offs Accepted:** Some legitimate slow workloads will block or stall under defaults and require a new attempt with code-level policy evolution, not an upward local override. Conservative limits reduce autonomous optimization breadth.
- **Technical Debt / Future Impact:** Sprint 40 should record actual consumption and may lower defaults. Raising a built-in default or adding a limit source is a governed product change. Public DTOs report effective and consumed values but not secret config material.
- **Alternatives Rejected:** Unlimited controls, resume-time reset, caller-selected higher limits, silent sample reduction, and model-selected budgets were rejected. Treating truncation as valid output was rejected because missing bytes can hide ambiguity.
